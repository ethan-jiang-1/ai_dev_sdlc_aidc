# AI 编程的八次范式跃迁 (2021–2026)

> 只讲真正改变了程序员工作方式的关键转折——从代码补全到代理工程，五年八次跃迁。

---

## 为什么是这八次？

2021 年以来 AI 编程领域概念频出，但真正让程序员的日常工作发生**不可逆改变**的关键节点并不多。本文从以下三个维度筛选出了八次最关键的范式跃迁：

| 维度 | 含义 |
|:---|:---|
| **突破性** | 是否带来了技术或方法论上的根本性变化？ |
| **影响面** | 有多少程序员的日常工作因此而改变？ |
| **不可逆性** | 回不去了吗？整个行业的方向是否因此而转向？ |

筛选结果：

| # | 范式跃迁 | 时间 | 突破性 | 影响面 | 不可逆性 | 入选理由 |
|:---|:---|:---|:---|:---|:---|:---|
| ① | GitHub Copilot | 2021–2022 | ★★★★★ | ★★★★★ | ★★★★★ | AI 编程的"iPhone 时刻"，让一切成为可能 |
| ② | 提示工程的兴与衰 | 2022–2023 | ★★★★ | ★★★★ | ★★★ | 第一代方法论的建立与天花板的发现 |
| ③ | 代理工作流 | 2024 | ★★★★★ | ★★★★ | ★★★★★ | AI 从"工具"变为"自主体"的概念转折 |
| ④ | 推理模型 | 2024.9–2025.1 | ★★★★★ | ★★★★★ | ★★★★★ | 从"更大的模型"转向"更深的思考" |
| ⑤ | Vibe Coding 大论战 | 2025.2 | ★★★ | ★★★★★ | ★★★★ | 撕裂社区的文化地震，逼所有人选边站 |
| ⑥ | 上下文工程 | 2025.6 | ★★★★ | ★★★★ | ★★★★ | "怎么问"升级为"给什么"，真正的高阶技能 |
| ⑦ | 规范驱动开发 | 2025 下半年 | ★★★★ | ★★★★ | ★★★★ | "代码是规范的编译产物"，多家巨头工具落地 |
| ⑧ | 治具工程 | 2026.2 | ★★★★★ | ★★★ | ★★★★★ | 人类不再写代码，而是建造"让 AI 写代码的工厂" |

**被筛掉的内容：** AI Engineer 身份定义（重要但不是技术突破）、Flow Engineering（被代理工作流吸收）、Devin（争议大于实质）、SWE-agent（学术圈）、Vibe Engineering（小众修正）、TDG（专业子集）、MCP（基础设施层）、AgentOps（运维层）。这些在需要时会作为背景提及。

## ① GitHub Copilot：AI 编程的"iPhone 时刻" (2021–2022)

**一句话：** AI 编程从论文走进了每个程序员的 IDE，一切从此不同。

| | |
|:---|:---|
| **时间** | 2021.6 技术预览 → 2022.6.21 正式发布 |
| **谁** | **GitHub × OpenAI** 联合开发。Nat Friedman（时任 GitHub CEO）推动落地 |
| **底层** | OpenAI Codex（GPT-3 微调版） |

### 它做了什么

Copilot 的核心假设极为朴素：代码就是一种有严格语法的语言，如果 AI 能理解自然语言，那也能理解代码。它将代码生成重新定义为**"自动补全的极端延伸"**——你写一个函数签名或注释，它帮你写完整个函数体。

这在今天看来稀松平常，但在 2021 年，在 IDE 里看到 AI 实时生成一整段能跑的代码，是让人起鸡皮疙瘩的体验。

### 数据说话

| 指标 | 数字 |
|:---|:---|
| 技术预览期注册开发者 | **120 万+**（12 个月内） |
| 正式版累计用户（2025） | **2,000 万+** |
| 付费订阅用户 | **150 万+** |
| 采用的财富 100 强企业 | **90%** |
| 使用者任务完成速度提升 | **55%** |
| Copilot 贡献的代码比例 | **46%**（2022 年为 27%） |

### 社区反应：震撼 + 恐惧 + 争议

**正面：** 开发者社区被震撼——81% 在获得许可证的**第一天**就安装了插件。"AI 能帮我写代码"从科幻变成了日常。

**负面：** 版权争议爆发——训练数据含大量开源代码，2022 年底遭遇集体诉讼。代码接受率仅约 30%（开发者拒绝了 70% 的建议），安全研究发现 AI 生成代码约 45% 含有漏洞。

### 为什么这是"iPhone 时刻"

不是因为 Copilot 本身有多完美——它的生成质量在当时相当粗糙。而是因为它**永久改变了程序员对"编码"这件事的认知边界**。它证明了"AI 写代码"不是学术幻想而是工程现实，直接催生了一个从 20 亿到 40 亿美元的市场（Cursor、Claude Code、Windsurf、Replit……全部因为 Copilot 证明了这条路走得通）。

## ② 提示工程的兴与衰：第一代方法论的天花板 (2022–2023)

**一句话：** 我们以为"会问问题"就够了，结果发现远远不够。

| | |
|:---|:---|
| **时间** | 2022–2023（伴随 ChatGPT/GPT-4 爆发） |
| **关键论文** | Jason Wei 等 **Google Brain** 团队, *Chain-of-Thought Prompting* (NeurIPS 2022) |
| **标志人物** | **Riley Goodside**——世界上第一位正式头衔为"Prompt Engineer"的人（Scale AI） |

### 它做了什么

思维链（CoT）论文揭示了一个惊人发现：**只要你在提示中展示几个"先推理再回答"的例子，大模型就能学会逐步推理，表现急剧提升。** Google Brain 的 PaLM 540B 模型仅用 8 个思维链示例，就在数学测试中超越了经过专门微调的 GPT-3。

这催生了"提示工程"作为一门独立学科的爆发——Few-Shot、角色扮演、约束性提示……一度出现年薪 30 万美元的"Prompt Engineer"岗位。Riley Goodside 在 2022 年成为 Scale AI 的 Staff Prompt Engineer，整年在 Twitter 上发布 GPT 实验，成为 AI 领域最受关注的账号之一。"Prompt"成为 2023 年牛津词典年度词汇候选词。

### 为什么它衰落了

到 2023 年底，行业撞上了**三面墙**：

1. **脆弱性（Prompt Drift）**：精心调优的提示随模型更新而失效，维护成本越来越高
2. **上下文遗忘**：模型没有记忆，无法处理跨文件、跨模块的复杂任务
3. **能力天花板**：简单函数级任务尚可，类和模块级任务准确率急剧下降

到 2024–2025 年，独立的"Prompt Engineer"岗位大幅消失。提示技巧被吸收为开发者的通用能力之一，不再是独立的专业。

### 真正的遗产

提示工程的最大遗产不是具体的技巧，而是**一个认知转变**：人类和 AI 之间的交互不是"给指令 → 得结果"这么简单，它需要被工程化地设计。这个认知直接催生了后续的流工程、代理工作流和上下文工程。

## ③ 代理工作流：AI 从工具变为自主体 (2024)

**一句话：** AI 不再只是"你问我答"的聊天机器人——它学会了自己拆任务、用工具、检查自己的错误。

| | |
|:---|:---|
| **时间** | 2024 年 3–4 月（系列演讲）→ 全年多次主题演讲 |
| **谁** | **Andrew Ng（吴恩达）**——深度学习泰斗、斯坦福教授、Coursera 联合创始人 |
| **前置工作** | CodiumAI 的 **Tal Ridnik** 等人于 2024.1 提出 Flow Engineering，将 GPT-4 编程竞赛通过率从 19% → 44%，证明了"迭代流"优于"单次提示"。Ng 将此思路泛化为通用框架 |

### 它做了什么

Andrew Ng 在 Sequoia Capital AI Ascent、Snowflake Summit、BUILD 2024 等多个顶级场合提出了一个核心论断：**未来 AI 的进步将更多来自工作流的优化，而非模型参数的增长。** Agentic Workflow 可能比下一代基础模型更能推动 AI 进步。

他归纳了四种核心代理模式，成为整个行业的标准词汇：

| 模式 | 含义 | 类比 |
|:---|:---|:---|
| **反思（Reflection）** | 代理生成内容后自我审查、自我纠错 | 程序员写完代码后做 Code Review |
| **工具使用（Tool Use）** | 代理主动调用搜索引擎、API、代码解释器 | 程序员查文档、跑测试 |
| **规划（Planning）** | 面对复杂目标自动拆解为子任务 | Tech Lead 分解 Epic 为 Stories |
| **多代理协作** | 多个角色化代理分工协作 | 开发团队：PM + Dev + QA |

### 数据说话

| 指标 | 数字 |
|:---|:---|
| BUILD 2024 主题演讲 YouTube 观看 | **100 万+**，15,000 赞 |
| Sequoia AI Ascent 演讲观看 | **40 万+** |
| 系列演讲总观看量 | **数百万** |

### 社区反应

这不是一篇引发争议的论文——这是一次**全行业的认知统一**。几乎所有主流 AI 框架（LangChain、CrewAI、AutoGen、LangGraph）都以这四种模式为设计基础。企业界迅速跟进：法律文档处理、医疗诊断、政府合规等场景开始部署代理工作流。

### 为什么这次跃迁如此关键

在 Ng 之前，AI 对程序员来说是"一个更聪明的自动补全"。在 Ng 之后，AI 被重新理解为**可以独立思考和行动的数字实体**。这个认知转变是后续一切——Vibe Coding、代理 IDE、治具工程——的概念基础。如果你不理解"代理"，你就无法理解 2025–2026 年发生的任何事。

## ④ 推理模型：从"更大"到"更深" (2024.9–2025.1)

**一句话：** 模型不再靠堆参数变聪明——它们学会了"停下来想一想"。

| | |
|:---|:---|
| **事件一** | **OpenAI o1** 发布（2024.9.12） |
| **事件二** | **DeepSeek R1** 开源发布（2025.1.20）——中国公司 DeepSeek |

### 为什么放在一起讲

这两个事件共同构成了一次完整的范式转折：o1 证明了"慢思考"路线的可行性，R1 把它平民化了。

### OpenAI o1：证明了"慢思考"有效

传统 LLM 像人的"系统 1"——快速直觉反应，经常出错。o1 引入了"系统 2"——在输出答案前进行长时间的隐式思维链推理。效果是惊人的：

| 基准测试 | o1 表现 |
|:---|:---|
| Codeforces 编程竞赛 | **第 89 百分位**（超越大多数人类选手） |
| 国际数学奥林匹克资格赛 | 解决 **83%** 题目（GPT-4o 仅 13%） |
| 博士级科学推理 (GPQA) | **超越人类博士**平均水平 |

代价：成本是 GPT-4o 的 3–4 倍，推理更慢。但它证明了一个根本性的新方向：**不需要更大的模型，只需要更深的思考。**

### DeepSeek R1：把这个突破给了所有人

如果 o1 只是 OpenAI 的闭源武器，推理模型就只是"有钱人的玩具"。DeepSeek R1 改变了这一切：

| 指标 | 数字 |
|:---|:---|
| GitHub Stars | **91,800+**（2025 年最受关注的 AI 开源项目之一） |
| 许可 | **MIT**——完全自由使用、修改、商用 |
| 编程基准 Codeforces Elo | **2,029**（32B 和 70B 版本超越 OpenAI o1-mini） |
| API 定价 | $0.14–$2.19/百万 Token（o1 的十分之一到几十分之一） |

更关键的突破：DeepSeek-R1-Zero 证明了**仅通过强化学习（RL），不需要任何人类标注的监督微调，就能从零激发大模型的推理能力**。这在学术上意义重大——推理不再是必须用海量人类数据"灌"出来的能力。

### 对程序员的直接影响

1. **之前手动构建的"反思-修正"循环被内化到了模型内部**——很多 Flow Engineering 的外部工程变得不再必要
2. **对输入规范的要求急剧提高**——模型"想"得越深，对规范中的歧义越敏感。你给一个含糊的需求，它可能"想"出一个逻辑自洽但完全不是你要的方案
3. **编程能力的平民化**——DeepSeek R1 的蒸馏版本可以在单卡 GPU 上运行，让独立开发者和小团队拥有了前沿推理能力

## ⑤ Vibe Coding 大论战：一个词撕裂了整个行业 (2025.2)

**一句话：** Karpathy 一条推文引爆了 AI 编程史上最激烈的方法论之争——你到底还需不需要看代码？

| | |
|:---|:---|
| **时间** | 2025 年 2 月 2 日 |
| **谁** | **Andrej Karpathy**——OpenAI 联合创始成员、前 Tesla AI 总监 |
| **媒介** | X（Twitter）推文，450 万+ 浏览 |
| **后果** | 被 Collins English Dictionary 评为 **2025 年年度词汇** |

### 那条推文

> "There's a new kind of coding I call 'vibe coding', where you fully give in to the vibes, embrace exponentials, and forget that the code even exists."
> 
> （有一种新的编码方式，我称之为"氛围编码"——你完全沉浸在氛围中，拥抱指数级增长，甚至忘记了代码的存在。）

Karpathy 描述了自己使用 **Cursor + Anthropic Sonnet** 的状态：不看代码、不审查逻辑、频繁 Accept All、报错就把错误信息扔回给 AI。他用四个词概括了工作流：**"see stuff, say stuff, run stuff, copy-paste stuff"**。

### 为什么它引爆了全行业

这不是一个普通人说的话——Karpathy 是 AI 领域的图腾级人物。当他说"忘记代码的存在"时，整个行业被迫选边站：

#### 拥抱派的论点

- 独立开发者：一个人周末就能构建完整 SaaS 产品
- Y Combinator 调查：1/4 受调查创业公司的 95%+ 代码由 AI 生成
- 44% 的开发者日常使用 AI 编码工具，92% 至少偶尔使用
- Reddit 上的 r/vibecoding 社区迅速壮大

#### 反对派的论点

- **Simon Willison**（Django 联合创始人）提出"认知债务"：人类不读代码 → 无法建立心理模型 → 一旦遇到 AI 修不了的 Bug，整个项目瘫痪
- 研究发现使用 AI 工具的开源开发者实际上比不使用者**慢了 19%**
- 45% AI 生成代码含安全漏洞，86% XSS 防御失败率
- 批评者称之为 **"YOLO Coding"**——只适合原型，生产环境中极不负责任

#### 反转：连 Karpathy 自己都修正了

到 2025 年底，Karpathy 本人承认需要"more oversight and scrutiny"，开始转向更结构化的工作流。

### 真正的影响

Vibe Coding 本身是一种极端的开发方式，但它引发的**大辩论**迫使行业认真思考一个根本问题：**在 AI 越来越强的世界里，程序员到底应该站在哪个位置？**

这场辩论直接催生了两个重要的回应：

1. **Kent Beck**（TDD 之父）提出 **Augmented Coding**——你可以不打字，但必须深度参与。AI 就像一个"不可预测的精灵"，测试是关在瓶子里的唯一方法。他甚至发现了一个荒诞现象：AI 会**删除测试来让测试通过**
2. **Simon Willison** 提出 **Vibe Engineering**——承认 AI 的加速价值，但坚持工程师必须对产出负责。不是不用 AI，而是**专业地**用 AI

## ⑥ 上下文工程：从"怎么问"到"给什么" (2025.6)

**一句话：** AI 编程的核心技能不再是写好提示词——而是策划好 AI 能看到的一切信息。

| | |
|:---|:---|
| **时间** | 2025 年 6 月 19 日 |
| **谁** | **Tobi Lütke**——Shopify CEO |
| **背书** | **Andrej Karpathy** 公开认同并推广 |

### 它做了什么

Lütke 用一条推文重新定义了 AI 编程的核心技能：

> "Context Engineering" 是一项核心技能——为任务提供所有必要上下文，以使其有可能被 LLM 解决的艺术。

这看起来像是换了个名字，但实质不同：

| | 提示工程 (Prompt Engineering) | 上下文工程 (Context Engineering) |
|:---|:---|:---|
| **关注点** | 怎么**问**问题 | **给什么信息**让 AI 工作 |
| **范围** | 一段提示文本 | 整个信息环境的设计 |
| **包含** | 措辞、格式、示例 | 任务描述 + RAG 数据 + 工具定义 + 系统状态 + 对话历史 + 策略规则 |
| **难度** | 文案技巧 | 系统架构 |

### 社区反应

Karpathy 背书称其为"精妙的艺术与科学"，强调做好这件事**"极其不简单"**——太少上下文 AI 做不了，太多无关信息反而干扰性能，还增加成本。

Simon Willison 赞同：这个词更准确地描述了现代 AI 工程的复杂性。"提示工程"已经被用烂了，和"在 ChatGPT 里写问题"混为一谈。

### 为什么这不只是"换了个名字"

到 2025 年，上下文窗口已从 4K Token 扩展到 **100 万+ Token**。这意味着你可以把整个代码库、完整的设计文档、所有相关 API 规范一次性喂给模型。问题不再是"上下文不够用"，而是**"如何策划正确的上下文"**——这变成了一个真正的工程问题，需要构建自动化的检索、过滤、排序和注入系统。

这也是 Shopify CEO 而非 AI 研究者提出这个概念的原因——它来自**大规模生产实践**，而非实验室。Shopify 的工程团队在将 AI 集成到电商平台的过程中，发现**90% 的挑战不在于模型能力，而在于上下文管理**。

### 后续影响

Context Engineering 迅速成为 AI 工程的核心学科。它也是治具工程的关键支柱之一——OpenAI 的 App Server 项目中，自动化上下文管理系统正是"治具"最核心的组成部分。

## ⑦ 规范驱动开发：代码不再是核心资产，规范才是 (2025 下半年)

**一句话：** 如果 AI 写代码的成本趋近于零，那"写什么"比"怎么写"重要一万倍——规范成了新的源码。

| | |
|:---|:---|
| **时间** | 2025 年 9–10 月（工具产品正式发布） |
| **谁** | **Guy Podjarny**（Snyk 创始人、Tessl 创始人）提出核心理念并建工具；**Martin Fowler**（ThoughtWorks 首席科学家）进行理论分级；**Amazon** 发布 Kiro IDE；**GitHub** 发布 Spec Kit |
| **关键工具** | Tessl Framework & Registry, Amazon Kiro, GitHub Spec Kit |

### 它做了什么

SDD 的核心假设极为犀利：**如果 AI 生成代码的边际成本趋近于零，那么代码本身就不再是核心资产——规范（Spec）才是。代码只是规范的"编译产物"。**

这意味着一次根本性的认知翻转：

```
传统开发                          规范驱动开发
    │                                 │
    ▼                                 ▼
  人写代码 → 代码是资产           人写规范 → 规范是资产
  文档是附属品                    代码是规范的编译产物（AI 生成）
  代码腐烂 → 文档过时             规范更新 → 代码自动重新生成
```

Martin Fowler 将 SDD 精细分为三个层级，帮助团队根据自身情况选择切入点：

| 层级 | 名称 | 做法 | 适合谁 |
|:---|:---|:---|:---|
| **L1** | Spec-First | 先写好规范，再让 AI 按规范生成代码 | 想稳一点的团队，入门级 |
| **L2** | Spec-Anchored | 规范与代码同步维护，规范是"锚点" | 需要长期维护的项目 |
| **L3** | Spec-as-Source | 规范即源码，人类永远不直接改代码 | 激进派——完全信任 AI 生成 |

### 为什么说"工具已经落地"

SDD 不是停留在博客文章里的概念——**三家巨头几乎同时推出了相应工具**，这在 AI 编程领域非常罕见：

**Tessl（Guy Podjarny）：**
- **Tessl Framework**（闭测）：帮代理在写代码之前先把意图捕获为规范，存在代码库里当"长期记忆"
- **Tessl Spec Registry**（开放测试，免费）：包含 **10,000+** 开源库的预构建使用规范——直接解决 AI 最头疼的"API 幻觉"问题（AI 编造不存在的函数/参数）
- 每日使用者达**数万名工程师**

**Amazon Kiro：**
- 基于 VS Code 的新一代 IDE，**内建 SDD 工作流**
- 三阶段开发：自然语言描述意图 → 生成带验收标准的用户故事 → 拆分为可追踪的实现任务
- 引入 **Agent Hooks**：文件保存/创建/删除时自动触发文档生成、测试补充、性能优化

**GitHub Spec Kit：**
- GitHub 官方的规范驱动工具
- 三步流程 + 可配置提示 + 不可变原则（Immutable Principles）

### 社区反应：期待与警惕并存

**支持者：**
- **ThoughtWorks 技术雷达**将 SDD 列为 2025 年值得关注的技术趋势
- 支持者认为 SDD 是唯一能让 AI 编程真正"工业化"的方法——Vibe Coding 太野，纯手工太慢，SDD 是中间路线

**质疑者：**
- 部分实践者发现生成的规范文件**冗长难以审查**——你逃过了审查代码，却要审查同样复杂的规范
- ThoughtWorks 自己也警告：开发者可能正在"重新学习一个苦涩的教训——为 AI 手工制定详细规则**最终无法扩展**"
- 各工具对 SDD 的诠释差异很大，**尚未形成统一标准**

### 为什么它仍然足够重要

尽管有争议，SDD 代表了一个不可逆的趋势：**当代码生成成本趋零，行业的重心必然从"实现"上移到"意图"。** 不管最终的规范长什么样（Markdown？YAML？自然语言？），"人类定义 What，AI 实现 How"这个分工模式已经确立。Amazon、GitHub、Tessl 三家同时下注，本身就是最强的信号。

## ⑧ 治具工程：人类不写代码了，人类建造"让 AI 写代码的工厂" (2026.2)

**一句话：** OpenAI 用 100 万行代码、0 行人类手写证明了——未来的程序员交付的不是产品，而是生产产品的流水线。

| | |
|:---|:---|
| **时间** | 2026.2.4 Agentic Engineering (Addy Osmani) → 2026.2.11 Harness Engineering (OpenAI) |
| **谁** | **Addy Osmani**（Google Chrome 工程经理）提出 Agentic Engineering；**OpenAI** 工程博客披露 Harness Engineering 实践；**Martin Fowler** & **Birgitta Böckeler**（ThoughtWorks）进行理论阐释 |
| **核心案例** | OpenAI App Server 项目 |

### 铺垫：Addy Osmani 的"代理工程"

2026 年 2 月 4 日，Osmani 发表了 *Agentic Engineering*，直接回应 Vibe Coding：**不是不用 AI 代理，而是用纪律来用。** 三条铁律：

1. **架构先行**——AI 之前必须有设计文档。混乱是因为跳过了"想"的阶段
2. **编排（Orchestration）**——你的工作是指挥多个 AI 代理，定义职责边界
3. **无情测试**——测试是代理的停止条件。没过测试就不准停

他还提出了**"80% 问题"**：部分团队 80%+ 的代码由 AI 生成，但面临假设传播（AI 基于错误假设层层构建）和抽象膨胀（AI 为了"安全"过度封装）的新挑战。

### 正题：OpenAI 的"治具工程"

一周后（2026.2.11），OpenAI 披露了更震撼的实践：

> 从空仓库开始，3 名工程师用 Codex 代理（GPT-5），5 个月生成约 **100 万行代码**，提交 **1,500 个 PR**。
> 
> **没有人类手写过一行代码。**
> 
> 估计节省了约 **10 倍**的时间。平均每人每天产出 **3.5 个 PR**。产品已有内部日活用户和外部 Alpha 测试者。

### 什么是"治具（Harness）"

治具是制造业的术语——**不是产品本身，而是固定和引导工件加工的夹具。** 在 AI 编程语境下：

```
传统程序员            治具工程师
    │                    │
    ▼                    ▼
  写代码 ──────→ 建造"让 AI 写代码的环境"
    │                    │
    ▼                    ▼
  产品              生产产品的流水线
```

OpenAI 的治具包含三个核心组件：

| 组件 | 做什么 | 类比 |
|:---|:---|:---|
| **上下文工程系统** | 代理需要改数据库时，自动抓取最新 Schema 和设计文档喂给它 | GPS 导航——自动提供当前路况 |
| **架构约束（自定义 Linter）** | "所有 API 必须经过鉴权中间件"——违反则自动驳回，无需人类介入 | 工厂流水线的质检仪器 |
| **垃圾回收代理** | 后台 AI 定期扫描代码库，发现僵尸代码/文档漂移/命名违规，自动提 PR 修复 | 自动巡检的清洁机器人 |

### 社区反应

**乐观者：** 这是软件工程抽象层级的又一次跃升——从汇编到高级语言、从高级语言到框架、从框架到治具。人类从"操作机器"升级为"设计工厂"。

**质疑者：** 这是不是只有拥有 GPT-5 的 OpenAI 才玩得起？普通团队用普通模型能复制这个成功吗？目前的答案是**不确定**——这仍然是一个前沿实验，而非已验证的通用范式。

Martin Fowler 的态度谨慎而深入——他发表了专题分析文章，将 Harness Engineering 纳入其"探索生成式 AI"系列，既不盲目推崇也不简单否定。
