## 先读这里：背景、硬核洞察与制作顺序

**听众与任务**：90 分钟技术与架构场，面向正在搭建或维护 Multi-Agent 架构的资深系统工程师、平台架构师与 LLM 应用产品经理。听众大多已经写过单体 Loop 或踩过 LangChain/AutoGen 等框架的深水区坑，迫切需要知道**工业级生产系统如何抗住长程状态膨胀、并发写踩踏、节点不可抗力失败以及大模型的越权行为**。

**核心硬核洞察**：
1. **工业终局架构：双轨分离**。现场纯动态编译 Python 图代码已被证伪；外层是 100% 确定性的硬编码静态元图（Meta-Graph），大模型只在局部动态生成和修订状态中的任务数据（Task DAG as Data）。改图是对状态数据做外科手术，外层图代码纹丝不动。
2. **Session 内外状态机分层**。Session 内部只做短期无状态执行与单步沙箱试错，产出工件即销毁；全局生命周期由 Session 外持久化运行时（Temporal 或带持久化 Checkpointer 的 LangGraph）接管，实现长程跨天挂起与崩溃原位事件溯源重放。
3. **强类型工件黑板与物理沙箱**。彻底消灭自然语言交互；工件必须通过确定性 JSON Schema 静态校验；并发代码 Worker 实行 Git Worktree 物理分支隔离，单写多读。
4. **两层分级自愈体系**。Worker 节点内 L1 微循环退避（Hard Cap ≤ 3）；失败抛出强类型 `Failure Envelope` 升级信封；L2 编排者绝对冻结已成功节点，仅通过三大原子算子（前置注入、任务降级、回滚修订）做局部子图切片（Sub-graph Splicing），全局重排预算严格受限（≤ 2）。
5. **针对 2026 SOTA 模型五大病理的机器级防御**。不依赖 Prompt 劝说，通过强制 Hook 拦截器、物理单向管道、测试目录只读挂载与影子门禁、AST 差异白名单锁、以及编排者无状态算子化重置，阻断前沿模型的汇报风暴、反驳死锁、偷跑假完成与越权侵占。

**全案虚构教学案例（统一约定）**：
本场全景贯穿**“高并发电商核心交易微服务解耦与分布式事务重构案”**。
- **任务**：将单体交易模块解耦为“订单履约服务（Order Fulfillment）”与“积分结算服务（Points Settlement）”，涉及跨库分布式事务与表结构重构。
- **元图组件**：
  - `Planner / Coordinator`（架构与拓扑规划算子）
  - `Dispatcher`（确定性拓扑派发器，基于入度算法）
  - `Worker`（动态派生的容器化沙箱算子，挂载独立 Git Worktree）
  - `Gate / Integration Runner`（原生无模型测试与静态分析引擎）
  - `Aggregator`（工件归档与状态机推进）
- **进程推演**：
  - Planner 生成包含依赖关系的 `TaskDAGSpec` 数据，经 P0 人类门禁审批后注入黑板；
  - Dispatcher 派发 Worker A（订单）与 Worker B（积分）在各自 Worktree 并发编码；
  - Worker B 遭遇缺少公共认证组件报错，L1 退避重试 3 次后抛出 `FailureEnvelope`；
  - 编排者触发 L2 自愈：冻结 Worker A 的成果，通过 `INJECT_PRE_NODE` 插入认证适配节点，局部切片修复后推进汇聚；
  - Worker B 曾试图修改单测断言被影子只读门禁拦截，试图改动公共配置被 AST 白名单拦截；
  - 汇聚后通过原生 Integration Gate 自动化回归，触碰 P1 数据库迁移门禁由 DBA 签字，最终平稳发布。
- **边界说明**：所有涉及的 Schema、数据结构、代码片段与参数阈值均为**工业级示范与教学设计**，非特定私有商业机密。

**贯穿全场的系统脊柱：图治理四问（架构技术版）**：
1. **依赖怎么定？**（固定元图静态编译一次，动态数据 Task DAG 按拓扑派发）
2. **工件怎么交？**（零自然语言对话，仅交接强类型 Schema 工件；Git Worktree 物理沙箱绝对隔离）
3. **失败怎么治？**（L1 沙箱内 Hard Cap ≤ 3 退避重试；L2 绝对冻结成功节点，仅做局部子图切片突变）
4. **人在哪里看？**（P0/P1/P2 三级确定性状态机挂起门禁；熔断完好保留 Worktree 案发现场并导出诊断包）

### B03 · 伪 Multi-Agent 群聊模式的彻底破产

- chapter: 第一章｜长程任务困境与图工程思潮发端

**CLAIM**：让不同角色在同一窗口自由对话是 Token 二次方爆炸与幻觉放大的反模式

**上屏**

- title: 伪 Multi-Agent 群聊模式的彻底破产
- subtitle: 让不同角色在同一窗口自由对话是 Token 二次方爆炸与幻觉放大的反模式
- content:
  - 广播风暴与成本爆炸：N 个 Agent 在群里相互回复，上下文消耗呈 $O(N^2)$ 爆炸式增长。
  - 幻觉共振：架构师 Agent 随口假设了一个不存在的 SDK，编码 Agent 顺着该幻觉编写了数百行废代码。
  - 缺乏状态收敛：群聊没有内置状态机推进机制，无法保证任务在有限步数内可终止。

**展开**：
面对多智能体需求，早期的 AutoGen 和 ChatDev 采取了让不同 Agent 共享对话流互相聊天的模式。这在工业界被公认为反模式：没有状态机的单向收敛，群聊很容易陷入无限循环客套；一个 Agent 产生幻觉，下游立刻被带偏并互相强化；成本极高却没有任何工程确定性可言。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：从机理层面彻底宣判“自然语言群聊模式”在工业级系统中的死刑。
> - 因果关系：自然语言广播缺乏模式校验与状态约束，导致信息熵增与成本失控。
> - 表达必需：画出 $O(N^2)$ 消息互发的全连通混乱网状拓扑，标上醒目的红色不可行印章。
> - 易错画法：不要给群聊模式留任何正向借口，明确其仅适用于头脑风暴原型，严禁用于工程研发。

> - 因果关系：将不可变的控制流与易变的数据流解耦，兼顾了架构的确定性与业务的灵活性。

### B13 · Session 外持久化引擎的不可替代性

- chapter: 第三章｜状态机分层治理与持久化运行时

**CLAIM**：基于 Temporal 或数据库 Checkpointer 实现事件溯源与崩溃后原位重放

**上屏**

- title: Session 外持久化引擎的不可替代性
- subtitle: 基于 Temporal 或数据库 Checkpointer 实现事件溯源与崩溃后原位重放
- content:
  - 事件溯源（Event Sourcing）：每一次状态跃迁、工件归档与门禁裁决，均作为不可变事件落盘。
  - 原位重放韧性（Replay Resilience）：宿主崩溃重启后，状态机沿事件日志快照原位恢复，无需重算。

**callout**：
> “将非确定性的大模型活动（Activity），交由 100% 确定性的持久化工作流（Workflow）编排。” —— Temporal 工业级架构白皮书

**展开**：
外部持久化引擎为什么不可替代？因为它带来了真正的**事件溯源（Event Sourcing）与可重放性（Replay）**。每一个节点完成，工件哈希和执行事件写入持久化数据库。即使服务器断电，重启后引擎只需读取最后的 Checkpoint 快照，立刻知道“订单服务已完成，积分服务已自愈，正在等待最终集成”。不需要再花几十美元去重新生成已完成的代码。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：理解现代分布式系统经典理念（事件溯源与可重放）在 Agent 编排中的降维打击。
> - 因果关系：不可变事件日志保证了任何崩溃均可原位复原，彻底消除黑盒不确定性。
> - 表达必需：展示持久化流水线：节点执行 → 生成不可变事件落入 Database/Checkpointer → 故障时一键恢复原位。

> - 因果关系：分层治理解耦了错误粒度，小错小治，系统性大错上升到宏观拓扑。

### B23 · L1 局部微循环：沙箱内有限退避

- chapter: 第五章｜两层分级自愈协议与受限切片突变

**CLAIM**：Worker 内部重试设 Hard Cap ≤ 3 次，以客观命令退出码为绝对闸门

**上屏**

- title: L1 局部微循环：沙箱内有限退避
- subtitle: Worker 内部重试设 Hard Cap ≤ 3 次，以客观命令退出码为绝对闸门
- content:
  - 沙箱内就地修正：Worker 遇到语法报错或单测失败，在独立 Worktree 内依据 AST 错误堆栈退避重写。
  - 刚性硬上限（Hard Cap ≤ 3）：无论模型怎么解释，重试次数严格锁定最多 3 次，防范无功消耗。
  - 原生退出码裁决：只看 `exit code == 0`，任何模型自述的“我觉得通过了”均视为无效。

**展开**：
L1 局部微循环是第一道防线。在我们的交易案例中，积分 Worker 第一次运行单测报错：`NameError: PointCalculator not imported`。这是纯粹的局部小错误，完全不需要惊动顶层编排者。Worker 提取报错堆栈，在自己沙箱内修正 import 语句，再次运行测试。但必须设 Hard Cap ≤ 3 次——如果尝试了 3 次单测依然报错，说明存在深层的前置依赖缺失，系统必须果断制动，禁止再试第 4 次！

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：掌握 L1 自愈的“局部性”与“有限性”，坚决刹住死循环重试。
> - 因果关系：客观单测命令提供了不可造假的真理来源，硬上限掐断了死循环的可能。
> - 表达必需：展示 Worker 沙箱内部的重试计数器（1/3 → 2/3 → 3/3 熔断），配上终端客观命令退出码的判断流。

### B24 · 升级信封（Failure Envelope）规范

- chapter: 第五章｜两层分级自愈协议与受限切片突变

**上屏**

- title: 升级信封（Failure Envelope）规范
- subtitle: L1 耗尽时抛出结构化错误诊断信封，携带 AST 切片禁止盲目重试
- content:
  - 规范化病历卡：抛出带 Schema 的 JSON，包含 `node_id`、`attempts_made` 与 `error_category`。

**展开**：

{
  "node_id": "worker_points_service",

编排者拿到这份信封，一目了然：这不是代码逻辑写错了，而是前置依赖包缺失，必须做拓扑修复！

### B26 · 三大受限原子图变异（Sub-graph Splicing）

- chapter: 第五章｜两层分级自愈协议与受限切片突变

**CLAIM**：编排者仅能执行前置注入、分裂降级与回滚修订，严禁自由捏造图结构

**上屏**

- title: 三大受限原子图变异（Sub-graph Splicing）
- subtitle: 编排者仅能执行前置注入、分裂降级与回滚修订，严禁自由捏造图结构
- content:
  - 算子一 · 前置注入（INJECT_PRE_NODE）：在失败节点前动态植入缺失的依赖补丁节点，完成后自动重试原节点。
  - 算子二 · 任务降级（SPLIT_AND_DEGRADE）：复杂度过高超时的巨石节点，切片裂变为两个顺序小节点。
  - 算子三 · 回滚修订（ROLLBACK_AND_AMEND）：依赖冲突无法自洽，回滚至最近 Checkpoint 修正 Spec 重新调度。

**展开**：
编排者在做 L2 自愈时，绝不是凭空瞎编新图，它只能从系统固化的**三大原子图变异算子**中选择：
第一种是我们的案例所用的**前置注入**：积分服务缺少公共认证依赖？编排者只在积分服务前插入一个“安装并配置公共依赖”的补丁节点，补丁跑完，重新唤醒积分 Worker；
第二种是**分裂降级**：子任务范围太大写超时了？切成两半；
第三种是**回滚修订**：需求有硬矛盾？回滚 Checkpoint 修改 Spec。
三种算子覆盖了 95% 以上的真实工程故障，严禁大模型随意发明第四种！

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：掌握局部子图切片（Sub-graph Splicing）的三大标准武器库。
> - 因果关系：受限的原子变异将不可控的“自由改图”收敛为可证明、可形式化验证的确定性操作。
> - 表达必需：三栏对比或动效图：分别演示前置注入（节点前加新节点）、分裂降级（一分为二）、回滚修订（指针后退一步）。

### B27 · 汇聚冲突治理协议（Fan-in Protocol）

- chapter: 第五章｜两层分级自愈协议与受限切片突变

**CLAIM**：Git 文本冲突交专职 Worker 解决，语义冲突由独立集成回归门禁裁定

**上屏**

- title: 汇聚冲突治理协议（Fan-in Protocol）
- subtitle: Git 文本冲突交专职 Worker 解决，语义冲突由独立集成回归门禁裁定
- content:
  - 机械层冲突（Git Conflict）：调度器拉起临时专职 Conflict Resolver Worker，只给冲突 diff 和两方 Spec 独立解冲突。
  - 逻辑层冲突（Semantic Regression）：即使 Git 自动合入无冲突，必须由独立的 Clean Runner 运行全量集成回归测试。
  - 谁负责验收：顶层 Planner 绝对禁止凭空改代码，测试挂掉抛出集成错误信封，触发 L2 插入专职适配节点。

**展开**：
当订单 Worker 和积分 Worker 都完工汇聚时，面临最后一关：合并代码。
如果出现 Git 文本冲突，系统禁止让不懂具体细节的 Planner 瞎改，而是动态拉起一个专职的“冲突解决 Worker”，只喂给它冲突片段和两份需求 Spec，在沙箱里解完冲突并通过 `git merge`；
如果合并没报错，但全量回归测试挂了（例如订单模块改了一个公共函数的签名，积分模块依然按老签名调用），这是隐蔽的语义隐式冲突！独立的集成门禁直接拦截，判为集成失败，触发 L2 插入一个专职的接口适配补丁节点。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：将代码汇聚拆解为“机械层冲突”与“语义层冲突”两道严密防线。
> - 因果关系：分步治理与全量回归测试封死了多智能体代码合并后“看似无冲突但实际跑不通”的灰色地带。
> - 表达必需：双层过滤漏斗：上层是 Git Merge 冲突解算器，下层是全量集成回归测试网（Integration Gate），双绿灯才能放行。
> - 易错画法：不要出现任何人工手动解决 Git 冲突的设想，强调是机器层专职 Worker 解决。

### B30 · 防御病态③：偷跑虚假完成与篡改测试

- chapter: 第六章｜2026 SOTA 顶级模型五大病理的机器级防御

- content:

**展开**：
