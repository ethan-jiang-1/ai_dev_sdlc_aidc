# Outline — Graph Engineering（入门场：从群聊幻觉到组织同构）

## 0. 这场要解决什么

听众不需要先学会写复杂的状态机代码；他们需要带走一张**企业级多智能体协同治理地图**：
**当单 Agent 无法胜任长程复杂研发时，绝不能退回到“让多个 Agent 在同一个群里自由聊天”的伪多智能体幻觉中；多智能体的本质是人类软件工程组织结构在机器侧的代码化同构；节点之间只交接强类型工件，通过两层自愈协议与人机门禁，让机器团队具备可预测的交付确定性。**

---

## 1. 核心判断

**单体 Loop 无法承担长程复杂任务，但伪 Multi-Agent 群聊只会放大混乱；生产级图治理的核心是用显式拓扑实现职责隔离，用强类型工件消灭自然语言客套，用局部自愈避免推翻全图，在关键节点设置人类把关门禁。**

---

## 2. 贯穿全场的系统脊柱：图治理四问

```text
谁定前后依赖？  → 显式拓扑结构（静态元图编排动态任务工单）
节点如何交接？  → 强类型工件契约与物理隔离，严禁自然语言闲聊
出了故障怎么治？→ L1 执行者局部微循环退避，L2 编排者做局部子图切片
人在哪里把关？  → 架构方案门禁、破坏性操作拦截与优雅熔断
```

## 3. 六章叙事节奏与页面清单（27 页）

### 第 1 章：群聊的幻觉与单体的尽头（N01–N04）
- **核心问题**：为什么我们看到的 Multi-Agent 演示很惊艳，一进真实项目就崩溃？
- **带走判断**：单 Agent 会遭遇注意力腐蚀，而多 Agent 自由群聊是成本与确定性的灾难。
- **转场理由**：既然自由聊天不行，真实团队是怎么协同的？

| 页码 | Title | Subtitle (CLAIM) |
|---|---|---|
| **N01** | 它说完成了，但代码没法上线 | 复杂的软件研发任务无法靠单 Agent 的单体会话一次性交付 |
| **N02** | 单体 Loop 的物理上限 | 随着对话轮次增加，单一上下文必然遭遇注意力稀释与反驳死锁 |
| **N03** | 自由群聊的灾难 | 让多个角色在同一个对话窗口客套，只会带来 Token 爆炸与幻觉扩散 |
| **N04** | 概念澄清：伪多智能体 vs 图工程 | 真正的多智能体不是聊天室，而是带约束的状态转移拓扑网络 |

---

### 第 2 章：组织的同构：从聊天群到流水线（N05–N08）
- **核心问题**：如果不是聊天室，生产级多智能体系统应该长成什么样？
- **带走判断**：多智能体系统的本质是人类研发组织在机器侧的同构映射。
- **转场理由**：组织分工明确了，各工序之间怎么传递信息？

| 页码 | Title | Subtitle (CLAIM) |
|---|---|---|
| **N05** | 软件工程组织的机器同构 | 机器多智能体是人类组织架构与研发规程的代码化映射 |
| **N06** | 显式拓扑（DAG）：分工先于对话 | 谁先做、谁后做、谁能并行，必须由显式拓扑在执行前严格锁定 |
| **N07** | 并发扇出与汇聚 | 相互独立的子任务必须在隔离环境中并发，最后通过质量门禁统一汇聚 |
| **N08** | 承接页：图治理的底座原则 | 能单 Agent 搞定的绝不上图，能扁平串联的绝不上复杂拓扑 |

---

### 第 3 章：消灭自然语言，确立工件契约（N09–N13）
- **核心问题**：节点之间如何交流，才能杜绝传话走样和越权篡改？
- **带走判断**：节点间零自然语言对话，只认 Schema 校验的强类型交付物。
- **转场理由**：有了规整交付物，节点内部干砸了怎么办？

| 页码 | Title | Subtitle (CLAIM) |
|---|---|---|
| **N09** | 为什么工作群里全是无效客套 | 自然语言传递意图极其脆弱，容易产生连锁误解与执行漂移 |
| **N10** | 强类型工件契约 | 节点之间只交接带数据模式校验的结构化交付物，格式不合规直接阻断 |
| **N11** | 全局单一事实来源：黑板模式 | 所有共享进度与交付物沉淀至全局看板，遵循单写多读纪律 |
| **N12** | 物理沙箱隔离 | 每一个干活的 Worker 必须拥有独立的工作目录，杜绝文件脏写入 |
| **N13** | 呼吸页：工件驱动的研发流 | 需求出 Spec，开发出 Patch，测试出 Report，系统只凭客观证据推进 |

---

### 第 4 章：两层分级自愈：微创手术与防死锁（N14–N18）
- **核心问题**：多步骤流水线中，某个节点失败了，必须全盘重来吗？
- **带走判断**：底层做有限微循环，顶层做局部切片替换，绝不推翻全图。
- **转场理由**：机器能自动重试，但如果陷入致命死循环谁来踩刹车？

| 页码 | Title | Subtitle (CLAIM) |
|---|---|---|
| **N14** | 灾难的反模式：整图推翻重来 | 单点故障引发全量重新规划，会导致系统陷入状态抖动与无限空转 |
| **N15** | L1 局部微循环：打工人就地纠错 | 执行者在沙箱内依据客观单测做有限退避重试，上限不超过三次 |
| **N16** | 升级信封：带着诊断卡求援 | 局部自愈耗尽时抛出结构化错误报告，绝不私自盲目重试 |
| **N17** | L2 拓扑自愈：局部微创切片 | 编排者绝对冻结已成功节点，仅在失败节点前做受限的外科手术式重排 |
| **N18** | 防死锁硬红线：重排预算受限 | 全局改图预算严格受限，同类错误连击坚决停止并呼叫人类 |

---

### 第 5 章：人在哪里把关：审批门禁与优雅熔断（N19–N23）
- **核心问题**：在高度自主的图系统中，人的位置在哪里？
- **带走判断**：人不再做逐步监工，而是在方案、破坏性动作与发布门禁当守门员。
- **转场理由**：理解了全套机制，企业该如何一步步落地？

| 页码 | Title | Subtitle (CLAIM) |
|---|---|---|
| **N19** | 人从监工转向守门员 | 人类工程师不在每一步指手画脚，而在关键决策断点行使否决权 |
| **N20** | 三道核心审批门禁 | 架构设计后、破坏性变更前、生产合入时，系统必须挂起等待人类审批 |
| **N21** | 影子门禁：防止偷跑假完成 | 测试环境对干活模型只读，最终验收由独立客观容器执行 |
| **N22** | 优雅熔断：完好保留事故现场 | 触碰预算红线时系统冻结沙箱并导出诊断包，严禁清理案发现场 |
| **N23** | 成本与配额双锁 | 全局设置 Token 与财务硬顶，彻底封死多 Agent 并发失控的经济风险 |
