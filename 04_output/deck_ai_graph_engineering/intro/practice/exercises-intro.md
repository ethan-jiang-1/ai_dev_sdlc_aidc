# 入门场现场练习（学员版）

> 本练习为《Graph Engineering 入门场：从群聊幻觉到组织同构》配套现场诊断题。
> 练习采用口头或纸面形式完成，不设无锚开放题，旨在帮助业务与研发管理者识别伪群聊反模式、判断工件契约完备性、选择关键人机审批门禁。

---

## 练习一（对应 N10）：工件契约合规性诊断

**场景背景**：
某团队搭建了一个多 Agent 系统来自动完成“用户积分明细分页接口开发”。在执行中，架构师 Agent 在完成方案后，向执行编码的 Agent 发送了以下对话消息：
> “嗨！我已经把接口设计好了，你就按照刚才我们讨论的方案，在现有的订单数据库表里加一个积分字段，字段名你看着起一个符合规范的就行，另外记得兼容之前的老版本，改完了直接告诉我。”

**学员任务**：
1. 请指出上述交互违反了图治理的哪 3 条核心原则？
2. 请按照“强类型工件契约（Typed Artifact）”的要求，为该交付物重构一份合格的结构化数据摘要。

## 练习二（对应 N17）：故障自愈层级判断

**场景背景**：
系统在编排并发任务时，Worker B（负责编写前端展示组件）在本地沙箱运行单测时，由于拼写错误抛出异常：`SyntaxError: unexpected token '}' in file PointsCard.tsx`。
系统的编排大模型感知到测试未通过，立即将全流程暂停，删除了原本生成的 5 个任务节点，并提示：“检测到不可恢复语法错误，正在重新为整个需求设计全新的 DAG 架构”。

**学员任务**：
1. 该编排系统的自愈处理犯了什么严重反模式？
2. 按照“两层分级自愈协议”，这起故障应该由谁负责、在哪个层级（L1 还是 L2）解决？标准处理流程是什么？

## 练习三（对应 N20）：HITL 审批门禁设卡

**场景背景**：
某科技团队希望实现“Issue-to-Production 完全无人值守研发”。产品经理输入一段需求，系统自动拆解子任务、并发拉起 Worker 编写代码、自动合并主干并直接部署上线生产环境。系统运行第一周，发生了因大模型误删数据库关键索引导致的生产雪崩事故。

**学员任务**：
若要兼顾流水线的高吞吐与系统的绝对安全，请在这条全自动流水线中选出**必须设立人工审批断点（Checkpoint Gates）的 3 个关键位置**，并说明每个人工门禁的守门职责。
