# 文稿 — 技术产品场

> **给 PPT Agent：本文件是唯一制作输入。** 无须打开大纲、研究、练习件或手册来补背景。只制作 B01–B37 共37页；章节、追问卡、控制实验均不是新增页。外部来源仅供核验，不是追加内容指令。本稿为制作内容输入，讲解时长和听众理解仍待排练验证。

## 制作前先读：背景、判断顺序与边界

**听众与任务**：正在搭或维护 Agent 系统的工程师、设计 Agent 功能的产品经理。他们已经在跑循环，本场不教第一次调用模型，而是教如何识别已交出的决定、配对应控制、验证失败出口。听众带来的任务与环境可能不同，因此夜间回归值守是贯穿的教学故事，不是产品真实日志。

**开场故事与核心洞察**：你把站内搜索的夜间回归值守交给 Agent：每晚构建之后，它自己跑回归、自己修到绿，早上你看报告。它接手的第一份工作，是修复「分页返回后 query 丢失」的回归；本场 37 页就是这份职责从第 1 周走到第 3 个月的故事。关键不是它跑得多快，而是谁按什么证据判断完成、动作是否受限、出错如何停止与接手。本场逐步交出三类决定：动作审批、是否续跑、何时唤醒；阶梯仅是教学顺序，真实配置须逐面核查，不假定三个面必然累积。任何完成判定都不能把实际停止、指定验收者签认、真实用户效果混成同一件事。

**全案虚构教学故事（统一约定）**：全场只讲一件开放的事——「夜间回归值守」，按七个阶段推进；每页的场景行从当前阶段取材，听众随时知道故事走到了哪一天：

| 故事阶段 | 故事时间 | 页 | 此刻发生了什么 |
|---|---|---|---|
| 开场（闪回） | 第 2 周末之夜 | B01 | 第一次无人续跑的深夜，它回报「完成」——悬念留给全场 |
| 为什么交出去 | 第 1 周回溯 | B02–B04 | 之前你逐轮指挥修了一周；今晚决定把「接替」画成格子 |
| 授权日 | 第 2 周周一 | B05–B11 | 你给的不是开关，是一张分级处置表和一张会过期的 token |
| 第一次无人续跑 | 第 2 周末 | B12–B20 | 你写清「绿」的定义、裁判与出口；它第一次自己跑到停——B01 的那一晚 |
| 复盘与分账 | 第 3 周 | B21–B28 | 它宣称全绿——你拆清单、走用户路径、守判据、分三账 |
| 夜间值守上线 | 第 1 个月末 | B29–B32 | 每晚构建自动开跑；取消要传到 worker；跨次有总账 |
| 值守三个月后 | 第 3 个月 | B33–B37 | 它成了值班同学；两条岔路（行业支线旁白）、高手错觉、定档收尾 |

技术事实层沿用同一条站内搜索回归链路：值守 Agent 在 `agent/search-pagination` 分支工作；token 绑定主体、动作、目标、分支、有效期和本次 run；每晚构建跑 E2E，某晚抓到「返回后 query 丢失」；原始 trace 进入 Eval，verdict 决定修复、补证据、停止或交接；scheduler 只负责唤醒，cancel 要传播到 scheduler、worker 和副作用；control、acceptance、outcome 三账分开。演练页（负例、取消、资源耗尽）是故事里的「放权前演练」事件——每多交一个决定之前，先演练一次它的坏路径，这正是这个故事建立信任的方式。所有 branch、token、run、字段、状态、阈值和伪代码均为**本场虚构示意／教学设计**，不是事故复盘、真实运行、产品 API 或收益数据。真实产品机制和公开来源只支持其各自的有限主张，不能当作本案例出处。每页的场景行让听众看见故事推进到哪一天；「事件→误判→正确追问→可迁移判断」留给讲者备注，不上屏成模板标签。

**阅读顺序**：先读本节与术语、章节导航；然后每页按 CLAIM → title/subtitle/content → 做片知识说明 → 展开/证据 → 接页读。CLAIM 说明本页要证明什么，知识说明提供概念关系、前提和图示推理；展开是讲者备注，不自动挤进上屏。最后的追问与实验只帮助理解边界，不能据此新增配置页。

**内容层级**：每页 title、subtitle 与 content 必须保留；content 是最小可读正文，最多3条。chapter 是导航字段，章首在既有页角显出完整名称，其余页可小标提示；第7章非章首页统一用短名“扩展与判断”，完整名称只在B33章首出现。callout 是单独的一行署名证据，不当第四条正文，视觉负担仍须计入；放不下时先删装饰和非必要图例，不能省掉限定语或缩字硬塞。**全场 9 处 callout 是金句系统的一部分，必须逐条渲染为页角/底部一行，做片方不得省略、合并或折叠进备注**；漏一条按制作缺陷返工。章末口头回扣、练习提示、做片说明均留备注；无额外章节页或练习页。subtitle 按语义在分号或转折处分成两行；CLAIM 不再重复展示，章节小标不占正文区域，不缩字号塞入备注解释。每页一项认知变化，图应表现因果、授权或证据关系，不只是给名词配图标。

**全场证据纪律**：作者定义、产品机制、个人案例、公开报告、本场教学设计必须区分。产品文档证明机制存在，不证明普遍收益；公开 issue 仅是失败线索，不证明根因或发生率；教学参数不可抄生产。署名 callout 的原文、日期与限定在同页备注保留。Stop、Blocked、unknown、outcome_pending 不改写成完成。手册只作为听众带走的操作入口，不是制作必读输入。

## 90分钟节奏与练习处理（仅讲者备注，不新增页面）

讲解63分钟＋三题23分钟＋收束提问缓冲4分钟。B01–B11讲18分钟；B12–B14讲6分钟，练习1用8分钟；B15–B18讲9分钟，练习2用7分钟；B19–B28（含 B20 呼吸页）讲17分钟；B29–B32讲7分钟，练习3用8分钟；B33–B37讲6分钟。累计在24/41/72分钟开练，在32/48/80分钟结束，86分钟结束讲解，90分钟收束。这是待排练预算，不是实测；超时优先缩短支线案例展开，保留四问回扣与停止/验收边界。

- **B14 后练习1：写 Goal，8分钟**。题面：为真实任务写可测终态、证明它的检查、不变约束、无进展出口、资源上限。分页合格示例：第二页能打开、返回保留条件；浏览器断言覆盖整条路径并保留原始结果；不改接口、不删测试；连续任务预设的 N 轮无改善则交人；达到预设时间/成本上限则保存状态停止。N 和预算由任务确定，不能直接照抄产品例。写5分钟、互查2分钟、点评1分钟。合格线：五件齐全、别人能复查、业务采用率不冒充产物终态。若阈值无基线，注明待验证，不声称可上线。
- **B18 后练习2：让已知错误被拦，7分钟**。题面：在正确版本和通过基线上，改坏分页返回条件保留行为，保持原断言；先写预期哪项失败，再运行定向检查并保留版本、原始输出和失败原因。合格表现：失败来自预期行为，不是无关语法/环境错误；未被拦就指出缺失路径并修检查。另可测试删/跳过检查应被保护策略或差异核对拦住。操作4分钟、追问2分钟、还原确认1分钟；仅可回滚分支，不碰生产，仅还原本题改动，保留既有未提交工作。无环境则写错误/预期检查/证据计划，标待演练；纸面方案和一个负例被拦都不证明通用安全。
- **B32 后练习3：逐面验证拟交决定，8分钟**。题面：分别写动作/续跑/唤醒当前是否已交与证据，再写本次拟交什么。动作核作用域变异和允许/人批/硬拒绝三路；续跑核目标负例、Eval校验、无进展与资源出口；唤醒核取消到worker、去重、恢复、跨次预算与接手。每项记通过/不过/待演练，非适用写理由，最后写满四问。合格示例：只读定时巡检核唤醒控制，并明确未获写入或目标续跑权；取消未演练则记录待演练、暂不多交决定。填5分钟、追问2分钟、收束1分钟。现场填写合格只代表设计工件，不等于上线批准。

## 术语

Loop：结果进入判断并影响下一行动的循环组织方式；Agent：执行任务的一方；Harness：承载工具、权限、状态与控制的运行系统；Goal：可验证的目标；Eval：按判据进行评估，判定者可为人、规则或 evaluator/grader；Feedback：用于调整后续行动的观察和理由。

| 概念 | 本场含义 | 与相邻概念的区别 |
|---|---|---|
| Loop / Agent / Harness | Loop 组织后续行动；Agent 执行任务；Harness 承载工具、权限、状态与控制。 | Agent 不是整个系统；有 Harness 不代表已配置目标续跑；外层重复调用不自动保证有效 Feedback。 |
| Goal / Eval / Feedback | Goal 定义待达成状态和约束；Eval 按判据解释证据；Feedback 是用于调整下一步的观察和理由。 | 目标不是评分；工具输出不是天然可信的判定；只存结果却不消费，不等于据此修正。 |
| check / grader / evaluator / rubric | check 是具体检查；grader/evaluator 是判定角色或组件；rubric 是判据。 | 清单不是判定者；角色分离不要求一定换模型型号，但输入和权限不能由执行者单方面操纵。 |
| 终态 / 不变约束 / 停止出口 | 终态定义做成什么；约束定义不能牺牲什么；出口定义何时停止尝试。 | 预算耗尽是出口，不是终态证据；检查被删后的通过不能证明约束满足。 |
| Stop / Accepted / outcome | Stop 记录实际停止；Accepted 记录有权验收者签认；outcome 记录真实用户或业务结果。 | 三者可同时处于不同状态，不能压成一个 done，也不是必然相继的状态链。 |
| 授权 / 审批 / 隔离 | 授权限定可做什么；审批决定有限动作是否获准；隔离限定实际副作用。 | 申请已发出不是批准；普通批准不能覆盖硬策略；批准偏好不是执行安全边界。 |
| tree / run_id | tree 标识一次运行对应的代码版本（git 提交树）；run_id 标识一次运行实例。 | 证据必须绑定到具体 tree 与 run，才能防止拿别的版本的结果判本次；二者都不等于质量判定。 |
| worker / scheduler | worker 是执行任务的运行体；scheduler 是按时间表或事件唤醒它的调度者。 | scheduler 只决定何时开跑，不赋予动作权限或完成判定；worker 退出要单独确认。 |
| E2E | 端到端测试：从用户入口走完整条路径的自动化检查。 | 它证明用户路径可走通，不替代验收签认。 |
| nonce | 绑定本次运行实例的一次性字段（本场教学命名）。 | 与 expiry 一起防止旧批准被沿用到新任务。 |
| Met / NotYet / unknown / Impossible | Eval 的判定值：Met＝条件满足；NotYet＝未满足；unknown＝证据不足；Impossible＝有证据证明不可满足。 | Met 只是停止候选不是验收；unknown 不能写成 Impossible。 |

授权面、策略件、负例、交接单、定档四问沿中文说明使用。负例是已知应被拒绝或应使检查失败的样本，不是随便制造一个错误。交接单说明原因、版本、责任人、证据和恢复位置，不只是完成总结。关键术语不逐字替换成中文同义词；具体产品枚举、字段名和源引句保持原样。

### B01 · 你离开后，它说做完了

**CLAIM**：难的不是让它干活，而是它说「做完了」——你凭什么信。

**上屏**

- chapter: 01 · 看清交出的决定

- title: 你离开后，它说做完了
- subtitle: 难的不是让它干活，而是它说「做完了」——你凭什么信。
- content:
  - 第 2 周末深夜，值守 Agent 的第一次无人续跑结束了——它回报「完成」。
  - E2E 却显示返回时丢了 query。
  - 谁按哪份原始证据验收？

> **做片知识说明（不上屏）**
> - **本页认知变化**：从收到完成消息，转为追问谁有权接受这份消息。
> - **关键洞察与机制关系**：执行者能生成完成宣告，但宣告本身不提供验收权；运行、检查、验收尚需分别确认。
> - **案例前提与可推断范围**：假设 Agent 修改了站内搜索分页，离开后继续运行，回来只看到“完成”。这只能证明它发出了消息，不能推断第二页和返回路径已通过。
> - **图中必须保留的关系**：消息“完成” → 验收者提出证据问题；保留一个未知检查结果的位置，后文再展开。
> - **不能这样画及原因**：不能把消息旁边画成已验收勾选：这会把执行者的自述误当成独立确认。
> - **章首导航**：既有页角显示“看清交出的决定”，不新增封面。

**展开**：教学任务固定为 `branch=agent/search-pagination`：worker 修改分页后，E2E 暴露“返回丢 query”。收到「完成」只说明 worker 发了宣告；程序是否停止、原始 trace 是否通过、谁验收哪个 tree，都未确认。后文每次只推进这条链的一步，B25 再把完成问题拆成三本账。工程师常见误判是把 `worker exited=0` 当成用户路径通过；正确追问是“哪一个 `run_id/tree` 的原始证据支持哪一项 verdict？”迁移时保留终态—证据—责任人的关系，不搬分页字段。

**上屏**

- chapter: 01 · 看清交出的决定

- title: 为什么有人开始「写 loop」
- subtitle: Osmani 一句话说清：让系统接替你，逐次去提示 agent；今天要工程化的，是里面的反馈、判断和边界。
- content:

> **做片知识说明（不上屏）**
> - **本页认知变化**：理解“写 Loop”是在设计下一轮如何产生，而非重复提示或单纯换更强模型。
> - **关键洞察与机制关系**：执行结果进入检查，检查理由再影响下一行动；Harness 承载工具、状态与控制，反馈可调整方向但不保证修正成功。

**证据与展开**：分页 worker 若要提交改动，审批事件必须带 `reviewer/request_id/delivered/resume_pointer`；这些字段是教学设计、非产品 API。工程师误判是“请求已发出＝已升级”，PM 误判是“通知看见＝可恢复”；正确追问是“指定人是否实际收到、批准后从哪个 run/action 恢复？”[Claude Code issue #67519](https://github.com/anthropics/claude-code/issues/67519)（观测 2026-09-27）用户报告反复授权后仍被拒绝，是单用户报告，根因未确认，不能外推为平台全部审批不可达。拒绝合理性与合法升级可达性分开核；本场建议记录指定 reviewer、送达情况、动作目标和恢复指针。无人响应时保持未授权并停止相应动作，不把请求已发出写成已批准。组件状态是 `requested→delivered→decided→resumed`；工程师误判是看通知存在，PM 误判是把 delivered 当批准。正确追问是“delivery_record 和 resume_pointer 是否绑定同一 run？”迁移时只保留送达与恢复不变量。

### B13 · 反馈是循环的燃料

**CLAIM**：下一步得由反馈说了算；证据留下来，这条路才查得回去。

**上屏**

- chapter: 03 · 给续跑写清目标与出口

- title: 反馈是循环的燃料

> **做片知识说明（不上屏）**
> - **本页认知变化**：区分收到工具结果和真正利用 Feedback：下一步必须依据结果作决定。

**展开**：触发事件是 `e2e.failed(query_lost_on_back)`；worker 状态先记 `NotYet`，再用 `evidence_ref` 指向原始 trace，决定定位状态保存而非盲目重写。Feedback 被消费不等于动作每轮都不同：可以继续同一检查。工程师误判是把“第二页成功”当根因；正确追问是“失败发生在哪一跳、下一行动如何由理由决定？”迁移到别的领域时保留 `observed→reason→next_action`，重写事件名。内存中的工具结果也能构成反馈回路；跨轮复查与交接需要将它记录成可检索工件。`evidence_ref` 是本场建议字段，非定义条件。Aider 编辑后 lint 失败回灌是早期机制旁证；结构化数据优先读原始结果文件，别把执行者的总结当原始输出。

> - **案例前提与可推断范围**：若删除返回状态断言，剩余测试成功不证明分页已修好；新增功能需要新测试，也不等于所有测试修改都是作弊。
> - **图中必须保留的关系**：同一失败行为在原断言下失败，删除断言后未被检查，两种结果对照；独立审查作为判据变更入口。
> - **不能这样画及原因**：不能画成永不修改测试的锁：保护的是验收权限，不是阻止合理工程演进。

**展开**：Kent Beck《Augmented Coding: Beyond the Vibes》（2025-06-25，观测 2026-09-27）个人记录把禁用/删除测试列为跑偏信号，不是发生率证据。本场核对 `skip`、删文件、断言降级、`|| true`，并核基线已有失败与新增失败。硬 hook 或写权限能保护指定基线，但新增功能需要新测试，须另行审查；执行者不能一边削弱检查一边宣告成功。

**接到下一页**：有了检查依据，也不能把停止、验收和外部结果混成一个完成状态。

### B25 · Stop ≠ Accepted；三本账

**CLAIM**：控制状态、产出验收、外部结果三本账分开记——谁停的、谁验收的、结果谁在何时复查。

**上屏**

- chapter: 05 · 区分完成、停止与人的判断

- title: Stop ≠ Accepted；三本账
- subtitle: 控制状态、产出验收、外部结果三本账分开记——谁停的、谁验收的、结果谁在何时复查。
- content:
  - 控制账：worker 是否实际停止、为什么停（预算烧停也算），`resume_pointer` 在哪。
  - 验收账：谁对哪个 `tree/evidence_ref` 签认，依据哪份原始证据。
  - 结果账：query 保留后的真实采用有没有人观测、谁在何时复查。

> **做片知识说明（不上屏）**
> - **本页认知变化**：把停止、验收、外部效果分别记录，避免一个 done 混掉责任。
> - **关键洞察与机制关系**：控制账说明实际停止及原因；验收账说明谁签认何版本；结果账说明真实用户观测与复查责任，三者不是流水状态。
> - **案例前提与可推断范围**：分页检查满足且已退出，可同时是 stopped、unaccepted、outcome_pending；签认后仍不等于采用率已观察。
> - **图中必须保留的关系**：三本账并列，各保留主体、证据或复查时间；不得连接成 stopped→accepted→outcome。
> - **不能这样画及原因**：不能只展示三个英文标签不展示责任：这样仍无法回答谁停、谁认、谁复查。

**展开**：三本账是本场设计，非产品统一状态机。组件状态分别记录 `stopped/unaccepted/outcome_pending`；工程师误判是把 stopped 当 accepted，PM 误判是把验收当采用。正确追问是“哪位责任人在何时凭哪份证据签认？”迁移时保留三账分离。分页 E2E 通过可记 `verdict=Met`，但 worker 仍可能 running；真正退出才记 `control_status=stopped`。验收者对照 `tree + evidence_ref` 签认才写 `accepted_by`；用户采用未观测仍是 `outcome_pending`。PM 常把 Met 当 accepted，工程师常把 worker exited 当 outcome；正确追问是“哪本账、谁、何时、凭哪份原始证据？”迁移时保留三账分离，不复制字段名。三个字段能同时成立，不把 `accepted` 当控制账的下一状态。硬拒绝/待人处理也按原因分列，不默认完成。

**接到下一页**：控制账里另一种常见停机原因，是资源耗尽——它不证明质量。

### B26 · 资源上限限制消耗，不证明质量

**CLAIM**：资源上限只管花费，不替代质量判定；耗尽先保全状态并交接。

**上屏**

**接到下一页**：资源耗尽或熔断触发，系统会发起停止——还要核实停在哪里、如何交接。

### B29 · 两种运行边界

### B32 · 多交决定前，逐面验证

# 可直接拆解的控制实验（不上屏）

> **以下13节是讲者/技术补充，不新增PPT页，不把配置代码抄上屏。** 一套待接入真实运行器的演示设计，对应各交接面护栏。所有 YAML/JSON/伪代码是本场设计模板，不是可直接执行的产品 API 配置；接入时须实现项目权限、预算控制与审计存储。例中的编号、时间、样本计数只作教学示意，不可原样用于生产；产品参数另按同页出处核查。

## 1. Goal / Eval 合约（续跑条件）

```yaml
id: search-pagination-v1
terminal_state:
  - page_2_opens
  - query_and_filters_survive_navigation
checks:
  - command: npm test -- search-pagination
    type: deterministic
  - command: npm run e2e -- search-pagination.spec.ts
    type: environment_path
constraints:
  branch: agent/search-pagination
  forbidden: [public_api_change, test_deletion, push]
stop:
  no_progress: {criterion: task_specific, window: task_specific}
  retryable: [query_lost_on_back, page_2_button_click_failed, route_404]
  blocked: [dependency_temporarily_unavailable]
  dependency_retry: only_if_classified_transient_and_within_limits
  impossible: [constraint_conflict_proven_by_evidence]
  resource: [wall_clock, cost, retry_budget, expiry]
external_outcome:
  status: outcome_pending
  owner: product-owner-7
```

依赖暂不可用不等于 Impossible：可以先 blocked；只有分类为暂态、允许重试且未触退出条件时才 retryable。Impossible 的约束冲突必须有证据证明当前目标与不可变约束不能同时满足。no_progress 的 criterion 与 window 须按任务定义，不能留待模型临时猜测。

工程审查四问：终态可观察吗？检查覆盖实际路径吗？约束由运行器 enforce 吗？`impossible` 是逻辑不可满足还是暂时不可见？外部采用率不能填 `Met`。

## 2. Action authorization：把批准做成可失效对象（动作档护栏）

本模板与正文为同一授权模型：`expires_at` 对应 `expiry`；`nonce` 对应本次实例（旧稿 `run` 语义），示例值为 `run-0042`。这里的 `nonce` 只是教学字段命名，不宣称任何产品 API 或通用密码学语义。

```json
{
  "token_id": "auth-0042",
  "principal": "search-agent",
  "action": "edit",
  "target": "src/search/**",
  "branch": "agent/search-pagination",
  "scope": ["src/search", "tests/search"],
  "expires_at": "2026-09-28T18:00:00Z",
  "nonce": "run-0042",
  "denied_actions": ["push", "deploy"]
}
```

“三样”是语义概括，不是三字段 schema；`target/branch` 共同限定目标，`principal` 绑定主体，`nonce` 绑定本次实例，`expires_at` 限定有效期。

**变异测试**：依次改 `action`→commit、branch→main、target→`deploy/`、时间→过期、nonce→下一轮；每次都应拒绝旧 token 并写 `authorization_drift` 事件。变异仍通过，不能扩大相应授权。

## 3. Environment Feedback：证据通道而不是聊天文本

```text
run command
  ├─ exit_code
  ├─ stdout/stderr artifact
  ├─ browser trace / screenshot / network log
  └─ commit/tree identity
          ↓ durable evidence_ref
     evaluator input
          ↓ verdict + reasons
     next action or control state
```

最小事件：

```json
{
  "run_id": "run-0042",
  "action_id": "act-0042",
  "tree": "git:abc123",
  "exit_code": 1,
  "evidence_ref": ".loop/runs/run-0042/",
  "observed": ["query_lost_on_back"],
  "created_at": "2026-09-28T16:31:00Z"
}
```

本节是审计模式模板：下一轮消费原始观察；带 `evidence_ref` 后可跨轮和交接复查。内存反馈也能组织循环，不以该字段定义 loop。嵌套工具、retry、evaluator 都纳入实际 feedback path。

## 4. Eval schema：缺证据必须 fail closed

```json
{
  "verdict": "NotYet",
  "reasons": ["query_lost_on_back"],
  "evidence": [".loop/runs/run-0042/browser-trace.zip"],
  "evaluator": "search-checker-v3",
  "rubric_hash": "sha256:...",
  "input_digest": "sha256:..."
}
```

在本场审计模板中，完整的失败证据会给 `NotYet`；`verdict/reasons/evidence/rubric_hash` 缺一就保留 `unknown`、拒绝自动放行；修复并沿同一路径重测后才可能得到 `Met`。这不是 loop 的存在条件。`Met` 无证据不能进入验收，未知 verdict 不得降级成 true/false。promptfoo 缺 `pass`/无 threshold 反例说明评估器接口本身要测。

## 5. 裁判校验集与反操纵

```yaml
cases:
  - id: known-fail-route
    expected: NotYet
  - id: known-pass-route
    expected: Met
  - id: ambiguous-copy
    expected: human
  - id: adversarial-test-weakened
    expected: NotYet
  - id: human-conflict-01
    expected: record_conflict
record:
  judge_version: search-checker-v3
  rubric_hash: sha256:...
  false_accept: 0
  false_reject: 0
```

至少保留 known-fail、known-pass、ambiguous、adversarial、human-conflict 五类；已知失败测误放行，已知成功测误拒绝，歧义与人工冲突测交人，压力样本测操纵或削弱检查。`false_accept=0` 只是本批样本观察，不是质量证明；METR reward-hacking 样本说明独立 evaluator 仍可能被输入、时钟或代理目标操纵。

## 6. 控制决策与三本账（本场设计，非产品统一状态机）

```text
控制账：观察反馈
  ├─ hard_deny -------------------------→ blocked
  ├─ unknown / missing evidence --------→ 保持未判定；按授权和预算补证据或重试 Eval
  │                                      无法继续则 blocked；合法请求送达待决定才 awaiting_human
  ├─ Not yet met + retryable + budget remaining + no_progress未触发 + expiry未到
  │                                     → running（理由指导下一轮）
  ├─ no_progress / schedule_expiry 触发 → stopping（保全状态并发起停止）
  ├─ Met + artifact complete -----------→ 停止候选；实际退出后记 stopped
  ├─ Impossible ------------------------→ stopping（明确理由并发起停止）
  └─ budget exhausted ------------------→ stopping（保全状态并发起停止）

  stopping + worker/副作用均已退出 ------→ stopped

验收账：unaccepted --指定验收者签认+证据--> accepted
结果账：outcome_pending --真实用户观测--> outcome_met / outcome_not_met
```

三个账各记事件，可同时是 `control=stopped; acceptance=unaccepted; outcome=outcome_pending`。`Met` 不改变验收账；签认也不改写停止原因。`Impossible` 与证据当前不可见要分开，后者按原因记 blocked 或 awaiting_human。各分支保留理由、证据引用与下一责任人；使用者还需定义异常、暂停和恢复的真实实现。

## 7. 资源上限与耗尽前的状态保存

```yaml
budget:
  turns: task_specific
  wall_clock: task_specific
  cost_usd: explicit
  retry_budget: explicit
  deadline: explicit
  nested_paths: [agent, tool_retry, evaluator, scheduler]
checkpoint_before_exhaustion: true
on_exhaustion:
  - persist_state
  - persist_last_feedback
  - write_stop_reason
  - assign_reviewer
  - emit_resume_pointer
```

`max_turns` 只覆盖一个维度；evaluator 或 tool retry 在预算外重调仍可能无限运行。耗尽不是验收通过，优先保全状态并交接。

## 8. 拒绝与审批恢复演练

```yaml
deny_retryable:
  record_reason: true
  next: choose_safe_alternative
  max_retries: project_defined
deny_hard:
  next: blocked
  approver_can_override: false
approval_required:
  reviewer: release-reviewer-7
  request_id: approval-0042
  delivered: true
  delivery_record: inbox-event-0042
  if_request_delivered: awaiting_human
  if_reviewer_unreachable: blocked
  hard_deny: blocked
  requires: [reviewer, request_id, delivered, delivery_record, last_action, evidence_ref, resume_pointer]
```

演练三条授权路径：允许执行；需人批准时记录 approval_required、reviewer、request_id、delivered 和 delivery_record，送达后从同一状态恢复；硬拒绝直接记 blocked，不可被普通批准覆盖。再模拟拒绝后安全替代、无人响应和熔断：未送达记 blocked，送达待决定才记 awaiting_human。父线程须看见子线程最后状态，恢复前复核授权和当前版本。

## 9. 长任务 ledger：不要把三种状态压成 done

```json
{
  "feature_id": "search-42",
  "control": {
    "status": "awaiting_human",
    "stop_reason": "approval_required",
    "reviewer": "release-reviewer-7",
    "request_id": "approval-0042",
    "delivered": true,
    "delivery_record": "inbox-event-0042",
    "last_action_id": "act-0042",
    "resume_pointer": "run-0042/action-0043"
  },
  "acceptance": {
    "status": "unaccepted",
    "accepted_by": null,
    "evidence_link": null
  },
  "outcome": {
    "status": "outcome_pending",
    "owner": "product-owner-7",
    "next_check": "2026-09-29T09:00:00Z"
  },
  "priority": {"old": 2, "new": 1, "changed_by": "release-lead", "reason": "release dependency"}
}
```

此例是合法审批请求已送达而尚未决定，才记 awaiting_human；delivered=false 或入口不可达记 blocked，hard deny 也记 blocked，不能借普通审批覆盖。

本主题建议的控制行，不是公开统一标准。单任务 progress 和 git history 不能自动回答 priority、授权史、阻塞原因和验收人四列。

## 10. 新增授权前故障注入清单

```text
[ ] 删除/削弱测试：机器闸门是否失败？
[ ] 修改 evaluator 输入：是否被拒绝并记录？
[ ] 取消：scheduler 不再派发、worker 退出、side-effect 停止，三项证据是否齐？
[ ] 重复取消/重复事件：是否去重且不重入？
[ ] 让内层 retry 绕过 budget：是否被外层总预算拦住？
[ ] 让 token 换 branch/action/expiry：是否重新授权？
[ ] 恢复时授权已过期：是否重新申请而不是沿用旧批准？
[ ] 让 reviewer 入口不可达：是否进入 blocked 而非假升级？
[ ] 无进展窗口或 expiry 触发：是否停止并保留原因？
[ ] 让外部 outcome 不可见：是否保持 outcome_pending？
[ ] 让人工与 evaluator 冲突：是否停止自动扩大授权并保留样本？
```

这份清单验的是控制链能否拒绝已知坏路径，不证明业务质量、收益或组织可规模化。按本次交接选择适用项，每项都有证据、处理理由和责任人，才有依据减少相应值守。非适用项写明理由，纯动作授权不要求全部完成裁判和结果字段。

## 11. 从示意 YAML 泛化成项目控制面

| 语义不变量 | 搜索案例字段 | CI / 数据管道 / 发布系统的可能映射 |
|---|---|---|
| 目标与终态 | `terminal_state` | build artifact ready / DAG partition complete / release candidate healthy |
| 路径与动作约束 | `constraints`, `scope` | 允许目录 / 允许表分区 / 允许环境与变更类型 |
| 环境事实 | `evidence_ref`, `exit_code`, trace | test report / run manifest / deploy health events |
| 判定 | `verdict`, `reasons`, rubric | gate result / data-quality rule / canary policy |
| 继续资格 | `retryable`, budget remaining | retry class / backfill budget / rollback window |
| 停止原因 | `stop_reason` | failed gate / budget exhausted / policy denied / human pause |
| 权威与责任 | `accepted_by`, reviewer | release approver / data owner / on-call |
| 恢复 | `resume_pointer`, checkpoint | rerun key / partition cursor / rollback or resume version |
| 外部结果 | `outcome.owner`, `next_check` | adoption / freshness / incident-free window |

**先分三层，不要把整份 YAML 当通用标准**：控制不变量（跨领域保留：目标可观察、证据可追溯、判定有理由、停止原因独立、验收有权威、升级可恢复）／承载结构（可变：YAML、JSON、数据库行、事件流、CI artifact）／领域策略（不可直接搬运：阈值、重试次数、谁审批、什么算不可修复）。

**迁移规则**：①先写领域终态与不可变约束，不复制 goal.yaml；②控制动作映射为领域事件；③判定绑定 evidence、判据版本、责任来源；④明确缺证据/未知/拒绝/耗尽是否 fail closed；⑤用领域特有坏样本做负例；⑥演练恢复（进程重启、权限过期、上游延迟、人工冲突）；⑦最后才决定承载。

**三个迁移例子**：

```text
CI：build artifact + test report → gate verdict → retry / block / release approval
数据管道：partition manifest + quality report → freshness/completeness verdict → backfill / pause / owner review
发布：canary health + rollback checkpoint → policy verdict → continue rollout / rollback / incident handoff
```

共享控制语义，不共享阈值、判据或恢复动作。自建运行器的 p95 阈值、重试或拒绝上限可按领域风险、成本和历史基线设计；无基线标待定。现有产品固定不可配置的阈值必须遵守产品实现，例如 B10 的 Claude Code 拒绝预算，不可改成项目自定。个人案例的10轮也不能直接迁移。

## 12. 两个领域的完整迁移例子

### A. 数据管道：从「页面完成」换成「分区可交付」

```yaml
terminal_state: partition=2026-09-28 is complete and queryable
constraints: do_not_overwrite certified partitions; source schema unchanged
feedback: run_manifest + row_count + null_rate + freshness_timestamp
verdict: quality_gate_version=12
continue: retry transient source read or backfill missing partition
stop: certified or budget exhausted
escalate: schema drift / owner decision required
accepted_by: data_owner
resume_pointer: dag_run=...; partition=...
outcome_pending: downstream dashboard freshness not yet observed
```

领域负例不是「按钮坏了」，而是：row count 为零、freshness 超期、schema drift、已认证分区被覆盖——每个负例都要确认同一质量门会失败，且失败原因能回到下一步。

### B. 发布系统：从「产出验收」换成「风险可控地推进」

```yaml
terminal_state: canary meets release policy for the observation window
constraints: deploy only approved artifact; no production schema migration
feedback: health events + error budget + rollback checkpoint
verdict: canary_policy_version=7
continue: expand rollout within authorized slice
stop: policy met, then release_approver signs
escalate: error budget breach / rollback unavailable / conflicting verdict
accepted_by: release_approver
resume_pointer: rollout_id + last healthy checkpoint
outcome_pending: incident-free window not yet complete
```

发布系统的 `stop` 不是「部署命令返回 0」；可能是回滚、暂停或等待观察窗。领域负例：部署成功但错误率超预算、artifact digest 不在批准清单、rollback checkpoint 不可恢复。

## 13. 泛化验收：用变换而不是改名检查

1. **换领域**：同一控制语义映射到数据管道和发布系统，能否说清终态、事实、判定、出口、责任和恢复？
2. **换承载**：YAML 改成数据库事件或 CI artifact，审计信息仍可追溯吗？
3. **换失败类型**：权限过期、外部依赖延迟、判据版本漂移、人工冲突——控制账仍能区分 blocked 与 stopped、验收账能区分 unaccepted 与 accepted、结果账能保留 outcome_pending 吗？

只替换字段名、没定义领域终态/负例/恢复动作的「泛化」是假的。每换一个领域都能保留控制不变量、重写领域策略、并用负例让门失败，才是**语义泛化**。
