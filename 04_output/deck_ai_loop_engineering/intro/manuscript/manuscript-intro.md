## 先读这里：背景、洞察与制作顺序

**听众与任务**：60 分钟入门场，面向听说过 Agent 自动干活、但没跑过反馈循环的业务与管理听众。不要预设他们懂权限策略、评估器或代码驱动。全场从“你离开，它继续跑，回来告诉你完成”开始，回答这句话凭什么可信。

**核心洞察**：自主不是一个总开关，而是分别交出三个决定：允许做哪些动作、是否再开一轮、何时再次启动。每交一个决定都要配相应边界。Feedback 必须参与下一步决策，必要时调整做法，也可支持重查或停止；Goal 与 Eval 在交续跑时才成为系统的条件；停止、产出验收和业务结果不能互相代替。留在人逐轮判断的基线是合理选择，不是失败。

**全案虚构教学案例（统一约定）**：本场只有一个站内搜索分页案。PM 是需求负责人和本例有权验收者；Agent 是执行方；Eval 是按约定分页判据解释证据的评估角色。PM 离开前授权 Agent 在 `agent/search-pagination` 分支加分页，初次只交动作，不自动交续跑；后续章节回看这次交接并演练“如果再交续跑，需要什么”。Agent 生成 PR 草稿与测试结果；真实推送、开远端 PR 需另行批准，本例由 PM 明确批准后才发生，绝不从编辑许可继承。浏览器返回丢查询后，按反馈修正；若触上限，实际停止并保全证据，不能称完成。后续检查通过、签认、上线与新索引唤醒是同案的后续教学阶段或明确对照分支，不是停到上限就自动成功。所有案例角色、状态、字段、分支、命令、时点和参数均为**本场虚构示意／教学设计**，不是已发生事故、真实执行或收益数据；署名来源只支持机制，不是本案例的出处。每页下面的现场判断串说明事件、误判、决定和迁移判断，不另增上屏正文。

**制作阅读顺序**：先读本节与术语表，掌握六章怎样推进问题；再按 N01–N27 读 title/subtitle/content 及展开、接页、知识说明；最后按需要读追问卡与虚构样本。逐页证据备注是限定主张的必要信息，不是额外正文。不能只抽 title 或把 CLAIM 再堆到 content。

**上屏规则**：保留 27 页和页号；title 与本页页名一致，subtitle 等于 CLAIM；content 是必须写出的最小表达，≤3 条，不再从备注增一整档。四处明确 callout 保留署名、日期和中文节选意译。PPT Agent 知识说明不上屏。subtitle 按语义换行，优先在分号或判断转折处分成两行；不重复展示 CLAIM，不用缩小字号容纳额外解释。若同页同时有 callout，先减少装饰或图例，保留正文限定；章节小标不能占据正文区域。表格也有阅读负担，不把备注的大表搬上屏。没有额外章节页，章首 N01/N04/N07/N10/N17/N24 的既有页显示 chapter 同名小标，其余页保留 chapter 字段作为归属。

### N02 · 为什么有人开始「写 Loop」

- chapter: 第一章｜为什么要写 Loop

**CLAIM**：Osmani 将 Loop Engineering 定义为用系统接替人逐轮提示 Agent；系统再根据反馈组织下一步。

**上屏**

- title: 为什么有人开始「写 Loop」
- subtitle: Osmani 将 Loop Engineering 定义为用系统接替人逐轮提示 Agent；系统再根据反馈组织下一步。
- content:
  - PM 先不逐轮提示，演练让 Loop 接手下一步改法。
  - 浏览器返回丢查询，反馈让下一步改法变化。
  - Loop 接手的是接力，不是验收。

**展开**：Agent 是负责执行任务的角色；Loop 是让下一步依据反馈决定的循环，必要时调整，也可按证据重查或停止。Osmani 在 D1《Loop Engineering》中给出的定义是：设计系统，接替人逐轮提示 Agent。后来的 D2《Practical Loop Engineering》再说明系统反复行动、测试结果并调整方法。本页前半讲定义，后半补机制，不把两篇拼成同一句原文。交出去的是逐轮接力，不是业务标准和最终责任；根据反馈尝试调整，也不保证每次修对。

**Callout（上屏，中文节选意译）**：Addy Osmani · 2026-06-07：用系统接替人逐轮提示 Agent。

**来源（页内完整信息）**：Addy Osmani，《Loop Engineering》，2026-06-07，https://addyosmani.com/blog/loop-engineering/

**原文复核（同页备注）**："Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead." 已对照 [evidence-a §4 D1](../../../../02_research/01_agent_engineering/loop_engineering/raw/evidence-2026-09-26-a-originators.md)。反馈补句依据同档 D2《Practical Loop Engineering》（2026-08-14，https://addyosmani.com/blog/practical-loop-engineering/）原文 "repeatedly acts, tests its results and adjusts its approach"；不把反馈补句冒充 D1 定义的逐字原话。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：Loop Engineering 不是把提示词写得更长，而是把“收到结果后如何提示下一步”交给系统设计。
> - 因果关系：Agent 能调用工具，环境返回结果，系统据此组织下一轮；关键是提示接力者换了，不是人的标准消失了。
> - 来源前提：Osmani 的 D1 提供接替逐轮提示的定义，D2 补充行动、测试、调整；二者不能合成一段逐字引语，更不证明收益。
> - 表达必需：对照人逐轮提示与系统接续，只替换接力位置；保留反馈回到下一步的关系。callout 带作者和日期。
> - 易错画法：不画无人监管的永动机，不暗示收到失败就必然修对；不得借用 Boris 或 Peter 署名。

**现场判断串（本场虚构示意／教学设计，不上屏）**：PM 原本每次读失败再提示修法，现在考虑让系统接替；管理者若把接替提示误当接替责任，就会无人定标准。让系统消费返回丢查询的反馈，但保留验收责任。可迁移判断：交接力不等于交最终责任。

- title: 你已经在阶梯上

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：听众日常的“问一句、看一次、再问”已有反馈结构，只是续轮和判断仍由人负责。
> - 关系：Agent 执行一段→人查看结果→人决定下一句；并非人不会自动化，而是当前任务选择保留这两个决定。
> - 场景前提：基线不要求完整 Goal/Eval 机器，但按风险仍要限制动作范围并检查结果。
> - 表达必需：人的查看位置放在两轮之间；第三条传达可以留在这里，不用再配升级动机。
> - 易错画法：不把人工判断画成拖累或落后，不把人查看当成已配置好的自动验收。

**现场判断串（本场虚构示意／教学设计，不上屏）**：回看 PM 离开前的人工基线：Agent 做一段，PM 看查询是否保留再提示；经理若嫌这不够先进，就可能提前撤掉判断。标准未稳定时先保留逐轮查看。可迁移判断：低档是任务控制选择。

  - 无视结果重跑，只是再抽一次卡。

**展开**：反馈（Feedback）是参与下一步决策的信息，可来自工具、产物、人或评估理由。关键不在每轮动作是否不同，而在**下一步是否依据上一轮结果决定**：报错指出按钮失效，就定位按钮；若证据提示瞬时故障，可以按约定重试同一检查；满足条件则形成停止候选。无视结果、固定重问，才比喻为抽卡。retry 不与 Loop 互斥，有依据反馈选择的 retry 可以位于 Loop 内。只保存反馈而不使用，也不足以说明有反馈决策。

**Callout（上屏，中文节选意译）**：Anthropic · 2024-12-19：agent 依靠环境反馈，在循环中使用工具。

**来源（页内完整信息）**：Erik S.、Barry Zhang（Anthropic），《Building effective agents》，2024-12-19，https://www.anthropic.com/engineering/building-effective-agents

**原文复核（同页备注）**："They are typically just LLMs using tools based on environmental feedback in a loop." 已对照 [evidence-b §2](../../../../02_research/01_agent_engineering/loop_engineering/raw/evidence-2026-09-26-b-stop-and-scheduling.md)；这是机制说明，不是质量收益数据。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：不能只数次数或比较动作变没变，要追问证据是否参与下一步决定。
> - 对比关系：瞬时故障证据可支持再跑同一检查；定位到按钮错误可支持修改；满足条件可支持停止。无视反馈固定重跑才是抽卡。
> - 案例前提：人的纠偏、工具输出、Eval 理由都能进入 Feedback。retry 可以在 Loop 内；Anthropic 引语说明机制，不提供收益数据。
> - 表达必需：反馈箭头接到下一步决策，再分向续修、依据证据重查或停止；不要只接日志存储。保留抽卡比喻标识与署名日期。
> - 易错画法：同样动作不代表没有反馈，不同答案也不证明使用了反馈；不画“反馈输入→必然成功”。

**追问**：重试可以是 Loop 的一步；要核对是否按错误类型、证据或约定条件选出了这次重试，而不是无视结果固定重跑。

**现场判断串（本场虚构示意／教学设计，不上屏）**：浏览器观察到返回丢查询，PM 又补充保留搜索词的理由；Agent 若无视结果只重跑测试，才是盲重跑。先定位返回状态；仅瞬时故障证据才支持按约定 retry。可迁移判断：判断是否用反馈，不看动作是否重复。

**接到下一页**：当反馈还要用于恢复和审计，就需要留成可复查记录。

### N08 · 规则要能限制实际执行

- chapter: 第三章｜先交动作，不交判断

**CLAIM**：要求模型遵守规则，不等于运行时能阻止越界。

**上屏**

- title: 规则要能限制实际执行
- subtitle: 要求模型遵守规则，不等于运行时能阻止越界。
- content:
  - Agent 尝试改授权范围外文件；“只改 search”写在提示里，不等于拦住它。
  - 策略件限制 Agent 只能改该分支；推送仍被挡住。
  - 规则能否执行，要看实际 Harness，不看口头承诺。

**展开**：提示词里的“不许越界”是给模型看的要求；它会影响选择，却未必能拦住一次真实执行。可执行策略件是运行器实际读取的规则，沙箱或 allow/deny 再限制能做什么。Agent 周围这套工具、权限、执行和检查环境常被称为 Harness；但不能只说“有 Harness”就认定安全。Cursor 文档把自动审查与安全边界分开，我们只用它说明这个区别。

**追问（数字仅备注）**：François Zaninotto 在《The State of AI Harness Engineering 2026》（2026-09-24，https://marmelab.com/blog/2026/09/24/the-state-of-ai-harness-engineering-2026.html）转述 arXiv:2608.27443 的 113 人研究：预写规则组比逐动作审批组少拦 20.1 个百分点的坏动作。这是转引研究，不是“提高安全”；本轮 arXiv 原页受网络限制未重取，不作直接论文引语。另：Anthropic《How we built Claude Code auto mode: a safer way to skip permissions》（John Hughes，2026-03-25，https://www.anthropic.com/engineering/claude-code-auto-mode）报告自家用户批准 93% 权限提示。两个数字来源与样本不同，不混成因果结论，不外推。

**来源（页内完整信息）**：Cursor，《Run Modes》，活文档无发布日期，观测 2026-09-30，https://cursor.com/docs/agent/security/run-modes

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：写给模型看的要求，与运行时能阻止动作的规则，不是同一种保障。
> - 因果关系：偏好影响选择倾向；沙箱、allow/deny 等执行机制限制实际能做什么。可执行策略件是后者读取的规则，不是某种固定文件格式。
> - 案例前提：Cursor 区分自动审查与安全边界，不能外推到所有产品。Harness 指周围的工具、权限、执行和检查环境，不是安全性的别名。
> - 表达必需：让两类规则分别指向“倾向”与“可执行范围”；Cursor 只作第三条的产品例子。
> - 易错画法：不画提示词形成保护罩；不将研究数字上屏或改写为安全提升，完整来源与样本限定保留备注。

**现场判断串（本场虚构示意／教学设计，不上屏）**：Agent 尝试触及授权范围外文件；PM 若只凭提示里的“不要越界”就放心，误把偏好当隔离。用运行策略实际拦截，并验证越界被拒。可迁移判断：写了规则，还要查谁执行它。

### N09 · 一次授权，绑定三项边界

- chapter: 第三章｜先交动作，不交判断

**CLAIM**：一次批准绑定动作、目标范围和有效期；其中任何一项改变，都要重新批准。

**上屏**

- title: 一次授权，绑定三项边界
- subtitle: 一次批准绑定动作、目标范围和有效期；其中任何一项改变，都要重新批准。
- content:
  - 准许编辑 ≠ 准许提交 ≠ 准许推送 ≠ 永久推送。
  - 换分支、换任务、从「改文件」变成「提交」——重新问。
  - 公开报告中的边界漂移示例：小范围修改授权，被误用作更大范围发布许可。

**展开**：允许改这个分支，不等于允许推送到另一个分支；允许今天做一次，也不等于以后永久允许。这里的“目标”指动作作用的文件、分支或系统范围，不是下一章的 Goal。动作、目标范围、有效期任何一项变了，就重新批准。公开 issue #95749 只用来说明边界漂移的报告形态，不称为已验证事故。

**章末口头回扣**：少点几次允许之后，每轮是否继续，仍由你决定。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：批准不是给 Agent 一张永久通行证，而是批准一次有边界的动作。
> - 关系：动作类型、目标范围、有效期三者共同限定许可；编辑换成推送、目标换分支、时间过期，都需要重新核准。
> - 案例前提：公开 issue 报告用于说明授权漂移可能长什么样，不能当已验证事故或发生率证据。
> - 表达必需：用编辑≠提交≠推送强调许可不能继承；目标指分支、文件或系统对象，不与下一章 Goal 混用。
> - 易错画法：不画成权限等级逐层包含；不要让批准图标同时覆盖多个动作、目标和无限时间。

**现场判断串（本场虚构示意／教学设计，不上屏）**：Agent 从编辑分页转向提交、推送，甚至换 main；PM 若沿用旧许可，是授权漂移。动作、范围或有效期一变就重新核准。可迁移判断：批准绑定三边界，公开报告只是形态参照，不是本案事故。

**接到下一页**：到这里，动作档只减少打断，判断还在你手里。再交续跑，门票就变贵了。

### N14 · 三个出口各管一件事

**CLAIM**：只有未达成、可重试且未触出口时才继续；其他状态按原因停止或交人。

**上屏**

- title: 三个出口各管一件事
- subtitle: 只有未达成、可重试且未触出口时才继续；其他状态按原因停止或交人。
- content:

**展开**：分页返回后查询丢了，若问题可重试且尚未触及无进展、时间或资源出口，就把失败位置和原因回传下一轮。未达成不意味着无限继续。条件满足可形成停止候选，仍待验收；明确不可能就停止并交接。unknown、超时也停并交人，但记录为无法判定，不能写成 Impossible。达到无进展或资源边界则按对应停止原因保全状态并交接。

> **PPT Agent 知识说明（不上屏）**

> - 关系：仅未达成、可重试且未触出口才带理由继续；条件满足为停止候选；不可能和无法判定同样停并交人，却不是同一判定。

**现场判断串（本场虚构示意／教学设计，不上屏）**：在可恢复副本故意制造返回丢查询；检查却放行时，PM 若仍交续跑，就依赖了无效裁判。先修检查，恢复副本后再跑正常路径。可迁移判断：负例拒绝只证明这类错误，不证明全覆盖。

### N20 · 第三层：不能靠削弱测试过关

- chapter: 第五章｜它说完成，还要查什么

**CLAIM**：保住判据，检查通过才有原本的意义；Agent 应修分页行为，而不能自行删断言或跳过测试。

**上屏**

- title: 第三层：不能靠削弱测试过关
- subtitle: 保住判据，检查通过才有原本的意义；Agent 应修分页行为，而不能自行删断言或跳过测试。
- content:
  - 误判：为过关删掉“返回保留查询”断言。
  - 纠偏：保留断言，修分页行为再验证。
  - 过关靠修产物，不靠削弱检查。

**展开**：仍是同一分页案例：失败断言是“返回后查询仍保留”，不能删掉断言或加 skip 得到通过。后态保留单测、API 与端到端判据，修改分页行为后重跑。执行方不能自行改目标、测试描述或裁判；必要的测试变更由有权的人复核并重新演练。保护可以由权限、受保护文件或差异检查实施，具体做法留手册，不塞上屏。

**来源与边界（备注）**：Justin Young（Anthropic），《Effective harnesses for long-running agents》，2025-11-26，https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents 。原文 "It is unacceptable to remove or edit tests" 是强措辞提示；配套 quickstart 仅在 prompt 约束，源码未强制校验（[evidence-l](../../../../02_research/01_agent_engineering/loop_engineering/raw/evidence-2026-09-28-l-quickstart-code.md)，观测 2026-09-28）。本场要求控制面保护是工程建议，不冒充产品默认。

> **PPT Agent 知识说明（不上屏）**

> - 案例前提：虚构分页案例沿用同一断言。Anthropic 强措辞原文是提示约束，quickstart 源码未硬校验；控制面保护是本场建议。

### N21 · 人的反馈要能改变下一轮

- chapter: 第五章｜它说完成，还要查什么

**CLAIM**：人的业务信息和纠偏理由，应参与后续行动的决定。

**上屏**

- title: 人的反馈要能改变下一轮
- subtitle: 人的业务信息和纠偏理由，应参与后续行动的决定。
- content:
  - PM 纠偏：用户会返回修改搜索词；先确认是否纳入本次 Goal。
  - 有权者确认标准后再重查；Agent 不自行改 Goal。
  - 人补业务上下文，并负责歧义与验收。

**展开**：人知道业务怎么运转、用户有什么习惯，而 Agent 可能只看到当前任务。Andrew Ng 所说的上下文优势就是这种信息差。纠偏时把缺失信息说清；拒绝后若仍允许继续，给出可回流的理由，帮助选择更安全的下一步。硬拒绝、停止或撤销授权时不承诺再开一轮，也不能靠追问绕过。若因此需要改 Goal 或判据，由有权者明确变更并重新核查；不是悄悄换标准。保留人的入口，不等于要求每轮机械审批。

**Callout（上屏，中文节选意译）**：Andrew Ng · 2026-06-30：人类对用户和产品场景仍有上下文优势。

**来源（页内完整信息）**：Andrew Ng，《Loop Engineering: My 3 Key Loops for Building 0-to-1 Products》，2026-06-30，https://x.com/AndrewYNg/status/2071988145667928442

**原文复核（同页备注）**："humans as having a significant context advantage over current AI systems — we know a lot more than the AI system about the users and the context the product has to operate in"。已对照 [英文原文 §Loop 2](../../../../01_seed_reference/reference/kol/_raw_loop_engineering/andrew_ng/raw_ng_x_post_en.md)。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：人的价值不只是在终点打勾，还在把系统不知道的业务事实与拒绝理由补进下一步。
> - 因果关系：人掌握用户、场景和取舍，Agent 可能只看到当前工件；信息不对称未解决，自动检查再多也可能朝错误方向优化。
> - 案例前提：分页都通过，但客服知道用户会在返回后继续修改搜索词；新增需求应由有权者明确改标准，不偷偷变更判据。
> - 表达必需：允许继续时，人的反馈接回后续决策；硬拒绝或停止分支不画自动回环。环境反馈路径仍保留，Ng 的 callout 强调上下文信息，不强调人天然优越。
> - 易错画法：不把人画成每轮审批机器，也不画完全静默为成功；原文不能扩展成停止条件的定义。

**现场判断串（本场虚构示意／教学设计，不上屏）**：PM 补充用户返回后还会改搜索词；Agent 若静默把 Goal 改成只保留旧词，就把业务纠偏误当自行改标准。确认这是现有解释还是新增要求，有权者批准变更后再检查；硬拒绝不绕开。可迁移判断：人的理由能改变下一步，但不自动授予新权。

### N22 · Stop ≠ Accepted

- chapter: 第五章｜它说完成，还要查什么

**CLAIM**：超时、资源耗尽或模型收尾，只说明控制流停止；验收要由有权的人依据证据另行签认。

**上屏**

- title: Stop ≠ Accepted
- subtitle: 超时、资源耗尽或模型收尾，只说明控制流停止；验收要由有权的人依据证据另行签认。
- content:
  - 记录：查询仍丢而达到上限，还是检查通过而停止。
  - PR、测试结果交 PM 验收，另记人和证据。
  - 没验收证据，就保持“未验收”。

**展开**：Stop 说明控制流停止，Accepted 说明有权者依据证据签认。`停止原因=轮数上限，验收=空` 与 `停止原因=目标检查通过，验收=评审人＋证据` 完全不同；还有检查通过但尚待签认的情况。记录要保留这种差别，不能从停止自动填上完成。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：同样的“停了”可以来自达成、上限、无进展或中断，不能自动解释为已交付。
> - 关系：Stop 记录控制流为何停；Accepted 记录有权者依据哪些证据验收。停止原因与验收状态应是两列，不是同一个字段。
> - 案例前提：分页跑到上限仍未验收；目标检查通过也只形成可提交验收的证据。签认缺失就保持未验收。
> - 表达必需：用两组记录对照停止原因与验收人/证据，第三条约束未知状态的写法。
> - 易错画法：不用 Stop→Accepted 的必然箭头，不把耗尽进度条画成完成勾；“由人签”指有权责任人，不要求另增人数。

**现场判断串（本场虚构示意／教学设计，不上屏）**：本次达到教学资源上限，查询仍丢，驱动实际退出；Agent 若把“停了”报“完成”，PM 不应签认。控制账记上限停止，验收账保持未验收；后续修复须明确恢复决定。可迁移判断：停止原因与验收依据分别记录。

**接到下一页**：产出已经签认，是否就能说业务变好了？

### N23 · 产出和业务结果是两本账

- chapter: 第五章｜它说完成，还要查什么

**CLAIM**：PR、测试和日志支持产出验收，不自动证明业务变好；采用率、满意度等外部结果，要另设观测与责任人。

**上屏**

- title: 产出和业务结果是两本账
- subtitle: PR、测试和日志支持产出验收，不自动证明业务变好；采用率、满意度等外部结果，要另设观测与责任人。
- content:
  - 产出账：PR、测试、日志，PM 依据证据签认。
  - 结果账：用户是否继续使用分页，另设观测窗。
  - 看不见时写“待观测”，不编造收益。

**展开**：分页检查通过，可以形成产出证据；有权者签认后，是按约定交付。用户是否使用、满意度是否提高，要上线后再看，并写清谁在什么时候复查。没看见就记待观测，不提前填成功或失败。上一页的控制账，加上本页的验收账与结果账，共三本账，并列记录而不是成功流水线。三种记录责任可以由同一人承担，不要求三个岗位。

**章末口头回扣**：一次停下是什么意思已经分清，最后看看谁能让系统下次自己起跑。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：产物按约定交付，不自动说明用户采用或满意；能复查的产出与需要观测窗的业务结果要分账。
> - 关系：测试、PR、日志支持产出验收；采用率、满意度要上线后由负责人在指定时间复查。尚看不到不是失败，也不是成功。
> - 案例前提：分页路径通过并被签认，仍可能少有人使用；这不推翻产出证据，却不能声称体验已改善。
> - 表达必需：本页两栏并列，结果账保留待观测；讲者明确回扣上一页的控制账，三本账共同成立，不画三步成功流水线。
> - 易错画法：PR 合并不自动填验收人，不把待观测画成负面；三个责任可以同一人承担。

**现场判断串（本场虚构示意／教学设计，不上屏）**：同案后续由 PM 明确恢复，修复后路径通过并获签认；经理若立刻声称用户满意度提高，是把交付偷换成收益。结果账由 PM 另定观测窗，尚无用户数据就待观测。可迁移判断：控制、验收、结果三账并列，不串成功流程。

### N25 · 每一档，人守的责任不同

- chapter: 第六章｜决定交到哪一步

**CLAIM**：交出的决定不同，人要守的标准、权限和接手责任也不同；人不是被移出了 Loop。

**上屏**

- title: 每一档，人守的责任不同
- subtitle: 交出的决定不同，人要守的标准、权限和接手责任也不同；人不是被移出了 Loop。
- content:
  - 基线：PM 发起、判断并接手分页结果。
  - 动作档：PM 守分支授权；续跑档：PM 守判据、验收和结果。
  - 唤醒档：PM 守总账、取消、接手和“还要不要跑”。

**展开**：交动作后，人守执行范围；交续跑后，人更多守判据、方向与验收；交唤醒后，还要守跨次运行的预算、取消与接手。人的位置变了，责任没有凭空消失。阶梯只帮我们逐项读懂，真实系统仍要分别核查三面，不能因为能定时启动就认为前面都已落实。

**四问回扣（备注；本场教学映射）**：

| 面 | 谁启动下一轮 | 谁判断完成 | 谁能改变系统 | 出错谁停下接手 |
|---|---|---|---|---|
| 基线 | 人 | 人按证据判 | 有权的人 | 当前负责人 |
| 动作档 | 人决定续轮 | 人 | 执行方只改授权范围；策略由有权者改 | 策略拒绝／风险点到指定人 |
| 续跑档 | 条件与控制器 | 裁判判条件、人显式验收 | 执行方改产物，不自行改判据／权限 | 上限、无进展、歧义到指定人并保全状态 |
| 唤醒档 | 时间表或事件 | 另查本次检查与验收，不能从唤醒推断 | 另查动作策略与目标授权 | 取消传达到在途任务，再到指定负责人 |

这些答案用于查交接面，不是某产品的全套默认行为。

> **PPT Agent 知识说明（不上屏）**
> - 认知变化：自动化改变人的工作位置，不消除标准、权限、验收和接手责任。
> - 对比关系：基线人逐轮发起与判断；交动作后守权限；交续跑后守判据与验收；交唤醒后还须守总预算、取消和接手。
> - 案例前提：这是本场教学分工，真实系统可独立组合三面；责任可由同一人承担，但每个问题都要有明确答案。
> - 表达必需：三条作全场回顾，四问表只给讲者备查，不上屏挤成大矩阵。
> - 易错画法：不画人逐级淡出直到消失；不让时间调度自动包含执行权限和完成裁判。

**现场判断串（本场虚构示意／教学设计，不上屏）**：PM 不再逐轮提示，却仍要确认分支权限、分页标准和上限后接手；经理若把 PM 从责任表删除，是误把自动化当责任消失。逐面登记谁启动、谁判断、谁能改、谁接手。可迁移判断：责任位置改变，不等于退出。

# 一套可以现场拆开的实战样本（不上屏）

> 完整虚构样本：给站内搜索增加分页。**动作单对应动作档护栏，goal/eval 工件对应续跑档门票，触发与取消对应唤醒档；基线是人发起与判断**。数值、分支名、命令与路径都是教学模板，不是已运行的真实仓库证据，不是厂商默认值，也不是实测收益。部署时替换成项目实际入口与检查。

## 1. Goal 工件：先把「做完」写成可判定对象（续跑档门票）

```json
{
  "goal_id": "search-pagination-v1",
  "terminal_state": "结果列表第二页可打开、可返回、查询条件不丢失",
  "checks": [
    "npm test -- search-pagination",
    "npm run e2e -- search-pagination.spec.ts：浏览器搜索→第2页→返回，查询与结果对应正确；退出码0且报告留存"
  ],
  "constraints": [
    "只改 agent/search-pagination 分支",
    "不得修改公共 API",
    "不得删除或放宽既有测试"
  ],
  "stop_clause": "两次连续无改善或达到项目资源上限时停止并保全状态",
  "outcome": "用户采用率另行观测，不作为本轮自动 Met"
}
```

四个细节：终态不是「搜索体验变好」；检查不是「模型觉得可以」；约束是不可越过的边界；采用率当前不可见，只能是 `outcome_pending`。

## 2. Action 工件：每次只拿一张可审计的动作单（动作档护栏）

```json
{
  "action_id": "act-0042",
  "principal": "search-agent",
  "action": "edit",
  "target": "src/search/pagination.ts",
  "branch": "agent/search-pagination",
  "scope": ["src/search", "tests/search"],
  "expires_at": "2026-09-28T18:00:00Z",
  "approval": "reviewer-17",
  "denied": ["commit", "push", "public-api-change"]
}
```

把 `edit` 改成 `push`、branch 改成 `main`、目标移到 `deploy/`，都算新动作重新审批——一次批准不能靠文字相似度继承。

## 3. Feedback 工件：把环境返回物落盘

```sh
set -o pipefail
mkdir -p .loop/runs/run-0042
npm run e2e -- search-pagination.spec.ts \
  > .loop/runs/run-0042/stdout.log \
  2> .loop/runs/run-0042/stderr.log
status=$?
printf '{"run":"run-0042","exit_code":%s,"commit":"%s"}\n' \
  "$status" "$(git rev-parse HEAD)" \
  > .loop/runs/run-0042/result.json
exit "$status"
```

在**本可审计示例模式**中，下一轮先读 `result.json`，再读失败日志，最后按证据选动作或停止。不是所有 Loop 都必须先读文件：会话内也能直接消费工具反馈。记录模式只是本例的恢复与审计实现。

## 4. Eval 工件：反馈和判定分开

```json
{
  "eval_id": "eval-0042",
  "goal_id": "search-pagination-v1",
  "evidence": [
    ".loop/runs/run-0042/result.json",
    ".loop/runs/run-0042/stderr.log"
  ],
  "verdict": "NotYet",
  "reasons": ["query_lost_on_return"],
  "evaluator": "search-checker-v3",
  "rubric_hash": "sha256:...",
  "missing_fields_are": "reject"
}
```

`exit_code=0` 只是环境事实；`verdict` 须覆盖页面路径、API 约束和测试保护。缺字段时拒绝，不猜。

## 5. 三本账并列记录：控制、验收、业务结果

```text
控制账 control：running / stopped / blocked / awaiting_human
  continue候选：NotYet且可重试，未触无进展、资源、时间或授权有效期出口
  stop候选：Met或出口触发；仅实际驱动退出后才记stopped
  blocked：权限/依赖阻塞，或合法人工请求尚未送达
  awaiting_human：合法请求已送达指定人，保留送达记录与恢复入口
验收账 acceptance：unaccepted；有权者依据证据签认后才记accepted
结果账 outcome：outcome_pending / observed；按观测窗、责任人与证据另记
```

三账是并列记录，不是 running→stopped→accepted→outcome_pending 的成功流水线。`Met` 只形成停止候选，驱动可能尚未退出；产出签认也不由控制流自动生成，不要求业务结果先观测完成。外部结果可一直待观测，与任务是否停、产出是否验收分别回答。继续条件还要检查授权是否有效；硬拒绝不能伪装成等待批准。

## 6. 负例演练：先证明门会拒绝

在可恢复副本中造出已知错误分页行为，或用不是真实凭据的 dummy key 演练对应扫描，跑正常任务会运行的同一条检查：非零退出码、明确失败位置、证据位置、下一轮可读的修复理由。恢复后再跑正常路径。演练成功只证明这一类错误拦得住；若检查仍放行，先修检查，不交续跑权。不能仅把测试期望改错后测出失败，就声称已验证真实分页故障覆盖。

## 7. 熔断交接单：人真正接得住才叫升级

```yaml
feature_id: search-42
state: awaiting_human
stop_reason: missing_dependency
last_action: edit src/search/pagination.ts
last_feedback: query_lost_on_return
accepted_by: null
outcome_status: outcome_pending
evidence_link: .loop/runs/run-0042/result.json
reviewer: product-owner-7
delivery_record: "legal-request-17 delivered to product-owner-7 at 2026-09-28T18:02:00Z"
resume_pointer: run-0042/action-0043
next_check: 2026-09-29T09:00:00Z
```

这是允许请求人工协助的依赖阻塞示例，不是硬拒绝后的升级通道。请求合法、已送达指定人并有 `delivery_record`，才记 awaiting_human；未送达时仍是 blocked。`reviewer` 为空、送达无记录或 `resume_pointer` 指不到状态，就不能称已交接；硬拒绝不能改名等待审批。

## 8. 现场定档顺序（v3：从审计改为定档）

1. 先答四问：谁启动下一轮／谁判断完成／谁能改变系统／出错谁接手——现在的答案是什么？
2. 对答案缺的那格分别查：动作授权面→续跑目标／裁判→唤醒触发／取消。三个面可独立组合，不从 `/loop` 推断前两面成立。
3. 每配一种检查，先用对应的已知错误验证它会拒绝。
4. 答不出又不急着升：留在当前级——这是控制决策，不是失败。

## 9. 这套字段怎么泛化

不要从字段名出发，从控制问题出发：

| 控制问题 | 示例字段 | 换系统仍要保留的语义 |
|---|---|---|
| 要达到什么 | `terminal_state` | 可观察的产出终态 |
| 不能做什么 | `constraints` | 不可越过的范围与路径约束 |
| 凭什么判断 | `checks` / `evidence` | 外部可复查的证据和判据 |
| 谁能做什么 | `approval` / `scope` | 动作、目标、有效期和授权主体 |
| 为什么下一步这样走 | `verdict` / `reasons` | 判定及理由回到下一行动 |
| 现在停在哪里 | `state` / `stop_reason` | 控制状态与停止原因分开 |
| 谁接手、怎么恢复 | `reviewer` / `resume_pointer` | 责任人、恢复位置和所需证据 |
| 产出是否带来结果 | `outcome_status` | 外部结果独立于产出验收 |

**最小迁移法**：先用纸填这八个问题；再映射到已有工具；最后用一个已知错误和一次合法拒绝演练，验证证据确实参与继续、停止或交人的决定。
