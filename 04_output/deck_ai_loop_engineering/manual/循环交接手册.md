# 循环交接手册（Loop Handover Manual）

> 把哪个决定交给循环，交之前配什么护栏，它说做完了凭什么放行。两场 Loop Engineering talk 的听众操作件。
>
> **单文件双篇**：入门篇给没跑过循环的人——读完那一篇就够；高级篇给在跑循环的人——按时刻翻，从任何一节进来都能用。卷首的状态语汇表是全书唯一的语汇权威，所有篇章说「完成」「停止」时都指回它。

---

# 卷首 · 用法与状态语汇

## 怎么用这本手册

1. **卷首必读**：参数锚约定、档位语言、状态语汇表——三页纸，全书的地基。
2. **入门篇顺序读**：要不要交 → 反馈怎么回流 → 交动作 → 写续跑门票 → 看停止、验收与结果。五节读完可作判断；高级篇按使用时刻查，动手配置时再翻。
3. **高级篇按时刻翻**：交动作、交续跑、交唤醒、升一档、它说做完了、它停了、可选方向——你在哪个时刻，翻哪一节。每节自足，不依赖其他节。
4. **先看「什么时候不要」，再看怎么配**。每节的退回条件与正面步骤同权重。交出去之前先确认自己不在退回区。

## 参数锚约定

- 手册里每条具体参数（阈值、时长、费用、命令语法、默认值）都带**「（产品与版本，观测日期）」**。产品会改默认值，抄进配置前先核对你手上的版本。
- **docs 与源码打架时，以源码为准**；手册会显式标出两个值与各自出处。
- 没有锚的参数，手册写「以你所用版本的官方文档为准」——那是提醒你去找，不是省略。
- **教学数值一律不可抄进生产**：下文虚构任务、阈值、轮次、时长、日志时间、ID、配置与演练记录均为示例，不是推荐值；必须按本任务风险、基线和资源重新设定。作者原文的例句与案例数字也不是生产建议。
- **版本锚不是引入日期**：Claude Code 活文档锚 v2.1.228／v2.1.283 对应 auto mode 默认行为，v2.1.269 对应 `/goal` 恢复逻辑（观测 2026-09-26），不能据此断言所有参数在这些版本引入。Managed Agents 的 `managed-agents-2026-04-01` 是 API beta header／文档锚，不是发布日期或正式可用承诺（观测 2026-09-30）。
- **无精确版本的活文档只用于核机制**：命令、枚举和配置键以链接文档的观测快照为依据，部署前核本机版本；缺少精确参数锚的时限、阈值与默认值不在这里作产品保证。步骤组合、记录模板与检查单均为**本手册编排（非产品默认）**。

## 档位语言

手册说「档」，只指**交出去的决定**是哪一种：动作（高级一）、续跑（高级二）、唤醒（高级三）。档不是成熟度等级：

- 升档不是毕业，退档不是失败；按任务的风险、可逆性、验收成本选位置，随时允许退回。
- 没有任何通用刻度说「跑 N 轮必须人看」。能写成门的是事件：动作类别、拒绝预算、无进展、歧义、升级后是否有人接得住。
- **逐面审计，不按命令名累加**：`/goal` 只证明条件续跑机制，`/loop 5m` 只证明定时唤醒机制；是否交出动作审批、是否有目标裁判，要另查权限策略与停止实现。三个面可以独立组合。

每一步交接前，四个问题要能写在纸上：

1. 谁启动下一轮？
2. 谁判断完成？
3. 谁能改变系统？
4. 出了错，谁能及时停下并接手？

写不出来，就是护栏还没配好，先别交。

## 状态语汇表（全书唯一权威）

任何状态都有「最多能声称什么」。看到把左列偷换成右列的说法——那是误读，或事故的开始。

| 你看到的 | 它最多说明 | 不能偷换成 |
|---|---|---|
| 检查通过（测试退出码 0、lint 干净、构建成功） | 写在条件里的检查，在该环境、该版本上通过 | 需求无遗漏、无回归、业务会变好 |
| 裁判判「尚未达成」（Not yet met） | 当前证据未满足约定条件；理由可指导下一轮 | 已失败；或可以无视预算、权限继续跑 |
| 裁判判「达成」（Met） | 该裁判按**它可见的证据**判约定条件成立 | 人已验收、生产业务已改善 |
| 裁判判「不可能」（Impossible） | 该裁判判断约定条件无法满足，终止 | 所有尚不可见的结果都已证明不可能 |
| 检查失败 / 证据不足 | 该次验证不支持「达成」，进入修复或升级 | 任务本质不可能；也不可静默改判达成 |
| 轮数、时间、预算、成本耗尽 | 资源到边界，必须停或交人 | 任务已完成或已失败 |
| 拒绝熔断 / 人工暂停 / 停止（stopped） | 循环不再运行，状态可交接 | 产出已被接受 |
| 阻塞（blocked） | 当前缺依赖、权限或可达接手入口，不能继续 | 已升级成功、已失败或已验收 |
| 等待人（awaiting_human） | 合法请求已送达指定人、尚待决定；恢复位置已记录 | 已获批准；无人可达时也不能写这个状态 |
| 人或专家验收（accepted） | 有权验收者对指明版本、范围、样本和时间窗**显式签认，并留证据** | 检查通过自动 accepted；或自动推广到所有用户和任务 |
| 外部结果待观测（outcome_pending） | 产出可能已验收，但外部结果尚不可见，责任人和复查时点已登记 | Impossible、业务失败或业务已达成 |
| 上线后业务指标改善 | 观测窗口内的外部结果 | 离线检查可替代上线观测；或可归因于循环设计本身 |

四条硬边界（这张表的骨架）：

1. **停止 ≠ 接受**：超时、耗尽、拒绝、模型自己收尾，都只是控制流停了；是否验收另算。
2. **产出 ≠ 结果**：可观察的产物（PR、测试、构建）与外部业务结果分账记录；结果尚不可见时写「待观测」，不写达成。
3. **达成 ≠ 验收**：裁判只在其判据与可见证据范围内工作；可以辅助评内容，不能替有权验收者签认真实需求。人的责任是定标准、处理歧义与分歧，不是宣称机器绝不能评品味。
4. **反馈要改变后续动作**：工具结果、运行输出或人的纠偏要到达下一步；落盘工件是本手册采用的**可审计实现**，不是 loop 的定义条件。人不必每轮介入，但关键歧义、越界、验收和标准变更必须有可达入口。

### 三本账怎么记（本手册编排，非产品默认）

| 账 | 记录 | 对应信号 |
|---|---|---|
| 控制流账 | `run_state / verdict / stop_reason / blocked_reason / owner / resume_pointer` | `Not yet met` 与 `Met / Impossible` 是裁判信号；`blocked / awaiting_human / stopped` 是运行或交接状态，分别记，不互相覆盖 |
| 产出验收账 | `artifact_version / acceptance_status / accepted_by / accepted_at / accepted_scope / evidence_ref` | 未签认保持未验收；仅有检查通过或 `Met` 不能填写 `accepted` |
| 外部结果账 | `outcome_status / observation_window / outcome_owner / next_check / evidence_ref` | 尚不可见填 `outcome_pending`；观测后只声称该窗口、该样本内的结果 |

三本账可由同一人维护，但责任分别明确；不能用一句「完成了」代替它们。

**一条总警告**：无人值守地跑，和无人值守地对，是两件事。授权与调度解决「跑」，不解决「凭什么放行」。每一次交接：护栏先于放权。

# 入门篇 · 判断层

> 给没跑过循环的读者。五节读完，你能做四个判断：这个任务交不交、反馈回路搭没搭、第一个台阶怎么迈、目标怎么写才算数。要动手配完整机器的那天，再去高级篇。

## 入门一 · 要不要交给循环

### 三问诊断（前两问任一答「否」→ 先别上循环；第三问决定恢复与跨次边界）

| 问题 | 答「否」意味着什么 | 下一步 |
|---|---|---|
| 1. 停止条件依赖上一轮的结果吗？ | 不依赖的是重试（retry），不是循环 | 写脚本或手动重跑，不建循环 |
| 2. 单次运行受控吗？ | 不受控时，循环只是把错误复制得更快 | 先治单次运行（约束写进环境：沙箱、审批、测试），再回来 |
| 3. 重启或交接时，状态能复原吗？ | 仅靠临时对话，恢复与审计不可靠；不代表会话内反馈循环不存在 | 会话内可先有界试行；跨会话或需审计时补文件 / git / 持久日志 |

### 完成条件体检（第二道门）

- ✅ 能写成可观察句子，且检查确实覆盖目标：测试退出码 / 本任务的性能阈值 / 目标队列状态 → 具备目标门票；还需授权、裁判校验、无进展与资源出口，才可交续跑（高级二）
- ⚠️ 产出可核、外部结果不可见：把自动停止范围收窄到产出（如「PR 已生成且检查通过」），业务结果另行观测（高级五）
- ❌ 写不出（「做到生产就绪」「设计变好」）：拆小、人工标样、或交人——**不靠增加轮次硬跑**

坏目标的典型（署名原话）："a vague goal would be 'keep going until this UI design is good'. What does that mean? Good to who? How is it being evaluated?"（Addy Osmani《Practical Loop Engineering》，2026-08-14）

### 判定实例（三个任务过三关，判定过程写全）

**实例 A｜重命名 2,000 张截图（教学示意，不可抄生产）**：第一问就死——停止条件不依赖上一轮结果（第 1,733 张和第 1 张毫无关系），这是批处理。判定：**不交**，写一个小脚本。错法：为它配循环脚手架——拿大炮修桌子，还得自己擦炮膛。

**实例 B｜修 flaky 测试到三连绿**：三问全过（这次没修好才知道下次改哪＝依赖上轮反馈）；完成条件可观察。判定：**交**，按入门四的模板填本任务的条件。下例三连绿与八轮上限是教学示意，不可直接用于生产，也不能证明 flaky 已根除：

```text
Fix the flaky cart-total test until `npm test` exits 0 on three consecutive runs.
Do not modify unrelated tests.
Stop after 8 turns.
```

**实例 C｜「把体验改到用户满意」（指标数字为教学示意，不可抄生产）**：完成条件写不成可观察句子。判定：**先拆**——拆出可观察的代理指标：

| 拆出的子目标 | 可观察吗 | 去处 |
|---|---|---|
| Lighthouse 性能分 ≥ 92 | ✅ 可测 | 可交循环 |
| 支付页崩溃率 < 0.1% | ⏳ 需指定样本与观测窗口 | 未观测时记待观测；可靠采集后再按窗口判定 |
| 用户满意度提升 | ⏳ 外部结果，延迟可见 | 待观测，业务负责人复查（高级五） |

**同一个任务拆完，一部分交、一部分不交——这是常态，不是失败。**「先拆」不是拖着不办，是把「满意」翻译成机器能对照的句子、把翻译不出去的部分诚实留给人。

### 什么时候不要

1. **单次小任务不建复杂循环脚手架**——先按风险配最小护栏（范围、权限、检查、资源上限），不要等失控才治理；只在真实重复问题出现后增加复杂度。
2. **存量代码库慎用无限循环**——Ralph 式裸循环作者的适用警告："There's no way in heck would I use Ralph in an existing code base"（Geoffrey Huntley，发布 2025-07-14，观测 2026-09-26）。这是作者对其 greenfield 做法的警告，不是所有循环的禁令。
3. **标准会随样本变化的任务**（品味、审美、法律判断）：保留人工检查点，不塞进自动达成。
4. **别把品味和判断一起委托**——"check yourself, that you are not delegating the taste and the judgment to your agent. You're delegating the task, and then you are actually checking back that it's meeting your bar."（Osmani，同上）

### 交到哪一档（本手册路线）

| 你想交出的决定 | 去哪节 |
|---|---|
| 只减少逐动作审批 | 入门三（最小版）→ 高级一（完整规程） |
| 让它自己跑多轮到目标 | 入门四（门票）→ 高级二（完整机器） |
| 让它定时 / 按事件自己起跑 | 高级三 · 交唤醒 |

**来源注**：[Anthropic《Building effective agents》](https://www.anthropic.com/engineering/building-effective-agents)（发布 2024-12-19，观测 2026-09-26）给出环境反馈、检查点与上限；[Geoffrey Huntley《Ralph Wiggum as a “software engineer”》](https://ghuntley.com/ralph/)（发布 2025-07-14，观测 2026-09-26）给出适用警告；[Addy Osmani《Practical Loop Engineering》](https://addyosmani.com/blog/practical-loop-engineering/)（发布 2026-08-14，观测 2026-09-27）给出目标与品味例句。诊断、分流及最小护栏为本手册编排（非产品默认）。

## 入门二 · 反馈让循环成为循环

循环和抽卡（比喻）的关键区别：**后续动作有没有被已有反馈改变**。工具结果本身就可以构成反馈，不必先落盘才算循环；为了恢复与审计，本手册建议将关键证据留存。反馈有两路，但不要求人每轮发言：

| 路 | 是什么 | 落成什么 |
|---|---|---|
| 环境反馈 | 退出码、失败日志、运行产物 | 关键证据留存成可复查工件，下一轮读取后再选动作 |
| 人的反馈 | 纠偏、品味、拒绝的理由 | 在检查点、歧义、越界或验收时介入；影响后续工作的理由留存并回灌 |

- 「我刚才试过了」不是可复查证据——原始工具结果与留存工件才支持审计。
- 完全静默的无人值守不是目标：接手、验收、复查都是人的反馈。
- 高手的隐性判断不能被当作无人值守的默认能力；把标准、检查点和接手责任显式写出来。

### 消费前的三追问（本手册编排，非产品默认）

拿到任何一条反馈——退出码、报告、人的话——让它改变下一步动作之前，先过三问：

| 追问 | 答不出时怎么办 |
|---|---|
| 1 它属于本次工作吗？ | 核版本锚：目标 / 工件 / 判据 / 环境任一变了，它就是旧结果，不进本轮 |
| 2 下一步依据它作什么决定？ | 指不出谁读、进哪个分支、什么去向（修复 / 重查 / 有界重试 / 停止 / 交人）＝只是记录，不是反馈 |
| 3 人改要求后它还适用吗？ | 目标或标准变更后，旧结论按历史处理，按新边界重验 |

**旧版绿灯对照（教学示意）**：昨天的优化通过报告写着「Lighthouse 92」（数值为教学示意，不可抄生产）；今早目标页从 `/dashboard` 换成了 `/dashboard/v2`。昨天的 92 分**还是真的**，但它属于昨天的页面——只留作历史，不签今天的验收，按当前页重测。诚实边界：产品级的「旧版结果自动批量失效」**未见**任何一手机制；「旧结果只作历史」是工程纪律，照着做靠人核版本锚，不是产品默认行为。

**什么时候不要**：暂时没有可靠检查或标准仍在变化，先保留人审的有界探索；可以用人工标样、rubric 或反馈记录，不以「没有检查命令」判定不能循环。

**来源注**：[Anthropic《Building effective agents》](https://www.anthropic.com/engineering/building-effective-agents)（发布 2024-12-19，观测 2026-09-26）；证据落盘、人工入口安排、消费前三追问与旧版绿灯对照为本手册编排（非产品默认）；「旧版结果自动批量失效」未见一手机制，此处如实登记为工程纪律（Aider / Claude Code 截断等机制反例见高级二来源注，观测 2026-10-04）。

## 入门三 · 第一个台阶：交动作

从基线走到动作档：把逐条点「允许」交出去——**省掉的是打断，不是判断**，每轮结束看的还是你。

| 处置 | 例 |
|---|---|
| 允许直行 | 读目标文件、跑定向测试 |
| 沙箱内跑 | 写指定目录、无网络出站 |
| 必须人批 | commit、外部调用 |
| 硬拒绝 | push、删库、生产配置 |

两条纪律：①安全边界落实为**可执行策略与隔离**，提示词只作辅助，不当硬边界；②一次批准绑定**动作 × 目标 × 有效期**，任何一个变了都算新动作。

**什么时候不要**：动作类别列不全就先别放大授权；未列类应拒绝或转人，并用负例核实际默认处置，不能假定所有产品都会默认放行。完整规程（演练、变异测试、偏好与隔离两层）在高级一。

**来源注**：[Cursor《Run Modes》](https://cursor.com/docs/agent/security/run-modes)（Cursor 3.6 changelog 为模式锚，文档观测 2026-09-30）；[Claude Code issue #95749](https://github.com/anthropics/claude-code/issues/95749)（用户事故报告，观测 2026-09-27）。分级表与绑定授权为本手册编排（非产品默认）。

## 入门四 · 门票：目标怎么写才配循环

> 这一节是**交续跑档的门票**：只有决定让系统自己跑到目标为止才需要它；留在基线或只交动作，不需要完成条件自动续跑。

### 目标模板（官方三要素＋上限子句）

```text
目标（一个可度量终态）：
  "All tests in test_status.py pass" / "the endpoint returns 200 with the new field"
检查（声明式——怎么证明：哪条命令、哪个退出码、哪份输出）：
  "`npm test` exits 0" / "`git status` is clean"
约束（路径上不许变的东西）：
  "no other test file is modified"
上限子句（推荐常备）：
  "… or stop after 20 turns"（轮次或时间均可）
```

（模板要素：[Claude Code《Keep Claude working toward a goal》](https://code.claude.com/docs/en/goal)，文档恢复逻辑锚 v2.1.269，观测 2026-09-26；模板组合为本手册编排，非产品默认。20 turns 是官方例句，不是默认上限或生产建议。）

**作者全例**（Addy Osmani，发布 2026-08-14，观测 2026-09-27）——包含可度量终态、声明式检查、约束、无进展中止、轮次上限；所有数字为作者示例，不可直接用于生产：

> "/goal Refactor the data-fetching layer in Dashboard.tsx until Lighthouse performance score is >= 92 and LCP is under 1.8s as shown by the Lighthouse CLI output. Do not change the public API of any hooks. Each turn must improve at least one reported metric; abort if two consecutive turns show no improvement. Stop after 10 turns."

### 三值判定（续跑的出口）

| 裁定 | 含义 | 下一步 |
|---|---|---|
| Not yet met | 约定条件未达成 | 继续，**评估理由作为下一轮的指导** |
| Met | 条件在裁判可见证据内成立 | 停止本轮——注意：**Met ≠ 验收**（见卷首对应语汇） |
| Impossible | 裁判判条件无法满足 | 停止并交人；「业务结果还看不见」不得误报为 Impossible |

### 写法红线

1. **含糊目标不配循环**（见入门一的坏目标例句）。
2. **别把品味和判断一起委托**——委托任务，检查是否达到你的标准。
3. **别让特定评估器越权**："It doesn't look at the content to see if it's good or bad in any way, shape, or form. All it does is examine the conversation transcript to see if the hard rules you specified have been met."（Osmani，发布 2026-08-14，观测 2026-09-27）描述其讨论的评估机制，不是「机器不能评内容」的通则；人仍定标准并处理分歧。
4. **续跑信号可以比入口目标弱**："The harness just needs some signal that lets it continue. It does not have to be objective or binary, it just has to be useful enough to drive another iteration."（Armin Ronacher，发布 2026-06-23，观测 2026-09-30）——中间推进信号只要「够用」，最终接受仍需对应证据；两句别混成一句。

**什么时候不要**：完成条件写不成可观察句子 → 回入门一分流；无进展出口和上限子句配不出来 → 没有兜底的续跑是烧钱循环（配法在高级二）。

## 入门五 · 读信号：三个最常见的假完成

凌晨两点你回来，值班日志里有三条信号。逐条对照卷首语汇表，看它**最多**说明什么：

**信号 1｜`npm test 退出码 0`**
最多说明：写在条件里的检查在该环境通过了。不能偷换成：需求没遗漏、业务会变好。测试只覆盖写进条件的那部分——条件没写的，它一言不发。

**信号 2｜裁判给了 `Met`**
最多说明：约定条件在**这个裁判可见的证据里**成立。不能偷换成：人已验收。裁判看的是它被喂的证据——证据不全，它裁得再果断也是错的。人还要对照真实需求看一眼产出。

**信号 3｜`已运行 10 轮，上限触发，循环停止`**
最多说明：资源到边界，必须停或交人。不能偷换成：任务完成或失败。轮数上限是资源熔断，不是质量分；它只约束该驱动的后续轮次，不保证在途请求、子代理或外层调度立即停止计费。

**三连问带走**：停止了吗？验收了吗？外部结果看见了吗？——**三个是三件事**，日志里一个词的差别就是三种完全不同的处境。

**什么时候不要**：有人拿「运行次数」「唤醒成功率」「代理数量」当质量证据 → 那些是活动量，不是成果；证据链怎么看，高级五。

# 高级篇 · 操作层

> 给在跑循环的读者。七节各是一个使用时刻，从任何一节翻进来都能用；语汇一律指回卷首。

## 高级一 · 交动作

> 你受够了每个动作都点一次「允许」。这节管交出**动作审批**之前怎么划边界：授权面是分级处置表，不是开关。

### 本节最小交接记录（本手册编排，非产品默认）

```text
任务 / 版本：<task_id、目标分支或产物版本>
授权：<动作、目标、批准人、有效期、策略版本>
暂停：<stop_reason、decision_source、denial_reason、待执行动作与参数>
责任：<owner、reviewer、接手渠道、下次复查时点>
恢复：<thread_id、父线程可见性、evidence_ref、resume_pointer>
       不支持持久恢复时明确写「无」，从已验证基线重启，不宣称断点恢复。
```

失败先阻止待执行动作；策略硬拒绝保持禁止。合法请求已送达指定人填 `awaiting_human`，入口不可达填 `blocked`；恢复前重核动作、目标与授权有效期。

### 划面五步（本手册编排，非产品默认）

| 步 | 做什么 | 检查 |
|---|---|---|
| 1 列动作 | 列全本任务会发生的动作类别：读 / 写 / 测试 / commit / push / 部署 / 外部调用 | 未列类先拒绝或转人；用负例核运行器实际默认处置 |
| 2 标处置 | 每类标四级之一：**允许直行 / 沙箱内跑 / 必须人批 / 硬拒绝**，写进**可执行的策略件**（allow/deny 规则、沙箱配置），不写在提示词里 | 以提示词收尾的规则不是规则（见下） |
| 3 保高风险 | auth / billing / 破坏性变更保留当场审批与随时中断 | 高风险类不进 allowlist |
| 4 演练 | 低风险可回滚仓库里故意触发一个面外动作 | 记录里真实发生 propose → decision → tool result；不拿「最终测试通过」冒充审批通过 |
| 5 验收 | 抽一条已放行的动作，答出：谁批的？批的哪个目标？有效期到哪？ | 答不出＝授权依据不可审计，暂停该类动作并核实际策略 |

### 三条铁则

**1. 一次批准绑定「动作 × 目标 × 有效期」**（本手册编排，非产品默认）：[Claude Code issue #95749](https://github.com/anthropics/claude-code/issues/95749) 是单用户公开报告，根因未确认，只作作用域测试样例：

> "Editing files must not imply authorization to commit."（准许编辑 ≠ 准许提交）
> "Authorization to commit must not imply authorization to push."（准许提交 ≠ 准许推送）
> "Authorization for one push must not become standing authorization for later pushes."（一次 push ≠ 永久 push）

换分支、换 feature、从 edit 变 commit/push，都算**新动作**，重新请求授权。报告描述：一个两行的窄授权被当成大功能发布的许可，14 个文件直推 main；报告不证明平台普遍发生率。

**2. 拒绝是引导信号，不是终点。** 拒绝作为工具结果返回，附带「找一条更安全的路」的指令；Claude Code auto mode 在反复拒绝后暂停并恢复人工提示，无界面环境则终止进程。**这是动作拒绝预算，不是轮数上限**。精确阈值与是否可配置，以所用版本的 [Permission modes](https://code.claude.com/docs/en/permission-modes) 为准；本手册不把文档默认行为锚 v2.1.228／v2.1.283 当作拒绝阈值引入版本（观测 2026-09-26）。停机不等于接手人已收到请求。

**3. 审批有三个动作，不只是放 / 拦**：approve / **edit** / reject（[LangChain《Human-in-the-loop》](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)，文档 commit `933a2f9217f6293a54fa59d40ce69b619aaa1172`，观测 2026-09-27）——「改了再跑」最容易被忽略，也最常用。

### 偏好与隔离是两层

- **偏好规则**（如 Cursor `permissions.json`）：管**倾向**批准 / 拦截什么；
- **执行隔离**（如 `sandbox.json`）：管**实际能碰到**什么（路径、网络）。

官方原话：Auto-review "is not a security boundary"（[Cursor《Run Modes》](https://cursor.com/docs/agent/security/run-modes)，模式锚 Cursor 3.6，发布 2026-05-29；文档观测 2026-09-30）。`Run Everything` 模式每个工具调用自动运行、**无沙箱、无分类器**——它交出的是动作审批权本身，启用前单独评估，不是本节的默认形态。**宽 allow 规则永远不能代替真正的执行隔离。**

### 写了规则 ≠ 有授权面（实测数据）

- [François Zaninotto《The State Of AI Harness Engineering 2026》](https://marmelab.com/blog/2026/09/24/the-state-of-ai-harness-engineering-2026.html)（发布 2026-09-24，观测 2026-09-26）转引 [arXiv:2608.27443](https://arxiv.org/abs/2608.27443)：113 人比较中，预写规则组相较逐动作审批组**少拦 20.1 个百分点**的坏动作。依据为该博客转引，不声称本手册已核论文全文或复现实验。
- **93% 是另一来源与样本**：[John Hughes／Anthropic《How we built Claude Code auto mode》](https://www.anthropic.com/engineering/claude-code-auto-mode)（发布 2026-03-25，观测 2026-09-26）说 Claude Code 用户批准了 93% 的权限提示；不能将该产品观察并入上述 113 人试验，也不是行业普遍批准率。
- 同文审计：391 个仓库里只有 **12 个**提交 deny 规则；这是仓库可见配置的统计，不证明其余运行时完全没有边界。
- "A rule that ends in a prompt isn't a rule." 是 Zaninotto 的评论，手册将其落实为「提示词不能代替执行边界」，不抹掉人工审批本身的作用。
- 升级不可达的真实案例：用户在对话里反复明确授权同一个动作，拒绝依然不可翻案（claude-code issue #67519）——拒绝合理性之外，**升级可达性是第二个独立的控制问题**。

### 划定实例（修一个支付回调 bug 的授权面，填好的样子）

**第 1–2 步产物**——动作类别 × 处置 × 落点：

| 动作类别 | 处置 | 落在哪个策略件 |
|---|---|---|
| 读 `payments/`、`tests/` | 允许直行 | read 类 allowlist |
| 跑 `npm test` / `npm run lint` | 允许直行 | exec allowlist：只列这两条精确命令，不写 `npm *` |
| 改 `payments/webhook.ts` 与对应测试 | 沙箱内跑 | 沙箱可写路径＝本仓 `payments/`、`tests/`；无网络出站 |
| `git commit`（本分支） | 必须人批 | PR 描述里的 commit 门 |
| `git push`、部署、改 `prod/*` 配置 | 硬拒绝 | deny 规则 |
| 调外部支付沙箱 API | 必须人批 | 凭证注入由人完成，密钥不进上下文 |

**第 4 步演练日志长什么样**（示意，核对这三行真实发生过）：

```text
[10:02:11] propose  : bash(git push origin fix/cart-total)
[10:02:11] decision : DENY（rule: push/* — hard deny, no override）
[10:02:12] result   : push 被策略拒绝；该动作在硬拒绝清单
```

有这三行＝审批真实走过策略件。只有「最终测试通过」＝没验过——测试通过和审批通过是两条不相干的证据链。

**审批策略的概念形态**（本手册编排，非产品默认；**整段是伪代码，不可执行，不是 LangChain API**）：

```text
# 伪代码：全部键、变量与取值只表达处置含义
interrupt_policy = {
    "write_file": True,          # 需要人决定：approve / edit / reject
    "read_data":  False,         # 该教学任务的允许直行类，不代表所有读取安全
    "git_push":   "approve_only" # 自造占位值：需要批准，不允许编辑
}
```

`approve_only` 不是官方枚举；不能把前两项与自造项混合复制进运行配置。要看的是**粒度**：审批细到工具名与参数。可运行实现须按 [LangChain《Human-in-the-loop》](https://docs.langchain.com/oss/python/langchain/human-in-the-loop) 的 `interrupt_on / allowed_decisions`、checkpointer 与 thread 配置重新构造（文档 commit `933a2f9217f6293a54fa59d40ce69b619aaa1172`，观测 2026-09-27），并实测暂停与恢复。

### 什么时候不要

- 动作类别列不全（第 1 步做不完）→ 先别放大授权；未覆盖动作按拒绝或转人处置，实际默认行为须负例验证。
- 高风险动作的审批入口不可达（人不在、父线程看不见请求）→ 保持逐动作审批。
- 所用产品只有偏好规则、没有真正的执行隔离 → 授权面收窄到「可回滚」类动作。

**来源注**：[Cursor 3.6《Auto-review Run Mode》](https://cursor.com/changelog/auto-review)（发布 2026-05-29）与 [Run Modes](https://cursor.com/docs/agent/security/run-modes)（观测 2026-09-30）；[Anthropic《How we built Claude Code auto mode》](https://www.anthropic.com/engineering/claude-code-auto-mode)（发布 2026-03-25）与 [Permission modes](https://code.claude.com/docs/en/permission-modes)（文档默认行为锚 v2.1.228／v2.1.283，观测 2026-09-26）；[LangChain《Human-in-the-loop》](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)（文档 commit `933a2f9217f6293a54fa59d40ce69b619aaa1172`，观测 2026-09-27）；[issue #95749](https://github.com/anthropics/claude-code/issues/95749)／[issue #67519](https://github.com/anthropics/claude-code/issues/67519)（用户报告，观测 2026-09-27）。划面、交接与演练为本手册编排（非产品默认），不构成安全保证。

## 高级二 · 交续跑

> 单轮跑稳了，你想让它**自己跑到目标为止**——交出的是「本轮之后是否再开一轮」。这节从目标到失败交人完整配置；不用先读入门四。动作审批仍另查，续跑命令不自动放宽权限。

### 先填这张续跑契约（本手册编排，非产品默认）

```text
目标：<一个可观察的产物终态，不把尚不可见业务结果写入自动达成>
检查：<命令或 rubric、正确环境/页面、目标版本、原始输出位置>
约束：<允许修改的路径、不可变接口/测试/判据、动作与网络边界>
无进展出口：<比较什么进展信号、何种停滞触发暂停，理由回传>
资源上限：<时间/轮次/费用、重试和子代理计费范围、谁覆盖跨次总额>
裁判：<类型、实现/模型版本、判据版本、样本集版本、输入 evidence_ref>
反馈准入：<上一轮结果适用当轮的核查——目标/工件/判据/环境版本未变才可用；旧结果降级为历史，不作放行依据>
预期消费者：<谁读这条结果、它进入哪个控制分支——清单字段、修复分支或指定人的线程>
失败去向：<修复 / 重查 / 有界重试 / 停止 / 交人，各自触发条件；失败交人一行的 owner 与渠道是「交人」的具体落点>
失败交人：<owner、reviewer、合法接手渠道、下次复查时点>
恢复：<task_id、run_id、artifact_version、thread_id、resume_pointer>
      不支持持久恢复则写「无；从已验证基线重启」。
```

继续只在「未达成＋授权有效＋资源未到界＋有推进依据」时成立。`Met` 停目标并送产出验收；证据缺失、判据冲突、无进展或资源到界先暂停，不默认成功。请求送达指定人填 `awaiting_human`，入口不可达填 `blocked`，保留理由与证据，不自动重试危险动作。

**教学填好例（全部数字是示例，不可抄生产）**：目标＝Dashboard 性能分至少 92、LCP 低于 1.8s；检查＝固定页面与固定环境的 Lighthouse CLI 原始输出；约束＝不改 hook 公共 API、不改判据与测试；无进展＝连续两轮无指标改善就暂停；资源＝十轮或团队核定的费用上限先到者；裁判＝独立检查者、判据版本 `dashboard-perf-demo-v1`；接手＝评审者甲通过本任务评审线程；恢复＝当前 commit＋原始报告＋已验证暂停指针。数值沿 Osmani 作者例句教学，不是 Claude Code 默认值。

### 反馈要落成基建（可审计实现，非 loop 定义）

循环和抽卡（比喻）的区别：后续动作有没有被已有反馈改变。本手册建议的最小链路（本手册编排，非产品默认）：**命令 → 退出码＋原始输出 → 留存证据（evidence_ref）→ 准入核查 → 指定消费者消费 → 记录去向**。四步：

1. **留存**：原始输出落到可复查位置，只存指针不复制日志；
2. **准入**：下一轮先核结果适用当轮（目标 / 工件 / 判据 / 环境版本未变），旧结果降级为历史；
3. **消费**：指定的读者读它，进入实际控制分支——「模型说读过」不算消费；
4. **记录**：写一行去向（修复 / 重查 / 有界重试 / 停止 / 交人）与理由。

最小反馈记录（本手册编排，教学填好例，全部值不可抄生产；记录轮内反馈消费明细，不替代卷首三本账）：

```text
本次目标/工件版本/检查环境：dashboard-perf-demo-v1 ＋ commit a1b2c3d ＋ 固定页面与固定环境
实际执行的检查及原始结果位置：Lighthouse CLI，第 3 轮原始输出 → runs/lh-turn3.txt
结果是否适用及理由：适用——判据与页面未变；第 2 轮结果不适用（那轮改了公共 API），已按历史存档
去向与理由：修——第 1 轮 88 分（教学示意），下一轮改数据层
后续复验位置：runs/lh-turn4.txt（产出后回填）
```

两条不变纪律：数据管道读结构化结果文件，不解析自然语言终端输出；嵌套工具、retry、evaluator 都要纳入实际反馈路径——内层通过、外层无限重试仍会失控。

缺 / 错反馈处置（本手册编排；未核机制如实写「未见」，反例为源码机制观测、非实际执行验证）：

| 症状 | 先查什么 |
|---|---|
| 没产生（结果不存在却像发生过） | 查执行件：检查是否真的配置并运行——有产品在「开了自动测试但未配测试命令」时把结果记为通过，未执行与通过在结果通道里同值（Aider，源码走读，观测 2026-10-04） |
| 没送达（产生了但下一轮看不见） | 查截断 / 摘要：长输出会被截断且压缩会丢关键事实（Claude Code 截断须附引导指令；压缩不总是把清晰指令传给下一个 agent——一手负面句，均观测 2026-10-04）；精确上限以所用版本官方文档为准 |
| 错关联（结果存在但不属于本次） | 核版本锚：目标 / 工件 / 判据 / 环境版本对不上的，按历史处理；平台级「旧版结果批量失效」未见，靠人核 |
| 没消费（红灯打出来没人读） | 指定消费者与去向：裁决要落到固定字段或分支（如清单 `passes` 字段），不进会随对话丢失的摘要 |

### 裁判选型（五式，按场景选一）

| 裁判 | 适用 | 风险 |
|---|---|---|
| 人判（品味） | 探索、清单语义撑不住 | 不可规模化 |
| 文件清单逐条判定 | 目标可枚举（见下节） | 清单本身要保护 |
| 独立小模型每轮判定 | 会话内目标 | 裁判自身可信度要校验 |
| 干活模型自判 | 缺少独立检查时的弱基线，不声称是多数产品默认 | 必须配保护＋熔断补偿 |
| 被审批方提出、审批方判定 | 越界动作 | 审批方可能被操纵（红队实证） |

选型次序：优先机器可核；必须人判的，把判断点集中在门上。

### 保护裁判四件

1. **锁定验收基线，检查不能被削弱**：指定测试与判据由写权限或钩子保护；删除、跳过或放宽断言不能换来合格。合理新增或调整测试须独立审查后纳入新基线；提示词可说明要求，但不构成执行隔离；
2. **可考虑 JSON 清单**：Anthropic 在该实验中观察到相较 Markdown 更少不当改写；这是作者经验，不是格式提供安全隔离（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)，发布 2025-11-26，观测 2026-09-26）；
3. **裁判输入防操纵**：完成裁判必须看真实证据。动作审批分类器可采用更窄输入；Claude Code auto mode 只看用户消息与工具调用，剥掉模型自述和工具输出，称 "reasoning-blind by design"（[auto mode 工程文](https://www.anthropic.com/engineering/claude-code-auto-mode)，发布 2026-03-25，观测 2026-09-26）。**这是动作审批机制，不能直接拿来遮蔽完成裁判所需的测试输出**；
4. **看真实证据不看转述**：带运行 ID、目标版本与原始输出的测试 / 扫描记录。

### 目标可枚举时：进度清单七步

粗目标 → 逐条 feature（JSON 结构，初始全部 `passes: false`）→ 三件套（清单＋进度文件＋初始 commit）→ 每轮固定开场（定位目录 → 读 log 与进度 → **选最高优先级未完成项** → 先过基线：环境留在坏状态时先修它）→ **一次只做一件** → 该前端案例的完成判定须走用户路径（单测或 curl 可证明各自覆盖条件，不能单独证明浏览器交互）→ 干净收尾（描述性 commit＋进度更新）。**只允许改 `passes` 字段。**

清单条目长这样（结构样例，Anthropic 长程 harness 实录，观测 2026-09-26；实际项目一例清单 200+ 条）：

```json
{
  "category": "chat",
  "description": "a user can open a new chat, type in a query, press enter, and see an AI response",
  "steps": ["render chat page", "submit query", "assert response visible"],
  "passes": false
}
```

官方反例对照："declares victory on the entire project too early" → 设清单；"marks features as done prematurely" → 认真测试后才翻 passing。

### 走一遍（一份 goal 的三轮，教学示意非产品日志）

用本节上面的 Lighthouse 教学契约跑三轮，看每道闸各拦什么；数值不可直接用于生产：

```text
第 1 轮  改数据层 → Lighthouse 88 分（< 92）
        裁判：Not yet met（评估理由回传：「performance 88, LCP 2.4s」→ 下一轮知道改哪）

第 2 轮  分数 93、LCP 1.7s ——但 diff 显示改了 useCart 的 public API
        约束检查：违例（"Do not change the public API of any hooks"）
        裁判拒判 Met：分数达标、路径犯规；指标不检查 API，另核 diff 与兼容性证据

第 3 轮  恢复 API、改内部实现 → 93 分、LCP 1.7s，固定目标页与环境，API 兼容检查通过
        裁判：Met（完整条件与约束均成立），目标停止；实际运行退出另记控制账
        指定验收者复核版本与证据后签认，外部结果仍待观测
```

**第 2 轮是整套机制存在的原因：分数会达标，犯规不会被分数看见。**

### 预算的语义（别读错数字）

预算是**花费暂停阀**，不是「达成」的同义词。[Claude Managed Agents《Budgets》](https://platform.claude.com/docs/en/managed-agents/budgets) 的官方示例写 `"max_list_cost": {"amount":"125","currency":"USD"}`，**125 是美分，即 $1.25**（API beta header／文档锚 `managed-agents-2026-04-01`，观测 2026-09-30）。金额仅为官方示例，不可抄生产；触顶 `stop_reason=budget_reached`、状态 `idle`，在途请求可稍超额完成，启动新工作的事件返回 HTTP 400；提高或移除预算会恢复暂停工作，须先重核授权；**按会话计，不等于跨次总额**。

### 判停权要追到代码（不看博客看源码）

某官方 quickstart 的驱动循环**最小源码片段**长这样（[Anthropic `claude-quickstarts/autonomous-coding` 官方仓库](https://github.com/anthropics/claude-quickstarts/tree/main/autonomous-coding) 的 [主循环源码](https://github.com/anthropics/claude-quickstarts/blob/main/autonomous-coding/agent.py)，源码 blob 锚 `8856d40`，观测 2026-09-28；这是 demo，不是完整实现或生产默认）：

```python
while True:
    iteration += 1
    if max_iterations and iteration > max_iterations:   # 该驱动的显式上限退出分支；异常/人工中断另算
        print(f"Reached max iterations ({max_iterations})")
        break
    # 成功时 run_agent_session 恒返回 ("continue", response) ——没有完成分支
```

进度条打印 `passing/total` 是**给人看的**（`count_passing_tests` 读清单的 `passes` 字段），驱动层没有 `passing == total` 的停机判断；源码函数参数 `max_iterations=None` 表示该 demo 的默认无限，不能当产品通用默认；「不可改测试」只写在提示词里，驱动层不校验。该 demo 的打印文案 “will run until completion” 没有对应的驱动层完成分支；这与 Claude Code `/goal` 是不同实现，不能混为一谈。源码还可能因异常或人工中断退出。**交续跑之前，先找到你家驱动循环的 `break`、完成判定和异常分支在哪里。**

### 什么时候不要

- 反馈无法改变后续动作，或没有可复查的证据 / 标准 → 先保留人工、有界试行，补最小记录与检查；不是靠增加轮次解决。
- 无进展出口和上限子句配不出来 → 没有兜底的续跑是烧钱循环。
- 你的裁判就是干活的那个模型、又没有保护四件 → 自判＋无保护是最弱一极，配齐再交。

**来源注**：[Anthropic《Effective harnesses for long-running agents》](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)（发布 2025-11-26，观测 2026-09-26）支持 feature 清单、逐条验证和保护经验；[Claude Managed Agents《Budgets》](https://platform.claude.com/docs/en/managed-agents/budgets)（文档锚 `managed-agents-2026-04-01`，观测 2026-09-30）支持预算状态语义；[Anthropic 官方 quickstart `agent.py`](https://github.com/anthropics/claude-quickstarts/blob/main/autonomous-coding/agent.py)（源码观测 2026-09-28）支持 demo 的反例。裁判选择、契约、失败交人、反馈准入与消费记录、缺错反馈处置为本手册编排（非产品默认）；反馈断点反例（未执行与通过同值、截断丢事实）依一手源码走读与网页一手引句，观测 2026-10-04，Aider 机制依源码、非实际执行验证。

## 高级三 · 交唤醒

> 任务跑完一轮就停，你想让它**到点或按事件自己再起跑**——交出的是「何时再跑」。本节只证明唤醒面；不自动证明动作审批已交出，也不自动证明目标条件、结果或验收。定档实例必须逐面核对。

### 本节最小唤醒记录（本手册编排，非产品默认）

```text
任务 / 版本：<task_id、deployment/automation 版本>
触发：<cron、事件、时区、初始事件；链接官方配置或真实调度器>
状态：<scheduler 状态、next/upcoming run、run/session/worker ID>
取消：<停止请求、调度器已停派、worker 已退出的证据>
副作用：<最后一次外部写入、幂等键、账单/告警/commit 检查>
责任：<owner、夜间接手渠道、下次复查时点>
恢复：<session/event/run ID、resume_pointer；不支持则写「无」>
```

先核调度器、worker 和副作用三面，再声称「停了」或「已取消」。没有可查询的调度器或 worker 证据，记录无法确认并阻塞相应继续动作；只有合法请求已送达指定人，才写 `awaiting_human`，入口不可达则写 `blocked`。不靠空的 `upcoming_runs_at` 推断取消。

### 触发器选型

| 方式 | 下一轮何时开 | 何时停 |
|---|---|---|
| 条件驱动（`/goal` 式） | 上轮结束、闲置检查点、自动重试到期 | 条件满足 / 判不可能 / 需人修 / 显式清除 |
| 时间驱动（`/loop` 式） | 时间间隔到 | 你停它，或它判工作完成 |
| 脚本驱动（Stop hook） | 上轮结束 | 你的脚本或提示词决定 |

**`/loop` 三种拍法**（Claude Code 官方文档，观测 2026-09-26）：

- `/loop 5m check the deploy`——固定间隔＋提示词（命令与 `5m` 是官方示例，不是生产推荐）；
- `/loop check the deploy`——间隔由产品动态选择；精确范围与默认行为以所用版本的 [scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks) 文档为准，不把示例区间当通用参数；
- `/loop`——无提示词，读内置维护提示词或项目级 `.claude/loop.md`（项目级优先）。内置维护提示词的范围封顶：继续未完工作 → 照料当前分支 PR → 清理，**不开范围外新动作**；push / 删除等不可逆动作必须核对会话里的授权仍覆盖本次动作与有效期。

三档调度面：**云上例行任务｜桌面定时｜会话内 `/loop`**。具体最小间隔、恢复能力和费用以你所用产品版本的官方文档为准；缺少精确版本锚不在此写死数字。auto mode 不在此列——它只管轮内审批，不开新轮。

### 两种运行边界（最容易用错的一条）

| | 会话内定时 | 跨会话持久任务 |
|---|---|---|
| 活在哪 | 当前会话；**会话退出即失效** | 云端调度器；本地会话关了它还在 |
| 状态 | 会话内 | 必须另有持久化（进度文件、日志、事件 ID） |
| 停止 | 退出会话 / 停止命令 | **取消要同时到达调度器和运行中的 worker** |

官方原话划界："loops are session-scoped … If you need something that outlives your session, /schedule runs it in the cloud."（Addy Osmani《Practical Loop Engineering》Fine print，2026-08-14）

### 跨会话的额外门槛（缺一不交）

1. **持久状态**：重启后从哪读目标、进度、上次结果——有触发器不等于有持久化；
2. **取消传播**：单用户公开报告——用户显式关掉自动化，"the kill did not propagate to the actual tmux sessions"（claude-code issue #46787）。**面板标「已关闭」不算停**：核对调度器不再派新任务、既有 worker 确已退出、外部副作用不再发生；
3. **硬上限**：Claude Code scheduled tasks 文档的当前示例语义包含自动过期与未续排的 fallback wakeup；具体时长必须按所用版本的 [scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks) 核对（文档观测 2026-09-26）。本手册不把文档数字推广为云任务或其他产品默认；云任务上限另查平台。
4. **可达的人工接手**：谁能在半夜取消它、看到它正在做什么。

### 同一任务的两种配置（部署监视）

**会话内（教学示例，不是生产配置）**：开着会话敲 `/loop 5m check the deploy`——五分钟一醒；合上电脑它就没了。具体间隔、权限和恢复语义以所用版本官方文档为准。

**跨会话**（[Claude Managed Agents scheduled deployments](https://platform.claude.com/docs/en/managed-agents/scheduled-deployments) 的 **deployment Markdown 形式片段**：YAML frontmatter＋初始消息正文；API beta header／文档锚 `managed-agents-2026-04-01`，观测 2026-09-30。部署监视是教学改写，占位值须替换，不能原样执行）：

```markdown
---
name: Deployment monitor
agent: agent_<provided-by-platform>
environment_id: env_<provided-by-platform>
schedule:
  type: cron
  expression: "<your cron expression>"
  timezone: <your IANA timezone>
---
Inspect the deployment status. Report findings; do not change it.
```

将片段保存为 `deployment.md`，官方 CLI 入口是 `ant apply deployment.md`（上述 API／观测锚；执行前核当前 CLI 版本、凭证、真实 agent/environment 与权限，例值不是生产建议）。该官方形式要求至少一个初始 `user.message` 或 `user.define_outcome` 事件；此处不把自造的 `initial.user.message` YAML 键声称为真实 API。创建后核真实 deployment 的 `status`、`last_run_at`、`upcoming_runs_at`，并核 session/worker 与副作用；空的 `upcoming_runs_at` 只能说明查询未返回下一次计划，不能单独证明取消。Managed Agents 的会话状态 `idle / running / rescheduling / terminated` 中，预算暂停是 `idle`，不是完成也不是销毁。

### 取消核对三步（对着真实事故写；空 `upcoming_runs_at` 不充分）

```text
1. 调度器：确认 deployment 已暂停/取消且不再派新任务；结合 status、last_run_at、upcoming runs 与调度器审计日志
2. worker  ：确认在跑的进程真的退出——
   报告描述：任务已关闭，"the kill did not propagate to the actual tmux
   sessions"（issue #46787）；查进程表/会话列表，不是查开关
3. 副作用：确认外部世界不再被碰（新 commit、新 PR、新告警、新的云账单行）
```

三步都过，才可以说「停了」。面板绿了或 `upcoming_runs_at` 为空都只是第 0 步。取消核对是本手册编排（非产品默认），不提供安全保证。

### 无人值守变体（高风险场景，门槛另加）

到点跑只证明「醒来并执行过」，不是「目标已达成」。无人值守前先按要交出的面做高级四门禁与控制路径演练。[Anthropic《The AI-Native SDLC playbook》“Closing the loop”](https://claude.com/blog/the-ai-native-sdlc-playbook) 的分层响应机制（活文档观测 2026-09-26；缺精确参数版本锚）在此仅作概念示意，不复制 σ 数值；以下组合为**本手册编排，非产品默认、安全保证或通用阈值**：

- 轻度异常只记录；需要调查时仅只读诊断；允许行动的严重异常也只开 PR 或触发预批流程。阈值按本任务的基线、误报与影响重新验证，不抄生产；
- 检测脚本版本化＋单测，**全程确定性、模型不参与**；
- 回滚必须是管线里**演练最多的路径**：单命令、agent 可执行、staging 定期演练。

### 跨次反馈的适用条件（本手册编排，非产品默认）

跨次结果关联、迟到 / 历史结果处置、重复事件处置——三项**只对跨会话持久任务强制**：它们消费的是上一次唤醒留下的结果，必须先核归属再使用。会话内短任务若同步工具回灌已闭环（工具结果直接改变下一动作），不强制持久化登记与去重，按入门二三追问核对即可；记录负担按任务分级，没有压力不要求全字段。

| 情形 | 何时适用 | 处置 |
|---|---|---|
| 跨次结果关联 | 本次要消费上一唤醒 / 上轮运行留下的结果 | 先核归属：run / 触发器 / 工件版本对得上才用；对不上按历史处理 |
| 迟到或历史结果 | 结果到达时本轮已推进，或判据 / 授权已变更 | 先核归属再消费；过期即按历史，不作放行依据，按当前版重验 |
| 重复事件 | 同一事件可能重复投递、重复唤醒（跨会话持久任务必配） | 防重复副作用；重复结果不产生新信息，复用不重跑——重复**通过**结果的平台级去重未见显式机制（观测 2026-10-04） |

### 什么时候不要

- 跨会话四门槛缺任何一项 → 停在会话内定时。
- 要委派自动修复或声称目标完成，却没有完成判定与失败出口 → 先不交这部分；只读定时观测可以有界试行，但仍须有权限、资源、取消与接手边界。
- 幂等与防重入没设计（同一事件重复投递怎么办）→ 事件触发先不上。

## 高级四 · 升一档

> 现在的档位跑稳了，你想把下一个决定也交出去。这节是全书的铰链：**升档不是毕业，是用护栏换放权**。

### 三项门禁（按本次交接面分流，缺适用门禁不可升）

| 门禁 | 何时适用 / 检查什么 | 不过怎么办 |
|---|---|---|
| 1 门会红吗 | 所有要放大的面：故意引入对应负例，看动作门、目标门或调度取消门会不会拦住 | 没做过负例的检查视为摆设；门不会红就不升 |
| 2 裁判独立且判据可用吗 | **仅升续跑或宣称产出可信时适用**：抽看本任务的人工核对与自动判定是否一致；纯动作授权或只读唤醒不强制虚构 goal 裁判 | 需要目标裁判却是干活模型自判＋无保护＝不升；不适用时留 `not_applicable` 并说明原因 |
| 3 熔断与接手配了吗 | **所有自动化面适用**：本次面对应的拒绝 / 无进展 / 取消 / 资源上限和人工接手可达；只读定时也必须能停，不等于必须配自动 goal | 没有兜底，或接手不可达，就保持当前档位 |

### 控制路径演练（升相应面前做一次；本手册编排，非产品默认）

只演练本次要交出的面：动作授权演练副作用动作；续跑演练目标门与失败交人；唤醒演练调度器取消、worker 退出和副作用核对。**续跑面另加反馈闭环演练（本手册编排）**：故意触发一个红灯，核三件事——红灯送达**正确消费者**、进入**实际控制分支**（不是只贴日志、不是模型说读过）、产生**预期处置**（修复 / 重查 / 暂停之一实际发生）。只查本次要交面的适用项，**不以全模板替换逐面门禁**；未实做的保持「待演练」，纸面填完不算。不要为了让门通过而虚构不相关的 goal 或独立裁判。

若本次包含动作授权，挑一条**有外部副作用**的动作，写清「动作＋目标＋本次授权有效期」，分别触发三种处置：

- **允许**：只在当前边界内执行；
- **需人批准**：执行前让指定人看到具体参数与风险、作决定、按同一线程恢复；
- **硬拒绝**：停下并暴露原因，**不得用普通审批覆盖**。

演练后任一情形不成立——人不在、父线程看不见请求、状态不可恢复——保持暂停，退回需要人在环的档位。**不要把权限开大来让演练通过。**下一轮换目标或从 edit 变为 commit/push 时，重新请求授权。

### 演练记录（填好的样子，示意）

| 项 | 值 |
|---|---|
| 演练动作 | `bash(git push origin fix/cart-total)` |
| 目标 / 有效期 | 仅 fix/cart-total 分支，仅本次评审周期 |
| 触发「允许」 | 在边界内执行；日志有 propose → execute → result 三行 ✓ |
| 触发「需人批准」 | 执行前暂停；审批人看到 diff 与目标分支；批准后按同一线程恢复 ✓ |
| 触发「硬拒绝」 | 停止＋原因回传；普通审批不可覆盖 ✓ |
| 人不在场复测 | 合法请求送达指定人并有送达记录；父线程可见、恢复指针有效 → `awaiting_human`；未送达 → `blocked` |
| 结论 | 三路全通 → 可交动作审批（高级一档） |

结论栏写「不通过——人不在场时请求不可见」**也是合格产出：它挡住了一次真事故**。演练的目的是暴露断点，不是走个过场。

### 判定冲突时

裁判与人工验收者对同一产出结论冲突：

1. **暂停自动验收与升档**；
2. 把样例交给有权判定的人；人也无法一致判断 → 先重新明确「成功」的定义，再用固定样本复核；
3. 改过判据或样本集后记录新版本，**新旧分数不直接横比**；
4. 不能靠模型自报或提高轮次上限通过。

### 定档实例（三条样例的判定）

- 「agent 改文件、跑测试都在我看着的时候，每个 push 我批」→ **信息不足，不能直接定为已交动作审批**：若所有动作仍逐个由人批准，就是人工基线；若编辑与测试有预先放行的策略，只在该范围交了动作面。续跑与唤醒仍分别核查。
- 「`/goal` 最多十轮，修到 Lighthouse 达标为止」→ 交了**条件续跑**（高级二）；是否交动作审批、是否有人验收要另查；十轮是教学示意，不是生产默认；
- 「`/loop 5m` 值班看部署」→ 只证明**定时唤醒**（高级三）；不自动证明动作审批、目标裁判或成果验收：CI 绿不是部署成功，放行另查（高级五）。

### 档位速查（本手册编排）

| 交出的决定 | 节 | 已配护栏 |
|---|---|---|
| 动作审批 | 高级一 | 分级处置＋绑定授权＋拒绝预算 |
| 续跑 | 高级二 | 三要素目标＋裁判选型与保护＋熔断 |
| 唤醒时机 | 高级三 | 触发器＋持久状态＋取消传播＋硬上限 |

三条交接面都能在不同产品或实现中观察到，但这不构成统一成熟度等级、效果保证或必须逐档升级的规则；**高阶不是毕业要求**。上述分面与速查表为本手册编排（非产品默认）。

### 什么时候不要

- 三项门禁任何一项没过 → 不升。
- 演练三条路有一条走不通，或要升的续跑面没做反馈闭环演练 → 不升。
- 说不清「升这一档省下的是什么、换来的是什么」→ 先写下来再决定。

## 高级五 · 它说做完了

> 你回来了，它说「完成」。这节管**放行**：凭什么接受这次结果。

### 放行五接口

| 接口 | 必须先问 | 看什么记录；缺失时怎样退回 |
|---|---|---|
| 1 目标契约 | 目标是**产物终态**（可观察）还是**业务结果**（要等外部用户行为）？不得更改什么？ | 目标、测量方法、不变式、授权范围、退出/升级条件。外部结果尚不可见 → 只委派可观察产物，不宣告业务达成 |
| 2 环境证据 | `npm test` 成功验证的是哪部分？测了正确版本 / 页面吗？执行者能删测例、改进度、伪造工具日志吗？ | 带运行 ID、目标版本与原始输出的记录；**只在提示词里禁止改测例不算隔离**；测不到的质量维度记「待验收」，不写已完成 |
| 3 裁决协议 | 谁能给「达成」？它看的是真实环境还是只看对话？判据谁持有、谁能改？ | 裁判的输入、版本、输出与失败出口；可能错判的部分另做独立检查或人抽验。**分离执行者与裁判只减利益冲突，不保证裁判正确** |
| 4 资源与进度 | 总预算谁覆盖（续跑、重试、子代理、定时重跑）？连续无进展怎么收口？ | 每轮反馈、费用 / 时间 / 轮数、暂停理由。**预算触顶＝停止或交接，不是成功**；按会话计的预算不等于跨次总额 |
| 5 跨次责任 | 上次的目标、授权、观察结果还新鲜吗？取消真的传达到了调度器和 worker？ | 任务 ID、幂等键、执行日志、审批人、接手渠道。**按时唤醒不等于可靠完成** |

### 放行检查单（对着五接口，可复印）

```text
□ 目标：本次验收的是产物终态还是业务结果？二者有没有被写成同一个「完成」？
□ 不变式：约定的「不许变」在哪份记录里核对过了？（diff / 测试清单）
□ 证据：检查记录带运行 ID、目标版本、原始输出吗？执行者有没有删改的写权限？
□ 裁决：给 Met 的是谁？它的输入是什么？判据版本多少？失败时默认放行还是默认拦？
□ 预算：这次花了多少轮、多少钱？谁的总账在记？按会话的预算覆盖跨次总额吗？
□ 接手：如果现在按「暂停」，下一个人从哪个指针恢复？
```

六个全勾 → **只进入验收流程，不自动填写 `accepted`**。有一格填不出 → 按卷首状态语汇表选一个诚实的状态，转高级六。只有有权验收者对版本、范围、样本、时间窗显式签认并留下 `accepted_by / accepted_at / evidence_ref`，产出验收账才可写 `accepted`；外部结果仍可为 `outcome_pending`。

### 证据三核（六勾第 3 格的展开；本手册编排，非产品默认）

「证据：检查记录带运行 ID、目标版本、原始输出吗」一格，勾之前过三核：

| 核查 | 通过条件 | 勾不掉的典型 |
|---|---|---|
| 实际执行 | 原始输出位置打得开，能对到本次运行 ID | 「没跑＝通过」：有产品在检查未配置时把未执行与通过记为同值（Aider，源码走读，观测 2026-10-04，机制依源码、非实际执行验证） |
| 当前版本 | 证据的版本锚与**本次**验收的工件版本一致 | 上一版的通过报告被当成当前版的放行依据 |
| 适用范围 | 写清测了什么、**没测什么** | 未覆盖的质量维度记「待验收」，不写已完成 |

旧版通过只保留历史，不签当前验收：「旧版结果自动批量失效」**未见**任何一手机制——靠工程纪律执行：每份证据带版本锚，人工把旧证据降级为历史（入门二三追问的验收侧用法）。

### 三个对照案例（同一触发器，能宣布的不同）

- **夜间巡检**：每晚跑依赖扫描、退出码 0——仍要查扫描范围、漏洞库更新时间、锁的是哪个版本；超时 / 扫描器不可用 / 证据过期分别写「暂停 / 未知并通知人」，不写达成。要声称「线上风险已消失」，还得看实际部署了什么版本。
- **每五分钟看部署**：CI 还在跑、没收到告警，都不是部署成功；CI 绿只支持「约定检查在该版本通过」。业务指标几小时后才出现？完成声明停在「检查条件满足，业务结果待观察」。
- **跨任务错位**：夜间任务 A 的 CI 绿了，共享组件却让任务 B 回归失败；白天有人改过优先级，取消后面板绿了但旧 worker 还在写。单一任务的退出码、日志里一句 Met、面板的「已关闭」，都证明不了「当前版本已通过验收且已停机」。

### 轮末交接核对（三列清单）

对比本轮起止，逐列列出：

1. 测试文件与测试清单的**删除、跳过、弱化、该新增而未新增**；
2. **基线已有失败、本轮新失败、实际跑过的检查与退出码**；
3. **超出授权范围**的功能 / 文件改动。

任何一列有异常：先不翻完成，交独立检查者决定修复、回退或重新授权。**「缺失的测试没有失败」不能代替通过。**

### 产出与外部结果分账

交接时分别记两行：

- `产出检查 ＋ 证据链`：本轮可复查的测试 / 产出；
- `结果状态 ＋ 责任人 ＋ 复查时点`：业务结果已观测 / 待观测。

状态记录行实例（填好的样子，全部值为教学示意，不可抄生产）：

```text
stop_reason       = goal_gate_met           # 目标门通过而停（不是资源耗尽）
acceptance_status = accepted                # 只有下列签认字段齐全才可写
accepted_by       = @xiaoming               # 有权人签认了指定版本的 diff＋回归记录
accepted_at       = <recorded-at>
accepted_scope   = <artifact-version-and-window>
evidence_ref      = <run-id>, <pr-or-report> # 可复查的指针
outcome_status    = outcome_pending         # 采用率仍待观测
outcome_owner     = @product
next_check        = <observation-window>
```

记录分属三个责任：控制流、产出验收、外部结果——**三件事分账，可由同一人承担，不合成一句「完成了」**。

### 什么时候不要

- 五接口有一项查不动（记录根本没留）→ 状态写「证据不足」，不放行，转高级六。
- 裁判可以被执行者改写 → 退回高级二补保护，本轮结果全部转人工。
- 有人拿「运行次数」「唤醒成功率」「代理数量」当质量证据 → 那些是活动量，不是成果。

**来源注**：[Anthropic《Building effective agents》](https://www.anthropic.com/engineering/building-effective-agents)（发布 2024-12-19，观测 2026-09-26）与 [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)（发布 2025-11-26，观测 2026-09-26）支持环境证据、检查点、逐条验证与提前宣告完成的反例；[Claude Code《Keep Claude working toward a goal》](https://code.claude.com/docs/en/goal)（观测 2026-09-26）支持三值与独立评估边界；[Kent Beck《Augmented coding beyond the vibes》](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)（发布 2025-06-25，观测 2026-09-27）；[Steve Yegge《Introducing Beads》](https://yegge.ai/essays/introducing-beads-a-coding-agent-memory-system/)（发布 2025-10-13，观测 2026-09-27）。五接口、检查单、三本账、签认门与证据三核为本手册编排（非产品默认）；证据反例（未执行与通过同值）观测 2026-10-04。

## 高级六 · 它停了

> 它熔断、超时、或自己停了。停止不是失败，也不是完成——是**交接时刻**。

### 第一步：阻止待执行动作

- 支持持久化暂停的实现 → **保存当轮状态**；
- 不支持 → 记下请求并停机，**不假装可从原位恢复**。

### 三路处置

| 情形 | 处置 | 红线 |
|---|---|---|
| 策略明确禁止 | 维持硬拒绝 | 不得改名为「待人批准」 |
| 可由人决定 | 有合法审批入口 → 交指定审批者 | 入口不可达或无人接手 → 记 `blocked`，**不自动重试同一危险动作** |
| 入口不可达 | 保持阻塞并记录 | 不把阻塞写成「已升级」 |

交接记录实例（填好的样子，示意）：

```text
task_id         = fix-cart-total-42
action          = bash(git push origin fix/cart-total)
target          = repo:shop, branch:fix/cart-total
decision_source = exec_policy: push → Forbidden
denial_reason   = 硬拒绝（push 不在授权面；本次授权只覆盖编辑与测试）
authorized_scope= 编辑 payments/、跑 npm test；不含 commit/push
reviewer        = @xiaoming（审批入口：PR #217）
resume_pointer  = paused_state:88f3      # 持久化暂停；恢复后从断点继续
thread_id       = session-12             # 父线程可见该请求 ✓
```

恢复时第一步：重核 `authorized_scope` 的**有效期**——上次批的是那次评审，这次是新的，重新请求（高级一·铁则一）。

### 异常处置按事实分流（本手册编排，非产品默认）

停止后按**事实**选暂停 / 补查 / 交人，不按感觉重启；退出码通道不区分失败种类，先分清是检查坏了还是目标没达成，再选行：

| 异常事实 | 处置 |
|---|---|
| 目标失败（检查执行了且失败） | 修复 → 重验：重跑同一检查并核对版本 |
| 工具 / 环境异常（检查设施坏了，如进程拉不起、命令不存在） | 恢复检查设施后**有界重查**；不与目标失败混记——设施故障曾被记成「通过」或「失败」两态皆是反例（Aider，源码走读，观测 2026-10-04） |
| 缺失 / 截断证据 | 补原始输出；没有原始结果不判通过 |
| 旧版结果（版本锚对不上本次） | 降级为历史，按当前版重验，不作放行依据 |
| 政策拒绝 | 沿原授权流程（高级一三路处置），不在事故现场开口子 |
| 事实未知（缺证据、变更是否生效未知） | 阻止达成声明与扩权；允许**授权内**有界补查 |

接手例（填好的样子，全部字段为教学示意，不可抄生产）：

```text
最后有效目标  = dashboard-perf-demo-v1：固定页面 Lighthouse ≥ 92（判据 v1，工件 commit a1b2c3d）
停止事实      = 第 4 轮 Lighthouse CLI 无法启动——环境异常，非目标失败；第 3 轮 88 分为最后一次有效检查
证据          = runs/lh-turn3.txt（88 分，判据 v1，适用）；turn4 无原始输出，按缺失证据处理，不判通过
消费者与去向  = 已交 @xiaoming（本任务评审线程）：恢复 Lighthouse 环境后有界重查；88 分留作历史，不签当前验收
恢复位置      = resume_pointer = paused_state:77c1；恢复后先核判据 / 工件版本未变，再按当前版重验
```

### 两个常见误处置（对照修）

| 误处置 | 正解 |
|---|---|
| 把硬拒绝现场改成「待人批准」 | 策略说禁止就是禁止；要改的是策略本身，走策略变更流程，不在事故现场开口子 |
| 入口不可达时自动重试同一动作（教学示意） | 正确状态是 `blocked`＋记录；重复撞墙不会把墙撞开，只会烧预算 |

### 两件事分记（不可互相冒充）

| 记什么 | 记哪些值 | 不能冒充 |
|---|---|---|
| `stop_reason`（为什么停） | 目标门通过而停 / 资源耗尽 / 连续拒绝 / 不可恢复错误 / 人暂停 / 模型自行收尾 | 「已验收」——**没有验收证据就保留未验收** |
| `accepted ＋ 证据链`（谁收了货） | 有权验收者的签认、版本/范围/时间窗与测试、PR、日志或人工记录的指针；未签认留空 | 不能从超时、模型消息或测试进程结束推断已交付 |

不可恢复错误四类（触发即清空目标，Claude Code `/goal` 文档，观测 2026-09-26）：认证失败｜额度耗尽｜压缩解决不了的上下文溢出｜模型不可用；其余错误的重试与暂停次数以所用实现文档为准，本手册不概括成通用次数。

### 退档信号

熔断频发、假把控症状复现（测试被动过、越界实现、未说明的失败）→ 退一档重新稳住再升（高级四）。停止本身不构成退档理由——**正常停与事故停要分得清**：目标门通过而停是设计内；拒绝熔断与无进展熔断频发才是信号。

### 什么时候不要

- 别在没看清 `stop_reason` 前重启循环——重启烧掉的预算和上次一样。
- 别把「它自己收尾了」读成任何一种完成（卷首 `stopped` 与 `accepted` 的边界）。

**来源注**：[Claude Code《Keep Claude working toward a goal》](https://code.claude.com/docs/en/goal)（文档观测 2026-09-26）支持不可恢复错误与暂停语义；[Claude Managed Agents《Sessions》](https://platform.claude.com/docs/en/managed-agents/sessions)（文档锚 `managed-agents-2026-04-01`，观测 2026-09-30）支持事件持久化、interrupt 与状态边界。三路处置、字段、恢复模板与异常处置分流、接手例为本手册编排（非产品默认）；产品具体重试次数必须核所用版本，不在此推广。异常分流的机制反例（失败种类不可分辨、设施故障两态）依一手源码走读，观测 2026-10-04。

## 高级七 · 可选方向

> 听说多代理编排、循环自我改进很神。这节管预期：局部已有实例，整体未成熟；**高阶不是毕业要求**。

### 两条支线现状

| 支线 | 交出什么 | 已证 | 未证 |
|---|---|---|---|
| A 多主体编排 | 分工、并行、汇总由谁协调 | 编排器-工人、受约束并发、分布式文件锁均有实例 | **写入拓扑不收敛**：有人推荐写入单线程，有人多代理各自 clone / 改 / 合且不用编排器——共同问题只有三个：避免冲突、合并、验证 |
| B 改进循环本身 | 谁提议 / 应用对规则、工具描述、配置的改动 | 外围改动（如工具描述）有局部实例 | 核心自改（自动改判据 / 评估器）未成熟 |

支线 B 的四个层次，别混为一谈——每往右一层都是**不同的授权决定**，不能一口气交出：

```text
人亲自改 → 代理给建议、人应用 → 受控应用外围改动 → 自动改写核心判据
```

### 两个实例（都真实，都不是模板）

**编排**：Nicholas Carlini 的 [Anthropic 工程博客《Building a C compiler with a team of parallel Claudes》](https://www.anthropic.com/engineering/building-c-compiler)（发布 2026-02-05，观测 2026-09-30）记录了 16 个代理、约 $20k 的个人案例；数字和拓扑都是案例参数，**不是建议或生产预算**。作者自述大部分精力在**验证器与环境设计**——"it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem." 每个代理各自 clone、修改、push、merge，**不用编排代理**。而 [Cognition《Multi-Agents: What's Actually Working》](https://cognition.com/blog/multi-agents-working)（发布 2026-04-22，观测 2026-09-30）推荐写入单线程；**两条路线都是真实案例，不形成正确拓扑或通用结论。共同要解决的是避免冲突、合并、验证。**

**元循环外围**：[Anthropic《How we built our multi-agent research system》](https://www.anthropic.com/engineering/multi-agent-research-system)（发布 2025-06-13，观测 2026-09-30）记录了工具描述改写这一局部实例；它不是核心判据自动改写的成熟证明。已有外围局部改写实例，但代理自治发布、独立验收与自动修改核心判据的完整授权政策尚未证明成熟；往下一层（人审代理建议、人工应用）现在即可在可回滚环境试行。

### 进支线的正确姿势

- 现在就能做**人审、可回滚的试行**：代理只提建议，人应用改动；这不是安全保证，也不需要先爬到最高档；
- 整树预算、写入所有权、合并与**独立验收**先配好——分工之后更要合并验收，**改动者不能自行放行自己的改动**；
- 元循环：提案与评估分离；改动可回滚、被评估。没有这个闭环之前保持人审；试行结果不能外推为生产安全或效果。

### 什么时候不要

- 单代理有界任务还没跑稳 → 支线放大的是你没修好的问题。
- 有人拿「这是必然趋势」当成熟度证明 → 趋势证词不是效果证据："If attackers and reporters loop, defenders will eventually need to loop too to keep up." 是趋势判断，不是安全证明。
- 你的角色已经开始模糊——第一人称体验："In the harness operated loop I'm not sure what my role even is. Even the 'done' signal loses all meanings … My role is reduced to that of a messenger."（Armin Ronacher，发布 2026-06-23，观测 2026-09-30）→ 这正是退回高级四门禁的信号：交出触发权，不等于交出成果裁决权。
