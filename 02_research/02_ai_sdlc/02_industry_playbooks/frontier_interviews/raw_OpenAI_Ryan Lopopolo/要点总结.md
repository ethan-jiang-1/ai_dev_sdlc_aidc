# Ryan Lopopolo：Harness Engineering — 智能体优先世界的工程新范式

> 原文：*Harness Engineering: Leveraging Codex in an Agent-First World*（OpenAI 官方博客）
> 作者：Ryan Lopopolo，OpenAI 技术团队成员，Frontier Product Exploration 团队
> 日期：2026 年 2 月 11 日

---

## 核心实验：100 万行代码，零人工手写

> *"人类负责掌舵，智能体负责执行。"*

5 个月，从空仓库开始，3 人团队（最终 7 人），约 100 万行代码，~1500 个 PR，平均每人每天 3.5 个 PR。全程**零人工提交代码**。产品已有数百日活内部用户。

代码包括：应用逻辑、测试、CI 配置、文档、可观测性、内部工具、评估框架、审查评论、仓库管理脚本。

时间压缩到传统手工编码的 **~1/10**。

| 公司 | 代表人物 | 核心观点 |
|---|---|---|

## 重新定义工程师角色

**核心原则：不手写代码。** 当代码提交完全委托给智能体后，工程师的三项新工作：

| 旧角色 | 新角色 |
|---|---|
| 写代码 | **设计环境** — 工具、抽象、内部结构 |
| Debug | **澄清意图** — 把高层目标拆成小构件 |
| Code Review | **构建反馈回路** — 让智能体自行发现和修正错误 |

当事情进展不顺，解决方案不再是"再努力一点"。而是追问：**智能体还缺什么能力？怎样才能让这个能力对它可读、可强制执行？**

---

## "Ralph Wiggum 循环"：智能体自我审查

Codex 自己审查自己的改动、发起专用审查智能体、逐条响应反馈（来自人类和其他智能体），循环往复直到所有审查者满意。

**人类审查 PR 已不再是必需流程。** 几乎所有审查工作已调整为智能体之间完成。

---

## 让应用对智能体"可读"

> *"人类的时间和注意力是硬约束，所以把更多信息直接暴露给 Codex。"*

三个关键改造：

1. **Git worktree 独立实例** — 每个修改启动独立应用实例，Codex 亲自操作
2. **Chrome DevTools 接入** — DOM 快照、截图、导航；自行复现 bug、验证修复
3. **本地可观测性堆栈** — LogQL + PromQL；智能体可以验证 "服务启动 < 800ms" 或 "关键 span < 2s"

Codex 经常在一个任务上**连续工作 6 小时以上**，恰好是人工休息时段。

## 知识管理：地图，不是一千页手册

> *"给 Codex 一张地图，而不是一千页手册。"*

**失败方案**：一个超大 `AGENTS.md`
- 挤占上下文 → 漏掉关键约束
- "一切重要 = 一切都不重要" → 局部模式匹配
- 迅速腐化成陈旧规则坟场
- 无法机械检查新鲜度

**成功方案**：`AGENTS.md` 作为 ~100 行的目录页，真实知识组织在 `docs/` 结构化目录中。

**渐进式披露**：智能体从小而稳定的入口开始，被明确指向下一步看什么。

**自动化治理**：
- 专用 linter + CI 检查文档新鲜度、交叉链接、结构合理性
- "doc-gardening" 智能体定期扫描过时文档，自动发起修复 PR

> 这与 Thariq Shihipar 的 "implementation-notes.md 记录偏离" 和 "测验确保理解" 形成呼应 — 都是将隐性知识显性化、结构化的工程实践。

## 用约束固化架构

> *"智能体在边界严格、结构可预测的环境中表现最好。"*

**分层的领域架构**（每个业务域固定层次 + 严格依赖方向）：

```
Types → Config → Repo → Service → Runtime → UI
              ↑
          Providers（唯一横切入口：认证、连接器、遥测、功能开关）
```

**机械强制执行**：自定义 linter + 结构测试（由 Codex 自己生成），报错信息直接写修复指令。

**品味也是一等约束**：结构化日志、schema 命名约定、文件大小限制、平台可靠性要求 → 全部编码为 lint 规则。

> *"在传统人工团队里，这类约束容易被觉得迂腐甚至束缚。但有了智能体，它们成了倍增器。"*

## 合并哲学的颠覆

| 传统 | Agent-First |
|---|---|
| 多个阻塞式合并门 | 极少数阻塞门 |
| 长 PR 生命周期 | 短 PR 生命周期 |
| Flaky 测试阻塞一切 | Flakes 通过后续重跑处理 |
| Code Review 捕捉所有问题 | 结构约束 + linter 捕捉问题 |

> **"当修复成本低、等待成本高时，等式反转了。"**

---

## 熵与垃圾回收

> *"Codex 会复制仓库里已有的模式，包括那些不好的。"*

团队曾每周五花 **~20% 的时间**清理 "AI 残留物" → 不可扩展。

解决方案：**"黄金原则"编码进仓库 → 后台 Codex 定期扫描偏差 → 自动发起小重构 PR**。大多数 PR 一分钟内审查并自动合并。

> 这就像**技术债的持续 GC**：小额高频偿还，而不是让坏模式在仓库里扩散数周。

## 关键共识：跨公司的方法论趋同

这篇文章的发表时间（2026 年 2 月）早于 Anthropic 和 Cursor 的同类文章，但其方法论与后续发布的文章高度一致：

| 概念 | Ryan (OpenAI) | Anthropic | Cursor |
|---|---|---|---|
| 知识管理 | AGENTS.md 作为地图 | CLAUDE.md 分层 | Dynamic Context Discovery |
| 验证机制 | 智能体自我审查循环 | Trust but Verify | Agent Harness 评估 |
| 上下文策略 | 渐进式披露 | Skills 渐进加载 | 按需拉取 vs 静态注入 |
| 角色转变 | 设计环境 > 澄清意图 > 构建反馈 | JIT Planning + 角色模糊 | Plan Mode + Agent Review |
| 人工角色 | 设定优先级、验证结果、补充缺口 | 法律/安全/品味 | 评审 + 架构决策 |

## 核心教训

> **"软件开发仍然需要纪律，只不过纪律越来越多地体现在支撑结构上，而不是代码本身。"**
>
> **"智能体缺的不是能力，而是可读的上下文。不在代码仓库里的知识，对智能体来说就等于不存在。"**
>
> **"当修复成本低、等待成本高时，等式反转。允许偶发失败、快速重试，比无限期阻塞更合理。"**
