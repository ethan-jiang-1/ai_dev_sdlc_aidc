# 治具工程 (Harness engineering)：在 Agent 优先的世界中利用 Codex

> 译注：此文档原文来源于 OpenAI 官方博客发表于 2026 年 2 月的核心工程文章《Harness engineering: leveraging Codex in an agent-first world》。该文描述了 OpenAI Harness 团队利用 Codex 智能体完成百万行级别的原生项目，并在 5 个月内实现真正意义上“0 行人类手写代码”的具体敏捷开发落地方案。本文代表了“跃迁4”叙事中，属于“主控与治具流程派”的第一手核心实录依据。

在过去的五个月里，我们的团队一直在进行一项极其硬核的工程实验：完全依靠 **0 行人工手写代码**来构建并发布一款软件产品的内部 Beta 版本。

这款产品有每天活跃的内部高频用户以及外部 Alpha 测试人员。它经历了真实的发布、部署、崩溃并被修复的生命周期。与众不同的是，它的每一行代码——包括应用逻辑、测试用例、CI 持续集成配置、文档资料、以及监控链路设施与内部铺助工具——100% 都是由 Codex 编写的。据我们估计，对比以往纯人力的开发模式，这种工作流直接把开发周期缩短了约九成（花费了传统手写代码模式约十分之一的时间）。

**人类负责定舵掌控方向，智能体 (Agents) 负责执行。**

我们刻意选择了“不能人工手写代码”这一极端且痛苦的限制，以此逼迫自己去构建那些能够呈数量级倍数提升工程进度的必要基建工具。为了在短短数周内交付规模最终达百万行代码级的项目，我们必须深刻理解：当一个软件工程团队的主要工作从“写代码”，转变为“设计 AI 运行环境、下达规范意图，并建立出能使 Codex 智能体可靠运作的反馈循环”时，工程范式究竟会发生怎样颠覆性的改变。

这篇文章讲述了我们在通过智能体团队构建全新产品时所学到的经验——什么机制失效了，什么流程产生了复利，以及如何最大化利用我们工程环节中唯一真正稀缺的资源：人类的时间和注意力。

## 从一个完全纯净的 Git 空仓库开始起步

向这个空壳仓库的第一次代码提交发生于 2025 年 8 月末。

最初始的基础脚手架代码——仓库结构、CI 配置、代码格式化规则、包管理设置以及应用主框架——都是由 GPT-5 驱动的 Codex CLI 依据少量的已有模板所生成的。就连用来向智能体发布规则指令、教导其如何在此代码库内协同工作的基础引导文件 `AGENTS.md`，也是由于 Codex 自主生成的。

在系统中，没有任何预先保留的、由人类手写的底层代码来作为系统对照的锚点。从第一天起，这个系统仓库就是完全由智能体勾勒并塑造出来的。

五个月后，该库涵盖了高达百万量级的代码阵列，这些代码散落于应用逻辑、基础设施、工具周边、说明文档等方方面面。在此期间，在一个仅有 3 名人类工程师“驾驶 (driving)” Codex 运作的小型精干团队操作下，开启并合并了大约 1500 个拉取请求（Pull Requests）。这意味着每位工程师每日平均的合码吞吐量达到了惊人的 3.5 个 PR。更令人惊讶的是，随着团队扩展到了现在的 7 名工程师，这个吞吐量效能还在成正比增加。

重要的是，这绝不是在“为了刷代码行数而产出”：该产品至今已被内部数百名用户深度使用，其中更包括那些重度的高频用户。并且在整个开发过程中：**人类从未直接贡献过任何一行代码。这也是整个团队最为核心的哲学：无手写代码 (no manually-written code)**。

## 重新定义工程师的系统级角色

由于不能触碰键盘亲自撸代码，这完全**引入了一种截然不同的工程开发作业范式：工程师的工作重心必须彻底转向“系统、脚手架设施以及对杠杆率 (leverage) 的把控”**。

早期进度的推进比我们预想的要难熬且缓慢。原因并非大模型 Codex 的能力不足，而是任务指定的周边环境限制没有说清楚，使得系统环境规范严重不够明确。智能体极度缺乏能令它们能继续向高级目标阶段推进所需的排障工具、逻辑抽象层以及仓库的内部结构依托。因此，我们工程团队当时最核心的主业完全变成了：究竟该如何赋能智能体，让其能够放开手脚去完成真正有用的干活？

在实践中，这意味着必须采取深度优先的工作方式：将宏大目标切割分解为微小的积木块（设计、编码、代码审查、测试等各类环节模块），利用大语言模型提示词（prompt）去呼叫带领智能体去构造好这每一块砖瓦，最终再利用它们来解锁极其复杂的聚合型目标功能。当工作流在某个环节出现故障抛锚时，应对的修复思路绝对不该再是简单敷衍地告诉模型“用提示词想办法再试一次”。既然唯一能实质性推动系统进度的是 Codex 智能体去干活发力，那么人类工程师解决这些复杂业务就必然需要深度切入并拷问自己：“当前的系统环境究竟欠缺了什么能力机制，我们该如何把这个欠缺的能力点，以一种即让智能体‘能精准读懂和理解’（legible）又能对其具有极高‘规则制约力’（enforceable）的形式构建到环境规范当中去？”

人类主要是通过描述各类系统级的提示词流转来与系统发生交互互动的：工程师只需要去向控制中枢描述好这个任务，按下运行按钮跑起对应职能的智能体，接着由它独自扛住压力直到成功提上一个有效的 Pull Request。

为了能平稳推进并让系统成功通过一条新提交的 PR 代码支路，我们会写好流程强制约束指示 Codex 程序首先去执行一次“本地化的自我检视”，顺便同步向驻守于云端以及本地的特定代码审计 Agent 呼叫发起专门的代码审查动作。接着 Codex 就自动响应无论是由人或是由别的辅助 Agent 发回来的审查意见的反馈动作，然后陷入一个自我改进并审阅修改的死循环操作流里，一直打转拉扯，直到所有充当“检验端审查者”的 Agent 都亮起了“放行满意”的绿灯。此过程中，Codex 将自行接管了那些包含在 gh(Github) 工具包里面去调用相关脚本搜集获取所需代码运行上下文状态的高密量复杂动作，以避免让任何有价值的人力再去像个只会死板操作 CLI 控制面板粘贴搬运工似的。

人类是可以介入以审阅那些 PR 的，但事实上团队这压根就不是一道硬性必备的开发流程。反而随着系统进化累积，我们已经基本上把所有的纯代码代码审查负担包袱全部甩向并倾斜分摊交给了“智能体对智能体 (agent-to-agent)”的全自动流来承载和处理掉了。

## 不断提升应用环境对于机器的“易读可探知性 (Legibility)”

随着代码生成吞吐量的爆发式提升，研发过程的“阿喀琉斯之踵”开始转移到“人类 QA (质量保证) 所能承载吞吐的有限精力瓶颈”上来了。由于固定死板且无法逾越的人类时间流和他们有限的聚焦视线这类客观限制难以跨过这道坎，大家开始另辟蹊径，就是转而去直接赋予 Codex 等智能工具获取识别包含此应用内系统界面的 UI 控制数据面板、应用程序产生输出的这些海量 Log 日志系统甚至运行监控时程序等指标参数信息这种强悍的数据读写感知能力，从而这这些本属于为给研发人类工程师去理解研判排除问题的各种排错应用能被 Codex 进行直接并且没有代沟障碍地顺畅分析和利用 (legible to Codex)。

## 将代码仓库打造成“唯一真相来源 (System of Record)”知识记录统筹系统 

在将去使得这用于指名指派的让那些智能引擎去处理去完成去实施极高极其繁复及这极为重大海量庞杂这复杂类型大型工作任务这类之过程挑战当里：那么在这个中间如何做到把去这去进行和去处理系统那运行上下文关系给做上有效与极高效这进行统筹输送并以及去对其加以这精准管理就是被认为是并在也是在这各种大最为艰难考验和困难的各种难题并困难里面最严重的一这等一项和困难的一个最大挑战这课题这也一点都不算得上是。这对于并且有关于这也是我们在非常最初这早期开发摸索的这段那当中最先也就是所发觉并从中也是我们所能被教导也是学得所知了解到学获得一个深刻体会但这极为极其明了并很简单极其质朴一个的道理并这经验这个事实并教训的，这是也极其那就是这且那也就极其：这去只需要交给 Codex 给塞入一这张这精准并结构简要清晰这种导引指向用的这类一张指导地图这这并能可以指北及指这进行寻径指路用的地图这即可，而绝非也不是那些或者这也绝不要试图想或想去给去和强制塞去强行丢出向和往它们脑门扔入这扔去这种动辄就有成百乃至这超过千页多达那极长超长那种文字型操作指示这类之文本手册指南大合集的此类极其。

过去这曾经确确实实我们曾是也的确有这么想这与有过去试过并去这实验过那些采取那些采取想要将系统全局规制都塞进这一并采用所谓之的那叫所谓去弄这一份极长极巨极其长这的这种巨大内容这那种被称为就只凭那一本单一内容及单一巨大文件的且巨大这体量的 “一个叫这和那极其巨大这份这种 `AGENTS.md` 巨大内容指导”等这类这去这样搞这种。但这无疑如毫无这是如这这等一如它那极其容易能这并且也是在它这也是能这种在人们意料猜测预想这这当之中般的那极其这种毫不例外般地这种地这就并极其这是就这也毫无以极可预见的那样这就是在彻底是并完全是并以一种这极其。它失败了在这：

* **这因为对于系统空间而言这存放上下文内容存放等记忆等存留空间其自身本这就是并它就是属于那一项这极为受限并是一项它这极度这稀缺这种的一种限制级别的这核心资源。**如果提供一份异常极其异常臃肿之极其极巨大体量的巨量指令这类这种指引性说明这文件将会势必会在等导致直接挤压霸占剥夺掉并将这也极大挤压去去用于能放置及给这些用装用于放置运行代码内容还有那那些真正在以及这各类这种这类这些实际这那等正这被实施处理的实质正事与各类实质事务工作这种用于描述实际各类和还有这这类以及各项真正需要及该用的这种等这这其他如相关的那些代码或者是那些相关等其它辅助及相关需要调看用于这些相关配合这些用来调看用于这些相关的各查询指引之文献文档类用于这参考这种等其余这资源信息可用之去加载及可调出的其空余之存储操作之类这就极巨耗这。所带来最终后引发导致结果要么将是致使这类让运行等指派让让这执行之和让这些等将。不仅是导致这并迫使或去促使那或是等将会致之等令这类将会使。
* **过多无用指导反成乱向**。如果“事事都重中之重”，最终系统只会陷入失去重心的无序徘徊，陷入琐碎的重用匹配模式中，从而完全丧失宏观导航掌控功能。
