# 用并行的 Claude Agent 团队构建一个 C 编译器

发布期：2026年2月5日

我们向使用 Agent 团队（智能体团队）架构的 Opus 4.6 下达了构建一个 C 编译器的任务，然后（基本上）就撒手不管了。以下是它教给我们的关于自主软件开发未来的经验。

_作者：Nicholas Carlini，Anthropic 护栏（Safeguards）团队的研究员。_

最近我一直在试验一种监督大语言模型的新方法，我们称之为“智能体团队（agent teams）”。

在智能体团队的模式下，多个 Claude 实例会在同一个代码库上并行工作，期间无需人类的主动干预。这种方法极大地扩展了 LLM 智能体所能达成的项目范围。

为了对它进行压力测试，我给 16 个 Agent 下达了一个任务：从零开始用 Rust 编写一个 C 编译器，并且要强大到能够编译 Linux 内核。在经历了近 2000 次 Claude Code 会话以及近 2 万美元的 API 调用成本后，这个 Agent 团队制作出了一个近 10 万行代码的编译器，它成功在 x86、ARM 和 RISC-V 架构上编译出了 Linux 6.9。

[这个编译器本身就是一个非常有意思的产物](https://github.com/anthropics/claudes-c-compiler)，但我今天这里的重点是，我想谈谈在为长期运行的自主智能体团队设计“运行脚手架（harness）”时，我都学到了什么：如何编写能够在没有人类监督的情况下让 Agent 保持在正轨上的自动测试用例，如何去构建工作流以使多个 Agent 可以并行推进进度，以及这种方法的极限瓶颈究竟在哪里。

## 让 Claude 得以长时间持续运行

现有的像 Claude Code 这样的智能体脚手架，通常都需要操作员在线并随时准备进行联合工作。如果你要求它解决一个漫长且复杂的问题，模型可能会解决其中的一部分，但最终它还是会停下来等待你继续输入指令——无论是回答它的问题、提供状态更新，还是对需求进行澄清。

为了诱导出一种持续的、完全自主推进的工作流，我编写了一个能把 Claude 困在一个简单循环里的治具脚手架（如果你用过 Ralph-loop，应该会对这个很熟悉）。当它完成一个任务时，就会立刻无缝接起下一个。_(注意：请在容器中运行这段代码，绝对不要在你真实的宿主机上跑)。_

```bash
#!/bin/bash

while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"

    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y &> "$LOGFILE"
done
```

在给 Agent 的初始提示词里，我告诉 Claude 它要解决什么问题，并要求它通过将问题拆解成小块、追踪当前的进度、弄清楚下一步该做什么，从而切实地一直循环推进下去，直到一切完美为止。（对于这最后一点，Claude 实际上根本别无选择。因为这个 Bash 循环是永远运行的——不过有一次，我确实看到 Claude 不小心把自己给 `pkill -9 bash` 进程杀死了，从而终结了循环。哎哟！）。

## 让 Claude 并行运转

并行运行多个实例可以解决单体 Agent 脚手架的两个致命弱点：

-   **单线程瓶颈**：一个 Claude Code 会话同一时间只能做一件事。随着项目范围的不断扩大，能同时并行调试多个 Issue 显然要高效得多。
-   **角色专业化分工**：运行多个 Claude Agent 允许进行专业化分工。我们可以指派几个核心 Agent 去解决手头的实际问题，同时可以召唤其他专业化的 Agent 去（比如）维护项目文档、死盯代码质量，或者解决非常具体刁钻的子任务。

我实现的“并发版 Claude”极其硬核且返璞归真。我会先创建一个全新的裸 Git 仓库，然后为每一个 Agent 启动一个 Docker 容器，并把这个仓库挂载到容内的 `/upstream` 目录。每个 Agent 都会克隆一份代码到自己的 `/workspace` 目录里，当它干完活了，再把自己独立容器里的变更 push 推送回上游的那个共用库里。

为了防止两个 Agent 同时挤去解决同一个问题，我的运行脚手架使用了非常朴素的同步锁算法：

1.  Claude 通过在 `current_tasks/` 目录下写入一个文本文件来对一项任务加上“文件锁”（例如，一个 Agent 可能会锁住 `current_tasks/parse_if_statement.txt` 声明它在做如果语句解析，而另一个锁住了 `codegen_function_definition.txt` 去做代码生成）。如果两个 Agent 试图认领同一个任务，Git 原生的版本同步冲突机制就会强迫第二个动作慢的 Agent 放弃并去挑选另一个任务。
2.  Claude 专心处理任务，完成后从上游拉取（pull）最新代码，合并其他 Agent 的变更，推送（push）自己的心血，最后移除自己的文件锁。虽然合并冲突频发，但 Claude 足够聪明，它自己能解决掉 Git 的合并冲突。
3.  最外层的无限 Agent 生成循环紧接着又会在一个全新的干净容器里生成一个新的 Claude Code 会话，如此周而复始。

这是一个非常早期的原型研究。我还没来得及让 Agent 之间实现任何其他的沟通方式，也没有强制执行任何高层级的全局目标管理流程。我压根没有使用所谓的“编排协调者（Orchestration Agent）”。

相反，我完全把“决定该怎么做”的权力下放给了每一个独立的 Claude 自己。在大多数情况下，Claude 总是会挑“下一个最明显”的臭虫或者问题去捡漏。当遇到解不开的 Bug 卡壳时，Claude 经常会自己建一份跟踪文档，把试错失败的方法和剩余待办全记下来。在这个项目的 [Git 官方代码仓库](https://github.com/anthropics/claudes-c-compiler) 的历史记录里，你可以亲眼看到它在这个文件锁机制里来回跳跃争抢各项子任务。

## 在与 Claude 智能体团队结对编程中吸取的教训

脚手架的确让 Claude 进入了死循环死磕，但这个循环只有在 Claude 完全清楚“怎样才算取得了进度”时才有用。我绝大部分的精力实际上都花在了为 Claude **精心构建其周围的生存环境要素**上——测试用例、基础设施环境、反馈信号收集通道——以便它能在没有我插手的情况下自己弄清楚方向。在交响乐般去协调多个 Claude 实例时，我发现下面这些理念最为有效。

### 编写极高水准的测试用例（Write extremely high-quality tests）

Claude 会自我驱动去解决我扔给它的任何问题。所以，作为“验收方（task verifier）”的测试套件必须近乎完美，否则 Claude 就会偏离轨道去解决完全错误的问题。改进这个测试引擎需要我去寻找最高质量的编译器测试库，为开源软件包编写验证器和构建脚本，并死死盯着 Claude 常犯的那些错误模式，然后针对性地设计新的测试用例来卡住这些它会跌入的陷阱。

比如，在项目快收尾时，Claude 开始频繁地在每次实现新功能时把已经写好的旧有功能给搞坏。为了解决这个问题，我直接搭建了一个 CI （持续集成）流水线，实施了更严苛的代码阻断执行规范，以便 Claude 能更稳妥地跑测它自己的产出，确保那些新提交的 PR 绝对不会把已建成的代码地基给弄塌。

### 设身处地代入 Claude 的视角（Put yourself in Claude’s shoes）

我必须时刻勒令并提醒自己：我写这个测试用例的受众是给机器 Claude 看的，而不是给我自己人脑看的！这就要求我推翻大量此前关于“究竟什么样的报错结果才算好”的经验假设。

试想一下，每个 Agent 就像个失忆者被突然空投进一个全新的干净容器里。在一片汪洋的大型项目里，它要想摸清状况必须得耗费极长的时间来定位自己。为了能在测试报错之前先让 Claude “帮到它自己”，我加入了明确的指令要求它：你必须去疯狂地维护大量巨细无遗的 README 文件和进度追踪文件，而且得用它当前最新的业务状态极其高频地去刷新这些内容储备。

我也始终牢记大语言模型生来就有的固有缺陷，并必须绕开它们去设计方案：

*   **上下文窗口污染（Context window pollution）**：测试脚手架绝对不能向控制台狂喷数千字节毫无营养的报错垃圾字符串。充其量只能输出几行最简明的引文，然后把所有巨量的重要细节全部默默写进日志文件里，让 Claude 取出需要的部分去检索。日志文件必须做到让程序极易自动解析：如果报错，Claude 需要在同一行直接写入 `ERROR` 以及原因说明，这样用 `grep` 就能一把搜出来。如果能提前把那些需要聚合汇总的统计数据替 Claude 算好再喂给它，那就更完美了，这样能省去它宝贵的 Token 去重算这些玩意儿。
*   **时间盲区（Time blindness）**：Claude 是没有时间观念的，如果不加干涉，它会非常开心地花上好几个小时在那死循环跑测而毫无进展。由于每次 Agent 的随机采样子集是确定且固定的验证块，但横跨不同虚拟机验证时又实现了全覆盖，这使得脚手架可以通过默认开跑极小比例快随切片样本的方案让它仍然能完美敏锐地感知到项目的 Regression 退化和倒退。

### 让并行变得水到渠成（Make parallelism easy）

当遇到大批互不干扰的微小报错测试案例时，搞多线程并发那是简直再简单不过的事了：让每个 Agent 各自去领走一个不同的报错项去单线程冲杀。测试套件熬到 99% 的通过率后，各个 Agent 就被分配去死磕怎样把不同的小型开源项目（比如 SQlite、Redis、libjpeg、MQuickJS、Lua 等）给编译跑通。

但当特种 Agent 分队开始冲击编译这块硬骨头 Linux 内核时，它们大面积卡壳了。编译 Linux 内核是一座难以分割的史诗级巨型高塔，所有 Agent 都会在同一个 Bug 坑里摔倒，然后他们分别给出修复，接着又在代码合并时互相覆盖践踏对方的 PR，此时拉出 16 个分身来并跑也全无卵用，因为全卡死在同一关卡了。

解药是利用现成的活体神谕 [GCC](https://gcc.gnu.org/) 作为一个标定的线上绝对正确对比版本。我写了一个新的测试台：对于绝大部分内核代码使用 GCC 盲编，只留下少数特定文件交给 Claude 的新 C 编译器来试炼。如果内核最终组装顺畅，那么问题干脆就不在 Claude 分配到的那堆文件中；如果崩溃报错了，就可以用 GCC 把这一小批刺头重新再编一次进行缩小排除。这种将混沌缩小为具体“背锅侠代码”的能力，才彻底使得各个平行的 Agent 能够真正实现分工并行。

### 给 Agent 分配多元化职位（Multiple agent roles）

并发同样也极大地赋能了“工种专业化”。LLM 写的初级代码往往会为了苟活而大面积重写已经存在的基础功能，所以我直接派出了一个专项 Agent 去专职合并一切重复代码。另一位被任命主抓编译器自身的运行性能，第三位则负责输出更高效的下游编译目标码。我还拉来了一位专门站在资深 Rust 开发者视角的 Agent 去无情批判整个项目架构，还有人专门负责给天书般的代码配上文档。

## 压力测试智能体团队的突破极限（Stress testing the limits of agent teams）

这个项目设立的初衷就是一个能力天花板的试金石。我着迷于极度压榨测试当下 LLM （大模型）刚刚所能*勉强摸到*的极限短板，以帮我们做好未来大一统模型完全具备高可靠性时的心理预演。

我一直用 C 编译器这类巨物项目作为全系 Claude 4 模型能力的度量衡。一如往常，我给出了非常苛刻的大纲：一个毫无第三方依赖的、零起步优化的编译器、完全兼容 GCC、能啃下 Linux 内核编译、支持构建多后端输出接口。尽管我会点拨一下设计范式（比如告诉它必须要拉一个 SSA IR 中间层出来），但我绝对不告诉它这具体究竟该长什么样。

之前的 Opus 4 初级版连个能用的破轮子都捏不出来。Opus 4.5 是第一个迈过分水岭、拿出了一个虽然能跑过大型测试集但依旧无法啃下任何真正大型开源项目的残次版。这次我用 Opus 4.6 再次向神之禁区发起了冲击。

### 验收评估结果（Evaluation）

历经长达两周时间里的 2000 多次 Claude Code 会话切磋，Opus 4.6 丧心病狂地吞噬了 20 亿输入 Token 和生生吐出了 1.4 亿输出 Token，总计消耗的算力账单略微不到 2 万美元！相比于人工手搓和开天价薪水雇团队，这成本简直连零头都算不上。

这是一个完全断网瞎摸的净室环境（clean-room implementation，即 Claude 看不到任何网上的小抄答案）；它全凭这 Rust 里的那点基础标准库作为原力。这套狂飙出来的 10 万行代码最终炼成的编译器成功地在 x86、ARM 和 RISC-V 各种硬件地基上启动了 Linux 6.9！还能连带编译出 QEMU、FFmpeg 等一大波全家桶，更离谱的是它不仅在那个被称作 GCC 地狱受难测试集中达成了 99% 的通关率，甚至还通过了属于顶级开发者的终极信仰仪式：它成功编译并且运行了神作游戏《Doom》！

当然，这就快逼近 Opus 神力的极限边界了，也带有明显短板缺陷：

*   对于在 x86 设备上极其复杂和麻烦地想引导启动 Linux 从而退回古早期所跑的“16位实模式”这一阶段，Opus 因为生成的编译体积过大撑爆了极限，只能在这块代码逻辑上作弊地悄悄向 GCC 老爷子借用了一下援助（但这仅仅限于 x86 构架在这一段而已，如果是基于 ARM 和 RISC-V 那一套，编译器其实是可以硬刚下来全流程自主打包的）。
*   它的原生 Assembler 汇编器和底层的 Linker 链接器依然是软肋且极度容易犯蠢崩溃，演示版最后也全靠外包回 GCC 打底收尾。
*   它并不是无敌通配符，还不配给任何正宗正统编译器当替补。编译出来的底层效能奇差无比，基本相当于给一辆开了优化的跑车里装了个油耗比老年代步车还糟心的破引擎。
*   里面用来搭建主体的这海量 Rust 源码，虽然质量还说得过去，但跟那种登峰造极的大神级纯手工代码依旧有断层级别的落差。

这个终极成品的 C 编译器产物几乎已全然逼近并触达了 Opus 眼下全部潜能与极限的最高峰点。这玩意就开源在这 [GitHub 链接](https://github.com/anthropics/claudes-c-compiler) 了！

## 前瞻寄语（Looking forward）

每一代语言模型的演进都在开辟与其共舞的全新姿态。初期大家还将其供奉为 IDE 代码自动补全；接着它能在给出注释后帮你完成函数封装；直到诸如 Claude Code （还有像是 Cursor、Devin 这类新锐）这般的黑魔法应用推出，智能体才算真正破圈进入主流视线。但这些所有全都被束缚在一个极大的伪命题前提下：必须得有个大活人当保姆在那等着看它发功运行后，人类还要自己再跟一句来确认和调整它。

但这种由 AI “Agent Teams （智能体雇佣兵团队）”组网并行包揽掉全部重头工程的做法，完全彻底地将整包工程这种极高维复杂度和体量的独立接盘全自动无人值守实现变为了让人战栗的可能性。

这种全自动化的黑箱开发当然伴生着可怕的风险：当无人值守时代来临，那些你永远都没读过一遍就要发布上线的代码，会不会让你在午夜汗流浃背？所以我眼下既兴奋，也在这感到如坐针毡的担忧之中！能在2026年之初就在极高程度上去接近这神之禁区，完全超出我的心力预期。随着我们步入无人区接管全盘的这段荒蛮开发季里，我们太需要新的法则了！
