# Loop Engineering 研究推进计划

> 状态：v0.5，2026-09-28 更新；在 v0.4 的文章/KOL归档映射、Osmani 增量规则、§2.3 扩容地图、§4.1 采样预算纪律之上，新增“控制链”作为所有后续回源的归位骨架。本文是研究过程的控制面，不是 loop governance 操作规程，也不把当前假设写成行业共识。
>
> 研究主题入口：[`../README.md`](../README.md)。素材权威在本目录 `raw/` 与 `01_seed_reference/`，判读权威在 `digested/`，实践操作权威在 [`../../../../03_practice/loop_governance/`](../../../../03_practice/loop_governance/README.md)。

## 0. 为什么要研究

用户在使用 DSH 插件时出现了一个初步体感：工作开始像“让系统替自己持续提示、推进、验证”，但这种体感没有稳定的概念边界，也还没有足够清楚的跨 feature 可见性、授权和验收方式。用户原本以 SDD 为参照系，因此研究不能只回答“loop engineering 是什么”，还要解释：

- 这是不是一个有稳定含义的实践流派、命名事件，还是几个相近实践者对同一现象的不同命名；
- 哪些部分来自真实的一手实践，哪些只是博客作者事后整理出的模型；
- loop 与 SDD、harness/context 治理分别解决什么问题，能否组合，在哪些地方会互相替代或互相冲突；
- DSH 的 `goal`、续轮、todo、plan、插件仓自建的 roadmap/notes，分别落在这张地图的哪里；
- 最终哪些观察可以升格成 `03_practice/loop_governance/` 的实践主干，哪些只能保留为假设、案例或开放缺口。

**工作假设**：用户感受到的可能不是“没有 SDD 后就变成 loop”，而是控制重心从“人预先规定变更产物和阶段”转向“系统持续取题、执行、检查、记忆和决定是否继续”。该假设必须持续接受反例检验。

## 0.1 统一研究骨架：控制链，而非素材清单

从本轮 KOL 对齐和 `stop_conditions` 深挖开始，后续研究不再把“loop engineering”主要当作人物、产品或环数的集合，而按一条可核的控制链归位每条证据：

```text
Goal / 边界
  → Action / 本轮行动
  → Environment Feedback / 环境反馈
  → Eval / 裁判与证据
  → Continue | Stop | Escalate / 控制决策
  → State & Outcome / 状态与外部结果分账
```

这条链是本主题的**研究抽象**，不是任何 KOL 的原文 taxonomy。Andrew Ng 的三环放在上位：它解释反馈如何在编码、开发者判断、真实用户验证三个时间尺度回流；Osmani、Claude Code、Anthropic、Ralph、LangChain 等材料提供链上机制。研究时必须分开三层：

- **概念层**：KOL 如何描述 loop、反馈、人和产品反馈；可用于概念对齐，不直接当规范。
- **机制层**：源码、官方 docs、运行轨迹和失败复盘如何实现 goal、eval、反馈、停止、权限与恢复；这是硬核研究主体。
- **效果层**：受控对照、真实指标、独立复盘是否证明质量/返工/吞吐变化；没有这一层，不写“有效”或“最佳实践”。

每条新证据进入档案时，至少标记它主要落在哪个控制节点，并写清“支持什么 / 不支持什么”：

| 控制节点 | 最小问题 | 不可偷换成 |
|---|---|---|
| Goal / 边界 | 目标可观察吗？范围和不可变约束是什么？ | “愿望写得更长”就是可执行 goal |
| Action | 下一步做什么、谁决定、授权覆盖什么？ | 自动执行就是自主治理 |
| Environment Feedback | 失败/通过信号是否来自可复查环境事实？ | 模型自述已经完成 |
| Eval / 裁判 | 判据测到目标了吗？谁能改判据？ | 有测试就等于验收正确 |
| Continue / Stop | 为什么继续、停止、暂停或熔断？ | 停机就等于完成 |
| Escalate / Authority | 拒绝后人能否看见、决定、恢复？ | 设计了升级按钮就等于可接手 |
| State / Outcome | 本轮状态如何接续？外部结果是否已观测？ | 持久日志就是 feature 控制面 |

**本骨架的硬边界**：三件停止骨架（机器闸门、硬上限、验收与干活分离）是控制内核；goal/eval 的构造与困难分支由 [`agent_goal_eval`](../../goal_eval_engineering/README.md) 负责；本计划只研究它们如何接入多轮控制。后续不得用 Ng 的“bug-free”替代可核判据，不得用 `/goal` 的某个产品阈值制造通用轮次刻度，不得把“机制存在”写成“效果已证”。

## 1. 研究问题树

### Q1：名称与边界

1. `loop engineering` 何时、由谁、在什么语境中被命名？
2. 不同使用者说的 loop 是否共享最小核心：反复行动、反馈/验证、状态记忆、停止或继续？
3. 哪些内容是定义，哪些是推荐架构，哪些只是作者自己的产品能力或案例？
4. `loop engineering` 是运动名、工程层、方法论，还是多个尺度的同名词？

### Q2：实际构件

1. 一轮如何触发，下一轮由谁/什么决定？
2. 工作如何跨轮、跨会话、跨 feature 记忆？
3. 何时算完成，谁来裁判，如何防止提前宣布完成？
4. 哪些反馈是 deterministic gate，哪些是 grader/LLM-as-judge，哪些必须由人判断？
5. 如何处理失败、拒绝、权限、风险和资源上限？
6. loop 是否会修改自己的 harness、规则或工作来源？如果会，如何防止自我强化错误？

### Q3：自主度与人在环

1. 实践者如何描述自主度阶梯？是按位置、动作类别、风险、事件还是轮次计量？
2. 人应该在哪些点介入：授权、范围变化、关键歧义、熔断、最终验收？
3. 是否存在可迁移的升档/降档判据，而不只是“感觉可以放手”？
4. 行为面（是否做了该做的事）如何补足动作面（是否触发了危险动作）？

### Q4：与 SDD / harness 的关系

1. spec、proposal、task、feature list、progress log 在 loop 中分别充当什么角色？
2. SDD 的阶段门哪些可以变成机械检查，哪些仍必须保留真人判断？
3. loop 是否吸收了 SDD 的外部记忆与验收功能；SDD 是否吸收了 loop 的自动推进？
4. harness/context 治理解决单次运行的约束，loop 治理解决多轮控制；两者的接口和混淆点是什么？
5. 是否有反例：小任务需要厚流程，或长任务不适合自动循环？

### Q5：DSH 对照与真实体感

1. DSH 原生提供的是会话执行能力、goal 续轮、todo/plan 等控制面，还是完整的跨 feature loop 管理？必须逐项回到源码/官方文档。
2. 插件仓自建的 roadmap、proposal、queue、验证门，哪些是在补上游空白，哪些只是项目自己的偏好？
3. “跑得动但看不清”究竟来自工作来源不可见、目标授权不清、进度不外置、质量验收不独立，还是多个因素叠加？
4. 能否用真实工作样本而非口述，观察催问次数、目标漂移、返工、提前完成和人工介入点？

### Q6：实践升格标准

一个建议只有在以下问题基本回答后，才可从研究层进入实践主干：

- 是否有至少两条独立的一手来源，或明确标为单源/案例性建议；
- 是否能写出适用边界、失败模式和反例；
- 是否能被人或机器观察/检查，而不是只靠“感觉更自主”；
- 是否明确它属于 prompt/context/harness/loop/graph 哪一层；
- 是否能在 DSH 或类似环境中用小规模实验验证，而不是直接宣布为规范。

## 2. 研究分路

后续每轮按问题分路，不按“找几个大人物”分路。一个 Agent 只负责一个可验收问题，回源档案按日期和路别归档。

| 路 | 目标 | 首选一手来源 | 主要产物 | 当前状态 |
|---|---|---|---|---|
| A 命名与定义 | 词源、定义、外延差异 | 作者原文、官方博客、原始视频/转写 | `evidence-*` + `digested/01` | 已有一轮，继续补冲突 |
| B 循环原语 | 触发、反馈、停止、熔断 | 官方文档、源码、工程复盘 | `evidence-*` + `digested/03` | 已有一轮，需补跨产品比较 |
| C 外层调度 | 下一项工作、跨会话记忆、事件/时间触发 | 官方产品文档、源码、真实工程案例 | `evidence-*` + 新议题 | 已有初步收敛，跨 feature 可见性仍缺证据 |
| D 自主度与人在环 | 升档、降档、介入点、风险 | 一手 playbook、工程团队复盘、产品机制说明 | `evidence-*` + `digested/03` | 位置阶梯已有，量化判据空白 |
| E SDD 对照 | spec/plan/task 如何进入循环 | SDD 官方 docs/release、实践者原文 | `evidence-*` + `digested/05` | 已有双向收敛判断，需持续防止二选一叙事 |
| F harness/context 接口 | 单次运行约束与多轮控制的边界 | 官方工程文、源码、失败复盘 | `evidence-*` + 边界判读 | 已有分层，待找反例 |
| G DSH 一手对照 | 原生能力、实际行为、插件补层 | DSH 源码、官方 docs、session schema、插件 repo | 独立 evidence，不把 FAQ 当主证 | FAQ 有初步样本，需按真实实验复核 |

| I 先进团队与思想扩容 | 命名簇（Osmani/Runkle/Ng/Anthropic）之外的高影响 KOL、先进 AI 团队、社区的盲区扫描——每个候选必须绑定一个缺口或控制问题，不按人名扫街 | 官方 docs、工程博客、本人长文、论文页、定量研究报告 | `evidence-i*` + 台账 §B/§C1（处置规则见 §2.3） | 批次 1 已收口（高影响面控制实践）；批次 2 raw 档案已形成，主验与侦察回源混合，综合判读待筛选 |

**委派原则**：A–I 可以并行，但同一事实只有一个素材 home。新 Agent 先读 `CURRENT.md`、本计划和对应 evidence 索引，先声明不重复的切口，再写档案。

### 2.1 一篇文章如何进入主题：文章、KOL、判读三层拆分

以 Addy Osmani 2026-06-07《[Loop Engineering](https://addyosmani.com/blog/loop-engineering/)》为例，归档路径固定如下：

| 内容 | 唯一归宿 | 本例当前状态 | 处理规则 |
|---|---|---|---|
| **文章原文及逐字摘录** | `raw/evidence-*.md` 回源档案 | 已在 [`evidence-2026-09-26-a-originators.md`](evidence-2026-09-26-a-originators.md) §4 与补充回源节 | 记录 URL、发布日期、观测日期、作者、原句、最小主张、证据强度、限制；同一篇文章不因“值得深挖”再复制成第二份事实档案 |
| **作者是否算本主题 KOL** | `raw/kol-roster.md` 唯一名单权威 | `addy_osmani` 已入 §A | 记录身份、号召力依据、对本主题的一句话主张、证据指针；台账不复制文章正文 |
| **作者的完整观点** | `01_seed_reference/reference/kol/_raw_loop_engineering/` 或已有个人卡 | Osmani 当前素材留 evidence；Andrew Ng 有历史四件套卡 | 只有独立一手长文达到主题建卡门槛（当前规则：≥3 份）才建卡；否则以 evidence 按问题组织 |
| **文章点名的其他人** | 先回到各自的 evidence，必要时更新台账 §A/§B/§C | Cherny、Steinberger 已有词源定性；Runkle 有独立一手文章；Andrej 等需按来源另判 | “被 Osmani 提到”只证明引用关系，不自动等于 KOL 入册；要分别检查其本人原文、深度、影响力和时间窗 |
| **多篇文章之间的综合判断** | `digested/` | `digested/01`、`03`、`05` 已综合 | 只在这里比较“共同核心、外延冲突、定义/建议/案例”；不把某一作者的 opinion 直接升格为规范 |
| **可执行的实践建议** | `03_practice/loop_governance/` | 已有 backbone/manual 初稿，待复核 | 只有经过证据筛选、写出边界/失败模式并能观察验证，才从 `digested/` 进入实践层 |

因此，Osmani 文章不是“放在 KOL 目录里”或“只放在 raw 里”二选一：**原文放 evidence，作者进 KOL 台账，点名人物按人分别回源，跨人比较进 digested，实践建议再进 practice**。这是同一事实的不同索引，不是五份重复正文。

#### KOL 收录的四步门

1. **提及登记**：文章点名某人时，先在 evidence 中记录“谁提到了谁、原文怎么说、是否为转引”。
2. **原文回源**：找到被点名者自己的原帖、博客、官方文档、演讲或访谈；拿不到时只能写“经 X 转引”，不能伪装成本人逐字证据。
3. **深度与影响力判定**：按主题 README §1 的口径判断是否入 `kol-roster.md`；碎片级词源可以留在时间线/证据，但不强行建深度卡。
4. **分离三种声音**：被引用者的原话、引用者的解释、我们自己的综合判读必须分开写。尤其“他也有这个意见”要标明是原话、转述还是我们的相似性判断。

#### 本例的 KOL 映射

- **Addy Osmani**：命名者/主要定义者，已入 §A；两篇文章是一手素材，不需要再建“文章人物卡”来复制正文。
- **Boris Cherny**：Osmani 点名的词源人物；当前只能把 WorkOS 回顾和 YC transcript 支持的内容与未取得的访谈原声分开，不能把流传名句当本人逐字定义。
- **Peter Steinberger**：词源推文经 Osmani 转引；其深度应回到本人长文与 OpenClaw 官方文档，不能只依据 Osmani 的一句转述。
- **Sydney Runkle / LangChain**：有自己的《The Art of Loop Engineering》一手长文，观点应独立归档并与 Osmani 对照；四环模型不能自动当成 Osmani 模型的同义扩展。
- **Andrew Ng**：已按独立三环观点保留个人卡；他的“context advantage”和产品反馈环属于方法论层，不能压缩成停止条件工程定义。
- **文章中仅作为背景或引用出现的人**：先进入证据档案的“引用关系”，只有满足独立回源和 KOL 门槛才升台账；否则留在候选/谱系区。

## 2.2 新议题：Automation → Autonomy → Harness → Loop？

用户提出的体感假设是：AI Coding Agent 早期更强调 **automation**（替人执行重复动作），模型能力提升后，实践者更关心 **autonomy**（系统自主决定如何推进目标）；当单次运行越来越自主，可靠性、上下文、工具、权限、验证和恢复问题集中暴露，于是 **harness engineering** 被强调；harness 把单次运行托住以后，下一层自然变成跨轮、跨会话、跨任务的调度与控制，也就是 **loop engineering**。

这条链目前只能作为**候选因果模型 H1**，不能作为已证历史。研究时并列保留以下竞争解释：

| 假设 | 说法 | 若为真，应观察到什么 | 主要反证 |
|---|---|---|---|
| **H1 能力推动的控制面迁移** | 模型从“执行动作”变成“可持续做判断”，工程问题从自动化动作转到自治循环；harness 是单次自治的地基，loop 是多轮自治的控制层 | 一手文本按时间出现：workflow/工具调用 → 自主 agent/环境反馈 → 长程 harness → 外层 loop/调度；后文明确引用或继承前文机制 | 早期已同时存在 autonomous agent、harness 和外层循环，只是后来才改名；没有概念依赖链 |
| **H2 命名与产品包装** | 机制一直并存，2026 年只是把已有的自动化、agent、harness、调度能力用新名字重新打包 | 各词源文本外延互不兼容；命名者主要在做术语聚合；后续产品 marketing 扩散大于机制新增 | 发现新出现的控制原语、独立失败模式和新的工程接口，而非只是改名 |
| **H3 失败模式驱动** | 不是模型能力本身，而是“自动化跑起来后暴露失控/失忆/提前完成/质量难验”的失败，逼出 harness；harness 稳定后才需要 loop 层 | 长程 harness 文本明确记录失败模式，并给出 feature list/progress/git/test 等补丁；loop 文本继续强调 unattended mistakes、done≠proof、comprehension debt | 如果 loop 的主要动力来自吞吐/成本/组织协作，而不是失败修复 |
| **H4 产品能力同步演进** | Codex/Claude Code 等产品把 automation、worktree、skills、connectors、sub-agents、goal、schedule 同时产品化；社区观察到的是组合能力，不是阶段迁移 | 同期产品文档把 primitives 并列映射；不同厂商出现相似表面形状，但无共同演进顺序 | 找到明确的“harness 是 loop 的前置层”或跨厂商引用链 |

### 这条议题的证据门

- **时间顺序不等于因果**：必须记录发布日期、作者/机构、是否直接引用前一概念，以及文本是在描述机制、建议实践还是事后命名。
- **automation 与 autonomy 不做二元对立**：至少区分“自动触发/自动执行”“模型自主选择下一步”“系统自主决定是否继续”“人是否保留授权/验收权”四个维度。
- **harness 与 loop 分层要按问题而不是词判断**：harness 主要回答单次运行的环境、工具、上下文、约束与验证；loop 主要回答多轮触发、停止、记忆、调度与人在环。若同一来源把两者合并，保留其原作者外延并标冲突。
- **效果证据另算**：一篇官方文章说“更可靠”只构成设计主张（P-existence/P-mechanism）；只有运行指标、受控比较或独立复盘才进入 P-outcome。

### 当前初步判断（待 H 路回源修订）

最可能不是“automation 被 autonomy 取代”，而是**控制对象外移**：早期自动化控制动作，模型变强后控制权部分移给模型；于是工程师必须设计环境与反馈（harness），再设计循环的触发、停止、记忆、调度和授权（loop）。因此可以暂定为“控制问题逐层外移/叠加”，不能暂定为严格的行业阶段论。

### 阶段 1.1：控制链审计卡（每条机制进入判读前必填）

为避免“有 evidence 但结构不硬”，每条进入 `digested/` 的机制至少按以下字段审计；缺字段就留在 raw 或标为开放缺口，不直接进实践主干：

```text
control_node: Goal | Action | Feedback | Eval | Continue/Stop | Escalate/Authority | State/Outcome
actor: 谁发起、谁执行、谁观察、谁裁判、谁能改判据
input: 本轮拿到的目标、授权、上下文或上一轮结果
observable: 外部可复查的事实（退出码、状态、日志、文件、指标或人工记录）
decision: 继续 / 停止 / 暂停 / 拒绝 / 升级 / 接受中的哪一种
handoff: 停止或升级后是否有人能看到、决定、恢复；恢复指针是什么
boundary: 该机制明确不能保证什么
failure: 至少一个误报、漏报、绕过、漂移或资源失控面
claim_level: P-existence | P-mechanism | P-outcome
```

**三条硬审计规则**：

1. `observable` 为空时，不能把作者的“完成/可靠/bug-free”表述写成可核停止条件；
2. `decision` 只有“模型说完成”时，必须标为自判弱点，不能与环境闸门并列；
3. 没有 `handoff` 时，“支持人在环/可升级”只能写成概念或产品意图，不能写成可用控制路径。

**控制链的研究输出不是把所有节点填满**。某一节点长期为空，本身就是结果；例如目前仍缺通用轮次刻度、feature 级授权史和跨 feature 验收。不得用相邻节点的材料代填。

### 阶段 2：寻找反例和失败边界

至少主动寻找：

- 有 loop 但没有可靠停止条件，导致重复错误或提前完成；
- 有 spec 但 agent 不遵守，导致“文档把控感”而非真实质量；
- 有机械门但无法检查遗漏/意图/体验；
- 有外部队列但目标授权和优先级仍不清；
- 小任务被过度治理，循环成本超过收益；
- 自动审批提高吞吐但扩大安全/质量风险；
- 词源人物的口号与其长期实践不一致。

每个反例至少记录：上下文、触发条件、失败表现、现有保护、保护的盲点、是否可泛化。

### 阶段 3：做小规模实践实验

研究层稳定后，才在 `03_practice/loop_governance/` 组织实验性规程。每次实验只改变一个控制变量，优先用已有 DSH 插件仓和小 feature：

- 固定同一个工作项，对照“对话内 goal”与“外置工作来源 + goal 引用”；
- 比较不同停止条件：测试门、验收清单、独立评估、人工最终裁判；
- 记录取题、授权、续轮、阻塞、人工介入、返工和提前完成；
- 观察控制面是否真的减少“催问”与“做完才发现”；
- 实验结果仍标为本地实践，不外推成行业事实。

## 4. Agent 委派协议

每个并行 Agent 的任务必须包含以下字段：

1. **问题边界**：只回答一个 Q 或一个控制问题；
2. **来源边界**：优先指定官方文档、原作者文章、源码、release、原始访谈；
3. **时间窗**：记录发布日期和观测日期，不能用当前页面状态代替历史状态；
4. **交付格式**：URL、发布日期、原文摘录、自己的判读、证据强度、负结论、限制；
5. **不得外推**：没有作者行为证据时，不从仓库目录推断实际工作流；没有量化来源时，不制造轮次阈值；
6. **交叉检查**：指出与现有 evidence/digested 的一致、冲突和重复；
7. **停止条件**：查完指定来源并完成反例/限制段落即可交付，不以“把整个互联网搜完”为完成标准。

## 4.1 低成本多 Agent 采样协议：高召回、低信任、主 Agent 收口

用户可以让多个较弱模型并行反复跑，以扩大来源覆盖和暴露遗漏。这是本主题允许且推荐的**研究采样层**，但必须遵守一句话：

> **弱模型负责找、抄、比、挑错；主 Agent 负责回源、归属、定级、综合和落盘。重复次数增加召回率，不自动增加证据强度。**

### 适合交给弱模型的任务

- **Source scout**：按一个问题寻找官方 docs、原作者文章、源码、release、issue、原始访谈；返回 URL、作者/机构、日期和可能的引用链；
- **Quote extractor**：只从指定一手页面摘录支持/反驳某个最小主张的原句，带页面标题、段落线索和原文上下文；
- **Metadata checker**：核对发布日期、版本、commit、作者身份、URL 是否重定向或失效；
- **Concept coder**：按固定字段给多个来源标注 automation/autonomy/harness/loop、trigger/stop/memory/verification/approval 等，不要求它下最终结论；
- **Counterexample hunter**：专门寻找与当前判读相反的来源、失败案例、限制条款和“设计存在但无效果证据”的句子；
- **Gap auditor**：对现有 evidence/digested 逐条检查“引用是否真的支持这句话”“是否把机制写成采用/效果”“是否重复计票”。

### 不允许弱模型自行拍板的事项

- 不直接决定一个来源是不是 KOL、是否入 `kol-roster.md`；
- 不把转引、搜索摘要、中文编译或 issue 评论写成原作者逐字证据；
- 不自行判定 P-existence / P-mechanism / P-outcome；只能提出候选并说明依据；
- 不自行宣布“行业趋势”“阶段迁移”“因果关系”“最佳实践”或“已收敛”；
- 不直接改 canonical `raw/evidence-*.md`、`digested/`、`CURRENT.md` 或 `03_practice/`；
- 不把多个弱模型说出同一句话当作多个独立来源。来源独立性按原作者、机构和引用链计算，不按 Agent 数量计算。

### 并行批次怎么跑

1. **一个问题拆多个互斥切口**：例如同一 P0 分为官方产品文档、开源源码、失败 issue、反方来源、历史来源，不让所有 Agent 重复扫同一个搜索结果页。
2. **至少三种角色交叉**：一批 scout 找来源，一批 extractor 摘句，一批 skeptic 专门找反例；不要让同一个模型既找证据又替证据判案。每批开始前必须声明 `max_agents`、`max_attempts_per_agent`、时间/Token 预算和允许的重复率；没有预算就不启动批次。
3. **默认预算而非无限并发**：一个研究切口先用 3–5 个 Agent 做第一批；只有出现新的独立一手来源或真正新反例，才开第二批。达到预算、连续 3 个 Agent 无新增，或候选结果重复率超过预设阈值时停止。
4. **独立提示、隔离结果**：弱模型先不要看到其他 Agent 的答案，避免共识只是互相模仿；结果放仓库根 `.tmp-loop-research-<batch>/` 或直接返回，不进入 canonical 目录。
5. **结构化交付**：每条候选事实至少返回以下字段：

```json
{
  "question": "Q/C 控制问题编号",
  "source_url": "一手 URL",
  "publisher": "作者/机构",
  "published_date": "YYYY-MM-DD 或 unknown",
  "observed_date": "YYYY-MM-DD",
  "quote": "原文摘录，保留上下文",
  "supports_minimal_claim": "这句话最多支持什么",
  "does_not_support": "不能推出什么",
  "source_type": "official-doc/source/blog/interview/issue",
  "candidate_evidence_level": "P-existence/P-mechanism/P-outcome/uncertain",
  "citation_chain": "本人/官方转引/第三方转引/unknown",
  "duplicate_or_conflict": "已知重复或冲突来源",
  "limitations": "访问、版本、样本和推断限制"
}
```

5. **主 Agent 合并而不是投票**：按 URL/commit/原作者去重；回到原页面逐字核对；检查摘录前后文；把“观察、推断、建议”分开；只有核验后的事实才进入 evidence 档案。
6. **反向攻击一轮**：初稿判读形成后，再让弱模型只做 adversarial review：找过度断言、缺少反例、错误归属、重复计票和“存在性→效果”的跳跃；它们不负责改稿，主 Agent 根据原文决定是否修改。

### 批次停止条件

- 每个切口至少取得一手来源，或明确写出检索范围内的负结论；

- 已经只有重复转述、搜索摘要、社区情绪或无法回源的线索时，停止堆数量，转入人工回源/缺口登记；
- 预算优先给“来源发现”和“反例攻击”，不要无限重复同一摘要任务；
- 一轮结束必须由主 Agent 写入：新增事实、证据等级、独立性去重、仍缺字段和下一步唯一入口。

### 质量解释

多 Agent 并行适合回答“我们有没有漏掉重要材料”，不适合单独回答“这个结论是真的吗”。因此本主题把它视为一个**召回率工具**：弱模型越多，越可能找到候选来源与反例；但最终可信度仍取决于一手回源、引用链、证据层级和是否有 P-outcome。没有主 Agent 的回源和合并，跑得越多只会产生越大的重复噪声。

## 5. 证据纪律与质量门

- 一手原文优先；作者转述、媒体转述、中文编译必须分层标注；
- 发布日期和观测日期分开写；动态页面要记录版本/commit/tag；
- “未找到”必须写搜索范围和检索词；“官方没有”必须说明检查了哪些官方入口；
- 观点、机制、行为、效果四类主张分开，不用观点证明行为，不用机制存在证明机制被采用；
- 每条结论额外标注证据层级：**P-existence**（一手材料证明某个名字/观点/功能存在）、**P-mechanism**（源码/文档/运行轨迹证明怎样工作）、**P-outcome**（受控对照、真实运行指标或独立复盘证明效果）。P-existence/P-mechanism 不能自动升级为 P-outcome；
- 统计“独立来源”时按作者、机构和引用链去重：同一厂商的多篇演化文档不算多家独立票，Osmani 转引 Cherny/Steinberger 不增加原始来源票，Thoughtworks 内部不同作者需注明同阵营；
- 任何单个作者的建议都不得直接升格为术语准入条件；
- 研究结论只写到证据支持的粒度，宁可保留两个竞争解释；
- 外部 FAQ 15 只作问题线索与对照，未经本主题独立回源不能当主张依据；
- evidence 档案是素材常态形态；同一事实不复制到多个档案，判读只在 `digested/` 写综合判断；
- 每轮结束更新 `CURRENT.md`：新增事实、仍开放的问题、下一轮唯一优先入口、委派结果状态。

## 7. 每轮收口格式

本轮新的收口要求：先回答控制链落点，再回答证据新增。不要只写“新增了某人/某产品”。

每轮只回答三件事：

1. **控制链落点与新增事实**：它落在哪个节点（Goal / Action / Feedback / Eval / Continue-Stop-Escalate / State-Outcome），新增什么可回源事实？（链接到 evidence）
2. **改变了哪一个判读或缩小了哪一个不确定性？**：区分概念、机制、效果三层；链接到 digested；没有改变就说没有。
3. **下一轮最值得做的一个问题是什么？**：只留一个可验收入口，链接到 backlog；不要泛泛列十项。

当一轮没有新增一手事实，只产生解释或实践建议时，必须明确标成“解释/建议”，不能更新为“研究已证实”。

## 8. 现阶段暂定结论

- `loop engineering` 已是公开使用的命名，但核心共识比外延更稳定；不能把单一作者的模型当成统一标准。Willison 2025-09 的 *designing agentic loops* 是相邻旧名，不是这个词的提前发明。
- 高影响面并不共识“让模型自己 loop 到目标”。Horthy 要求人拥有控制流；Beck、Yegge 把删测试和提前宣布完成写成真实失败。OpenAI、Cursor、GitHub 的循环都还把环境和人的交接留在外面。这扩大了样本，没有产生新的行业规范。
- 当前最可靠的共同问题不是“要不要一直跑”，而是：下一步工作从哪里来、如何验证、何时停止、状态如何跨轮记住、人在何处负责授权与判断。
- 现有材料支持 loop 与 SDD 组合，而不支持“loop 已取代 SDD”；规格可以是工作来源、外部记忆和验收依据，循环可以自动推进和反馈。
- 现有 DSH 对照支持“执行循环与跨 feature 控制面不一定同等成熟”的研究假设。`digested/07` 把这句话收成四列空格：授权史、priority 变更、业务阻塞原因、跨 feature 验收。这是综合，不是新的一手证实。2026-09-27 的本地日志（evidence-j）只再确认：一条真实 goal 上这四列仍空，而且 goal 被 resume 时 driver 可以一次轮都不计。对照臂没跑，所以这不是效果证据。
- `03_practice/loop_governance/` 当前已有实践主干初稿；本计划的作用是约束它后续只吸收达到证据门槛的结论，并保留开放缺口。
