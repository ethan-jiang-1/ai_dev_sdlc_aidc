# 01. 为什么必须抛弃“多 Agent 自由聊天”，走向“DAG 状态机与强类型工件”？

> **判读依据**：`raw/evidence-20261001-field-exchange.md`、`raw/evidence-20260718-steinberger-graph-shift.md`。

---

## 1. 早期 Multi-Agent 的“群聊诱惑”与工业级破产

在 2023 ~ 2024 年 Multi-Agent 原型探索期（以 AutoGen、ChatDev、MetaGPT 早期版本为代表），开发者最直观的想法是构建一个“虚拟软件公司”：
- 为不同 LLM 实例注入身份：`System: You are a Product Manager`、`System: You are a Tech Lead`、`System: You are a Python Developer`、`System: You are a QA Engineer`；
- 将它们置于同一个 Group Chat 上下文中，让它们像真实人类在 Slack/飞书群组里一样依次自由发言、讨论、互相提建议。

这种模式在演示 Demo（编写贪吃蛇小游戏、20 行算法题）中表现惊艳，但在**真实工业级复杂系统工程（数万行代码重构、跨模块联动开发）中遭遇了彻底的工程破产**。

---

## 2. 自由聊天的四大工程死穴

在一线工程实践中（参见 2026-10-01 现场实录：“多 Agent 聊天还是个太贵的方案”、“不，不能让多 Agent 聊天”），自由聊天模式存在四个无法克服的系统性死穴：

### ① Token 消耗呈二次方（甚至指数级）爆炸
- **机制**：群聊中第 $N$ 轮发言必须拼接前 $N-1$ 轮所有角色的全量历史。
- **代价**：当会话推进到 20 轮、涉及 4 个角色时，单次模型调用的 Prompt 上下文迅速膨胀到数十万 Token。一次普通的需求迭代即可轻易烧穿每日 API 配额，经济成本完全不可承受。

### ② 客套礼貌与注意力稀释（Context Dilution）
- **机制**：LLM 具备极强的社交对齐本能，角色之间频繁出现冗长的公关套话（“非常感谢 PM 详尽的 PRD”、“架构师的拆解非常深刻，我完全赞同”、“让我来为您编写这段代码”）。
- **代价**：大量毫无信息增量的社交噪音不仅占用了宝贵 Context，更稀释了大模型在注意力机制（Self-Attention）中对核心业务逻辑和代码规范的关注度，诱发幻觉。

### ③ 缺乏终止仲裁，易陷入反驳死循环（Doom Loop）
- **机制**：当 Coder 提交的代码未通过 Reviewer 的审美标准，两者若在同一聊天室内对话，极易陷入无穷尽的“修改-反驳-再修改-再反驳”哲学辩论，缺乏强制性的终局状态判决。
- **代价**：没有任何一方有权威宣布“停止并升级”，直到上下文超限崩溃。

### ④ 产物形态松散，缺乏确定性测试闸门
- **机制**：自由对话中产生的是非结构化自然语言段落，混杂着 Markdown 代码块、解释文字与闲聊。
- **代价**：自动化测试工具（pytest、tsc、linter）无法直接挂载在松散对话中；没有强类型的工件边界，下游角色无法确认上游到底提交了什么。

---

## 3. 替代方案：DAG 状态机（DAG State Machine）

生产级 Graph Engineering 的核心原则是：**消灭自然语言群聊，全面拥抱显式有向图与强类型状态机。**

```text
       [自由聊天 (Chat-based) - 反模式]                      [DAG 状态机 (Graph-based) - 生产范式]
       
      ┌───────────────────────────────┐              ┌───────────────┐
      │   Shared Chat Room (Context)  │              │  Spec Node    │
      │  PM ◄──► Lead ◄──► Dev ◄──► QA │              └───────┬───────┘
      │   (Token爆炸 / 礼貌客套 / 死锁) │                      │ Typed Artifact: spec.json
      └───────────────────────────────┘                      ▼
                                                     ┌───────────────┐
                                                     │  Task DAG Gen │
                                                     └───────┬───────┘
                                                             │ Static Lint (环路检测/契约校验)
                                                             ▼
                                                ┌─────────────────────────┐
                                                ▼ (Fan-out 并发)          ▼
                                         ┌──────────────┐          ┌──────────────┐
                                         │ Worker A Node│          │ Worker B Node│
                                         │ (独立上下文) │          │ (独立上下文) │
                                         └──────┬───────┘          └──────┬───────┘
                                                │ Patch A                 │ Patch B
                                                └────────────┬────────────┘
                                                             ▼ (Fan-in 汇聚)
                                                     ┌───────────────┐
                                                     │ Test & Review │ (确定性函数门禁)
                                                     └───────────────┘
```

### 核心运作规范：
1. **静态合法性校验（Static Graph Validation）**：
   - 编排者（Planner）生成的不是自然语言聊天指令，而是一份结构化的任务图定义（JSON / YAML）；
   - 在图执行前，执行严格的静态代码校验：
     - **有向无环校验（Acyclic Check）**：主向依赖必须无死锁环路；
     - **契约对齐校验（I/O Schema Match）**：后继节点的输入 Schema 必须是前驱节点产物的超集；
     - **资源与模型声明（Resource Manifest）**：明确每个节点分配的模型档位与超时硬上限（Timeout Cap）。
2. **节点间严禁直接会话**：
   - Worker 之间互不可见、互不通信；
   - 节点流转仅靠**强类型工件（Artifacts）**：例如需求规范文档、Git Patch、编译日志 JSON。
3. **上下文完全物理隔离**：
   - 每个 Worker 仅在执行自己对应的任务时分配独立的单次上下文；
   - 依赖的前驱信息由状态机按需精准投影，执行结束立刻销毁，彻底根除 Context Rot。

---

## 4. 业务语义：DAG 即组织结构与岗位交接

一线工程实践（参见 Willis 在 2026-10-01 的洞见）揭示了 Graph Engineering 的本质：

> **“DAG 的图就是业务逻辑，类似于人岗位的对接关系。”**

- **Node（节点）= 专职岗位（Role Function）**：不再是拥有泛化人格的“角色扮演”，而是具备明确职责、限定输入输出的专职算子（如：数据库迁移执行器、前端组件编写器、静态代码分析器）；
- **Edge（边）= 交付物标准与审批流（Handoff Contract & PR Review）**：正如人类工程师交接工作需要提 PR、附带单测报告并等待 CI 绿灯，图节点之间的跳转条件正是机器可核的质量闸门；
- **Cycle（回路）= 明确定义的返工流水线**：回路不再是无序的反驳，而是受限重试（Retry Cap <= 3）与条件重路由。

**结论**：Graph Engineering 的终极目标不是让模型学会画图，而是**将人类成熟的软件工程治理（规范驱动开发、敏捷分支、CI/CD、双人评审）编译为不可逾越的机器状态机**。
