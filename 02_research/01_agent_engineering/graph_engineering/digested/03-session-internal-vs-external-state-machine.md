# 03. 核心架构抉择：Session 内 Tool 驱动 vs Session 外 外部状态机驱动

> **判读依据**：`raw/evidence-20261001-field-exchange.md`（李奕晨与一线开发者研讨）、`raw/evidence-2026-langgraph-temporal-state-machines.md`。

---

## 1. 架构争议的源起

在 2026-10-01 的一线研讨中，李奕晨 Ethan 提出了一个直击图工程底层架构的根本问题：

> **“这个实践中，这个是做在 session 内的 tool，比如是主 Agent 和 sub Agent 用这种编排工具推进呢。还是做成了外部的逻辑呢？”**
> **“我主要是在看，这些逻辑究竟是做在主 session 内还是 session 外。”**

这代表了业界在设计复杂 Agent 系统时的**两大对立流派**。

---

## 2. 路线 A：Session 内 Tool 驱动（Agent-Centric Inside-Out）

### 机制：
一个全能型的主 Agent（Orchestrator）在自己的长 Session 内运行，图编排能力被包装为它可调用的工具（Tools）：
- `create_subtask(name, dependencies, prompt)`
- `wait_for_task(task_id)`
- `update_dag_structure(new_edges)`
- `inspect_task_result(task_id)`

主 Agent 自主决定何时调工具建图、何时派发子任务，并通过上下文记忆维护任务全局进展。

```text
┌────────────────────────────────────────────────────────┐
│                   Main Agent Session                   │
│                                                        │
│  [Prompt History ──► LLM Thought ──► Call Tool]        │
│          ▲                                │            │
│          │ Append Output                  ▼            │
│          └───────────────────────── [Tool: Run DAG]   │
│                                           │            │
└───────────────────────────────────────────┼────────────┘
                                            ▼
                                   [Sub-agent / Worker]
```

### 致命缺陷（生产不可承受之重）：
1. **上下文腐蚀（Context Rot）**：随着子任务的不断完成、报错、重试，海量工具调用结果和子任务日志被持续追加到主 Agent 的 Session 中。即便有总结机制，主 Agent 的注意力也会在数十轮后严重退化；
2. **“计划遗忘”与指令漂移**：在长程任务中，主 Agent 经常在执行到后期时“忘记”最初由用户设定的全局目标或架构红线；
3. **脆弱的进程生命周期**：若主机网络抖动、进程被杀，整个主 Session 的内存调用栈完全损毁，无法安全恢复；
4. **单点幻觉扩散**：主 Agent 一旦在某一步编排工具调用中产生参数幻觉（如传递了错误的路径），后续所有图流转均在错误基础上滚雪球。

---

## 3. 路线 B：Session 外 外部独立状态机驱动（Engine-Centric Outside-In）

### 机制：
系统的控制权**不在任何大模型手中，而是在确定性的代码状态机（如 Temporal、Raven A2A 或独立 Python 调度器）手中**：
- 调度引擎负责根据 DAG 图的拓扑依赖依次触发节点；
- 每一个 Worker Agent 只是一个**无记忆的、瞬态调用的外部算子（Ephemeral Worker Operator）**；
- 状态机向 Worker 派发任务时，只投影一份精准、最小的局部上下文；
- Worker 执行完成后，将结构化工件返回给状态机，Worker 进程/会话随即销毁；
- 状态机使用确定性校验器（Lint、Pytest、Schema Validator）检查产物，合规后才驱动图状态向前流转。

```text
┌─────────────────────────────────────────────────────────────────┐
│        外部确定性状态机引擎 (Session 外: Temporal / Raven / Go)       │
│                                                                 │
│   [DAG 拓扑定义] ──► [依赖就绪检测] ──► [确定性门禁 pytest] ──► 流转 │
└───────────────┬───────────────────────────────▲─────────────────┘
                │ Dispatch (最小干净上下文)       │ Return Typed Artifact
                ▼                               │
      ┌───────────────────┐           ┌───────────────────┐
      │ Worker 1 (独立Session)│       │ Worker 2 (独立Session)│
      │ 运行结束即销毁       │           │ 运行结束即销毁       │
      └───────────────────┘           └───────────────────┘
```

### 核心工程优势：
1. **彻底消除 Context Rot**：没有长期膨胀的主 Session，每个任务节点的执行环境都是 100% 崭新、纯净的；
2. **长生不老（Durable Execution）**：借助事件溯源（Event Sourcing）与持久化检查点，系统可以暂停等待人类审批数天，甚至在服务器重启后原位重放继续执行；
3. **沙箱与安全强隔离**：恶意代码或崩溃被严格限制在 Worker 单一节点沙箱内，绝不污染全局控制平面；
4. **强可测试性**：外层状态机是纯确定性代码，可以编写完备的单元测试和集成测试，无需盲目向 LLM 祈祷。

## 4. 全方位工程权衡对比矩阵

| 对比维度 | 路线 A：Session 内 Tool 驱动 | 路线 B：Session 外 外部状态机驱动 |
|---|---|---|
| **控制主体** | 大模型自身（LLM As Orchestrator） | 确定性代码状态机（Engine As Controller） |
| **上下文管理** | 单一主 Session 持续累加，易 Context Rot | 严格物理隔离，节点间单向工件投影 |
| **长期稳定性** | 低。长程任务后期失控率高达 60%+ | 极高。状态确定性推进，失败可精准回放 |
| **持久化与恢复** | 依赖 LLM 会话保存，极难精确状态恢复 | 数据库/Checkpointer 逐节点落盘，支持 Time-travel |
| **开发门槛** | 极低。只需为 LLM 绑定几个 Tool 即可跑通 | 较高。需搭建分布式状态机、定义强类型 Schema |
| **人类在环 (HITL)** | 很难优雅挂起（模型 Session 一直占用/超时） | 原生支持。状态机挂起节点，等待外部 Webhook/Signal |
| **适用阶段** | 个人 CLI 工具、一次性探索脚本、单机实验 | **中大型企业系统、复杂代码库重构、高可信 SDLC** |

---

## 5. 结论与工程演进建议

一线工程团队与工业界的主流演进规律表明：
- **原型期（PoC）**：可以从路线 A 起步，验证任务是否能够被拆解为子任务；
- **商业化/生产落地（Production）**：**必须坚决重构成路线 B（Session 外状态机硬治理）**。
- 将控制权收归到确定性代码手中，是大模型技术从“玩具”跃升为“企业级基础设施”的必经之路。
