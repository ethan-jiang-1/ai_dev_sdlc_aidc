# 02. 两层自愈体系深度解构：Worker 局部 Loop vs 编排者动态 DAG 重排

> **判读依据**：`raw/evidence-20261001-field-exchange.md`（Jarvan 日成实录）、`raw/evidence-20260718-steinberger-graph-shift.md`。

---

## 1. Loop 与 Graph 的工程接合点：微观自愈与宏观编排

在工业界大论辩中，许多人常将 Loop Engineering（循环工程）与 Graph Engineering（图工程）对立起来。但正如一线实录所揭示：

> **“在执行过程中做有限重试和退避，Worker 修不了的让编排者改 DAG 再重试。”**

这两者不是竞争关系，而是**分层嵌套的两层自愈体系（Two-tier Self-Healing Architecture）**：
- **微观（Micro）**：每一个图节点（Node）内部，都是一个标准的 **Loop Engineering** 闭环；
- **宏观（Macro）**：由节点组成的拓扑链路，由 **Graph Engineering** 状态机负责全局调度与容错。

## 2. L1 层：Worker 节点内局部自愈（Loop Engineering 范畴）

```text
       [调度进入 Worker Node]
                 │
                 ▼
       ┌───────────────────┐
       │   执行代码变更    │ ◄─────────────────────────┐
       └─────────┬─────────┘                           │
                 │                                     │
                 ▼                                     │
       ┌───────────────────┐                           │
       │ 运行确定性门禁     │                           │
       │ (pytest / tsc)    │                           │
       └─────────┬─────────┘                           │
                 │                                     │
         ┌───────┴───────┐                             │
         │ 是否全部 Pass? │                             │
         └───┬───────┬───┘                             │
        Pass │       │ Fail                            │
             │       ▼                                 │ 重试
             │  ┌─────────────────────────┐            │
             │  │ 重试次数 <= N (Hard Cap) │ ─── Yes ────┘ (携带错误栈+退避剪枝)
             │  └────────────┬────────────┘
             │               │ No (耗尽预算)
             │               ▼
             │      [向外抛出结构化异常]
             ▼               │
      [节点成功完成]         ▼
                     [触发 L2 拓扑自愈]
```

### L1 自愈的核心机制：
1. **职责边界**：仅处理局部的、轻量级的实现问题（例如：语法拼写错误、单文件 import 遗漏、单测断言格式微调）；
2. **硬性重试上限（Hard Cap）**：严格限制重试次数（通常为 3 次，绝对不超过 5 次），防止陷入死循环消耗 Token；
3. **有限退避策略（Backoff & Pruning）**：
   - 第 1 次重试：喂入原始报错堆栈；
   - 第 2 次重试：精简上下文，只提取核心出错行及其 AST 切片；
   - 第 3 次重试：强制模型使用更保守的实现策略；
4. **机器判据闸门（Machine-checkable Gates）**：由真实的外部命令执行（如 `npm test`、`pytest`、`ruff check`）给出生死判决，绝不使用 LLM 自我反思进行主观评判。

## 3. 升级协议：从 L1 跃迁到 L2 的边界判定

什么情况下 Worker 必须停机并向上抛出异常？
- **耗尽 L1 预算**：3 次有限重试后单测依然红灯；
- **语义冲突与假设破裂**：Worker 在实现过程中发现需求规范（Spec）存在根本逻辑矛盾（例如：要求实现的函数依赖一个根本不存在的下游微服务）；
- **环境或权限不可达**：缺少依赖包但没有网络权限下载、缺少数据库表迁移权限。

此时，Worker 节点停止执行，不产生污染性代码，并将一份包含以下字段的**结构化诊断报告（Failure Envelope）**回写进黑板状态机：
```json
{
  "node_id": "worker_backend_auth_impl",
  "status": "FAILED",
  "error_category": "SPEC_ASSUMPTION_VIOLATION",
  "attempt_count": 3,
  "last_exit_code": 1,
  "diagnostic_summary": "Assumed User model has 'tenant_id', but schema.prisma does not support multi-tenancy.",
  "suggested_action": "REPLAN_SCHEMA_OR_MODIFY_SPEC"
}
```

## 4. L2 层：编排者的动态 DAG 重规划（Graph Engineering 范畴）

当 L1 失败升级后，图状态机暂停后续依赖该 Worker 的下游节点，激活中央编排者（Planner / Orchestrator）：

```text
                  [接收 Failure Envelope 异常]
                                │
                                ▼
                  ┌───────────────────────────┐
                  │ 编排者评估根因与影响面     │
                  └─────────────┬─────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        ▼                       ▼                       ▼
 策略 A: 插入排错子图      策略 B: 任务细粒度拆分   策略 C: 状态回滚与变更高阶Spec
 ┌────────────────┐     ┌────────────────┐    ┌──────────────────────────┐
 │ 动态在当前节点 │     │ 将大任务拆解为 │    │ 回退到上一版本 Checkpoint│
 │ 前插入补丁节点 │     │ 两个串行小任务 │    │ 重新生成整体系统设计     │
 └────────────────┘     └────────────────┘    └──────────────────────────┘
        │                       │                       │
        └───────────────────────┼───────────────────────┘
                                │
                                ▼
                  ┌───────────────────────────┐
                  │ 重新静态校验修改后的 DAG  │
                  └─────────────┬─────────────┘
                                │ Pass
                                ▼
                  [恢复调度，执行新的任务图]
```

### L2 动态改图的三大模式：
1. **模式一：插入前置依赖节点（Inject Prerequisite Node）**：
   - 场景：Worker 发现缺乏某个数据表或基础模块。
   - 动作：编排者在当前 Worker 前面动态插入一个 `db_migration_node`，待其执行成功后再重新唤醒 Worker。
2. **模式二：任务拆分扇出（Task Fission）**：
   - 场景：Worker 节点因任务粒度过大、改动文件过多而导致单测无法收敛。
   - 动作：编排者将该 Node 裂变为 3 个更小粒度的子节点，形成扇出并发执行拓扑。
3. **模式三：回滚检查点与重构 Spec（Checkpoint Rollback & Spec Revision）**：
   - 场景：底层架构假设被推翻。
   - 动作：借助持久化检查点（Checkpointer / Time-travel），将代码库与状态回滚到规划前的干净状态，修订 Spec 后重新生图。

## 5. 两层体系的对比总结

| 维度 | L1 局部自愈 (Loop) | L2 全局自愈 (Graph) |
|---|---|---|
| **执行实体** | 单个 Worker Agent | 中央编排者 (Orchestrator) / 状态机引擎 |
| **关注视野** | 局部函数、单文件语法、单模块单测 | 全局系统依赖图、跨模块契约、架构假设 |
| **自愈手段** | 有限重试、提示词退避、修剪上下文 | 动态改图 (Dynamic DAG)、节点插入、任务拆分、回滚 |
| **重试上限** | 严格限制（3~5 次硬上限） | 严格限制（通常最多 1~2 次重规划，超限转人工 HITL） |
| **对上下文影响** | 会随重试积累局部噪音，但任务结束即销毁 | 编排者拥有全新的结构化诊断摘要，不承担 Worker 内部杂音 |
