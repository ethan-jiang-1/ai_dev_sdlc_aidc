## 二、候选的第五定义源是否同指一件事：核心只在内环同指，外延不兼容

**核心同指**（Osmani / Runkle / CC 团队 / Ng）：**用一个系统替换"人逐轮写 prompt"**——agent 在循环里反复行动、自测、调整，直到一个写清的目标达成。

**外延不兼容**（一手证据）：

1. **Runkle 的第 4 环越界**：hill-climbing loop（"用运行轨迹改写 harness 本身"）——按 **Osmani 自己的分层**（loop engineering 是 "one floor above the harness"），改 harness 属于 **harness engineering 那一层**。LangChain 把它收进 "loop engineering"，Osmani 不收。
2. **验证语义不同**：Osmani / CC 团队＝**机器可核的停止条件**（测试/构建退出码/清单逐条 passes）；Runkle＝**rubric 评分**（grader 分 deterministic 与 agentic/LLM-as-judge——后者是评分不是闸门）。
3. **Ng 的三环是方法论层**（agentic coding / developer feedback / external feedback）：外环修正内环方向，人的价值是上下文优势。不含工程原语，也不参加停止条件的工程化讨论。

**Tessl 2026-09-14 提出一个候选五定义，和前四个明显错位**（[`evidence-i2`](../raw/evidence-2026-09-27-i2-teams-evals-outcome.md) Source E2，侦察回源，主 Agent 未复验；厂商自家框架，不是行业标准）。如果原文复核成立，它先把 context engineering 定为单次运行的仓内引导物，再把 loop engineering 写成更宽的三层：内环是单次运行，中环跨多次运行分析行为并提议改进，外环问已交付功能有没有推动它要的业务指标。

和前四个的冲突是四条，不是「又多了一层」：

| 对照 | 前四个把边界画在哪 | Tessl 画在哪 |
|---|---|---|
| Osmani | 四级按触发高度排：单次 agentic loop → `/goal` → `/loop`/`schedule` → proactive。改 harness 在 loop 的下一层 | 中环就是跨运行分析并提议改进，收在 loop engineering 里面。内环（单次运行）也收在 loop 里，而 Osmani 把单次运行的环境放在 harness 那一层 |
| Runkle | 四环里的 hill-climbing 用 trace 改写 harness，这一环收在 loop engineering 里 | 中环和这一环是同一类对象，所以 Tessl 站在 Runkle 一边、不站在 Osmani 一边。外环的业务指标是 Runkle 四环里没有的一层 |
| CC 团队 | loop ＝ agents repeating cycles until a stop condition is met；四类按触发分（turn / goal / time / proactive） | 三层按改进的时间尺度分，不是按触发分。2026-09-14 的定义句没有写停止条件 |
| Ng | 外环是 external feedback，用来修正内环方向 | 外环是一个具体问题：交付出去的功能有没有推动目标业务指标。这两句不要收成同一个外环 |

次日（2026-09-15，同一档案）还有一句产品定义：loop 是已经部署、会自动跑的 skill。前四个都没有把 loop 定义成一件部署物。这句不并进 09-14 的三层定义。原文还写 improves over time，没有数据。

**判定**：截至 2026-09，**"loop engineering" 的核心共识只覆盖「系统替人把一轮跑完」。** Tessl 的内环（若原文复核成立）可以放进这句话；它的中环和外环不行。层数（四级 / 四环 / 三环 / 三层）、验证语义（机器闸门 vs rubric）和最外层（停在 proactive、停在改 harness、停在外部反馈，还是停在业务指标）互不兼容。引用时必须指明用的是谁的外延。实践层因此不沿用这个词（§四）。

## 三、操作模型（本主题采用的分层共识版）

**最小 loop 模型**：**触发 · 反复行动 · 反馈/验证 · 可记忆状态 · 停止或继续**。这是跨材料的分析框架，不是任何单一作者的原文定义；Osmani 的五件套（automations、worktrees、skills、plugins/connectors、sub-agents）加 memory 是一份更具体的设计 checklist，Claude Code 官方四类则按 trigger、stop、primitive、task fit 描述运行模式，不能互相当作同义 taxonomy。

两个硬判据（什么不算可靠的 loop）：

1. **停止/继续必须参考上一轮结果或明确的完成条件**——不看结果的“循环”更接近重试；
2. **单次运行必须受控**——单次不受控时，循环只会更快复制错误（与 Ralph 的 greenfield 限定、Anthropic“先过基线再干活”同向）。

**外层调度是扩展问题，不是最小定义的必要条件**：`/goal` 可以独立驱动一个 bounded task；`/loop`、`/schedule`、事件触发、持久化队列则解决“何时再跑、下一项做什么、如何跨任务/会话接续”。它们对长程自主工作很关键，但不能把缺少外层调度的单任务 loop 判为“不算 loop engineering”。两类调度形态及其证据边界见 [`03-构件.md`](03-构件.md)。

这比用户的“体感像 loop”多出的，通常是**明确的完成/继续判据与外部状态**；是否需要跨 feature 的调度，要按任务规模和风险单独判定。

## 四、对命名的结论（为什么实践层不沿用这个词）

1. **词源是热度**（§一），思考含量来自事后工程化——把 KOL 词当实践命名，会把热度误当收敛；
2. **外延未收敛**（§二）——四个已确认定义源加一个候选定义互不兼容，沿用即站队；
3. **实践层按仓库自己的五层框架命名**：Prompt → Context → Harness → **Loop** → Graph 的第 4 层，治理主题名＝**`loop_governance`**，与 `harness_governance` 同构成对（环境轴 / 控制轴）。KOL 词保留在研究层作运动名（[`../raw/kol-roster.md`](../raw/kol-roster.md)）。
