# 结果可证成性：R0–R3 的另一条轴（教学接口，不是 R4）

> 本页只回答：**已交出去的循环控制权，够不够支持所声称的结果？** R0–R3 的交接面及证据强度以 [00-map](00-map.md) 为准。goal/eval 怎样构造、效果数据怎样判读以 [agent_goal_eval](../../agent_goal_eval/README.md) 及其 [三篇判读](../../agent_goal_eval/digested/README.md) 为准；机器闸门、硬上限、裁判分离的机制见 [stop_conditions](../stop_conditions/README.md)。这里做交接处的联调，不另立该两主题的第二份权威。

## 一、为什么不是 R4

R1 交工具动作权，R2 交本轮后是否继续，R3 交下次何时唤醒；这些是**控制平面**。终态能否观察、证据是否覆盖需求、裁判能否被执行者改写、结果是否真的被用户接受，则是**结果可证成性**。两者不随同一刻度单调上升：一个会话内 R2 可以用外置测试和人终审交出很可靠的有限产物；一个跨会话 R3 即使按时运行，也可能从未接入任何业务结果的观察源。多主体和自改分支只增加验证难度，不能代替验证。

这里的“可靠”指**对具体任务、在明确边界内有足够证据支持一次声明**，不是保证所有工作都能客观量化，更不是某产品提供的通用可靠度等级。`/goal` 的 `Met`、测试退出码 0、费用触顶、用户接受、上线后的业务改善，分别是不同事件；任何两个都不能直接画等号（[R2 的四种信号](rung-02-goal-driven.md)、[机器闸门与熔断](../digested/03-构件.md)）。

## 二、交接前检查的五个接口

| 接口 | 必须先问的技术问题 | 看什么记录；缺失时怎样退回 | 来源/归属 |
|---|---|---|---|
| **目标契约** | 目标是能在环境中观察的**产物终态**，还是要等外部用户行为的**业务结果**？不得更改什么？ | 目标、测量方法、不变式、授权范围、退出/升级条件。外部结果尚不可见时，只委派可观察的产物，不宣告业务已达成。 | goal 的不同写法与产物/结果界限见 [goal 构造](../../agent_goal_eval/digested/01-goal-构造.md)；Claude `/goal` 三要素见 [R2 §⑦](rung-02-goal-driven.md)。 |
| **环境证据** | `npm test` 成功验证的是哪部分？是否测了正确版本/页面？执行者能否删测例、改 `passes`、伪造工具日志？ | 带运行 ID、目标版本与原始输出的测试/扫描/外部状态；隔离不可改的检查输入。测不到的质量维度记为**待验收**，不写成已完成。 | [机器闸门](../stop_conditions/01_machine_gates/README.md)、[裁判保护](../digested/03-构件.md)；[官方 quickstart 反例](rung-02-goal-driven.md)提醒“展示进度”不等于驱动停机。 |
| **裁决协议** | 谁能给 `Met`？它只看 transcript 还是看真实环境？判据谁持有，错误/缺字段/分歧时会否默认放行？ | 保留 grader 的输入、版本、输出与失败出口；对可能错判的部分另做独立检查或人抽验。**分离执行者与裁判只减利益冲突，不保证裁判正确**。 | [验收分离](../stop_conditions/03_verdict_split/README.md)与其[失效清单](../stop_conditions/03_verdict_split/insights.md)；终态 oracle 的适用边界也在后者。 |
| **资源与进度** | 谁覆盖外层续跑、重试、子代理及定时重新起跑的总预算？连续无进展后如何收口？ | 每轮反馈、费用/时间/轮数、重试计数、暂停理由及局部成果。`budget_reached`/超时＝**停止或交接，尚非成功**；硬上限要落在真实反馈路径上。 | [硬上限](../stop_conditions/02_hard_caps/README.md)、[R2 的预算暂停实例](rung-02-goal-driven.md)。 |
| **跨次责任** | 上次的目标、授权、观察结果仍新鲜吗？取消是否送达 scheduler 和运行中的 worker？人回来后能否复原为什么判定？ | 持久任务 ID、版本/事件 ID、幂等键（按任务设计）、执行日志、裁决证据、审批人和接手渠道；核对未派新任务且已有 worker 退出。**按时唤醒不等于可靠完成**。 | [R3 调度与取消案例](rung-03-time-event-driven.md)、[控制问题矩阵](../digested/07-控制问题矩阵.md)；幂等键是本页的工程检查，不声称产品默认提供。 |

这不是要求所有任务一律使用独立 LLM 裁判或硬性二元指标。环境确定性断言适合能观察终态的部分；品味、法律/临床判断等可以用人、专家 rubric 或分块验收；尚未有能信任的检查句子时，先切小核对面、让人标失败或把外部结果留给人。[设计不出来的三类情形](../../agent_goal_eval/digested/03-难设计.md)并不等同于“停止研究”或“假装能自动验收”。

## 三、同为 R3，能宣布什么却不同

**案例 A：夜间巡检（示意设计，非已运行产品日志）。** 任务“每晚检查仓库依赖，直到没有高危漏洞”若只每晚跑扫描并拿到退出码 0，仍需问扫描范围、漏洞库更新时间、锁文件/容器镜像版本、扫描命令的错误语义。预先约定检查目标与不可改范围；由执行者以外的 CI/扫描环境保存结果和目标 commit。超时、扫描器不可用、无扫描覆盖、证据过期分别写成**暂停/未知并通知人**，不是 `Met`。若要自动合并修复，另需回归测试、权限边界与人批准不可逆动作；若要声称“线上风险已消失”，还得观测实际部署版本与生产结果。该扫描和判定组合是**教学设计**，非某厂商的默认协议。

**案例 B：每五分钟看部署。** [R3 的 `/loop 5m check the deploy` 走读](rung-03-time-event-driven.md)只证明“定时再次询问”可以被委派。CI 还在跑、未收到告警，都不是部署成功；CI 绿只支持约定检查在对应版本通过。若业务指标需上线后几小时才出现，完成声明也只能停在“CI 条件满足，业务结果待观察”。取消界面标“已关闭”还要核 worker 真正停，事故案例在 [R3 §⑩](rung-03-time-event-driven.md)。

**对照：有界 R2 可比持久 R3 更可证成。** 一个范围固定的代码修复，可以让外置测试检查原始缺陷与回归、人审差异；即便永不定时唤醒，产物也可能已有充分证据。反过来，“每天自动把体验改好”即使具备 R3，也缺少能独立判决的目标和上线效果观察；允许它生成候选与可复现报告，不授予无人值守发布和“已做好”的声明。[goal 的不同写法](../../agent_goal_eval/digested/01-goal-构造.md)与[离线/上线指标分离实例](../../agent_goal_eval/digested/02-eval-调优.md)说明了为什么不能把代理数、触发频率或离线分数当成果质量。

**案例 C：跨 feature 的错位验收（示意设计）。** 夜间任务 A 的 CI 绿了，但共享组件使任务 B 的回归失败；白天 owner 又改过 priority，取消 A 的 scheduler 后旧 worker 仍在写。单一任务的测试退出码、日志里的一句 `Met`、调度面板的“已关闭”，都不能证明**当前目标版本已通过跨 feature 验收且已停机**。进入下一次自动运行前，需能追溯授权与 priority 变更、业务阻塞原因、A/B 各自的接受人和 worker 的退出证据；这四类在现有 [控制问题矩阵](../digested/07-控制问题矩阵.md) 中仍是待补的 feature 级空列，不说成已有系统能力。

## 四、一次运行要分开记的结论

| 状态 | 最多可声称什么 | 不能偷换成什么 |
|---|---|---|
| `Met`（若某产品的 grader 可见条件成立） | 该 grader 按**其可见证据**判约定条件达成 | 无遗漏需求、人已验收、生产业务已改善 |
| 检查失败 / 证据不足 | 该次验证未支持达成，进入修复或升级 | 任务“本质不可能”；也不可静默贴 `Met` |
| `Impossible`（特定产品判定） | 该产品判断约定条件不能满足并终止 | 所有尚不可见的结果都已证明不可能 |
| 预算、时间、无进展、人工取消 | 运行暂停/终止并保留可复核成果 | 达成目标或失败质量判定 |
| 人/专家接受；业务指标后验观测 | 指明版本、样本、时间窗内的接受或结果 | 自动推广到所有用户/任务或给 loop 设计作因果效果证明 |

**工程收口**：升级 R2/R3 时，写下「可检查的产物」「不可检查或延迟可见的结果」「谁判、谁能改判据」「不确定/预算耗尽时交给谁」。四件缺一时可保持 R0/R1 或做只读/有界 R2，甚至保持有界 R3 只做观测；**不把持续自主等同于持续可信**。以上为跨来源的**教学准入检查**，不是已验证的普适产品认证标准。
