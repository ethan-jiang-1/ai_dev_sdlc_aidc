# 仓库 Agent-Friendly 评估体系 v1.7（定义层）

> 状态：v1.7（2026-09-21）。取代 [`../90-archive/framework-v0.md`](../90-archive/framework-v0.md) 成为体系定义的当前权威（v0 保留作历史底稿）。
> 结构推敲自 raw 七篇（观测日期 2026-06，见 [`../90-archive/raw/README.md`](../90-archive/raw/README.md)）；本文件只定义体系本身，不绑定任何具体仓库。

## 0. v0 → v1.7 演进了什么

v0 保留五维框架与四条设计约束，但在评估报告推敲（2026-09-21）中发现两处逻辑硬伤与一处结构缺失，此后各版同日推敲：

1. **聚合结构**：v0/raw 的"线性加权 + 维度五一票否决"是两种不相容的聚合函数混用。v1 把安全护栏维度改为**独立门禁层**，其余维度才做加权（§4）。
2. **可复现性**：v0 声称"两个审计者应得出一致结果"，但部分判据是主观抽查且无抽样协议。v1 引入**证据等级（evidence tier）**与判据分级，不同 tier 有不同的可复现性承诺与审计成本（§3.2）。
3. **泛化结构**：v0 是单层五维，把 harness 维度丢掉了。"对 agent 友好"不是仓库的单一属性——同一仓库对不同 harness 得分不同。v1 建立**三层对象模型**（§1）。
4. **维度正交化**（v1.1）：五维扩为八维，2026-06 后话题主干（SDD 漂移、失败可恢复、资产新陈代谢等）按正交纪律独立立维，边界声明成文（§3.4）；正交纪律升为目录级纪律（目录 README）。
5. **形态档案定调**（v1.2）：被测实例按正确性模型分 A/B 两型，B 增运行时消费路径（§3.5）；分线评估面定义拆至 line-a / line-b 两文件。
6. **充分性审查 + 系统化**（v1.3）：八维扩为九维（新增⑨版本控制与协作面，A/B 两线分立）；本文件升格为评估系统的 spec 层，器械/运行分目录，操作规程移交目录 `AGENTS.md`。
7. **度量语义定标**（v1.4）：三档数值映射、A–D 等级刻度、⑤ 门禁 ⚠️ 封顶 B、可复现性承诺改写为 agent 执行语境（[ADR 度量语义](adr/2026-09-21-metric-semantics.md) D1–D4）。
8. **无状态评估器**（v1.5–v1.6）：run bundle 归属被测仓库、`30-runs/` 删除、系统目录收敛三层（[ADR 无状态评估器](adr/2026-09-21-stateless-auditor-run-bundle.md)）。
9. **一致性加固**（v1.7）：N/A / 条件判据 / 观察项进度量层（ADR 度量语义 D5）、B 线双路径评级域（D6）、tier-2 演练映射补⑥并给写入豁免（无状态 ADR v3）；清理 v1.3–v1.6 编辑残留（§4.1 重复段、悬空指针、口径不一）。

## 1. 三层对象模型

体系评估的对象不是"仓库"这一个东西，而是三层的组合：

| 层 | 是什么 | 变化频率 | 内容归属 |
|---|---|---|---|
| **L-core 核心判据** | 仓库无关、harness 无关的原则级判据（由 context rot、注意力预算、自主执行体等第一性原理支撑） | 慢（原理级稳定） | 本体系 checklist-A/B（`../20-instruments/`，待建）主体 |
| **L-profile harness 档案** | 各 harness 消化仓库指引的机制事实：指令载体、注入时机、预算上限、静默失败模式 | 快（厂商实现，需复验） | 本体系 `../20-instruments/harness-profiles.md`（raw 03 篇为其素材源） |
| **L-instance 被测实例** | 具体仓库 + 审计时实际使用的 harness 集合 | 每次审计 | run bundle，**归属被测仓库**（`<目标>/agent-friendly-runs/`，[ADR 无状态评估器](adr/2026-09-21-stateless-auditor-run-bundle.md)）；自举审计同规则，落本仓库根 `agent-friendly-runs/`——L-instance 数据不在本系统 |

**评估 = L-core 判据 × L-instance 仓库现状，再按 L-profile 修正。** 被测实例同时带**形态档案**（A 确定性应用 / B 智能体，见 [`archetypes.md`](archetypes.md)）：形态决定评估面组合与条件判据，不改九维定义。推论：

- 同一仓库对 harness 集合 {Claude Code} 与 {Cursor} 可得出不同总分——这是体系的特性，不是缺陷。
- 一条判据若只在特定 harness 下才成立（如"`.cursor/rules/` 必须用 `.mdc`"），**不进 L-core**，归入对应 profile 的修正项。
- profile 层条目标注"实现级"（§3.3），厂商变更时按复验机制处理。

## 2. 体系回答的问题与设计约束

给定任意代码仓库与一组实际使用的 harness，系统性评估其 agent 友好度，产出：可复现的评分 + 按优先级排序的整改清单。

设计约束（继承 v0，措辞按 v1 收紧）：

1. **仓库无关**：L-core 判据不含特定仓库锚点；具体仓库只作被测实例。
2. **一手源可溯**：每条判据标注依据类型：`一手`（厂商规范/官方文档/研究报告）或 `经验`（无一手依据的调研者判断）。经验判据不冒充规范。
3. **可复现且诚实分级**：可复现性按 tier 分档承诺（§3.2、[ADR 度量语义](adr/2026-09-21-metric-semantics.md) D4）——tier-0 任意执行者复跑一致；tier-1 同 harness 同版本复跑一致；tier-2 同模型同协议方向性一致，跨模型承认评审差异。
4. **门禁与加权分离**（§4）。
5. **原理级 / 实现级分离**（§3.3），实现级判据带复验机制。

## 3. 判据层：schema 与组织

### 3.1 判据 schema（每条判据的固定字段）

```
id:        <两位维度号>-<序号>（如 01-03；profile 项为 P<harness名>-<序号>）
dimension: 九维之一（见 §3.4）
question:  这条判据检查什么（一句话）
probe:     怎么查（只读命令 / 注入验证 / 演练步骤）
pass:      合格标准（可判定的行为描述，不是某仓库的做法）
tier:      evidence tier（见 §3.2）
applicable: 无条件 | 条件（<何时适用，一句话>；条件不满足记 N/A，见 §4.1）
basis:     一手（+出处链接）| 经验
harness:   无 | 某 profile（有依赖者不进 L-core）
sampling:  抽样协议（tier-2 判据必填：抽几处、从哪里抽、几处不合格算 ⚠️/❌）
```

### 3.2 证据等级（evidence tier）

| tier | 名称 | 判定方式 | 可复现性 | 审计成本 |
|---|---|---|---|---|
| 0 | 自动扫描 | 纯只读命令/脚本可判定（文件存在、行数、lockfile 在库） | 高（可进 CI 常驻监测） | 极低 |
| 1 | 注入验证 | 在目标 harness 内用自检命令确认机制真实生效（如 Claude Code `/context`、Codex "Summarize the current instructions."） | 高（给定同版本 harness） | 低 |
| 2 | 演练/评审 | 端到端闭环演练或专家抽样评审（失败信息可行动、措辞具体、命名质量） | 中（协议化抽样后达到可用一致） | 高 |

规则：

- 审计按 tier 0 → 1 → 2 顺序采证，便宜的证据先采；tier-2 只对 tier-0/1 无法判定的问题启用。
- 每条判据的 tier 是体系的固定属性，不是审计时临时决定。
- 报告须注明各 tier 的判定所用的 harness 版本。
- tier-0/1 的证据必须是命令/脚本的**原始输出引用**，不得转述为"存在/正常"（可复现性承诺的证据基础，见 [ADR 度量语义](adr/2026-09-21-metric-semantics.md) D4）。

### 3.3 原理级 / 实现级

- **原理级判据**：由第一性原理（注意力预算、无状态读者、自主执行体）或多方收敛的规范支撑（如"指令少而具体""确定性验证命令存在"），预期长期稳定。
- **实现级判据**：依赖某厂商当前实现参数（如 200 行建议、32KiB 截断、`.mdc` 扩展名要求）。必须标注观测日期；厂商变更时该判据降级为 ⚠️ 并触发复验，而不是默认继续成立。**B 线扩展**：被测产品所依赖的模型升级同为复验触发器（[`line-b-agentic-repo.md`](line-b-agentic-repo.md) §3）。

### 3.4 维度框架（v1.3：九维，正交化）

五维继承 v0；v1.1 按正交纪律扩为八维，v1.3 经充分性审查（[`adr/2026-09-21-dimension-sufficiency-review.md`](adr/2026-09-21-dimension-sufficiency-review.md)）扩为**九维**。**⑤ 为门禁层**，其余八维参与加权。每维附与相邻维度的分界声明。**各维展开定义（核心问题/边界/判据族/依据/开放问题）一维一文件，见 [`dimensions/`](dimensions/README.md)；本表只留总表，不复制正文。**

| 维 | 名称 | 核心问题 | 2026-06+ 话题来源 | 与相邻维度的分界 |
|---|---|---|---|---|
| ① | 上下文供给与预算 | Agent 能否在合适时机、以最低 token 成本找到正确指引？ | T2a 注意力稀释（context rot 原义）、T3 渐进披露（[Knowledge Activation](https://arxiv.org/html/2603.14805v2)、deferred tools/skills）、T8 上下文自身治理规则 | 管的是"**这一次任务**里指引找不找得到、省不省"；指引内容本身新不新鲜归⑦，指引与实现是否一致归⑧ |
| ② | 可验证性与证明 | Agent 能否自主确认"我改对了"，并产出可 review 的证据？ | T5 proof-is-bottleneck（[AAIF 2026-09](https://aaif.io/blog/code-is-cheap-proof-is-the-bottleneck)：generation-verification asymmetry、comprehension debt）、handoff 证据义务 | 管的是"**改后**判定对错+交付证据"；跑不起来归③，卡住了出不来归⑥ |
| ③ | 可执行环境（冷启动） | Agent 能否从零把环境跑起来，失败是否可行动？ | raw 01 维度三 | 只管**从零到可跑**的路径；运行中卡死的恢复归⑥ |
| ④ | 可修改性 / 局部性 | Agent 改一处代码时，需要理解的涟漪范围有多大？ | raw 01 维度四（每条须带 AX 理由：注意力预算/无状态读者，纯人类工程质量不进） | 管的是**静态结构**的涟漪；随时间才暴露的不一致归⑧ |
| ⑤ | 安全护栏（门禁层） | 软指令与硬约束是否各司其职、危险面是否结构性可控？ | raw 01 维度五 | 不参与加权（§4.2） |
| ⑥ | 失败可恢复性 | Agent 运行中卡住/失败时，有没有结构性的出口？ | T6（Amazon 6000+ trajectory 审计：死循环+超时约占 1/3，harness 决定恢复还是越陷越深，[AAIF](https://aaif.io/blog/code-is-cheap-proof-is-the-bottleneck)）：超时/重试预算、逃生舱命令、干净重来路径、失败上报通道 | ②管"判定对错"，⑥管"卡住脱身"；③管冷启动失败信息可行动，⑥管冷启动之后的循环与超时面 |
| ⑦ | 指令资产新陈代谢 | Agent 指引资产（指令文件/skills/agent 文档）是否保鲜、有打扫机制？ | T2b 指令资产腐化（[Stale AI Configuration Artifacts](https://raw.githubusercontent.com/agentpatterns-ai/website/refs/heads/main/patterns/anti-patterns/stale-ai-configuration-artifacts.md)）、T4 定期打扫（[Anthropic session/compaction 2026](https://claude.com/blog/using-claude-code-session-management-and-1m-context)）：staleness 可检测、修剪政策成文、文档更新政策、清扫节奏 | 管的是**指引资产自身**随时间变质；指引描述的行为与实现不一致归⑧（⑦管"文件旧了没人删"，⑧管"文件还新但说的和代码做的已经是两回事"） |
| ⑧ | 漂移治理（SDD） | 规格/契约/实现/文档声明之间的一致性，是否被机器守护？ | T1（SDD 工具链 drift detection 成一等公民：[spec-driven-development-skill](https://github.com/mariano-aguero/spec-driven-development-skill)；SDD 适用边界：[InfoQ](https://www.infoq.com/articles/when-spec-driven-development-pays-off/)）：规格-实现一致性测试、契约 lockstep、漂移检测门禁、spec 为单一事实源 | 管的是**仓库工件之间**的一致性；指引资产自身的新鲜度归⑦ |
| ⑨ | 版本控制与协作面 | Agent 产出的改动能否顺畅进入版本主干——提交、隔离、合并、回退、进入 review——且不与人类或其他 agent 互相踩踏？ | 并行 agent（worktree 多会话）、code review agent、AI 产出披露与评审责任常态化（2026-06 后实践共识，多为经验判据） | 管的是改动的**协作旅程**；推送安全红线归⑤、卡住脱身剧本归⑥、PR 内证据义务归②、lockfile 漂移机器检查归⑧。详见 [`dimensions/09-vcs-collaboration.md`](dimensions/09-vcs-collaboration.md) |

正交性自检（新增话题时执行）：一个话题若能被上表某维的核心问题完整覆盖→并入该维；若需引用另一维的结论才能打分→说明拆分不对，重新划界；若两维打分总是同起同落→不是正交坏了，就是效标重叠，校准时检验。

### 3.5 形态档案（v1.2）

被测实例按**产出的应用种类**分型：形态 A（确定性应用）/ 形态 B（智能体）。分型依据是**正确性模型**（二元断言 vs 统计评估），不是"代码由谁写"；漂移是两形态共同的敌人，不是分型依据。形态决定：评估面组合（B 多一条运行时消费路径）、条件判据（⑧ 等 A/B 子族）、成熟度标注。**B 线报告按消费路径分两个评级域（开发时 / 运行时），分别呈现、不合并**（[ADR 度量语义](adr/2026-09-21-metric-semantics.md) D6）。**权威定义见 [`archetypes.md`](archetypes.md)，本节只留指针。**

## 4. 度量层：聚合结构（v1 定型，权重待校准）

### 4.1 单条判据

✅ / ⚠️ / ❌ 三档，数值映射 **✅=1.0、⚠️=0.5、❌=0.25**（❌ 不记 0：加权层管梯度排序喂校准，绝对红线归⑤门禁；映射为经验设定，随 §4.4 校准可修订——裁决理由见 [ADR 度量语义](adr/2026-09-21-metric-semantics.md) D1）。⚠️ 与 ❌ 均须注明证据（引 probe 的实际观察）。禁止无证据打分。

另有两种**不计分状态**（裁决见 [ADR 度量语义](adr/2026-09-21-metric-semantics.md) D5）：

- **N/A（不适用）**：条件判据（schema `applicable` 字段）的条件不满足时记 N/A——不进均分分母、不进短板 min、无证据义务，但报告须列 N/A 条目与理由（无理由的 N/A 视同无证据打分）。规模分档（②⑥⑨ 的小仓库场景，落条时以 `applicable` 条件表达）同此语义，无"加分项"机制。
- **观察项**：B 线探索级判据单列呈现，不进三档、不进任何聚合；升"共识"级后才入算。

### 4.2 聚合：门禁层 + 加权层

```
总评 = 门禁判定 × 加权层画像
门禁判定 = 维度⑤（安全护栏）任一 ❌ → 总评 D 级（不合格），
           无论加权分多高；所有门禁 ❌ 进整改清单首部。
         = 维度⑤ 有 ⚠️ 而无 ❌ → 不降级，但总评封顶 B 级
           （安全有警告不称示范），且必须进整改清单次段。
加权分   = 维度①②③④⑥⑦⑧⑨ 各自的条目得分聚合（聚合函数见 4.3），
           按维度权重加权求和。
```

**等级刻度（校准前即可用，不依赖权重）**：

| 级 | 判定 |
|---|---|
| A 示范 | 门禁 ✅ 且所有加权维 ≥ 0.9 |
| B 健全 | 门禁 ✅ 且所有加权维 ≥ 0.7 |
| C 欠账 | 门禁 ✅ 但存在 < 0.7 的加权维 |
| D 不合格 | 门禁 ❌（⑤ 任一 ❌） |

刻度取**最弱维**而非均值——与 §4.3 短板制同哲学（裁决理由见 [ADR 度量语义](adr/2026-09-21-metric-semantics.md) D2/D3）。门禁层与加权层**分别报告、不混算**。**整维全 N/A 的维不参与刻度与加权，报告标注"不适用"及理由**（同 ADR D5）。

### 4.3 维度内聚合函数（v1 新定，待试测检验）

维度内不用等权平均（一条 ❌ 会被九条 ✅ 稀释）。采用**短板制**：维度分 = min(条目均分, 最低条目分 × 2)。理由：agent 友好度是约束满足问题——验证闭环缺失（②全绿但无测试命令）时，其余维度的分数不构成补偿。例（映射见 §4.1）：九条判据一条 ❌ → min(0.917, 0.5) = 0.5（腰斩而非清零）；一条 ⚠️ → min(0.944, 1.0) = 0.944。此函数与映射均为经验设计，标注为待试测校准项。**N/A 条目从均分分母与最低值中排除**（§4.1、ADR 度量语义 D5）。

### 4.4 权重校准协议

- v1 **不给权重数值**。v0/raw 的"维度①②×1.5"是无论证的经验值，不继承。
- 校准方法：**效标回归**，不止看区分度。流程：
  1. 选 2–3 个风格迥异的开源仓库试测（bundle 落各自目标仓库；其 manifest 即分布式登记，校准时临时聚合，工作清单走仓库根 `.tmp-` 刮擦区，不入系统）；
  2. 对每仓库采集外部效标：真实 agent 会话的任务完成率、返工轮数、token 消耗、绕过/放弃点（方法论承 raw 04 §8 Anthropic eval-driven 方法）；
  3. 检验维度分与效标的相关性，据此定权重；无相关性的判据修订或移除。
- 效标采集前不定权重；报告可以先行——**A–D 评级照给**（§4.2 刻度不依赖权重），加权数值分与总分列暂缺。

## 5. 操作层：审计流程（三步采证 + 一步产出）

raw 90 篇（[审计清单](../90-archive/raw/90-audit-checklist.md)）的四步中"打分与整改排序"是报告环节不是采证环节，v1 收敛为三步采证 + 一步产出（执行评估的 agent 按**七步仪式**操作——分型、建 run 目录、写 manifest 等前置与产出环节——见目录 [`../AGENTS.md`](../AGENTS.md)；本节只定采证结构，两者不冲突）：

1. **Tier-0 静态扫描**：指令文件定位与体量、命令文档化、lockfile/模板分离等全部机器可判条目。可脚本化——脚本属器械层 `../20-instruments/scan/`（不随 run 交付），bundle 的 manifest 记录所用脚本版本。
2. **Tier-1 注入验证**：在实际使用的每个 harness（L-profile 选定）内确认指令真实加载、无静默失败、无超预算截断。
3. **Tier-2 演练与评审**：一次真实小改动闭环演练（**在一次性 worktree/克隆内进行、结束即删**——对被测目标的写入豁免仅此一处，见 [ADR 无状态评估器](adr/2026-09-21-stateless-auditor-run-bundle.md) v3；卡点及其脱身路径映射到②③⑥⑨条目——⑥的"出口真实可达"判据正是经演练的卡点窗口采证）+ 协议化抽样评审（①④的主观条目）。
4. **产出**：评分卡（门禁判定 + 分维度短板分 + 加权分[权重定型后]）+ 整改清单（排序：⑤ 门禁 ❌ 置首 → 其余 ❌ 按维度短板分升序，短板越深越靠前 → ⚠️ 随其维），每条附判据 id 与依据。
