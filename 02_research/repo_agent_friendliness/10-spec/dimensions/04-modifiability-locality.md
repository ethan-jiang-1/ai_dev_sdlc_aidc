# 维度 04 · 可修改性 / 局部性

> 角色：加权维。形态适用：A+B。判据归族待 checklist-A/B 逐条落。

## 核心问题

Agent 改一处代码时，需要理解的涟漪范围有多大？

## 为什么独立成维

管**静态结构**决定的认知负荷。经典软件工程原则（深模块薄接口等）在这里被重新论证：对无状态、注意力受限的非确定性读者，局部性直接决定 token 成本与错误率（[builder.io AX 原则 6](https://www.builder.io/blog/agent-experience) 引 Ousterhout）。

## 边界声明（本维最严，防"通用工程质量"混入）

- 归此维的**准入条件**：判据必须带 AX 理由——对无状态读者或注意力预算**额外**重要。纯人类工程质量问题（代码重复率、抽象层次美感、DRY）**不进本体系**。
- 归此维：深模块薄接口、模块大小量化规则、公共 API 冻结策略、跨组件契约显式化（静态面）、生成物隔离、命名空间消歧、高频操作聚合、文档与代码同源政策、危险区前置成文、修改涟漪可枚举。
- 归他维：契约**随时间**被违反的守护归 08（本维管"契约有没有显式存在"，08 管"一致性有没有被机器守护"）；指引文件自身的更新政策归 07。

## 判据族（草案）

1. **模块边界**：深模块薄接口；模块大小有量化规则；无散装全局单例。
2. **API 治理**：public/internal 分界成文；公共 API 冻结策略。
3. **契约显式**：跨组件契约文件化；生成物隔离且有生成器。
4. **命名消歧**：前缀命名空间一致；工具面数量可一屏枚举；高频复合操作有单入口。
5. **文档同源**：文档与代码同一变更集同步的政策成文；危险区（GC/并发/安全边界）前置成文。
6. **涟漪可枚举**：受影响面可从 contracts/目录地图推出。
