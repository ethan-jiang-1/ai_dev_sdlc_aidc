# 维度充分性审查 v1（八维够不够）

> 状态：v1（2026-09-21）。用户定调的三个体系问题之一：**维度到底 8 个够不够**。
> 方法：不是默认继承 v1.1 的八维，而是按任务生命周期覆盖 + 正交纪律（见目录 README）重新过一遍；候选缺口逐一走"立维 / 归入现有维 / 不立"三选一，处置理由成文。

## 1. 审查方法

两条独立的检验，都过才判"够"：

1. **生命周期覆盖**：agent 在一个仓库上完成一次任务的全链条——发现指引 → 环境跑通 → 理解并修改 → 验证 → 失败脱身 → 改动进入主干；再叠加时间轴（资产保鲜、工件一致）与红线（安全）。每一环必须恰有一维认领。
2. **正交性自检**（framework §3.4 末尾）：每维能独立回答一个核心问题；打分不需引用他维结论；两两无同起同落的效标重叠。

## 2. 生命周期覆盖核对（现有八维）

| 生命周期环节 | 认领维 | 判定 |
|---|---|---|
| 指引在场、低成本到场 | ① 上下文供给与预算 | ✅ |
| 从零到可跑 | ③ 冷启动 | ✅ |
| 静态结构的认知涟漪 | ④ 可修改性/局部性 | ✅ |
| 改后判定对错 + 证据产出 | ② 可验证性与证明 | ✅ |
| 运行中卡住的出口 | ⑥ 失败可恢复性 | ✅ |
| 红线与强制 | ⑤ 安全护栏（门禁） | ✅ |
| 指引资产随时间保鲜 | ⑦ 新陈代谢 | ✅ |
| 工件间一致性被机器守护 | ⑧ 漂移治理 | ✅ |
| **改动进入主干**（提交/合并/回退/并行隔离） | **无维认领** | ❌ 见 §3 |

前三段（①③④）、验证段（②）、失败段（⑥）、时间轴（⑦⑧）、红线（⑤）均有着落且边界成文。唯一无主环节：**版本控制与协作面**——agent 产出的改动如何提交、如何与其他 agent/人类并行不互踩、如何干净回退、如何进入 review 流。这是 2026-06 后实践变化最大的一段（并行 agent、code review agent、worktree 隔离成为常态），而现有八维只在⑤（推送安全红线）和⑥（合并冲突逃生剧本）各捡走一两角。

## 3. 候选缺口逐一审

### G1 版本控制与协作面 → **立维⑨**（本次唯一立维结论）

- **候选核心问题**：Agent（或多个 agent 并行）产出的改动，能否顺畅进入版本主干——提交、隔离、合并、回退、进入 review——且不与人类或其他 agent 互相踩踏？
- **独立性检验**：可不看任何其他维的结论独立打分（只看 VCS 面、提交历史、协作文档）。✅
- **为什么不是归入现有维**：
  - 归⑤？⑤只收**安全后果**（禁 force push、只推 fork），而提交粒度、并行隔离、可回退性不是安全问题，塞进⑤就是把门禁层混入加权话题，破坏 §4.2。
  - 归⑥？⑥的核心问题是"卡住脱身"，合并冲突剧本只是它的一族判据；"改动的协作旅程"整体是另一个问题。
  - 归②？②管"判定对错 + 证据"，review 适配的**格式面**可归②，但分支模型/隔离/回退不是验证话题。
  - 判据量足够成族（6 族以上，见 09 维文件），不构成"为省条目硬拆"。
- **边界声明**（与相邻维，成文于 09 文件）：改动能否进主干的**协作面**归⑨；推送与强制的**安全红线**归⑤；卡住后**脱身**归⑥；PR 内**证据义务**归②。

### G2 工具/接口面独立成维？→ 不立，维持现有归属，边界补强

raw 04 篇整篇讲工具面设计（命名、返回值 token 预算、聚合、数量），曾疑似缺口。核对现有归属：命名/聚合/数量→④（修改视角）、可发现/预算→①（发现视角）、错误可行动→按上下文归③②⑥、信任面→⑤。**每个话题都有着落**，缺的只是"同词多视角"在 checklist 里互相注明防双算（④ 开放问题已记）。若立独立维会与①④大面积同起同落——违反正交纪律。处置：不立，checklist-v1 落条时在①④的共享表面条目互相加指针。

### G3 记忆/状态外化独立成维？→ 不立

L4 记忆层话题已在⑥-B（干净重来/context reset）与⑦-B（状态清理、保留/丢弃分离）落位。B 线评估时这两族合起来完整覆盖记忆面；单独立维会与⑥⑦双双重叠。

### G4 成本/效率（token、wall-clock、算力）独立成维？→ 不立

token 预算已被①吸收（这正是①的存在理由）；wall-clock 与算力消耗主要是 harness/厂商实现属性（L-profile 层），不是仓库侧判据，不立。

### G5 依赖与供应链安全独立成维？→ 不立，扩⑤判据族

依赖投毒、MCP/tool 供应链、可执行配置的信任边界本质是**危险面结构性可控**，是⑤的核心问题的子问题。处置：⑤判据族 3（攻击面）在 checklist-v1 时显式纳入依赖与 tool/MCP 供应链条目。

## 4. 减维检验（可减/可并的方向，逐一审）

充分性不只是"要不要加"，也要审"有没有该合的"：

| 并维候选 | 判定 | 理由 |
|---|---|---|
| ③ 并回 ⑥（环境+恢复合一） | **不并** | 判据形态不同：③是"路径存在且有序"（tier-0/1 静态可查），⑥是"出口存在且可达"（tier-2 演练）；合并会把 cheapest-first 采证顺序打乱。v1.1 拆分时的论证经复审仍成立 |
| ⑦ 并回 ①（供给+保鲜合一） | **不并** | ①管"这一次任务里在场吗"，⑦管"随时间变质没人管吗"；同一仓库可以①高分⑦低分（此刻干净、但无打扫机制），互不参考即可打分——正交性自检通过 |
| ⑦ 并入 ⑧（资产新鲜度+工件一致性） | **不并** | 分界口诀成立：⑦"文件旧了没人删"，⑧"文件还新但说的和代码做的是两回事"。守护对象不同（指引资产 vs 工件间一致），判据形态不同（⑦多为流程/政策条目，⑧多为机器守护条目） |
| ② 并入 ⑧（验证+漂移） | **不并** | ②管"改后判定对错+产出证据"，⑧管"工件间一致性被机器守护"；无 spec 的仓库可②满分⑧低分，两者无必然相关 |
| ⑤ 并入加权层 | **不并** | 门禁/加权分离是 v1 修正过的聚合结构硬伤（§0.1），回退即重新引入"安全被平均稀释"问题 |

结论：现有维无一可并。九维为当前充分且必要的集合——每一维独立回答一个核心问题，两两边界成文。

## 5. 结论

**八维不够，扩为九维**：新增 **⑨ 版本控制与协作面**（加权维，A+B 适用；B 下因多 agent 并行使该维从边缘变一等）。G2–G5 处置为"归入现有维/不立"，理由如上。

连带效应：

- 门禁/加权结构不变：⑨ 参与加权；⑧ 之外加权维由七个变八个。
- B 线重心维集更新为 ②⑥⑦⑧⑨（⑨ 在 B 下因并行 agent 常态化而加重）。
- framework §3.4 总表与 `10-dimensions/` 索引同步增⑨；定义细节见 [`10-dimensions/09-vcs-collaboration.md`](10-dimensions/09-vcs-collaboration.md)。
