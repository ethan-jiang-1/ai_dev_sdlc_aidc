## 1. 体系要回答的问题

给定任意一个代码仓库，**系统性地评估它对 coding agent（Claude Code / Codex / Cursor / Gemini CLI / Aider 等）的工作友好程度**，产出：可复现的打分 + 可执行的整改清单。

设计约束（继承自 raw 并升为原则）：

1. **仓库无关**：所有判据不含特定仓库的案例锚点；具体仓库只作审计时的"被测对象"，不进体系定义。
2. **一手源可溯**：每条判据给出厂规范 / 官方文档依据；无依据的判据须标注"经验判据"。
3. **可操作**：每条判据含"怎么查"（只读命令 / 抽查方法）与"合格标准"，两个不同审计者应得出一致结果。
4. **硬约束与软指令分开评**：能被 hooks / CI 强制的判据，与只能靠提示词遵守的判据，分属不同维度、不混算。

## 2. 五维框架

| 维度 | 核心问题 | 覆盖的判据族 |
|---|---|---|
| ① 上下文供给 / 可发现性 | Agent 能否在合适时机、以最低 token 成本找到正确指引？ | 指令入口规范性与层级、文件预算（行数/字节）、无矛盾、不复述可推导内容、具体可验证措辞、路径作用域、命名可 grep、无 distractor、活文档机制 |
| ② 可验证性 / 反馈闭环 | Agent 能否自主确认"我改对了"？ | 确定性构建/测试/lint 命令文档化、快速子集、测试确定性、外部依赖替身、本地与 CI 同门禁、格式检查归 CI、flaky 出口、失败信息可行动 |
| ③ 可执行环境 | Agent 能否从零把环境跑起来，错误是否可行动？ | setup 顺序显式、失败模式已说明、配置模板分离、就绪探测真实、确定性命令包装器、隐式全局状态清零、跨平台/编码兼容、依赖 pin |
| ④ 可修改性 / 局部性 | Agent 改一处时，需要理解的涟漪范围有多大？ | 深模块薄接口、模块大小规则、契约显式化、生成物隔离、命名空间消歧、高频操作聚合、文档与代码同源、危险区前置成文 |
| ⑤ 安全护栏 | 软指令与硬约束是否各司其职？ | 上下文 vs 强制的分界（hooks/permissions）、指令文件自身的供应链攻击面、敏感操作就近显式禁令、破坏性操作可辨识、密钥分离 |

反模式与判据逐条对照 raw 五篇（01 的框架推导、03 的消费机制、04 的接口设计、05 的验证基建）；60 条初版清单见 [`../raw/90-audit-checklist.md`](../raw/90-audit-checklist.md)。

## 3. 打分模型（待打磨）

- 每条判据 ✅ / ⚠️ / ❌ 三档；⚠️ 须注明理由。
- 维度加权（raw 初版：①②×1.5、③×1、④⑤×?）——**权重是 v0 最未定型的部分**，需要多仓库试测后校准。
- 总评折算字母级（A±~D）只是表达层，不是体系核心。

## 5. 推敲路线

1. **泛化 60 条清单** → 本目录 `result/checklist-v1.md`（逐条去锚点、genericity 审查、补"经验判据"标注）
