## V8 的完整论证

1. **P1-P3 先立 OPC 的责任压力**：五个 Engineering 不是工具目录，而是信息、行动、组织三层越来越重的责任。团队可以分工，OPC 必须知道哪些可借、哪些不能外包。
2. **P4-P8 解释责任为何上移**：模型越强，人的动作越从亲手做转向设计系统怎么做；Prompt、Context、Harness、Loop、Graph 各自回答不同问题。
3. **P9-P14 证明为什么问题回到 Harness**：Loop / Graph 会放大结果，却补不上缺失的执行边界；模型可以提议，执行端必须独立决定放行。
4. **P15-P19 给 OPC 一条可执行判断**：默认借成熟 Harness；只有运行边界进入业务差异化，才寻找可组合 Harness。DSH 的热度只是入口，owner 价值来自自己验证过的能力组合，以及共同合同与共同事实。
5. **P20-P23 完成责任闭环**：P20 提出四个责任问题，P21 用 owner final say 回答，P22 给出三层掌握标尺，P23 留下一句“部件可借，边界自己定”。

## 逐页生产事实

### P1-P2 · 提问与全貌

- P1：**OPC 航海指南——一个人，AI Coding 要掌握到多深？**
- P2：**AI Coding 的五个 Engineering，先看全貌**；说清任务 → 让动作可靠 → 把工作组织起来。
- 视觉与详细文案继承 V7。

### P3 · OPC 面对的三层责任

- 标题：**五个 Engineering 背后，是三层越来越重的责任**
- 副题：团队可以分工；OPC 必须知道，哪些可以借，哪些不能外包
- 01 信息责任：把任务说清，把当下事实挑对
- 02 行动责任：决定能做什么、如何验证、何时停止
- 03 组织责任：把可靠行动连成 Loop，编排成 Graph
- 收束：**整场只追一个判断：哪一层的最终决定必须在手**

### P4-P5 · 责任为什么上移

- P4：模型越强，工程对象越从一句话往系统上移。
- P5：Prompt 与 Context 解决“说什么、看什么”，仍未解决安全行动。
- 视觉与详细文案继承 V7。

### P6 · Harness 的定义

- 标题：**Harness Engineering：把“能做”变成“可交付”**
- 副题：它不替模型思考；它定义能做什么、谁来检查、如何留下记录
- 公式：**Agent = Model + Harness**
- 构件：权限 / 沙箱 / 工具 / 验证 / 执行记录 / CI
- 解释：权限、沙箱、工具、验证、记录与 CI，是模型之外让行动可交付的一切。
- 转场：一次动作可靠后，才讨论怎样把反馈连成 Loop、把任务组织成 Graph。

### P7-P8 · 让可靠行动持续并被组织

- P7：Loop 让反馈回到下一轮；Graph 把复杂任务写成显式依赖。
- P8：五个 Engineering 同时活着，但各自回答不同问题；每一次真实动作都要经过 Harness 的执行边界。
- 视觉与详细文案继承 V7。

### P9 · 上层能力补不上执行边界

- 标题：**Loop / Graph 会放大结果，不会补上缺失的执行边界**
- 副题：上层组织能力越强，每个节点越要先独立授权、检查、记录
- 流程：上层提出下一步 → Harness 授权、检查、执行 → 结果进入下一轮 / 下一节点
- 解释：每一个节点最终都落到一次真实执行；上层不会自动修复底层缺口。
- 收束：**上层越复杂，越不能把可靠性寄托在模型自觉上；所以问题重新回到 Harness。**

### P10 · 能力上限与交付底线

- 标题：**模型决定能力上限，Harness 决定交付底线**
- 副题：同一个模型，换一圈 Harness，交付底线就变了
- 公式：**能力上限：Model + 交付底线：Harness**
- 六项交付属性：权限清楚 / 环境隔离 / 工具受控 / 结果可验 / 过程可追 / 失败即停
- 解释：Harness 不替模型思考；它把可靠性变成可执行、可检查的系统行为。
- 收束：**同一个模型，换一圈 Harness，就是两套交付系统。**

### P11-P12 · 可靠性怎样发生

- P11：可靠性发生在行动前约束和行动后反馈；确定的事交给系统，需要理解语义时才交给模型或人。
- P12：先圈住、拦住、看清，再承载 Knowledge Map 等专业知识。
- 视觉与详细文案继承 V7。

### P13 · 提议权与执行权分开

- 标题：**模型可以提议下一步；执行端必须独立决定放行**
- 副题：Loop / Graph 安排下一步；Harness 决定这一步能不能发生
- 提议：模型 / Loop / Graph 给出下一步动作
- 检查：权限 + 确定性门禁独立判断
- 执行：放行 / 拒绝并留下记录
- 结论：**提议权可以交给模型；执行权必须留在 Harness。**
- 证据：GraphARC 的模型提议工作图、确定性检查器决定放行。

### P14 · 执行时授权事故

- 伪造工具调用无需模型也能触发真实动作；修复是在执行端独立授权。
- 原则：`authorize at execution, not at generation`。
- 转场：边界必须有人负责，但不等于每个 OPC 都要自己造 Harness。
- 视觉与详细文案继承 V7。

### P15 · 是否掌握边界的判断标准

- 标题：**只有当运行边界进入业务，才值得自己掌握**
- 副题：工具多不是理由；标准边界开始限制真实交付，才是理由
- 判断：**不是“要不要自建”，而是“边界是否已经成为差异化”**
- 边界仍是通用能力：继续借成熟 Harness，把注意力留给业务。
- 边界已经进入业务：要改模型、工具、门禁、环境或知识。
- 收束：**业务开始要求改边界，才寻找可组合 Harness。**

### P16-P17 · 默认借现成，DSH 作为例外信号

- P16：Codex、Claude Code 已经很强；默认借现成，只有边界成为业务才寻找可组合 Harness。
- P17：DeepSeek Harness 公开约 14 天接近 20 万 GitHub stars；注意力聚到可扩展边界，但热度不是质量认证。
- 视觉与详细文案继承 V7。

### P18 · 从热度回到 OPC 价值

- 标题：**热度只是入口；对 OPC，价值在少盯、敢放、能复用**
- 副题：别人替你探索过，不等于替你验证过
- 定义：**真正可借的，不是插件数量，而是自己验证过的能力组合**
- 省手：换底座时少重写。
- 敢放手：审批 fail-closed，事实可重建。
- 可复用：自己验证过的组合带到下一项目。
- 收束：先验证，再借力；少回手工，敢交真活。

### P19 · DSH 的定位与价值机制

- 标题：**DSH 不是插件商店；它是一套可组合的 Harness runtime**
- 副题：上一页三项收益，来自共同合同和共同事实，不来自插件数量
- 四类能力：模型 / 工具 / 执行后端 / 规则与 Loop
- 共同合同：模型、工具、后端与规则可组合、可替换。
- 共同事实：发生过的行动按顺序留下；append-only session log。
- 收束：插件扩展 Harness；Harness 负责运行合同与事实记录。

### P20 · 四个责任问题

- 插件进入执行链后，真正的问题变成“谁说了算”。
- 谁允许它进来？谁能换实现？谁在执行前签字？谁能还原事实？
- 四问是运行边界的责任清单，不是插件功能清单。
- 视觉与详细文案继承 V7。

### P21 · Owner 的 final say

- 标题：**Harness 在手，不是全部自建，而是 owner 有 final say**
- 副题：能接什么、换什么、执行什么、留下什么，都能由你最终决定
- 我决定接什么：能力能否进入。
- 我决定换什么：实现能否替换。
- 我决定何时执行：门禁是否放行。
- 我决定如何追溯：事实能否重建。
- 收束：**部件可以借；最终决定权必须留给 owner。**

### P22 · 回答开场

- 标题：**OPC 要掌握到 Harness 这一层**
- 副题：不是为了造框架，而是知道何时借、何时改、何时必须自己决定
- 标尺：掌握深度不按工具数量算，按对运行边界的责任算。
- 1 会用成熟 Harness。
- 2 看懂运行边界。
- 3 需要时握住 final say。
- 带走句：**部件可借，边界自己定。**

## 口径红线

- 五层是工程注意力与责任对象的叠加，不是严格运行时包容关系。
- P6 只定义 Harness；P9 证明上层为何依赖边界；P10 才落到交付底线，三页不得重新合并为重复定义。
- 模型 / Loop / Graph 可以提出下一步；真正执行前仍需由 Harness 独立授权、检查与记录。
- GitHub stars、forks 与生态条目只能说明 attention / 扩展面，不能证明质量、安全或成熟度。
- “四项决定权”“final say”“部件可借，边界自己定”是本 talk 的解释性结论，不冒充 DSH 官方原话。
- DSH 不被描述成 Codex / Claude Code 的替代品；默认策略仍是借用成熟 Harness。
