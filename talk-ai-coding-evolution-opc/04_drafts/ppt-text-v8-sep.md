## P1
- OPC 航海指南
- 一个人，AI Coding 要掌握到多深？
---
## P2
- AI Coding 的五个 Engineering，先看全貌
- 说清任务 → 让动作可靠 → 把工作组织起来
---
## P3
- 五个 Engineering 背后，是三层越来越重的责任
- 团队可以分工；OPC 必须知道，哪些可以借，哪些不能外包
- 信息责任：把任务说清，把当下事实挑对
- 行动责任：决定能做什么、如何验证、何时停止
- 组织责任：把可靠行动连成 Loop，编排成 Graph
- 哪一层的最终决定必须在手？
---
## P4
- 模型越强，工程对象越从一句话往系统上移
---
## P5
- Prompt 与 Context：先说清，再看对
- 下一问：它究竟能在什么边界里行动？
---
## P6
- Harness Engineering：把“能做”变成“可交付”
- Agent = Model + Harness
- 它定义能做什么、谁来检查、如何留下记录
---
## P7
- Loop 与 Graph：让可靠行动持续发生并被组织
---
## P8
- 五个 Engineering 同时活着，但各自回答不同的问题
- 每一次真实动作都要经过 Harness 的执行边界
---
## P9
- Loop / Graph 会放大结果，不会补上缺失的执行边界
- 上层提出下一步 → Harness 授权、检查、执行 → 结果进入下一轮 / 下一节点
- 上层越复杂，越不能把可靠性寄托在模型自觉上
---
## P10
- 模型决定能力上限，Harness 决定交付底线
- 权限清楚 / 环境隔离 / 工具受控 / 结果可验 / 过程可追 / 失败即停
- 同一个模型，换一圈 Harness，就是两套交付系统
---
## P11
- 可靠性发生在两次：行动前约束，行动后反馈
---
## P12
- Harness 先把行动变可靠，再把专业知识放进去
- 圈住 / 拦住 / 看清 / Knowledge Map
---
## P13
- 模型可以提议下一步；执行端必须独立决定放行
- 提议 → 独立检查 → 放行 / 拒绝并记录
- 提议权可以交给模型；执行权必须留在 Harness
---
## P14
- 伪造工具调用，无需模型也能触发真实动作
- authorize at execution, not at generation
- 边界必须有人负责，但不等于每个 OPC 都要自己造 Harness
---
## P15
- 只有当运行边界进入业务，才值得自己掌握
- 工具多不是理由；标准边界开始限制真实交付，才是理由
- 边界仍是通用能力 → 借成熟 Harness
- 边界已经进入业务 → 寻找可组合 Harness
---
## P16
- Codex、Claude Code 已经很强：大多数 OPC 应直接借用
- DSH 不是替代成熟产品，而是让边界可改
---
## P17
- 公开 14 天，DeepSeek Harness 接近 20 万 GitHub stars
- “边界可扩展”需求爆发的信号，不是质量认证
---
## P18
- 热度只是入口；对 OPC，价值在少盯、敢放、能复用
- 真正可借的，不是插件数量，而是自己验证过的能力组合
- 先验证，再借力；少回手工，敢交真活
---
## P19
- DSH 不是插件商店；它是一套可组合的 Harness runtime
- 三项收益来自共同合同和共同事实，不来自插件数量
- 插件扩展 Harness；Harness 负责运行合同与事实记录
---
## P20
- 插件进入执行链后，真正的问题变成：谁说了算？
- 谁允许接入 / 谁能替换 / 谁在执行前签字 / 谁能还原事实
---
## P21
- Harness 在手，不是全部自建，而是 owner 有 final say
- 能力能否进入 / 实现能否替换 / 门禁是否放行 / 事实能否重建
- 部件可以借；最终决定权必须留给 owner
---
## P22
- OPC 要掌握到 Harness 这一层
- 会用成熟 Harness → 看懂运行边界 → 需要时握住 final say
- 部件可借，边界自己定
