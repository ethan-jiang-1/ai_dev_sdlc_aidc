# Talk 页面结构（现场版 v1.7 · 23 页 · 45 min）

> 本版已与 V8 成稿对齐。全场用“责任如何上移”串起五层：Prompt / Context 处理信息责任，Harness 承担行动责任，Loop / Graph 放大组织责任；OPC 最终要判断哪些可借、哪些不能外包。

## 开场（3.5 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P1 | OPC 航海指南 | 0.5 | 题目、Ethan Jiang、问题：一个人要把 AI Coding 掌握到多深？ |
| P2 | 五个角色，已经分别有人替你命名 | 1.5 | Boris Cherny 讲 Loop；Böckeler 定义 Harness；Steinberger 讲 State Graph；人从写一句话转为设计系统怎么工作。 |
| P3 | 五个 Engineering 背后，是三层越来越重的责任 | 1.5 | 信息责任 → 行动责任 → 组织责任；团队可以分工，OPC 必须知道哪一层的最终决定必须在手。 |

## 第一幕：五层不是五个新词（12 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P4 | 同一台发动机，把人的动作一格格往上推 | 2 | 模型能力增强 -> 单次交互边际收益下降 -> 杠杆点上移；METR 与 Anthropic 是两条证据；叠加，不是替代。 |
| P5 | Prompt 管表达，Context 管模型此刻所见 | 3 | Prompt 不是系统；Context 不是越多越好；context rot；两者解决不了执行边界。 |
| P6 | Harness Engineering：把“能做”变成“可交付” | 2.5 | Agent = Model + Harness；权限、沙箱、工具、验证、执行记录与 CI，让一次动作具备可交付条件。 |
| P7 | Loop 管时间上的反馈；Graph 管空间上的协作 | 2.5 | Loop 的黄金法则；Graph 的显式节点、边、状态；Graph 可在部分节点使用 Loop；两者均是新兴、低置信度。 |
| P8 | 五层同时活着，但不是一座从小到大的金字塔 | 2 | 关系图：Prompt/Context 服务一次模型调用；Harness 保障每次执行；Loop 跨运行；Graph 跨节点组织；今天重仓成熟的前三层。 |

## 第二幕：为什么答案停在 Harness（10 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P9 | Loop / Graph 会放大结果，不会补上缺失的执行边界 | 1 | 每个节点最终都落到一次真实执行；上层越复杂，每个节点越要先独立授权、检查、记录。 |
| P10 | 模型决定能力上限，Harness 决定交付底线 | 1.5 | 权限清楚、环境隔离、工具受控、结果可验、过程可追、失败即停；同一个模型换一圈 Harness，就是两套交付系统。 |
| P11 | Harness 同时在行动前引导、行动后反馈 | 3 | Guides / Sensors；computational / inferential；确定性优先。 |
| P12 | Harness 先保证可靠，再承载专业知识 | 2.5 | 圈住 / 拦住 / 看清是三项可靠性控制；Knowledge Map 在可靠边界上帮助模型找到归属与正确路径。 |
| P13 | 模型可以提议下一步；执行端必须独立决定放行 | 1 | 模型 / Loop / Graph 提议 → 权限与确定性门禁独立检查 → 放行或拒绝并记录；提议权可以交给模型，执行权必须留在 Harness。 |
| P14 | 2026 的教训：在生成时相信模型，不等于在执行时授权 | 1 | 工具调用形状被伪造/绕过 -> 执行端缺少独立授权 -> 操作发生；修复是 authorize at execution；结尾提出“边界有人负责，不等于人人自建”。 |

## 第三幕：一人公司看见 DSH 的爆发与收益（8.5 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P15 | 只有当运行边界进入业务，才值得自己掌握 | 1 | 工具多不是理由；标准边界开始限制真实交付、运行边界成为业务差异化，才是寻找可组合 Harness 的理由。 |
| P16 | 绝大多数场景，先借现成 Harness | 2 | 产品把沙箱、权限、观测等组件随产品交付；Start with the simplest viable system。 |
| P17 | 公开 14 天，DeepSeek Harness 接近 20 万 GitHub stars | 3 | 近 20 万是主信号；22,820 forks 与 2,286 条生态快照是支持信号；注意力迅速聚到“可扩展边界”，但不是质量认证。 |
| P18 | 热度只是入口；对 OPC，价值在少盯、敢放、能复用 | 2.5 | 真正可借的不是插件数量，而是自己验证过的能力组合；别人替你探索过，不等于替你验证过。 |

| 页 | 页面结论 | 时间 | 必讲要点 |

## 叙事检查

1. P2 给出五个 Engineering；P3 把它们翻译成 OPC 无法回避的信息、行动、组织三层责任；P4 再解释责任为何随模型能力上移。
2. P5-P8 逐层回答“说什么、看什么、怎样行动、怎样组织”；P8 明确所有真实动作仍落到 Harness 边界。
3. P6 只定义 Harness；P9 证明 Loop / Graph 补不上底层边界；P10 才说明边界怎样改变交付底线，避免三页重复。
4. P11-P14 依次讲可靠性机制、专业知识承载、提议权与执行权分离、执行时授权事故，完成“为什么是 Harness”的论证。
5. P14 提出“边界必须有人负责”，P15 给出业务差异化判断，P16 保住“先借现成”的默认答案。
6. P17 用 DSH 爆发建立需求信号，P18 把热度转成 OPC 可验证的收益，P19 解释收益为何来自 runtime 的共同合同与共同事实。
7. P20 把插件问题提升为责任问题；P21 用 owner final say 回答；P22 以三层掌握标尺直接回答开场，P23 留下原则。

## 口径红线

- 前三层成熟，Loop / Graph 是新兴观察对象，不讲成既定生产范式。
- Graph 可以编排 Loop，也可以包含工具、验证器或其它节点；不能把所有 Graph 节点画成 Loop。
- Harness 是可靠性边界，不等于一定在几何上“包住”所有分布式节点；P8 的图只表达 talk 的治理关系，不宣称严格运行时包含。
- DSH 的原生机制不是 MCP；说 `ctx.llm`、`ctx.tools`、capability seam、plugin。
- DSH GitHub star 与 2,286 条生态数据都是 2026-08-27 的快照；只能说明 attention / 扩展面，不能讲成产品成熟、插件可信或持续增长曲线。
- CVE 只讲执行时授权缺失的因果链，不把厂商名、编号堆成画面主体。
