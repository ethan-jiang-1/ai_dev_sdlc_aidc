# 第三幕：一人公司看见 DSH 的爆发与收益（v1.7）

> 本幕不把“固定”说成落后，也不把“灵活”说成从零造。它讨论的是：当任务越过现成产品公开的扩展合同，谁能改变运行边界。

## P15 只有当运行边界进入业务，才值得自己掌握（1 min）

**上屏**：工具多不是理由；标准边界开始限制真实交付，才是理由。

**判断问题**：不是“要不要自建”，而是“边界是否已经成为差异化”。边界仍是通用能力，就继续借成熟 Harness；边界进入业务，才需要改变模型、工具、门禁、环境或知识组织。

**讲点**：P14 已说明边界必须有人负责；本页给出可执行判断。标准边界尚未限制交付时，把注意力留给业务；业务开始要求改边界，才寻找可组合 Harness。

## P16 绝大多数场景，先借现成 Harness（2 min）

**上屏**：沙箱、权限、可观测性、provenance 与 CI 已能随产品交付。

**讲点**：Harness 的民主化使人不再需要自己写 bash 编排。固定产品在成熟、常见任务上提供了大量可靠性组件，正确的默认策略是 `Start with the simplest viable system`。DSH 只在“边界成为业务”的例外中出现，不替代 Codex 或 Claude Code。

## P17 公开 14 天，DeepSeek Harness 接近 20 万 GitHub stars（3 min）

**上屏**：主信号 **近 20 万**；199,846 stars / 2026-08-27 快照。支持信号：22,820 forks；2,286 条生态快照。

**三类正在涌入的东西**：桥（接外部能力）、渠（占分发入口）、窗（在对话驾驶舱上做增强）。

**讲点**：先让“近 20 万”形成爆发感，再立即加上可信度边界。这股注意力迅速聚到一套可扩展的 Harness 边界；它是“边界可扩展”需求爆发的信号，不是产品质量、插件安全或生态成熟度的证明。

**转场**：大家为什么涌进来，和 OPC 为什么需要它，是两件不同的事。

## P18 热度只是入口；对 OPC，价值在少盯、敢放、能复用（2.5 min）

**上屏**：
- **真正可借的，不是插件数量，而是自己验证过的能力组合。**
- **省手**：换底座时少重写。
- **敢放手**：审批 fail-closed；事实可重建。
- **可复用**：把自己验证过的组合带到下个项目。

**讲点**：别人替你探索过，不等于替你验证过。P17 的热度只是发现入口；对自用 owner，真正的生产力在少回到手工、敢交真活、把验证过的能力组合复用到下一项目。

**转场**：但这里出现一个定位问题：这些插件到底围绕着什么工作？DSH 是商店、Agent 产品，还是别的东西？
