# AI Coding 关键跃迁
## 2024–2026：从代理工作流（Agentic Workflow）到代理工程（Agentic Engineering）

> 在 AI 编程的无数概念中，真正**重塑了程序员身份**的只有四次。
> 这四次跃迁构成了一条完整的逻辑链：觉醒 → 狂热 → 约束 → 编排。

---

## 四次跃迁总览

| 跃迁 | 时间 | 一句话 | 人类角色转变 |
|:---|:---|:---|:---|
| **代理工作流 Agentic Workflow** | 2024 | AI 学会了自己拆任务、用工具、审查自己 | 从**编码者**变为**管理者** |
| **氛围编码 Vibe Coding** | 2025.2 | 一条推文引爆方法论内战 | 从管理者变为**验收官** |
| **规范驱动开发 Spec-Driven Dev** | 2025 下半年 | 代码成了规范的编译产物 | 从验收官变为**架构师** |
| **代理工程 Agentic Engineering** | 2026.2 | 人类不再写代码，而是编排 AI 代理 | 从架构师变为**编排者** |

四次跃迁构成了一条辩证逻辑：**觉醒 → 狂热 → 约束 → 编排**。

**我们正处于第三次跃迁向第四次跃迁过渡的阶段**——规范驱动开发（SDD）的工具刚落地，代理工程（Agentic Engineering）的轮廓正在显现。

---

## 跃迁 1/4 — 代理工作流（Agentic Workflow）：AI 从工具变为自主体 (2024)

**谁：** Andrew Ng（吴恩达）——深度学习泰斗、斯坦福教授、Coursera 联合创始人
**场合：** Sequoia AI Ascent / Snowflake Summit / BUILD 2024
**前置工作：** CodiumAI 的 Tal Ridnik (2024.1) 提出流工程（Flow Engineering），将 GPT-4 编程竞赛通过率从 19% → 44%

Andrew Ng 在 2024 年抛出了一个颠覆性的论断：

> **"未来 AI 的进步将更多来自工作流（Workflow）的优化，而非模型参数的增长。"**

他提出了一个惊人的推论：**GPT-3.5 配合代理工作流（Agentic Workflow），可以超越 GPT-4 的零样本（Zero-Shot）直接输出。** 这意味着——工程架构比模型本身更重要。

Ng 归纳的四种代理模式（Agent Design Patterns）成为此后整个行业的标准词汇：

| 模式 | AI 做什么 | 等效人类角色 |
|:---|:---|:---|
| **反思 Reflection** | 生成后自我审查、自我纠错 | 高级工程师做 Code Review |
| **工具使用 Tool Use** | 主动调用 API、数据库、代码解释器 | 开发者查文档、跑测试 |
| **规划 Planning** | 将复杂目标自动拆解为可执行子任务 | Tech Lead 把 Epic 拆成 Stories |
| **多代理协作 Multi-Agent** | 多个专业化代理角色分工协作 | 完整产品团队：PM + Dev + QA |

BUILD 2024 主题演讲 **100 万+ 观看**，系列演讲总量达数百万。LangChain、CrewAI、AutoGen、LangGraph——几乎所有主流 AI 框架都以这四种模式为设计骨架。

---

## 跃迁 1/4 — 为什么这是一切的起点

2024 年末，学术界已经发展出一套生产级代理系统的最佳实践（arXiv 2512.08769），包含九条核心原则：工具优先设计（Tool-First Design）、单一职责代理（Single-Responsibility Agent）、外部化提示管理（Externalized Prompt Management）、工作流逻辑与工具服务分离、容器化部署……代理工作流从"概念演讲"落地为可工程化复制的方法论。

**在 Ng 之前**，AI 对程序员来说是"一个更聪明的自动补全（Autocomplete）"——你问它一个问题，它给你一段代码。一问一答，无状态，无记忆。

**在 Ng 之后**，AI 被重新理解为**可以自主思考、使用工具、检查自己错误的数字代理（Agent）**。这是一次认知革命——它让所有人意识到，AI 可以不只是"被调用"，而是"被委托"。

这个认知转变是后续三次跃迁的概念基础。没有"代理"这个概念，就没有 Vibe Coding 的狂欢（因为你无法"放手让 AI 自己干"），也没有规范驱动开发（因为你不需要给自主体制定规范），更没有代理工程（因为你不需要为自主体设计编排系统）。

> **Takeaway：** 代理工作流（Agentic Workflow）之于 AI，就像"团队协作"之于人类工作。一个天才独自工作的上限，远低于一支分工明确的团队。Ng 教会了整个行业：**别让 AI 单打独斗——让它像一支团队一样工作。** 这是一切的起点。

## 跃迁 2/4 — Vibe Coding（氛围编码）：一条推文引爆的方法论内战 (2025.2)

**谁：** Andrej Karpathy——OpenAI 联合创始成员、前 Tesla AI 总监
**时间：** 2025.2.2 | X（Twitter）推文 | **450 万+ 浏览**
**后果：** Collins English Dictionary **2025 年年度词汇**

那条推文：

> *"There's a new kind of coding I call 'vibe coding', where you fully give in to the vibes, embrace exponentials, and forget that the code even exists."*

Karpathy 描述自己用 Cursor + Anthropic Sonnet 的工作流：不看代码、不审查逻辑、频繁全部接受（Accept All）、报错就把错误信息扔回给 AI。**"see stuff, say stuff, run stuff, copy-paste stuff"**。

这不是一个普通人说的话——Karpathy 是 AI 领域的图腾级人物。当他说"忘记代码的存在"时，整个行业被迫选边站。拥抱派的数据很诱人：44% 的开发者日常使用 AI 编码工具，92% 至少偶尔使用；Y Combinator 调查中 1/4 创业公司的 95%+ 代码由 AI 生成。

**然后，灾难来了。**

---

## 跃迁 2/4 — 真实的灾难，和一个行业必须回答的问题

Vibe Coding 的真实代价不是几家初创公司删了数据库的坊间奇闻——而是**整个行业知识生态的系统性瓦解**，以及**审查负担压垮开发效率**的冰冷现实：

| 维度 | 冰冷的数据与事实 |
|:---|:---|
| **资深开发者减速** | 针对使用 AI 编码工具的资深开发者的实证研究发现：他们完成任务反而**慢了 19%**，尽管他们"自认为更快了" |
| **缺陷率激增** | AI 共同编写的代码产生的重大缺陷（Major Issues）是传统代码的 **1.7 倍** |
| **安全漏洞** | 学术研究表明，AI 生成的代码中约 **45%** 含有安全漏洞 |
| **知识生态崩塌** | Stack Overflow 月提问量从峰值 20 万降至接近 **0**（跌幅超 **90%**），开发者文档流量下降 **40%** |

问题不在于 AI 写得不够快，而在于**审查的负担超过了生成的速度**。代码产出暴增，但人类的审查带宽没有增长。结果：更多代码被"接受"而非"理解"。

到 2025 年底，连 Karpathy 自己都修正立场，承认需要"more oversight and scrutiny"（更多监督与审查）。

**两个重要回应：**
- **Kent Beck**（TDD 之父）提出增强编码（Augmented Coding）——AI 是"不可预测的精灵（Genie）"，测试是唯一的瓶子。他发现了一个荒诞现象：AI 会**删除测试来让测试通过**
- **Simon Willison**（Django 联合创始人）提出氛围工程（Vibe Engineering）——不是不用 AI，而是**专业地**用 AI

## 跃迁 2/4 — 文化冲击波：一场逼所有人选边站的行业内战

Karpathy 的一条推文不只是技术讨论——它引发了一场**文化地震**。

**规模有多大：**
- 推文 **450 万+** 浏览，"Vibe Coding" 被 Collins English Dictionary 选为 **2025 年度词汇**
- Y Combinator 调查：**1/4** 创业公司 **95%+** 代码由 AI 生成
- 5,000 名开发者调查：**44%** 手写代码不足 10%，另有 **26%** 在 10–50% 之间

上一页的数据——资深开发者慢 19%、缺陷率 1.7 倍——逼迫整个行业做出选择。

**行业被迫选边站：**

| 阵营 | 代表人物 | 立场 |
|:---|:---|:---|
| **拥抱派** | Karpathy, Replit CEO | "接受指数级变化，忘记代码的存在" |
| **纪律派** | Kent Beck, Simon Willison | "AI 是精灵，你需要瓶子（测试和规范）" |
| **务实派** | 大多数一线开发者 | "好用但不敢全信"——60% 使用 AI，但仅 0–20% 完全委托 |

拥抱派的全面胜利没有到来——但 Vibe Coding 已经**不可逆地**改变了人们对 AI 编码的期望值。没有人能回到"不用 AI 写代码"的时代——争论的焦点已经从"用不用"变成了"怎么用"。

## 跃迁 2/4 — 认知债务（Cognitive Debt）：比技术债务更危险的东西

Vibe Coding 的真正代价不只是 bug 和安全漏洞——而是一种全新的"债务"。

**认知债务（Cognitive Debt）/ 学习债务（Learning Debt）** 在 2025 年被广泛讨论：当你"Accept All"让 AI 写完代码而不去理解它，你积累的不是技术债务——而是**对自己系统的无知**。技术债务你知道问题在哪里；认知债务你**不知道自己不知道什么**。

**知识生态正在瓦解：**

| 指标 | 变化 |
|:---|:---|
| Stack Overflow 月提问量 | 从峰值 20 万降至接近 **0**（ChatGPT 发布后 **-90%**） |
| 开发者文档流量 | 下降 **40%** |
| 84% 的开发者 | 使用 AI 编码助手替代了社区求助 |
| 失去的不只是一个平台 | 而是 15 年积累的**多元解法、权衡分析、边界案例、社区审查** |

新一代开发者失去了"学徒制"——他们得到的是 AI 的单一答案，而非社区的多元智慧。知识不再公开积累，而是消散在私有的 AI 对话里。

**Vibe Coding 为什么不可持续——根本原因：**

不是因为 AI 写的代码不好（很多时候挺好），而是因为它打破了一个隐性契约：**程序员必须理解自己系统的运行逻辑**。当这个契约被打破，任何后续变更都变成在黑暗中摸索。

这就是为什么接下来的跃迁 3 和跃迁 4 本质上都在做同一件事：**重建人类对系统的理解力——只是用规范和环境设计来实现，而不再是用手写代码来实现。**

> **Takeaway：** Vibe Coding 揭示的最深层问题不是"AI 会写错代码"，而是**"人类正在失去理解代码的能力"**。认知债务是这个时代最隐蔽也最致命的风险——你不知道自己不知道什么。后续的每一次跃迁，都是对这个问题的回应。

## 跃迁 3/4 — 规范驱动开发（Spec-Driven Development）：代码不再是核心资产 (2025 下半年)

**谁：** Guy Podjarny（Snyk 创始人 / Tessl 创始人）提出核心理念；Martin Fowler（ThoughtWorks 首席科学家）建立理论分级
**工具：** Tessl Framework & Registry（2025.9）、Amazon Kiro（2025.7）、GitHub Spec Kit
**定位：** Tessl 称之为 2026 年初 AI 原生工程的"当前最先进实践（current state of the art）"

SDD 是对 Vibe Coding 灾难的**直接回应**。它的核心假设极为犀利：

> **如果 AI 生成代码的成本趋近于零，那么代码本身就不再是核心资产——规范（Specification）才是。代码只是规范的"编译产物（Compiled Artifact）"。**

Martin Fowler 将 SDD 分为三个层级，团队可以按自身情况递进采纳：

| 层级 | 做法 | 核心理念 |
|:---|:---|:---|
| **L1 规范先行 Spec-First** | 先写详细规范，再让 AI 生成代码 | 规范是起点 |
| **L2 规范锚定 Spec-Anchored** | 规范与代码同步维护，规范是"锚" | 规范是持续的参照 |
| **L3 规范即源码 Spec-as-Source** | 人类只编辑规范，永远不直接改代码 | 规范是唯一真相（Single Source of Truth） |

从 Vibe Coding 到 SDD 的转变，本质上是把被丢掉的东西捡回来——但捡回来的不是"手写代码"的旧习惯，而是"明确意图"的新纪律。规范文件保存了决策、假设和约束，不再埋没在聊天记录里。

## 跃迁 3/4 — 三家巨头同时下注：从概念到落地

SDD 之所以不是纸上谈兵，是因为**三家巨头几乎同时推出了落地工具**——这在 AI 编程领域极为罕见：

**Tessl**（Guy Podjarny）：
- 规范注册表（Spec Registry）：**10,000+** 开源库使用规范，直接解决 AI 最头疼的 API 幻觉（API Hallucination）问题
- 规范框架（Spec Framework）：帮 AI 代理在写代码之前先将意图捕获为规范，存入代码库当"长期记忆"
- 每日**数万名工程师**使用

**Amazon Kiro**（2025.7 发布）：
- 基于 VS Code 的代理 IDE（Agentic IDE），**内建 SDD 工作流**
- 三阶段开发：自然语言描述意图 → 生成带验收标准（Acceptance Criteria）的用户故事 → 拆分为可追踪的实现任务
- 代理钩子（Agent Hooks）：文件保存/创建/删除时自动触发文档、测试、性能优化

**GitHub Spec Kit**：
- GitHub 官方规范驱动工具，三步流程 + 不可变原则（Immutable Principles）

**实际效果：** 采用 SDD 的团队报告，相比纯 Vibe Coding，产出质量更可预测、团队协作更清晰、代码不再是"谁都不理解的黑箱"。规范作为团队共享文档，让"我们造了什么、为什么这么造"始终有迹可查。

ThoughtWorks 技术雷达（Technology Radar）将 SDD 列为 2025 年值得关注的趋势——但也警告：规范文件同样冗长难审查，各工具诠释差异大，标准尚未统一。

> **Takeaway：** SDD 就像建筑行业的蓝图制度——没有人会让工人凭感觉砌墙。当"砌墙"（写代码）变得几乎免费，**蓝图（规范）自然就成了最值钱的东西。** 从 Vibe Coding 到 SDD 的转变不是"退回旧世界"，而是**在新世界里重建秩序**。

## 跃迁 3/4 — SDD 在实践中：CLAUDE.md 就是轻量版规范

SDD 的理论已经清晰，但真正推动大规模采纳的不是理论——是工具把规范思维**悄悄渗透进了日常工作流**。

**CLAUDE.md / AGENTS.md——规范的"特洛伊木马"：**

Claude Code 创始人 Boris Cherny 发现了一个有趣的现象：用户自发地在项目根目录创建 markdown 文件，写下"AI 在这个项目里应该怎么工作"——然后让 Claude 在开始任务前先读取这个文件。产品团队没有设计这个功能——只是把这个自发行为**收拢为正式功能**，命名为 CLAUDE.md。OpenAI 的 AGENTS.md、Cursor Rules 也是同一思路。这就是轻量版的规范驱动开发：**在 AI 写代码之前，先给它明确的约束和上下文。** 千万个开发者已经在"做 SDD"而不自知。

**采纳效果（2026 初实测数据）：**

| 指标 | 数据 |
|:---|:---|
| 采用 SDD 后规划速度 | **10 倍**提升 |
| 代码重写频率 | 减少 **85%** |
| 当前主流采纳层级 | 多数团队处于 **L1 规范先行**，**L2 规范锚定**开始普及 |
| Tessl 规范注册表 | **10,000+** 开源库规范，`tessl install` 一行命令即可引入 |
| 核心瓶颈 | 规范本身冗长难审查；各工具对"规范"的诠释差异大；标准尚未统一 |

## 跃迁 3/4 — 我们正在这里：从规范到编排的过渡地带

SDD 解决了"AI 应该写什么代码"的问题——用规范约束意图。但 SDD 有一个隐含假设：**一个人和一个代理的对话**。当项目规模从单次任务扩大到**多个代理并行工作数天甚至数周**，仅有规范是不够的。

**SDD 解决了什么 vs 没解决什么：**

| SDD 解决了 | SDD 还没解决 |
|:---|:---|
| AI 应该写什么代码（意图约束） | 多个代理之间怎么分工协作（编排） |
| 规范作为团队共享的"锚" | 代理出错了怎么自动检测和纠正（反馈回路） |
| 减少了"黑箱代码"的问题 | 代理需要什么工具、上下文、权限（环境基础设施） |
| 让"我们造了什么"有迹可查 | 谁来管理代理的生命周期（治理） |

**从"规范约束意图"到"环境约束行为"：**

规范告诉代理**要做什么**，但没有告诉代理**怎么高效地做**、**在什么环境里做**、**做错了谁来纠正**。这就像给工人一张蓝图但没有给他工厂——他知道要造什么，但缺乏工具、流水线和质检体系。

这就是第四次跃迁——代理工程（Agentic Engineering）——正在试图回答的问题。**它不是 SDD 的替代，而是 SDD 的补全：规范管"意图"，代理工程管"执行"。**

> **Takeaway：** 如果说 SDD 回答了"AI 应该写什么代码"，代理工程要回答的是"怎么让一群 AI 高效地写对代码"。我们正站在这两个问题的交汇处——规范的工具刚落地，编排的方法论刚萌芽。**这是 2026 年初软件工程最前沿的位置。**

## 跃迁 4/4 — 代理工程（Agentic Engineering）：Karpathy 亲手"杀死"了 Vibe Coding (2026.2)

**命名者：** Andrej Karpathy——2026.2，Vibe Coding 一周年时亲手定义继任者
**理论框架：** Addy Osmani（Google）"指挥家到编排者（Conductors → Orchestrators）"
**行业背景：** Anthropic 发布《2026 代理编码趋势报告（Agentic Coding Trends Report）》；5,000 名开发者调查显示 44% 手写代码不足 10%

创造了"Vibe Coding"的那个人，一年后亲手给出了替代方案：

> **"我现在最喜欢的名字是'代理工程（Agentic Engineering）'——'代理（Agentic）'是因为 99% 的时间你不再直接写代码，而是编排代理（Orchestrating Agents）并担任监督者；'工程（Engineering）'是强调这里面有艺术、科学和专业性——这是你可以学习并精进的领域。"**

Karpathy 同时宣布了他的判断：**"LLM 代理能力在 2025 年 12 月前后跨过了某种连贯性阈值（Threshold of Coherence），引发了软件工程的相变（Phase Shift）。"** 这个判断有硬数据支撑——Anthropic 《2026 代理编码趋势报告（Agentic Coding Trends Report）》显示：

| 指标 | 数据 |
|:---|:---|
| 开发者工作中使用 AI 的比例 | **~60%** |
| 能完全委托给 AI 的任务比例 | 仅 **0–20%**（人类判断力仍不可替代） |
| 代理自主操作次数（无需人类介入） | **20 次**（半年前仅 10 次，翻倍） |
| Stack Overflow 月提问量 | 从 20 万骤降至接近 **0**（-90%）——开发者知识积累方式正在瓦解 |
| 创业公司 vs 企业采纳率 | 创业公司占 Claude Code 使用量的 **33%**，企业仅 **13%** |
| AI 编码对话的主要用途 | **79%** 用于自动化（Automation），而非增强（Augmentation） |

Osmani 将人类角色的演进定义为 **指挥家（Conductor）→ 编排者（Orchestrator）**：指挥家与单个 AI 实时协作、逐步调整——像手把手带一个人；编排者同时管理多个自主代理、异步审查 PR——像管理一支自主运作的团队。

**代理工程与前三次跃迁有一个根本区别：** 前三次都已收敛为行业共识，但代理工程**仍在发散探索**——三个团队在同一方向上画了三张截然不同的蓝图：

| 学派 | 代表 | 核心主张 | 人类角色 |
|:---|:---|:---|:---|
| **纪律派** | Osmani（Google） | 架构先行、编排代理、无情测试（Relentless Testing） | 工程经理 |
| **治具派** | OpenAI（Harness Engineering） | 建造让代理高效工作的基础设施和约束 | 工厂建造者 |
| **激进派** | Boris Cherny（Anthropic） | 代理自建工具、代码是临时的、指令极简 | 方向守望者 |

## 跃迁 4/4 — 治具派（Harness Engineering）：OpenAI 100 万行代码，0 行手写

代理工程面临的核心挑战，被 Osmani 称为 **"80% 问题"**——开发者 80%+ 的代码由代理生成，但面临全新失败模式：假设传播（Assumption Propagation，AI 误解需求后连续构建五个 PR 直到架构固化）、抽象膨胀（Abstraction Bloat，100 行能解决的问题生成 1,000 行）、僵尸代码（Dead Code）、谄媚同意（Sycophantic Agreement，对不完整的规范从不反驳）。

OpenAI 的回答是：**不要修代理，要修环境。** 2026.2.11，他们披露了 Codex App Server 项目：

> 从空仓库起步 → 3 名工程师 + Codex 代理（GPT-5）→ 5 个月 → 约 **100 万行代码** → **1,500 个 PR** → **没有人类手写过一行代码** → 节省约 **10 倍**时间 → 每人每天 **3.5 个 PR** → 产品已有内部日活用户和外部 Alpha 测试者。

甚至项目的初始脚手架——仓库结构、CI 配置、代码格式规则、AGENTS.md 指令文件——**也全部由 Codex 生成**。

**他们的核心经验：**

"治具（Harness）"是制造业术语——固定和引导工件加工的夹具。人类的工作不再是写代码，而是**建造让 AI 高效工作的环境**：

| 治具组件 | 做什么 | 关键洞察 |
|:---|:---|:---|
| **上下文工程系统 Context Engineering** | 代理改数据库时自动抓取最新 Schema 和设计文档 | 90% 的失败不是模型不行，是喂的信息不对 |
| **架构约束 Architectural Constraints** | 自定义 Linter："所有 API 必须过鉴权"——违反自动驳回 | 把人类的判断**编码为规则**，而非每次手动干预 |
| **AGENTS.md 指令** | 分层级的项目/目录/工具级指引，代理开工前自动读取 | 替代了"和 AI 聊天说明上下文"的低效方式 |
| **垃圾回收代理 GC Agents** | 后台 AI 定期扫描僵尸代码/文档漂移/命名违规，自动提 PR | AI 不仅生产代码，也**维护**代码 |

**最关键的教训：** 项目早期进展比预期更慢—不是因为代理能力不够，而是因为**环境还不够好**。代理缺乏必要的工具、抽象和内部结构。团队领悟到：当 AI 失败时，不要问"怎么让它更努力"，而要问**"缺了什么能力？怎么让它对代理既可见又可执行？"**

采用**深度优先（Depth-First）**策略：把大目标拆成小模块，让代理先构建基础模块，再用基础模块解锁更复杂的任务。人类几乎完全通过提示（Prompt）与代理交互—描述任务，代理提交 PR，人类审查。

**战略断言：企业为什么必须重仓"治具派"？**
Martin Fowler 将治具派的精髓总结为：**成功的 AI 代码不是靠无限自由度，而是靠约束解空间（Constraining the Solution Space）**—用特定的架构模式、标准化结构和强制边界，换取可维护性和信任。
对于寻求技术护城河的企业而言，**治具（基础设施与上下文编排）才是真正的资产，是对抗大模型更迭的最佳防御。** 不要和基础模型对赌，但必须建立自己的"特制流水线"。

但同一时间，另一个团队正在把代理工程推向更激进的境地。

---

## 跃迁 4/4 — 激进派：Boris Cherny "工厂正在学会自我进化"

2026 年 2 月，Claude Code 创始人 Boris Cherny 在 Y Combinator 圆桌上分享了一组震撼数据：

| 指标 | 数据 |
|:---|:---|
| Boris 个人代码 AI 生成比例 | **100%**（"我把 IDE 都卸了，不再手写任何一行代码"） |
| 每人每天 PR 数量 | **20 个**（对比 OpenAI 的 3.5 个） |
| Anthropic 人均工程产出变化 | Claude Code 推出后 **+150%**（"在 Meta 时 2% 提升就需要几百人干一年"） |
| Anthropic AI 生成代码比例 | 公司整体 **70–100%** |
| Steve Yegge 的评价 | Anthropic 工程师平均生产力是"Google 巅峰工程师的 **1000 倍**" |
| CLAUDE.md（= AGENTS.md）起源 | 用户自发写 markdown 让 agent 读取—产品只是把这个行为**收拢为功能** |

**代理拓扑（Agent Topologies）—超越"一个人管一群代理"：**

Boris 描述了一个惊人的案例：团队给 Claude 一个规范（Spec）和一块 Asana 看板，**Claude 自己在 Asana 上创建了 ticket，然后 spawn 了一堆 sub-agents，agents 开始自行认领任务**。Plugins 功能几乎由这样一个 agent swarm 在一个周末"跑出来"，几乎无人工干预。这不再是"一个人管一群代理"—而是"代理管理代理"。

**Boris 的三条激进判断—代理工程的前沿：**

1.  **"不要和模型对赌（Never Bet Against the Model）"**—你今天搭的脚手架，六个月后就会变成技术债。六个月前的代码"几乎没有一行还保留着"。代码的保质期（Shelf Life）只有几个月

2.  **指令要极简**—Boris 自己的 CLAUDE.md 只有两行。模型变强后，需要的指引越来越少。Plan mode 可能一个月后就消失—它本质只是 prompt 里加一句"先别写代码"

3.  **Agent 正在学会自建工具**—工程师 Daisy 没有直接给 Claude Code 加功能，而是先加了一个"让 Claude 测试任意工具"的工具，然后让 Claude **自己写自己的工具**。这不再是人类建工厂—而是让工厂学会改造自己

纪律派说"要有规矩"，治具派说"要建工厂"，激进派说"工厂也是临时的"。三者的共识只有一个：**人类正在攀爬抽象阶梯，每一步都比上一步更远离代码本身。**

## 跃迁 4/4 — 代理工程的行业冲击：从技术范式到组织重构

代理工程不只是一种新的编码方式—它正在重塑整个软件行业的结构。

**ThoughtWorks 2026 年 Looking Glass 报告** 将"为代理重新布线（Rewiring for Agents）"列为核心趋势：企业必须重建工作流和数据孤岛，让代理能够跨组织访问信息，并配备透明度、护栏和持续改进机制。报告指出：为人类开发者设计的现有实践正在**"以可预测的方式崩溃"**。五大战略方向：AI 优先的软件交付、为代理重新布线、意图驱动的交互设计、AI 就绪的数据生态、负责任 AI 的基础治理。
**Anthropic 经济研究**（anthropic.com/research）估算：当前一代 AI 模型可以将美国劳动生产率年增长提升 **1.8 个百分点**——相当于**近十年增速翻倍**。在实际 Claude 对话中，AI 将任务完成时间平均缩短 **80%**。先行组织的研发人均产出出现了 +150%（Anthropic 内部）的惊人跃升。

**财务视角的残酷颠覆：从人力成本（OPEX）到算力成本**
随着代理自主操作次数翻倍（半年前 10 次 → 现在 20次），并开始引入并行的"Sub-agents"处理复杂任务（Test-time compute），单兵工程师的效率被无限放大。
- **过去：** 规模=人头。企业为扩大产能，唯一的路径是线性增加高薪的传统开发工程师（占OPEX极大比重）。
- **现在：** 规模=算力+统筹者。成本中心开始向 API Token 消耗账单（如 Claude 4.5/5 推理成本）和 AgentOps 监管工具（追踪、评估）转移。这是彻底的降本增效拐点。

**先行者与后来者的鸿沟正在拉大：**

| 维度 | 先行者（创业公司 / AI 原生团队） | 后来者（传统企业） |
|:---|:---|:---|
| 交付周期 | 小时级（Agents 并行工作） | 周级（传统流程） |
| 人均代码产出 | 10–20 个 PR/天 | 1–2 个 PR/天 |
| 核心竞争力 | Agent 编排能力 + 规范质量 | 个人编码技巧 |
| 组织形态 | 极少架构精英 + 多面手通才（Super Generalist） | 臃肿的单职能团队（纯前端/后端） |
| Claude Code 使用占比 | 创业公司 **33%** | 企业 **13%** |

**尚未回答的问题与管理层的应对：**

- **安全**：Anthropic 报告将"双重用途风险（Dual-Use Risk）"列为关键趋势—代理越强大，攻击面越大
- **治理**：谁为代理生成的代码负责？当 Agent 做了错误的架构决策，责任在建造治具的人、写规范的人、还是模型本身？
- **人才选拔的新标准（给管理者的建议）**：当编码技巧不再是核心竞争力，传统的经验导向面试将失效。未来的核心选人标准是**"新手心态（Beginner Mindset）与第一性原理思考"**。未来的面试题将不再是写红黑树，而是考察："给我一个你曾经错了的例子，以及你是如何放弃旧经验，利用 AI 重新出发的？"

> **Takeaway：** 代理工程不只是"程序员怎么写代码"的问题——它正在重新定义**"软件组织应该长什么样"**。先行者与后来者之间的差距已从百分比级别扩大到**数量级差距**。这不再是"要不要用 AI"的选择题，而是"你的组织能不能为代理时代重新布线"的生存题。而这一切仍在发散探索中——方向不可逆，终局未定。

## 四次跃迁，一条完整的逻辑链

```
    跃迁 1                跃迁 2                跃迁 3                跃迁 4
  Agentic Workflow  →   Vibe Coding     →   Spec-Driven Dev   →  Agentic Engineering
  代理工作流              氛围编码              规范驱动开发           代理工程

  "AI 可以自主工作"  →  "放手让它干"    →  "不行，得有规范"  →  "编排代理，而非编写代码"

      觉醒           →      狂热          →       约束          →        编排
```

**人类角色：管理者 → 验收官 → 架构师 → 编排者**

这不是四个孤立的事件——而是一条因果链。没有代理工作流的觉醒，就不会有 Vibe Coding 的狂热；没有 Vibe Coding 的灾难，就不会有规范驱动的约束；没有规范的基础，就不会有代理工程的编排。

**注意第四次跃迁与前三次的本质区别：** 前三次已经"盖棺定论"——行业有明确共识。第四次仍在"百家争鸣"——三个学派在同一方向上各执己见，终局未定。

## 控制权的辩证法

### 正题（2024）：觉醒

Andrew Ng 证明了 AI 可以像团队一样自主工作。我们看到了可能性。

### 反题（2025 初）：狂热

Karpathy 说"别管代码了"。我们放弃了控制。结果——资深开发者反而更慢、缺陷率翻倍、知识生态瓦解、认知债务堆积。

### 合题（2025 末–2026）：编排——一个仍在展开的答案

我们用规范（Spec）约束意图，用治具（Harness）约束行为，用纪律（Discipline）约束流程——**在更高的抽象层重建了控制权**。不是写代码来控制 AI——而是编排代理、设计环境和规则来引导 AI。

但这个"合题"本身还没有定论。Osmani 说"要有纪律"，OpenAI 说"要建基础设施"，Boris 说"连基础设施都是临时的，代码保质期只有几个月"。他们唯一的共识是：**人类正在攀爬抽象阶梯，而这个阶梯还没有顶。**

这不是经典辩证法里那种"大团圆"的合题——而是一个**开放式的合题**。螺旋还在上升，终局未定。

> **这四次跃迁讲述了同一个故事：**

> **人类发现 AI 可以自主工作 → 兴奋地放手 → 被现实教训 → 在更高的层面重建秩序。**
>
> **前三次跃迁已经盖棺定论。**
> **第四次还在发散——纪律、治具、激进三派各执一词。**

>

> Boris Cherny 说："最重要的能力是新手心态（Beginner Mindset）——承认自己错了，然后重新出发。"
>
> **在这个代码保质期只有几个月的时代，**
> **唯一不会过期的，是你学习新事物的速度，**
> **以及在不确定性中做出判断的勇气。**
