# Fable 5 资料库计划

> 这份文档不是人物资料，也不是来源池地图。
> 它记录的是当前这套资料库背后的思路、筛选标准、扩展顺序和落地计划，方便后面继续做时不跑偏。

---

## 1. 这套资料库到底要做什么

当前 `sdlc_hacker_fable5/` 要做的，不是泛泛收集“大家都说 Fable 5 很强”，而是建立一套可持续扩展的资料库，用来回答下面几个问题：

- 哪些非模型公司、应用团队、个人开发者，真的在用 Fable 5 干活
- 他们具体把 Fable 5 放在工作流的哪个位置
- 他们说出来的“感觉”到底是什么，是爽感、是效率、是边界变化，还是组织分工变化
- 哪些材料只是热闹，哪些材料可以沉淀成长期有价值的人物 / 公司样本

这意味着资料库的目标不是“新闻摘要”，而是“人物与组织样本库”。

---

## 2. 当前已经明确的方向

### 2.1 不再以模型公司为主轴

一开始容易自然滑向 `Anthropic`、`OpenAI`、Claude Code 团队本身，因为这些材料最密、最容易拿到。

但这条线虽然有意义，不应该再是资料库的新增重点。原因很简单：

- 模型公司自己的说法，本来就容易被持续跟踪
- 真正稀缺的是外部使用者怎么把 Fable 5 塞进自己的真实工作流
- 更值得保留的是“应用公司 / 非模型公司 / 中腰部硬货作者”的一手经验

所以，后续新增样本时，优先级应该是：

1. 非模型公司
2. 应用团队
3. 明确讲 Fable 5 用后感或工作流变化的人

### 2.2 必须尽量聚焦 Fable 5

这套库目前是 `fable5`，不是泛 agentic 库，也不是泛 Claude Code 库。

所以新增材料时优先保留：

- 明确提到 `Claude Fable 5`
- 明确是 Fable 5 上手之后的工作方式变化
- 明确有任务边界、角色变化、成本判断、风险判断

而这些材料要谨慎处理：

- 只有 `Claude Code`，但没有明确 Fable 5
- 只有 `Codex`
- 只有“AI agent 很强”这种泛表述

这类高价值但非 Fable 5 专属的内容，不应该硬塞进这里，而应该分流到 `sdlc_hacker_agentic/`。

## 3. 当前已经形成的资料结构

每个值得保留的样本，默认按 `run_公司_名字/` 建目录。

目录内部尽量统一为：

- `profile.md`
- `sources.md`
- `quotes.md`
- `raw_*.md`
- 必要时再补 `analysis_*.md`

这样做的目的不是好看，而是为了后续可以稳定扩展：

- `profile.md` 负责回答“这人是谁，为什么值得留”
- `sources.md` 负责回答“证据从哪来，还有什么缺口”
- `quotes.md` 负责保留最值得复用的原话和判断
- `raw_*.md` 负责保存一手材料，不让库退化成二手摘抄

## 4. 当前的筛选标准

### 4.1 什么样的人值得单列

- 真的在用 Fable 5 干活
- 不只是说“震撼”“好强”，而是讲清楚任务形态
- 最好能说明：
  - 什么时候开 Fable 5
  - 什么时候不开
  - 它替代了什么
  - 它没有替代什么
  - 它带来了什么边界或角色变化

### 4.2 什么样的材料不值得单列

- 纯转述媒体
- 只有评测结论，没有 workflow 细节
- 只有 demo，没有真实任务
- 只有营销口径，没有一手痕迹

### 4.3 什么样的样本特别值得保留

- 中腰部但很硬的人，不一定最有名
- 讲 trade-off 的人，而不是只吹的人
- 能讲清任务边界的人
- 能讲风险、保密、成本、延迟、验证的人

## 5. 当前我对来源池的判断

### 5.1 最该长期盯的池子

当前最值得长期盯的几个来源池，排序如下：

1. `Every`
2. `Simon Willison`
3. `GitHub Issues / PR / Discussions`
4. `Hacker News`
5. `LessWrong`

### 5.2 为什么是这个顺序

#### Every

`Every` 不是普通媒体，它更像 AI-native 团队把自己的 workflow 公开出来。

它的优势是：

- 有组织级样本
- 有多角色视角
- 有后续连续更新
- 一篇文章经常能扩成多个人物目录

#### Simon Willison

Simon 这类独立博客的价值在于：

- 是自己真测
- 会写具体任务
- 会写具体 bug
- 会写具体命令和工具行为

#### GitHub

GitHub 的价值在于它最接近“证据链”：

- 有 issue
- 有 PR
- 有 commit
- 有明确动作痕迹

如果能在这里找到 “Action by Claude Fable 5” 这类信息，价值通常非常高。

#### Hacker News

HN 更像雷达站：

- 能快速看到高手在关注什么
- 能知道当前争议在哪
- 能知道外部链接里什么被反复提到

但它不适合作为人物资料正文来源。

#### LessWrong

LessWrong 更像高密度分析池：

- 擅长系统卡、安全边界、限制分析
- 对“什么时候不用 Fable 5”特别有价值

但不一定每次都能直接沉淀成 workflow 样本。

## 6. 当前已经形成的样本逻辑

目前资料库里已经逐渐出现几种不同类型的 Fable 5 样本：

### 6.1 应用团队角色样本

这类样本的价值在于说明同一组织里，不同角色怎么用 Fable 5。

例如 `Every` 线里已经出现：

- 增长角色
- 平台角色
- 咨询角色
- 应用 AI 工程角色
- 产品 / builder 角色

这比只找一个“最强工程师”更有意义，因为它更接近真实组织。

### 6.2 独立开发者实测样本

这类样本最适合回答：

- 模型到底表现出什么新的行为特征
- 它在具体任务里和旧模型有什么不同
- 它是怎么主动推进任务的

### 6.3 边界 / 治理样本

有些样本之所以值钱，不是因为最会夸，而是因为最会划边界。

例如：

- 保密问题
- NDA 风险
- token 消耗
- 延迟和协作舒适度
- benchmark 强但不适合日常协作

这些样本非常重要，因为它们能防止整个资料库变成单向吹捧。

## 7. 后续扩展计划

### 第一阶段：继续把 `Every` 线补厚

原因：

- 已经挖出多个人物
- 来源连续
- 角色分工清晰
- 容易形成组织级视角

这一阶段重点不是再泛泛收集，而是把已出现的人物继续补厚：

- 增补更多一手原文
- 增补更多代表性句子
- 补齐他们彼此之间的角色差异

### 第二阶段：从 `Simon + GitHub` 扩到其他非模型公司

这一阶段重点是从来源池里继续找：

- 真正拿 Fable 5 做了工程动作的人
- 有 issue / PR / workflow 痕迹的公司或个人
- 能和 `Every` 形成对照的外部样本

### 第三阶段：建立“组织使用模式”的横向比较

当人物样本积累到一定程度后，可以考虑单独整理：

- 哪些团队把 Fable 5 用在长任务
- 哪些团队把 Fable 5 用在修复和 review
- 哪些团队把 Fable 5 放在中间执行层
- 哪些团队因为成本、延迟、保密原因只部分使用

这一步不急，但它会让资料库从“人物集合”变成“方法模式库”。

## 8. 实际执行时的工作顺序

后面继续扩时，建议每次都按这个顺序来：

1. 先看 `fable5_source_pool_map.md`
2. 决定这次从哪个来源池开挖
3. 只筛明确和 Fable 5 相关的高信号样本
4. 先判断值不值得立目录
5. 值得的话再建 `run_公司_名字/`
6. 至少补 `profile.md`、`sources.md`、`quotes.md`
7. 尽量落一份 `raw_*.md`
8. 如果发现它其实不是 Fable 5 专属，而是泛 agentic 高价值样本，分流到 `sdlc_hacker_agentic/`

---

## 9. 当前的核心原则

后面不管怎么扩，都尽量不要丢掉这几个原则：

- 不把人物混写成一锅
- 不只收观点，尽量收原文
- 不只追顶流，也追 Bob/Joe 型硬货作者
- 不把模型公司当新增重点
- 不把泛 agentic 内容硬塞进 Fable 5 库
- 不只保留“爽感”，也保留边界、代价和限制

---

## 10. 现在最值得做的下一步

如果紧接着继续做，当前最合理的下一步是：

- 继续沿 `Every` 线补厚
- 同时顺着 `Simon + GitHub + HN` 扫下一批非模型公司样本
- 新样本依旧只保留“明确 Fable 5 用后感 / workflow 变化 / 工程痕迹”的对象

换句话说，下一阶段不是重新改结构，而是按这套结构稳定扩张。
