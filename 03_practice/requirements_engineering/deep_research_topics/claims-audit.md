# Claims Audit — 原文高流量断言的证据强度审查

> **目的**：原文 [User Story vs EARS 深度比较.md](../raw_dr/User%20Story%20vs%20EARS%20深度比较.md) 带有**明显偏向 EARS** 的立场，并引用了若干**精确到小数点**的数字与**厂商白皮书**级结论。直接沿用这些断言做 Deep Research，会让下游报告的**精度上限被原文封顶**，并继承原文立场偏差。
>
> 本文件对 **10 条高流量断言**做证据强度标注，供 DR agent / 研究者在引用时参考。

## 证据强度分级

| 级别 | 含义 |
|------|------|
| **A. 同行评审学术文献** | 可作为较强证据，但仍需看样本量与重复实验 |
| **B. 行业共识 / 多方独立来源** | 有多家非利益相关方交叉验证 |
| **C. 单篇学术文献 / 会议论文** | 可引用，**需明确单一来源**，不等于行业共识 |
| **D. 厂商白皮书 / 案例研究** | 有利益相关，应视为**营销叙事**，需独立复核 |
| **E. 博客 / Medium / Reddit** | 观点表达，不构成证据；可作为"行业叙事"参考 |
| **F. 行业隐喻 / 作者主观** | 修辞性描述，不可当作事实断言 |

## 10 条断言审查

### 1. "EARS 在系统工程界优于 User Story"

- **原文位置**：§1 引言、§9 结语反复出现
- **证据强度**：**F**（作者立论，非事实断言）
- **解读**：这是本文的核心**论点**，不是可独立验证的事实。原文结语其实也在承认二者**互补**，但标题与引言选择了对抗性表述以获注意力。
- **DR 建议**：将其视为**待论证命题**而非前提；在检索时明确排除"如何证明 EARS 更好"类单向查询。

### 2. "ChatGPT 需求解析准确性 +59.17%、Gemini +26.07%"（§6.2）

- **原文引用**：[33] ResearchGate: *Exploring the Use of LLMs for Requirements Extraction from User Stories*
- **证据强度**：**C**（单篇文献，ResearchGate 预印本性质）
- **风险**：
  - 小数点两位精度暗示**大样本严谨实验**，但需核对实际样本量、评审者信度、baseline 定义。
  - "结构化提示词"与"EARS"并非同一物，原文做了**等价跳跃**。
  - ResearchGate 往往是预印本，未必经过同行评审。
- **DR 建议**：引用时明确标注"据单篇文献 [33]"；不要做"EARS 提示词让 LLM 准确率提升 59%"这类强命题。

### 3. "CR 0.94 vs 0.81 / DD 0.63 vs 0.91 / DL 0.15 vs 0.20 / Velocity 31.8 vs 26.8"（§6.3）

- **原文引用**：[37] MDPI: *Comparing Measured Agile Software Development Metrics ... sMBSAP vs Scrum Only*
- **证据强度**：**C**（单篇 MDPI 期刊文章，准实验）
- **风险**：
  - 10 个 Sprint 的准实验**样本很小**、单团队，外部效度有限。
  - **sMBSAP ≠ EARS**：sMBSAP 是"敏捷模型驱动系统架构流程"，原文把它当作"EARS 类结构化规约"的代理，存在**概念替换**。
  - MDPI 期刊在不同学科的同行评审严格度不均。
- **DR 建议**：可引用，但须说明"单篇 MDPI、小样本、sMBSAP ≠ EARS"；寻找**复现研究**或多团队数据作为补强。

### 4. "AI 自动化审查削减 50–75% 评审时间"（§8.3）

- **原文引用**：[48] QRA: *Automating the INCOSE Guide for Writing Requirements*
- **证据强度**：**D**（QRA 是 QVscribe 的厂商自家白皮书）
- **风险**：厂商自述数据，样本选择偏差极大。
- **DR 建议**：标注为"QRA 厂商白皮书声称"；检索独立第三方评测或客户实证报告。

### 5. "单个大型项目节省 15 万美元返工与沟通成本"（§8.3）

- **原文引用**：[50] INCOSE Texas Gulf Coast Chapter 2021 meeting slides
- **证据强度**：**D**（工具供应商在行业协会会议上的宣讲 slides）
- **风险**：会议 slides 往往为产品宣传目的，缺乏方法论透明度。
- **DR 建议**：引用时降格为"某企业案例声称"；不作为普遍结论。

### 6. "User Stories Are Dead. Long Live User Prompts!"（§6.1 基调）

- **原文引用**：[29] Erez Morabia, Medium 博文
- **证据强度**：**E**（Medium 博客观点）
- **风险**：标题党属性强；原作者观点，不具代表性。
- **DR 建议**：作为"行业叙事的一种声音"保留，不作证据。

### 7. "TDD is Dead"（§7 开篇基调）

- **原文引用**：[38] Roost.ai 博客
- **证据强度**：**E**（厂商博客 + 标题党）
- **风险**：
  - Roost.ai 是生成式测试厂商，"TDD 死、USDD 生"的立论本身服务于其产品叙事。
  - David Heinemeier Hansson 有更早的 "TDD is Dead"（2014）论战，但语境完全不同；原文引用存在**语境错置**。
- **DR 建议**：引用时明确厂商性质；不作为 TDD 状态的证据。

### 8. "EARS 与 Gherkin 之间存在完美同构映射，可零人为干预、零语义损耗转为 Cucumber 脚本"（§7）

- **原文引用**：[9][27] conductofcode 博客与 Inflectra.ai 文章
- **证据强度**：**D**（博客 + 厂商）
- **实际情况**：
  - **结构**同构（While/When/If vs Given/When）是真实的。
  - "零语义损耗" 是**过强表述**：现实中 EARS 的复合模式、Optional、复杂响应需要人工设计 step definitions。
- **DR 建议**：接受"高度同构、可工程化转换"，拒绝"零语义损耗"这种绝对化表述。

### 9. "用户故事是房间装修指南，EARS 是建筑工程蓝图"（§9 结语）

- **证据强度**：**F**（作者原创隐喻）
- **解读**：教学效果好，**但不是事实断言**。在 DR 报告中使用时应说明为"本文的类比框架"，避免作为行业共识引用。
- **DR 建议**：当作**教学锚点**而非结论；在批判性综述中可引用以呈现作者立场。

### 10. "大模型依赖自身权重概率分布猜测，即发生严重的逻辑幻觉"（§6.1）

- **证据强度**：**E→C 之间**（观点 + 部分学术支撑）
- **实际情况**：
  - "LLM 在模糊输入下幻觉加重" 有多篇实证支撑（如 Liu et al. on hallucination taxonomy），是**弱共识**。
  - 但原文直接把 "User Story 留白"与"幻觉"因果挂钩，**缺少控制变量实验**。原文 [33][36] 触及但未等同。
- **DR 建议**：表述改为"模糊自然语言输入倾向于放大 LLM 幻觉（多项实证支持），但 User Story 格式与幻觉之间的**因果链**尚需单独论证"。

## 汇总：原文证据强度分布

| 级别 | 条目数（本审查 10 条中）|
|------|------------------------|
| A（同行评审 + 行业共识）| 0 |
| B（多方独立来源）| 0 |
| C（单篇学术）| 2（[33]、[37]）|
| D（厂商白皮书）| 3（[9/27]、[48]、[50]）|
| E（博客 / Medium）| 2（[29]、[38]）|
| F（作者立论 / 隐喻）| 3 |

**结论**：原文**没有任何一条核心断言**达到 A 或 B 级证据。这不意味着原文错，但意味着——

> **做 Deep Research 时，所有"精确数字 / 绝对化表述 / 对比性结论"都应当被独立补证，而不是作为前提直接采信。**

## 在每个 Topic 中的使用建议

- **Topic 2 / 3**：教程部分（格式、模板、模式表）大多为**行业共识**（B 级），可直接用；断言性、对比性描述需对照本文件。
- **Topic 4**：§1–3 的现状部分几乎全部涉及 C/D/E 级来源，**必读本审查**。§4 前瞻维度是新增内容，未沿用原文数字，但同样需要下游 DR 独立补证。
- **Topic 5**：§9 矩阵本身是**作者综合判断**（F 级）；可作为选型起点，但每一行都应在本地项目语境下**重新打分**。
