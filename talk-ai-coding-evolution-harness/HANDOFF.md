## 八、已知陷阱（最容易做错的地方）

| # | 陷阱 | 正确做法 |
|---|---|---|
| 1 | **Pi 有没有 MCP** 有两个版本在打架 | 采信有源码锚点的一方：`pi-mono/_digested/harness/02-Boundaries/2.2` 做过源码级核对——**无 MCP/ACP 实现**。讲"生态锁在自家 extension API，外部工具要付适配层税"，**不要把那个未合并的 PR 当已 GA** |
| 2 | Pi 的"无沙箱"怎么说 | **不说"不安全"**。说"**Pi 把信任放在『谁装了它』，而不是『它是什么代码』上**"。并区分"沙箱执行工具"（有思路）与"沙箱运行扩展代码"（无机制） |
| 3 | Codex 的数字口径 | 是 **⚠️ 厂商自述**，无第三方审计；且一手原文是"**输出** token 少 6 倍"。同屏必须标证据强度 |
| 4 | 8-harness 对照实测 | **⚠️ 趋势级**，来源是快讯类、无方法论文档。只作方向性信号，**不作基准** |
| 5 | Pi 星数 / DSH 插件数 | 都是**会漂移的值**，标观测日期，只作趋势；DSH 的 2000 / 3000 来自不同第三方商店，**口径不可比，不要合成一个数字** |
| 6 | DSH 的机制表述 | **DSH 的原生机制不是 MCP**。说 `ctx.llm` adapter、`ctx.tools`、capability seam、plugin |
| 7 | 2026 授权事故 | 只讲**因果链**（授权为何必须在执行端），不点名厂商、不堆 CVE 编号 |
| 8 | 四条"本 talk 的判断" | 瓶颈从生成移到交付 / Loop·Graph 补不上运行边界 / 同一模型换 harness 就是两套系统 / 团队里那圈最容易散 ——**讲述时要认领（"我的判断是……"），不要假借上游报告背书** |

## 十、用户怎么协作（这一条很重要）

- **他先要思路，不要成品。** 问"怎么做"之前，先把叙事/判断讲清楚，让他过一遍。
  他会明确说"我们大概过一下看叙事怎么样"。
- **他喜欢表格化、结构化的说明**，喜欢方案对比再给推荐。
- **他会给方向性纠正，且纠正往往比原方案好**。比如：
  "别提 OPC 免得让人困惑"、"不要点行业，换观众我还得改"、
  "别只有轮廓，内容太少了"、"两边素材都得有"。
  **收到这类纠正时，先想清楚它背后的一般化原则，再改，不要只改字面。**
- **他会直接说"继续往下做"**，此时按你的建议值推进，并在文件里标注"临时生效、可随时否决"。
- **用中文，语气轻松**。他看重"信噪比"——文档要干净。
