# 听众、时长与核心目的

## 听众（按特征定义，不按行业定义）

**做「团队协作开发、交付物对可靠性 / 合规 / 审计要求高、质量门槛高」的软件团队。**

- 组成：**产品经理 + 程序员**，都是给真实业务系统做研发的人，不是学生、不是 demo 玩家。
- 深度：**已有一定 AI Coding 基础**——用过 Claude Code / Codex / Cursor 一类工具，
  知道 prompt、context 大概是什么，但未必系统想过 harness 这一层。
- 推论一：**不做 prompt / context 科普**，那两层只讲"为什么它救不了你"。
- 推论二：**有产品经理在场**，机制必须落到 PM 也能跟上的表达——先给结论和后果，再给机制。

> **命名纪律**：稿子与上屏文字里**不出现听众所属行业名**，也不使用只在某个行业通用的说法。
> 目的是换观众时不用改稿。听众特征用"团队协作、质量要求高、要过审、要能查、要能还原"这类
> 通用描述来承载，让听众自己对号入座。

## 时长与形式

- **75–90 分钟，按 84 分钟排正文，实际约 85.5 分钟**（正文 45 页 + 4 张停顿页 I1–I4；无 demo）。
- 停顿页插在密集块之间（P8 / P17 / P20 / P34 之后），单句大字、留白 ≥60%、**不显示页码**，
  20–30 秒、念完即静默——**它们不承担新信息，只让听众把刚讲完的那块消化掉**。
- 结构：开场 5 + 第一幕 17 + 第二幕 20 + 第三幕 13 + 第四幕 16 + 第五幕 9 + 收尾 4。
- **尾巴（第三幕 → 收尾）22 页 / 约 42 分钟**，是这场真正的赌注所在。

## 核心目的

1. **把"瓶颈在交付、不在生成"讲成共识**——这是全场的问题定义，讲不清后面全部失效。
2. **把五层演变讲成一条因果链，而不是五个名词**。重点是让听众理解：
   前两层改不动"能不能上线"，Loop / Graph 会放大结果但不补运行边界。
3. **让 harness 变成一个可操作的概念**：模型给能力、harness 给可靠性；
   圈住 / 拦住 / 看清；提议权与执行权分开。
4. **认真地说清结论**：Coding Agent 的能力依赖底下的 harness——手上那些成品 harness 已经很强，
   但最近两个进展（可组合的 harness runtime）把 harness 从"产品的一部分"变成了"可以改的东西"。
5. **给出判断标准**，并诚实说出什么时候**不该折腾**。

## 一句话 pitch

- 题目（工作稿）：**AI Coding 演变指南：从 Prompt 到 Harness**
- 听众听完要带走的一个东西：**生成不是瓶颈，交付才是；而交付取决于那圈叫 harness 的东西——它是变量。**

## 讲述基调

- **专业、抓要害、有边界感**。不是炫技，不是产品推荐，不是合规讲座。
- **证据强度必须自己先打折**：这批听众会当场追问来源，主动标注"这是厂商自述""这是趋势级、没有方法论"，
  比被人挑出来更可信。
- **对称讲代价**：讲 Pi 和 DSH 时，优点与代价必须同屏。否则整场会被判成软广。

## 三个禁止

1. **禁止出现 OPC、一人公司、以及任何姊妹项目的引用。**
2. **禁止出现听众所属行业名与行业专属术语。**
3. **禁止讲成合规 / 安全培训**——圈住 / 拦住 / 看清是桥，终点仍是"AI Coding 演变 + harness 是变量"。
