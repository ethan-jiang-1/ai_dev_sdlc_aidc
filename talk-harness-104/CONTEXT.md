# 104 听众、术语与表达边界

## 听众与学习目标

业务熟、对AI有初步理解，已经动手搭Agent，希望以工程方式把它做稳。能理解流程和责任，不假定熟悉代码、分布式系统或运维。深入体现在工程设计的取舍与验证，不靠术语密度。

讲完应能画出自己系统的执行路径，区分模型判断与确定性控制，说明工具和状态的约定，设计一次失败恢复与一次版本验证，并确定允许动作、观察信号和停止/接手路线。

## 角色与词义

| 词 | 含义与边界 |
|---|---|
| 开发Agent | 协助设计、实现与验证系统的一方，不能和被开发的业务助手混称“它” |
| 工单助手 | 独立合成案例中的业务Agent，分类、检索依据、提出处理建议；获授权后才可创建内部任务 |
| Harness | 模型之外支持和约束Agent运行的工作环境；包含工具、权限、资料、规则、检查和状态 |
| 工程建设 | 将要求落实为可重复执行、可观察和可维护的系统机制，不以一次演示或更多文件作为完成证明 |
| 工具契约 | 输入、输出、错误、权限、副作用及重复调用行为的明确约定 |
| 幂等 | 同一操作重复执行，不重复产生同一业务副作用；须说明操作标识、保存位置与原子性，不能只靠提示 |
| 持久状态 | 中断后仍可查找和恢复的任务事实；与聊天上下文和模型推断分开 |
| 评估（eval） | 用任务、预期和判断方法检验Agent行为；与交付代码的常规测试互补，不以单次通过宣称稳定 |
| 回归检查 | 检查变更是否让原来正确的行为变差；对客优先说“检查原有行为是否退化” |
| 可观察性 | 从记录和指标知道做了什么、依据是什么、在哪失败及花费多少；记录必须控制敏感信息 |
| 隔离 | 限制不同任务的状态、权限和修改互相影响；独立上下文不等于独立权限或存储 |
| 人工门禁 | 有权者在明确条件下批准动作；模型自称批准、环境变量或普通文本不自动构成有效授权 |

## 讲法纪律

1. 主问题固定，封面副标题唯一为“Harness 104｜工程建设”。
2. 独立成篇，不在对客文字出现仓库路径、姊妹项目页号或内部研究目录名。
3. 自然专业中文，保留AI、Agent、Harness及必要接口字段，术语首次出现跟具体例子。
4. 单一案例逐步建设；每个工程动作说明输入、位置、输出/证据、失败和接手。
5. 确定性流程并不保证业务规则正确；模型灵活性不等于可任意修改流程、权限或验收标准。
6. 指令、技能、程序检查、权限和隔离各有证明范围，不宣称hooks绝对不可绕过。
7. 不把通用聊天记录当作持久状态；超时不代表工具未执行；重试必须考虑重复副作用。调用前原子占用次数并记可能在途状态，失败和崩溃也消耗额度；次数与计时跨重启保留，冻结标记约束实际派发。当前请求拒绝不证明先前操作无副作用；停写不等于撤回已受理请求。
8. 并行以任务独立、状态隔离及合并责任为条件；多Agent不是默认升级路线。
9. 代码测试与Agent行为评估分开；保留失败样本和正常样本，解释随机性、代表性及评估器局限。
10. 发布必须能定位模型、提示、工具、规则、数据和评估版本；告警阈值按任务约定，不照抄材料数值。
11. 回滚代码/配置不自动撤销业务副作用；外部补偿需另有授权和确认。
12. 合成案例未运行，不填伪造日志、准确率、收益或审批准据。供应商建议和本场教学设计明确区分。
13. 101、102、103及上游材料只读；不将104进度写进前三场或上游状态。
14. 工具能否并行先看实际输入依赖；历史版本留存用于追溯，不绕过受理时有效权限和事实/规则检查。政策判定时刻以案例源为准，不混同接收、分析、审批和执行时刻。
