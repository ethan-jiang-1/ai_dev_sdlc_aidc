# 文件接口｜PPT文案 v0.1（不上屏）

本文件是30页上屏候选池，不是逐字讲稿，也不是每页必须全部排入的清单。30页／60分钟为内容预算提案，未排练、未定稿；页号与时间以[逐页结构](<../03_outline/00-page-structure-v0.1.md>)为准。案例事实以[案例源](<../01_storyline/02-case-walkthrough.md>)为准，方法来源与主张强度见[来源台账](<../02_evidence/00-sources.md>)。

接口约定：L1为标题；L2为图示指令，仅供制页；L3为支撑文字；L4为页脚。每页的独立页背景、L2图示指令和制页说明全部位于off-screen注释内。外部文字才是上屏候选。优先级依次为L1、L3[必上]、落点[必上]、例子[例][必上]、必要脚注、L4；[可选]在空间不足时删减，不以缩字号强塞。例子[例][必上]保留承担本页职责的核心情境，正常输入、工具结果和失败条件不可全删；仅标[例]的补充例子可按版面选择。P1仅一个L3副标题；P15/P29是题目与条件，不排落点、评分提示或答案；主持答案唯一在03。

所有教学故事、字段、样本、事件板、恢复动作和发布方案均为合成设计，未实现、未运行。正文中的“预期”“应”是待验证要求，不是通过记录。没有实测日志、准确率、收益或真实审批凭据。来源借鉴不等于行业效果证明，字段不承诺特定产品兼容。本轮只交付文字，不制作PPTX、不实现系统。

通用制页原则：每页保留一个主要关系图和一条业务结论；必要术语当场解释；不做产品或工具目录。图形上的批准、受理、成功均标为教学条件或预期，不用绿色勾选冒充实测。隐藏区中的技术细节用于讲者理解，不自动转成正文。L4页脚仅为本页页码，不排口号、状态说明或仓库路径。

### P6

### P7
<!-- off-screen:begin -->
页背景：两个接口承担读与写对照，不列工具全目录。契约包含失败与重复语义；所有接口服务端验证范围。
L2图示指令：左右两张契约卡，各按输入、返回、失败、下一步排列；写卡下方另列授权和重复请求约定。
制页说明：少量伪字段辅助定位；字段不成为背诵目标。写接口不是模型直接持有的凭据。
<!-- off-screen:end -->
L1｜工具契约，要把失败也说清楚

[例][必上]｜读订单：输入经验证的关联订单；返回版本与关键事实；时间冲突返回 `DATA_CONFLICT`，由客服核实。

### P8
<!-- off-screen:begin -->
页背景：三类结果导向不同路径，FAILED_FINAL须有持久记录及无任务保证，不能由客户端猜测。
L2图示指令：请求之后分成功、明确失败、结果未知三路；未知路只连接查证，不直接连重试建单。
制页说明：成功只定义为内部任务持久创建，不延伸到业务解决。错误码不是全量枚举。
<!-- off-screen:end -->
L1｜成功、明确失败、结果未知，不能混记

L3[必上]｜成功：任务服务确认持久创建，取得原任务ID。
L3[必上]｜明确失败：权限或授权拒绝，或服务持久确认没有创建任务。
L3[必上]｜结果未知：请求超时、连接断开，或查询暂未得到确定结果。

[例][必上]｜请求超时 → 记为“执行结果未知” → 按原操作ID查证；不能记成“创建失败”。

落点[必上]｜下一步动作由证据决定，不由“看起来失败了”决定。

脚注[必上必要]｜只有服务保证没有创建任务的终态，才能作为明确失败；成功也不证明建议正确。

### P10

### P11
<!-- off-screen:begin -->
页背景：调用前崩溃与创建后崩溃必须拆开。客户端账本与outbox在同一数据库事务提交，不包含跨服务授权原子性。
L2图示指令：两条时间线：A保存后/发送前重启；B服务创建后/客户端回写前重启。客户端账本+待发送项框在同一边界内，服务端在另一边界。
制页说明：原子性用“一起保存或都不生效”解释；有效意图占位保护未决/成功，失败历史不删除。技术字段仅背景。
<!-- off-screen:end -->
L1｜先留下同一次操作，再把请求发出去

L3[必上]｜执行器先保存操作ID与待发送项：两项一起成功保存，或一起不生效。
L3[必上]｜发送前重启：恢复原待发送项；创建后尚未回写就重启：用原操作ID查询结果。
L3[必上]｜未决或成功的同一处理意图占住位置，阻止替代操作；历史失败仍保留。

[例][必上]｜保存 `OP-104-001` → 发请求 → 重启 → 仍加载 `OP-104-001`，不发明新标识。

落点[必上]｜客户端账本保住操作身份，但不能单独保证服务端不重复建单。

脚注[必上必要]｜恢复派发前仍检查授权与冻结状态；跨服务调用不是天然一个事务。机制未实现、未运行。

### P12
<!-- off-screen:begin -->
页背景：服务端必须兑现幂等与唯一业务意图；并发原子性、授权消耗及保留窗口都是待实现假设。
L2图示指令：两个同ID请求汇入服务端同一任务卡；异内容请求进入冲突；不同ID同意图请求指向已有任务/冲突。
制页说明：不让去重仅依赖模型提醒或客户端列表检查。记录保留期不编造天数，新尝试边界在脚注给出。
<!-- off-screen:end -->
L1｜幂等不是“提醒模型别重复”

L3[必上]｜幂等：同一操作重复执行，不重复产生同一业务副作用。
L3[必上]｜同ID、同内容 → 返回该操作已有状态和结果，成功才返回原任务ID；同ID、不同内容 → 冲突，不能当重试。
L3[必上]｜同一工单的有效售后跟进意图，最多创建一项内部任务；不同ID也不能绕过。

[例][必上]｜两个并发请求抵达任务服务 → 服务一起保存任务、结果和去重事实 → 其余请求取得原结果或明确冲突。

落点[必上]｜没有服务端创建与去重保证，就不能承诺自动安全恢复。

脚注[必上必要]｜去重事实覆盖任务生命周期与全部可能重试窗口。权威确认无任务且无在途创建后，人工批准有效审批下的新尝试，以新ID原子接管已释放的失败占位；保留旧记录，旧ID仍返回失败终态，成功占位不释放。

### P13
<!-- off-screen:begin -->
页背景：审批绑定建议/任务/输入，执行器派发前检查和服务受理时核验不同。跨服务技术保证可在背景说明，正文讲可理解条件。
L2图示指令：审批卡连接确切建议、任务正文、输入版本、范围和期限；受理点画闸门，撤回与有效受理按先后两支展示。
制页说明：教学假设审批服务提供可在受理时验证消耗的凭证；无法实现就人工建单。不要暗示远程查一次有效消除了竞态。
<!-- off-screen:end -->
L1｜批准的是这份内容，不是笼统地“让AI去做”

L3[必上]｜审批记录绑定：谁批准、哪份建议、完整任务内容、输入版本、允许动作和有效期限。
L3[必上]｜执行器派发前检查，任务服务在决定受理时再次核验；模型只能提出申请。

[例][必上]｜批准后修改任务正文或订单版本 → 尚未受理的创建不能沿用旧审批。
