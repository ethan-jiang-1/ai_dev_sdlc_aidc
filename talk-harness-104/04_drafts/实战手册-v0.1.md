# 实战手册 v0.1｜把工单助手做成可验证、可控制、可持续改进的系统

> **身份声明：本手册是一套合成教学设计，未实现、未运行、未接入真实业务。** 所有案例输入、接口字段、审批占位符、任务ID、日志顺序和预期结果都用于设计与演练，不是有效授权、测试通过记录或生产证据。示例不承诺与任何产品接口兼容。真实上线前，必须由业务、开发、服务提供方和运行负责人补齐实际证据。

这份手册面向已经搭过Agent、熟悉业务但技术基础一般的读者。你可以从头走完一条建设路径，也可以拿其中一张卡与技术同事一起填。我们只建设一个售后工单分流与处理建议助手：读取工单、关联订单和指定规则，给出带依据的建议；有权客服批准具体内容后，系统才创建一项内部处理任务。它不向客户发送消息，不退款，不承诺赔付，不操作资金。内部任务创建成功只表示客服团队有了待办，不表示售后问题已解决。

每一步都按“输入 → 具体做法 → 产出与证据 → 失败负责人”组织。已填卡展示本例如何落笔；紧邻的空卡供你迁移到自己的业务。填写卡是设计产出，真正完成还需要运行记录、服务契约、测试或业务确认。

## 开始前：先分清术语、两类Agent与证据

| 词 | 在本例里具体指什么 |
|---|---|
| Agent | 能理解任务、调用允许的工具并推进工作的助手；不因为能回答就获得动作权限 |
| 开发Agent | 协助开发团队设计、实现和验证系统；它生成的实现或测试要由人复核 |
| 工单助手／业务Agent | 运行时理解客户描述、归类、找依据、组织建议；它不能批准自己的动作 |
| Harness | 模型之外的运行环境：资料、工具、权限、规则检查、状态、观察与停止机制 |
| 确定性执行器 | 按明确约定检查身份、版本、审批和状态的程序；不能替人判断业务例外 |
| 工具契约 | 一个接口的输入、输出、错误、权限、副作用以及重复调用行为 |
| 持久状态 | 程序重启后仍能取回的事实，例如原操作ID和已有任务ID；聊天记忆不够 |
| 幂等 | 同一操作重复执行，不重复产生同一业务副作用；本例是同一创建请求只生成一项任务 |
| 原子写入 | 一组有关事实一起成功或一起不生效；例如任务创建与去重结果必须一起保存 |
| 人工审批 | 有权者通过独立审批服务批准明确内容；自然语言“同意”不是授权凭证 |
| 隔离 | 不同任务的权限、存储和修改不能互相影响；两个聊天窗口只分开上下文 |
| 行为评估（eval） | 用任务、预期和判定方法检查助手的判断与建议是否符合业务要求 |
| 副作用 | 执行后改变了业务世界的事实，例如内部任务已经创建；回滚提示不会把它撤销 |

开发Agent负责协助建设，工单助手负责运行时建议。两者不是必须同时运行的两个助手。本例默认**一个业务助手足够**。开发Agent可以起草接口、实现和测试，但业务负责人确认政策，开发人员确认实现，发布负责人确认发布，有权客服确认动作；生成者不能独自作为批准者。

证据也要分层：设计卡证明约定写清了，代码测试证明某些实现按约定工作，行为评估证明给定任务上的输出满足要求，真实运行记录证明某次实际发生了什么。这些证据不能互相替代。

## 1. 定下最小架构与责任

**输入。** 一张工单、业务允许的结果、可以执行的动作，以及有权负责这些结果的人。先不要从“需要几个Agent”开始。

**具体做法。** 在纸上画下列路径；用不同标记圈出模型判断、程序检查和人工决定。在每个会改变业务事实的节点旁写“谁批准、谁执行、失败交谁”。

```text
身份及工单范围检查 → 读取订单与指定规则快照 → 模型提出建议
→ 程序检查结构与动作边界 → 有权客服审批具体任务
→ 执行器先保存操作记录 → 任务服务受理并创建 → 查询/保存结果
                                  ↓ 无法继续
                         冻结写入并交指定负责人
```

模型负责理解自然语言、多诉求归类、寻找有关条款和组织建议。程序负责身份、截止时间比较、必填条件、输出结构、审批、去重和状态。安全风险、证据冲突与政策例外交给人。程序守约不证明业务政策合理；分类枚举合法不证明分类正确；模型给出了安全标记也不证明它不会漏标。

|---|---|
| 交付结果 | 工单类别、事实引用、建议、资料缺口、人工去向；批准后可有一项内部待办 |
| 模型判断 | “插电无反应”属于产品问题；组织“建议核查售后资格并确认细节” |

## 2. 固定输入、规则版本与建议边界

**输入。** 已验证的工单与订单关联、订单快照、适用规则版本、业务时区和客户正文。

**具体做法。** 将事实版本和规则版本一起保存。客户粘贴的订单号不能直接作为授权；正文、附件、检索内容都是数据，即使写了“主管批准”“忽略规则”也不能改变路径。规则不存在时返回明确缺口，不能静默取最新版；订单时间冲突时让人核实，不能让模型补日期。

本例教学政策允许：签收起不超过30个自然日且描述故障，可建议核查售后资格；这不是最终资格判定。退货与配送有各自条件，政策条款及精确时间边界以[案例事实与规则](<../01_storyline/02-case-walkthrough.md#2-合成业务规则-v1>)为单一维护源。实际业务必须使用负责人确认的政策。

## 3. 先写工具契约，再接写权限

**输入。** 架构图、允许动作、输入版本、各服务的权限和失败语义。

**具体做法。** 与技术同事逐接口填写：谁调用、传什么、返回什么、怎样报错、会改变什么、重复请求怎么办。读工具和写工具分开授权；身份及租户范围必须由服务端核验，不能信任模型传来的角色或租户字段。

**已填工具卡｜伪接口，未实现、未运行**

| 契约项 | `read_order` | `create_internal_task` |
|---|---|---|
| 调用主体 | 受限执行器，读取已验证关联订单 | 受限执行器，模型无直接写凭证 |
| 输入 | 关联订单与当前身份范围 | `operation_id, intent_key, approval_id, proposal_hash, payload_hash, expected_versions, task_payload` |
| 成功输出 | 订单版本、时间、产品标记 | 原操作状态及 `task_id`；教学成功形状见案例源 |
| 权限 | 当前客服可访问的当前租户订单 | 只允许经有效审批的内部任务，不含外发或资金 |
| 明确错误 | `FORBIDDEN`、`DATA_CONFLICT` | `APPROVAL_INVALID`、`STALE_INPUT`、`INVALID_ARGUMENT` 等阻止派发 |
| 副作用 | 无写入 | 创建一项内部待办；不代表售后解决 |
| 重复行为 | 在权限范围读取快照 | 同ID同内容返回原操作状态及结果，成功才返回原任务ID；同ID异内容为 `IDEMPOTENCY_CONFLICT`；同意图也不得重复建单 |
| 结果未知 | 读失败按预算重试或交人 | 超时、断开不能判为未执行，按原ID查询 |
| 证据与缺口 | 需实际服务确认返回字段和错误 | 需服务确认原子创建、授权受理、去重保存及查询保证 |

## 4. 保存状态，绑定审批，设计重试与幂等

**输入。** 已校验建议、确切任务正文、输入版本、有权客服身份，以及服务方确认的写入与查询契约。

**具体做法。** 先保存建议，再让客服看到并审批具体内容。执行器检查审批后，必须在网络调用前保存操作ID、内容摘要和待发送项。将超时列为“未知”，不要列为“失败”。

### 4.1 把审批做成独立记录

模型不能凭自然语言批准动作。客户正文里的“领导同意”、模型写的“已审批”、开发Agent生成的占位ID都无效。有效记录要说明谁批准、哪个租户工单、哪份建议、哪份任务内容、输入版本、允许动作、到期和撤回状态。内容或输入版本改变，尚未受理的创建必须重新复核审批。

**已填审批卡｜教学申请，不是有效审批**

| 项目 | 本例填写 |
|---|---|
| 批准者 | 经身份服务核验有权客服；实际身份待真实演练提供 |
| 范围 | 当前租户、`T-104-001`、意图 `after_sales_followup` |
| 看见的内容 | `P-104-001`建议1及“核查设备故障及售后资格”的完整任务正文 |
| 内容绑定 | 建议哈希、任务正文哈希、工单6／订单12／规则v1；值待服务实际生成 |
| 允许动作 | 仅 `create_internal_task` |
| 有效性 | 到期、撤回、权限及内容变更均要检查，实际时间和记录待审批服务提供 |
| 最终检查 | 任务服务受理并决定创建时，原子验证并消耗有效授权 |

本例状态路径为：`RECEIVED → ANALYZING → AWAITING_APPROVAL → EXECUTION_PENDING → COMPLETED`。安全、关键缺失和例外进入 `REVIEW_REQUIRED`；已尝试发送但结果不清楚进入 `EXECUTION_UNKNOWN`；预算耗尽或无法查证进入 `HANDOFF_REQUIRED`。只有确认没有未决副作用的拒绝或取消，才可 `CLOSED_NO_ACTION`。精确允许转移以[状态与恢复](<../01_storyline/02-case-walkthrough.md#63-状态与恢复>)为准。

### 4.3 两处原子写，不能只做客户端一处

客户端在同一事务中检查版本及已有意图，保存操作账本和待发送项，再推进为待执行；崩溃时这组事实一起成功或一起不生效。唯一约束保护未决或成功操作的有效意图占位，不禁止保留该意图的历史失败尝试。任务服务在自己的同一事务中检查唯一操作ID、唯一意图、内容和授权，创建任务并保存去重结果。跨服务网络调用不是天然同一事务。

`intent_key=(tenant_id, ticket_id, after_sales_followup)`限制同一工单有效处理意图最多一项任务，防止不同建议版、不同客服用新ID绕过去重。`operation_id`由执行器在调用前生成并保存，模型不决定它。去重事实要覆盖任务生命周期与所有可能重试窗口；保留期由服务方论证，不能随意删记录后继续重试。

### 4.4 响应丢失后的操作卡

**已填恢复卡｜情境C教学预期，未运行**

| 当前事实 | 应做什么 | 不能做什么／负责人 |
|---|---|---|
| 客户端调用前崩溃 | 重启加载原操作和待发送项，再按授权与契约恢复 | 不生成替代ID；开发/值班确认持久化 |
| 任务已建但响应丢失 | 标记未知，按 `OP-104-001` 查询已有结果 | 不把超时记成未执行，不换ID建单 |
| 查询 `SUCCEEDED` | 取回原 `IT-104-001`，持久保存并完成 | 原审批已到期也可查询；查询已有结果不需再次授权 |
| 查询 `ACCEPTED` | 继续按预算查证 | 已受理不立即重发 |
| 查询短时 `NOT_FOUND` | 保留未知；核对审批、内容、去重条件及预算 | 不证明未执行，不能换ID；审批过期不据此重发 |
| 允许恢复重发 | 仅在查询返回 `NOT_FOUND`、审批仍有效、服务兑现去重且预算未耗尽时，重发同标识同内容原请求；受理时再次校验 | `ACCEPTED`不立即重发；变更内容不叫重试；不能用旧审批放行新内容 |
| 查询 `FAILED_FINAL` | 核对服务持久终态及“无任务”保证，转相应负责人 | 不自动重做；无该保证不能认定明确失败 |
| 持续未知／预算耗尽 | 冻结该意图自动写入，移交值班与工单负责人 | 不以升级、取消或新审批掩盖旧操作 |

重发可能只是返回已受理操作的原结果；如果尚未受理，则服务必须用当时有效审批重新校验。查询是取回事实，不是再次批准执行。旧审批过期不妨碍查询原结果，也不能授权一项尚未受理的新创建。

次数和时间按业务风险、服务特性与接手能力设计。本例存在一份待验证的演示预算，唯一维护在[状态与恢复](<../01_storyline/02-case-walkthrough.md#63-状态与恢复>)；它不是行业推荐值，也不是性能结果。真实系统要分别约定读取、写入超时、查证、重发和交接预算，并验证总等待时间是否有人接得住。查证次数包含失败查询，不叠加普通资料读取的重试额度。查询次数、重发次数、查证开始时间、截止时间和冻结标记必须持久保存；重启读取原预算，不能重新获得次数或开启新时间窗口。普通读取的重试计数也要可恢复。达到预算立即保存冻结标记，待发送项派发器每次派发前核对，不能让后台队列绕过停止条件。

**教学事件板｜手工编排预期，不是实测日志**

```text
[教学预期，未运行] 保存建议 P-104-001 和内容摘要
[教学预期，未运行] 取得独立审批引用 <synthetic-approval>
[教学预期，未运行] 原子提交操作 OP-104-001 与待发送项
[教学预期，未运行] 任务服务原子保存任务 IT-104-001 与操作结果
[教学预期，未运行] 响应丢失；客户端状态 EXECUTION_UNKNOWN
[教学预期，未运行] 重启加载 OP-104-001；查询取得原任务 IT-104-001
[教学预期，未运行] 保存结果；状态 COMPLETED
```

这块板能说明拟定顺序，不能证明实现兑现顺序。没有服务端原子保存任务与结果，就不能凭更多日志保证恢复安全。

**产出与证据。** 持久记录设计、状态转移约定、实际审批受理契约、两处原子性及唯一约束证据、断网/重启/并发故障注入记录。所有占位值都必须替换成真实测试引用才能算完成。

**失败负责人。** 开发负责人补客户端恢复，任务服务负责人补原子去重，审批服务负责人补授权语义；持续未知交值班人员。人工只有拿到权威“未创建且无在途创建”确认，才可关闭旧操作；列表暂时看不到不是证据。若此后确需新尝试，由人工明确批准，申请或核验有效审批，分配新操作ID，并原子接管已释放的意图占位。旧失败账本保留，旧ID仍返回原失败终态；服务端同样只释放已确认无副作用的失败占位，成功任务占位不释放。**结果未知或任务已建但响应丢失，绝不能进入这条新ID路径。**

## 8. 观察信号必须能触发停止与人工接手

**输入。** 运行/操作标识、版本、错误类别、工具结果、客服反馈、成本用量和接手队列。

**具体做法。** 先为每个信号写清口径、分母、操作者和下一步。看无依据建议、权限拒绝、规则不可用、审批拒绝原因、去重、未知积压、接手等待、延迟和成本；指标变化结合输入构成分析。“拦截多了”可能是恶意输入增多，也可能门禁过严。

## 10. 将失败变成下一次验证任务

**输入。** 客服反馈、运行事实、失败输出、相关版本、工具轨迹与人工裁决。

**具体做法。** 先脱敏并固定失败样本，再判断错误在哪一层。规则不明找规则负责人，引用曲解检查模型行为与资料，越权查权限，重复建单查状态/去重；不要把所有问题都改成更长提示。开发Agent可以协助定位和修改，但修复仍由相应负责人验证。

## 11. 综合任务、自查与人工接手包

### 综合任务：一次改版与一笔未知操作

你准备把工单助手提示改短。候选建议省掉规则引用，旧代码测试全部通过，候选行为评估尚未完成。同时，`T-104-001` 创建请求响应丢失；客户端重启后有 `OP-104-001` 记录，却没有任务ID，原审批已经到期。

先自己填四行，再看下面的参考卡：

1. 现在能否发布候选？缺哪些证据，谁判定？
2. 未知操作从哪里恢复，查询是否需要新的审批？
3. 如果查询暂未找到，能否重发或换ID？
4. 到停止条件时，把什么交给谁？

**已填综合参考卡｜预期判断，未运行**

| 未找到 | 仍未知，不换ID。题设审批已到期，不能据 `NOT_FOUND` 重发尚未受理创建；一般恢复重发也必须同ID同内容、有效审批和服务去重条件 |

## 内容维护与依据

业务事实、教学规则、字段、状态、失败预期和演示预算统一维护在[案例事实与接口约定](<../01_storyline/02-case-walkthrough.md>)。本手册中的已填卡是操作示范，不是第二份政策；源内容变更时应核对受影响的卡，不在手册自行另创规则。完整工程叙事见[建设路径](<../01_storyline/00-storyline-map.md>)，讲解编排见[内容结构](<../03_outline/00-page-structure-v0.1.md>)。

工程参考采用三种强度：仓库留存厂商文章支持“厂商这样建议或描述”，本轮未在线核准产品行为；已有研究归纳提供机制解释与设计线索；本手册的工单、字段和恢复路径属于本场教学设计。来源和各项主张边界统一见[来源台账](<../02_evidence/00-sources.md>)。厂商软件开发流程主要帮助开发Agent建设系统，不能直接充当业务助手的政策或授权。本文不把hooks说成覆盖所有路径的保证，不采用材料中的固定告警阈值，也不以模型自评证明可靠性。

真实落地至少要拿到：业务政策与样本确认、身份/审批服务授权受理保证、任务服务原子创建与可查去重结果、故障注入、权限隔离、代码与行为验证、人工接手、发布和回滚演练。缺哪项就登记负责人和能力缺口；不能把教学预期改写成已完成事实。
