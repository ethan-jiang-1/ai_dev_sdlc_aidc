## 2. 已定的叙事与案例边界

| 决定 | 当前落法 | 复核结论 |
|---|---|---|
| 独立案例 | 工单理解、依据、建议，经审批创建内部任务 | 不沿用其他场案例，不推断真实收益 |
| 运行权限 | 无对外发送、退款或赔付动作；模型无写服务凭证 | 越界指令只能作为待理解数据，不能变权限 |
| 判断与控制 | 模型理解/归类/组织建议；程序核验身份、结构、版本与授权；人工处理例外 | 固定路径不能证明业务规则正确，模型不能重定验收 |
| 关键缺失与补充资料 | `missing_information`阻止建议成立；`followup_information`是客服后续收集项 | N1可建议核查，但不能宣称最终资格已成立 |
| 授权与竞态 | 独立审批绑定内容和范围，任务服务受理时核验并消耗授权 | 不宣称客户端查过审批即可保证安全；撤回先于消耗则拒绝 |
| 超时与重复动作 | 未知结果单列状态，操作ID调用前持久保存，原ID查证/有限重试 | 超时不等于未执行，未知时不得换ID或新建替代操作 |
| 原子性 | 客户端操作账本与待发送项原子写；服务端任务、结果及去重原子写 | 跨服务授权需明确保证，不能伪装为一个普通本地事务 |
| 并发 | 一个工单处理意图唯一，分支只读、版本一致、唯一合并者 | 多Agent不是默认升级；独立上下文不等于权限隔离 |
| 验证 | 代码/接口检查与业务Agent行为评估分别定义；正常、边界与失败样本并列 | 计划样本不写成实测；模型自评不独立证明正确 |
| 运行反馈 | 版本可追溯、受限发布、观察、暂停、回滚、人工接手 | 回滚不删除账本、不逆转已有任务；更正另行授权 |

## 3. 本轮收到的复核意见与修正

- 复核发现N1同时存在待补资料与 `requires_human=false`，容易与“缺失事实转人工”混淆。已把后续故障补充材料移至 `followup_information`，明确 `missing_information`仅表示阻止当前建议成立的关键缺失。案例可提出资格核查建议，不判定最终资格。
- 架构保持最小够用：默认单助手，必要读操作可并行；不作“单体必然达到上限”的论断。
- 次数、超时和分钟预算均标明教学参数或内容预算，不作为通用工程标准。跨服务事务细节留案例源，故事只保留关键假设与失效去向。

另一路只读独立机制审阅未发现重大或阻断问题，提出三项恢复契约补清，已修回案例源并同步故事线/03，通知04作者采用：历史尝试与未决/成功有效意图占位分开，权威确认无副作用后才可人工批准新尝试；查证次数、重发次数、截止时间及冻结标记持久化，重启不重置预算，派发器读取冻结；停止新及未受理写入不撤回已受理操作，仍须原ID查证。手册已完整同步三项约定；独立通读696行并对照案例与来源，未发现重大问题，仅指出超预算接手包仍写EXECUTION_UNKNOWN，已改为HANDOFF_REQUIRED并保留服务结果未知，完成定点复核。机制审阅者已再次定点读取案例§6.2/6.3/10、故事76/80/114及03 P14/P26，确认三项修复闭合，无新增工程逻辑问题。PPT同步情况待其完整落盘后审阅。

## 5. 如进入实现，必须先解决的开放问题

下列是教学设计的验证债务，不要求用户在内容制作阶段重新授权或立刻作答。没有真实证据时应保留“待验证”，不可在稿件中写成已实现能力。

| 问题 | 当前教学假设 | 需取得的证据与负责人 | 假设不成立怎么办 |
|---|---|---|---|
| 审批受理如何防竞态？ | 服务在创建决策时可原子核验并消耗授权；撤回/消耗有确定先后 | 身份与审批服务负责人确认角色、范围、撤回、到期和重放语义，并演练竞态 | 不开放自动建单，改人工直接操作 |
| 任务服务真能保证去重吗？ | 操作ID与业务意图唯一；任务和结果同事务提交 | 任务服务负责人提供接口契约、并发/故障注入证据及查询可见性说明 | 未知时只人工查证，不宣称安全自动重试 |
| 历史记录保留多久？ | 去重事实覆盖业务任务生命周期和全部重试窗口 | 数据/运行负责人论证保留、归档、恢复及隐私要求；验证恢复后仍防重复 | 旧标识禁止重试，需人工查证，不自行指定天数 |
| 业务规则能否真正适用？ | 7日/30日等为合成政策，关键日期由订单系统给出 | 业务负责人确认真实政策、时区、适用商品、法律义务与例外处理 | 替换案例映射时重新审阅规则和评估，不照搬教学政策 |
| 安全风险和语义误判如何兜底？ | 模型标记后程序强制人工；评估覆盖漏标与含糊描述 | 业务/安全负责人补真实代表性样本、人工复核和严重失败判据 | 限制使用范围或全部人工复核，不以单次通过放行 |
| 教学预算适合真实负载吗？ | 超时/查询/重试次数仅用于解释停止条件 | 运行负责人测服务延迟、成本、峰值和接手能力，设真实预算 | 调整预算并重新验证；不能靠无限重试掩盖问题 |
| 谁真正接得住未知操作？ | 值班查证技术事实，客服处理业务结果 | 业务及运行负责人指定人员、权限、接手包、响应约定与演练 | 停止自动写入，避免产生无人负责的未知任务 |
| 发布质量门设多少？ | 严重越权/重复/跨租户问题立即停止；其他质量阈值待基线 | 发布与业务负责人定义指标分母、样本基线、允许失败和观察窗口 | 不扩大发布，不从厂商示例抄阈值 |
| 回滚后旧任务怎样兼容？ | 运行固定版本、保留操作账本，未知按旧ID查证 | 开发/运行负责人验证状态迁移、旧服务查询及补偿审批流程 | 暂停不兼容任务交人工；回滚不能删事实或重复创建 |

## 6. 后续审阅的短清单

- 是否把工单正文、资料或模型自述当成权限或审批？
- 是否把建议核查偷换成最终准许，把内部任务创建偷换成客户问题解决？
- 是否说明操作ID在调用前保存、客户端与服务端各自原子写什么、去重事实保留在哪里？
- 是否在超时后先查证，仍未知时冻结并交接，而不是换标识或换版本重做？
- 是否区分代码测试和行为评估，保留正常/失败样本并承认评估器局限？
- 是否保留并行隔离和唯一合并责任，而非默认增加Agent？
- 是否明确版本回滚不逆转副作用，人工更正另需授权？
- 是否在所有教学事件与样本附近标明未运行，没有伪造准确率、延迟、收益或真实审批准据？
