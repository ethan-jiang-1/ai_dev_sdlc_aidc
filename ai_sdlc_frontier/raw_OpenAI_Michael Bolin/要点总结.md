## 核心论断：Agent Loop 是最底层的战争

> *"每个 AI 智能体的核心都是 Agent Loop：协调用户、模型和工具之间的循环交互。"*

在 OpenAI 内部，Codex CLI、Codex Cloud 和 Codex VS Code 插件共享同一套 Agent Loop 框架。Michael Bolin 的系列文章是 OpenAI 首次对外公开这个框架的内部实现细节。社区评价：**"优秀的架构远胜于花哨的工具。"**

## Agent Loop 的四拍循环

```
用户输入 → 构建提示词 → 模型推理 → 
  工具调用？→ 执行工具 → 追加输出 → 重新查询模型
  助手消息？→ 返回用户 ✓
```

每一轮交互最终以一条 **assistant message** 收尾，标志着 Agent Loop 进入终止态。

## 提示词工程：用户的话放在最后

Codex **不直接**把用户输入发给模型。提示词按严格的优先级拼接：

| 顺序 | 内容 | 角色 |
|---|---|---|
| 1 | 模型专属指令（来自 `config.toml` 或内置） | system |
| 2 | 沙箱环境描述（仅限 Codex 内置 Shell 工具） | developer |
| 3 | 用户 `developer_instructions` 配置 | developer |
| 4 | `AGENTS.md` / `AGENTS.override.md`（多层叠加） | user |
| 5 | Skills 元数据 + 调用说明 | user |
| 6 | 本地环境信息（工作目录、Shell 类型） | user |
| 7 | **用户的原始消息** | user |

> 表述越具体的指令排序越靠后。用户的输入反而放在最后。

## 缓存策略：O(n²) → O(n) 的工程艺术

### 问题
每轮 API 调用发送**完整对话历史**，JSON 负载随对话轮次呈二次方增长。

### 方案
**依赖提示词缓存，而非 `previous_response_id`。**

OpenAI **故意弃用** `previous_response_id` 参数，选择让每次请求完全无状态——这是为了兼容 **Zero Data Retention (ZDR)** 隐私合规。

### 缓存命中的关键：精确前缀匹配

破坏缓存的元凶：
- ❌ 对话过程中修改工具列表
- ❌ 切换模型
- ❌ 修改沙箱配置或审批模式
- ❌ 修改工作目录
- ❌ MCP 工具枚举顺序不一致（已修 bug）

### 变更如何传达
不修改早期消息，而是**在输入末尾追加新消息**。比如沙箱配置变了 → 追加一条 `role=developer` 消息。

## 上下文压缩：自动 Compact

当 token 超阈值时自动触发：
- 早期版本需要手动 `/compact`
- 现在使用专用 `/responses/compact` 端点
- 返回压缩条目 + `encrypted_content` 字段保留语义
- **完全自动**，无需用户介入

## 核心教训

> **"缓存命中率决定 Agent 的实际性能。每改一个工具列表、每切换一次模型，都是实实在在的成本。"**
>
> **"用户的输入放在提示词最末尾不是 bug，是 feature——让静态前缀最大化缓存命中。"**
>
> **"所有 Agent Loop 的工程决策最终都回到一句话：保持前缀不变。"**
