# Fiona Fung：运营 AI 原生工程团队 — 要点总结

> 原文：*Running an AI-native engineering org*（Code w/ Claude SF 2026 演讲）
> 作者：Fiona Fung，Anthropic Claude Code & Claude Cowork 工程总监。前 Microsoft 11 年（Visual Studio, TypeScript），Meta 创始 Facebook Marketplace
> 日期：2026 年 6 月 3 日

---

## 核心论断：瓶颈转移了

> *"过去服务于你的流程，可能已经不再适用。"*

软件工程的一切流程（瀑布 → 敏捷）都建立在同一个前提上：**工程带宽是昂贵且稀缺的**。Agentic coding 让写代码、写测试、重构不再是瓶颈。

**新的瓶颈变成了三个东西：**

| 旧瓶颈 | 新瓶颈 |
|---|---|
| 写代码太慢 | **Verification** — 代码对不对？ |
| 人手不够 | **Code Review** — 人类跟不上 AI 的产出量 |
| 排期紧张 | **安全与信任边界** — 什么可以交给 AI？ |

---

## 四个被颠覆的工程规范

### 1. 规划：从六个月路线图 → JIT（即时规划）

六个月路线图到第三个月就过时了。现在：**原型 → 拉内测用户 → 根据反馈迭代**。

> *"Build is cheap. Argument is expensive."* — 与其争论文档，不如直接原型看效果。

### 2. 上下文获取：找人问 → 问 Claude

旧习惯：找到代码作者问。新习惯：**先问 Claude 你需要知道什么**。每次都追问一句：**"这个能自动化吗？"**

Fiona 每天早上手动看客户反馈的习惯，已被 Claude 自动化替代。

### 3. Code Review：人力全覆盖 → 信任但验证

| Claude 负责 | 人类负责 |
|---|---|
| 风格、lint、bug 检查 | 法律审查 |
| PR 反馈请求、补充测试 | 安全敏感代码、信任边界 |
| PR babysitting | 产品品味（product taste） |

"我让 Claude 给 CLI 加雪人主题，设计师说看起来像 Mr. Peanut——AI 没有品牌品味。"

### 4. 团队构成：固定角色 → 角色模糊

只重点招募两种人：
- **有产品感的创造性 Builder**（dreamers who ship）
- **深度系统专家**（如分布式系统）

**不再看重裸吞吐量** — 模型已经覆盖了这部分。PM 写代码，工程师做设计，边界在消融。

---

## 三条铁律

1. **疯狂 dogfood** — 全员（含非工程）每天用 Claude Code & Cowork
2. **组织尽可能扁平** — 每个经理必须先做 IC，通过交付理解工程师的日常
3. **允许且鼓励杀掉旧流程** — 任何人可以质疑任何流程，不合适就毙

---

## 三个信号判断新流程有效

| 指标 | 含义 |
|---|---|
| **入职 ramp time ↓** | 新人第一周就能交付真实代码 |
| **PR cycle time ↓** | 但要警惕 CI/构建系统成为新瓶颈 |
| **Claude 辅助提交率 ↑** | Fiona 近四个月没见过一个非 Claude 辅助的 commit |

> ⚠️ *"不要混淆吞吐量和成功。"* — 真正要衡量的是：你解决的问题对不对。

---

## 入门方法："最吵的工作流"练习

找到团队最痛苦、最昂贵、最让人畏惧的那个工作流，问三个问题：

1. **它还在服务于最初的目的吗？**
2. **如果是，AI 能自动化吗？**
3. **如果不是，直接砍掉行不行？**

经典案例：一个 50 人的周常状态汇报会，所有人低头看笔记本直到轮到自己发言。Fiona 问了一句"为什么我们还在开这个会？" — 全场沉默，然后取消了。
