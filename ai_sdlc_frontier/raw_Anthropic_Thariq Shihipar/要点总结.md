# Thariq Shihipar: Fable 5 使用指南 — 要点总结

> 原文：*A Field Guide to Fable: Finding Your Unknowns*（机器之心编译）
> 作者：Thariq Shihipar（Claude Code 工程师）

---

## 核心隐喻：地图 ≠ 疆域

| 地图 | 疆域 |
|---|---|
| 你的提示词、Skill、上下文——你交给 Claude 的东西 | 真正需要发生工作的地方：代码库、现实世界约束 |

**地图与疆域之间的差距，就是「未知项」（Unknowns）。** Claude 遇到未知项时，只能根据对你意图的最佳猜测来做决定。任务越复杂，未知项就越多。

> **Fable 5 是第一个让「澄清未知项的能力」成为工作质量瓶颈的模型。**

---
### 未知项的四象限（Rumsfeld 矩阵）

| | |
|---|---|
| **已知的已知** | 写在提示词里的内容，你明确知道自己要什么 |
| **已知的未知** | 你清楚自己还没搞清楚的事情 |
| **未知的已知** | 对你显而易见、你不会写下来，但一看到就能认出来的东西 |
| **未知的未知** | 你完全没考虑过的事；你不知道一件事能做到多好 |

> **减少并提前规划未知项，就是智能体式编程的核心能力。** 这是一项可以通过与 Claude 协作不断提升的技能。

---

## 黄金法则：帮助 Claude 就是帮助你自己

给 Claude 下指令是一种微妙的平衡：

- **过于具体** → Claude 严格照做，即使有更好的方案也不会转向
- **过于模糊** → Claude 基于行业最佳实践做假设，不一定适合你的场景

两种失败模式的根源相同：**你没有充分思考自己的未知项。**

Claude 可以帮助你更快发现未知项，关键是给它足够的起点上下文：你思考到哪一步了？你对这个问题和代码库有多熟悉？

## 实现前：五种发现未知项的模式

### 1. 盲点扫描（Blindspot Pass）
直接让 Claude 帮你找「unknown unknowns」。告诉它你是谁、你知道什么，让它解释你可能遗漏的东西。

> *"我做了一个 blindspot pass，帮我找出 unknown unknowns，让我能更好地写提示词。"*

### 2. 头脑风暴与原型
用于发现「未知的已知」——那些你看到才能认出来的东西。用 HTML 快速出多个方向，在代价变高之前先识别问题。**几乎每次编码会话都以探索/头脑风暴开始。**

> *"用假数据做 4 种风格差异很大的设计方向，我先反馈，你再去动真实代码。"*

### 3. 反问（Counter-questions）
让 Claude 采访你，一次一个问题，围绕歧义点追问。优先问那些会改变架构设计的问题。

> *"请一次只问我一个问题，围绕任何存在歧义的地方采访我。"*

### 4. 参考资料
当你无法描述想要什么时，直接给 Claude 指路：源代码文件夹、喜欢的网站模块、库的实现。**即使参考代码是另一种语言也没关系。**

> *"vendor/rate-limiter 里的 Rust crate 实现了我要的重试行为，读它，在我们的 TS 客户端里复现。"*

### 5. 实现计划
让 Claude 先出计划供审阅，**开头优先呈现最可能变化的决策点**（数据模型、类型接口、UX 流程），机械重构放最后。

---

## 实现中：持续记录

维护一个 `implementation-notes.md`，记录遇到的边界情况和偏离计划的决策。这样可以从每次尝试中学习。

> *"遇到边界情况必须偏离计划时，选保守方案，在 Deviations 下面记录原因，然后继续推进。"*

---

## 实现后：巩固理解

### 推介与解释文档
将原型、规格说明、实现笔记打包成一份文档，加速评审者理解和专家审批。

### 测验（Quiz）
让 Claude 围绕变更出题测验你。**只有完美通过测验后才合并代码。** 只看 diff 只能得到浅层理解。

> *"给我一份 HTML 报告帮我理解变更，底部附一份我必须通过的测验。"*

## 串联案例：用 Claude Code 剪辑 Fable 发布视频

Thariq 用这套方法完成了一件他完全不懂的事（视频剪辑）：

1. 从已知出发 → 让 Claude 解释 Whisper 转录原理
2. 原型验证 → 用 Remotion + 转录文本做视频原型
3. 发现盲点 → 做调色时不知道什么是"好"，不盲目生成版本，而是让 Claude 教他调色

## 核心教训

> **模型越强，你越能通过正确的方法完成更多事情。**

当长周期任务返回错误结果时，问题很可能不在模型——而在于你需要花更多时间定义自己的未知项。

每一种低成本方法（解释文档、头脑风暴、访谈、原型、参考资料）都是在修复代价变高之前，先发现你不知道的事情。

> **开始下一个项目时，先让 Claude 帮你找到自己的未知项。**

## 延伸阅读：AI Engineer World's Fair 演讲补充

在近期的演讲中，Thariq 补充了上述方法论背后的更深层语境：

### 1. 解除 Claude 的束缚（Unhobbling Claude）
模型很多能力其实早已存在，只是没有合适的接口释放出来（Anthropic 内部称为 **Capability Overhang / 能力悬余**）。例如让聊天模型背出特定规律的宝可梦名字它做不到，但给它代码执行工具，两秒就能写脚本过滤出来。

正因如此，Claude Code **砍掉了 80% 的系统提示词**。对于 Fable 这个级别的模型，过多的示例和硬约束反而会限制它的想象力。现在的最佳实践是：**多给上下文，少给约束；告诉它情况，不告诉它不许做什么。**

### 2. 态度重塑：打破常规（Be Unreasonable）
随着模型能力的跃升，过去的很多经验正在失效。我们过去习惯了在“好、快、省”中做取舍，这是一种本能的防御。但在 Fable 时代，与其先设好优先级排除掉一部分，不如**先用更强的模型和工具把边界往外推，看看现实是不是真的会逼你做取舍。**
