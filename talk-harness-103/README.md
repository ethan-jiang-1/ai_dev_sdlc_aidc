## 定位

**同一听众的提高与收尾场：需求说清楚，验收有方，Harness 持续有人治理。** 听众与讲法基准见 [CONTEXT](<CONTEXT.md#一听众基准>)。

用户已确认本场定调，并授权持续完成 103 内容交付：需求说清楚、验收有方的两头业务能力，与 AI 反复对齐，Harness 治理承接有效依据。内容稿可以继续自主打磨；对外标题、合成案例和演讲规格仍可调整，不把定调认可写成产品验收或最终版批准。

> **主问题提案：怎样让 AI 真正对齐你的业务判断？**

核心主张：**业务理解撑住两头：需求说清楚，验收有方；与 AI 反复对齐，再用 Harness 留住并维护打磨后的依据。** 需求与验收不是项目两端的独立手续：具体输出会暴露原先没说出的标准，验收反馈回到需求，再进入下一次试做；需求变更也会改变证据的适用范围。用户定调与“经验打磨／直接反馈”的讲法边界见 [CONTEXT](<CONTEXT.md#一听众基准>)。

| 能力 | 主要承载 | 深浅安排 |

**用户已认可定调：先收好三场，本阶段不另开 104。** 最值得补的是拿真实业务练一遍，可作为系列配套工作坊：业务人直接澄清、看具体输出、指出偏差和理由、调整并重验、留下有效依据。它补实践，不增加一套概念。

如果后续明确要覆盖**投入日常使用后怎样判断业务效果、维护成本、异常与停用**，可另设 104；该主题跨出“搭与打磨”的范围，应有真实运行案例和明确听众需求再立题。多 Agent 拓扑、源码或平台细节属于另外的技术提高路线，不作为同受众必修续篇。104 尚未立项，也未获用户确认。

## 范围

- **需求说清楚**：沿决策依赖追问；可查事实先查；给选项、建议和代价；人确认取舍；未知有去向。
- **验收有方**：需求与样本互校，明确检查什么、凭什么证据、谁决定；验证检查本身；保留人工业务判断。
- **Harness 治理**：现行依据可找，关键约束有执行点，失败有接手路径；变更按影响重验，新增约束复核，旧约束审慎退出。
- 循环续停只讲与证据、授权的连接；不展开循环调度、多 Agent 拓扑、产品源码、部署配置或组织制度全景。

## 工作方式与完成门

进入先读 CURRENT；首次进入再读本文件，写对客内容前读 CONTEXT。案例事实只改案例源，外部主张先查来源台账。上游研究和实践只读，不向其状态文件登记本场进度。

本轮完成标准：

- 两头业务能力、直接反馈与反复对齐有独立展开，治理接住打磨成果；三部分能解释为什么适合作系列收尾。
- 需求追问有具体对话与收口条件；三次试做分清已有要求遗漏、新标准发现和理解偏差；验收有已填样本、证据和决定；治理有执行点、变更、复核与退出动作。
- PPT 内容池每页有独立背景、具体候选材料与明确优先级；长版手册关键操作有空模板、已填例和失败去向；手册页版一页一提醒，可以独立消费。
- 作者 skill、一手源码、仓库实践归纳和本场教学提案可区分；不把 Grill-me 说成完整的验收体系。
- 案例只标为合成脚本、未运行；检查通过不等于全面可靠，最终交付不等于已发送或业务效果达成。
- 来源、文件链接、案例规则彼此一致；未决项只在开放问题维护，CURRENT 给接续入口。

不设额外 AGENTS 文件：当前无本场工具链或特殊门禁，纪律集中在本文件与 CONTEXT。临时件放仓库根 `.tmp-harness-103-*`，不依赖聊天记忆或临时文件续工。
