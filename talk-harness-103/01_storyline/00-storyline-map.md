# 103 故事线 v0.1 — 怎样让 AI 真正对齐你的业务判断

> **上游讨论稿，不是逐页上屏稿。** 定位见 [README](<../README.md>)，词义见 [CONTEXT](<../CONTEXT.md>)，案例事实与样本只在 [案例走读](<02-case-walkthrough.md>)维护；主张强度见 [来源台账](<../02_evidence/00-sources.md>)。本稿以系列分工明确、三部分因果成立为本轮完成目标。

## 一、系列衔接与新增价值

101 给听众完整概念地图和基本做法，停在这一场也能开始改善；102 深入逐轮工作的工程组织。103 接住他们下一句：“我知道要说清、要验，也会组织它干活了，但我以为说清的标准，AI 真理解了吗？看了具体结果，我怎样给出有用的判断？”

**提高发生在人这一侧：业务理解撑住需求与验收两头，并在与 AI 的反复试做中逐渐对齐。** 很多例外、优先级和不可接受的后果，业务人看见具体结果才说得出来；把这些反馈转成可复用的样本和当前依据，才逐步形成可靠判断。技术协作者能帮实现和整理，关键取舍与原始反馈仍需回到业务人核对。Harness 治理接住这种打磨的成果，使下一次无需从头猜。

不把听众升级成平台工程师，不重讲研发流程全貌。这里比 102 再推进的一步是“人的标准与 AI 的理解如何逐渐对上”，102 的主要动作仍是依据反馈修交付、决定下一轮。

| 共同认识与已有内容 | 103 再推进一步 | 本场使用它的目的 |
|---|---|---|
| 101：把老手脑子里的东西写出来 | 追问会互相影响的业务决定，检验“我以为说清了” | 不重讲五件事；展示答案如何改变下一问与样本 |
| 101：能让代码查的，别让 AI 自己说 | 判断代码到底查了什么、查不到什么；业务判断如何保留 | 用“算术全对、来源却错”的草稿拆开证据范围 |
| 102：需求与验收一起写 | 如何构造标准，如何识别两套合理预期暴露的需求空白 | 聚焦追问与判断过程，不再讲任务卡、拆分颗粒度 |
| 102：一轮失败决定下一轮 | 如何判断检查本身可信、验收报告是否足以接受 | 只讲证据与决定，不重复连续任务／轮次卡 |
| 102：当前入口和实际读取一致 | 谁维护，变化后哪些证据要重建，约束怎样转正和退出 | 治理拥有独立的持续维护段，追到模型升级后的试撤 |

**独立入口**：用一句话交代模型之外还有资料、规则、工具、检查等工作环境，再进入‘业务熟仍需核共同理解’。不要求听众回忆术语或听过前两场；已有认识帮助继续深入，不以删掉衔接划分范围。

## 二、主轴与推导

主问题提案：

> **怎样让 AI 真正对齐你的业务判断？**

推导：

**业务人提出当前要求 → AI 复述并试做 → 业务人看具体结果、指出偏差及理由 → 修正需求／理解／实现，重验并再试 → 有相应证据才接受当前范围 → 将有效样本、依据和约束留在 Harness 中持续维护。**

需求说清楚与验收有方在这条循环的两头；验收发现的新情况会再回到需求，不是先一次说完、最后一次打勾。业务资料或模型变更后，还要判断哪些旧依据和证据失效。

三件事相互制约：需求若仍空白，验收没有准星；检查若只验表面，完成就没有依据；环境若过期，这次通过也不能为下一次作保证。这里是本场的教学归纳，不声称为 Grill-me 作者的三段体系。

对外标题建议：**《怎样让 AI 真正对齐你的业务判断？》**。副标题候选：**需求说清楚，验收有方，让打磨后的经验持续有效。** 标题与规格待用户反馈，状态只在 [开放问题](<04-open-questions.md#叙事与规格>)维护。

## 三、开场：两个结果，都看起来像对的

**观众已有感受**：Agent 交得很快，人却要从头重查；或者所有测试通过，销售仍不敢把报价发出去。

用 [案例 §一](<02-case-walkthrough.md#一开场的两份草稿>)呈现价格更新后的两份草稿。先问哪个可接受，再补优惠授权与价格变化的事实；随后倒回首版，看这套依据怎样建立，又怎样随变更更新。把听众从“错在生成”引到“要求、证据、现行依据各缺了一环”。

不是要制造陷阱题；是让他们认出自己经常凭经验补的那半步。

**本段拿走**：**看着对，不够；知道为什么能接受，才有交付的依据。**

**转场**：先别加一段“请务必准确”，让开发 Agent 问出它不能替你定的决定。

## 四、第一幕：用追问把需求说到能判断

**人的难点**：一句“快、准、专业”里混了结果、偏好、授权和业务政策，自己也未必分开。

核心走读来自 [案例 §二](<02-case-walkthrough.md#二沿着决定追问>)：

1. **可查先查。** 价格资料、已有权限、已明确的流程由开发 Agent 回源；两份表谁生效若无法查证，才请有权的人确认。
2. **沿依赖追问。** “草稿还是直接发送？”决定后续需要的权限和检查；“客户说有折扣算不算批准？”决定缺记录的处理；“待确认还是默默报原价？”由具体样本逼出。
3. **给推荐，讲代价。** 首版只做草稿可缩小风险，但仍需要人工发送前复核。负责人接受的是取舍，不是 Agent 默认答案。
4. **用反例复述。** 两个人对同一输入给出不同合理预期，说明业务决定仍没清楚，不能拿多数投票代替确认。
5. **到当前范围够用就收口。** 有结果、边界、重要样本和未知去向即进入下一步；对话不能解决的问题转验证或原型。

命名可在演示之后给：“这类沿决定追问的做法，在 Grill-me 的思路里很突出。”当前作者入口关系、版本与限制见 [研究笔记](<../02_evidence/01-grill-me-requirements-acceptance.md>)。不把“一次只问一题”或“追问所有枝叶”硬写成通用纪律。

**现场微练习**：给出“帮我把报价做专业一些”，请听众写下一项会改变验收的决定，并给一个检验该决定的例子。参考答案：可复核的价格来源／批准依据／缺口状态；“换个字体”只有在明确品牌要求时才属于相应标准，不取代业务正确性。

**本幕拿走**：**需求说清楚，不是你讲得多，是你们对关键情境知道怎样判断。**

**转场**：大家都点头了仍不够。进入 [案例中的三次试做](<02-case-walkthrough.md#看输出才说出脑子里的标准>)：业务人看输出才发现“待确认”还要说清找谁、查什么；AI 又可能把“专业”理解成客气话。两头的对齐要靠这种具体反馈反复打磨，随后才把已确认的表现落实成验收证据。

## 五、第二幕：验收有方，先知道要证明什么

**人的难点**：“检查全绿”听起来客观，但检查与实现可以一起误解要求；独立 AI 也可能接受同样的错误来源。

走 [案例 §四](<02-case-walkthrough.md#四验收不是一句测试全绿>)，先给听众一张可复用的五问验收卡：**检查什么？拿什么输入与可信参照？预期看到什么？实际证据在哪？谁接受或打回？** 这是本场综合的教学工具，不归名为 Grill-me 原生模板。

再层层追问：

- **从要求到表现。** 正常、资料不足、优惠未确认、越权和来源冲突各写一例。负责人先确认预期，不从当前生成结果倒推正确答案。
- **从表现到证据。** 金额重算、实际来源核对、优惠批准匹配、权限行为与销售可复核性分别有证据；每条只证明它能观察的性质。
- **从证据到决定。** 缺证据标未验证，业务空白交负责人，检查失败回对应实现／规则／检查；没有“AI 已宣布完成”这一条捷径。
- **检查要经得起反例。** 故意放错金额验证会失败；再放字段运算正确、业务依据却错的草稿，区分算术检查与按独立基线验金额，并核来源／优惠。若错表碰巧同价，金额检查也发现不了，仍需来源关；正常样本要能通过，避免误拒绝。
- **业务人直接反馈，协作者保留原意。** 走读同一 A3 的三次试做，分清“标准没说全”“AI 理解偏了”“实现没做到”；展示‘给出缺口与下一步’被转述成‘更友好’后的偏差。业务人核对 AI 的复述与改后输出，协作者保留原情境、具体片段和理由，不凭印象代传。
- **需要判断的，不装成机械证明。** “销售是否能复核”用人判过的例子说明，AI 可初审，分歧回到具体草稿与理由；有波动就报告场景、重复与失败情况。标准修订由业务人确认并更新依据，当前验证仍有明确标准。
- **完成一次开发验证，不等于真实业务效果。** 当前范围验收、限定试用、实际收益分别需要相应证据；不凭几张样本宣称长期准确。

用 [案例 §五](<02-case-walkthrough.md#五一份能作决定的验收报告>)说明人不是逐行重干：审当前范围、证据质量、重要未覆盖项和需要的决定。报告未运行就明示未运行，展示格式不造日志。

**本幕拿走**：**验收看的是“这条要求有没有相应证据”，不是有多少个绿勾。**

**转场**：当价格、规则、模型开始变化，这套证据怎样继续成立？到这里治理才成为不可缺的一环。

## 六、第三幕：把可信交付维护成日常能力

**人的难点**：前面反复打磨，好不容易把经验说清，换一次会话又只剩最早那句‘专业一点’；下一次换了资料或模型，过去的补丁还可能淹没当前依据。

治理先接住已确认的业务取舍、样本、反馈理由和本轮标准，使开发 Agent 能找到它们、业务人能复核它们；再把适合机器判断的约束放到执行点。三次试做不是自动进步的保证，只有确认并留存的改进才可被下一次使用。

先走 [案例 §六](<02-case-walkthrough.md#六价格变了旧绿灯怎样处理>)：价格从 Q1 改 Q2，算术检查没坏，但旧报告不能替当前版本验收。原有不发送权限没有因价格变化而扩大。要求听众做“按影响处理”的决定，不背版本管理术语。

再走 [案例 §七](<02-case-walkthrough.md#七把一次失败变成环境改进>)，沿同一次旧价失败连续诊断：哪些证据失效、哪里只要修当前结果、哪里需要修共享环境、新约束何时转正。下表的四项动作供讲者整理，制页不连续念分类，也不当行业标准四分法：

| 日常动作 | 听众需要做的判断 | 案例落点 |
|---|---|---|
| 依据有人维护 | 哪份现行、谁更新、旧版如何退出入口 | 当前价目与批准来源，不能凭日期或聊天回忆猜 |
| 约束有执行点 | 是提醒、机器拦截还是人审？实际入口会命中吗？ | 来源检查与只读权限，故意使用旧价／请求发送验证 |
| 失败有人接 | 失败对象、原因、依据和下一步送到谁手上 | 指出用了 Q1 而要求 Q2；交开发 Agent 重取资料或交负责人确认 |
| 规则定期复核 | 原根因是什么，是否过宽／冲突，能否撤？ | 新约束待复核、正反例、退役旧入口，能力补偿项试撤 |

**持续治理包括减法。** 走 [案例 §八](<02-case-walkthrough.md#八新模型来了哪些东西可以减>)：用新模型比较“保留／试撤”某项表格转写提示，保持条件可比、重放原失败和正常情况、记录恢复路径。业务责任和权限边界不由模型变强而撤销。

**现场判断题**：先判断 Q2 要求下实际读取 Q1、只有旧绿灯时能接受什么；再回看第一次‘待确认’输出和当轮已定要求，写一句指出偏差、业务理由与处理去向的反馈。不倒算新标准，不凭一段输出断定理解根因。具体题面、控时与答案只在 [03 主持卡](<../03_outline/00-page-structure-v0.1.md#p25接受什么怎样给反馈>)维护；不做工具操作，也不扩成完整工作坊。

**本幕拿走**：**治理让现行依据、实际执行和验收证据一直对得上。**

## 七、收尾：听众的业务判断成为可积累的能力

回到开场，同一份报价草稿现在可以有根据地判断：取舍已确认、证据能核查、当前依据有效，才接受约定范围；任何一环缺失都知道回到谁、补哪种依据。

全系列在本场汇合，但对客收尾不必点名场次：

> **让 Agent 越用越稳，要把需求说清楚，把验收做扎实，再把那一圈维护好。**

业务理解撑住两头：一头把希望得到的结果和关键取舍说清，另一头判断实际结果是否合用。与 AI 对齐难，需要业务人带着具体例子反复打磨；技术协作者帮助实现、整理和验证，关键判断保持与业务情境相连。Harness 把确认过的依据接住，使这份经验可以积累和复用。

**回去做一件事**：挑一个你已在搭的 Agent，用一条真实需求补一项关键决定；看一次具体输出，写偏差与业务理由，再核 AI 的复述；为它选正常例和反例，说明怎样验；留下当前依据和实际执行点。先做一次可核对的反馈，不要一次扩成整个平台。

## 八、下游展开与预算入口

用户已确认本场定调并授权完成内容交付。逐页结构与时间分配统一维护在 [03 逐页结构](<../03_outline/00-page-structure-v0.1.md>)，本文件不继续维护第二份页表。早期 22 页位拆成更多轻页，是为三次试做与直接反馈留出独立段落，未扩大主题；页面数与实际时长仍为未排练提案。

下游展开六段：开场的判断缺口 → 需求追问与收口 → 同一情境的三次试做及反馈 → 验收标准和证据 → 打磨成果的治理 → 回到一次具体判断。对齐段先讲经验如何被看见、纠正、确认，再进入更正式的检查设计；原先位于第一幕与第二幕的试做引用可在讲述中合成这一独立段，不重复走两遍。

若需要较短场次，先减少表格展示和练习展开，保留两头业务能力、直接反馈、变更重验和规则复核／退出。若要深讲真实业务工作坊或模型对照实验，应另增实践时间，不在原预算上暗塞。

## 九、上游自检

- 三部分都能回到同一报价案例，治理承担独立段落，需求不是把所有业务判断写成长文。
- Grill-me 贡献在追问与澄清，不为整套验收／治理方法背书。
- 术语先有具体动作；不重讲 101 的五件事与档位，不重讲 102 的拆分和轮次交接。
- 报价助手与开发 Agent 分开；规则范围、样本预期、Q1／Q2 变更均消费案例源。
- 教学脚本尚未运行，不能下“检查有效、产品通过”结论。
- 评审结果与后续缺口只在 [开放问题](<04-open-questions.md>)记录，当前进度由 CURRENT 维护。
