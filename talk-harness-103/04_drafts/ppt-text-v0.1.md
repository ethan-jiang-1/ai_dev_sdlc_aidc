## 开场

### P1 · 做出来了，为什么还不敢交出去？

<!-- off-screen:begin -->

- **页背景（不上屏）**：阶段是全场开场。听众已在搭 Agent，业务人能识别业务后果，开发 Agent 能协助实现，报价助手承担生成草稿的任务。当前缺口是结果看起来完整，却没有足够依据判断是否可接受。本页建立一条主问题，让后续需求、反复对齐、验收和治理都围绕可信交付展开。
- **L2 图示指令（不上屏）**：画一张报价草稿卡，右侧留三个待核标签“要求／证据／当前依据”。只显示这些标签与草稿示意，不绘制“通过”勾。
- **制页说明（不上屏）**：标题为视觉中心，副标题只保留一行。讲者、场次、日期可填空；不要把全场结构表搬到封面。

<!-- off-screen:end -->

- **L1 标题**：**做出来了，为什么还不敢交出去？**
- **L3 支撑 [必上]**：需求说清楚，验收有方，让打磨后的经验持续有效。
- **L3 支撑 [可选]**：Agent 能帮你做，业务判断需要你把握。
- **例子 [例]**：一份报价草稿：金额、价格来源、优惠依据、待确认事项，都要能核对。
- **落点 [必上]**：**交付之前，要知道为什么可以接受。**
- **L4 页脚**：1

### P2 · 两份草稿，都像是对的

<!-- off-screen:begin -->

- **页背景（不上屏）**：阶段是看价格更新后的一次失败片段，后面会倒回首版。销售收到报价助手的候选草稿，业务负责人补充现行价格与优惠授权信息；开发 Agent 还缺判断“算术成立”和“报价成立”的完整依据。草稿都用了旧单价，本页让听众认出金额、授权和现行来源是不同问题。
- **L2 图示指令（不上屏）**：并排画草稿甲、乙；第一层显示单价、数量、小计，第二层补“乙：客户转述九折，未核批准”，第三层补“现行单价已改为 125.00 元”。两张卡都不画通过标识。
- **制页说明（不上屏）**：按信息层次逐步揭示，避免一开始把所有解释摆满。必须显示“价格更新后的片段”，保证后来倒回 Q1 首版不被误读为重新认可旧价。

<!-- off-screen:end -->

- **L1 标题**：**两份草稿，都像是对的**
- **L3 支撑 [必上]**：价格更新后，报价助手给出两份候选草稿：
  - 甲：单价 120.00 元 × 数量 3，小计 **360.00 元**。
  - 乙：同一产品、数量，依据“客户说经理答应九折”，自行给出 **324.00 元**。
- **L3 支撑 [必上]**：乙的优惠批准尚未核对；甲、乙所用单价都来自旧表，现行单价已是 **125.00 元**。
- **L3 支撑 [可选]**：看起来完整的格式，没有回答价格是否现行、优惠是否获准。
- **例子 [例]**：“帮销售做个报价助手，要快、准、专业。”——这句话还没有交代哪些依据必须核对。
- **落点 [必上]**：**算术成立、优惠获准、来源有效，要分别有依据。**
- **脚注 [必上]**：合成教学片段，未运行；以下倒回首版，再走到这次价格变更。
- **L4 页脚**：2

### P3 · 业务理解撑住两头

<!-- off-screen:begin -->

- **页背景（不上屏）**：阶段是从案例现象建立全场重心。业务人负责希望得到什么结果和判断结果是否合用，开发 Agent 协助澄清与实现，报价助手生成候选草稿。AI 缺少业务人脑中的例外、优先级和后果判断；业务人也未必一次说全。本页说明两头能力如何通过反馈相连，以及协作中关键判断仍需业务核对。
- **L2 图示指令（不上屏）**：三段横向图，左“需求：说清结果与取舍”，中“AI：协助查、问、做、验”，右“验收：判断结果是否合用”；右端回箭头指向左端，标“看结果，补理解”。两端可用同一业务人物，也可用两位协作人物。
- **制页说明（不上屏）**：突出两头与回箭头，避免变成岗位职责全景。直接沟通有助于核对原意，但不要画成自动正确的保障。

<!-- off-screen:end -->

- **L1 标题**：**业务理解撑住两头**
- **L3 支撑 [必上]**：
  - 开工前：说清希望得到的结果、关键取舍和边界。
  - 看结果时：判断哪里合用，哪里不能接受，并说出理由。
  - 有新发现：把反馈带回需求，再试、再验。
- **L3 支撑 [可选]**：两头可以由同一人承担，也可以协作；关键业务判断要有人负责。
- **例子 [例]**：“专业”在销售眼里，可能意味着看得出依据、缺口和下一步；AI 可能只理解成措辞客气。
- **落点 [必上]**：**业务经验要在具体要求与具体判断中体现。**
- **L4 页脚**：3

## 需求说清楚

### P4 · 一句要求，藏着几项决定

<!-- off-screen:begin -->

- **页背景（不上屏）**：阶段倒回报价助手首版的需求澄清。业务负责人提出“快、准、专业”，开发 Agent 尚不清楚使用者、输出用途和允许动作，报价助手的职责也未确定。本页把抽象偏好展开为当前范围内能决定、能核对的要求，保留以后随结果补充的空间。
- **L2 图示指令（不上屏）**：上方一句原需求，下方四张卡“给谁／给什么／做到哪／怎样用”。卡中放销售、报价草稿、未含税费且不发送、销售复核四个对应标签。
- **制页说明（不上屏）**：四个问题与已填例相邻；不要再加完整规格目录。先界定本次范围，允许后续发现新的要求。

<!-- off-screen:end -->

- **L1 标题**：**一句要求，藏着几项决定**
- **L3 支撑 [必上]**：“报价要快、准、专业”，先问清：
  - 给谁：销售。
  - 给什么：可复核的报价草稿。
  - 做到哪：单一产品、未含税费，不自动发送。
  - 怎样用：销售核查后，决定实际发送。
- **L3 支撑 [可选]**：当前先确认影响结果和授权的决定，远期功能可以另行讨论。
- **例子 [例]**：首版输出至少让销售看到产品、数量、单价、小计及价格来源；有优惠时还要看到批准依据。
- **落点 [必上]**：**先定当前结果和边界，才知道后面要问什么。**
- **脚注 [必上]**：本场案例只生成草稿，不修改价格、不批准优惠、不处理税费。
- **L4 页脚**：4

### P5 · 事实先查，取舍再问

<!-- off-screen:begin -->

- **页背景（不上屏）**：阶段是首版动手前的资料核对。开发 Agent 可读取价目、流程和已有权限，业务负责人确认资料冲突与业务取舍，授权者决定允许动作。Agent 已发现 Q1、Q2 两份资料，但没有明确生效状态，缺少选择依据。本页让听众分清可查事实、需人决定的事项与授权，避免让人回答能回源的问题或让 AI 猜政策。
- **L2 图示指令（不上屏）**：两路图，上路“已有资料→查原来源”，下路“状态不明／取舍未定→有权者确认”；旁边小框“查到资料≠获准行动”。不用真实文件路径或工具截图。
- **制页说明（不上屏）**：Q1／Q2 只是教学版本标签，不解释工具配置。本阶段负责人确认 Q1 用于首版，Q2 的正式切换在后段发生。

<!-- off-screen:end -->

- **L1 标题**：**事实先查，取舍再问**
- **L3 支撑 [必上]**：
  - 价目、已有流程和工具权限：开发 Agent 先查来源。
  - 两份价格表谁生效仍不清楚：交有权的负责人确认。
  - 是否允许发送、采用什么优惠规则：需要明确决定。
- **L3 支撑 [必上]**：不能凭修改日期猜生效版本；能读取资料，也不代表获准发送报价。
- **L3 支撑 [可选]**：回源后说明“查到了什么、依据在哪、还缺哪项决定”，再向人提问。
- **例子 [例]**：首版负责人确认使用 Q1：产品 A 单价 120.00 元。优惠另按批准记录核对，客户转述不能代替批准。
- **落点 [必上]**：**可查的先查，关键取舍交给有权决定的人。**
- **脚注 [必上]**：合成澄清脚本，未运行；版本与授权均需在实际任务中核实。
- **L4 页脚**：5

### P6 · 一个决定，改变后面的问题

<!-- off-screen:begin -->

- **页背景（不上屏）**：阶段是从首版目的追问下游决定。开发 Agent 帮业务人梳理选择，报价助手尚未具备被确认的工作范围；Agent 缺少决定间的依赖，直接开做会把业务空白当作自由选择。本页通过短对话展示先确认用途，再问能力、依据和异常。沿决定依赖追问借鉴 Grill-me，但案例、验收与治理均为本场教学转译。
- **L2 图示指令（不上屏）**：两条简短决策链：“草稿／直接发送→所需授权与检查”；“优惠凭什么→缺批准怎样处理”。每条只显示本案例已确认分支；推荐旁标一项理由和一项代价。
- **制页说明（不上屏）**：优先选用草稿用途对话，优惠链作为第二组材料。作者与 Grill-me 小字最多出现一次，不展示技能安装或内部调用。

<!-- off-screen:end -->

- **L1 标题**：**一个决定，改变后面的问题**
- **L3 支撑 [必上]**：
  - 先问：给销售复核的草稿，还是直接发客户？
  - 负责人确认草稿：接着核来源、金额、缺口及人工复核方式。
  - 再问：优惠凭什么采用？缺批准时怎样处理？
- **L3 支撑 [可选]**：建议要带理由与代价；负责人接受的是业务取舍。
- **例子 [例]**：
  - 开发 Agent：“建议首版只做草稿，便于控制范围；代价是保留人工复核与发送环节。可以吗？”
  - 业务负责人：“可以，先让销售看得懂、核得清。”
- **例子 [例]**：“客户说经理答应九折”，是否足够？负责人确认：需要可核对的批准记录；缺批准则待确认。
- **落点 [必上]**：**沿着决定往下问，每个答案都要改变后续工作依据。**
- **脚注 [必上]**：追问思路借鉴 Matt Pocock 的 Grill-me；本例为合成教学转译，未运行。
- **L4 页脚**：6

### P7 · 用同一情境，核对是否理解一致

<!-- off-screen:begin -->

- **页背景（不上屏）**：阶段是首版澄清即将收口。业务人和开发 Agent 已同意“不凭转述给优惠”，但报价助手缺批准时应怎样输出仍可能有不同解释。前置讨论已要求待确认、不套优惠，并保留请求和批准缺口。本页用同一输入对比两种可能预期，让有权者确认处理方式和理由；具体接手人与下一步仍会在后面的试做中发现。
- **L2 图示指令（不上屏）**：上方原输入；下方两张候选理解卡“直接按原价给可用草稿”“待确认，保留请求和批准缺口”。再显示负责人确认后一张卡，使用“已确认的预期”而不是运行通过标识。
- **制页说明（不上屏）**：强调这里确认的是需求理解。不要提前把具体销售负责人和处理步骤画成已完整确定的前置标准。

<!-- off-screen:end -->

- **L1 标题**：**用同一情境，核对是否理解一致**
- **L3 支撑 [必上]**：客户提出九折，却没有可核对的批准记录。两种理解：
  - 直接报原价，把草稿标为可用。
  - 标为待确认，保留优惠请求并说明缺批准。
- **L3 支撑 [必上]**：业务负责人确认第二种：不套优惠，也不能把客户的请求静默忽略。
- **L3 支撑 [可选]**：出现两套合理预期时，先查业务决定；不能靠多数票定政策。
- **例子 [例]**：开发 Agent 复述：“我会保留客户九折请求，指出缺少批准记录，保持待确认。”负责人核对这段理解。
- **落点 [必上]**：**具体情境能暴露点头之后仍存在的理解差异。**
- **脚注 [必上]**：合成需求样本，未运行；确认预期不等于输出已经做到。
- **L4 页脚**：7

- **L2 图示指令（不上屏）**：三层纵向图“字段间运算／独立业务基线／实际来源与批准”，每层写能回答的问题；不要把它们画成任一层通过即可交付的闸门。

- **页背景（不上屏）**：阶段是验证检查机制。开发 Agent 准备给报价助手的正常和错误输出跑检查，业务负责人先确认期待判断。当前缺口是检查可能未运行、抓不住错误或误拒绝正常情况。本页说明应观察哪些结果，并保持这些为未运行的设计预期；不编造日志、运行时间或通过率。
- **L2 图示指令（不上屏）**：四张测试卡：正常草稿、故意错金额、无批准优惠、错来源；每张下标“应接受／应拒绝／需另核”的期待判断，不画实测结果仪表盘。
- **制页说明（不上屏）**：明确表格列名为“应观察到的结果”。不得使用“已通过”或伪造运行编号。缺资料正确待确认也是正常异常处理，不宜被画成错误输出。

<!-- off-screen:end -->

- **L1 标题**：**检查也要经得起正反例**
- **例子 [例]**：

  | 受控情境 | 应观察到的结果 |
  |---|---|
  | Q1 正常草稿，小计 360.00 元 | 算术与独立基线金额检查应通过；来源仍须核 |
  | 输入不变，故意把小计改成 361.00 元 | 两种金额检查都应失败 |
  | 无批准却套九折，运算仍正确 | 不能作为合格草稿；优惠核对与业务基线检查应抓住问题 |
  | 错表恰好同价 | 金额可能不变，来源检查应指出不匹配 |

- **L3 支撑 [必上]**：确认检查真的运行；目标错误能被发现，正常输出和正确的待确认处理不会被误伤。
- **L3 支撑 [可选]**：模型输出有波动时，选代表情境并重复观察，记录条件与失败类型；次数依据任务风险确定。
- **落点 [必上]**：**检查在该失败时能失败，在该接受时不误拒绝，才有使用依据。**
- **脚注 [必上]**：以上均为应观察的教学预期，尚未运行；不能据此宣称检查已有效。

## Harness 治理

### P20 · 把打磨后的理解留在工作环境里

<!-- off-screen:begin -->

- **页背景（不上屏）**：阶段是从一次反复对齐走向可接续工作。业务负责人确认当前标准，开发维护者整理原反馈、标准变化与证据状态，开发 Agent 下次需要找到它们；报价助手也要沿现行要求生成。当前缺口是经验只留在聊天、三次试做和“更友好”的转述可能混成同等现行。本页首次命名 Harness，并说明治理怎样承接已确认的业务理解。
- **L2 图示指令（不上屏）**：画一个外部工作环境框，中心“当前要求＋样本”，旁边“证据状态／入口与负责人”，历史试做单独放在外侧并有按需箭头。显示 Harness＝模型外面那一圈的说明，不展开架构图。
- **制页说明（不上屏）**：重点是当前与历史的分工及维护责任，不要求每格建立新文件；文件名、仓库路径不上屏。

<!-- off-screen:end -->

- **L1 标题**：**把打磨后的理解留在工作环境里**
- **L3 支撑 [必上]**：Harness，就是模型外面支持和约束 Agent 工作的那一圈。治理要让确认后的依据能找到、能核对、能生效。
- **L3 支撑 [必上]**：保留四类信息：
  - 当前要求与对应样本。
  - 原情境、反馈理由和标准变化。
  - 证据条件、是否运行与待验项。
  - 生效入口、维护者和失败接手人。
- **例子 [例]**：缺批准时的最终规则是现行依据；三次候选输出与业务反馈标为历史，保留每次采用的标准。
- **L3 支撑 [可选]**：可以放在已有工作单或业务系统中，不必每项新建一份材料。
- **落点 [必上]**：**把确认过的经验保存为当前依据，使下一次判断有来路。**
- **脚注 [必上]**：本案例仍无运行证据；留存教学脚本不等于产品已成立。
- **L4 页脚**：20

<!-- off-screen:end -->

- **L1 标题**：**练习：旧检查全绿，现在能接受什么？**

  - 工具实际读取 Q1。
  - 旧检查全绿。
  - 当前来源检查尚未运行。
