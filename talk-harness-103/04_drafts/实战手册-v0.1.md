业务理解撑住两头：开工前，你要说明希望得到什么结果、哪些取舍不能由 AI 猜；交付时，你要判断实际结果是否合用、证据是否够。中间的查资料、提方案、实现和检查可以请 AI 协助，两头的业务判断需要你参与。

说过一遍、AI 点过头，并不保证理解一致。很多例外和优先级要看到具体输出才说得出来。你可以拿实例指出偏差，再请 AI 复述、调整和重验，把有效判断留给下一次工作。

这份手册适合已经在搭 Agent、懂自己的业务，但对工程流程尚缺手感的人。不需要手写每条检查，也不需要逐行指挥 AI。你需要能说清：为什么接受，为什么打回，还缺什么。

## 从一件熟悉的业务开始

贯穿示例是**报价草稿助手**。开发 Agent 帮你构建它，报价助手生成供销售复核的草稿；两者在文中分开称呼。

**全部示例都是合成教学脚本，尚未实现、未运行。** 问答、输出、金额和检查结果只说明应该怎样判断，不是产品证据。三次试做不保证稳定，少量样本也不代表真实业务整体质量。

案例首版只处理单一产品、正整数数量，金额保留两位，明显标示“草稿，未含税费”。它不自动发送、不改价格、不批准优惠、不计算税费。销售在实际发送前仍要复核。

你可以把八步放到现有工作单中，不必为每步新建一份文件。短任务用一张单，长任务或跨会话时再增加必要记录。

| 步骤 | 你要留下的结果 |
|---|---|
| 1．先定结果，可查事实先查 | 当前范围、资料来源、未决事实 |
| 2．追问取舍，核对共同理解 | 经业务人确认的决定、关键样本和未知去向 |
| 3．看输出，直接给反馈 | 具体偏差、理由、改动类别和下一次验证目标 |
| 4．用五问设计验收 | 标准、输入／参照、预期、证据与验收者 |
| 5．检验检查本身 | 能抓错误、不会误伤正常情况的验证记录 |
| 6．据证据决定是否接受 | 已证明的范围、未验证项和下一步 |
| 7．留住打磨成果，让约束生效 | 现行依据、实际入口、检查点和接手路径 |
| 8．变化后重验，复核和试撤约束 | 影响清单、当前证据和约束去留理由 |

## 第一步：先定结果，可查事实先查

“帮我做得快、准、专业”不足以指导执行。先说明谁用、用来做什么、首版做到哪，再请开发 Agent 检查已有资料与权限。能回源的事实不必反复问你；资料查不到、互相冲突或缺生效状态时，才交有权确认的人决定。

**做法**：限定只读调查范围，让开发 Agent 返回找到的依据和缺口；你确认结果与边界，不把最新文件日期直接当生效证明。

| 项目 | 填写 |
|---|---|
| 谁使用，希望得到什么结果 | ______ |
| 首版做到哪里，不允许什么动作 | ______ |
| 请先查哪些现有资料／权限 | ______ |
| 查到了什么，来源及生效状态如何 | ______ |
| 哪项仍不确定，交谁确认 | ______ |

**紧邻已填例：报价草稿助手**

| 项目 | 本例填写 |
|---|---|
| 谁使用，希望得到什么结果 | 销售拿到可复核的报价草稿，减少查价和算金额的工夫 |
| 首版做到哪里，不允许什么动作 | 单产品商品金额草稿，未含税费；不发送、不改价、不批优惠 |
| 请先查哪些现有资料／权限 | 价格表、优惠批准记录、销售流程及实际工具权限 |
| 查到了什么，来源及生效状态如何 | 有 Q1、Q2 两份价格表，但现行状态不明；不能仅按文件日期选择 |
| 哪项仍不确定，交谁确认 | 销售负责人确认本轮生效价格；授权者确认只读和草稿范围 |

**结果／失败去向**：有依据的事实留出处；未经确认的事实标未决。资料不足时，报价助手应列缺口并保持待确认，不编造可用金额。只读调查所需资料或权限不可用时报告限制，交负责人补齐；调查结束不等于功能完成。

## 第二步：沿关键决定追问，核对共同理解

业务人脑子里常有隐含的例外。开发 Agent 可以帮你沿依赖追问，给有理由的推荐，但取舍要由你确认。先决定“草稿还是直接发送”，后面的授权和验收才有范围；先决定“客户转述是否算批准”，才能判断优惠异常。

**做法**：让每个关键问题给出选项、建议和代价。回答后请 AI 复述结果、边界和样本，检查它有没有补了你未同意的政策。重要情境有一致预期、未知有去向，就可以开始限定范围试做。靠对话判断不了的体验做原型，技术事实做验证，不无限追问。

**紧邻已填例**

> 我理解：给销售使用，得到供复核的单产品报价草稿，未含税费；首版价格由负责人确认使用 Q1。允许读价与批准资料、生成草稿，不发送、不改价、不批优惠。产品 A 数量 3、无优惠时商品小计为 360.00 元；客户说九折但无批准记录时，待确认、不套优惠，保留请求并说明缺批准。工具能否取得所需依据仍需限定范围验证，由开发维护者处理，实际资源上限在开工前确认。

**结果／失败去向**：业务人确认后，这才成为当前工作依据。同一情境有两个合理预期时回到业务取舍，不让 AI 选个默认答案。可行性未知交限定验证；超出调查范围或预算仍无结论，带着发现和限制交人，不能标完成。

## 第三步：看具体输出，直接给反馈

业务熟不等于一次就能把经验说全。看输出能发现遗漏，也能发现你还没说出的标准。反馈尽量直接连到业务人：原输入是什么、哪段输出不合用、为什么、下一次希望看到什么。

**做法**：先对照当轮已经确认的要求，区分三条路径：已有要求没做到，修实现；AI 理解偏了，纠正复述和例子；要求原来没说全，由业务人确认新标准再重验。一条反馈可能同时包含两类问题，不必强行只选一种。

**紧邻已填例：同一优惠未批准情境的三次合成试做**

试做前已经确认：无批准记录要待确认、不套九折，保留客户请求、说明缺批准。具体接手人和下一步尚未明确。

| 试做 | 输出片段 | 业务人直接反馈 | 去向与下次检查 |
|---|---|---|---|
| 第一次 | “待确认。” | “看不出卡在哪里，也不知道下一步找谁。” | 漏掉已定的请求与缺口，修实现；接手人和下一步是新发现标准，请业务人确认后补入 |
| 第二次 | “尊敬的同事，本次优惠尚待确认，敬请留意。” | “只是客气了，仍不知道找谁、查什么。专业是能接着办。” | 核对是否把可操作性理解成礼貌语气；纠正理解并实现已确认的处理路径，原请求与缺口也仍要补齐 |
| 第三次 | “草稿，待确认。客户提出九折；缺可核对的优惠批准记录。请销售负责人确认该请求并提供有效记录，当前不采用该优惠。” | 核对请求、缺口、接手人和下一步是否正确可用 | 按确认后的标准重验本例，再验带有效批准的正常例，避免所有请求都被挡成待确认 |

**紧邻已填例**

> 原情境：客户说九折，无批准。原输出：“待确认。”业务反馈：保留客户请求，写清缺批准，并说明找谁处理。协作者若压缩成“更专业、友好一点”，AI 可能只改措辞。应保留原片段和理由，把“销售负责人确认并提供有效记录”的复述回给业务人核对；未经确认的部分仍标待定。

**结果／失败去向**：下一次有明确的改动目标和检查情境。三次仅是讲法，不是通用轮数或稳定性保证。反馈仍模糊就用具体好坏例继续澄清；无进展、权限不足或达到约定资源上限，带着偏差和未决项交人，不直接交付。

## 第四步：用五问设计验收，分清证据范围

AI 能跑检查，不等于它有权定义“做对”。先让业务人确认预期，再请开发 Agent 帮你写检查、取得证据。对不能机械判断的业务可用性，用人已判过的好坏例说明尺度，AI 可以初审，分歧仍回到具体片段与理由。

## 第五步：让检查在该失败时失败

一项检查从没报错，可能是质量好，也可能是没检查到关键问题。请开发 Agent 在受控条件下放入目标错误，再给正常例，观察它是否分别打回和通过。这是在检验检查，不是故意损坏真实业务。

**紧邻已填例：应然设计，尚未执行**

| 正常输入／结果 | 故意放入的错误 | 哪项检查应怎样反应 | 实际反应与证据 | 不符预期怎么办 |
|---|---|---|---|---|
| Q1，A 数量 3，小计 360.00 | 仅把小计改成 361.00 | 算术和独立业务基线金额检查均应失败；正常例均应通过 | 未运行，无证据 | 查检查取值和判定逻辑，修后重测 |
| 正确现行来源 | 改为已退出的旧来源，假设碰巧同价 | 金额可能通过，来源检查必须指出不匹配；正常来源不误拦 | 未运行，无证据 | 修来源检查，不能用金额绿灯代替 |
| 有效 D1，九折获批 | 没有批准记录却套九折 | 业务基线／批准检查应拒绝该优惠；单纯算术可能通过 | 未运行，无证据 | 查批准证据和规则执行点 |
| 缺数量，正确输出待确认 | 虚构小计并标可用 | 异常检查应失败；正确待确认不能被判错 | 未运行，无证据 | 修检查尺度，必要时回业务人核预期 |

如果用 AI 评审，先拿业务人判过的例子校准，观察它漏了哪类错误、是否误伤正常例。换一个独立 Agent 不代替校准。输出有波动时，按实际风险选择代表情境和重复次数，报告分母、失败类型与条件，不从一次成功推导稳定性。

**结果／失败去向**：关键检查确实能抓目标错误，正常路径没有被误拦，才有使用它的依据。检查未执行是未验证；执行失败需补环境或修检查；无法可靠判的业务含义交人，不能假装已经有机器绿灯。

## 第六步：只接受证据覆盖的当前范围

验收不是替 AI 把工作全部重干一遍，而是判断：当前版本的证据支持哪些要求，哪些还未验证，未覆盖风险是否允许限定接受。接受范围要说清楚；检查通过不自动获得发送或上线授权。

下面三种条件不要混成一个“完成”：

| 如果实际证据是这样 | 可以作什么决定 |
|---|---|
| 只有草稿字段的算术检查通过 | 只可确认字段运算；来源、批准与业务正确性仍未验证，不能接受完整报价 |
| 当前约定要求均有对应证据，指定验收者认可，限制明确 | 可接受该范围内的开发结果；真实试用、业务收益及实际发送另按相应依据决定 |
| 检查不可用、预算用完或权限阻塞 | 暂停并交人；说明缺口与接手人，不因停止而标完成 |

上述是决定方法，不是本案例已有通过结果。原始证据要能复查，报告应注明当前需求、价格、实现、模型／工具条件、样本与检查版本，以及实际结果和限制。

**结果／失败去向**：验收决定有明确范围和依据。证据不足先补验证；业务标准未决回负责人；实际效果不可观察时保留人工观察与后续试用，不用代码或样本绿灯代替业务收益。

## 第七步：留住打磨成果，让约束在实际流程中生效

## 第八步：变化后重验，复核新增约束，审慎试撤

## 下次开工前，问自己三句

- 需求这一头：关键情境里希望得到什么，AI 的理解是否经过业务人核对？
- 验收这一头：哪条要求有什么证据，哪些仍未验证，谁有权接受？
- 中间与下一次：确认过的依据能不能被找到，约束是否实际生效，变化后怎样重验？

从一条真实需求开始，给一个正常例和一个反例，直接指出偏差及业务理由，再把确认过的判断留住。业务经验由此逐渐成为可以复用的工作依据。
