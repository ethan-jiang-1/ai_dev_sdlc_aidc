# CONTEXT — 103 的听众、角色与讲法

## 一、听众基准

**用户已定：与 101、102 同一类型的观众，提高与收尾。** 本场以业务熟、对 AI 有初步理解、已经动手搭 Agent、技术能力尚不足以把它搭稳的人为基准。他们能让 AI 做出东西，也知道业务错在哪里，缺少把业务判断转成工作依据、验收证据和持久约束的办法。

不教语法、配置或部署；不假定不会碰代码。提高体现在能判断“问得够不够、检查能证明多少、这次变更后什么还有效”。101 是可以独立满足多数读者的完整概念入门；本场在共同认识上延展业务判断。相同概念可再次使用，重点看它是否支持标准表达、共同理解、接受决定与经验维护，不以零重叠作为质量要求。

**用户补充定调：业务理解更加重要，两头的能力是需求说清楚、验收有方；与 AI 对齐难度高，依赖经验，需要反复打磨，借另一人转述容易失真。** 业务熟不等于已经能把经验完整说出来：具体输出常会暴露原先没说出的例外、优先级和不可接受的后果。

本场将“经验主义”落实为拿具体情境和输出作判断、说出理由、重试并积累可复用的例子；不凭印象随意验收，也不承诺模板填好就一次对齐。业务负责人尽量直接参与 AI 的澄清与结果反馈；技术同事可以协助实现和整理，但关键取舍与原始反馈要回到业务人核对。

## 二、角色与词义

| 词 | 本场含义 | 表达边界 |
|---|---|---|
| 需求负责人 | 确认预期结果、业务规则和取舍的人 | AI 可提建议，不能用默认值填补未获决定的业务政策 |
| 授权者／验收者 | 分别决定允许的动作、接受当前范围结果的人 | 小团队可同一人；清楚其当下是在做哪一种决定 |
| 开发 Agent | 帮人查资料、澄清、设计检查、实现与执行验证的 coding agent | 不与被开发的业务助手混称“它” |
| 报价助手 | 案例中的业务 Agent | 只生成供销售复核的草稿；开发 Agent 才是构建它的一方 |
| 需求说清楚 | 对当前范围的结果、边界、重要取舍与未知去向形成可核对的共同理解 | 不等于一次写完所有细节；不是文档越长越清楚 |
| 验收标准 | 本轮验证前约定用什么可观察表现判断当前范围是否满足要求 | 可随新发现修订，但须业务人确认原因、更新当前依据并重验；不能为迁就输出随手改预期 |
| 验证／验收 | 验证产生证据，验收据证据作接受决定 | 执行者可跑检查；自报、独立 AI 评语都不自动成为验收证明 |
| 反例 | 应被判断为失败、待确认或越界的输入／结果 | 要验证检查真能抓住目标错误，并校对正常情况没有被误伤 |
| Harness | 支持与约束 Agent 工作的外部环境：资料入口、工具、权限、规则、检查和状态等 | 首次出现跟一句“模型外面那一圈”；可以继续使用准确术语 |
| Harness 治理 | 持续维护环境中依据、约束和反馈的有效性 | 需求取舍属于人的业务职责；下一轮调度属于循环控制，二者与环境治理配合 |
| 现行依据 | 当前范围内生效的需求、业务规则和数据来源 | 不能只凭文件日期猜；要有明确状态与唯一维护处 |
| 变更后重验 | 依据变化影响识别哪些检查、证据或授权需更新 | 不等于全量归零，也不等于旧绿灯全部继承 |
| 规则退出 | 在受控条件下验证约束确实冗余后将其撤出当前环境 | 不等于“新模型某次没犯错就删”；业务责任与权限边界不由模型能力升级取消 |

## 三、讲法纪律

1. **一条主问题，一件贯穿案例。** 不按需求工程、测试、治理三个术语章节拼接；先让听众看到同一交付如何因要求、证据或环境失效而不能接受。
2. **每个动作给输入、做法、结果和失败去向。** 表格要有已填例；问题要显示答案怎样改变下一个问题或检查。
3. **Grill-me 是思路来源，出处核准在证据层。** 对客先讲“沿着关键决定追问”，再按需署名；不做技能安装课，不照搬其工具指令。
4. **人被追问的是取舍，可查事实先查。** 推荐答案必须带理由与代价；人确认后才成为决定。不能用连串问题把资料搜索推给听众。
5. **需求与验收互相检验。** 同一句模糊要求出现两个合理预期时，先澄清业务决定，不让实现与验收共同猜一个答案就算对。
6. **证据有适用范围。** 只按草稿字段重算的算术检查不证明业务依据正确；按独立基线验金额也不能替代实际来源和批准核对。样本表现不代表真实整体质量。
7. **检查也要验。** 用会失败的反例和会成功的正常例检查它；AI 评审先用人判过的例子校准，分歧可追问证据。
8. **不把治理讲成多写文档。** 资料指引、机器拦截、人审与失败交接各有位置；实际入口必须命中，绕过后不能仍宣称约束生效。
9. **规则有来路、复核和退出。** 区分局部缺陷修复与可复用的环境改进；安全／业务边界可事先设置，不必等真实事故发生。
10. **变更与清理按风险执行。** 识别影响后再重验；试撤约束要保持其他条件相同、测试原失败与正常行为。不能以一次结果证明永久可靠。
11. **自然中文，必要术语当场说明。** 不沿用 101 的英文出现次数、数字和产品名规则；不用术语密度表达提高，不向该受众抛治理三轴图。
12. **对客内容自成篇。** 不出现本仓库路径、内部项目名、姊妹 talk 页号；合成教学、作者自述、实测和教学建议明确区分。
13. **两头都有业务人，反馈能回到原情境。** 展示具体输出如何逼出隐含标准、业务人如何纠正 AI 的复述；协作者保留原始样例、理由和待确认项，不用一句“更专业”替代原反馈。
14. **对齐靠反复打磨，不保证一次成功。** 区分需求尚未表达完整、AI 理解偏了和实现不符合已定要求；据此补标准、纠正理解或修实现，再测原失败和正常样例。新增标准有明确变更记录，不能悄悄把旧失败改成通过。
