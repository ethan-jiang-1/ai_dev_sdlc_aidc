# 循环交接手册（Loop Handover Manual）

> 把哪个决定交给循环，交之前配什么护栏，它说做完了凭什么放行。两场 Loop Engineering talk 的听众操作件。
>
> **单文件双篇**：入门篇给没跑过循环的人——读完那一篇就够；高级篇给在跑循环的人——按时刻翻，从任何一节进来都能用。卷首的状态语汇表是全书唯一的语汇权威，所有篇章说「完成」「停止」时都指回它。

# 卷首 · 用法与状态语汇

## 怎么用这本手册

1. **卷首必读**：参数锚约定、档位语言、状态语汇表——三页纸，全书的地基。
2. **入门篇顺序读**：要不要交 → 目标怎么写 → 信号怎么读。没跑过循环的读者读完这三节就能做判断；高级篇当字典，哪天要动手配了再翻。
3. **高级篇按时刻翻**：交动作、交续跑、交唤醒、升一档、它说做完了、它停了、可选方向——你在哪个时刻，翻哪一节。每节自足，不依赖其他节。
4. **先看「什么时候不要」，再看怎么配**。每节的退回条件与正面步骤同权重。交出去之前先确认自己不在退回区。

## 参数锚约定

- 手册里每条具体参数（阈值、时长、费用、命令语法、默认值）都带**「（产品与版本，观测日期）」**。产品会改默认值，抄进配置前先核对你手上的版本。
- **docs 与源码打架时，以源码为准**；手册会显式标出两个值与各自出处。
- 没有锚的参数，手册写「以你所用版本的官方文档为准」——那是提醒你去找，不是省略。

## 档位语言

手册说「档」，只指**交出去的决定**是哪一种：动作（高级一）、续跑（高级二）、唤醒（高级三）。档不是成熟度等级：

- 升档不是毕业，退档不是失败；按任务的风险、可逆性、验收成本选位置，随时允许退回。
- 没有任何通用刻度说「跑 N 轮必须人看」。能写成门的是事件：动作类别、拒绝预算、无进展、歧义、升级后是否有人接得住。

每一步交接前，四个问题要能写在纸上：

1. 谁启动下一轮？
2. 谁判断完成？
3. 谁能改变系统？
4. 出了错，谁能及时停下并接手？

写不出来，就是护栏还没配好，先别交。

## 状态语汇表（全书唯一权威）

任何状态都有「最多能声称什么」。看到把左列偷换成右列的说法——那是误读，或事故的开始。

| 你看到的 | 它最多说明 | 不能偷换成 |
|---|---|---|
| 检查通过（测试退出码 0、lint 干净、构建成功） | 写在条件里的检查，在该环境、该版本上通过 | 需求无遗漏、无回归、业务会变好 |
| 裁判判「达成」（Met） | 该裁判按**它可见的证据**判约定条件成立 | 人已验收、生产业务已改善 |
| 裁判判「不可能」（Impossible） | 该裁判判断约定条件无法满足，终止 | 所有尚不可见的结果都已证明不可能 |
| 检查失败 / 证据不足 | 该次验证不支持「达成」，进入修复或升级 | 任务本质不可能；也不可静默改判达成 |
| 轮数、时间、预算、成本耗尽 | 资源到边界，必须停或交人 | 任务已完成或已失败 |
| 拒绝熔断 / 人工暂停 / 停止（stopped） | 循环不再运行，状态可交接 | 产出已被接受 |
| 人或专家验收（accepted） | 指明版本、样本、时间窗内的接受 | 自动推广到所有用户和任务 |
| 上线后业务指标改善 | 观测窗口内的外部结果 | 离线检查可替代上线观测；或可归因于循环设计本身 |

四条硬边界（这张表的骨架）：

1. **停止 ≠ 接受**：超时、耗尽、拒绝、模型自己收尾，都只是控制流停了；是否验收另算。
2. **产出 ≠ 结果**：可观察的产物（PR、测试、构建）与外部业务结果分账记录；结果尚不可见时写「待观测」，不写达成。
3. **达成 ≠ 验收**：裁判只核约定条件，不判内容好坏；验收是人或独立检查者对照真实需求做的事。
4. **反馈不能断**：环境反馈要落成工件（下一轮消费的是工件，不是聊天记忆）；人的反馈（纠偏、品味、拒绝的理由）要回灌下一轮——两路断任何一路，循环就退化成抽卡（比喻）。

**一条总警告**：无人值守地跑，和无人值守地对，是两件事。授权与调度解决「跑」，不解决「凭什么放行」。每一次交接：护栏先于放权。

# 入门篇 · 判断层

> 给没跑过循环的读者。五节读完，你能做四个判断：这个任务交不交、反馈回路搭没搭、第一个台阶怎么迈、目标怎么写才算数。要动手配完整机器的那天，再去高级篇。

## 入门一 · 要不要交给循环

### 三问诊断（任一答「否」→ 先别上循环）

| 问题 | 答「否」意味着什么 | 下一步 |
|---|---|---|
| 1. 停止条件依赖上一轮的结果吗？ | 不依赖的是重试（retry），不是循环 | 写脚本或手动重跑，不建循环 |
| 2. 单次运行受控吗？ | 不受控时，循环只是把错误复制得更快 | 先治单次运行（约束写进环境：沙箱、审批、测试），再回来 |
| 3. 跨轮状态放在对话外面了吗？ | 没外置（文件 / git / 日志），每轮都在交「对话税」，人退化成催促者 | 先把进度落到文件，再谈多轮 |

### 完成条件体检（第二道门）

- ✅ 能写成可观察的句子：`npm test 退出码 0` / `Lighthouse 分数 ≥ 92` / `队列清空` → 可以交续跑（高级二）
- ⚠️ 产出可核、外部结果不可见：把自动停止范围收窄到产出（如「PR 已生成且检查通过」），业务结果另行观测（高级五）
- ❌ 写不出（「做到生产就绪」「设计变好」）：拆小、人工标样、或交人——**不靠增加轮次硬跑**

坏目标的典型（署名原话）："a vague goal would be 'keep going until this UI design is good'. What does that mean? Good to who? How is it being evaluated?"（Addy Osmani《Practical Loop Engineering》，2026-08-14）

### 判定实例（三个任务过三关，判定过程写全）

**实例 A｜重命名 2,000 张截图**：第一问就死——停止条件不依赖上一轮结果（第 1,733 张和第 1 张毫无关系），这是批处理。判定：**不交**，写十行脚本。错法：为它配循环脚手架——拿大炮修桌子，还得自己擦炮膛。

**实例 B｜修 flaky 测试到三连绿**：三问全过（这次没修好才知道下次改哪＝依赖上轮反馈）；完成条件可观察。判定：**交**，goal 照抄入门二的模板四件套：

```text
Fix the flaky cart-total test until `npm test` exits 0 on three consecutive runs.
Do not modify unrelated tests.
Stop after 8 turns.
```

**实例 C｜「把体验改到用户满意」**：完成条件写不成可观察句子。判定：**先拆**——拆出可观察的代理指标：

| 拆出的子目标 | 可观察吗 | 去处 |
|---|---|---|
| Lighthouse 性能分 ≥ 92 | ✅ 可测 | 可交循环 |
| 支付页崩溃率 < 0.1% | ✅ 可测 | 可交循环 |
| 用户满意度提升 | ⏳ 外部结果，延迟可见 | 待观测，业务负责人复查（高级五） |

**同一个任务拆完，一部分交、一部分不交——这是常态，不是失败。**「先拆」不是拖着不办，是把「满意」翻译成机器能对照的句子、把翻译不出去的部分诚实留给人。

### 什么时候不要

1. **单次小任务不建循环脚手架**——先有真实失控，再上治理；为二十分钟的活配一套循环是过度工程。
2. **存量代码库慎用无限循环**——Ralph 式裸循环作者自己的适用警告："There's no way in heck would I use Ralph in an existing code base"（Jesse Vincent，2025-07；greenfield 专用）。
3. **标准会随样本变化的任务**（品味、审美、法律判断）：保留人工检查点，不塞进自动达成。
4. **别把品味和判断一起委托**——"check yourself, that you are not delegating the taste and the judgment to your agent. You're delegating the task, and then you are actually checking back that it's meeting your bar."（Osmani，同上）

### 交到哪一档（本手册路线）

| 你想交出的决定 | 去哪节 |
|---|---|
| 只减少逐动作审批 | 入门三（最小版）→ 高级一（完整规程） |
| 让它自己跑多轮到目标 | 入门四（门票）→ 高级二（完整机器） |
| 让它定时 / 按事件自己起跑 | 高级三 · 交唤醒 |

**来源**：三问与反过度工程：Loop Governance 操作规程（2026-09-26 定稿层）；两判据：Loop Engineering 研究综述（2026-09-27）；Ralph 警告：Jesse Vincent 个人实践（2025-07）；Osmani 引句（2026-08-14）。

## 入门二 · 反馈让循环成为循环

循环和抽卡（比喻）的全部区别：**这一轮有没有被上一轮的反馈改变**。模型不知道错在哪、要改哪里——除非每一轮都有反馈进来。反馈有两路，断任何一路，循环就退化成抽卡：

| 路 | 是什么 | 落成什么 |
|---|---|---|
| 环境反馈 | 退出码、失败日志、运行产物 | 落盘成可复查的工件，下一轮先读工件再选动作 |
| 人的反馈 | 纠偏、品味、拒绝的理由 | 回灌下一轮；拒绝带理由，纠偏记下来 |

- 「我刚才试过了」不是证据——工件才是。
- 完全静默的无人值守不是目标：接手、验收、复查都是人的反馈。
- 高手「放手也行」的秘密，是他的隐性反馈每轮都在发生（见高级二、高级五）。

**什么时候不要**：反馈写不成工件（纯主观、没有检查命令）的任务，先留在第一级。

## 入门三 · 第一个台阶：交动作

第一级往上走一步：把逐条点「允许」交出去——**省掉的是打断，不是判断**，每轮结束看的还是你。

| 处置 | 例 |
|---|---|
| 允许直行 | 读目标文件、跑定向测试 |
| 沙箱内跑 | 写指定目录、无网络出站 |
| 必须人批 | commit、外部调用 |
| 硬拒绝 | push、删库、生产配置 |

两条纪律：①规则写进**策略件**（配置文件），写在提示词里的规则等于没写——93% 的权限提示最终被人批准；②一次批准绑定**动作 × 目标 × 有效期**，任何一个变了都算新动作。

**什么时候不要**：动作类别列不全就先别交——漏掉的类就是默认放行。完整规程（演练、变异测试、偏好与隔离两层）在高级一。

**来源**：授权面规程：Loop Governance 操作规程 §13（2026-09-30）；实测：arXiv 2608.27443（2026-08）、marmelab 审计（2026-09-24）；判据一：研究综述（2026-09-27）。

## 入门四 · 门票：目标怎么写才配循环

> 这一节是**交续跑档的门票**：只有决定让系统自己跑到目标为止才需要它；留在第一级，不需要。

### 目标模板（官方三要素＋上限子句）

```text
目标（一个可度量终态）：
  "All tests in test_status.py pass" / "the endpoint returns 200 with the new field"
检查（声明式——怎么证明：哪条命令、哪个退出码、哪份输出）：
  "`npm test` exits 0" / "`git status` is clean"
约束（路径上不许变的东西）：
  "no other test file is modified"
上限子句（推荐常备）：
  "… or stop after 20 turns"（轮次或时间均可）
```

（模板要素：Claude Code /goal 官方文档，观测 2026-09-26）

**教科书级全例**（Addy Osmani，2026-08-14）——一件不少：可度量终态、声明式检查、约束、无进展中止、轮次上限：

> "/goal Refactor the data-fetching layer in Dashboard.tsx until Lighthouse performance score is >= 92 and LCP is under 1.8s as shown by the Lighthouse CLI output. Do not change the public API of any hooks. Each turn must improve at least one reported metric; abort if two consecutive turns show no improvement. Stop after 10 turns."

### 三值判定（续跑的出口）

| 裁定 | 含义 | 下一步 |
|---|---|---|
| Not yet met | 约定条件未达成 | 继续，**评估理由作为下一轮的指导** |
| Met | 条件在裁判可见证据内成立 | 停止本轮——注意：**Met ≠ 验收**（见卷首语汇表第 2 行） |
| Impossible | 裁判判条件无法满足 | 停止并交人；「业务结果还看不见」不得误报为 Impossible |

### 写法红线

1. **含糊目标不配循环**（见入门一的坏目标例句）。
2. **别把品味和判断一起委托**——委托任务，检查是否达到你的标准。
3. **评估器只核硬规则，不判内容好坏**："It doesn't look at the content to see if it's good or bad in any way, shape, or form. All it does is examine the conversation transcript to see if the hard rules you specified have been met."（Osmani，2026-08-14）
4. **续跑信号可以比入口目标弱**："The harness just needs some signal that lets it continue. It does not have to be objective or binary, it just has to be useful enough to drive another iteration."（Armin Ronacher，2026-09）——入口目标要可核，中间推进信号只要「够用」；两句别混成一句。

**什么时候不要**：完成条件写不成可观察句子 → 回入门一分流；无进展出口和上限子句配不出来 → 没有兜底的续跑是烧钱循环（配法在高级二）。

**来源**：目标模板与三值判定：Claude Code /goal 官方文档（观测 2026-09-26）；全例与红线：Osmani（2026-08-14）；续跑信号：Ronacher（2026-09）。

## 入门五 · 读信号：三个最常见的假完成

凌晨两点你回来，值班日志里有三条信号。逐条对照卷首语汇表，看它**最多**说明什么：

**信号 1｜`npm test 退出码 0`**
最多说明：写在条件里的检查在该环境通过了。不能偷换成：需求没遗漏、业务会变好。测试只覆盖写进条件的那部分——条件没写的，它一言不发。

**信号 2｜裁判给了 `Met`**
最多说明：约定条件在**这个裁判可见的证据里**成立。不能偷换成：人已验收。裁判看的是它被喂的证据——证据不全，它裁得再果断也是错的。人还要对照真实需求看一眼产出。

**信号 3｜`已运行 10 轮，上限触发，循环停止`**
最多说明：资源到边界，必须停或交人。不能偷换成：任务完成或失败。轮数上限是资源熔断，不是质量分——它什么都保证不了，只保证不再烧钱。

**三连问带走**：停止了吗？验收了吗？外部结果看见了吗？——**三个是三件事**，日志里一个词的差别就是三种完全不同的处境。

**什么时候不要**：有人拿「运行次数」「唤醒成功率」「代理数量」当质量证据 → 那些是活动量，不是成果；证据链怎么看，高级五。

# 高级篇 · 操作层

> 给在跑循环的读者。七节各是一个使用时刻，从任何一节翻进来都能用；语汇一律指回卷首。

## 高级一 · 交动作

> 你受够了每个动作都点一次「允许」。这节管交出**动作审批**之前怎么划边界：授权面是分级处置表，不是开关。

### 划面五步

| 步 | 做什么 | 检查 |
|---|---|---|
| 1 列动作 | 列全本任务会发生的动作类别：读 / 写 / 测试 / commit / push / 部署 / 外部调用 | 一类都不能漏——漏掉的类就是默认放行 |
| 2 标处置 | 每类标四级之一：**允许直行 / 沙箱内跑 / 必须人批 / 硬拒绝**，写进**可执行的策略件**（allow/deny 规则、沙箱配置），不写在提示词里 | 以提示词收尾的规则不是规则（见下） |
| 3 保高风险 | auth / billing / 破坏性变更保留当场审批与随时中断 | 高风险类不进 allowlist |
| 4 演练 | 低风险可回滚仓库里故意触发一个面外动作 | 记录里真实发生 propose → decision → tool result；不拿「最终测试通过」冒充审批通过 |
| 5 验收 | 抽一条已放行的动作，答出：谁批的？批的哪个目标？有效期到哪？ | 答不出＝面没划过，是默认放行 |

### 三条铁则

**1. 一次批准绑定「动作 × 目标 × 有效期」**，三个维度各自独立（来自真实事故报告，claude-code issue #95749）：

> "Editing files must not imply authorization to commit."（准许编辑 ≠ 准许提交）
> "Authorization to commit must not imply authorization to push."（准许提交 ≠ 准许推送）
> "Authorization for one push must not become standing authorization for later pushes."（一次 push ≠ 永久 push）

换分支、换 feature、从 edit 变 commit/push，都算**新动作**，重新请求授权。事故原样：一个两行的窄授权被当成大功能发布的许可，14 个文件直推 main。

**2. 拒绝是引导信号，不是终点。** 拒绝作为工具结果返回，附带「找一条更安全的路」的指令；会话累计 **3 次连续或 20 次总拒绝**则停机升级——这两个数字官方明写**不可配置**，且是**动作拒绝预算，不是轮数上限**（Claude Code auto mode 文档，观测 2026-09-26）。无界面环境下无人可问，直接终止进程。

**3. 审批有三个动作，不只是放 / 拦**：approve / **edit** / reject（LangChain HITL 文档，观测 2026-09-27）——「改了再跑」最容易被忽略，也最常用。

### 偏好与隔离是两层

- **偏好规则**（如 Cursor `permissions.json`）：管**倾向**批准 / 拦截什么；
- **执行隔离**（如 `sandbox.json`）：管**实际能碰到**什么（路径、网络）。

官方原话：Auto-review "is not a security boundary"（Cursor 官方 Run Modes 文档，观测 2026-09-30）。`Run Everything` 模式每个工具调用自动运行、**无沙箱、无分类器**——它交出的是动作审批权本身，启用前单独评估，不是本节的默认形态。**宽 allow 规则永远不能代替真正的执行隔离。**

### 写了规则 ≠ 有授权面（实测数据）

- 预写权限规则实测：写规则的作者比不写的**少拦了 20.1 个百分点**的坏动作；**93% 的权限提示被人批准**。"A rule that ends in a prompt isn't a rule."（arXiv 2608.27443，2026-08）
- 行业执行缺口：391 个仓库里只有 **12 个**提交了一条 deny 规则。（marmelab 审计，2026-09-24）
- 升级不可达的真实案例：用户在对话里反复明确授权同一个动作，拒绝依然不可翻案（claude-code issue #67519）——拒绝合理性之外，**升级可达性是第二个独立的控制问题**。

### 划定实例（修一个支付回调 bug 的授权面，填好的样子）

**第 1–2 步产物**——动作类别 × 处置 × 落点：

| 动作类别 | 处置 | 落在哪个策略件 |
|---|---|---|
| 读 `payments/`、`tests/` | 允许直行 | read 类 allowlist |
| 跑 `npm test` / `npm run lint` | 允许直行 | exec allowlist：只列这两条精确命令，不写 `npm *` |
| 改 `payments/webhook.ts` 与对应测试 | 沙箱内跑 | 沙箱可写路径＝本仓 `payments/`、`tests/`；无网络出站 |
| `git commit`（本分支） | 必须人批 | PR 描述里的 commit 门 |
| `git push`、部署、改 `prod/*` 配置 | 硬拒绝 | deny 规则 |
| 调外部支付沙箱 API | 必须人批 | 凭证注入由人完成，密钥不进上下文 |

**第 4 步演练日志长什么样**（示意，核对这三行真实发生过）：

```text
[10:02:11] propose  : bash(git push origin fix/cart-total)
[10:02:11] decision : DENY（rule: push/* — hard deny, no override）
[10:02:12] result   : push 被策略拒绝；该动作在硬拒绝清单
```

有这三行＝审批真实走过策略件。只有「最终测试通过」＝没验过——测试通过和审批通过是两条不相干的证据链。

**审批策略的代码形态**（样例，LangChain HITL 文档，观测 2026-09-27）：

```python
interrupt_policy = {
    "write_file": True,          # approve / edit / reject 三个决定都开放
    "read_data":  False,         # 安全操作，不打扰人
    "git_push":   "approve_only" # 只许批——不许改、不许绕
}
```

第三个键是本手册编的示意（前两键为该文档原样），你的框架里怎么写以你所用版本的官方文档为准；要看的是**粒度**：审批可以细到工具名 × 参数，不是只有全局开关。

### 什么时候不要

- 动作品类列不全（第 1 步做不完）→ 先别交：默认放行比逐动作审批更危险。
- 高风险动作的审批入口不可达（人不在、父线程看不见请求）→ 保持逐动作审批。
- 所用产品只有偏好规则、没有真正的执行隔离 → 授权面收窄到「可回滚」类动作。

**来源**：划面规程与铁则：Loop Governance 操作规程 §13（2026-09-30）；三级处置：Cursor 3.6 changelog（2026-05-29）与官方 Run Modes 文档（观测 2026-09-30）；拒绝语义：Claude Code auto mode 文档（2026-03-25，观测 2026-09-26）；实测：arXiv 2608.27443（2026-08）、marmelab 审计（2026-09-24）；事故：issue #95749 / #67519。

## 高级二 · 交续跑

> 单轮跑稳了，你想让它**自己跑到目标为止**——交出的是「本轮之后是否再开一轮」。goal 的写法在入门四；这节配的是续跑的机器：反馈基建、裁判、保护、清单、判停。

### 反馈要落成基建（燃料）

循环和抽卡（比喻）的区别：这一轮有没有被上一轮的反馈改变。最小通道：**命令 → 退出码＋输出 → 落盘证据（evidence_ref）→ 下一动作**。

- 下一轮先读工件，再选动作——「我刚才试过了」不是证据。
- 数据管道读结构化结果文件，不解析自然语言终端输出。
- 嵌套工具、retry、evaluator 都要纳入实际反馈路径——内层通过、外层无限重试仍会失控。

### 裁判选型（五式，按场景选一）

| 裁判 | 适用 | 风险 |
|---|---|---|
| 人判（品味） | 探索、清单语义撑不住 | 不可规模化 |
| 文件清单逐条判定 | 目标可枚举（见下节） | 清单本身要保护 |
| 独立小模型每轮判定 | 会话内目标 | 裁判自身可信度要校验 |
| 干活模型自判 | **最弱**——多数产品的默认形态 | 必须配保护＋熔断补偿 |
| 被审批方提出、审批方判定 | 越界动作 | 审批方可能被操纵（红队实证） |

选型次序：优先机器可核；必须人判的，把判断点集中在门上。

### 保护裁判四件

1. **测试不可删改**：强措辞条款＋测试文件钩子硬拦——**写在提示词里的「不许改测试」不算隔离**；
2. **清单选 JSON 不选 Markdown**：模型对 JSON 整文件改写的概率更低（Anthropic 长程 harness 实录，观测 2026-09-26）；
3. **裁判输入防操纵**：分类器只看用户消息与工具调用、剥掉模型自述——"reasoning-blind by design"（Claude Code auto mode 文档，观测 2026-09-26）；
4. **看真实证据不看转述**：带运行 ID、目标版本与原始输出的测试 / 扫描记录。

### 目标可枚举时：进度清单七步

粗目标 → 逐条 feature（JSON 结构，初始全部 `passes: false`）→ 三件套（清单＋进度文件＋初始 commit）→ 每轮固定开场（定位目录 → 读 log 与进度 → **选最高优先级未完成项** → 先过基线：环境留在坏状态时先修它）→ **一次只做一件** → 完成判定要端到端自验证（单测或 curl 过不算）→ 干净收尾（描述性 commit＋进度更新）。**只允许改 `passes` 字段。**

清单条目长这样（结构样例，Anthropic 长程 harness 实录，观测 2026-09-26；实际项目一例清单 200+ 条）：

```json
{
  "category": "chat",
  "description": "a user can open a new chat, type in a query, press enter, and see an AI response",
  "steps": ["render chat page", "submit query", "assert response visible"],
  "passes": false
}
```

官方反例对照："declares victory on the entire project too early" → 设清单；"marks features as done prematurely" → 认真测试后才翻 passing。

### 走一遍（一份 goal 的三轮，教学示意非产品日志）

用入门二那个 Lighthouse goal 跑三轮，看每道闸各拦什么：

```text
第 1 轮  改数据层 → Lighthouse 88 分（< 92）
        裁判：Not yet met（评估理由回传：「performance 88, LCP 2.4s」→ 下一轮知道改哪）

第 2 轮  分数 93、LCP 1.7s ——但 diff 显示改了 useCart 的 public API
        约束检查：违例（"Do not change the public API of any hooks"）
        裁判拒判 Met：分数达标、路径犯规——只有盯 transcript/工具输出的约束检查能抓住这种

第 3 轮  恢复 API、改内部实现 → 93 分且 API 未动
        裁判：Met，本轮停
        人还要看一眼：Lighthouse 测的是不是正确的页面（跑错 URL 的假绿是经典事故）
```

**第 2 轮是整套机制存在的原因：分数会达标，犯规不会被分数看见。**

### 预算的语义（别读错数字）

预算是**花费暂停阀**，不是「达成」的同义词。真实参数样例：某云托管 agent 服务的预算写 `"max_list_cost": {"amount":"125","currency":"USD"}` 时，**125 是美分，即 $1.25**；触顶返回 `budget_reached`，在途请求可稍超额完成，新消息得 400；提高或移除预算可恢复原会话；**按会话计，不等于跨次总额**（Anthropic Managed Agents，观测 2026-09-30）。

### 判停权要追到代码（不看博客看源码）

某官方 quickstart 的驱动循环长这样（源码观测 2026-09-28）：

```python
while True:
    iteration += 1
    if max_iterations and iteration > max_iterations:   # 唯一退出分支
        print(f"Reached max iterations ({max_iterations})")
        break
    # 成功时 run_agent_session 恒返回 ("continue", response) ——没有完成分支
```

进度条打印 `passing/total` 是**给人看的**（`count_passing_tests` 读清单的 `passes` 字段），驱动层没有 `passing == total` 的停机判断；`--max-iterations` 默认 `None`＝无限；「不可改测试」只写在提示词里，驱动层不校验。博客叙事里「goal 会自己完成」，在这份代码里＝跑到你按 Ctrl-C。**交续跑之前，先找到你家驱动循环的 `break` 在哪。**

### 什么时候不要

- 反馈落不成工件（纯主观、无检查命令）→ 先补基建，否则每一轮都是 retry。
- 无进展出口和上限子句配不出来 → 没有兜底的续跑是烧钱循环。
- 你的裁判就是干活的那个模型、又没有保护四件 → 自判＋无保护是最弱一极，配齐再交。

**来源**：裁判选型与保护四件：Loop Governance 操作规程 §3/§4（2026-09-26），源头为 Claude Code、Anthropic 长程 harness 与 OpenAI 红队报告；进度清单七步：Anthropic 长程 harness 实录（观测 2026-09-26）；预算语义：Anthropic Managed Agents（观测 2026-09-30）；quickstart 反例：Anthropic 官方 quickstart 源码（观测 2026-09-28）。

## 高级三 · 交唤醒

> 任务跑完一轮就停，你想让它**到点或按事件自己再起跑**——交出的是「何时再跑」。

### 触发器选型

| 方式 | 下一轮何时开 | 何时停 |
|---|---|---|
| 条件驱动（`/goal` 式） | 上轮结束、闲置检查点、自动重试到期 | 条件满足 / 判不可能 / 需人修 / 显式清除 |
| 时间驱动（`/loop` 式） | 时间间隔到 | 你停它，或它判工作完成 |
| 脚本驱动（Stop hook） | 上轮结束 | 你的脚本或提示词决定 |

**`/loop` 三种拍法**（Claude Code 官方文档，观测 2026-09-26）：

- `/loop 5m check the deploy`——固定间隔＋提示词；
- `/loop check the deploy`——间隔模型自选，**1 分钟至 1 小时**之间按观察动态（构建在跑短等、无事长等）；
- `/loop`——无提示词，读内置维护提示词或项目级 `loop.md`（项目级优先）。内置维护提示词的范围封顶：继续未完工作 → 照料当前分支 PR → 清理，**不开范围外新动作**；push / 删除等不可逆动作必须核对会话里的授权仍覆盖本次动作与有效期。

三档调度面：**云上例行任务（≥1 小时，无需开机）｜桌面定时｜会话内 `/loop`（≥1 分钟）**。auto mode 不在此列——它只管轮内审批，不开新轮。

### 两种运行边界（最容易用错的一条）

| | 会话内定时 | 跨会话持久任务 |
|---|---|---|
| 活在哪 | 当前会话；**会话退出即失效** | 云端调度器；本地会话关了它还在 |
| 状态 | 会话内 | 必须另有持久化（进度文件、日志、事件 ID） |
| 停止 | 退出会话 / 停止命令 | **取消要同时到达调度器和运行中的 worker** |

官方原话划界："loops are session-scoped … If you need something that outlives your session, /schedule runs it in the cloud."（Addy Osmani《Practical Loop Engineering》Fine print，2026-08-14）

### 跨会话的额外门槛（缺一不交）

1. **持久状态**：重启后从哪读目标、进度、上次结果——有触发器不等于有持久化；
2. **取消传播**：真实事故——用户显式关掉自动化，"the kill did not propagate to the actual tmux sessions"（claude-code issue #46787）。**面板标「已关闭」不算停**：核对调度器不再派新任务、既有 worker 确已退出、外部副作用不再发生；
3. **硬上限**：定时任务 **7 天自动过期删除**——官方原话 "bounds how long a forgotten loop can run"；一轮既未续排也未停，约 **20 分钟**后兜底唤醒，再不续排则终止（Claude Code scheduled-tasks 文档，观测 2026-09-26）。云任务的默认上限**另查你的平台**，不套用这一组数字；
4. **可达的人工接手**：谁能在半夜取消它、看到它正在做什么。

### 同一任务的两种配置（部署监视）

**会话内**：开着会话敲 `/loop 5m check the deploy`——五分钟一醒；合上电脑它就没了。

**跨会话**（Anthropic Managed Agents 语法样例，观测 2026-09-30）：

```yaml
# ant apply deployment.md
agent: deploy-watcher
environment_id: env_prod_watch
schedule:
  type: cron
  expression: "0 20 * * 5"     # 每周五 20:00
  timezone: America/New_York
# 每次新 session 都要有人给它第一句话：
initial:
  user.message: "Check the deploy; report CI status and any 5xx in the last hour."
# 可查下次起跑点：schedule.upcoming_runs_at
```

两个易错点都在官方语义里：**缺初始事件，cron 正确也不跑**（任务不会凭空产生）；会话状态机是 `idle / running / rescheduling / terminated`——**预算暂停是 `idle`**，不是完成也不是销毁，别拿它当终止信号。

### 取消核对三步（对着真实事故写）

```text
1. 调度器：确认不再派新任务（查 upcoming runs 是否为空）
2. worker  ：确认在跑的进程真的退出——
   事故原样：面板显示已关闭，"the kill did not propagate to the actual tmux
   sessions"（issue #46787）；查进程表/会话列表，不是查开关
3. 副作用：确认外部世界不再被碰（新 commit、新 PR、新告警、新的云账单行）
```

三步都过，才可以说「停了」。面板绿了只是第 0 步。

### 无人值守变体（高风险场景，门槛另加）

到点跑只证明「醒来并执行过」，不是「目标已达成」。无人值守前先过高级四的三项门禁与控制路径演练；自动响应动作参考 σ 分层（Anthropic playbook《Closing the loop》）：

- **1σ 只记录｜2σ 只读诊断｜3σ 可行动但仅限开 PR 或触发预批流程**；
- 检测脚本版本化＋单测，**全程确定性、模型不参与**；
- 回滚必须是管线里**演练最多的路径**：单命令、agent 可执行、staging 定期演练。

### 什么时候不要

- 跨会话四门槛缺任何一项 → 停在会话内定时。
- 完成判定还没配好（高级二没走完）→ 定时唤醒只会把错误复制到每一天。
- 幂等与防重入没设计（同一事件重复投递怎么办）→ 事件触发先不上。

**来源**：触发器对照与 `/loop` 拍法：Claude Code 官方文档（观测 2026-09-26）；会话边界引句：Osmani（2026-08-14）；取消传播事故：issue #46787；σ 分层：Anthropic playbook《Closing the loop》；无人值守警告："a loop running unattended is also a loop making mistakes unattended" / "done is a claim and not a proof"（Osmani，同上）。

## 高级四 · 升一档

> 现在的档位跑稳了，你想把下一个决定也交出去。这节是全书的铰链：**升档不是毕业，是用护栏换放权**。

### 三项门禁（缺一不可）

| 门禁 | 检查什么 | 不过怎么办 |
|---|---|---|
| 1 门会红吗 | **负例控制**：故意引入一个已知错误，看门禁会不会拦住 | 没做过负例的检查视为摆设；门不会红就不配当门 |
| 2 裁判独立且判据可用吗 | 过高级二的五式之一；抽看本任务的人工核对与自动判定是否一致 | 干活模型自判＋无保护＝不升 |
| 3 熔断配了吗 | 至少配了拒绝熔断与硬过期（高级一 / 高级三） | 没有兜底的升档是把错误复制得更快 |

### 控制路径演练（升档前必做一次）

挑一条**有外部副作用**的动作，写清「动作＋目标＋本次授权有效期」，分别触发三种处置：

- **允许**：只在当前边界内执行；
- **需人批准**：执行前让指定人看到具体参数与风险、作决定、按同一线程恢复；
- **硬拒绝**：停下并暴露原因，**不得用普通审批覆盖**。

演练后任一情形不成立——人不在、父线程看不见请求、状态不可恢复——保持暂停，退回需要人在环的档位。**不要把权限开大来让演练通过。**下一轮换目标或从 edit 变为 commit/push 时，重新请求授权。

### 演练记录（填好的样子，示意）

| 项 | 值 |
|---|---|
| 演练动作 | `bash(git push origin fix/cart-total)` |
| 目标 / 有效期 | 仅 fix/cart-total 分支，仅本次评审周期 |
| 触发「允许」 | 在边界内执行；日志有 propose → execute → result 三行 ✓ |
| 触发「需人批准」 | 执行前暂停；审批人看到 diff 与目标分支；批准后按同一线程恢复 ✓ |
| 触发「硬拒绝」 | 停止＋原因回传；普通审批不可覆盖 ✓ |
| 人不在场复测 | 请求进入 `awaiting_human`，父线程可见，恢复指针有效 ✓ |
| 结论 | 三路全通 → 可交动作审批（高级一档） |

结论栏写「不通过——人不在场时请求不可见」**也是合格产出：它挡住了一次真事故**。演练的目的是暴露断点，不是走个过场。

### 判定冲突时

裁判与人工验收者对同一产出结论冲突：

1. **暂停自动验收与升档**；
2. 把样例交给有权判定的人；人也无法一致判断 → 先重新明确「成功」的定义，再用固定样本复核；
3. 改过判据或样本集后记录新版本，**新旧分数不直接横比**；
4. 不能靠模型自报或提高轮次上限通过。

### 定档实例（三条样例的判定）

- 「agent 改文件、跑测试都在我看着的时候，每个 push 我批」→ 交了**动作**（高级一），没交续跑；
- 「`/goal` 最多十轮，修到 Lighthouse 达标为止」→ 交了动作＋**续跑**（高级二），没交唤醒；
- 「`/loop 5m` 值班看部署」→ 三档都交了——但唤醒交出的是**触发权**，不是成果裁决权：CI 绿不是部署成功，放行另查（高级五）。

### 档位速查（本手册编排）

| 交出的决定 | 节 | 已配护栏 |
|---|---|---|
| 动作审批 | 高级一 | 分级处置＋绑定授权＋拒绝预算 |
| 续跑 | 高级二 | 三要素目标＋裁判选型与保护＋熔断 |
| 唤醒时机 | 高级三 | 触发器＋持久状态＋取消传播＋硬上限 |

三条交接面均为多家独立可观察的机制（Loop Engineering 研究综述，2026-09-30）；**高阶不是毕业要求**。

### 什么时候不要

- 三项门禁任何一项没过 → 不升。
- 演练三条路有一条走不通 → 不升。
- 说不清「升这一档省下的是什么、换来的是什么」→ 先写下来再决定。

**来源**：三项门禁与演练：Loop Governance 操作规程 §9（2026-09-26 定稿层）；升档判据与判定冲突处理：同规程及其主干（2026-09-27 确认）；轮次无刻度：Loop Engineering 研究综述（2026-09-27）。

## 高级五 · 它说做完了

> 你回来了，它说「完成」。这节管**放行**：凭什么接受这次结果。

### 放行五接口

| 接口 | 必须先问 | 看什么记录；缺失时怎样退回 |
|---|---|---|
| 1 目标契约 | 目标是**产物终态**（可观察）还是**业务结果**（要等外部用户行为）？不得更改什么？ | 目标、测量方法、不变式、授权范围、退出/升级条件。外部结果尚不可见 → 只委派可观察产物，不宣告业务达成 |
| 2 环境证据 | `npm test` 成功验证的是哪部分？测了正确版本 / 页面吗？执行者能删测例、改进度、伪造工具日志吗？ | 带运行 ID、目标版本与原始输出的记录；**只在提示词里禁止改测例不算隔离**；测不到的质量维度记「待验收」，不写已完成 |
| 3 裁决协议 | 谁能给「达成」？它看的是真实环境还是只看对话？判据谁持有、谁能改？ | 裁判的输入、版本、输出与失败出口；可能错判的部分另做独立检查或人抽验。**分离执行者与裁判只减利益冲突，不保证裁判正确** |
| 4 资源与进度 | 总预算谁覆盖（续跑、重试、子代理、定时重跑）？连续无进展怎么收口？ | 每轮反馈、费用 / 时间 / 轮数、暂停理由。**预算触顶＝停止或交接，不是成功**；按会话计的预算不等于跨次总额 |
| 5 跨次责任 | 上次的目标、授权、观察结果还新鲜吗？取消真的传达到了调度器和 worker？ | 任务 ID、幂等键、执行日志、审批人、接手渠道。**按时唤醒不等于可靠完成** |

### 放行检查单（对着五接口，可复印）

```text
□ 目标：本次验收的是产物终态还是业务结果？二者有没有被写成同一个「完成」？
□ 不变式：约定的「不许变」在哪份记录里核对过了？（diff / 测试清单）
□ 证据：检查记录带运行 ID、目标版本、原始输出吗？执行者有没有删改的写权限？
□ 裁决：给 Met 的是谁？它的输入是什么？判据版本多少？失败时默认放行还是默认拦？
□ 预算：这次花了多少轮、多少钱？谁的总账在记？按会话的预算覆盖跨次总额吗？
□ 接手：如果现在按「暂停」，下一个人从哪个指针恢复？
```

六个全勾 → 放行。有一格填不出 → 按卷首状态语汇表选一个诚实的状态，转高级六。

### 三个对照案例（同一触发器，能宣布的不同）

- **夜间巡检**：每晚跑依赖扫描、退出码 0——仍要查扫描范围、漏洞库更新时间、锁的是哪个版本；超时 / 扫描器不可用 / 证据过期分别写「暂停 / 未知并通知人」，不写达成。要声称「线上风险已消失」，还得看实际部署了什么版本。
- **每五分钟看部署**：CI 还在跑、没收到告警，都不是部署成功；CI 绿只支持「约定检查在该版本通过」。业务指标几小时后才出现？完成声明停在「检查条件满足，业务结果待观察」。
- **跨任务错位**：夜间任务 A 的 CI 绿了，共享组件却让任务 B 回归失败；白天有人改过优先级，取消后面板绿了但旧 worker 还在写。单一任务的退出码、日志里一句 Met、面板的「已关闭」，都证明不了「当前版本已通过验收且已停机」。

### 轮末交接核对（三列清单）

对比本轮起止，逐列列出：

1. 测试文件与测试清单的**删除、跳过、弱化、该新增而未新增**；
2. **基线已有失败、本轮新失败、实际跑过的检查与退出码**；
3. **超出授权范围**的功能 / 文件改动。

任何一列有异常：先不翻完成，交独立检查者决定修复、回退或重新授权。**「缺失的测试没有失败」不能代替通过。**

### 产出与外部结果分账

交接时分别记两行：

- `产出检查 ＋ 证据链`：本轮可复查的测试 / 产出；
- `结果状态 ＋ 责任人 ＋ 复查时点`：业务结果已观测 / 待观测。

状态记录行实例（填好的样子，示意）：

```text
stop_reason    = goal_gate_met           # 目标门通过而停（不是资源耗尽）
accepted_by    = @xiaoming               # 人审了 diff＋回归记录
evidence_link  = ci.run/8841, pr#217     # 可复查的指针
outcome_status = 待观测                   # 采用率要等上线 48h
next_check     = 10-02 14:00，责任人 @product
```

五行分属三个主体：控制流（机器）、验收（人）、外部结果（业务负责人）——**三件事三个人记，不合成一句「完成了」**。

### 什么时候不要

- 五接口有一项查不动（记录根本没留）→ 状态写「证据不足」，不放行，转高级六。
- 裁判可以被执行者改写 → 退回高级二补保护，本轮结果全部转人工。
- 有人拿「运行次数」「唤醒成功率」「代理数量」当质量证据 → 那些是活动量，不是成果。

**来源**：放行五接口与对照案例：Loop Engineering 研究层「结果可信闭环」判定（2026-09-30）；轮末三列核对：来自两位实践者的第一人称失败案例（Beck / Yegge，观测 2026-09-27）；分账：Loop Governance 操作规程 §10（2026-09-26 定稿层）。

## 高级六 · 它停了

> 它熔断、超时、或自己停了。停止不是失败，也不是完成——是**交接时刻**。

### 第一步：阻止待执行动作

- 支持持久化暂停的实现 → **保存当轮状态**；
- 不支持 → 记下请求并停机，**不假装可从原位恢复**。

### 三路处置

| 情形 | 处置 | 红线 |
|---|---|---|
| 策略明确禁止 | 维持硬拒绝 | 不得改名为「待人批准」 |
| 可由人决定 | 有合法审批入口 → 交指定审批者 | 入口不可达或无人接手 → 记 `blocked`，**不自动重试同一危险动作** |
| 入口不可达 | 保持阻塞并记录 | 不把阻塞写成「已升级」 |

交接记录实例（填好的样子，示意）：

```text
task_id         = fix-cart-total-42
action          = bash(git push origin fix/cart-total)
target          = repo:shop, branch:fix/cart-total
decision_source = exec_policy: push → Forbidden
denial_reason   = 硬拒绝（push 不在授权面；本次授权只覆盖编辑与测试）
authorized_scope= 编辑 payments/、跑 npm test；不含 commit/push
reviewer        = @xiaoming（审批入口：PR #217）
resume_pointer  = paused_state:88f3      # 持久化暂停；恢复后从断点继续
thread_id       = session-12             # 父线程可见该请求 ✓
```

恢复时第一步：重核 `authorized_scope` 的**有效期**——上次批的是那次评审，这次是新的，重新请求（高级一·铁则一）。

### 两个常见误处置（对照修）

| 误处置 | 正解 |
|---|---|
| 把硬拒绝现场改成「待人批准」 | 策略说禁止就是禁止；要改的是策略本身，走策略变更流程，不在事故现场开口子 |
| 入口不可达时自动重试同一动作 | 正确状态是 `blocked`＋记录；每五分钟再撞一次墙不会把墙撞开，只会烧预算 |

### 两件事分记（不可互相冒充）

| 记什么 | 记哪些值 | 不能冒充 |
|---|---|---|
| `stop_reason`（为什么停） | 目标门通过而停 / 资源耗尽 / 连续拒绝 / 不可恢复错误 / 人暂停 / 模型自行收尾 | 「已验收」——**没有验收证据就保留未验收** |
| `accepted ＋ 证据链`（谁收了货） | 验收者与测试、PR、日志或人工记录的指针；未验收留空 | 不能从超时、模型消息或测试进程结束推断已交付 |

不可恢复错误四类（触发即清空目标，Claude Code 官方文档，观测 2026-09-26）：认证失败｜额度耗尽｜压缩解决不了的上下文溢出｜模型不可用；其余错误重试若干次后暂停。

### 退档信号

熔断频发、假把控症状复现（测试被动过、越界实现、未说明的失败）→ 退一档重新稳住再升（高级四）。停止本身不构成退档理由——**正常停与事故停要分得清**：目标门通过而停是设计内；拒绝熔断与无进展熔断频发才是信号。

### 什么时候不要

- 别在没看清 `stop_reason` 前重启循环——重启烧掉的预算和上次一样。
- 别把「它自己收尾了」读成任何一种完成（卷首语汇表第 6 行）。

**来源**：三路处置与交接字段：Loop Governance 操作规程 §7（2026-09-26 定稿层）；拒绝熔断参数与不可恢复四类：Claude Code 官方文档（观测 2026-09-26）；「停止原因不等于完成证据」：Loop Governance 主干 §1（2026-09-27 确认）。

## 高级七 · 可选方向

> 听说多代理编排、循环自我改进很神。这节管预期：局部已有实例，整体未成熟；**高阶不是毕业要求**。

### 两条支线现状

| 支线 | 交出什么 | 已证 | 未证 |
|---|---|---|---|
| A 多主体编排 | 分工、并行、汇总由谁协调 | 编排器-工人、受约束并发、分布式文件锁均有实例 | **写入拓扑不收敛**：有人推荐写入单线程，有人多代理各自 clone / 改 / 合且不用编排器——共同问题只有三个：避免冲突、合并、验证 |
| B 改进循环本身 | 谁提议 / 应用对规则、工具描述、配置的改动 | 外围改动（如工具描述）有局部实例 | 核心自改（自动改判据 / 评估器）未成熟 |

支线 B 的四个层次，别混为一谈——每往右一层都是**不同的授权决定**，不能一口气交出：

```text
人亲自改 → 代理给建议、人应用 → 受控应用外围改动 → 自动改写核心判据
```

### 两个实例（都真实，都不是模板）

**编排**：16 个代理并行写一个 C 编译器，预算 $20k，作者自述大部分精力不在编码而在**验证器与环境设计**——"it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem."（Carlini，Anthropic 工程博客）。写入拓扑：每个代理各自 clone、修改、push、merge，**不用编排代理**。而另一位实践者（Cognition 方向）推荐写入单线程——**两条路线都真实，共同点只有三个：避免冲突、合并、验证。没有「正确拓扑」。**

**元循环外围**：有团队报告让代理参与改写工具描述后效率改善（Anthropic，观测 2026-09-30）——这是「受控应用外围改动」层的实例。往上的两层（自动应用外围改动、自动改写核心判据）在公开材料里没有成熟案例；往下一层（人亲自改、代理给建议）是你现在就能安全做的。

### 进支线的正确姿势

- 从**有界任务**进入即可（高级一 / 高级二配好后就能试编排），**不需要先爬到最高档**；
- 整树预算、写入所有权、合并与**独立验收**先配好——分工之后更要合并验收，**改动者不能自行放行自己的改动**；
- 元循环：提案与评估分离；改动可回滚、被评估——没有这个闭环之前，保持人审。

### 什么时候不要

- 单代理有界任务还没跑稳 → 支线放大的是你没修好的问题。
- 有人拿「这是必然趋势」当成熟度证明 → 趋势证词不是效果证据："If attackers and reporters loop, defenders will eventually need to loop too to keep up." 是趋势判断，不是安全证明。
- 你的角色已经开始模糊——第一人称体验："In the harness operated loop I'm not sure what my role even is. Even the 'done' signal loses all meanings … My role is reduced to that of a messenger."（Armin Ronacher，2026-09）→ 这正是退回高级四门禁的信号：交出触发权，不等于交出成果裁决权。

**来源**：支线判定与四层次：Loop Engineering 研究层交接面判定（2026-09-30，观测同日）；写入拓扑分歧双方：Cognition 与 Carlini 案例（Anthropic 工程博客）；角色模糊与趋势引句：Ronacher（2026-09）。
