# 04 · 交唤醒

> 任务跑完一轮就停，你想让它**到点或按事件自己再起跑**——交出的是「何时再跑」。

## 本章回答什么

两件事：触发器怎么选；**会话内定时与跨会话持久是两种运行边界**，后者另有一套门槛。

## 触发器选型

| 方式 | 下一轮何时开 | 何时停 |
|---|---|---|
| 条件驱动（`/goal` 式） | 上轮结束、闲置检查点、自动重试到期 | 条件满足 / 判不可能 / 需人修 / 显式清除 |
| 时间驱动（`/loop` 式） | 时间间隔到 | 你停它，或它判工作完成 |
| 脚本驱动（Stop hook） | 上轮结束 | 你的脚本或提示词决定 |

**`/loop` 三种拍法**（Claude Code 官方文档，观测 2026-09-26）：

- `/loop 5m check the deploy`——固定间隔＋提示词；
- `/loop check the deploy`——间隔模型自选，**1 分钟至 1 小时**之间按观察动态（构建在跑短等、无事长等）；
- `/loop`——无提示词，读内置维护提示词或项目级 `loop.md`（项目级优先）。内置维护提示词的范围封顶：继续未完工作 → 照料当前分支 PR → 清理，**不开范围外新动作**；push / 删除等不可逆动作必须核对会话里的授权仍覆盖本次动作与有效期。

三档调度面：**云上例行任务（≥1 小时，无需开机）｜桌面定时｜会话内 `/loop`（≥1 分钟）**。auto mode 不在此列——它只管轮内审批，不开新轮。

## 两种运行边界（最容易用错的一条）

| | 会话内定时 | 跨会话持久任务 |
|---|---|---|
| 活在哪 | 当前会话；**会话退出即失效** | 云端调度器；本地会话关了它还在 |
| 状态 | 会话内 | 必须另有持久化（进度文件、日志、事件 ID） |
| 停止 | 退出会话 / 停止命令 | **取消要同时到达调度器和运行中的 worker** |

官方原话划界："loops are session-scoped … If you need something that outlives your session, /schedule runs it in the cloud."（Addy Osmani《Practical Loop Engineering》Fine print，2026-08-14）

## 跨会话的额外门槛（缺一不交）

1. **持久状态**：重启后从哪读目标、进度、上次结果——有触发器不等于有持久化；
2. **取消传播**：真实事故——用户显式关掉自动化，"the kill did not propagate to the actual tmux sessions"（claude-code issue #46787）。**面板标「已关闭」不算停**：核对调度器不再派新任务、既有 worker 确已退出、外部副作用不再发生；
3. **硬上限**：定时任务 **7 天自动过期删除**——官方原话 "bounds how long a forgotten loop can run"；一轮既未续排也未停，约 **20 分钟**后兜底唤醒，再不续排则终止（Claude Code scheduled-tasks 文档，观测 2026-09-26）。云任务的默认上限**另查你的平台**，不套用这一组数字；
4. **可达的人工接手**：谁能在半夜取消它、看到它正在做什么。

## 无人值守变体（高风险场景，门槛另加）

到点跑只证明「醒来并执行过」，不是「目标已达成」。无人值守前先过 [05 章](05-升一档.md)的三项门禁与控制路径演练；自动响应动作参考 σ 分层（Anthropic playbook《Closing the loop》）：

- **1σ 只记录｜2σ 只读诊断｜3σ 可行动但仅限开 PR 或触发预批流程**；
- 检测脚本版本化＋单测，**全程确定性、模型不参与**；
- 回滚必须是管线里**演练最多的路径**：单命令、agent 可执行、staging 定期演练。

## 什么时候不要

- 跨会话四门槛缺任何一项 → 停在会话内定时。
- 完成判定还没配好（03 章没走完）→ 定时唤醒只会把错误复制到每一天。
- 幂等与防重入没设计（同一事件重复投递怎么办）→ 事件触发先不上。

## 同一任务的两种配置（部署监视）

**会话内**：开着会话敲 `/loop 5m check the deploy`——五分钟一醒；合上电脑它就没了。

**跨会话**（Anthropic Managed Agents 语法样例，观测 2026-09-30）：

```yaml
# ant apply deployment.md
agent: deploy-watcher
environment_id: env_prod_watch
schedule:
  type: cron
  expression: "0 20 * * 5"     # 每周五 20:00
  timezone: America/New_York
# 每次新 session 都要有人给它第一句话：
initial:
  user.message: "Check the deploy; report CI status and any 5xx in the last hour."
# 可查下次起跑点：schedule.upcoming_runs_at
```

两个易错点都在官方语义里：**缺初始事件，cron 正确也不跑**（任务不会凭空产生）；会话状态机是 `idle / running / rescheduling / terminated`——**预算暂停是 `idle`**，不是完成也不是销毁，别拿它当终止信号。

## 取消核对三步（对着真实事故写）

```text
1. 调度器：确认不再派新任务（查 upcoming runs 是否为空）
2. worker  ：确认在跑的进程真的退出——
   事故原样：面板显示已关闭，"the kill did not propagate to the actual tmux
   sessions"（issue #46787）；查进程表/会话列表，不是查开关
3. 副作用：确认外部世界不再被碰（新 commit、新 PR、新告警、新的云账单行）
```

三步都过，才可以说「停了」。面板绿了只是第 0 步。
