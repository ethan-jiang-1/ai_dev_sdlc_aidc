# 02 · 交动作

> 你受够了每个动作都点一次「允许」。这章管交出**动作审批**之前怎么划边界：授权面是分级处置表，不是开关。

## 本章回答什么

四件事：授权面怎么切；一次批准绑定什么；拒绝怎么回流；什么情况等于没交。

## 划面五步

| 步 | 做什么 | 检查 |
|---|---|---|
| 1 列动作 | 列全本任务会发生的动作类别：读 / 写 / 测试 / commit / push / 部署 / 外部调用 | 一类都不能漏——漏掉的类就是默认放行 |
| 2 标处置 | 每类标四级之一：**允许直行 / 沙箱内跑 / 必须人批 / 硬拒绝**，写进**可执行的策略件**（allow/deny 规则、沙箱配置），不写在提示词里 | 以提示词收尾的规则不是规则（见下） |
| 3 保高风险 | auth / billing / 破坏性变更保留当场审批与随时中断 | 高风险类不进 allowlist |
| 4 演练 | 低风险可回滚仓库里故意触发一个面外动作 | 记录里真实发生 propose → decision → tool result；不拿「最终测试通过」冒充审批通过 |
| 5 验收 | 抽一条已放行的动作，答出：谁批的？批的哪个目标？有效期到哪？ | 答不出＝面没划过，是默认放行 |

## 三条铁则

**1. 一次批准绑定「动作 × 目标 × 有效期」**，三个维度各自独立（来自真实事故报告，claude-code issue #95749）：

> "Editing files must not imply authorization to commit."（准许编辑 ≠ 准许提交）
> "Authorization to commit must not imply authorization to push."（准许提交 ≠ 准许推送）
> "Authorization for one push must not become standing authorization for later pushes."（一次 push ≠ 永久 push）

换分支、换 feature、从 edit 变 commit/push，都算**新动作**，重新请求授权。事故原样：一个两行的窄授权被当成大功能发布的许可，14 个文件直推 main。

**2. 拒绝是引导信号，不是终点。** 拒绝作为工具结果返回，附带「找一条更安全的路」的指令；会话累计 **3 次连续或 20 次总拒绝**则停机升级——这两个数字官方明写**不可配置**，且是**动作拒绝预算，不是轮数上限**（Claude Code auto mode 文档，观测 2026-09-26）。无界面环境下无人可问，直接终止进程。

**3. 审批有三个动作，不只是放 / 拦**：approve / **edit** / reject（LangChain HITL 文档，观测 2026-09-27）——「改了再跑」最容易被忽略，也最常用。

## 偏好与隔离是两层

- **偏好规则**（如 Cursor `permissions.json`）：管**倾向**批准 / 拦截什么；
- **执行隔离**（如 `sandbox.json`）：管**实际能碰到**什么（路径、网络）。

官方原话：Auto-review "is not a security boundary"（Cursor 官方 Run Modes 文档，观测 2026-09-30）。`Run Everything` 模式每个工具调用自动运行、**无沙箱、无分类器**——它交出的是动作审批权本身，启用前单独评估，不是本章的默认形态。**宽 allow 规则永远不能代替真正的执行隔离。**

## 写了规则 ≠ 有授权面（实测数据）

- 预写权限规则实测：写规则的作者比不写的**少拦了 20.1 个百分点**的坏动作；**93% 的权限提示被人批准**。"A rule that ends in a prompt isn't a rule."（arXiv 2608.27443，2026-08）
- 行业执行缺口：391 个仓库里只有 **12 个**提交了一条 deny 规则。（marmelab 审计，2026-09-24）
- 升级不可达的真实案例：用户在对话里反复明确授权同一个动作，拒绝依然不可翻案（claude-code issue #67519）——拒绝合理性之外，**升级可达性是第二个独立的控制问题**。

## 什么时候不要

- 动作品类列不全（第 1 步做不完）→ 先别交：默认放行比逐动作审批更危险。
- 高风险动作的审批入口不可达（人不在、父线程看不见请求）→ 保持逐动作审批。
- 所用产品只有偏好规则、没有真正的执行隔离 → 授权面收窄到「可回滚」类动作。

## 划定实例（修一个支付回调 bug 的授权面，填好的样子）

**第 1–2 步产物**——动作类别 × 处置 × 落点：

| 动作类别 | 处置 | 落在哪个策略件 |
|---|---|---|
| 读 `payments/`、`tests/` | 允许直行 | read 类 allowlist |
| 跑 `npm test` / `npm run lint` | 允许直行 | exec allowlist：只列这两条精确命令，不写 `npm *` |
| 改 `payments/webhook.ts` 与对应测试 | 沙箱内跑 | 沙箱可写路径＝本仓 `payments/`、`tests/`；无网络出站 |
| `git commit`（本分支） | 必须人批 | PR 描述里的 commit 门 |
| `git push`、部署、改 `prod/*` 配置 | 硬拒绝 | deny 规则 |
| 调外部支付沙箱 API | 必须人批 | 凭证注入由人完成，密钥不进上下文 |

**第 4 步演练日志长什么样**（示意，核对这三行真实发生过）：

```text
[10:02:11] propose  : bash(git push origin fix/cart-total)
[10:02:11] decision : DENY（rule: push/* — hard deny, no override）
[10:02:12] result   : push 被策略拒绝；该动作在硬拒绝清单
```

有这三行＝审批真实走过策略件。只有「最终测试通过」＝没验过——测试通过和审批通过是两条不相干的证据链。

**审批策略的代码形态**（样例，LangChain HITL 文档，观测 2026-09-27）：

```python
interrupt_policy = {
    "write_file": True,          # approve / edit / reject 三个决定都开放
    "read_data":  False,         # 安全操作，不打扰人
    "git_push":   "approve_only" # 只许批——不许改、不许绕
}
```

第三个键是本手册编的示意（前两键为该文档原样），你的框架里怎么写以你所用版本的官方文档为准；要看的是**粒度**：审批可以细到工具名 × 参数，不是只有全局开关。
