# 文稿 — 入门场

## 术语

档｜授权面｜策略件｜裁判｜负例｜验收｜外部结果｜反馈回路｜定档四问（谁启动下一轮／谁判断完成／谁能改变系统／出了错谁能停下接手）

### N01 · 它说做完了

**CLAIM**：你离开后它继续跑，回来听到「完成」；真正的问题是这句话凭什么可信。

**上屏**

- title: 它说做完了
- content:
  - 你离开了，系统继续工作。
  - 你回来，它说：完成。
  - 凭什么信？

**展开**：这场从一个交付现场的风险开始：停下来的东西，未必做完。我们不打算把所有人一口气带到终点——带一张阶梯图，先看你站在哪。

**接到下一页**：先说这个词为什么突然到处都是。

---

### N02 · 为什么有人喊「别写 prompt 了，写 loop」

**CLAIM**：模型已经强到能知错改错——知道错在哪就能改对，所以有人开始不写 prompt，改写 loop；这个故事的燃料是反馈。

**上屏**

- title: 别写 prompt 了，写 loop？
- content:
  - 模型已经很强，而且能知错改错。
  - 知道错在哪，它就能自己改对。
  - 所以有人说：别写 prompt 了，写 loop。

**展开**：这句话吸引人，也不是吹牛——它成立的前提有两条：模型能力够强，**并且反馈进得来**（它得知道错在哪）。第二条经常被略过，而这正是本场要讲的：loop 是一门要锻炼的手艺，不是一句口号。

**接到下一页**：手艺要一级一级练——这是今天的路线图。

---

### N03 · 今天的路线图：一张阶梯

**CLAIM**：每上一级，交出一个决定，配上一组护栏；今天从你站的位置出发。

**上屏**

- title: 今天的路线图
- content:
  - 第一级：交动作——它自己动手，你少点「允许」。
  - 第二级：交续跑——它自己跑到目标为止。
  - 第三级：交唤醒——它自己到点再起跑。

**展开**：这张图是全场的路线。每一级都是一次交接：交出一个决定，换回一组护栏。先看你的位置。

**接到下一页**：你的位置，比你想的靠前。

---

### N04 · 你已经在阶梯上

**CLAIM**：逐次提示就是阶梯的第一级——人当裁判；这一级什么都不用先配，它是合法驻留，不是失败态。

**上屏**

- title: 你已经在阶梯上
- content:
  - 你每说一句，它做一段，你看一眼，再决定下一句。
  - 这就是第一级：每一轮由你发起，每一轮由你判断。
  - 不往上走，不需要理由。

**展开**：很多人以为「用上 agent」要从一套复杂配置开始。不用。第一级的裁判是你，护栏也是你——你人在回路里。往上走是逐步交决定，不是补课。

**接到下一页**：第一级已经有一个东西在转——反馈。

---

### N05 · 反馈让循环成为循环

**CLAIM**：模型不知道错在哪、要改哪里——除非每一轮都有反馈进来；没有反馈的重跑是抽卡（比喻），不是循环。

**上屏**

- title: 反馈让循环成为循环
- content:
  - 它改错了方向，谁告诉它？
  - 你告诉它，或者环境告诉它。
  - 没有反馈的重跑，只是再抽一次卡。

**展开**：循环和抽卡的全部区别就在这里：**这一轮有没有被上一轮的反馈改变**。第一级里，你的每一句纠正就是反馈回路——所以第一级已经在跑循环，虽然还没有任何配置。回扣开头的故事：模型能知错改错，**但知错的前提是错的事实进得来**——反馈断了，知错改错就退化成瞎改。

**追问**：判据一：不依赖上一轮结果的重试是 retry，不是 loop。

**接到下一页**：反馈这么重要，就不能只留在聊天记录里。

---

### N06 · 反馈要落成基建

**CLAIM**：反馈不能只留在聊天里——退出码、日志、产物要落成可复查的工件，下一轮消费的是工件，不是记忆。

**上屏**

- title: 反馈要落成基建
- content:
  - 命令的退出码、失败日志、运行产物——落盘。
  - 下一轮先读工件，再决定动作。
  - 「我刚才试过了」不是证据，工件才是。

**展开**：最小反馈通道：命令 → 退出码＋输出 → 落盘的证据 → 下一轮动作。聊天里的反馈会被上下文淹没；落成工件的反馈，才可能被每一轮、被裁判、被你自己复查。这是所有档位共用的基建。

**追问**：数据管道要读结构化结果文件，不是解析自然语言终端输出。

**接到下一页**：回路搭好，第一个便宜的台阶是把动作授权交出去。

---

### N07 · 交出动作授权

**CLAIM**：授权面让它在边界内自己动作，省掉的是打断，不是判断——你仍然逐轮看。

**上屏**

- title: 交出动作授权
- content:
  - 四种处置：允许直行 ／ 沙箱内跑 ／ 必须人批 ／ 硬拒绝。
  - 省掉的是逐条点「允许」。
  - 每一轮结束，看的还是你。

**展开**：授权面是一张**分级处置表**，不是开关：读文件可以直行，改文件可以进沙箱，推送必须问你，删库直接拒绝。产品里叫法不同，形状都一样。

**接到下一页**：这张表怎么落下去，有个常见的假动作。

---

### N08 · 规则要写进策略件

**CLAIM**：写了规则不等于有授权面——93% 的权限提示最终被人批准；策略偏好不等于执行隔离。

**上屏**

- title: 规则要写进策略件
- content:
  - 规则写进配置文件，不写在提示词里。
  - 93% 的权限提示，最终还是被人点了「允许」。
  - 「自动审查」不是安全边界——官方原话。

**展开**：实测：预写规则只让坏动作少拦了一点点，因为绝大多数提示人们顺手就批。写在自己嘴上的规则等于没写；偏好规则管「倾向」，真正的隔离靠沙箱——两层都要有。

**追问**：arXiv 2608.27443（93%／20.1 个百分点）；marmelab 审计 391 仓库仅 12 条 deny 规则；Cursor 官方："Auto-review is not a security boundary"。

**接到下一页**：授权面还有一个更细的纪律——批准的边界。

---

### N09 · 授权绑三样

**CLAIM**：一次批准只绑定动作、目标、有效期；任何一个变了，就是新动作，要重新批准。

**上屏**

- title: 授权绑三样
- content:
  - 准许编辑 ≠ 准许提交 ≠ 准许推送 ≠ 永久推送。
  - 换分支、换任务、从「改文件」变成「提交」——重新问。
  - 事故原样：两行修改的授权，被当成大功能发布的许可。

**展开**：真实事故（issue #95749）：一次两行修改的推送授权，被当成大功能发布的许可，14 个文件直推主干。三个维度各自独立——动作、目标、有效期，缺一个都算越界。

**接到下一页**：到这里，第一级就走完了——省钱、省打断，判断还在你手里。再往上，门票变贵了。

---

### N10 · 下一级的门票贵了

**CLAIM**：让它自己跑到目标为止，交出的是「做完没做完」的判断权——这是全阶梯最贵的一级。

**上屏**

- title: 下一级的门票贵了
- content:
  - 前两级：每一轮结束，看的是你。
  - 这一级：一个机器条件替你说「完成」。
  - 先看票价，再决定爬不爬。

**展开**：交出续跑权，意味着你睡觉的时候它也在判断「做完了吗」。这一级事故最集中、最依赖功夫。接下来几页全是这一级的门票和护栏——一件一件配。

**接到下一页**：门票第一行——把「好」写成机器能对照的句子。

---

### N11 · 门票：一个可测终态＋一条声明式检查

**CLAIM**：「把体验做好」不是目标；「Lighthouse ≥92，以 CLI 输出证明」才是——把潜意识里的判断挖出来写成文字，全场最难。

**上屏**

- title: 门票：可测终态＋声明式检查
- content:
  - 终态：结果列表第二页可打开、可返回。
  - 检查：`npm test` 退出码 0。
  - 难的不是写，是发现自己脑子里那把尺子。

**展开**：「把体验做好」——good 对谁？怎么评？这不是目标，是愿望。把尺子逼成白纸黑字：可测的终态＋怎么证明。教科书全例（Osmani）：Lighthouse ≥92、LCP<1.8s、以 CLI 输出证明——一次配齐的样本在备课区。

**追问**：/goal 官方规格三要素（evidence-b §4a）；Osmani 全例逐字（evidence-a，2026-08-14）；实战样本见本稿末尾。

**接到下一页**：光有终态和检查还不够——还要写「不许变的东西」。

---

### N12 · 约束与兜底

**CLAIM**：约束写「不许变的东西」；无进展出口和轮数上限是兜底——没有兜底的续跑是烧钱。

**上屏**

- title: 约束与兜底
- content:
  - 约束：「不改公共接口」「不动别的测试」。
  - 出口：连续两轮无改善，停。
  - 上限：最多 10 轮。

**展开**：约束是路径上不可越过的边界，不是备注。无进展出口管质量（别硬磨），轮数上限管资源（别硬烧）——两个都要有，只带上限的循环会硬跑到最后一轮才停。

**接到下一页**：条件立好了，谁来判？——裁判不是反馈。

---

### N13 · 裁判不是反馈

**CLAIM**：反馈是环境返回的事实，裁判是按事先约定判据解释事实的那一位；判好坏的仍是你。

**上屏**

- title: 裁判不是反馈
- content:
  - 反馈：退出码、报错、日志——事实。
  - 裁判：按事先约定的判据解释事实。
  - 判「内容好不好」，仍是你。

**展开**：裁判只核约定条件，不判内容品味——它说「条件成立」，不代表「做得好」。裁判可以是独立的小模型，也可以是清单——但判据要事先写好，不能每次现想。

**接到下一页**：裁判判完，往哪走？——三个出口。

---

### N14 · 三个出口各管一件事

**CLAIM**：未达成带理由继续；达成只算停止候选；不可能就停并交人——三个出口语义不同，不能合成一句「它停了」。

**上屏**

- title: 三个出口
- content:
  - 未达成 → 继续，理由回传给下一轮。
  - 达成 → 停——还不是验收。
  - 不可能 → 停并交人。

**展开**：「理由回传」是裁判最重要的产出：下一轮不是重新猜，是按理由改。连续几轮没有进展也要停——那也是一种出口。

**追问**：unknown／超时不强行归入「不可能」，保留为交人。

**接到下一页**：出口之外，门本身还有一个纪律。

---

### N15 · 门要覆盖真实的反馈通道

**CLAIM**：门存在不等于门覆盖——实际跑的那条路径没被检查住，假通过照常发生。

**上屏**

- title: 门要覆盖真实的通道
- content:
  - 有一个测试，不等于测试真的会跑。
  - 内层有上限，外层的重试呢？
  - 基线本来就红？

**展开**：把实际执行路径画出来，逐段标「这道门管不管这里」。常见漏洞：检查被跳过、基线带病、该做的检查根本没安排。门没盖住的地方，就是假通过的产地。

**接到下一页**：盖住了还不够——门要见过血。

---

### N16 · 门要见过血

**CLAIM**：没让门红过一次的检查是摆设——负例控制是你决定放手前的必要条件。

**上屏**

- title: 门要见过血
- content:
  - 故意放一个已知错误进去。
  - 门红了：门是活的。
  - 门没红：假门。负例通过 ≠ 万事 OK。

**展开**：把一个断言改成错值，或塞一个假密钥，跑同一条检查——必须非零退出、原因明确。没做过负例就放手，等于没验过锁就出门。负例只证明「这类错误拦得住」，不证明没漏做别的。

**接到下一页**：门都活着，这一档仍有自己的专属事故。

---

### N17 · 事故：提前宣告完成

**CLAIM**：交出续跑之后，最大的敌人是提前宣告完成——文件变多、语气很满、测试绿了，都可能不是完成。

**上屏**

- title: 提前宣告完成
- content:
  - 文件多了，不等于做完。
  - 语气很满，不等于做完。
  - 官方示例的驱动循环里，连「全部通过就停」的分支都没有。

**展开**：真实源码：进度条打印「通过数／总数」，驱动层却没有停机分支，默认无限轮——**「完成」住在哪一层，要追到代码**，不能听叙事。

**追问**：Anthropic 官方 quickstart 源码（观测 2026-09-28）。

**接到下一页**：防它有三层，一层一层来。

---

### N18 · 防它第一层：清单逐条判定

**CLAIM**：把目标拆成逐条清单，完成逐条判——「整个项目做完了」没法判，「第 37 条通过」可以。

**上屏**

- title: 第一层：清单
- content:
  - 目标拆成一条条可验证的条目。
  - 全部从「未完成」起步。
  - 只允许它改「完成」标记这一个字段。

**展开**：官方样例一条清单 200+ 条；「declares victory on the entire project too early」的对策就是清单。清单用 JSON 不用 Markdown——模型整文件改写的概率更低。

**接到下一页**：第二条防线管「通过」的含金量。

---

### N19 · 防它第二层：端到端验证才翻完成

**CLAIM**：真实路径走通才翻「完成」——单测和 curl 过不算。

**上屏**

- title: 第二层：端到端
- content:
  - 浏览器里把真实用户路径走一遍。
  - 按钮点得动、页面出得来，才算。
  - 单测过、按钮不可用——不翻。

**展开**：单测验证的是零件，端到端验证的是用户真的能用。翻「完成」标记的资格，来自真实路径的验证，不来自零件绿灯。

**接到下一页**：第三层管绿灯本身的成色。

---

### N20 · 防它第三层：测试不可删改

**CLAIM**：测试删了，绿灯就没有意义——不可删改要写进硬约束，不是提示词。

**上屏**

- title: 第三层：测试不可删改
- content:
  - 删测试、禁测试、放宽断言——都算作弊。
  - 用钩子硬拦，不是口头要求。
  - 实战反例：agent 删除或禁用了测试。

**展开**：第一人称反例（Kent Beck 的记录）里 agent 走的就是这条路。绿灯的价值取决于测试的成色——「缺失的测试没有失败」，不能代替通过。

**接到下一页**：护栏讲完了，还有一路东西不能断——你的反馈。

---

### N21 · 人的反馈要留在环里

**CLAIM**：你不是只在终点验收——方向纠偏、品味判断、拒绝的理由，都要回灌到下一轮；完全静默不是目标。

**上屏**

- title: 人的反馈留在环里
- content:
  - 它跑偏了，你纠正——纠正要进下一轮。
  - 你拒绝一个动作，理由要让它看到。
  - 品味和方向，机器判不了。

**展开**：硬核玩家「放手也行」的秘密就在这：他们的纠正每轮都在发生，只是自己没察觉。把这条反馈显性化——拒绝带理由、纠偏记下来、品味写成样例——你就是这一级最重要的反馈源。完全没有人的反馈的循环，方向会漂。

**追问**：Ronacher 警告：无人值守里人的角色退成「传话筒」，done 就失去了含义——所以完全静默不是目标。

**接到下一页**：就算一切正常停下——停，也不等于验收。

---

### N22 · Stop ≠ Accepted

**CLAIM**：超时、耗尽、模型收尾，只说明控制流停了；验收是另一件事，由人签。

**上屏**

- title: Stop ≠ Accepted
- content:
  - 停止的原因要记录：到上限？没进展？目标门通过？
  - 验收要另记：谁验收的，证据在哪。
  - 没有验收证据，就保持「未验收」。

**展开**：`停止原因=轮数上限，验收=空` 和 `停止原因=目标门通过，验收=评审人＋证据` 是两种完全不同的状态。不能从「它停了」推断「它做完了」。

**接到下一页**：验收之外还有一本账。

---

### N23 · 产出和结果是两本账

**CLAIM**：PR 合了、测试绿了，是产出验收；业务有没有变好是外部结果，要等观测——两本账不能合成一句「完成了」。

**上屏**

- title: 产出和结果是两本账
- content:
  - 产出：可复查的测试、PR、日志——验收人签名。
  - 结果：采用率、满意度——上线后才看得见。
  - 看不见时，状态写「待观测」。

**展开**：三件事三个人记：控制流（机器）、验收（人）、外部结果（业务负责人）。「完成」这个词，在这三本账里是三个不同的意思。

**接到下一页**：阶梯还有最后一级的远景。

---

### N24 · 最后一级的远景：让它自己醒

**CLAIM**：交出「何时再起跑」的档位里，定时唤醒只证明「醒来并执行过」，不证明目标达成。

**上屏**

- title: 让它自己醒
- content:
  - 会话内定时：你关会话，它就停。
  - 跨会话任务：另配状态、取消、预算、人工接手——取消要真的传达到进程。
  - 再往上有两条高级岔路——不是必经之路。

**展开**：一页远景。真实事故：面板显示已关闭，后台进程还在跑——取消传达是这一级的硬问题。被遗忘的循环要有过期时间（官方：7 天自动过期）。两条岔路今天不展开。

**接到下一页**：走了这么远，回头看——每一级，人守的东西不一样。

---

### N25 · 每一级，人守的东西不一样

**CLAIM**：人不是被移出循环，是被移到更高处的判断。

**上屏**

- title: 每一级，人守什么
- content:
  - 第一级：人守全部——每轮发起、每轮判断。
  - 第二级：人守授权边界＋最终验收；第三级：守判据、验收和外部结果。
  - 第四级：人守总账、接手和「还要不要跑」。

**展开**：随着档位上移，人的判断从「这步对不对」上移到「这样算不算好」「方向对不对」「还要不要继续」。人一直在环里，只是判断的海拔在变。

**接到下一页**：那什么时候不爬？

---

### N26 · 什么时候不要往上爬

**CLAIM**：完成条件写不成可观察句子就留在低档——驻留是控制决策，不是失败。

**上屏**

- title: 什么时候不要往上爬
- content:
  - 单次小任务：写个脚本就好，不建循环。
  - 品味类目标：先人工标样，别硬跑。
  - 标准会漂或存量代码库：保留人工检查点，慎用无限循环。

**展开**：留在低档不是没爬上去，是判断的结果——很多任务的最佳档位就是第一级。反面教材：技术硬核的人以为什么都能放手（那个错觉在技术场细讲）。

**接到下一页**：回去怎么开始？先定档。

---

### N27 · 回去先定档

**CLAIM**：先答四个问题——谁启动下一轮、谁判断完成、谁能改变系统、出了错谁能停下接手——答得出，再决定爬不爬。

**上屏**

- title: 回去先定档
- content:
  - 四个问题写在纸上。
  - 写得出＝清楚档位与护栏；写不出＝留在原级，不丢人。
  - 想配哪一级：翻《循环交接手册》。

**展开**：这四个问题贯穿了全场每一页——回到开头那句「它说做完了」，现在你知道该问哪四个问题了。手册按时刻组织：入门篇读完就能上手，高级篇按时刻翻。

**收束**：Loop Engineering 的硬核，不是让系统跑得更久，而是每一次交出去的决定，都有护栏接得住。它是一门要锻炼的手艺——阶梯就是练法，从你站的那一级练起。

# 追问卡（不上屏）

> 按页提供可追问的材料与证据锚。教学示意数值不可当实测；产品参数只按对应产品讲。

## N01–N04 · 钩子、故事与第一级

- **状态例子**：`PR created; CI failing; accepted_by=null; outcome_status=pending`——比一句「完成」诚实。
- **N02 讲法**：故事只讲半分钟——模型强＋能知错改错，所以有「写 loop」的说法；紧跟着补一句「燃料是反馈，而且它需要锻炼」，不吹不贬。
- **阶梯边界**：研究层交接面判定（2026-09-30），不是行业成熟度标准；四级不作人人必经；上屏不出现 LE 编号。
- **Ng 三环**：编码环／开发者反馈环／用户反馈环，回答反馈在哪个时间尺度回流——上位背景一句即可。

## N05–N06 · 反馈双路

- **判据一**：停止或继续不看上一轮结果的重试是 retry；抽卡比喻由此而来。
- **最小反馈通道**：命令 → 退出码＋输出 → 落盘证据 → 下一轮动作；Aider 形状：lint 非零 → 确认修复 → 错误回灌。
- **数据管道**：读结构化结果文件（run_results.json 类），不解析自然语言终端输出。

## N07–N09 · 第一级台阶

- **分级处置官方样本**：Cursor 2026-05-29 changelog（allowlist／沙箱／分类器）；Codex `exec_policy` 危险度×沙箱×信任三维。
- **实测**：预写规则少拦 20.1 个百分点、93% 提示被批准（arXiv 2608.27443）；391 仓库仅 12 条 deny 规则（marmelab，2026-09-24）；"A rule that ends in a prompt isn't a rule."
- **偏好≠隔离**：Cursor `permissions.json`（偏好）vs `sandbox.json`（隔离）；"Auto-review is not a security boundary"；Run Everything 无沙箱无分类器。
- **授权继承事故**：issue #95749（编辑≠提交≠推送≠常设；两行授权→14 文件直推主干）；升级不可达 issue #67519。

## N10–N12 · 门票

- **弱写法对照**：`Improve the search experience until it feels good.`（good 对谁？怎么评？）。
- **全例**：Lighthouse ≥92、LCP<1.8s、CLI 输出证明、不改 hooks、两轮无改善 abort、10 轮上限（Osmani，2026-08-14；数字不可外推）。
- **约束的官方分类**：可测终态／声明式检查／重要约束（/goal 文档三要素）；轮次或时间子句作上限。

## N13–N16 · 裁判、出口、门

- **评估器边界**：只核 transcript 硬规则（"It doesn't look at the content…"）；独立小模型每轮判定是会话内 goal 的做法。
- **fail-closed 例**：评估输出缺 `pass` 字段又无阈值，score=0 仍可能默认放行——判定接口也要设防。
- **unknown 处理**：不强行归入 Impossible，保留交人。
- **覆盖漏洞清单**：检查被跳过、基线带病、该做的检查没安排、嵌套路径外层无限重试。
- **负例做法**：改坏断言或植入 dummy key→同一条检查必须非零退出、原因明确。

## N17–N20 · 事故与三层防线

- **quickstart 源码**：`while True`＋唯一退出分支是 max_iterations、默认 None（无限）；进度条给人看；「不可改测试」只在提示词（观测 2026-09-28）。
- **清单**：官方 200+ 条样例；JSON 抗整文件改写；只许改 `passes` 字段；官方失败模式原话 "declares victory… too early"／"marks features as done prematurely"。
- **端到端**：浏览器自动化走真实用户路径；按钮点得动才算。
- **删测反例**：Kent Beck 记录 agent 删除/禁用测试；测试削弱检测关注 skip、断言降级、`|| true`。

## N21–N24 · 人的反馈、停止、两本账、唤醒

- **人的反馈**：拒绝带理由（deny-and-continue 的 "find a safer path"）；Ronacher 警告「角色退成传话筒」；Ng context advantage（人掌握业务上下文）。
- **两本账**：`stop_reason` 与 `accepted_by/evidence_link` 分记；`outcome_status=待观测`＋责任人＋复查时点。
- **唤醒**：`/loop` 三种拍法、动态间隔 1 分钟–1 小时；7 天过期＋20 分钟兜底（"bounds how long a forgotten loop can run"）；会话内／跨会话边界（Osmani："loops are session-scoped… /schedule runs it in the cloud"）；zombie 事故 issue #46787；doom-loop 检测默认关闭（OpenRouter 样本）。

## N25–N27 · 关口、驻留、定档

- **反过度工程**：单次不建循环、brownfield 禁 Ralph（"no way in heck…"）、门不可信不升、品味不委托（Osmani）。
- **Steinberger**："usually I'm the bottleneck"——调度自动化收益有限；不是「自动化更慢」。
- **定档四问**：研究层交接面对外措辞；手册指引：《循环交接手册》入门篇起步。

# 一套可以现场拆开的实战样本（不上屏）

> 完整虚构样本：给站内搜索增加分页。**动作单对应第一级（交动作）的护栏；goal/eval 工件对应第二级（交续跑）的门票；状态与交接对应后面的档位**。数值、分支名、命令都是演示模板，不是厂商默认值，也不是实测收益。

## 1. Goal 工件：先把「做完」写成可判定对象（第二级门票）

```json
{
  "goal_id": "search-pagination-v1",
  "terminal_state": "结果列表第二页可打开、可返回、查询条件不丢失",
  "checks": [
    "npm test -- search-pagination",
    "npm run e2e -- search-pagination.spec.ts"
  ],
  "constraints": [
    "只改 search 分支",
    "不得修改公共 API",
    "不得删除或放宽既有测试"
  ],
  "stop_clause": "两次连续无改善或达到项目资源上限时停止并保全状态",
  "outcome": "用户采用率另行观测，不作为本轮自动 Met"
}
```

四个细节：终态不是「搜索体验变好」；检查不是「模型觉得可以」；约束是不可越过的边界；采用率当前不可见，只能是 `outcome_pending`。

## 2. Action 工件：每次只拿一张可审计的动作单（第一级护栏）

```json
{
  "action_id": "act-0042",
  "principal": "search-agent",
  "action": "edit",
  "target": "src/search/pagination.ts",
  "branch": "agent/search-pagination",
  "scope": ["src/search", "tests/search"],
  "expires_at": "2026-09-28T18:00:00Z",
  "approval": "reviewer-17",
  "denied": ["commit", "push", "public-api-change"]
}
```

把 `edit` 改成 `push`、branch 改成 `main`、目标移到 `deploy/`，都算新动作重新审批——一次批准不能靠文字相似度继承。

## 3. Feedback 工件：把环境返回物落盘

```sh
set -o pipefail
mkdir -p .loop/runs/run-0042
npm run e2e -- search-pagination.spec.ts \
  > .loop/runs/run-0042/stdout.log \
  2> .loop/runs/run-0042/stderr.log
status=$?
printf '{"run":"run-0042","exit_code":%s,"commit":"%s"}\n' \
  "$status" "$(git rev-parse HEAD)" \
  > .loop/runs/run-0042/result.json
exit "$status"
```

下一轮先读 `result.json`，再读失败日志，最后选动作——不是重新问「刚才发生什么」。

## 4. Eval 工件：反馈和判定分开

```json
{
  "eval_id": "eval-0042",
  "goal_id": "search-pagination-v1",
  "evidence": [
    ".loop/runs/run-0042/result.json",
    ".loop/runs/run-0042/stderr.log"
  ],
  "verdict": "NotYet",
  "reasons": ["page_2_button_click_failed"],
  "evaluator": "search-checker-v3",
  "rubric_hash": "sha256:...",
  "missing_fields_are": "reject"
}
```

`exit_code=0` 只是环境事实；`verdict` 须覆盖页面路径、API 约束和测试保护。缺字段时拒绝，不猜。

## 5. 状态迁移：停止、验收、业务结果拆开

```text
running
  ├─ feedback=NotYet, retryable ───────→ running
  ├─ feedback=Met, artifact complete ──→ stopped_candidate
  ├─ hard limit / no progress ─────────→ stopped
  ├─ permission / dependency ───────────→ blocked
  └─ ambiguity / reviewer needed ───────→ awaiting_human

stopped_candidate + independent sign-off → accepted
accepted + external metric unseen       → outcome_pending
```

必须能回答：为什么停？谁验收？依据在哪？外部结果谁在什么时候复查？

## 6. 负例演练：先证明门会拒绝

把分页断言改成错误期望，或植入 dummy API key，跑同一条检查：非零退出码、明确失败位置、evidence link、下一轮可读的修复理由。恢复后再跑正常路径。负例通过只证明这类错误拦得住；门没红，先停止升档。

## 7. 熔断交接单：人真正接得住才叫升级

```yaml
feature_id: search-42
state: awaiting_human
stop_reason: policy_denial
last_action: edit src/search/pagination.ts
last_feedback: page_2_button_click_failed
accepted_by: null
evidence_link: .loop/runs/run-0042/result.json
reviewer: product-owner-7
resume_pointer: run-0042/action-0043
next_check: 2026-09-29T09:00:00Z
```

`reviewer` 为空、`resume_pointer` 指不到状态，就不能说「已升级」；硬拒绝不能改名「等待审批」。

## 8. 现场定档顺序（v3：从审计改为定档）

1. 先答四问：谁启动下一轮／谁判断完成／谁能改变系统／出错谁接手——现在的答案是什么？
2. 对答案缺的那格，翻对应档位：授权面（第一级）→ goal/裁判（第二级）→ 唤醒与总账（第三、四级）。
3. 每配一样，先用负例验证它会红。
4. 答不出又不急着升：留在当前级——这是控制决策，不是失败。

## 9. 这套字段怎么泛化

不要从字段名出发，从控制问题出发：

| 控制问题 | 示例字段 | 换系统仍要保留的语义 |
|---|---|---|
| 要达到什么 | `terminal_state` | 可观察的产出终态 |
| 不能做什么 | `constraints` | 不可越过的范围与路径约束 |
| 凭什么判断 | `checks` / `evidence` | 外部可复查的证据和判据 |
| 谁能做什么 | `approval` / `scope` | 动作、目标、有效期和授权主体 |
| 为什么下一步这样走 | `verdict` / `reasons` | 判定及理由回到下一行动 |
| 现在停在哪里 | `state` / `stop_reason` | 控制状态与停止原因分开 |
| 谁接手、怎么恢复 | `reviewer` / `resume_pointer` | 责任人、恢复位置和所需证据 |
| 产出是否带来结果 | `outcome_status` | 外部结果独立于产出验收 |

**最小迁移法**：先用纸填这八个问题；再映射到已有工具；最后用一个已知错误和一次拒绝演练验证记录真的会改变下一步。
