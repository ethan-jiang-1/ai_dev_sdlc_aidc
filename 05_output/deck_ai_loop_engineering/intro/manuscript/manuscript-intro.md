### N02 · 为什么有人开始「写 loop」

**CLAIM**：Addy Osmani 的定义是：用系统替代人逐轮提示 agent；系统靠环境反馈调整下一步。

**上屏**

- title: 为什么有人开始「写 loop」
- subtitle: Addy Osmani 的定义是：用系统替代人逐轮提示 agent；系统靠环境反馈调整下一步。
- content:
  - 人不再逐轮提示，系统接上下一轮。
  - 环境反馈让系统调整下一步。

**展开**：Addy Osmani 的一手定义把 loop engineering 说成「替代人逐轮提示 agent，设计一个会做这件事的系统」；关键不是把人的判断抹掉，而是把反馈接回下一步。loop 是要锻炼的手艺，不是一句口号。

**Callout（上屏，中文节选意译）**：Addy Osmani · 2026-06-07：用系统替代人逐轮提示 agent。

**原文复核（同页备注）**："Loop engineering is replacing yourself as the person who prompts the agent. ### N05 · 反馈让循环成为循环

**CLAIM**：环境或人的反馈进入下一步，系统根据结果调整行动；没有消费反馈的重跑是抽卡（比喻）。

**上屏**

- title: 反馈让循环成为循环
- subtitle: 环境或人的反馈进入下一步，系统根据结果调整行动；没有消费反馈的重跑是抽卡（比喻）。
- content:
  - 你或环境告诉它发生了什么；它据此决定下一步。
  - 没有反馈的重跑，只是再抽一次卡。

**展开**：循环和抽卡的关键区别在这里：**这一轮有没有被上一轮的反馈改变**。基线里，你的每一句纠正就是反馈回路；环境也可以返回退出码、日志和产物。回扣开头的定义：系统能替人提示下一步，前提是反馈真的进得来。

**Callout（上屏，中文节选意译）**：Anthropic · 2024-12-19：agent 依靠环境反馈，在循环中使用工具。

**来源（页内完整信息）**：Erik S.、Barry Zhang（Anthropic），《Building effective agents》，2024-12-19，https://www.anthropic.com/engineering/building-effective-agents

**原文复核（同页备注）**："They are typically just LLMs using tools based on environmental feedback in a loop." 已对照 [evidence-b §2](../../../../02_research/01_agent_engineering/loop_engineering/raw/evidence-2026-09-26-b-stop-and-scheduling.md)；这是机制说明，不是质量收益数据。

> **PPT-agent 引用块（不上屏）**
> - 意思：N05 定义反馈是循环的必要燃料，同时保留人的反馈路径。
> - 词解：环境反馈＝工具结果或代码执行等外部事实；抽卡＝没有被上一轮改变的重跑，比喻。
> - 禁止：不要说 Anthropic 证明了质量收益；不要把“环境反馈”写成只能是自动测试；不要把人的判断移除。
> - 版面：callout 一行；来源与原文英文放备注，不增加第四条 content。

**追问**：判据一：不依赖上一轮结果的重试是 retry，不是 loop。

### N06 · 反馈要落成基建

**CLAIM**：需要恢复或审计时，把退出码、日志、产物留成可复查工件；落盘是反馈的可审计实现，不是循环的定义条件。

**上屏**

- title: 反馈要落成基建
- subtitle: 需要恢复或审计时，把退出码、日志、产物留成可复查工件；落盘是反馈的可审计实现，不是循环的定义条件。
- content:
  - 会话内：直接读工具结果，再决定动作。
  - 需要恢复或审计：留存退出码、日志、产物与版本。
  - 恢复时先读留存证据，让接手者可以复查。

**展开**：本场采用的可审计实现是：命令 → 退出码＋输出 → 留存证据 → 下一轮动作。会话内也可以直接消费工具反馈；需要恢复、跨会话或审计时，再把结果落成工件。反馈改变下一步才是定义层，落盘是实现层。

**追问**：数据管道要读结构化结果文件，不是解析自然语言终端输出。

> **PPT-agent 引用块（不上屏）**
> - 意思：本页只推进这一主张：需要恢复或审计时，把退出码、日志、产物留成可复查工件；落盘是反馈的可审计实现，不是循环的定义条件。

# 追问卡（不上屏）

## N01–N04 · 钩子、故事与基线

- **状态例子**：`PR created; CI failing; accepted_by=null; outcome_status=pending`——比一句「完成」诚实。
- **N02 讲法**：用 Osmani 一手定义解释系统接替逐轮提示；反馈要到达下一步，不能承诺“知道错就改对”。不引 Boris/Peter 名句。

## N05–N06 · 反馈双路

- **判据一**：停止或继续不看上一轮结果的重试是 retry；抽卡比喻由此而来。
- **可审计反馈通道**：命令 → 退出码＋输出 → 留存证据 → 下一轮动作；Aider 形状：lint 非零 → 确认修复 → 错误回灌。会话内工具结果直接回传也属于反馈循环，不以落盘为定义门槛。
- **数据管道**：读结构化结果文件（run_results.json 类），不解析自然语言终端输出。

## N07–N09 · 动作档

- **分级处置官方样本**：Cursor 2026-05-29 changelog（allowlist／沙箱／分类器）；Codex `exec_policy` 危险度×沙箱×信任三维。

## N10–N12 · 门票

- **弱写法对照**：`Improve the search experience until it feels good.`（good 对谁？怎么评？）。
- **全例**：Lighthouse ≥92、LCP<1.8s、CLI 输出证明、不改 hooks、两轮无改善 abort、10 轮上限（Osmani，2026-08-14；数字不可外推）。

## N13–N16 · 裁判、出口、门

- **评估器边界（Claude Code `/goal`）**：Osmani 描述的评估器只核 transcript 硬规则（"It doesn't look at the content…"），不泛化到所有裁判；机器评分可辅助质量，最终责任仍需明确。
- **fail-closed 例**：评估输出缺 `pass` 字段又无阈值，score=0 仍可能默认放行——判定接口也要设防。
- **unknown 处理**：不强行归入 Impossible，保留交人。
- **覆盖漏洞清单**：检查被跳过、基线带病、该做的检查没安排、嵌套路径外层无限重试。

## N17–N20 · 事故与三层防线

- **quickstart 源码**：`while True`＋唯一退出分支是 max_iterations、默认 None（无限）；进度条给人看；「不可改测试」只在提示词（观测 2026-09-28）。

- **端到端**：浏览器自动化走真实用户路径；按钮点得动才算。
- **删测反例**：Kent Beck 记录 agent 删除/禁用测试；测试削弱检测关注 skip、断言降级、`|| true`。

# 一套可以现场拆开的实战样本（不上屏）

> 完整虚构样本：给站内搜索增加分页。**动作单对应动作档护栏，goal/eval 工件对应续跑档门票，触发与取消对应唤醒档；基线是人发起与判断**。数值、分支名、命令与路径都是教学模板，不是已运行的真实仓库证据，不是厂商默认值，也不是实测收益。部署时替换成项目实际入口与检查。

## 1. Goal 工件：先把「做完」写成可判定对象（续跑档门票）

```json
{
  "goal_id": "search-pagination-v1",
  "terminal_state": "结果列表第二页可打开、可返回、查询条件不丢失",
  "checks": [
    "npm test -- search-pagination",
    "npm run e2e -- search-pagination.spec.ts：浏览器搜索→第2页→返回，查询与结果对应正确；退出码0且报告留存"
  ],
  "constraints": [
    "只改 search 分支",
    "不得修改公共 API",
    "不得删除或放宽既有测试"
  ],
  "stop_clause": "两次连续无改善或达到项目资源上限时停止并保全状态",
  "outcome": "用户采用率另行观测，不作为本轮自动 Met"
}
```

四个细节：终态不是「搜索体验变好」；检查不是「模型觉得可以」；约束是不可越过的边界；采用率当前不可见，只能是 `outcome_pending`。

## 2. Action 工件：每次只拿一张可审计的动作单（动作档护栏）

```json
{
  "action_id": "act-0042",
  "principal": "search-agent",
  "action": "edit",
  "target": "src/search/pagination.ts",
  "branch": "agent/search-pagination",
  "scope": ["src/search", "tests/search"],
  "expires_at": "2026-09-28T18:00:00Z",
  "approval": "reviewer-17",
  "denied": ["commit", "push", "public-api-change"]
}
```

把 `edit` 改成 `push`、branch 改成 `main`、目标移到 `deploy/`，都算新动作重新审批——一次批准不能靠文字相似度继承。

## 3. Feedback 工件：把环境返回物落盘

```sh
set -o pipefail
mkdir -p .loop/runs/run-0042
npm run e2e -- search-pagination.spec.ts \
  > .loop/runs/run-0042/stdout.log \
  2> .loop/runs/run-0042/stderr.log
status=$?
printf '{"run":"run-0042","exit_code":%s,"commit":"%s"}\n' \
  "$status" "$(git rev-parse HEAD)" \
  > .loop/runs/run-0042/result.json
exit "$status"
```

下一轮先读 `result.json`，再读失败日志，最后选动作——不是重新问「刚才发生什么」。

## 4. Eval 工件：反馈和判定分开

```json
{
  "eval_id": "eval-0042",
  "goal_id": "search-pagination-v1",
  "evidence": [
    ".loop/runs/run-0042/result.json",
    ".loop/runs/run-0042/stderr.log"
  ],
  "verdict": "NotYet",
  "reasons": ["page_2_button_click_failed"],
  "evaluator": "search-checker-v3",
  "rubric_hash": "sha256:...",
  "missing_fields_are": "reject"
}
```

`exit_code=0` 只是环境事实；`verdict` 须覆盖页面路径、API 约束和测试保护。缺字段时拒绝，不猜。

## 5. 状态迁移：停止、验收、业务结果拆开

```text
running
  ├─ feedback=NotYet, retryable ───────→ running
  ├─ feedback=Met, artifact complete ──→ stopped_candidate
  ├─ hard limit / no progress ─────────→ stopped
  ├─ permission / dependency ───────────→ blocked
  └─ ambiguity / reviewer needed ───────→ awaiting_human

stopped_candidate + independent sign-off → accepted
accepted + external metric unseen       → outcome_pending
```

必须能回答：为什么停？谁验收？依据在哪？外部结果谁在什么时候复查？

## 6. 负例演练：先证明门会拒绝

把分页断言改成错误期望，或植入 dummy API key，跑同一条检查：非零退出码、明确失败位置、evidence link、下一轮可读的修复理由。恢复后再跑正常路径。负例通过只证明这类错误拦得住；门没红，先停止升档。

## 7. 熔断交接单：人真正接得住才叫升级

```yaml
feature_id: search-42
state: awaiting_human
stop_reason: policy_denial
last_action: edit src/search/pagination.ts
last_feedback: page_2_button_click_failed
accepted_by: null
evidence_link: .loop/runs/run-0042/result.json
reviewer: product-owner-7
resume_pointer: run-0042/action-0043
next_check: 2026-09-29T09:00:00Z
```

`reviewer` 为空、`resume_pointer` 指不到状态，就不能说「已升级」；硬拒绝不能改名「等待审批」。

## 8. 现场定档顺序（v3：从审计改为定档）

1. 先答四问：谁启动下一轮／谁判断完成／谁能改变系统／出错谁接手——现在的答案是什么？
2. 对答案缺的那格分别查：动作授权面→续跑目标／裁判→唤醒触发／取消。三个面可独立组合，不从 `/loop` 推断前两面成立。
3. 每配一样，先用负例验证它会红。
4. 答不出又不急着升：留在当前级——这是控制决策，不是失败。

## 9. 这套字段怎么泛化

不要从字段名出发，从控制问题出发：

| 控制问题 | 示例字段 | 换系统仍要保留的语义 |
|---|---|---|
| 要达到什么 | `terminal_state` | 可观察的产出终态 |
| 不能做什么 | `constraints` | 不可越过的范围与路径约束 |
| 凭什么判断 | `checks` / `evidence` | 外部可复查的证据和判据 |
| 谁能做什么 | `approval` / `scope` | 动作、目标、有效期和授权主体 |
| 为什么下一步这样走 | `verdict` / `reasons` | 判定及理由回到下一行动 |
| 现在停在哪里 | `state` / `stop_reason` | 控制状态与停止原因分开 |
| 谁接手、怎么恢复 | `reviewer` / `resume_pointer` | 责任人、恢复位置和所需证据 |
| 产出是否带来结果 | `outcome_status` | 外部结果独立于产出验收 |

**最小迁移法**：先用纸填这八个问题；再映射到已有工具；最后用一个已知错误和一次拒绝演练验证记录真的会改变下一步。
