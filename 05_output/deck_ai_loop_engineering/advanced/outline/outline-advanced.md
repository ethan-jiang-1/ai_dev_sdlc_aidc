# Outline — Loop Engineering（技术/产品场）

## 0. 这场要解决什么

听众已经在跑循环，本场不再解释“什么是 agent loop”，而直接处理一个生产问题：**你离开之后它说做完了，系统凭什么接受这句话？**

命名争议压缩为背景。Andrew Ng 的三环作为上位产品反馈图，不承担运行时定义；Osmani、Claude Code、Anthropic、Ralph、LangChain 的机制用于对照。控制链是本场的研究抽象，不是某一位 KOL 的统一 taxonomy；`stop_conditions` 的“双环三层”仍是专项深挖抽象，未回流判定层的部分不当作行业共识。

## 1. 核心判断

**Loop Governance 治理的不是“让 Agent 多跑几轮”，而是每轮继续、停止、升级和交人的资格：目标、行动、反馈、裁判、权限、状态和结果必须分开可审计。**

## 2. 核心控制链

```text
Goal / 边界
  → Action / 行动与授权
  → Environment Feedback / 环境事实
  → Eval / 裁判与证据
  → Continue | Stop | Escalate
  → State / Outcome 分账
```

三件停止骨架是控制内核：机器闸门提供局部事实反馈，硬上限提供资源包络，验收与干活分离处理完成签署权。它们不是三个“完成按钮”，也不覆盖全部控制链。

## 3. 叙事弧

```text
你离开后它说做完了
  → 完成宣告不是完成证据
  → 先把一轮完整控制链画出来
  → Goal/边界决定验收对象，Action/授权决定能做什么
  → Feedback 是环境事实，Eval 才解释是否满足
  → Continue/Stop/Escalate 是不同控制出口
  → State 与 Outcome 分账，停止不等于接受
  → 机器闸门、硬上限、独立验收分别堵三类失效
  → 裁判仍可能被操纵，必须校验而不是换模型迷信
  → 长程调度解决接续，不自动解决总账、授权与验收
  → 自主度不是第 N 轮，而是控制权能否在风险边界内转移
  → 先演练负例、权限、熔断、接手和恢复，再谈少守
```

## 4. 页面

**A01 · 你离开后，它说做完了**
Loop 的难题不是能否行动，而是回来时凭什么信完成宣告。

**A02 · 名称不是方法**
不同来源的 loop 外延不兼容；本场治理的是可审计控制决策，不站队某一种环数。

**A03 · 先画完整控制链**
Goal/边界 → Action/授权 → 环境反馈 → Eval/裁判 → 继续/停止/升级 → State/Outcome；这是研究抽象，不是 KOL 原话。

**A04 · Goal 决定“完成什么”**
目标必须有可观察终态、检查方式和路径约束；外部业务结果不可见时不能伪装成自动 `Met`。

**A05 · Action 决定“允许做什么”**
下一步行动必须落在本轮授权的目标、范围和有效期内；选择下一步不等于权限自动扩大。

**A06 · Feedback 是环境事实**
工具结果、测试、构建、浏览器路径、拒绝和失败原因必须进入下一步；不看反馈就重跑是 retry，不是 loop。

**A07 · Eval 是裁判，不是反馈**
Eval 用预设判据解释环境反馈；判据要能观察、能复查，并明确谁能修改它。

**A08 · 继续、停止、升级是三条控制路径**
未满足且可修复才继续；满足预设产出才成为停止候选；不可判、高风险、拒绝或无法恢复就升级/交人。

**A09 · Stop ≠ Accepted**
资源耗尽、无进展、拒绝熔断、模型收尾和人工暂停都可能停止控制流，但不自动代表产出被接受。

**A10 · State 与 Outcome 分账**
`running / blocked / awaiting_human / stopped` 是控制状态；`accepted` 是产出验收；`outcome_pending` 是外部结果等待观测。

**A11 · 第一类失败：提前宣告完成**
文件变多、回复很满、空壳能打开或单测通过，都可能不是目标完成；目标敌人是 premature completion。

**A12 · 三件停止骨架各管一件事**
机器闸门拦局部事实错误；硬上限管资源与失控；验收与干活分离处理签署权；三者不可合并为“它停了”。

**A13 · 闸门必须覆盖真实 feedback path**
存在一个 bound 或测试不够；实际嵌套反馈路径未覆盖、基线未过、测试被削弱或该做的事没做，仍会产生假通过。

**A14 · Eval 分离不等于判得对**
输入可被操纵、裁判偏好自身输出、代理目标会被过优化；独立模型不是可信度证明。

**A15 · 裁判要被单独校验**
用已知失败、人工标注冲突样本和版本化判据检查 false approve/false reject；没有效果阈值就不能伪造通用放行线。

**A16 · 逐轮判断要改变下一步**
`Not yet met` 带理由继续；`Met` 只接受预设产出；`Impossible` 停止并交人/改条件；不是问模型“做完了吗”。

**A17 · 资源上限是包络，不是质量分**
轮数、时间、拒绝、成本、过期和无进展检测保护系统资源；覆盖不到实际路径的上限等于没有上限，耗尽后先保全状态和交接。

**A18 · 拒绝不是统一的停机语义**
单次拒绝可以带理由寻安全路径；持续拒绝可熔断；硬政策拒绝不可改名为“待人批准”；每种出口必须记录原因和恢复语义。

**A19 · 人工审批必须可达**
执行前让指定人看到动作、目标和风险，能作决定，并能从同一状态恢复；父线程看不见、无恢复指针时，不能声称“已升级”。

**A20 · 批准只绑定一次动作**
授权绑定动作、目标、分支和有效期；换 feature、扩大范围或从 edit 变 commit/push 必须重新授权。

**A21 · 长任务把状态移出对话**
每轮恢复 State，再从未完成项选择 Action；文件队列和事件触发解决接续，不自动解决 feature 级授权史、优先级变更、阻塞和验收总账。

**A22 · 外层调度只决定“何时再跑”**
条件、时间、事件和持久进度是触发形态；触发前仍要检查目标、权限、反馈和资源资格。

**A23 · 自主度是控制权转移，不是第 N 轮**
升档要联测负例闸门、独立判据、预算、权限和接手路径；判定冲突或接手不可达就退回人工。

**A24 · 先审计链，再撤逐轮值守**
Goal/边界 → Eval/负例 → 真实 Feedback → State/Outcome → Stop/Escalate/恢复；只证明可治理设计，不宣称效率或质量收益。

## 5. 结论级关系

```text
Goal/Eval：定义要满足什么、如何判
stop_conditions：提供闸门、资源包络、验收分离
loop_governance：治理继续、停止、升级、授权、状态与交接
harness_governance：保证单次运行本身受控
```

## 6. 语言与证据边界

- 首现术语：目标（Goal）、行动（Action）、环境反馈（Environment Feedback）、评估/裁判（Eval/Grader）、验收（Accepted）、交还（Escalate）。
- 控制链是本仓研究抽象，不能说成 Ng、Osmani 或 Claude Code 的统一原话。
- `stop_conditions/README` 的“双环三层”在尚未回流判定层前只能作为专项研究抽象/提案，不写成已证行业架构。
- 不把 Stop、Blocked、Awaiting human 或 Outcome pending 说成完成。
- 不把某产品的 3/20、7 天、59 分钟等参数说成通用阈值。
- 不使用红、绿、灯作为术语；参数、源码版本和产品名留备注。

## 7. 旧稿取舍

- A02/A03 压缩命名外延，不让命名争议占据工程主线。
- A04–A11 先完整建立控制链，再用提前完成、Stop/Accepted 和 State/Outcome 组织失败。
- A12–A18 保留三件骨架和深挖硬核，但修正“硬上限=完成”“分离=可信”的错位。
- A19/A20 补齐审批可达、恢复指针和授权绑定。
- A21/A22 让调度服务 State/Action 接续，而不是单独讲文件和触发。
- A23 把自主度从等级表改成控制权升档条件。
