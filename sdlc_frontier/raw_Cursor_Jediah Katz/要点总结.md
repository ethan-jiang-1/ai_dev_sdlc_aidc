## 核心论断：少即是多

> *"给模型更少的预设信息，让它自己按需拉取上下文。"*

Cursor 团队发现在模型能力足够强之后，**静态上下文（一次性注入所有信息）的边际收益在递减**。反而给得越少，让 agent 自己搜索、自己决定该看什么，效果更好。

**两种上下文工程范式对比：**

| | 静态上下文（过去） | 动态上下文发现（现在） |
|---|---|---|
| 注入方式 | 启动时全部注入 | Agent 运行时按需拉取 |
| Token 效率 | 大量浪费在不需要的内容上 | A/B 测试降低 **46.9%** token 消耗 |
| 响应质量 | 无关信息干扰决策 | 只看到当前任务需要的内容 |
| 维护成本 | 需要人工更新预设上下文 | Agent 自行发现最新信息 |

## 五个动态上下文发现模式

### 1. 长工具响应 → 文件

Shell 命令和 MCP 调用的 JSON 响应可能巨大。传统做法是截断 — 可能丢失关键信息。

**Cursor 的做法**：把输出写入文件，让 agent 用 `tail` 检查末尾，需要时再 `read` 更多。**减少了因上下文超限触发的摘要次数。**

### 2. 摘要时引用聊天历史

长对话摘要时，agent 可以回溯引用聊天记录中丢失的细节，而不是只依赖当前上下文窗口。

### 3. 支持 Agent Skills 开放标准

Skills 作为动态上下文的一种：只在 agent 判断需要时才加载，而不是预置在系统提示词里。

### 4. 按需加载 MCP 工具

只加载当前任务需要的 MCP 工具，而不是全部工具列表。A/B 测试：**token 消耗降低 46.9%。**

### 5. 集成终端会话 = 文件

把终端会话暴露为 agent 可读取的"文件"。Agent 可以回溯检查自己之前执行的命令和输出。

## Agent Harness 工程：用产品思维造调度框架

这是 2026 年 4 月与 Stefan Heule 合著的文章，揭示 Cursor 如何对待 Agent Harness 如同**产品本身**。

### 上下文窗口的演进

```
2024 年底：大量静态上下文 + guardrails
             ↓
2026 年：   动态上下文 — agent 主动拉取，而非预先填入
```

### 双层评估体系

| 层 | 工具 | 衡量什么 |
|---|---|---|
| **离线** | CursorBench（自建）+ 公开基准 | 基础能力、回归检测 |
| **在线** | A/B 测试 | Keep Rate（代码保留率）、LLM 满意度 |

### 工具错误分类 + 自动修复

建立了分类体系：`InvalidArguments`、`UnexpectedEnvironment`、`ProviderError` 等。异常检测告警 + 每周自动 Cloud Agent 扫描日志、创建工单。

### 模型深度定制

**不同模型用不同的工具格式：**
- OpenAI → patch-based editing
- Anthropic → string replacement editing

细化到**模型版本级别**的定制提示词和反 quirks 措施。

### Mid-Chat 模型切换

支持对话中途切换模型（比如从 Haiku 切到 Opus），框架处理不同模型的工具集差异和缓存失效问题。

### 未来预测：多智能体协作

> *"AI 辅助软件工程的未来是多智能体 — 规划 agent、编辑 agent、调试 agent 各司其职。"*

## 核心教训

> **"上下文不是越多越好。给 agent 搜索和发现的能力，比把所有信息塞给它更有效。"**
>
> **"Agent Harness 应该像产品一样迭代 —— 离线评估 + 在线 A/B + 异常告警 + 自动化修复。"**
>
> **"不同模型需要不同的工具格式和提示词。不是所有模型都一样聪明，但它们可以一样好用 — 前提是你为每个模型定制了 harness。"**
