# Talk 页面结构（现场版 v0.1 · 23 页 · 45 min · 初稿）

> **初稿，待用户 review 故事线 v0.1 后再铺逐页内容。** 全场用「责任如何上移 + 组织如何分工」串起五层：
> Prompt / Context 是任务层（一线团队），Harness 是平台层（组织集中建设），Loop / Graph 是治理层（架构 + 治理）。
> 页面结构骨架继承 `-opc` 的 23 页（同 45 min 预算），但每页结论与必讲要点换成组织读法。

## 开场（3.5 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---|---|
| P1 | 组织航海指南 | 0.5 | 题目、讲者；问题：一个组织要把 AI Coding 建成怎样的能力？ |
| P2 | 五个角色，已经分别有人替你命名 | 1.5 | Boris Cherny 讲 Loop；Böckeler 定义 Harness；Steinberger 讲 State Graph；组织里这些角色不是一个人，是一群岗位。 |
| P3 | 五个 Engineering 背后，是三层越来越重的责任 | 1.5 | 信息责任 → 行动责任 → 组织责任；一人公司是一个人扛三层，组织是必须决定每一层该由谁承担、该不该集中。 |

## 第一幕：五层不是五个新词（12 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---|---|
| P4 | 同一台发动机，把人的动作一格格往上推 | 2 | 模型能力增强 -> 单次交互边际收益下降 -> 杠杆点上移；METR / Anthropic 两条证据；叠加，不是替代。 |
| P5 | Prompt 管表达，Context 管模型此刻所见 | 3 | 任务层的两件事，放权给一线；context rot；两者解决不了执行边界。 |
| P6 | Harness Engineering：把"能做"变成"可交付" | 2.5 | Agent = Model + Harness；权限、沙箱、工具、验证、执行记录与 CI；这是组织唯一该集中建设的一层。 |
| P7 | Loop 管时间上的反馈；Graph 管空间上的协作 | 2.5 | Loop 黄金法则；Graph 显式节点/边/状态；Graph 可在部分节点使用 Loop；均新兴、低置信度。 |
| P8 | 五层同时活着，但组织的岗位不能只有一种 | 2 | 关系图 + 组织读法：任务层 / 平台层 / 治理层；今天重仓成熟的前三层。 |

## 第二幕：为什么答案停在 Harness（10 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---|---|
| P9 | Loop / Graph 会放大结果，不会补上缺失的执行边界 | 1 | 每个节点最终都落到一次真实执行；上层越复杂，每个节点越要先独立授权、检查、记录。 |
| P10 | 模型决定能力上限，Harness 决定交付底线 | 1.5 | 权限清楚、环境隔离、工具受控、结果可验、过程可追、失败即停；同一模型换一圈 Harness 就是两套交付系统。 |
| P11 | Harness 在行动前引导、行动后反馈 | 3 | Guides / Sensors；computational / inferential；确定性优先——组织要审计，门禁必须可复现。 |
| P12 | Harness 先保证可靠，再承载组织知识 | 2.5 | 圈住 / 拦住 / 看清 = 统一沙箱 / 统一门禁 / 统一观测；Knowledge Map 承载组织归属与正确路径。 |
| P13 | 模型可以提议下一步；执行端必须独立决定放行 | 1 | 提议 → 权限与确定性门禁独立检查 → 放行或拒绝并记录；提议权交给模型，执行权留在 Harness（= 留在平台/治理）。 |
| P14 | 2026 的教训：生成时相信模型 ≠ 执行时授权 | 1 | 工具调用形状被伪造 -> 执行端缺独立授权 -> 操作发生；authorize at execution；结尾提出"边界必须有人负责"→ 组织里是治理层。 |

## 第三幕：组织的答案：共享平台 vs 各自为政（8.5 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---|---|
| P15 | 组织的失败模式：每个团队各装一套 harness | 1 | 重复建设、无法审计、供应链风险外溢；`-opc` 没有这个问题，组织一定有。 |
| P16 | 绝大多数场景，先借现成 Harness（但统一借） | 2 | 产品把沙箱、权限、观测随产品交付；Start with the simplest viable system——但准入与放行要统一。 |
| P17 | 公开 14 天，DeepSeek Harness 接近 20 万 GitHub stars | 3 | 近 20 万是主信号；2,286 条生态快照是支持信号；注意力聚到"可扩展边界"，但不是质量认证。 |
| P18 | 热度只是入口；对组织，价值在可治理、可审计、可复用 | 2.5 | 真正可借的不是插件数量，而是平台团队验证过的、可治理的能力组合。 |

## 第四幕：DSH 的定位与组织的治理边界（5 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---|---|
| P19 | DSH 不是插件商店；它是一套可组合的 Harness runtime | 1 | 三项收益来自共同合同和共同事实：能力可组合、可替换，行动按顺序进 append-only session log。 |
| P20 | 插件进入执行链后，真正的问题变成：谁说了算？ | 2.5 | 四个治理问题：谁允许接入、谁能替换、谁在执行前签字、谁能还原事实（准入/供应链/放行/审计）。 |
| P21 | Harness 的最终控制权归治理，不是人人自建 | 1.5 | 部件继续借；治理层最终决定能力能否进入、实现能否替换、门禁是否放行、事实能否重建。 |

## 收尾（2 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---|---|
| P22 | 组织要把 AI Coding 建成分层能力 | 2 | 任务归团队（Prompt/Context）→ 平台归组织（Harness）→ 边界归治理（Loop/Graph + 审计）；不是为了造框架，而是知道该集中什么、放权什么、治理什么。 |

## 叙事检查（骨架）

1. P2 给出五个 Engineering；P3 把它们翻译成组织无法回避的信息、行动、组织三层责任；P4 再解释责任为何随模型能力上移。
2. P5-P8 逐层回答"说什么、看什么、怎样行动、怎样组织"，P8 明确五层对应组织三层岗位（任务 / 平台 / 治理）。
3. P6 只定义 Harness；P9 证明 Loop/Graph 补不上底层边界；P10 才说明边界怎样改变交付底线。
4. P11-P14 依次讲可靠性机制、组织知识承载、提议权与执行权分离、执行时授权事故，完成"为什么是 Harness"论证。
5. P14 提出"边界必须有人负责"，P15 给出组织特有失败模式（各自为政），P16 保住"先借现成、但统一借"的默认答案。
6. P17 用 DSH 爆发建立需求信号，P18 把热度转成组织可治理的收益，P19 解释收益为何来自 runtime 的共同合同与共同事实。
7. P20 把插件问题提升为治理问题；P21 用"治理层 final say"回答；P22 以三层分工直接回答开场，P23 留下原则。

## 口径红线（继承 -opc，待本目录证据层落地后细化）

- 前三层成熟，Loop / Graph 是新兴观察对象，不讲成既定生产范式。
- Harness 是可靠性边界，不等于一定在几何上"包住"所有分布式节点。
- DSH 原生机制不是 MCP；说 `ctx.llm`、`ctx.tools`、capability seam、plugin。
- GitHub star 与 2,286 条生态数据都是 2026-08-27 快照；只讲 attention / 扩展面，不讲成熟或增长曲线。
- CVE 只讲执行时授权缺失的因果链，不堆厂商名 / 编号。
