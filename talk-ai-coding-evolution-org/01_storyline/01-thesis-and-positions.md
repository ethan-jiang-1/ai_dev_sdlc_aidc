# 核心论点与立场（v0.1 摘要）

> 详细论证与证据分布见 [`00-storyline-map.md`](./00-storyline-map.md)（各幕要点）。
> 与 `-opc` 同源但立场不同：`-opc` 落在「个人技能深度」，`-org` 落在「组织能力分工 + 治理」。

1. **责任叠加上升，组织把它翻译成"分工"**：五层不是换代，是信息、行动、组织责任随工程注意力一起叠加上移。
   一人公司是被迫一个人扛三层；组织是可以分工的常态——问题从"我掌握多深"变成"这三层责任该由谁承担、该不该集中"。
2. **成熟度标尺**：前三层（Prompt / Context / Harness）成熟可信；后两层（Loop / Graph）叙事期、低置信度。
3. **问题最终回到 harness**：这是**我们的判断**，不是报告背书（报告把 Context 与 Harness 并列）。
   Loop / Graph 会放大、组织结果，却不会补上节点缺失的执行边界；每一次真实动作仍需独立授权、检查与记录。
4. **可靠性是系统的属性**：模型给能力，harness 给可靠性；确定性优先（computational > inferential）。
   组织要审计、要合规，门禁必须建立在确定性之上。
5. **组织里唯一该"集中建设"的一层是 harness**：Prompt / Context 放给一线（任务自主），Loop / Graph 归治理层（编排 + 审计），
   而 harness 的可靠性、权限、门禁、观测、provenance 只有统一成平台才能规模化、被审计、被治理。
6. **组织的失败模式是"各自为政"**：每个团队各装一套 harness → 重复建设、无法审计、供应链风险外溢。
   转向共享平台的判断不是"工具多"，而是"组织开始承担运行边界的责任"。
7. **DSH 的爆发与定位**：热度只是入口，真正可借的是平台团队验证过的、可治理的能力组合；
   DSH 的定位是可组合的 Harness runtime，registry / adapter / capability seam / enforced gate / append-only session log
   正好是组织四项治理决定（准入、替换、放行、重建事实）的机制证据。
8. **Harness 最终控制权归治理**：不等于组织里人人自建；治理层必须能决定能力能否进入、实现能否替换、门禁是否放行、事实能否重建。
   带走原则：**部件可借，边界归治理。**（完整三层：任务归团队，平台归组织，边界归治理。）

## 一句话主线（源自 00-storyline-map）

模型越强，人机互动行为越变；组织要掌握的临界点同样是 **harness**——但组织的答案不是"让每个人都学会五层"，
而是把它建成**共享平台 + 治理边界**：任务归团队，平台归组织，边界归治理。
