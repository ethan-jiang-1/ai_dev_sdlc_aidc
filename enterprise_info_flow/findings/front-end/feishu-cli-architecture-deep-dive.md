## Lark CLI 架构

**核心设计理念**：将飞书从"人用工具"转变为"AI 可调用的执行层基础设施"。

### 三层调用结构

| 层 | 前缀 | 说明 |
|------|------|------|
| Shortcuts | `+` | 人类和 AI 都友好 |
| API Commands | — | 100+ 精选命令，对应开放平台端点 |
| Generic API | — | 覆盖全部 2500+ 接口 |

### 11 大业务域

即时通讯、云文档、日历、多维表格、邮箱、任务、视频会议、知识库、云空间、通讯录、事件订阅

### 为什么 CLI 比 MCP 更适合 Agent？

| 指标 | CLI | MCP |
|------|-----|-----|
| 单次调用成本 | 基准 | **高 10-32 倍** |
| 任务完成可靠率 | **100%** | 72% |
| 初始化开销 | 几乎为零 | Schema 加载数万 tokens |
| 错误恢复 | 重新执行命令 | 重新连接+重新加载 schema |

**根本原因**：LLM 训练数据包含数十亿行 CLI 命令和输出——模型天生"会用"CLI。MCP 是 2024 年才定义的协议，训练数据中几乎没有。

## 这意味着什么：流程引擎被 CLI 替代

传统 BPM 的流程引擎 = 预定义路径 + 条件分支 + 人工节点。

CLI 化之后：
- 没有预定义流程了——Agent 按需调用原子能力
- "审批"变成了一个 CLI 命令，Agent 在需要时调用
- "查数据"变成了一个 CLI 命令，Agent 在需要时调用
- 流程不是被"设计"出来的——是在 Agent 调用序列中**涌现**出来的

**但这不意味着流程消失了。** 它意味着流程从"预定义的 BPMN 图"变成了"Agent 行为边界 + 权限控制 + 审计追踪"。等价于 Camunda ProcessOS 的 "framed autonomy"——同一个范式，不同的术语。

## 对"信息加工流"研究的启示

飞书/钉钉的 CLI 化验证了一个推论：**AI 时代的信息加工流，执行层从"流程引擎"变成了"Agent 可调用的原子能力"。** 流程仍然存在——但它从预定义路径变成了在治理边界内的自由组合。这跟 SDLC 的 "AI Sandwich"（人在两端定义和验收，AI 在中间执行）是完全同构的。
