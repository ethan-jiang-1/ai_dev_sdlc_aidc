# talk-harness-102

## 定位

**工程流程实战场**：面向 AI 已经用起来、正在写智能体，但工程能力还没跟上的人。不是从零认识 AI，也不以熟悉团队研发交付为前提。

全场只追一个问题：

> **怎么让 Agent 一轮接一轮地干，而不是越干越糊涂？**

核心主张：**用研发与工程流程维护 Agent 的清醒：需求先加工、执行前先拆分、每轮用证据判断、有效结论回到现行状态，再进入下一轮。**

这里的“清醒”是工程上的工作状态，不是模型心理状态；术语定义见 [CONTEXT](<CONTEXT.md>)。

## 系列定位与本场边界

**101 是覆盖关键概念、可独立满足多数读者的完整入门；102 是深入工程执行的延展。** 本场仍独立成篇，不要求听众先听过任何内容；允许重用需求、验收、治理等必要概念，但以“怎样组织任务、让反馈决定下一轮并接续工作”为中心，不复刻其他场的页面或操作件。

本场从 **Agent 的工作视角**讲人的工程职责：让它始终能找到当前目标、工作边界、已验证进展、下一步和续停依据。需求拆分是进入执行的入口，iteration by iteration 是运行方式，Harness 治理是持续维护这条流程的工作。

- 讲需求如何进入执行、任务颗粒度如何判断、验证结果怎样决定下一步、现行状态与约束如何让工作接续。
- 人可以让 Agent 协助澄清、拆分和设计检查；人保留业务取舍、授权和最终验收的责任，不承担逐行指挥。
- 用一个“coding agent 开发业务 Agent”的例子贯穿；两种角色的称呼见 [CONTEXT](<CONTEXT.md#二角色与术语>)。
- 聚焦单条研发工作链。多 Agent 拓扑、产品源码解剖、具体平台配置不在本场范围。
- 工程流程不是瀑布式一次过关：验证暴露问题后，允许回到需求、拆分或检查设计。

## 来源与工作方式

本场参照实践层的需求工程目录分工；Harness 治理、Loop 治理采用已读的内部实践消化。需求澄清与拆分模板是本场教学提案。只在 [来源台账](<02_evidence/00-sources.md>)登记来源锚点，不修改上游、不把其他 talk 的文案搬过来。内部方法消化、外部一手证据和本场教学提案分别标注。

案例是**合成教学案例，尚未运行**，不是客户项目或实测效果。后续如做可运行演练，运行证据与叙事源分开保存。
