# 102 故事线 v0.1 — 工程流程维护 Agent 的清醒

> **供 review 的上游提案，不是逐页稿。** 定位以 [README](<../README.md>)为准，词义以 [CONTEXT](<../CONTEXT.md>)为准，案例事实只在 [案例走读](<02-case-walkthrough.md>)维护。来源分级见 [台账](<../02_evidence/00-sources.md>)。

## 主问题与推导

> **怎么让 Agent 一轮接一轮地干，而不是越干越糊涂？**

推导不是“把传统 SDLC 介绍一遍”，而是不断补齐开发 Agent 此刻工作所缺的依据：

**需求不等于可执行任务 → 执行前先拆 → 一个小闭环先成立 → 检查产生反馈 → 反馈决定下一轮 → 现行状态接住变化 → 当前范围有据可交付。**

从第一轮到下一轮，重复的是工作节奏，积累的是可信进展。需求澄清与拆分都可以由开发 Agent 协助完成，人负责业务取舍与边界确认；并非人写完所有计划，Agent 才被允许动手。本场的工程延展落在行动链：把需求加工为任务，按证据决定下一步，让有效状态与约束支持接续。

## 开场：做出来以后，下一轮该怎么推进？

**职责**：听众认领自己的工程困境，明确本场要解决的是任务、下一轮决策与工作接续，不是重新学 Agent 定义或展开一套通用交付观。

- 三个现象：开发 Agent 一口气做了很多却不是所需；改了几轮开始忘记前面的限制；换一次会话又从头猜。
- 把同一句模糊需求交给开发 Agent，展示它缺什么依据；引用 [案例 §一](<02-case-walkthrough.md#一先看一句需求为什么不能直接开工>)。
- 提问：“它此刻知道‘处理完’是什么意思吗？”不是质疑模型会不会写代码，是问工作有没有被组织好。

**听众拿走**：产出不自动给出下一步；要回到任务依据和当前证据作决定。

**转场**：先别催它开工，先把结果说清。

## 第一幕：需求先变成可以判断的结果

**Agent 的问题**：“你到底希望什么变化？哪些事不归我做？”

- 走读 [需求澄清小单](<02-case-walkthrough.md#二需求先加工成可判断的结果>)：从“自动处理”收窄到建议与依据，保留人工动作。
- 同时设计正常样本、不确定样本与越界请求；人确认预期，不让开发 Agent 把业务空白填成猜测。
- 验收不只是程序不报错。机器核结构、证据关联和边界；人确认业务含义。
- 不确定时可以先做有范围的探索，探索的输出是结论，不冒充功能完成。

**听众拿走**：需求与验收互相校对，未决问题有去向。

**转场**：结果清楚了，也不能把整个项目一口吞下去。

## 第二幕：执行前先拆，拆也有流程

**Agent 的问题**：“这次先让哪件事成立？哪些结果必须等前面？”

- 用 [五个拆分动作与工作清单](<02-case-walkthrough.md#三执行前先拆把需求加工成工作单元>)走一遍，而不只念任务卡字段。
- 示范太粗、太细、可执行的三个版本；用 T1 说明跨文件的纵向小闭环，不拿代码行数当粒度。
- 依据结果、未知、依赖、风险与验证边界拆；失败不能定位就再拆，拆成机械搬运就合并。
- 任务卡展示完整填法；开发 Agent 可提出清单，人审业务边界、依赖、验收与授权。

**练习一**：给一个“加上自动回复”的后续需求，让听众决定是立即执行、再拆还是先问人；写出一张任务卡中的结果、边界、验证和暂停条件。判题依据是有没有识别新授权与可检查结果，不考术语。

**听众拿走**：粒度来自“能验、能定位、风险能控”，不是切得越细越工程化。

**转场**：任务清单只是一张待验证的地图，开工后要靠结果修它。

## 第三幕：一轮先跑小闭环，检查不能只是打个勾

**Agent 的问题**：“我凭什么知道这一步成立了？”

- 示范 [一轮怎么跑](<02-case-walkthrough.md#四一轮怎么跑动作后面必须有去向>)，再演示 [演练一](<02-case-walkthrough.md#演练一先跑通一个小的完整结果>)。
- 正确队列仍可能没有有效依据；界面看起来好不等于可验收。
- 让一条坏例触发失败，说明检查也需要被验证。未执行、执行失败与通过分开。
- 执行者可跑检查和报告结果，但标准不能被随手降低以获得绿灯。

**听众拿走**：一个小结果要有真实证据；完成一个任务不等于完成整个项目。

**转场**：发现失败了，下一轮到底该改什么？

## 第四幕：iteration by iteration，让反馈真正改变下一轮

**Agent 的问题**：“这一轮学到了什么？下一轮依据它做什么？”

- 走 [失败去向表](<02-case-walkthrough.md#失败去向表>)与 [演练二](<02-case-walkthrough.md#演练二用反例决定修什么而不是凭感觉多加-prompt>)。
- 区分回需求、修实现、再拆、修检查、重核版本和交人；不是所有失败都加 Prompt，也不是所有失败都补全局规则。
- 修反例后回归已成立的行为，避免“这次好了，上次坏了”。
- 展示 [T2 连续两张卡](<02-case-walkthrough.md#同一-t2-跨两轮连续卡均为预设脚本>)：失败轮保留 T2 未完成，修复轮重读失败证据与剩余预算，仍做 T2，复验成立后才转下一个任务。一项任务可跨多轮；轮次不是任务数量。

**练习二**：给出“结果有输出，但检查没运行”的状态，再给“旧规则检查全绿”的状态。请听众为下一轮选目标并写理由。合格答案必须不标完成、不复用错版本绿灯，并给出重查或交人路径。

**听众拿走**：下一轮不是再来一次，而是根据有效反馈做下一件正确的事。

**转场**：但需求会变，人会补意见，会话也会断；哪些结论现在还有效？

## 第五幕：维护现行状态，这就是治理落地的地方

**Agent 的问题**：“我们现在到底做哪一版？哪些旧结论还能用？”

- 走 [演练三](<02-case-walkthrough.md#演练三规则变了又换了会话>)：改规则、换会话，旧通过记录不能替当前版本验收。
- 展示一份失败后的轮次卡，让零记忆开发 Agent 接续；它要能找到目标、规则、版本、未验证项与下一步，而不是读完整聊天历史。
- 用 [最小环境修复记录](<02-case-walkthrough.md#最小环境修复记录预设脚本关联-ev3>)演示错误入口如何被开轮核对拦住、修复后怎样复验与恢复，再看 [治理动作表](<02-case-walkthrough.md#六把-harness-治理做成日常动作>)：每个事实谁维护、每条规则在哪里执行、失败怎样送达决定分支。
- 当场命名 Harness 治理：持续维护外部工作环境，为当前执行提供现行依据、实际约束与检查入口。下一轮具体做什么由循环控制决定；两者配合，不把一切统称一层。
- 新增约束有失败锚点、验证与退出条件；过期材料退出现行入口。重点不是环境越写越厚，而是接手者能据当前状态继续正确的下一步。

**听众拿走**：长期清楚靠现行状态和执行点，不靠模型记住一切。

**转场**：环境能接续了，也不意味着应该无期限地做下去。

## 第六幕：可以继续、应该问人、已经够了

**Agent 的问题**：“现在该继续、暂停还是交付？”

- 走 [停止与交付](<02-case-walkthrough.md#七怎样停怎样交付>)：当前范围有证据与认可才算交付；预算耗尽、权限阻塞、没有进展只是暂停原因。
- 不给通用轮数，不承诺测试通过就能上线。业务效果不可观察时留待后续，不用代码结果偷换。
- 从开场的一口气写完，回到一轮一轮形成可信进展。

**收尾**：**需求落成可执行的任务，执行结果形成证据，证据决定下一步；每轮留下的现行状态，让工作能接着往前。**

## 讲述时间提案

| 段落 | 分钟 |
|---|---:|
| 开场 | 4 |
| 第一幕 | 6 |
| 第二幕，含练习一 | 11 |
| 第三幕 | 7 |
| 第四幕，含练习二 | 10 |
| 第五幕 | 10 |
| 第六幕 | 5 |
| **合计** | **53** |

这是内容分配提案，不是已实测时长或页数预算。短场先压练习与展开，不删“拆分→反馈→现行状态”三段因果。规格决策见 [开放问题](<04-open-questions.md>)。

## 进入下游前的 review 检查

- 不听 101 也能理解本场问题；没有重讲它的五件事。
- 第二幕没有吞掉后半场，需求拆分不是唯一落点。
- 第四幕明确上一轮结果如何改变下一轮；第五幕有变更与换会话两个断点。
- 每幕都能指到同一案例中的输入、动作、证据与失败出口。
- 业务 Agent 的质量检查与开发 Agent 的过程检查没有混成一个“AI 自己评自己”。
- 未决选择与缺口统一在 [开放问题](<04-open-questions.md>)，本文件不另立待定清单。
