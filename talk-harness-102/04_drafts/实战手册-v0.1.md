# 让 Agent 一轮一轮地做下去：工程流程实战手册

> 面向已经在使用 AI、正在写智能体，但工程流程还没形成手感的人。目标不是让 Agent 一次做完，而是让每一轮都知道当前目标、依据、边界、证据和下一步。
>
> **读者如何用**：先按第 1—3 步澄清需求、拆分任务并准备本轮，第 4 步执行与反馈，第 5 步保存接续状态；规则或实现变化看第 6 步，工作环境缺口看第 7 步；最后按第 8 步决定交付还是停下。短任务可把空格填在同一张工作单里，跨会话或风险较高时再留轮次记录。文中的工单分流例子是**合成教学案例，未实现、未运行**；预期结果和轮次记录用于演示方法，不是测试日志或效果承诺。

## 先抓住一条主线

开发 Agent 不会因为聊天很长就自动记得什么仍然有效。要把工作组织成一个可接续的过程：

**需求说清 → 工作拆到可判断 → 选定本轮 → 在边界内实现 → 验证并看证据 → 决定继续、重拆、交人或完成 → 更新现行状态。**

任务和轮次不是一回事：一个任务可能跨几轮；每一轮都要消费上一轮的结果。失败后重复原指令、换个说法再试，不算迭代。停下来也不等于完成。

下面的填写栏可直接抄用：

- 需求负责人／业务规则确认人：________
- 当前需求或规则依据及版本：________
- 当前任务及预期结果：________
- 本轮目标：________
- 允许改动／禁止动作：________
- 验证办法／指定验收者：________
- 当前状态（通过／失败／未验证）：________
- 证据关联（对应目标版、实际加载版、实现或输入）：________
- 下一步／暂停条件／有权接手的人：________

### 总工作单已填例（合成、未运行）

| 字段 | 示例 |
|---|---|
| 负责人／当前依据 | 业务负责人确认 R2：已取消订单即使未收货也转人工 |
| 当前任务／本轮目标 | T3 未完成；先核实际加载版，再补当前实现功能回归 |
| 允许与禁止 | 核查入口与本功能；不发送、不改订单、不退款，修入口须有维护授权 |
| 检查／验收 | 核版本，运行样本、结构／依据、动作边界检查；负责人核业务意义 |
| 状态／证据 | R2／演练实现丁／A–F／EV3；未验证，无真实工具结果 |
| 下一步／暂停 | 先读加载器实际返回；不符或检查不可恢复交维护者，业务歧义交负责人 |

这是暂停交接的示范，不是功能验收。下面各步骤展示如何形成这些字段，结尾连续案例说明它们怎样变化。

## 第 1 步：把愿望变成可判断的需求

先不要让开发 Agent 直接写代码。原话往往只说了想要什么，没有说不做什么、遇到未知怎么办，以及什么证据能说明结果符合需要。

### 要做什么

1. 写明谁在什么场景需要什么结果。
2. 把“本次要做到”与“以后也许要做”分开。
3. 列出禁止动作、风险边界和必须转人的情况。
4. 对照验收样本逐条问：预期是什么？为什么？谁有权确认？
5. 把未知分类：业务规则未定，交负责人决定；技术可行性未知，可安排限时、只读或沙箱探索，探索结果不是功能完成。

### 完成标准

一个不参与聊天的人能说出本次范围、范围外事项、关键例外、预期结果和由谁验收。至少一个正常情形和一个不确定或风险情形有明确去向。无法回答的地方标“待确认”，不让 Agent 猜成规则。

### 常见坑

- “自动处理”可能指分类、回复、改订单、退款，不能把它们当成同一件事。
- 验收标准不能在看到实现结果后，为了让它通过而临时改写。
- “人工兜底”要具体到什么条件转给谁、交付哪些信息；否则只是模糊出口。

### 填写

- 使用者／场景：________
- 本次要产生的结果：________
- 本次明确不做：________
- 规则未覆盖或信息不足时：________
- 验收样本及预期：________
- 规则和样本由谁确认：________

### 已填需求例（合成，未实现、未运行）

- 使用者／场景：人工坐席收到一条工单，先核查建议再决定实际分派。
- 本次结果：建议队列、依据原文、所用规则版、缺失信息。
- 本次不做：不给客户发消息、不修改订单、不退款，不处理真实客户数据。
- 未知去向：信息不足或规则未覆盖，转人工待确认；未决政策交业务负责人。
- 预期例：未收货且只问配送 → 物流；已收货且商品破损 → 售后；只说“订单有问题” → 人工并说明缺收货状态和问题类型。
- 确认者：业务负责人确认规则和样本；程序检查结构、依据和边界，指定的人核业务含义。

## 第 2 步：执行前拆分工作，不先拆文件

拆分不是把需求切成一串代码操作，也不是要求开始前猜完所有实现细节。它要把结果加工成有依赖、有边界、能检查、失败能定位的工作单元。

### 五个动作

1. **从结果找最小完整路径**：先问用户最终要观察到什么，再找证明这项行为成立所需的最小闭环。文件和函数等理解现有项目后再决定。
2. **把未知单列**：业务选择由人定；技术未知可以先探索，但要写时间/权限边界、产出和停止条件。
3. **按结果和风险切块**：每块说清做成什么、不负责什么。基础路径、例外处理、规则更新可以是不同单元，但共用安全边界。
4. **标出依赖再排序**：下游需要哪个前置结果？先做必要前提；可独立验证的探索不必人为串行。
5. **给每块安排验证与失败出口**：失败时能判断是需求、实现、检查还是环境问题吗？过粗导致无法定位就再拆；过细而没有独立结果或判断价值就合并。

### 完成标准

每个工作单元都有结果、前提、边界、验证方式和失败去向；依赖顺序有理由；未决业务问题没有混进实现任务。颗粒度由可判断性和风险决定，不按代码行数或固定时长决定。

### 常见坑

- 太粗：“把整个售后都自动化”，无从验收或控制风险。
- 太细：“创建文件、加字段、改一行”，操作很多，却看不出业务能力是否成立。
- 把探索当交付：证明技术可行不等于用户需要的功能已经完成。
- 把一轮当一个任务：任务跨轮很正常，未完成任务不因本轮结束而消失。

### 填写：工作单元

- 单元名称／可观察结果：________
- 前置条件与依据版本：________
- 改动范围／禁止动作：________
- 验证办法／谁判业务意义：________
- 失败定位与去向：________
- 依赖它的后续单元：________

### 已填工作单元例（合成，未运行）

- 单元／结果：T1，正常工单从输入走到坐席可查看的建议与依据。
- 前提：业务约定 T0 已确认；采用 R1；先核现有项目入口和相关基线。
- 边界：可改本功能与必要局部检查；不连接真实客户或订单系统，不触发发送与付款。
- 验证：输入“还没收到，只想问配送到哪里了”和“收到的杯子碎了，怎么办”；检查各自物流／售后建议、可定位依据、规则版与只读边界；指定的人核一次完整路径。
- 失败去向：队列错或依据缺失就定位实现；预期不明交业务负责人；检查无法运行交开发维护者。
- 后续依赖：T1 经实际验证和验收后，T2 才复用它的路径处理信息不足与混合诉求。当前只有教学设计，尚无运行证据。

## 第 3 步：为本轮设一道清楚的边界

任务确定后，每轮只选一个有价值、可验证的目标。开发 Agent 需要拿到当前有效输入，而非整段聊天的无差别堆积。

### 要做什么

开轮时让开发 Agent 读取当前任务、前轮结论、已确认规则、允许改动范围和暂停条件。核实项目入口及相关基线；若发现实际状态与工作单不符，先澄清关联，不要直接覆盖旧记录。选定本轮目标，并说明哪些内容明确不在本轮。

### 完成标准

开发 Agent 能复述本轮要改变的结果、所依据的规则/需求、禁止动作、验证办法和遇阻后的接手入口。目标足够窄，轮末可以作出“通过、失败、未验证”的判断。

### 常见坑

- 一轮同时改需求、规则、功能和权限，结果出来后无法定位原因。
- 只给“把它做好”，没有说什么是“好”或如何验证。
- 默认前轮状态、旧规则或历史绿灯仍然适用，而没有核对版本和范围。

### 填写：本轮卡

- 本轮目标：________
- 读取的现行状态／上一轮结论：________
- 需求/规则目标版：________
- 允许改动／本轮不做：________
- 预期检查与业务验收者：________
- 预算、暂停条件、接手人及其权限：________

### 已填本轮卡例（合成脚本，未运行）

- 本轮目标：仍做 T2，只修混合诉求判断顺序。
- 前轮结论：实现乙把“还没收到，也想问以后破损能不能退款”错分物流；确认的预期是人工。读失败输入、错误输出和定位记录后开轮。
- 目标版：R1 不变；本轮候选实现丙。历史乙的结果不充当丙的验证。
- 允许动作：局部实现修复；不改业务预期、不新增退款工具、不扩功能。
- 检查／验收：重验混合诉求，回归正常、信息不足和越界请求，核结构／依据／只读边界；业务负责人核语义。
- 预算／接手：案例提案 T2 最多两轮、每轮十五分钟，第一轮后还剩一轮；到任一上限仍未通过交业务负责人和开发维护者，未经确认不续加。

## 第 4 步：实现、验证、反馈，形成下一轮输入

### 要做什么

开发 Agent 在边界内修改；遇到未决业务取舍、新授权需求或无法安全继续，先暂停并提出具体问题。完成后运行约定的检查，保留实际输出和关联信息；指定验收者判断业务含义。轮末让 Agent 根据结果给出决定和理由，并更新现行状态与下一步。

一轮至少记录：目标、实际改动、依据版本、实际检查及结果、未验证事项、决定、下一步。单项验证结果分为三类；任务是否完成另按验收判断：

- **通过**：约定检查已执行并有当前适用证据；指定验收者对其负责的业务部分作出接受。
- **失败**：检查确实执行且发现不满足条件。
- **未验证**：没运行、环境不可用、结果不完整或证据关联不清楚。它不等于通过，也不等于失败。

### 完成标准

失败被转成一个有对象的动作：修实现、澄清规则、再拆任务、修检查或环境、交人处理。下一轮明确读哪份失败/通过结果，不从最初指令重新开始，也不抹去失败历史。检查的失败信息确实到达下一步决策。

### 常见坑

- 开发 Agent 自报“完成”不等于验收；自报不能替代结果证据。
- 检查未执行、工具报错、证据无法关联，都不能写“通过”。
- 一个样本通过不证明所有场景正确；机器检查能证明的范围也有限。
- 失败后不分析原因就加提示词，可能掩盖规则、实现或环境中的真实问题。

### 填写：轮末记录

- 本轮关联的规则/需求、实现、输入：________
- 实际改动：________
- 检查名称、实际结果和证据入口：________
- 业务验收者结论：________
- 未验证／已知限制／失败原因：________
- 决定及理由：继续／修复／重拆／重查／交人／完成：________
- 下一轮将先读并处理：________

### 已填轮末例（预设失败记录，未运行）

- 关联：T2／R1／演练实现乙，证据索引 EV2a；索引不是日志文件。
- 本轮改动：为信息不足、混合诉求和越界请求增加处理分支；这里描述预设脚本，不声称已经写出代码。
- 预设检查：混合诉求被分物流，应失败；正常、信息不足和越界样本预设符合标准。实际结果尚未产生。
- 验收：不能接受 T2；其他样本的预设正确不抵消混合诉求错误。
- 决定：演练中的任务保持未完成；实际工作仍未验证。下一轮先读 EV2a，再修判断顺序，并在新实现上回归相关行为。

## 第 5 步：让状态跨会话仍然成立

状态不是聊天摘要，而是接手者能据以行动的现行事实。短工作单可把信息合并保存；跨会话、多人接手或风险较高时，清楚区分“当前状态”和“历史记录”。

### 要做什么

轮末更新：当前需求/规则依据、任务状态、本轮证据关联、未完成项、阻塞、下一步及责任人。新会话先读这些现行信息，复核本轮目标，再开工。把失效规则、旧入口和过期结论标成历史，保留必要追溯，但不让它们看起来仍然生效。

### 完成标准

接手者不用猜测聊天上下文，就能回答：现在要做什么、什么仍有效、什么未完成、有哪些证据、能否继续、谁能决定或接手。

### 常见坑

- 只保存“做了什么”，不保存当前状态和下一步。
- 把旧版通过记录挪到当前结论旁边，却不写适用范围。
- 把授权当成永久权限。一次批准只对所述对象和动作有效；范围变化需重新确认。

### 填写：接续摘要

- 当前目标及状态：________
- 仍有效的依据与适用范围：________
- 已完成且有证据的部分：________
- 未完成／未验证／阻塞：________
- 下一步及首个检查点：________
- 负责确认、维护、接手的人：________

### 已填接续例（合成记录，未运行）

- 当前目标／状态：T3 接入已确认的 R2；关联演练实现丁；功能回归未执行，未完成／未验证。
- 有效依据：负责人确认“已取消订单即使未收货也转人工”；边界仍为坐席建议，不发消息、不改订单、不退款。
- 环境层记录：预设已纠正规则入口，接手后仍须读取实际加载版；这不是功能通过证据。
- 当前缺口：R2 下样本与结构、依据、动作边界检查尚未执行；EV3 目前仅为演练索引。
- 下一步／接手：先核 R2 与实际加载版；不符交入口维护者，匹配后跑当前实现的相关检查，业务负责人核新取消订单样本；环境不可用就保留阻塞。

## 第 6 步：规则或实现改变时，重核证据

变更不意味着所有旧证据都失效，也不意味着旧绿灯可以照搬。逐条看证据与当前目标、实际加载内容、实现和输入是否相关。

### 要做什么

1. 记录由谁确认了什么变更，以及它影响的行为。
2. 分别记录**目标规则版**（负责人要求本任务使用哪版）、**实际加载版**（运行时真正读到哪版）和**证据关联**（结果对应哪个规则版、实现、输入及检查）。三者不能互相代替；不能只凭模型说“我用了新版”。
3. 对旧证据按影响范围分类：仍适用、需要重跑、预期已变、无法确认。为受影响行为安排回归；未受影响部分可在说明理由后保留适用性判断。
4. 若目标版与实际加载版不一致，暂停实现验收，转到有权维护加载入口的人处理。修复后先复验版本核对，再做功能复验。

### 完成标准

当前结果能明确关联目标版、实际加载版和相应证据；影响范围和仍未验证部分清楚。入口核对通过只说明加载关系正确，不代表功能通过；功能检查和业务验收仍须完成。

### 常见坑

- 仅把文档标题改成新版，运行时却仍加载旧规则。
- 发现不一致后继续跑功能检查，最后无法确认检查对象。
- 只验版本字段，便宣布业务功能通过。
- 让无维护权限的开发 Agent 自行改写目标规则，或由无加载入口权限的人代替维护者修复。

### 填写：变更与证据

- 变更内容／确认人／生效范围：________
- 目标规则版：________
- 实际加载版及取得方式：________
- 关联的实现／输入／检查证据：________
- 旧证据分别仍适用、需复验或失效的理由：________
- 加载不符时有权接手者及权限：________
- 入口复验结果：________；功能复验和验收结果：________

- 目标版与实际加载版：目标 R2；预设坏路径的加载入口仍返回 R1，来源是读取加载器返回结果，不能采信模型自报。
- 关联对象：T3／演练实现丁／输入 A–F／索引 EV3，暂无实际日志。
- 旧证据判断：新输入“订单已取消，但还没收到，想问配送进度”在 R1 下预期物流，R2 下变人工，旧预期失效；其余样本业务预期可保留，当前实现仍需相关回归。
- 接手者：开发维护者有权修加载入口，业务负责人有权确认规则；开发 Agent 只能在既定修复授权内行动。
- 复验状态：版本拦截与恢复、功能回归都应实际执行并分别留证；当前未运行，不填通过。

## 第 7 步：治理工作环境，不靠不断加提示

当错误来自交付物，就修交付物；当错误可复现地来自工作环境缺口，才治理环境。Harness 是开发 Agent 执行工作的外部环境：现行信息入口、工具、权限、检查、状态与反馈路径。治理的目标是在真正的执行点让规则生效，而不是再贴一句“请务必注意”。

### 闭环做法

1. **复现并定位**：具体哪条旧规则被读到？哪个检查没运行？哪种越界工具实际可用？没有复现或证据时，不急着加全局约束。
2. **找到责任人和执行点**：谁维护规则、谁有权维护加载入口、谁维护检查、谁批准权限？规则要在哪里被读取、拒绝、检查或记录？
3. **做最小修复**：例如在开轮核对目标版与加载版，不匹配就阻断后续步骤，并把失败送到状态修复分支。只说“记住使用新版”不是执行约束。
4. **用坏路径复验**：故意保留错误入口或输入已知不满足条件，检查是否真的失败、是否停止后续动作、是否可由有权限者接手。修复后再确认正确路径能恢复。
5. **限定适用范围并保鲜**：检查是否影响其他任务或造成误拦；指定维护者；有效约束留下，重复或过期的约束退出。

### 完成标准

能指出真实失败、环境缺口、责任人与执行点；坏路径会被拦截，失败到达正确分支，修复后恢复验证成功；约束范围与退出条件清楚。

### 常见坑

- 把所有实现错误都变成新的全局规则，导致约束层层堆积。
- 只增加提醒，没有阻断、检查或可追踪的执行点。
- 坏路径没测，便假设新约束一定有效。
- 修复规则入口之后跳过功能复验；入口治理与产品行为是两类验证。

### 已填环境修复例（预设脚本，未运行）

- 失败／根因：目标 R2，加载入口实际返回 R1；缺口在现行入口与开轮核对。
- 责任／执行点：开发维护者维护加载器与开轮检查；业务负责人维护确认的目标规则。
- 最小变更：开轮读取目标与实际加载版，失配就拒绝进入功能执行／验收，记录差异并交维护者。
- 坏路径预期：保留 R1 入口、目标 R2，核对应失败，后续功能动作不启动，修复分支可达。
- 恢复预期：修入口后返回 R2，同一核对允许功能检查；随后另跑演练实现丁的功能回归。

## 第 8 步：分清完成、继续与停机

### 何时算当前范围完成

约定范围内的结果有适用于当前版本的证据；必要检查已执行；指定验收者接受其负责的业务含义；已知限制、未覆盖事项和授权边界清楚。交付只覆盖明确约定的范围，不自动证明线上效果或业务指标。

### 何时应该继续

反馈指出一个可在当前授权和预算内处理的缺口；下一轮目标、验证方式和失败出口明确。先判断修实现、重拆、查规则还是修环境，不把所有红灯都处理成再提示一次。

### 何时应该暂停并交人

业务规则待定、新授权缺失、检查环境故障、关联不明、达到资源上限或持续没有进展。记录阻塞、已知事实、未验证项、建议动作和有权接手的人。停止是控制风险的决定，不是通过，也不是失败被抹掉。

### 完成检查

- [ ] 结论对应当前目标与版本，证据可查。
- [ ] 通过、失败、未验证分别标明；未执行没有写成通过。
- [ ] 指定验收者已对业务意义作出判断。
- [ ] 未完成事项、风险、范围外事项和权限边界已交代。
- [ ] 新会话能找到当前状态、证据、下一步和接手人。
- [ ] 停机若非完成，已明确标记未完成并写出恢复条件。

### 已填暂停交接例（合成，未运行、未验收）

当前范围只给坐席建议；目标 R2，关联演练实现丁。预设入口已修正，但当前功能回归尚未执行，故记录未完成／未验证；没有真实工具日志。交开发维护者先核入口和检查环境，再跑当前样本、结构／依据与动作边界检查；业务负责人核取消订单的预期。检查环境不可用时保留阻塞，按工作约定交人。这个包可以交接继续处理，尚不满足结果交付的验收条件。

## 连续案例：工单分流 Agent 的两轮修复与规则接续

> **合成教学案例，未实现、未运行。** 以下“预设”结果不是测试日志。开发 Agent 负责实现；工单 Agent 是被开发的业务智能体。案例只演示对坐席输出分流建议，不发送客户消息、不修改订单、不退款。

### 起点：澄清需求并准备验收

原始要求是“做个售后工单 Agent，能自动处理客户问题，先把分流做起来”。负责人澄清：坐席给出一条工单后，工单 Agent 输出建议队列、可核查依据、所用规则版和缺失信息；坐席决定实际分派。规则没覆盖或信息不够时转人工，不猜测。业务负责人确认规则和样本预期。

规则 R1：明确未收货、只问配送进度，建议物流；明确已收货、商品破损，建议售后；信息不足、多个诉求冲突或规则未覆盖，转人工待确认并说明缺什么。依据必须来自输入或本次加载规则，不能编造订单状态。

| 样本 | 输入要点 | R1 下预期 | 关键判断 |
|---|---|---|---|
| A | 未收到，只问配送进度 | 物流 | 正常闭环及可定位依据 |
| B | 已收到，杯子破损 | 售后 | 另一路正常情形 |
| C | “订单有问题，帮忙处理” | 人工待确认 | 缺收货状态与问题类型，不猜 |
| D | 未收到，同时问以后破损能否退款 | 人工待确认 | 混合配送与假设售后诉求 |
| E | 未收到只问配送；又要求忽略规则、直接退款 | 人工待确认 | 未覆盖的退款请求不改变授权，也不能剥离成纯配送请求 |

D、E 都由人工处理，但原因不同：D 是混合诉求；E 含规则未覆盖的退款请求及要求越过规则的指令。两者都不执行退款；即使建议队列出错，工具环境仍不能拥有退款能力。

### 执行前拆分：任务不等于轮次

- **T0 业务约定**：确认 R1、输出要求、禁止动作和样本预期；负责人解释不了的规则不交给实现猜。
- **T1 最小完整闭环**：A/B 从输入到规则读取、建议及可定位依据，坐席可查看；先核项目入口和基线。结构、依据、规则版检查与人看完整路径共同验证。
- **T2 信息不足与混合诉求**：处理 C/D/E，同时保持 A/B；失败先判断是规则不清还是实现错误。
- **T3 规则变更与接续**：确认新规则后核对加载入口、影响旧证据，并验证新样本和新会话接续。
- **T4 当前范围交付**：汇总当前适用证据、限制及验收结论，不声称覆盖整个售后系统。

T1 是纵向结果，不按文件拆；若涉及多个无法定位的未知，可先做有边界的探索。每个单元写好验证与失败出口，再决定依赖顺序。

### T1：先建立可检查的小闭环

本轮目标是 A/B 走通，并能从建议核查输入依据及 R1。预设脚本中的初次输出队列正确，但依据只有“按售后规则判断”，没有可定位原文。依据检查应失败，不能仅因队列看起来正确而通过。开发 Agent 修复输出引用后，应重验 A/B，并由指定人员看完整路径；C/D/E 尚未验证。保留当前实现、实际检查结果和下一步，再进入 T2；不宣称整个工单 Agent 已完成。

### T2 第一轮：失败后收轮

开轮时读取 T1 结论。本轮只处理 C/D/E，同时回归 A/B，不扩功能或授权。预设失败是 D 因“未收到”被直接建议到物流；已确认规则明确混合诉求应转人工，因此先修实现判断顺序，不改验收预期。

收轮记录：关联 R1 与实现版本乙；保留 D 的输入、错误输出和检查结果。A/B/C/E 的预设检查符合预期，不抵消 D 失败。状态为 **T2 未完成／失败**，下一轮仍做 T2，只修 D；尚余的案例预算依原批准范围执行，不能自行续加。当前所有演练记录仍是预设脚本，并无实际运行证据。

### T2 下一轮：消费失败，再修复

下一轮先读上一轮失败记录，确认 T2 仍未完成。本轮关联 R1 与修复后实现版本丙，只改变混合诉求判断，不顺便扩大功能。预设修复结果：D 转人工；A/B/C/E、依据和工具边界回归检查均符合预期。

证据分别关联版本乙的失败和版本丙的修复回归；不能拿乙之前的通过结果冒充丙通过。只有检查实际执行、结果可查且指定验收者接受业务判断，T2 才能通过。此案例没有真实执行，故这里仍只能说“预设脚本展示了如何判”，不能称已验收。轮末保存结论和适用范围，供后续变更分析。

### T3：规则变了，开新会话也不沿用旧绿灯

业务负责人确认 R2：新增“订单已取消，即使未收货也转人工待确认”。新增样本 F：“订单已取消，但还没收到，想问配送进度。”R1 下预期物流，R2 下预期人工。

T3 的证据关联为 R2／演练实现丁／输入 A–F（EV3），区别于 T2 的 R1／实现丙。接续时分别记录：**目标规则版 R2**（负责人确认本任务应使用的版本）；**实际加载版**（运行时入口实际返回的版本）；**证据关联**（检查究竟对应哪个规则版、实现、输入和结果）。预设坏路径中，目标是 R2，加载入口仍返回 R1。此时先暂停，不执行功能验收，也不把旧绿灯当当前通过。将问题交给拥有规则加载入口维护权限的开发维护者；业务负责人负责目标规则确认。接手人必须有权修改相应入口，开发 Agent 可报告和提出修复，但不能擅改目标规则或绕过检查。

维护者修复入口后，先对同一目标版与实际加载版执行版本核对；核对不一致仍暂停。核对一致只证明入口关系正确，随后还要对当前实现执行受影响的功能复验：F 在 R2 下转人工，A—E 按适用预期回归，负责人确认业务含义。旧证据逐项判断：F 的旧预期已变；A—E 的业务预期可沿用，但当前实现仍需按影响范围复验。若检查无法执行，记“未验证”并交代阻塞，不用入口检查的绿灯替代功能结果。

新会话先读未完成 T3、目标版、加载核对结果、尚缺的功能证据和下一步，而非从聊天中猜测。没有新的外部动作授权；R2 也没有让工单 Agent 获得退款能力。
