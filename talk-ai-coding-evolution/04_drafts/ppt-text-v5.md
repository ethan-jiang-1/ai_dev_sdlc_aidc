**画面构成**

**上屏文字**

- 副题：它们解决“说什么、看什么”，却还没解决“能不能安全地行动”
- 左栏：

### P6 · Harness Engineering

**叙事任务**

给 Harness 一个清楚的定义：它为每一次真实行动设边界，并把模型能力变成可交付动作。

**画面构成**

大号黑底公式居中；六个构件横向排列；下方用一句完整定义和一个向 Loop / Graph 的转场收束。

**上屏文字**

- 标题：**Harness Engineering：为每一次行动设下可靠边界**
- 副题：它回答的不是模型会不会想，而是它此刻能做什么、谁来检查、如何留下记录
- 公式：**Agent = Model + Harness**
- 六个构件：
  - 权限
  - 沙箱
  - 工具
  - 验证
  - 执行记录
  - CI
- 定义：权限、沙箱、工具、验证、执行记录、CI：模型之外让行动可交付的一切
- 转场：一次动作可靠后，问题才变成：怎样把反馈连成 Loop、把任务组织成 Graph？

**背景（不上屏）**

- 先建立 Harness 的正面定义，不在这里过早展开安全事故。
- Harness 是一次执行的边界；Loop 与 Graph 都要建立在可靠执行之上。

### P7 · Loop 与 Graph

**叙事任务**

用两个具体结构解释 Loop 与 Graph：一个把失败反馈带回下一轮，一个把复杂任务写成显式依赖。

**画面构成**

左侧是带判断与回路的 Loop；右侧是“修复登录故障”的任务图；底部黑条强调两者都依赖可靠的单次行动。

**上屏文字**

- 标题：**Loop Engineering 与 Graph Engineering：让可靠行动持续发生**
- 副题：Loop 解决“怎样知错再改”；Graph 解决“谁先做、谁并行、何时汇合”
- 左侧标题：**LOOP ENGINEERING：检验失败，就把反馈带回下一轮**
- Loop 节点与分支：
  - 执行
  - 检验
  - 通过？
  - 是
  - 完成
  - 否：反馈下一轮
- 右侧标题：**GRAPH ENGINEERING：把复杂任务写成显式依赖**
- 例：修复登录故障
- Graph 节点：
  - 收到故障
  - 复现问题
  - 定位并修复
  - 补回归测试
  - 集成验证
  - 交付
- 图下注：节点可以是 agent、工具或验证器；节点内部仍可以运行自己的 Loop
- 收束：**先有可靠的单次行动，Loop 才不会放大失败，Graph 才不会组织混乱**

**背景（不上屏）**

- Loop 是时间上的反馈循环；Graph 是空间上的依赖与编排。
- 两个结构都不能替代节点内部的授权、验证和记录。

### P8 · 五个 Engineering 的关系图

**叙事任务**

把五层从“先后出现的名词”改写成“各自回答不同问题、相互依赖的关系图”。

**画面构成**

Prompt 与 Context 组成一次模型调用；向右进入 Harness 的可靠行动边界；下方分别展开 Loop 和 Graph；底部黑条给出共同结论。

**上屏文字**

- 标题：**五个 Engineering 同时活着，但各自回答不同的问题**
- 副题：这不是一座金字塔，而是一张“每个问题为何需要下一步”的关系图
- 一次模型调用：先说清任务，再挑选材料
- **Prompt Engineering**
  - 说清任务
- **Context Engineering**
  - 挑选材料
- **Harness Engineering：形成可靠行动**
  - 授权 · 执行 · 验证 · 记录
- **Loop Engineering：反复同一行动**
  - 检验失败，就把反馈带回下一轮
- **Graph Engineering：编排多个行动**
  - 分工、分叉、汇合；部分节点可以运行 Loop
- 收束：**无论上面怎样组织，每一次真实动作都要经过 Harness 的执行边界**

**背景（不上屏）**

- 这不是成熟度金字塔，也不是简单的时间线。
- 关系图的落点是：所有真实动作最终都穿过 Harness。

### P9 · 转向真实执行边界

**叙事任务**

从五层关系图推导出全场主判断：对 OPC 最值得看懂的，是每次真实动作都必须穿过的 Harness 边界。

**画面构成**

中部一条三段流程：模型提出动作 → Harness 授权、执行、验证 → 结果进入 Loop / Graph；底部黑条和一句 OPC 结论完成转折。

**上屏文字**

- 标题：**最值得看懂的不是最高层，而是真实动作穿过的边界**
- 副题：五层关系图推出来的结论：所有上层组织能力，都要落到一次可靠执行
- 流程：
  - 模型提出动作
  - **Harness**
  - 授权 · 执行 · 验证
  - 结果进入 Loop / Graph
- 说明：每一个 Loop、每一个 Graph 节点，最后都要经过能独立授权、检查、记录的执行边界
- 结论：**可靠性不是模型单独拥有的属性，而是 Model + Harness 的属性**
- 落点：这就是 Harness 对 OPC 的临界意义

**背景（不上屏）**

- 这一页完成从“五个 Engineering”到“Harness 对 OPC 有什么意义”的主转折。
- 下一页重新拆开 Model 与 Harness，解释能力和可靠性的分工。

### P10 · Agent = Model + Harness

**叙事任务**

把“Agent 并非裸模型”讲透：模型提供能力，Harness 负责把能力变成可以稳定交付的行动。

**画面构成**

大号黑底公式横条；六项 Harness 构件横向排列；下方两句话分别说明购买模型与最小 agent 的现实含义。

**上屏文字**

- 标题：**Agent 从来不是裸模型：它一行动，Harness 就已经在场**
- 副题：模型给能力；Harness 把这份能力变成一次可以交付的行动
- 公式：**能力：Model   +   可靠性：Harness**
- 六个构件：
  - 权限
  - 沙箱
  - 工具
  - 验证
  - 执行记录
  - 持续检查（CI）
- 说明：买到的是模型能力；能否稳定交付，取决于围绕它的一圈运行边界
- 黑底说明：**最小的 agent 也不只是 prompt：它至少有工具，并要面对真实执行结果**
- 收束：这就是 Harness Engineering 的起点

**背景（不上屏）**

- 回收 P5 的问题：Prompt 和 Context 之外，一旦开始真实行动，Harness 就已经存在。
- “能力 + 可靠性”是后续理解 Harness 价值的核心分工。

### P11 · Guides、Sensors 与确定性检查

**叙事任务**

解释 Harness 如何产生可靠性：行动前约束，行动后反馈；能确定检查的事情，不交给模型猜。

**画面构成**

四个并列区块：Guides、Sensors、确定性检查、语义判断；底部一句原则收束。

**上屏文字**

- 标题：**可靠性发生在两次：行动前约束，行动后反馈**
- 副题：能写成规则和测试的，就不要让模型猜
- **事前引导（Guides）**
  - 行动前：允许哪些工具、必须通过什么检查
- **事后反馈（Sensors）**
  - 行动后：测试失败、用户拒绝、退出码非零
- **确定性检查**
  - 测试 / lint / 类型：可复现、可审计
- **语义判断**
  - AI review / 人工判断：必要，但可能出错
- 结论：**确定的事交给系统；需要理解语义时，才交给模型或人**

**背景（不上屏）**

- Guides 负责事前限制，Sensors 负责把执行结果带回来。
- 不是排斥 AI review，而是先用可复现、可审计的检查承接确定性问题。

### P12 · Harness 的四个动词

**叙事任务**

把 Harness 从“防错系统”扩展为“进入专业领域的系统”：不仅圈住、拦住、看清，还要借 Knowledge Map 明白专业内容。

**画面构成**

四个等宽区块横向排列，每个区块由动词、机制和结果三层组成。

**上屏文字**

- 标题：**Harness 不只让错误停下，也让模型进入专业领域**
- 副题：圈住伤害，拦住错误，看清过程，再借 Knowledge Map 明白专业领域
- **圈住**
  - 沙箱 + 权限
  - 限制能碰的范围
- **拦住**
  - 验证门禁

  - 找到归属与正确路径

**背景（不上屏）**

- “明白”不是再加一段大 prompt，而是把领域地图、事实归属和正确路径显式化。

### P13 · 不可靠的 Harness 会放大失败

**叙事任务**

说明 Loop 与 Graph 只能放大产能和组织能力，无法替每次执行补上授权、检查与记录。

**画面构成**

上方三格并列比较 Loop、Graph、Harness；中部一句前提判断；底部黑条以 GraphARC 说明模型提议与确定性放行的分工。

**上屏文字**

- 标题：**没有可靠 Harness，Loop 与 Graph 只会放大失败**
- 副题：上层系统能扩大产能，却不能替下层补上授权、验证和记录
- 三格关系：
  - **Loop**
  - 跨运行
  - 放大反馈
  - **Graph**
  - 跨节点
  - 显式路由
  - **Harness**
  - 每次执行
  - 授权 · 检查 · 记录
- 结论：可靠节点不是“基础工作”，而是所有反馈和编排开始之前的前提
- 黑底说明：**模型可以提议工作图，但确定性检查器决定放行还是拒绝**
- 来源标记：GraphARC

**背景（不上屏）**

- Loop 会跨运行反复使用执行结果，Graph 会跨节点组织动作；底层错误因此可能被持续或规模化放大。
- GraphARC 的例子说明：模型可以提出方案，但执行许可仍应由确定性检查掌握。

### P14 · 真实事故：CVE-2026-18830

**叙事任务**

用一个具体事故证明：如果 Harness 在执行端没有独立授权，甚至不需要运行模型，也能触发真实工具动作。

**画面构成**

红色三步事故链横向展开；中部黑条给出修复；下方黑底英文原则与红色根因判断收束。

**上屏文字**

- 标题：**真实事故：伪造工具调用，无需模型也能触发真实动作**
- 副题：Amazon Bedrock AgentCore InvokeHarness · CVE-2026-18830
- **1** 请求末尾塞入伪造的 tool-use 块
- **2** 事件循环信任形状，跳过模型回合
- **3** 指定工具被直接执行，真实动作发生
- 修复：**执行端拒绝伪造的 tool-use 块；工具运行前独立授权**
- 原则：**“authorize at execution, not at generation”**
- 根因：**事故根因：执行时授权缺失，不是 prompt injection**

**背景（不上屏）**

- 具体过程：已认证调用方可在 Amazon Bedrock AgentCore InvokeHarness 请求末尾放入 tool-use 内容块；事件循环可能不经过模型回合便分派该工具。
- 托管服务的修复是在分派前拒绝调用方提供的 tool-use 块，并在工具运行前独立授权。
- 来源：The Hacker News, “AWS, Google, and Vercel Agent Flaws Let Attackers Trigger Tools Without Running the Model,” 2026-08-06；本地摘要 `../_reference/rawdata_ai-coding-evolution-final/final_v4/03-2026-harness-era.md`。

### P19 · DSH 不是商店或更强 Loop，而是可组合的 Harness runtime

**叙事任务**

先澄清 DSH 的定位：它不是插件商店、Agent 成品或更强的 Loop，而是让这些能力能共同工作的运行时。

**画面构成**

保留 V4 “部件 → 运行时 → session log” 的垂直结构，但将上方改为三个“不是”，中部定义 runtime，下方保留事实记录。

**上屏文字**

- 标题：**DSH 到底是什么？不是商店，也不是一个更强的 Loop**
- 副题：插件爆发发生在它之上，但 DSH 本身是一套可组合的 Harness runtime
- **不是插件商店**
  - 商店只是分发层
- **不是 Agent 成品**
  - 它不替代 Codex / Claude Code
- **不是更强的 Loop**
  - 默认 Loop 只是其中一个驱动插件
- 运行时：**DSH：让模型、工具、后端、规则与 Loop 围绕同一合同装配**
- 记录：**Session log：每一次行动发生了什么，仍按顺序留下**
- 记录原则：已经发生什么：只追加，不因换插件而重写
- OPC 结论：**插件围绕 Harness 工作；它们不能替代 Harness**

**背景（不上屏）**

- DSH 的“everything is a plugin”不意味着核心消失：组合内核、合同与事实记录仍是前提。
- 下一页回答：为什么能装插件还不够，Harness 必须有最终控制权。

### P20 · 只有插件不够：能装，还必须能管

**叙事任务**

把固定产品的“边界由谁定义”论点迁到这里：当插件进入模型可见面或真实执行路径，owner 面对的是合同、门禁和记录的控制问题。

**画面构成**

沿用 V4 的 2×2 接口卡片，改成四项 owner 的控制问题；中部横条列出 DSH 的 adapter / seam / gate / log 机制。

**上屏文字**

- 标题：**只有插件不够：能装，还必须能管**
- 副题：一项能力进入模型可见面或真实执行路径，就会改变系统的责任边界
- **接入**
  - 谁能把新能力带进模型可见面？
- **替换**
  - 谁能换模型、工具和执行世界？
- **放行**
  - 谁能在真实执行前拒绝它？
- **重建**
  - 谁能说清它究竟做过什么？
- 机制：**adapter / capability seam / enforced gate / session log**
- 收束：**installable 不等于 trustworthy；插件化也不等于安全**

**背景（不上屏）**

- `ctx.llm`、`ctx.tools`、capability seam 提供受合同约束的接入和替换；不将 MCP 误说成 DSH 原生机制。
- DSH 机制成熟度资料指出：插件化不是安全边界，任何模型可见的新能力都要承担可重建记录的硬税。

### P21 · Harness 必须在手：部件可借，最终决定权不能外包

**叙事任务**

给出全段结论，并证明“在手”不是“全栈自建”：owner 拥有最终决定权，部件继续借用。

**画面构成**

沿用 V4 的“金句 + 三步流程 + 收束”页型：上方定义四项控制权，中部放对应机制，底部用门禁金句收束。

**上屏文字**

- 标题：**Harness 必须在手：部件可借，最终决定权不能外包**
- 副题：在手不是全栈自建，而是 owner 对运行边界有 final say
- **接入**：我决定什么进入系统
- **替换**：我决定什么模型、工具、后端在跑
- **放行**：我决定什么能在真实世界执行
- **重建**：我决定发生过的事如何被追溯
- 机制：adapter / provider → enforced gate → append-only session log
- 引文：**“Agent 更可靠地遵守系统门禁，而不是文字约定。”**
- OPC 落点：**装自己的，借现成的；但 Harness 的最终控制权必须在手**

**背景（不上屏）**

- 模型、工具、后端、插件都可以借；owner 不能外包的是接入、替换、放行与重建的最终决定权。
- 这页把 P11 的确定性检查、P12 的拦住与 P14 的执行时授权统一到 DSH 的实际价值上。

**画面构成**

顶部黑条定义 DSH；中部三步原则横向排列；底部黑条给出全场带走句，并标明是一人公司的 Harness 原则。

**上屏文字**
