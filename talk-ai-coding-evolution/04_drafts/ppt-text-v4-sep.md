## P2 · 五个 Engineering 先完整出场

- 标题：**AI Coding 的五个 Engineering，先看全貌**
- 副题：它们不是新词清单，而是模型变强后，人要解决的问题不断上移
- **Prompt Engineering**：说什么？
- **Context Engineering**：看什么？
- **Harness Engineering**：在哪行动？
- **Loop Engineering**：何时重试？
- **Graph Engineering**：如何编排？
- 黑底结论：**说清任务  →  让动作可靠  →  把工作组织起来**
- 收束：模型越强，人的动作越从亲手做，变成设计它怎样做

> **背景（不上屏）**
>
> 先完整呈现五个听众熟悉的术语，再解释它们共同构成一张工程关注点上移的地图。

## P4 · 同一台发动机

- 标题：**模型越强，工程对象越从一句话往系统上移**
- 副题：五个 Engineering 由同一台发动机推动：模型变强，手工动作就得上移
- 数据：**50%** / 可靠性任务长度 / 约每 7 个月翻倍
- 来源标记：METR · 独立评估
- 因果链：模型能力更强 → 单次措辞优化收益递减 → 工程杠杆向上移
- 演进：写清一次任务  →  设计一次行动  →  设计一套系统怎样工作
- 引文：**“prompt 的精确措辞，越来越不重要”**
- 署名：Anthropic
- 收束：**不是替代，是叠加：旧问题仍在，新问题继续往上长**

> **背景（不上屏）**
>
> 模型能力增强使一次措辞优化的边际收益递减，工程杠杆随之上移；强调叠加，不暗示旧层被替代。

## P5 · Prompt 与 Context

- 标题：**Prompt Engineering 与 Context Engineering：先说清，再看对**
- 副题：它们解决“说什么、看什么”，却还没解决“能不能安全地行动”
- **Prompt Engineering**
  - 说清任务、约束和格式
  - 局限：文字不能代替系统控制
- **Context Engineering**
  - 挑出此刻需要的事实和状态
  - 局限：材料越多，关键内容越容易被淹没
- 转折：**说对、看对之后，下一问是：它究竟能在什么边界里行动？**
- 引出：这正是 Harness Engineering 出场的原因

> **背景（不上屏）**
>
> Prompt 和 Context 处理信息，却不提供真实执行环境、授权或验证；因此自然引出 Harness。

---

## P6 · Harness Engineering

- 标题：**Harness Engineering：为每一次行动设下可靠边界**
- 副题：它回答的不是模型会不会想，而是它此刻能做什么、谁来检查、如何留下记录
- 公式：**Agent = Model + Harness**
- 六个构件：权限 / 沙箱 / 工具 / 验证 / 执行记录 / CI
- 定义：权限、沙箱、工具、验证、执行记录、CI：模型之外让行动可交付的一切
- 转场：一次动作可靠后，问题才变成：怎样把反馈连成 Loop、把任务组织成 Graph？

> **背景（不上屏）**
>
> Harness 是一次真实执行的可靠边界。先建立正面定义，再进入 Loop 与 Graph。

---

## P7 · Loop 与 Graph

- 标题：**Loop Engineering 与 Graph Engineering：让可靠行动持续发生**
- 副题：Loop 解决“怎样知错再改”；Graph 解决“谁先做、谁并行、何时汇合”
- **LOOP ENGINEERING：检验失败，就把反馈带回下一轮**
  - 执行 → 检验 → 通过？
  - 是 → 完成
  - 否：反馈下一轮
- **GRAPH ENGINEERING：把复杂任务写成显式依赖**
  - 例：修复登录故障
  - 收到故障 → 复现问题 → 定位并修复 / 补回归测试 → 集成验证 → 交付
  - 节点可以是 agent、工具或验证器；节点内部仍可以运行自己的 Loop
- 收束：**先有可靠的单次行动，Loop 才不会放大失败，Graph 才不会组织混乱**

> **背景（不上屏）**
>
> Loop 是时间上的反馈循环，Graph 是空间上的显式依赖；两者都依赖节点内部的 Harness。

---

## P8 · 五个 Engineering 的关系图

- 标题：**五个 Engineering 同时活着，但各自回答不同的问题**
- 副题：这不是一座金字塔，而是一张“每个问题为何需要下一步”的关系图
- 一次模型调用：先说清任务，再挑选材料
- **Prompt Engineering**：说清任务
- **Context Engineering**：挑选材料
- **Harness Engineering：形成可靠行动**：授权 · 执行 · 验证 · 记录
- **Loop Engineering：反复同一行动**：检验失败，就把反馈带回下一轮
- **Graph Engineering：编排多个行动**：分工、分叉、汇合；部分节点可以运行 Loop
- 收束：**无论上面怎样组织，每一次真实动作都要经过 Harness 的执行边界**

> **背景（不上屏）**
>
> 五层是问题关系图，不是时间线或金字塔；所有真实动作最终穿过 Harness。

## P9 · 真实动作穿过的边界

- 标题：**最值得看懂的不是最高层，而是真实动作穿过的边界**
- 副题：五层关系图推出来的结论：所有上层组织能力，都要落到一次可靠执行
- 流程：模型提出动作 → **Harness：授权 · 执行 · 验证** → 结果进入 Loop / Graph
- 说明：每一个 Loop、每一个 Graph 节点，最后都要经过能独立授权、检查、记录的执行边界
- 结论：**可靠性不是模型单独拥有的属性，而是 Model + Harness 的属性**
- 落点：这就是 Harness 对 OPC 的临界意义

> **背景（不上屏）**
>
> 从五层地图转向 OPC：最值得掌握的是每一次真实动作都要穿过的执行边界。

---

## P10 · Agent = Model + Harness

- 标题：**Agent 从来不是裸模型：它一行动，Harness 就已经在场**
- 副题：模型给能力；Harness 把这份能力变成一次可以交付的行动
- 公式：**能力：Model   +   可靠性：Harness**
- 六个构件：权限 / 沙箱 / 工具 / 验证 / 执行记录 / 持续检查（CI）
- 说明：买到的是模型能力；能否稳定交付，取决于围绕它的一圈运行边界
- 黑底说明：**最小的 agent 也不只是 prompt：它至少有工具，并要面对真实执行结果**
- 收束：这就是 Harness Engineering 的起点

> **背景（不上屏）**
>
> 一旦 agent 开始调用工具并处理执行结果，Harness 就已经在场；模型给能力，周围的运行边界给可靠性。

---

## P11 · Guides、Sensors 与确定性检查

- 标题：**可靠性发生在两次：行动前约束，行动后反馈**
- 副题：能写成规则和测试的，就不要让模型猜
- **事前引导（Guides）**：行动前：允许哪些工具、必须通过什么检查
- **事后反馈（Sensors）**：行动后：测试失败、用户拒绝、退出码非零
- **确定性检查**：测试 / lint / 类型：可复现、可审计
- **语义判断**：AI review / 人工判断：必要，但可能出错
- 结论：**确定的事交给系统；需要理解语义时，才交给模型或人**

> **背景（不上屏）**
>
> Harness 通过事前约束和事后反馈产生可靠性；确定性问题优先交给可复现、可审计的系统检查。

---

## P12 · Harness 的四个动词

- 标题：**Harness 不只让错误停下，也让模型进入专业领域**
- 副题：圈住伤害，拦住错误，看清过程，再借 Knowledge Map 明白专业领域
- **圈住**：沙箱 + 权限 / 限制能碰的范围
- **拦住**：验证门禁 / 错误一出现就停止
- **看清**：Trace + 来源记录 / 还原每一步
- **明白**：Knowledge Map / 探索专业内容 / 找到归属与正确路径

> **背景（不上屏）**
>
> Knowledge Map 把领域地图、事实归属和正确路径显式化，使能力更强的模型能更有效探索 OPC 的专业领域内容。

## P13 · 不可靠的 Harness 会放大失败

- 标题：**没有可靠 Harness，Loop 与 Graph 只会放大失败**
- 副题：上层系统能扩大产能，却不能替下层补上授权、验证和记录
- **Loop**：跨运行 / 放大反馈
- **Graph**：跨节点 / 显式路由
- **Harness**：每次执行 / 授权 · 检查 · 记录
- 结论：可靠节点不是“基础工作”，而是所有反馈和编排开始之前的前提
- 黑底说明：**模型可以提议工作图，但确定性检查器决定放行还是拒绝**
- 来源标记：GraphARC

> **背景（不上屏）**
>
> Loop 和 Graph 会扩大产能与组织能力，也会扩大底层错误；模型可以提议方案，执行许可仍应由确定性检查掌握。

## P14 · 真实事故：CVE-2026-18830

- 标题：**真实事故：伪造工具调用，无需模型也能触发真实动作**
- 副题：Amazon Bedrock AgentCore InvokeHarness · CVE-2026-18830
- **1** 请求末尾塞入伪造的 tool-use 块
- **2** 事件循环信任形状，跳过模型回合
- **3** 指定工具被直接执行，真实动作发生
- 修复：**执行端拒绝伪造的 tool-use 块；工具运行前独立授权**
- 原则：**“authorize at execution, not at generation”**
- 根因：**事故根因：执行时授权缺失，不是 prompt injection**

> **背景（不上屏）**
>
> 已认证调用方可在 InvokeHarness 请求末尾放入 tool-use 内容块，使事件循环不经过模型便分派工具。修复是在分派前拒绝该块并独立授权。来源：The Hacker News，2026-08-06；本地研究摘要 `../_reference/rawdata_ai-coding-evolution-final/final_v4/03-2026-harness-era.md`。

## P15 · OPC 的真实痛点

- 标题：**回到 OPC：你是否已经被工具切换和知识分散拖慢？**
- 副题：工具越多、切换越频繁，知识与实践越散，协作成本就越像经营问题

> **背景（不上屏）**
>
> 在谈灵活 Harness 前，先判断工具切换与知识分散是否已成为每日交付摩擦；尚未发生就继续借现成。

## P16 · 现成 Harness 已经很强

- 标题：**Codex、Claude Code 已经很强：大多数 OPC 应直接借用**
- 副题：成熟 Harness 已把模型变成能工作的产品，而不只是一个会生成代码的模型
- **它们已经替你做好**
  - 工具调用与上下文
  - 沙箱、权限与执行记录
  - 验证与持续检查
- **所以，默认选择应该是**
  - 直接借现成 Harness
  - 把稀缺注意力留给业务
- 问题：**问题不是它们够不够强，而是业务要改变它们的边界时怎么办？**
- 引文：Anthropic · Start with the simplest viable system.
- 转折：真正的转折从这里开始：边界是不是已经变成业务的一部分？

> **背景（不上屏）**
>
> 先公平肯定成熟 Harness；DSH 的出现不是因为 Codex、Claude Code 不够强，而是某些业务需要改变它们的边界。

## P17 · 产品定义的边界

- 标题：**现成 Harness 很强，但它的边界由产品定义**
- 副题：只有业务差异化越过公开接入口，新的问题才出现
- **1 换模型 / 接内部工具**：产品没有对应接入口
- **2 换执行世界**：进入专用沙箱或集群
- **3 把项目规则变成门禁**：错误必须在执行前被拦住
- **4 改变执行链控制点**：工具运行前再次独立授权
- 结论：**这时要改的不是一句 prompt，而是 Harness 的运行合同**

> **背景（不上屏）**
>
> 只有公开接入口承载不了业务差异时，配置问题才升级为 Harness 运行合同问题。

## P18 · 可组合 Harness 的需要

- 标题：**新的问题：能不能既借现成，又拥有改变边界的能力？**
- 副题：OPC 需要的不是从零造框架，而是一个可组合的 Harness
- **保留现成的成熟**
  - 模型 adapter
  - 工具与技能
  - 已经验证过的部件
- **+**
- **装入自己的差异**
  - 内部模型与工具
  - 执行后端
  - 知识与可执行门禁
- 落点：**这就是 DeepSeek Harness（DSH）被需要的原因**

> **背景（不上屏）**
>
> 现成已经很好，但边界由产品定义；当 OPC 必须改变边界时，需要的不是从零造框架，而是可组合 Harness。

## P19 · DeepSeek Harness（DSH）

- 标题：**DeepSeek Harness（DSH）：把改变边界变成“换部件”**
- 副题：它不是替代 Codex / Claude Code，而是在边界必须可控时提供另一种选择
- 当前装着什么：可以替换
- 可替换部件：模型 adapter；工具 / 门禁；能力后端；默认 Loop
- 运行时：**DSH 运行时：把可替换能力按合同装进来**
- 记录：**Session log：每一次行动发生了什么，仍按顺序留下**
- 记录原则：已经发生什么：只追加，不因换插件而重写
- OPC 结论：**对 OPC：成熟的继续借，差异化的装进去**

> **背景（不上屏）**
>
> DSH 是可组合 Harness，不替代 Loop 或 Graph；能力可以替换，已经发生的 Session log 仍保持只追加。

---

## P20 · DSH 的组合接口

- 标题：**DSH 的组合方式：每一种变化都有明确接入口**
- 副题：可组合，不是随便改代码；是自己的能接入，现成的能复用
- **模型 → adapter**：把不同模型协议 / 转换成统一接口
- **工具 → tools registry**：登记后自动进入 / 模型可见的工具清单
- **后端 → capability seam**：调用方式不变 / 只换背后的实现
- **本次组合 → profile / plugin**：决定这次启动 / 实际装入什么
- 对照：**装自己的：接入新的 adapter / provider       借现成的：复用兼容实现**
- 收束：**加模型、加工具、换后端，都不必重写默认 Loop**

> **背景（不上屏）**
>
> “可组合”意味着每种变化都有明确接口；本页不把 MCP 作为 DSH 机制。

---

## P21 · 把文字规则变成执行门禁

- 标题：**DSH 的另一层价值：把“写给人看的规则”变成真实执行门禁**
- 副题：文档指出正确道路；门禁负责在真实路径上阻止错误
- 引文：**“Agent 更可靠地遵守系统门禁，而不是文字约定。”**
- 署名：DSH Harness philosophy
- 三步流程：
  - 把规则写成可检查的承诺
  - 检查失败就阻止执行
  - 接入 CI，进入真实执行路径
- 流程结论：先检查，再允许真正执行
- OPC 落点：**这正是 OPC 需要掌握到 Harness 边界的原因**

> **背景（不上屏）**
>
> 文档负责指出正确道路，系统门禁负责在真实执行路径阻止错误；规则能够失败，才成为工程约束。

## P22 · OPC 的最终判断

- 标题：**OPC 要掌握到哪一步？先借现成，直到业务要求你改变边界**
- 副题：五个 Engineering 让动作不断上移；Harness 决定动作能否可靠落地
- 定义：**DSH = 可替换组合的 Harness**
- **1 先借现成**：常见任务，复用成熟 Harness
- **2 看懂边界**：谁能做、谁检查、哪里留记录
- **3 必要时改变**：差异化进入执行链时，替换对应能力
- 带走句：**“装自己的，借现成的”**
- 署名：一人公司的 Harness 原则

> **背景（不上屏）**
>
> 回答封面问题：掌握深度由业务是否需要改变执行边界决定，而不是默认自建或自动拥有所有 Loop / Graph 能力。
