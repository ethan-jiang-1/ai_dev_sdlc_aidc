## P1 封面（0.5 min）

大家好。今天想聊一个很具体的问题：**一个人开公司，AI Coding 到底要掌握到多深？** 这个问题，就是今天这场"航海指南"要回答的。

---

## P2 钩子（1.5 min）

先做一个测试。两年前，你在干嘛？大概率在聊天框里精心打磨 prompt——怎么措辞、给几个例子、约束什么格式。

一年前呢？你在 Claude Code 里一行行审它改的代码，给它喂 context——把仓库里相关的文件 @ 给它。

那现在呢？风向已经开始变了。Anthropic Claude Code 的负责人 Boris Cherny 说了一句话："I don't prompt Claude anymore. I have loops running that prompt Claude… My job is to write loops."——我不再给 Claude 写 prompt 了，跑着的是替我写 prompt 的 loop，我的工作是写 loop。

注意，**你不是在追新工具。你是被模型一步步往上推**——模型越强，你和它的互动方式就越变。这条路，今天我用五个角色串给你：说话者、策展者、环境工程师、控制流作者、编排者。

---

## P3 路线图（1.5 min）

今天四站。第一站，五层演变——这两年工程注意力是怎么一层层往上走的。第二站，我想论证一个可能反直觉的判断：**五层讲完，根本还是 harness**。第三站，落到你身上：harness 这一格，用固定的还是灵活的？第四站，我讲一个把灵活性做到极致的 harness——DeepSeek Harness，DSH。最后，给你一句可以带走的话。

---

## P4 发动机（2 min）

先讲发动机。五层背后，其实只有一个原因。

模型的可靠能力在指数增长。METR 的独立评估给过一个数字：**50% 可靠性任务长度，大约每 7 个月翻一倍**。也就是说，模型能可靠干完的活，越来越长。

模型越能干，你花在"怎么跟它说话"上的功夫就越不值钱。Anthropic 自己都说了："The exact formatting of prompts is likely becoming less important as models become more capable."——prompt 的精确措辞，越来越不重要。

于是工程注意力就往上移：从"说什么"，移到"看什么"，再到"在什么环境里跑"。记住一个词：**杠杆点上移**。而且每一次上移，都是叠加，不是替代——后面每一层，都还踩着前面。

---

## P5 Prompt + Context（3 min）

从第一层看起：prompt engineering。工程对象是任务表达——系统提示、例子、格式、约束。一句话定义：**prompt 是行为控制面，不是系统本身**。它塑造模型怎么想，但不决定周围环境。

有个反常识的点：你把系统问题塞进更长的 prompt，只是"**把缺失的控制面，伪装成提示复杂度**"。说得再直白点——prompt 里写再多规矩，也不解决"它有没有权限、有没有测试、能不能恢复"这些系统问题。

一个例证。2024 年 Anthropic 在 SWE-bench 上故意保持最小脚手架，他们原话："The agent has a prompt, a Bash Tool, and an Edit Tool."——一个 prompt，加一个 Bash 工具，加一个编辑工具。就这么简单。记住这个，一会儿它还会出现。

很快大家发现，光说得好不够——模型得看到对的东西。这就是第二层：context engineering。工程对象从"怎么说"，移到"**模型此刻该看到什么**"：工具返回值、检索结果、仓库事实、任务状态。

这一层有个特别反直觉的量化证据：**context rot**。token 越多，模型准确回忆的能力越差——研究里最经典的现象是"两头好、中间差"：开头结尾记得住，中间忘了。所以 context 工程的目标不是塞更多，而是"在保持有用信息的前提下，最小化 token"。**塞得越多，记得越差。**

这一层的生态事件大家都听过：MCP、RAG。注意，这些技术本身不新——是"能力到位、注意力上移"之后，它们才成为焦点。人的角色也变了：从说话者，变成策展者——决定它看什么、给它多少 token 预算。

---

## P6 Harness（2.5 min，埋雷）

第三层：harness engineering。工程对象从"模型看到什么"，移到"**模型在什么系统里跑**"——权限、沙箱、工具协议、验证门禁、trace、CI。

一个定义，Böckeler 的：**"Agent = Model + Harness."**——一个 agent，等于模型，加上模型之外的一切。

为什么轮到它？因为 prompt 和 context 都不提供可执行的环境。模型再会说话、看到的再多，它也没有权限碰文件、没有沙箱兜底、没有测试验证它改对了。这些，都得 harness 给。

而且 2026 年的安全事件，就集中爆发在这一层。这个我们第二站再展开。

现在，请你记住一个词：**harness 是"单次运行容器"**。后面你会看到，loop 的每一次迭代，都要实例化一个 harness；graph 的每一个 agent 节点，也跑在它自己的 harness 里。记住这个，第二站要用。这一层，人的角色：环境工程师。

---

## P7 Loop + Graph（2.5 min）

第四层：loop engineering。工程对象是跨运行的控制流——**何时、为何、以什么条件重复**。但它的引擎很朴素：模型越来越强、尤其能"知错改错"，只要反馈得当，把结果喂回去，它就会不断输出更好的结果。

2026 年 6 月，一个月之内，四个方向同时给出了定义。最形象的是 Osmani 的："Loop engineering is replacing yourself as the person who prompts the agent."——loop 工程，就是把你从"给 agent 写 prompt 的人"这个位置，替换掉。

有一个黄金法则值得记住：**只有当一次运行的结果，改变下一次行动时，才叫 loop**。固定任务、固定调度，那是一次定时执行，不是 loop。

但它有个大坑：loop 可能错得更贵。Woliveiras 说："A loop can be wrong in ways that are subtle, expensive, and hard to detect."——一次错误，会被循环放大成很多次错误。

第五层：graph engineering。工程对象是多 agent 的**编排**（orchestration）——用一个 workflow、一个 DAG，把模型的乱发挥收进显式流程：谁先做、什么时候分支、什么时候停。核心诉求就一个：用编排换可靠、可审计的结果。产业派说：把 agent 建成状态图；学术派说：从个体智能到系统智能。

但这一层要泼两盆冷水。第一，它不是新东西——LangGraph 2024 年就提供了 workflow/DAG 的组件技术，只是那时候"编排 agent loop"这个需求还没凸显；新的只是"命名和学科意识"。第二，它火得快——Steinberger 一条推文 260 万浏览【注意：是 260 万，不是 2.6 亿】，但旁边什么框架、什么模型都没发布。火六周就被下一个概念接棒，恰恰说明：它还在叙事期，没沉淀。

---

## P8 叠加观 + 成熟度（2 min）

五层都过完了。回头看整体。

第一，**不是换代，是叠加**。五层同时活在 2026 年的成熟系统里，只是注意力集中在当前"卡脖子"的那层。报告里有个好比喻：loop 归根结底，是带着脚手架重复的 prompt；prompt 和 loop 是两件工具——**学会用扳手，不等于扔掉螺丝刀**。

第二，**成熟度不一样**。前三层——prompt、context、harness——是今天就在生产里跑的成熟层：有量化机制、有独立证据、有真实风险面。后两层——loop、graph——是刚冒头的新叙事。"火六周就被接棒"这个现象本身，就是它还没沉淀的证据。

所以，今天该重仓的，是 1 到 3 层。而且——五层里，有一层，是其他所有层的**承重墙**。第二站，我们就把这面墙找出来。

---

## P9 转折（1 min）

为什么说承重墙是 harness？先看一个结构事实：loop 的每一次迭代，实例化一个 harness；graph 的每一个节点，跑在它自己的 harness 里。也就是说，上面两层，是楼上的楼层；而 harness，是每一层都踩着的那个地基。

**五层讲完，根本还是 harness。** 声明一下：这不是报告的原话——报告把 context 和 harness 并列为成熟主体。"harness 是承重墙"是我们的判断。接下来我用三条线来撑它。

---

## P10 定义（1.5 min）

第一条线，先看定义。

Böckeler：**"Agent = Model + Harness."**——harness，就是 agent 里除了模型之外的一切：权限、沙箱、工具、验证、trace、CI。

说得大白话一点：你以为你在用一个聪明的模型，其实你用的是"模型 + 它周围一整圈系统"。

这个思想早有雏形。还记得吗？2024 年那个最小脚手架——"The agent has a prompt, a Bash Tool, and an Edit Tool."一个 prompt 加两个工具。**那就是最早的 harness**：模型之外的两样东西。harness 不是 2026 年才发明的新词，它是从 prompt 时代就存在的隐形地基。

---

## P11 两套控制 + 确定/概率（3 min）

第二条线，也是重点：harness 里头，到底在干什么？

Böckeler 把它拆成两套控制机制。第一套，**Guides**——引导，前馈控制，在 agent 行动之前约束它："按这个样式写"、"必须过这个 lint"、"只能用这些工具"。第二套，**Sensors**——感知，反馈控制，在 agent 行动之后把结果喂回去："测试挂了"、"用户拒绝了这个 diff"、"退出码非零"。

打个比方。教小孩做菜。Guides 是事前规矩：先洗手、刀口朝外、火别开太大。Sensors 是事后纠正：尝一口，咸了加水。一个管怎么开始，一个管怎么修正。没有这两套，等于把一个很聪明的小孩直接丢进厨房——再聪明，也会把厨房烧了。

这两套控制里，还有一档决定性的区别：**computational 和 inferential**。

Computational，确定性：测试、lint、类型检查、schema。结果可复现、可审计——你可以直接信它。

Inferential，概率性：AI review、模型当裁判。它给的是意见，意见本身可能错，你还得判断它判断得对不对。

所以原则是：**能交给确定性的，绝不靠概率性的**。直观感受一下：`npm test` 全绿，加上类型检查通过——这个你可以直接信。AI 说"这代码写得不错"——你敢直接信吗？

这条原则，是 Böckeler 整个设计的魂，而且它会一路向上渗透——后面 Loop 层的"五级验证梯"，从确定性到人工检查点，是同一套哲学。

---

## P12 圈住 / 拦住 / 看清（2.5 min）

把 harness 的六件套收一收，用三个动词就能记住。

第一个动词：**圈住**。沙箱加权限——让它只能碰该碰的文件、连该连的网、做被授权的操作。Claude Code 的沙箱，文件系统和网络双重隔离，内部实测减少了 84% 的权限提示。

第二个动词：**拦住**。工具协议加验证门禁——把"对错"变成机器可判的关卡，在错误离源头最近的地方，就地拦下，而不是等 review 才发现。

第三个动词：**看清**。可观测性加 provenance 加 CI——trace、metrics、logs 记下它的每一步：工具调用、重试、模型步骤、产出。出了问题，你能还原：它为什么成功？为什么循环？为什么花太多钱？

所以一句话收束：**模型给能力，harness 给可靠性**。你花大价钱买一个很强的模型，买到的是"能力"；但"可靠性"，是 harness 给出来的。可靠性是"模型加 harness"整个系统的属性，不是模型自己的属性。这是第二条线。

---

## P13 承重墙（1 min）

第三条线：连 loop 和 graph 自己的定义，都承认 harness 在底下。

Osmani 说："Loop engineering sits one floor above the harness."——loop 就在 harness 上面一层。Macedo 说："The harness supplies the engine; loop engineering writes the pilot."——harness 提供引擎，loop 写飞行员。

更有意思的是，上层自己都在长 harness。Graph 最前沿的 GraphARC：模型提议一张工作图，一个确定性的检查器，要么放行、要么带着理由拒绝，只有被放行的图才会执行。plan，check，execute——这是 harness 式的确定性门禁，在 graph 层复现了。

还有一句机制级的话，来自那份五层报告："**假设下层正确，是 bug 的来源；对下层显式验证，是工程成熟的标志。**"楼盖得越高，地基越不能虚。

---

## P14 2026 CVE（1 min）

上面全是正面论证。反面更直接——2026 年真实出过事。

2026 年 8 月，AWS、Google、Vercel 的 agent 工具触发漏洞被披露。关键：**这不是 prompt injection，而是执行时授权缺失**——工具调用形状的数据被当作权威，攻击者伪造工具调用，不需要运行模型，就能触发工具。

一句话教训：如果所有护栏都建立在"模型会发出合法工具调用"这个假设上，那当工具调用可以被伪造时，整条验证链都失效。修复方向：**authorize at execution, not at generation**——在执行时授权，不是在生成时授权。

这对你意味着什么？你选的 harness，如果只防"模型被诱导"、不防"工具被绕过"，就是不完整的。这是"harness 值得你亲自把关"的第一个现实理由。

---

## P15 抉择（1 min）

好，harness 是什么、为什么重要，讲完了。现在回到你——一人公司。

你的问题落成了一格：**harness 这一格，你用固定的，还是灵活的？**

注意，这不是"自己做 vs 依赖现成"的二选一。现成的好东西，该用就用。真正的区别在一条轴上：**固定，还是灵活**。

打个比方：精装公寓，拎包入住，但墙不能拆；带标准接口的空间，你得自己装，但能改成你要的样子——而且市面上现成的家具，直接搬进来就能用。

---

## P16 固定的好（2 min）

先公平地说，固定 harness 有它的价值，而且不小。

过去一年，harness 从"自己写 bash 编排"，变成了"**随产品交付**"。Osmani 的原话：一年前，你得写一堆 bash 自己维护；现在，组件随产品交付。

Claude Code 的沙箱，文件加网络双重隔离，开箱就有；Copilot 有云端沙箱；provenance 接 CI，也有产品替你做了。对常见任务，这些已经够好——沙箱有人设计、权限有人把关、可观测性有人接好。你省下的，是大量的基础设施时间。

这也符合 Anthropic 的工程忠告："**Start with the simplest viable system.**"——从最简单可行的系统开始。自治不是越高越好。所以，绝大多数人，应该从现成的开始。

---

## P17 固定的卡（3 min）

那卡在哪？**卡在你想改 harness 本身的时候。**

固定 harness 的 guides 和 sensors，是写死的、为大众设计的。常见任务，它替你设计好了；但"你的任务"，不等于"大众的任务"。

当你想改 harness 本身，就会卡住。举几个例子。

你想挂你自己的模型、你自己的工具——厂商支持什么，你才能用什么。想接你自己的数据源、自己的工具协议？要么等官方，要么绕。

你想换执行后端——比如换到远程沙箱？沙箱策略、工具集是定死的，没有这个接口。

你想挂你自己的 skill——你沉淀的"这件事该怎么做"的过程性记忆？只能塞进 system prompt，或者受它的规则限制。

你想挂你自己的 knowledge map——你自己项目的"地图"：哪里该改、归属谁、正确路径？它没有一等对象的位置，只能塞进一个大 prompt。而 context rot 告诉我们：**塞得越多，记得越差**。

更硬的证据：2026 年那个 CVE。固定 harness 的护栏，在执行侧有漏洞；而你想补"执行时授权"——你改不了它的内核，只能等厂商修复。

住精装公寓，想加个自己的接口、改个格局？物业说不行，或者，得走他们的流程。

---

## P18 本质（2.5 min）

所以，问题不是"现成不好"，是"**只能现成**"不行。

立场收束成一句话：**不是"别用现成"，是"别只能现成"。**

一个灵活的 harness，好就好在它同时给你两样东西。第一，**装自己的**：挂模型、挂工具、换后端、挂 skill、挂 knowledge map、自定义门禁。第二，**借现成的**：成熟的 adapter、现成的 skill、你选定的模型，直接复用。

它不逼你在"自己"和"现成"之间二选一——这才是"灵活"的意思。

对一人公司，这一点尤其重要：你没有团队分摊基础设施。你更需要一个"装得下自己、又接得上现成"的 harness——你自己那份价值，你的知识、你的流程、你的门禁，能进去；行业里成熟的东西，也能借。

那么问题来了：有没有这样一个 harness？有。这就是最后要讲的，DSH。

---

## P19 DSH（1 min）

DSH，DeepSeek Harness——一个把"灵活性"当第一原则的 harness。

它的架构哲学，一句话："**There is no privileged core to patch: you extend dsh by mounting a plugin beside the others.**"——没有特权内核。你要扩展，不是去改内核，而是在旁边，挂一个插件。

换句话说：它不给你写死的 harness，它给你一个"**能改 harness 本身**"的框架。精装公寓和能改格局的空间，DSH 是后者——而且接口是标准化的。

---

## P20 双向灵活（2.5 min）

"灵活"具体长什么样？两句话：装自己的，借现成的。

先说装自己的，四样机制，都是源码里真实存在的。

**挂模型**：在 `ctx.llm` 上注册一个 adapter。协议兼容的，纯配置就行；不兼容的，写一个小 adapter。

**挂工具**：在 `ctx.tools` 上注册，它的 schema 会自动进入模型可见面。

**换后端**：capability seam——一个能力由"定义、提供者、消费者"三角色组成。换 fs 后端、换 subprocess 后端，消费者一行都不用改。

**挂 skill、挂 knowledge map**：过程性记忆按需加载；你项目的"地图"是一等对象——"Each fact has one home"，每个事实只有一个家。

而且，加模型、加工具，都"**不必改 loop**"。这是源码消化里的原话。

再说借现成的：挂一个新 vendor，**15 行 YAML** 就够了。协议兼容，纯配置；行业里成熟的东西——你选定的模型、现成的工具——直接复用。

这不就是"装自己的，借现成的"吗？DSH，就是这句话的实现。

---

## P21 哲学（1.5 min）

最后一句哲学，是 DSH 整个设计的魂。

"**Agents follow enforced gates far more reliably than prose conventions.**"——agent 会可靠地遵守被强制执行的关卡，而不会可靠地遵守写在 prose 里的约定。

这不是 DSH 一家之言。还记得 Graph 层的 GraphARC 吗？模型提议工作图，确定性检查器放行或拒绝——同一套哲学。

这就是第二站讲的"确定性优先"，在一个真实 harness 里的样子：**你自己定义门禁，机器替你执行**。

对一人公司：你项目的规则——哪里该改、什么不能做、什么算完成——可以变成机器执行的关卡。不靠自律，靠系统。

## P22 回答 + 带走一句（2 min）

回到最开始那个问题：一个人，AI Coding 要掌握到多深？

先看角色表。一个成熟团队，需要五种角色：prompt 设计师、context 平台、harness 工程师、loop 设计师、graph 架构师。**责任是叠加上移的，不是岗位替代**——而一人公司，就是"被同一个人承担"的极端情况。

所以答案：**你要掌握到 harness 这一层。不用从零造，但要能改。**

为什么是这一层？第一，它是承重墙——上面两层都站在它上面。第二，一个灵活的 harness，会自动罩住上面两层：loop 每次迭代实例化 harness，graph 节点跑在它自己的 harness 里——harness 灵活了，loop 和 graph，也跟着灵活。

怎么选？从现成开始，但别停在"只能现成"——给自己留一个能改 harness 本身的选项。

最后，送给你一句话，八个字：**装自己的，借现成的。**

你的知识、你的流程、你的门禁，能进去；行业里成熟的东西，也借得上。这就是一人公司，掌握 AI Coding 该到的深度。
