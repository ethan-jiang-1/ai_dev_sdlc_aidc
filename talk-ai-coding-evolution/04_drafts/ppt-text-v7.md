## V7 的整场论证

1. **P1–P3 立题**：OPC 要把 AI Coding 掌握到多深？整场沿“信息 → 可靠执行 → 工作组织 → 业务边界”前进。
2. **P4–P8 建图**：模型越强，工程对象越从一句话往系统上移；五层同时存在，但各自回答不同问题。
3. **P9–P14 证明 Harness 为什么关键**：模型决定能力上限，Harness 决定交付底线；可靠性来自行动前约束、行动后反馈和执行时授权。
4. **P15–P18 给 OPC 判断规则**：默认借成熟 Harness；只有运行边界进入业务差异化，才寻找可组合 Harness。DSH 的 GitHub 爆发说明注意力和扩展需求，不说明质量。
5. **P19–P23 回答“边界在手”**：DSH 是可组合 Harness runtime；插件进入执行链后要回答四项责任问题。部件可借，owner 必须在关键时刻拥有 final say。

## 逐页生产事实

### P1–P2 · 立题与五层全貌

- P1：**OPC 航海指南——一个人，AI Coding 要掌握到多深？**
- P2：**AI Coding 的五个 Engineering，先看全貌**；说清任务 → 让动作可靠 → 把工作组织起来。
- 视觉与详细文案继承 V6。

### P3 · 整场问题地图

- 标题：**今天只沿一条主线：能力越强，边界越重要**
- 副题：从信息、执行、组织，一路走到 OPC 的最终选择
- 01：模型怎样说清、看对，形成一次行动？
- 02：行动怎样可靠，并被 Loop / Graph 放大与组织？
- 03：当边界进入业务，哪些可借，哪些必须自己决定？
- 预告：**最后用 DSH 回答：可组合能力，如何仍由 owner 控制运行边界**

### P4–P9 · 五层关系与 Harness 转折

- P4：模型越强，工程对象越从一句话往系统上移。
- P5：Prompt 与 Context 解决“说什么、看什么”，仍未解决安全行动。
- P6：Harness 为每一次行动设下可靠边界。
- P7：Loop 与 Graph 让可靠行动持续发生并被组织。
- P8：五个 Engineering 同时活着，但各自回答不同问题。
- P9：最值得看懂的不是最高层，而是真实动作穿过的边界。
- 视觉与详细文案继承 V6。

### P10 · 能力上限与交付底线

- 标题：**模型决定能力上限，Harness 决定交付底线**
- 副题：同一个模型，换一圈运行边界，能否交付就是两个系统
- 公式：**能力上限：Model + 交付底线：Harness**
- 构件：权限 / 沙箱 / 工具 / 验证 / 执行记录 / 持续检查（CI）
- 解释：Harness 不替模型思考；它把权限、验证和记录变成系统行为。
- 收束：**最小的 agent 也必须面对真实执行结果；所以，可靠性要从模型之外找。**

### P11 · 行动前约束，行动后反馈

- Guides / Sensors；确定性检查优先，语义判断留给模型或人。
- 视觉与详细文案继承 V6。

### P12 · 先可靠，再承载专业知识

- 标题：**Harness 先把行动变可靠，再把专业知识放进去**
- 副题：前三件事控制行动；Knowledge Map 决定它能否走对专业路径
- **圈住**：沙箱 + 权限；限制伤害范围
- **拦住**：验证门禁；错误出现就停止
- **看清**：Trace + 来源记录；还原发生过的事
- 第二层：**再承载专业知识——Knowledge Map：把事实归属、正确路径和项目地图放进边界内**

### P13 · Loop / Graph 前先过确定性门禁

- 上层负责反复与编排；Harness 在每次执行前独立授权、验证与记录。
- 视觉与详细文案继承 V6。

### P14 · 事故与 OPC 转场

- 事故：伪造工具调用，无需模型也能触发真实动作。
- 修复：执行端拒绝伪造块；工具运行前独立授权。
- 原则：`authorize at execution, not at generation`。
- 转场：**边界必须有人负责；但这不等于每个 OPC 都要自己造 Harness。**

### P15 · 什么时候值得自己掌握边界

- 标题：**什么时候值得自己掌握边界？看它是否已经进入业务**
- 副题：判断标准只有一个：运行边界是否已经成为业务差异化
- 中心判断：**工具多，不是理由；边界变成业务，才是理由**
- 边界是通用能力：继续借成熟 Harness，把注意力留给业务。
- 边界进入业务：需要改变模型、工具、门禁、执行世界或知识。
- 收束：**当标准边界开始限制真实交付，才需要灵活 Harness。**

### P16 · 默认借现成，DSH 只在例外中出现

- 标题：**Codex、Claude Code 已经很强：大多数 OPC 应直接借用**
- 默认答案：借现成，把稀缺注意力留给业务。
- 原则：Anthropic · `Start with the simplest viable system.`
- 转场：**DSH 正是在这个例外里出现：不是替代成熟产品，而是让边界可改。**

### P17 · DSH 的注意力爆发

- 标题：**公开 14 天，DeepSeek Harness 接近 20 万 GitHub stars**
- 副题：**这股注意力，迅速聚到一套可扩展的 Harness 边界**
- 主指标：199,846 stars；2026-08-27 快照；公开约 14 天。
- 支持信号：22,820 forks；2,286 条生态快照。
- 解释：注意力集中在“可扩展边界”，但热度不是质量。
- 收束：**这是“边界可扩展”需求爆发的信号，不是质量认证。**

### P18 · DSH 给 OPC 的收益

- 标题：**对 OPC，价值不在装得多，而在少盯、敢放、能复用**
- 省手：换底座时少重写。
- 敢放手：审批 fail-closed，事实可重建。
- 可复用：把自己验证过的组合带到下个项目。
- 收束：先验证，再借力；少回手工，敢交真活。
- 视觉与详细文案继承 V6。

### P19 · DSH 的定位

- 标题：**DSH 不是插件商店；它是一套可组合的 Harness runtime**
- 模型 / 工具 / 执行后端 / 规则与 Loop 围绕共同合同装配，并留下 append-only session log。
- 视觉与详细文案继承 V6。

### P20 · 插件进入执行链后的责任问题

- 标题：**插件进入执行链后，真正的问题变成：谁说了算？**
- 副题：可组合只是入口；接入、替换、放行、追溯都需要明确责任
- **接入**：谁允许它进来？· registry
- **替换**：谁能换实现？· adapter + seam
- **放行**：谁在执行前签字？· gate
- **重建事实**：谁能还原事实？· session log
- 解释：**四问不是插件功能清单，而是运行边界的责任清单。**
- 收束：**如果答案永远是厂商或插件作者，边界就不在你手里。**

### P21 · Owner 的 final say

- 标题：**Harness 在手，不是都自己做，而是关键时刻你有 final say**
- 副题：部件继续借；owner 决定什么进入、什么可换、什么能执行、事实如何留下
- 四项决定：我决定接什么 / 换什么 / 何时执行 / 如何追溯。
- 定义：这是本 talk 对“边界在手”的定义。
- 收束：**部件可借，决定权不能外包。**

### P22 · 直接回答封面

- 标题：**回答封面：OPC 要掌握到 Harness 这一层**
- 副题：不是为了造框架，而是知道何时借、何时改、何时必须自己决定
- 标尺：**掌握深度，不按工具数量算；按你对运行边界的责任算。**
- 1 会用成熟 Harness：常见任务直接借现成。
- 2 看懂运行边界：权限、门禁、验证与记录。
- 3 需要时握住 final say：差异化进入执行链，自己决定四件事。
- 带走句：**部件可借，边界自己定。**

## 口径红线

- 五层是工程注意力与对象的叠加，不是严格运行时包容关系。
- Harness 是每一次真实行动的可靠运行边界；Loop / Graph 负责跨运行反馈与多节点组织。
- GitHub stars、forks 与生态条目只能说明 attention / 扩展面，不能证明质量、安全或成熟度。
- “四项决定权”“final say”“部件可借，边界自己定”是本 talk 的解释性结论，不冒充 DSH 官方原话。
- DSH 不被描述成 Codex / Claude Code 的替代品；默认策略仍是借用成熟 Harness。
