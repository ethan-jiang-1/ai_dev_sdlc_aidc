# 核心论点与立场（v1.7 摘要）

> 详细论证与证据分布见 [`00-storyline-map.md`](./00-storyline-map.md)（各幕要点）与 `../02_evidence/00-absorption-plan.md`（故事线资产 §一）。

1. **责任叠加上升**：五层不是换代，是信息、行动、组织责任随工程注意力一起叠加上移；团队可以分工，OPC 必须知道哪些可借、哪些不能外包。
2. **成熟度标尺**：前三层（Prompt / Context / Harness）成熟可信；后两层（Loop / Graph）叙事期、低置信度——"火六周就被接棒"本身就是证据。
3. **问题最终回到 harness**：这是**我们的判断**，不是报告背书（报告把 Context 与 Harness 并列）。Loop / Graph 会放大、组织结果，却不会补上节点缺失的执行边界；每一次真实动作仍需独立授权、检查与记录。
4. **可靠性是系统的属性**：模型给能力，harness 给可靠性；确定性优先（computational > inferential）。
5. **默认借现成，边界进入业务才改变**：工具多不是理由；标准边界开始限制真实交付、运行边界成为业务差异化，才值得寻找可组合 Harness。
6. **DSH 的爆发与定位**：GitHub 关注度和插件涌现证明它成为扩展入口，不证明成熟或可信。热度只是入口，真正可借的是 owner 自己验证过的能力组合；DSH 的定位是可组合的 Harness runtime，而非插件商店或更强 Loop。
7. **Harness 最终控制权在手**：不等于自建全部部件；owner 必须能决定能力能否进入、实现能否替换、门禁是否放行、事实能否重建。带走原则：**部件可借，边界自己定。**

## 一句话主线（源自 00-storyline-map）

模型越强，人机互动行为越变——人从"亲手做"被推成"设计模型怎么做"；一人公司要掌握到 **harness 这一层**：不用从零造，但要把最终控制权握在手里。
