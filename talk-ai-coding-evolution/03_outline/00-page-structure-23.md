# Talk 页面结构（现场版 v1.3 · 23 页 · 45 min）

> 本版先校准故事与每页职责，暂不进入 PPT 制作。五层是 **attention stacking**，不是严格运行时层级；Harness 是可靠运行边界，Loop 与 Graph 是按任务需要叠加的组织方式。

## 开场（3.5 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P1 | OPC 航海指南 | 0.5 | 题目、Ethan Jiang、问题：一个人要把 AI Coding 掌握到多深？ |
| P2 | 五个角色，已经分别有人替你命名 | 1.5 | Boris Cherny 讲 Loop；Böckeler 定义 Harness；Steinberger 讲 State Graph；人从写一句话转为设计系统怎么工作。 |
| P3 | 今天只回答三个问题 | 1.5 | 为什么工程注意力上移？为什么可靠性落在 Harness？OPC 如何从现成开始又保留改变边界的能力？ |

## 第一幕：五层不是五个新词（12 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P4 | 同一台发动机，把人的动作一格格往上推 | 2 | 模型能力增强 -> 单次交互边际收益下降 -> 杠杆点上移；METR 与 Anthropic 是两条证据；叠加，不是替代。 |
| P5 | Prompt 管表达，Context 管模型此刻所见 | 3 | Prompt 不是系统；Context 不是越多越好；context rot；两者解决不了执行边界。 |
| P6 | 能行动之后，问题变成：它在哪个受控环境里行动 | 2.5 | Harness = 权限、工具、验证、记录；Agent = Model + Harness；这是每次动作的运行与治理边界。 |
| P7 | Loop 管时间上的反馈；Graph 管空间上的协作 | 2.5 | Loop 的黄金法则；Graph 的显式节点、边、状态；Graph 可在部分节点使用 Loop；两者均是新兴、低置信度。 |
| P8 | 五层同时活着，但不是一座从小到大的金字塔 | 2 | 关系图：Prompt/Context 服务一次模型调用；Harness 保障每次执行；Loop 跨运行；Graph 跨节点组织；今天重仓成熟的前三层。 |

## 第二幕：为什么答案停在 Harness（10 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P9 | 每一次真实动作，都要经过一个可靠性边界 | 1 | 这是“Harness 最关键”的推断，不冒充为报告原话；从 P8 的关系图推出。 |
| P10 | 模型买来的是能力，交付可靠性来自 Model + Harness | 1.5 | Böckeler 定义；模型之外的一切；最小脚手架让抽象落地。 |
| P11 | Harness 同时在行动前引导、行动后反馈 | 3 | Guides / Sensors；computational / inferential；确定性优先。 |
| P12 | 圈住、拦住、看清，才把能力变成可交付结果 | 2.5 | 权限与沙箱；执行门禁；trace / provenance / CI。 |
| P13 | 上层系统能扩大产能，却不能替下层补可靠性 | 1 | Loop 放大反馈，Graph 显式路由与门禁；没有可靠节点，放大和编排都只会放大问题。 |
| P14 | 2026 的教训：在生成时相信模型，不等于在执行时授权 | 1 | 工具调用形状被伪造/绕过 -> 执行端缺少独立授权 -> 操作发生；修复是 authorize at execution。 |

## 第三幕：一人公司要拥有哪一段能力（8.5 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P15 | 问题不是自建与否，而是边界由谁定义 | 1 | 固定 vs 灵活不是价值高低；先看你是否需要改变模型、工具、执行世界、门禁或知识组织。 |
| P16 | 绝大多数场景，先借现成 Harness | 2 | 产品把沙箱、权限、观测等组件随产品交付；Start with the simplest viable system。 |
| P17 | 当任务超出产品公开的扩展合同，才需要更灵活的 Harness | 3 | 用一条具体需求链讲清：新模型/后端/工具/门禁/知识组织；不是笼统声称现成产品“改不了”。 |
| P18 | 灵活不是重造，而是装自己的、借现成的 | 2.5 | 自己的能力能以合同接入；成熟的 adapter、skill、模型可以复用；这是 OPC 的选择原则。 |

## 第四幕：DSH 怎样把灵活性做成系统（5 min）

| 页 | 页面结论 | 时间 | 必讲要点 |
|---|---|---:|---|
| P19 | DSH 的关键不是“一个更强的 Loop”，而是可组合的 Harness | 1 | 插件树 + 运行记录；无特权核心；改新行为优先挂扩展点，而非修改默认 loop。 |
| P20 | 一项能力要能换，必须把合同、实现和消费者一起设计 | 2.5 | `ctx.llm` adapter、`ctx.tools`、capability seam；加模型或工具不必改 loop；纯配置 vendor 是“借现成”的实例。 |
| P21 | 规则写给人看，门禁才负责让系统做对 | 1.5 | mechanically checkable promise -> command -> CI；GraphARC 作为同一原则的上层例子；不靠自律，靠系统。 |

## 叙事检查

1. P2 提出“人被模型推上去”；P4 解释为什么会发生。
2. P5-P8 给出五个不同工程对象与正确关系；P9 自然提出“每次动作靠什么可靠”。
3. P10-P14 从定义、机制、能力、依赖、事故完整回答“为什么是 Harness”。
4. P15-P18 把技术判断翻译成 OPC 的选择；P19-P21 用 DSH 证明这不是口号；P22 回答开场问题。

## 口径红线

- 前三层成熟，Loop / Graph 是新兴观察对象，不讲成既定生产范式。
- Graph 可以编排 Loop，也可以包含工具、验证器或其它节点；不能把所有 Graph 节点画成 Loop。
- Harness 是可靠性边界，不等于一定在几何上“包住”所有分布式节点；P8 的图只表达 talk 的治理关系，不宣称严格运行时包含。
- DSH 的原生机制不是 MCP；说 `ctx.llm`、`ctx.tools`、capability seam、plugin。
- CVE 只讲执行时授权缺失的因果链，不把厂商名、编号堆成画面主体。
