# 第三幕：一人公司要拥有哪一段能力（v1.3）

> 本幕不把“固定”说成落后，也不把“灵活”说成从零造。它讨论的是：当任务越过现成产品公开的扩展合同，谁能改变运行边界。

## P15 问题不是自建与否，而是边界由谁定义（1 min）

**上屏**：固定 vs 灵活，不是成品 vs 自研。

**判断问题**：我是否需要改变模型、工具、执行世界、门禁或项目知识组织？如果不需要，现成系统就是正确选择。

**讲点**：精装公寓的价值不是低，标准化降低了大量成本；真正的差异在于改造权和扩展合同。把“一人公司该自己写 harness 吗”的假问题，改为“什么时候需要拥有改变边界的能力”。

## P16 绝大多数场景，先借现成 Harness（2 min）

**上屏**：沙箱、权限、可观测性、provenance 与 CI 已能随产品交付。

**讲点**：Harness 的民主化使人不再需要自己写 bash 编排。固定产品在成熟、常见任务上提供了大量可靠性组件，正确的默认策略是 `Start with the simplest viable system`。这也是 OPC 稀缺注意力的正确用法。

## P17 当任务超出产品公开的扩展合同，才需要更灵活的 Harness（3 min）

**上屏**：一条需求升级链。

1. 要接入一个新模型或工具；
2. 进而要替换执行世界或能力后端；
3. 再要把项目自己的知识、规则和可执行门禁接入真实运行路径；
4. 如果产品没有相应合同，只能等待厂商或在边缘绕行。

**讲点**：这不是笼统地说 Codex、Claude Code “改不了”，而是说任何产品的可变范围都由其公开合同决定。P14 的执行时授权正是典型例子：想补的不是一句 prompt，而是执行路径上的一个控制点。

## P18 灵活不是重造，而是装自己的、借现成的（2.5 min）

**上屏**：
- 装自己的：模型、工具、后端、知识组织、可执行门禁。
- 借现成的：成熟 adapter、skill、模型、验证工具。
- 原则：自己的能接入，现成的能复用。

**讲点**：灵活的价值是可组合，而不是“所有部件都由我写”。对 OPC 而言，成熟部件降低成本，自己的合同和门禁保留差异化与控制权。转场：DSH 是把这件事落到系统结构上的实例。
