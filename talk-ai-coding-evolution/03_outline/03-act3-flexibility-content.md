## S18 抉择（1 min）—— harness 这一格，用固定的还是灵活的？

- **目的**：把一人公司的问题落成具体一格，并明确问题不是"自己做 vs 依赖现成"的二选一。
- **讲点**：
  1. 前面讲了 harness 是承重墙——那一人公司的问题就落成了一格：**这一格，你用固定的还是灵活的？**
  2. 注意：这不是"自己做 vs 依赖现成"的二选一。现成的好东西该用就用。
  3. 真正的区别在一条轴上：**固定 vs 灵活**。
  4. 通俗例子：精装公寓 vs 带标准接口的空间——精装公寓拎包入住，但墙不能拆；后者你得自己装，但能改成你要的样子，还能把市面上现成的家具搬进来。
- **转场**：先公平地说，固定 harness 到底好在哪。

---

## S19 固定的好（2 min）—— Codex / Claude Code 开箱即用

- **目的**：公平地讲现成 harness 的价值——它把 harness 组件**民主化**了。
- **讲点**：
  1. 过去一年，harness 从"自己写 bash 编排"变成了"**随产品交付**"（Osmani：一年前你得写一堆 bash 自己维护，现在组件随产品交付）。
  2. Claude Code 沙箱（2025-10）：文件 + 网络双重隔离，开箱就有；Copilot 云端 sandbox（2026-06）；provenance 接 CI 也有产品替你做了。
  3. 对常见任务，这些已经够好：沙箱有人设计、权限有人把关、可观测性有人接好——你省下的是大量基础设施时间。
  4. 这也符合 Anthropic 的工程忠告："**Start with the simplest viable system**"——自治不是越高越好。绝大多数人应该从现成的开始。
- **金句**："组件随产品交付"——harness 民主化。
- **转场**：那卡在哪？卡在你想**改 harness 本身**的时候。

## S20 固定的卡（3 min）—— 想改 harness 本身时

- **目的**：讲清固定 harness 的边界——它的 guides/sensors 是写死的、为大众设计的。
- **讲点**：
  1. 固定 harness 的 guides / sensors 是**写死的、为大众设计的**。常见任务它替你设计好了；但"你的任务"不等于"大众的任务"。
  2. 当你想改 harness 本身时，就卡住了：
     - **挂你自己的模型 / 工具**：厂商支持什么，你才能用什么——想接你自己的数据源、自己的工具协议，得等官方或绕路。
     - **换后端**：沙箱策略、工具集是定死的，你想换执行后端（比如远程沙箱）没有接口。
     - **挂你自己的 skill**：你沉淀的"这件事怎么做"的过程性记忆，只能塞进 system prompt 或受它的规则限制。
     - **挂你自己的 knowledge map**：你自己项目的"地图"（哪里该改、归属谁、正确路径）没有一等对象的位置，只能塞进一个大 prompt——而 context rot 告诉我们：**塞得越多，记得越差**。
  3. 更硬的证据：2026 CVE 证明固定 harness 的护栏也可能在执行侧有漏洞；而你想补"执行时授权"——**改不了它的内核，只能等厂商修复**。
  4. 通俗例子：住精装公寓，想加个自己的接口、改个格局——物业说不行，或者得走他们的流程。
- **转场**：所以问题不是"现成不好"，是"只能现成"不行。

---

## S21 本质（2 min）—— 不是别用现成，是别只能现成

- **目的**：落到立场——灵活 harness = 装自己的 + 借现成的。呼应 slogan。
- **讲点**：
  1. 立场收束：**不是"别用现成"，是"别只能现成"。**
  2. 一个**灵活的 harness** 好就好在它同时给你两样：
     - **装自己的**：挂模型、挂工具、换后端、挂 skill、挂 knowledge map、自定义门禁；
     - **借现成的**：成熟的 vendor adapter、现成的 skill、你选定的模型，直接复用。
  3. 它不逼你在"自己"和"现成"之间二选一——这正是"灵活"的意思。
  4. 对一人公司：你没有团队分摊基础设施，你更需要一个"装得下自己、又接得上现成"的 harness——自己那份价值（你的知识、你的流程、你的门禁）能进去，行业里成熟的东西也能借。
  5. 金句落位：**装自己的，借现成的。**
- **转场**：有没有这样一个 harness？有——这就是最后要讲的 DSH。
