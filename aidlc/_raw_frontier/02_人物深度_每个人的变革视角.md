# 人物深度：每个人的变革视角

> 来源：`ai_sdlc_frontier/` 七位人物的一手材料
> 研究日期：2026-07-07
> 核心问题：每个人是怎么"发现"需要变的？他们各自看到了什么别人没看到的东西？

---

## 一、Erik Schluntz（Anthropic）— "被迫 Vibe Code 的人"

**身份**：Anthropic 研究员，编程智能体负责人，《Building Effective Agents》合著者
**触发事件**：手骨折打了两个月石膏，被迫把全部编码工作委托给 Claude

### 他看到了什么

22,000 行代码，一天合并。同样工作量人类需要两周。

但这不是他最深的洞察。他最深的是：

> **"AI 任务能力每 ~7 个月翻一倍。人类逐行 code review 终将成为瓶颈——必须找到不读代码也能验证的抽象层。"**

### 他的独特角度

Erik 和其他人最大的区别：他是从**被迫放手**中学会的。不是主动选择"不写代码"，而是写不了。这给了他一个别人没有的视角：
- 别人在想"怎么让 AI 写更好" → 他在想"**怎么让 AI 写的东西我可以不读就信任**"
- 别人在优化 prompt → 他在设计**验证层**

### 他的变革处方

| 维度 | 旧做法 | Erik 的做法 |
|---|---|---|
| 任务定义 | 给 Claude 一个任务 | 花 15-20 分钟做 PM 前置工作，然后放手 |
| 代码范围 | AI 可以改任何地方 | Leaf Nodes 策略——只改不被依赖的终端模块 |
| 核心逻辑 | 相信 AI | 逐行审查不可妥协 |
| 验证方式 | 读代码 | 长跑压力测试 + I/O 标准——不看代码看产品行为 |
| 信任边界 | 静态的 | **动态的**——随着模型进步，leaf node 边界向下移动 |

### 他最激进的一句话

> "忘掉代码存在，但永远别忘了产品存在。"

## 二、Fiona Fung（Anthropic）— "杀掉旧流程的人"

**身份**：Claude Code & Claude Cowork 工程总监。前 Microsoft 11 年（Visual Studio, TypeScript），Meta 创始 Facebook Marketplace
**触发事件**：加入 Claude Code 团队后，发现六个月路线图到第三个月就过时了

### 她看到了什么

写代码、写测试、重构已经不再是瓶颈。但瓶颈没有消失——它们**转移**了：

```
旧瓶颈：工程带宽（写代码太慢）
    ↓
新瓶颈：验证（代码对不对？）
         Code Review（人跟不上 AI 产出量）
         安全与信任边界（什么可以交给 AI？）
```

### 她的独特角度

Fiona 和其他人最大的区别：她是**管人的，不是管代码的**。她的视角是组织设计，不是工具设计。

她的核心贡献是**三条铁律**：
1. **疯狂 dogfood** — 全员（含非工程）每天用 Claude Code & Cowork
2. **组织尽可能扁平** — 每个经理必须先做 IC，通过交付理解工程师日常
3. **允许且鼓励杀掉旧流程** — 任何人可以质疑任何流程，不合适就毙

### 她的变革处方

| 旧流程 | 新流程 | 为什么 |
|---|---|---|
| 六个月路线图 | JIT 即时规划 | "Build is cheap. Argument is expensive." |
| 找人问代码 | 先问 Claude | "每一次都追问：这个能自动化吗？" |
| 人类全覆盖 Review | Trust but Verify | Claude 管风格/bug/测试，人管法律/安全/品味 |
| 固定角色（PM/工程师/设计师） | 角色模糊 | PM 写代码，工程师做设计 |
| 雇人看吞吐量 | 雇人看判断力 | "吞吐量模型覆盖了" |

### 她最激进的一句话

> "找你们团队最吵的那个工作流——问它还在不在服务目的。如果不在，杀。如果在，自动化。"

## 三、Thariq Shihipar（Anthropic）— "命名了未知项的人"

**身份**：Claude Code 工程师，Fable 5 方法论发布者
**触发事件**：Fable 5 发布后，发现瓶颈从模型能力转移到了人的澄清能力

### 他看到了什么

> **"Fable 5 是第一个让『澄清未知项的能力』成为工作质量瓶颈的模型。"**

他给了一个完整的理论框架——地图≠疆域：

```
地图（你给 Claude 的）          疆域（真正发生工作的地方）
提示词、Skill、上下文      ≠     代码库、现实世界约束
        ↓
    差距 = 未知项（Unknowns）
        ↓
    Claude 遇到未知项 → 只能猜你的意图
```

### 他的独特角度

Thariq 和其他人最大的区别：他**把 tacit knowledge（隐性知识）的问题命名了**。其他人说"需要更好的上下文"，他把它拆成了一个可操作的矩阵：

| | 已知 | 未知 |
|---|---|---|
| **已知** | 已知的已知（写在 prompt 里的） | 未知的已知（你觉得显而易见，不会写，但看到能认出） |
| **未知** | 已知的未知（你清楚自己还没搞清楚） | 未知的未知（完全没考虑过的事） |

方法论就是围绕这个矩阵展开的：盲点扫描、头脑风暴、反问、参考资料、实现计划、实现笔记、测验。

### 他的变革处方

**实现前**：blindspot pass → 头脑风暴/原型 → 反问（让 Claude 采访你）→ 参考资料 → 实现计划
**实现中**：维护 implementation-notes.md，记录偏离和原因
**实现后**：出解释文档 → 让 Claude 出题考你 → 完美通过才合并

### 他在演讲里补了两条态度层的

1. **"砍掉了 80% 的系统提示词"** — Fable 级别的模型，给太多示例反而限制它。新做法：多给上下文，少给约束；告诉它情况，不告诉它不许做什么

2. **"Be unreasonable"** — 过去好/快/省三选二是本能。先别急着取舍，用更强的模型把边界往外推，看看现实是不是真的会逼你做取舍

### 他最激进的一句话

> "减少并提前规划未知项，就是智能体式编程的核心能力。"

## 四、Ryan Lopopolo（OpenAI）— "零人工代码的人"

**身份**：OpenAI Technical Staff，Frontier Product Exploration
**触发事件**：从空仓库开始，5 个月，100 万行代码，0 行人工手写

### 他看到了什么

这不是"AI 辅助编码"。这是**完全不写代码**。团队核心原则：**不手写代码。**

> "人类负责掌舵，智能体负责执行。"

时间压缩到传统编码的 ~1/10。每人每天 3.5 个 PR。Codex 经常在一个任务上连续工作 6 小时以上。

### 他的独特角度

Ryan 的视角是最极端的。他不是在优化现有的软件开发流程——他是在**用实验证明流程本身可以被替换**。

他的核心发现不是"AI 能写代码"，而是：
- **进展慢不是因为 AI 不够强，而是环境规范不够明确**
- 解决方案不是"再努力一点" → 而是"AI 还缺什么能力？怎么让它可读、可强制执行？"
- 工程师的新工作：设计环境 → 澄清意图 → 构建反馈回路

### 他的变革处方

| 维度 | Ryan 的做法 |
|---|---|
| **代码** | 人类从未直接提交过代码 |
| **Review** | 人类审查 PR 不再是必需流程——几乎全部审查由 agent 之间完成 |
| **知识管理** | "给地图，不给一千页手册"——AGENTS.md ~100 行目录页，真实知识在 docs/ |
| **架构约束** | 分层领域（Types→Config→Repo→Service→Runtime→UI），linter 强制执行 |
| **合并哲学** | 修复成本低，等待成本高 → 少阻塞门，flaky 测试不阻塞 |
| **清理** | 从每周五手动清理 20% 时间 → 后台 agent 持续 GC |
| **人做什么** | 设定优先级、把用户反馈转成验收标准、验证结果、补缺口 |

### 他最激进的一句话

> "当修复成本低、等待成本高时，等式反转。允许偶发失败、快速重试，比无限期阻塞更合理。"

## 五、Michael Bolin（OpenAI）— "拆解 Agent Loop 的人"

**身份**：OpenAI Technical Staff
**触发事件**：OpenAI 首次对外公开 Codex Agent Loop 内部实现细节

### 他看到了什么

Michael 是做工程的，不是做方法论的。他的洞察全部在**技术实现**层面：

> "用户的输入放在提示词最末尾不是 bug，是 feature——让静态前缀最大化缓存命中。"
>
> "所有 Agent Loop 的工程决策最终都回到一句话：保持前缀不变。"

### 他的独特角度

他是唯一一个**从 Agent Loop 内部**看问题的人。其他人都在讲"应该怎么用 AI"，他在讲"AI 底层是怎么跑的"。

关键发现：
- Codex **故意不用** `previous_response_id`，每次请求完全无状态——为了 ZDR 隐私合规
- 提示缓存要求精确前缀匹配 → 工具列表顺序、模型切换、沙箱配置变更都会破坏缓存
- `encrypted_content` 三合一设计：隐私 + 语义保留 + ZDR 兼容

### 他的变革含义

Michael 自己不谈"变革"，但他的工程决策揭示了一个深层趋势：

**Agent 的性能不是由模型能力单方面决定的，而是由缓存策略、提示词结构、压缩方式这些"隐形工程"决定的。** 两个模型能力相同的 agent，工程实现不同，实际体验可以天差地别。

## 六、Jediah Katz（Cursor）— "发现『少即是多』的人"

**身份**：Cursor 工程师
**触发事件**：Cursor 团队发现模型能力越强，静态上下文注入的边际收益越低

### 他看到了什么

> "As models have become better as agents, we've found success by providing fewer details up front."

A/B 测试：MCP 工具动态加载 → **token 消耗降低 46.9%**。

五个动态上下文发现模式：
1. 长工具响应 → 写入文件，agent 用 tail/grep 按需取
2. 聊天历史文件 → 双层记忆（摘要 + 完整 transcript）
3. Agent Skills 开放标准 → 名称在静态，完整指令在动态
4. MCP 工具选择性加载 → 仅名称注入，schema 按需加载
5. 终端会话 → 暴露为文件

### 他的独特角度

Jediah 的独特贡献是**从源头上改变了问题定义**：

- 别人在问："怎么压缩？" → 他在问："**怎么不让上下文膨胀？**"
- 别人在做减法 → 他在做**重定向**（输出不进上下文，进文件，agent 自己决定读多少）
- 文件系统作为通用抽象 → "a safer choice than yet another abstraction that can't fully account for the future"

### 他的变革处方

| 旧的上下文工程 | 新的上下文工程 |
|---|---|
| 能注入的尽量注入 | 能不进上下文的绝不让它进去 |
| 人工决定 agent 需要什么 | Agent 自己决定需要什么、去哪找 |
| 静态文件一次写好 | 文件化 + 惰性加载——agent 每次 grep，始终最新 |
| 压缩是被动的（满了再压） | 动态上下文是主动的（从源头防膨胀） |

### 他所在的团队还做了什么

Cursor 把 Agent Harness 当做**产品本身**来迭代：
- 双层评估体系（离线 CursorBench + 在线 A/B）
- 工具错误分类 + 异常告警 + 每周自动 triage
- 按模型版本定制工具格式（OpenAI→patch-based, Anthropic→string replacement）
- Mid-chat 模型切换（Haiku→Opus，框架处理工具集差异和缓存失效）

## 七、Rody Davis（Google）— "盆景艺术家"

**身份**：Google 顶级 agentic 工程师
**触发事件**：Google Antigravity 2.0 从 agentic IDE 进化为完整 agent-first 平台

### 他看到了什么

> "AI 速度的最大瓶颈不是上下文窗口——是糟糕的代码库健康度。"

四个支柱：
1. **Skills as Context Cheat Sheets** — 把文档压缩成精准的 Skill 文件，agent 需要时加载
2. **Bonsai 代码审查法** — 像盆景艺术家持续修剪，state/UI/data 严格分离
3. **分层 Review** — 营销网站看视觉输出，后端看合约和 schema，重复模式人写第一个 agent 复制
4. **代码库健康是真瓶颈** — 投入清理代码库的时间，通过 agent 产出质量数倍回报

### 他的独特角度

Rody 是最不"技术精英"的一个——他的 insight 非常朴素但非常实战：
- "写第一个例子自己来，剩下的让 agent 抄" — 人的品味通过样本传播
- Skills 就是作弊条 — 不需要 fancy 架构，把文档压成 markdown 就能显著提升 agent 表现
- 扁平架构 → 一眼看出违规 — 设计原则：**让坏代码容易看出来**

### 他的变革处方

| 阶段 | 传统做法 | Rody 的 100X 做法 |
|---|---|---|
| 原型 | 手写一版 | 同一需求出多个框架版本对比 |
| 测试 | 手写几个关键测试 | 测试套件丰富度远超人工时代 |
| 审查 | 人工逐行看 | Bonsai 法：视觉审 UI，合约审后端 |
| 部署 | 一步步手动 | 一键多环境 + 自动回滚 |
| 维护 | 人发现问题再修 | Agent 持续扫描、自动发起清理 PR |

## 八、七个人的变革光谱

把七个人放在一条轴上，可以看出各自的侧重点：

```
组织/流程层                          工程/基础设施层
    Fiona          Erik          Thariq      Jediah    Michael     Rody      Ryan
    杀流程        Leaf Nodes    未知项      动态上下文  Agent Loop  Bonsai   零人工代码
    JIT规划       PM模式        地图≠疆域    少即是多    缓存策略    CheatSheet  Harness
    角色模糊      验证层         Be unreasonable             代码健康    Agent自我审查
    三条铁律      压力测试                                                GC机制
```

**左翼**（Fiona, Erik）：关心人怎么组织、怎么信任、怎么放手
**右翼**（Ryan, Rody, Michael）：关心系统怎么设计、agent 怎么跑、基础设施怎么搭
**中枢**（Thariq, Jediah）：关心信息怎么组织、上下文怎么流

## 九、他们没有共识的地方

共识文件（`01_变革共识_跨公司方法论趋同.md`）覆盖了他们一致的部分。这里记录不一致的地方：

### 分歧 1：Review 要不要人？

| 立场 | 代表人物 |
|---|---|
| 人类不用审 PR 了 | Ryan Lopopolo — "几乎所有审查已调为 agent 间完成" |
| 核心逻辑必须人审 | Erik Schluntz — "触碰系统主干，人类逐行审查不可妥协" |
| 人只审特定维度 | Fiona Fung — 法律、安全、品味需要人 |

### 分歧 2：上下文应该怎么给？

| 立场 | 代表人物 |
|---|---|
| 少给，让 agent 自己拉 | Jediah Katz — 动态上下文发现 |
| 给地图（目录页），指路 | Ryan Lopopolo — AGENTS.md ~100 行，结构化 docs/ |
| 给上下文，不给约束 | Thariq Shihipar — 告诉它情况，不告诉它不许做什么 |

### 分歧 3：agent 可以信任到什么程度？

| 立场 | 代表人物 |

### 分歧 4：流程是要杀的还是重建的？

| 立场 | 代表人物 |
