# P1-P50 视觉命题账本（v0.13）

本账本替代 v0.12 以“主体类型 + 安全区”为主的做法。每页先定义观众三秒内应当看见的判断，再决定构图与实现。内容职责仍以 `../03_outline/` 为准。

## 第一幕：让失配可见

| 页 | 三秒画面 | 主构图动作 | 可见痕迹 | 实现 |
|---|---|---|---|---|
| P1 | 一条线性软件交付链正在闭合成受控循环 | 六阶段轨道从右侧开始回弯，金色工件穿过红色门禁后沿青绿路径回流 | 工件、门禁、owner、反馈只作四个轻标记 | 原生，保留方向 |
| P2 | 编码段缩短了，交付总长却几乎没动 | 同一时间尺叠放“编码耗时”和“端到端周期”；被压缩的 Build 留出空腔，等待段从两侧侵入 | queue、first review、approval、deploy 等待刻度 | 原生精确结构 |
| P3 | Build 塌缩后，剩余阶段成为新的长杆 | 六阶段像机械连杆，Build 被压成薄片，规划/测试/发布的等待仍保持厚度 | Anthropic 原句固定在塌缩点旁，明确归属 | 原生精确结构 |
| P4 | 五层是对同一条 SDLC 逐层调焦 | 同一条六阶段路径被五个不同焦距的检查框依次扫过，不再画五张并列卡片 | 每次调焦只暴露一种问题：表达、约束、边界、回流、编排 | 原生 + 局部素描纹理 |

| P8 | 宽产出撞上窄控制，只剩排队或欠审 | 沿用已批准主体 | 控制容量、排队、审查不足 | 已批准 Image 2 |

| P10 | 工件链已经成形，但五个审计位置仍是空洞 | 六个工件沿同一轨道接力；身份、版本、证据、审批、强制门禁以五个未接通的灰色插槽出现 | 空插槽、断开的签名线和事件线 | 原生工件仿真 |
| P11 | 六阶段不是各加一个助手，而是六次控制方式换轨 | 六条轨道在同一垂直切面完成“人盯步骤→系统控制”的换轨，构建和发布的红色门禁最强 | 工件、前置约束、执行护栏、验证证据、独立授权、受控回流 | 原生，保留但增强尺度变化 |

## 第二幕：逐段重建六阶段

| 页 | 三秒画面 | 主构图动作 | 可见痕迹 | 实现 |
|---|---|---|---|---|
| P13 | 六份工件不是列表，而是六次接力构成的闭环 | 每个阶段把上一份工件展开、加工，再折成下一份；incident 沿青绿回路返回 intent | 版本号连续、owner 手印连续 | 混合工件接力 |
| P14 | 原始意图经过整理，但没有被改写成另一种意思 | 多股模糊但有来源的需求信号进入“整理夹具”，被压成清楚的 intent.md；被删改的内容以擦除痕迹留在旁边 | 原句、整理标记、未解决问题 | Image 2 工程素描 + 内生短标签 |
| P15 | intent.md 是一份仍带着提出者声音的工作文件 | 放大真实比例的 intent.md，左侧保留来源摘录，右侧五段结构，开放问题用红色未闭合标记 | 来源、版本、owner、open questions | 原生工件仿真，非空白文档 |
| P16 | intent 被产品 owner 在真实门禁前接受或退回 | intent.md 沿轨道进入 accept/reject 机械门；退回支路回到开放问题，放行支路进入设计；owner 的批准落在分叉点 | 批准/退回、理由、通过率刻度、返工回路 | 原生场景式收口，不用四框 |
| P17 | 多种约束在 Build 之前汇流，并在冲突处冒红 | brand/security/compliance/UX 像透明描图层覆盖到同一 spec 草图，冲突处出现红色批注并阻止继续 | 约束来源、冲突编号、政策 owner 引线 | Image 2 图文一体，精确冲突清单置外 |
| P18 | spec 不是 intent 的扩写，而是被政策校准后的方案 | intent.md 与版本化 skills 从两侧进入制图台，spec.md 在中央逐层显影；政策约束像量规在边缘校准 | skill 版本、施加点、spec 差异 | 混合工件工作台 |
| P19 | 风险与矛盾先被分流，两个 owner 在不同位置作决定 | spec 和 concern list 沿同一轨道先过矛盾筛，再过政策门；产品 owner 处理取舍，政策 owner 处理例外 | 双签名、被拒理由、返工到 spec 的路径 | 原生场景式收口 |
| P20 | 圈住、拦住、看清形成一个执行单元 | 沿用已批准主体 | 沙箱与权限、hooks 与门禁、观测与来源记录 | 已批准 Image 2 |
| P21 | plan.md 是代码区前的一道真实工作门 | 大幅 plan.md 与只读代码库并置；四段计划通过审查后，代码区的锁才打开；高风险项另行路由 | 只读锁、风险批注、tech lead 签名 | 原生工件近景 |
| P22 | 规则从散落脑内进入一套可触发的知识机械 | 左侧旧 wiki 和聊天碎片被归档，中央 AGENTS.md 成权威脊柱，右侧 skills 根据任务条件像抽屉一样弹出；一个失败样本回写规则 | 来源迁移、触发条件、版本 diff | Image 2 工件拼贴 + 内生短标签 |
| P23 | hook 不“提醒”，而是在工具前真正把错误动作挡落 | 一条工具执行轨道依次遇到保护路径、formatter/lint、credentials 三个不同机械门；负例撞门后落入拒绝槽 | deny 原因、修正后再通过、时间戳 | 原生动作型管道 |
| P24 | 三条并行工作线互不踩踏，但都能追到启动者 | 中央工程师控制台分出三条具有不同纹理的 worktree 轨道，每条有独立文件树、日志卷轴和责任线；subagent 只存在于一条局部支线 | branch/worktree、session id、owner、日志 | 原生精确轨道 + 工件细节 |
| P25 | 平台基线包围执行环境，但不吞掉改动责任 | 外圈是平台维护的沙箱、权限和 hooks；内圈是工程师的 plan/diff/tests；返工从测试证据回到 plan，而不是回到平台 owner | 双责任签名、rework 回路、基线版本 | 原生场景式收口 |
| P26 | 两种证据像双回路同时验证产品和控制系统 | 上回路：改动→测试→产品证据；下回路：配置→eval→harness 证据；两条回路在合并门前汇合 | guides 前馈、sensors 回馈、双证据包 | Image 2 技术素描主体或高精原生混合 |
| P27 | “完成”是一次能从失败走到证据的短循环 | 代码修改先撞出失败测试，修正后生成绿色证据卷；session/PR 像记录纸持续收集每次尝试 | 失败→修改→通过、不可改测试、工具输出 | 混合短连续叙事 |
| P28 | harness 配置也有自己的测试实验台 | 真实任务样本像抽屉进入 eval 台；AGENTS/skills/hooks 配置改变后，整套任务重新运行；阈值门决定能否合并 | 配置版本、事故回归样本、pass threshold | 原生实验台式结构 |
| P29 | QA 同时维护两套证据系统，而不是逐单点按钮 | 中央 QA 维护产品测试台和配置 eval 台，两份证据在合并门前汇合；趋势曲线从门后回流到套件维护 | QA/config owner 分工、首次通过率、漏检、失败趋势 | 原生场景式收口 |
| P30 | proposal 在生产边界前停住，授权令牌只在执行瞬间出现 | agent 把发布方案递到边界，生产侧保持物理断开；发布责任人在当下语境中签发一次性令牌后，桥才短暂闭合 | proposal、当前风险、一次性授权、过期/拒绝 | Image 2 结构剖面 + 内生标签 |
| P31 | 写码者的路径在“批准自己”处被红线截断 | PR 是中央卷宗；机器检查、AI 语境审查、人类风险判断像三层透明审查页覆盖其上；自批支路被红线剪断 | severity、通过阈值、批准签名、回写规则 | 混合工件近景 |
| P32 | allow、ask、block 是三个真正不同的执行出口 | 工具请求进入统一 pre-execute 枢纽，三条出口分别通向执行、等待答复、拒绝槽；托管配置像封条压住可变参数 | 时间戳、answerer、不可放宽项 | 原生精确执行图 |
| P33 | 自主权随着环境靠近生产而逐级收窄 | 同一 agent 携带同一工件穿过 dev、staging、production 三个越来越窄的舱门，rollback 是从生产直达安全状态的粗回路 | 身份、环境权限、生产签名、演练记录 | 混合空间阶梯 |
| P34 | 发布证据到达生产门后，代码 owner 和发布 owner 分位签字 | PR+release evidence 被夹在独立生产门前；允许和拒绝都进入日志；两位 owner 的签名位于门两侧 | 双签名、拒绝理由、等待时间、失败率回流 | 原生场景式收口 |
| P35 | 生产事实不是从运维旁路返回，而是重新进入 intent | 生产现场产生指标、日志和事件，沿青绿受控回路进入诊断台，再被折成新的 intent.md；人的判断位于回路上方控制闸 | 多节点边界、诊断证据、owner 决定 | Image 2 连续叙事主体 |
| P36 | 指标越界只触发对应等级的动作，不直接触碰生产 | 控制带是主画面；曲线越过 1σ/2σ/3σ 后，旁边分别弹出记录、只读诊断、提议 PR/runbook 三种工件 | 阈值、触发时间、intent 回路 | 原生数据 + 工件动作 |
| P37 | 每周扫描只是触发器，发现项仍要进入同一条门禁路径 | 周期钟触发 findings 卷宗；普通 finding 走 PR，重大 finding 转为 intent；忽略项必须携带理由 | confidence、ignore reason、eval 回归 | 混合周期场景 |
| P38 | 夜间事件先诊断，处置仍停在服务 owner 的授权点 | 一条 incident 轨迹贯穿夜间告警、agent 诊断、intent、PR/runbook 门、恢复验证；channel 是旁侧证据卷而非主路径 | on-call 签名、MTTR、复发率、lessons 回写 | Image 2 连续事件主体 + 精确门禁外置 |

## 第三幕：让控制面成为运行时

| 页 | 三秒画面 | 主构图动作 | 可见痕迹 | 实现 |
|---|---|---|---|---|
| P39 | P10 的五个空插槽被真实控制逐个接通 | 同一工件链回归；身份、版本、证据、审批和强制门禁像五层透明审计描图覆盖在链上，能够沿线追到决定 | 签名、版本戳、证据包、审批事件、不可绕过点 | Image 2 工件拼贴 + 精确覆盖关系一体生成 |
| P40 | 越接近不可违反的规则，控制越需要确定性底座 | 两条控制阶梯不是左右卡片，而是共同压在同一条“不变量基座”上；推断性审查位于上层、可复核但不冒充证明 | 概率结果、确定性通过、复核记录 | 原生尺度型结构 |
| P41 | 三项原则像承重结构共同托住前 38 页 | 知识外置、正确路径、可执行反馈三根结构梁托住同一控制面；梁下回挂 intent/spec/plan、gate、tests/evals | 前文回指、缺一则结构倾斜 | 原生 Hero 结构 |
| P42 | 一边是当前能力图，一边是刚才发生的事件流，loop 贯穿两者 | 保留已批准精确思路，但强化 live graph 的动态装配感和 event stream 的时间质感 | 配置节点、输入、询问、决定、工具结果 | 原生精确控制面 |
| P43 | 一个事实从碎片中被收拢到唯一权威位置 | wiki、聊天、口述和旧文档碎片被编辑标注线收拢到权威文件；ADR 与 rejected notes 像侧册保存理由和负知识 | owner 线、版本、搜索命中、未选理由 | Image 2 工件拼贴 + 内生短标签 |
| P44 | 变更请求沿最省力的合法入口上行，而错误路径被物理封死 | patch→extension→seam→loop 形成参与地形；每一级入口有门、合同与检查半径，越级路径撞上封板 | owner、入口、contract、检查范围 | 原生路径地形 |
| P45 | 门禁正在被一组负例持续撞击和验证 | pre-execute→execute→post 是主执行管道；下方多种无效动作从不同角度撞击 pre-execute，deny/ask 的结果进入测试记录 | 负例名称、期望结果、实际结果、CI | 原生动作型管道 |
| P46 | Provider 被抽换，Consumer 的连接保持稳定 | Definition 是固定能力插座，Provider 像可抽换模块，Consumer 只连接合同；替换前后叠影显示连接未动 | 合同版本、替换记录、Consumer 不改 | 原生技术剖面 |
| P47 | 一次执行可以沿日志逐事件复原 | append-only 日志不是五个小框，而是一条展开的证据卷；model-visible input、tool result、asked/decided 成对落印，缺 answerer 的分支自动闭合失败 | 时间、版本、身份、成对审批 | 混合工件近景 |
| P48 | 四项治理决定最终收敛成一条采用路径 | 准入、替换、放行、事实重建四个决定围绕同一运行时剖面落位；底部工件→门禁→闭环是一条逐步点亮的路径 | registry、seam、gate、log | 原生综合决策图 |
| P49 | 开场的线性链已经真正闭合 | 保留大字与受控 loop，复杂机制退为纸面暗线；不添加新内容 | 六阶段名称和回流方向 | 原生，保留方向 |
| P50 | 一条真实价值流等待听众在四个空位上作决定 | 不再四卡并列；画一条具体但未填满的价值流轨道，在一次最慢交接处留下 artifact、gate、owner、feedback 四个编辑插槽 | 可填写线、试点指标、改造前后对照位 | 原生行动画布 |
