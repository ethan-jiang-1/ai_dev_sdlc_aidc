# 50 页 PPT 生产事实稿（v0.14）

本文件保存 v0.14 候选稿实际使用的页面标题与副标题，是当前 audience-facing 文案入口。讲点与证据口径仍以 `../03_outline/` 和 `../02_evidence/02-claim-ledger.md` 为准；当前状态、页面实现和下一步见 `../CURRENT.md`。

| 页 | 标题 | 副标题 |
|---|---|---|
| P1 | AI-Native 软件研发组织 | 从产品意图到生产运维，重建整条软件交付链 |
| P2 | 编码环节已经变快，为什么交付周期没有同步缩短？ | 先看等待时间去了哪里，而不是只看代码产量 |
| P3 | 编码耗时缩短之后，前后环节会决定端到端交付 | Anthropic 的判断：Code is no longer the bottleneck |
| P4 | 五层不是另一条流程，而是五种观察深度 | 表达意图、策展上下文、控制执行、运行反馈、编排节点 |
| P5 | 模型决定能做什么，harness 决定能否可靠地做成 | 平台统一控制基线，领域责任人掌握取舍与例外 |
| P6 | 编码不再是主要约束，压力会向三个方向转移 | 等待移到链条两侧，控制通道开始失配，治理例外从旁路不断增加 |
| P7 | 传统控制方式默认：主要工作由人执行 | 人执行、人交接、人签字，流程才能继续 |
| P8 | 产出速度一旦超过控制能力，结果只有排队或审查不足 | agent 放大产出，控制容量不会自动增长 |
| P9 | 机器执行可重复判断，人负责意图、风险、例外和授权 | 人从流水线工位退到控制台，判断仍然留下批准或拒绝痕迹 |
| P10 | 工件链只是审计骨架，还不是完整的审计能力 | 身份、版本、证据、审批和强制门禁仍是五个空插槽 |
| P11 | 六个阶段都要从“人盯流程”转向“系统执行控制” | 工件可交接、门禁能执行、责任有人担、结果能回流 |
| P12 | 后面每个阶段，都回答同样四个问题 | 一张记录纸贯穿六阶段，五层只是旁边的深度标尺 |
| P13 | 工件把六个阶段接成一条能够回流的闭环 | 每次交接都展开上一份工件，再折成下一份 |
| P14 | 规划先解决：原始意图怎样不丢失 | 整理是让别人接得住，不是替提出者改写意思 |
| P15 | 用 intent.md 留住需求提出者的原意 | 来源、版本、责任人和开放问题必须同屏可见 |
| P16 | 意图既要能被批准，也要能被度量 | 退回必须带着理由回到开放问题；放行才进入设计 |
| P17 | 动手构建之前，先让约束和冲突可见 | 品牌、安全、合规和体验在同一份 spec 上叠图 |
| P18 | 形成 spec.md 时，就把政策约束施加进去 | intent 与版本化 skills 同时进入制图台 |
| P19 | 规格要带着风险和责任归属进入构建 | 产品责任人处理取舍，政策责任人处理例外 |
| P20 | 构建阶段不只要生成代码，还要把执行圈住、拦住、看清 | 圈住执行边界，拦住违规动作，看清事实轨迹 |
| P21 | 先审 plan.md，再允许修改代码 | 四段计划通过审查后，代码区的锁才打开 |
| P22 | 团队规则要写进 agent 每次都能读到的文件 | 权威规则常驻，条件政策按任务触发，失败样本继续改规则 |
| P23 | 必须遵守的规则，要由 hooks 自动执行 | 违规动作会被挡落，并留下拒绝原因与时间 |
| P24 | 并行会话越多，隔离和责任归属越重要 | 三条工作线互不踩踏，也都能追到启动者 |
| P25 | 平台维护共同基线，工程师对具体改动负责 | 共同护栏包围执行环境，但不吞掉改动责任 |
| P26 | 测试既要验证产品改动，也要验证 harness 配置 | 两类证据在同一道合并门前汇合；缺一份，都不能算完成 |
| P27 | agent 不能只说“完成了”，必须留下验证证据 | 失败、修改、通过是一段可复核的短循环 |
| P28 | 规则、skills 和 hooks 也要做回归测试 | 真实任务样本进入实验台，配置一变就重新运行 |
| P29 | QA 要从逐单执行，转向维护验证系统 | 产品证据与配置证据共同决定能否合并 |
| P30 | agent 可以提出动作，生产执行必须另行授权 | 生产侧保持断开；执行当下授权，桥才短暂闭合 |
| P31 | 写代码与批准发布，必须由不同角色承担 | 自批支路被剪断，机器检查和人的判断叠在同一份 PR 上 |
| P32 | 生产边界必须封在执行管道里 | allow、ask、block 是三个真正不同的执行出口 |
| P33 | agent 的权限止步于生产门禁 | 越接近生产，自主权越窄；回滚路径反而要更直接 |
| P34 | 生产门禁必须独立于代码生成 | 代码责任人与发布责任人分位签字，允许和拒绝都入日志 |
| P35 | 生产事实要沿同一条受控路径回流 | 事实先进入诊断，再形成新的 intent；人的判断始终在闭环之上 |
| P36 | 只有指标越界，才触发 agent 进入诊断 | 1σ 记录，2σ 只读诊断，3σ 才能提议 PR 或 runbook |
| P37 | 定时扫描发现的问题，也要走同一套门禁 | 普通 finding 走 PR，重大 finding 先变成新的 intent |
| P38 | 自动诊断可以先开始，处置授权仍由服务责任人掌握 | 夜间事件从告警走到恢复，授权点始终清楚可见 |
| P39 | 工件链补齐五项控制，才能真正支持审计 | 同一条链上必须追到身份、版本、证据、审批和强制门禁 |
| P40 | 机器负责可重复判断，人负责结合语境作决定 | 确定性检查托底，推断性审查补语境，两类决定都要留痕 |
| P41 | DSH 展示三项控制原则怎样进入运行时 | 知识外置、正确路径、可执行反馈共同托住控制面 |
| P42 | 共享控制面要同时说清：现在由什么组成，刚才做过什么 | 能力图描述当前状态，事件流还原刚才发生的事实 |
| P43 | 一个事实只认一个权威来源 | 事实归入权威文件，理由进入 ADR，未选方案也留下记录 |
| P44 | 正确路径应该最省力，不正确的路径应该走不通 | patch、extension、seam、loop 各有入口、合同与检查半径 |
| P45 | 门禁只有经过负例验证，才值得信任 | 无效动作持续撞击 pre-execute，结果进入测试记录 |
| P46 | 共享控制面统一能力合同，不统一所有后端 | Provider 可以抽换，Consumer 的连接保持不动 |
| P47 | 输入、工具结果和审批，都必须能从日志还原 | asked 与 decided 成对落印，无人作答时默认关闭 |
| P48 | 先让工件可读，再让门禁可信，最后运行闭环 | 准入、替换、放行、事实重建收敛成一条采用路径 |
| P49 | 代码不再是瓶颈，流程才是 | 转型不是追求更多代码，而是让整条 SDLC 能可靠运行 |
| P50 | 从最慢的一次交接开始 | 为一条真实价值流补齐一个工件、一道门禁、一位责任人和一个反馈指标 |

朗读与一致性检查：标题均可作为现场判断直接说出口；英文只保留产品名、文件名和精确机制名；六阶段、工件、门禁、责任人与反馈的用词保持一致。
