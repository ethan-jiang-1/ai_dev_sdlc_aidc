# 50 页 PPT 生产事实稿（v0.12）

> 历史基线：本文件记录完整 50 页首次生产时的 audience-facing 文案。v0.13–v0.14 已在成片中收紧部分副标题；当前版本、当前成片和下一步统一见 `../CURRENT.md`，不要把本文件单独当作 v0.14 当前态。

本文件只保存面向听众的上屏文案。讲点与证据口径仍以 `../03_outline/` 和 `../02_evidence/02-claim-ledger.md` 为准。

| 页 | 标题 | 副标题 / 主体短句 |
|---|---|---|
| P1 | AI-Native 软件研发组织 | 从产品意图到生产运维，重建整条软件交付链 |
| P2 | 编码环节已经变快，为什么交付周期没有同步缩短？ | 先看等待时间去了哪里，而不是只看代码产量 |
| P3 | 编码耗时缩短之后，前后环节会决定端到端交付 | Anthropic 的判断：Code is no longer the bottleneck |
| P4 | 五层不是另一条流程，而是五种观察深度 | 表达意图、策展上下文、控制执行、运行反馈、编排节点 |
| P5 | 模型决定能做什么，harness 决定能否可靠地做成 | 平台统一控制基线，领域责任人掌握取舍与例外 |
| P6 | 编码不再是主要约束，压力会向三个方向转移 | 等待转移、控制失配、治理例外增加 |
| P7 | 传统控制方式默认：主要工作由人执行 | 人执行、人交接、人签字，流程才能继续 |
| P8 | 产出速度一旦超过控制能力，结果只有排队或审查不足 | agent 放大产出，控制容量不会自动增长 |
| P9 | 机器执行可重复判断，人负责意图、风险、例外和授权 | agent 执行、工件交接、机器门禁、人作判断 |
| P10 | 工件链只是审计骨架，还不是完整的审计能力 | intent → spec → plan → diff+tests → PR+review → incident |
| P11 | 六个阶段都要从“人盯流程”转向“系统执行控制” | 工件可交接、门禁能执行、责任有人担、结果能回流 |
| P12 | 后面每个阶段，都回答同样四个问题 | 留下什么工件？哪道门禁必须执行？谁作最后决定？结果怎样回到下一轮？ |
| P13 | 工件把六个阶段接成一条能够回流的闭环 | 规划 → 设计 → 构建 → 测试 → 发布 → 运维 → 下一轮意图 |
| P14 | 规划先解决：原始意图怎样不丢失 | Prompt 镜头关注表达，不把规划简化成一句提示词 |
| P15 | 用 `intent.md` 留住需求提出者的原意 | 问题、结果、影响范围、约束、开放问题 |
| P16 | 意图既要能被批准，也要能被度量 | 工件：intent｜门禁：验收｜责任人：产品｜反馈：通过率与返工 |
| P17 | 动手构建之前，先让约束和冲突可见 | Context 不是资料堆积，而是可版本化、可路由的约束 |
| P18 | 形成 `spec.md` 时，就把政策约束施加进去 | intent + versioned skills → spec |
| P19 | 规格要带着风险和责任归属进入构建 | 工件：spec｜门禁：风险与冲突｜责任人：产品+政策｜反馈：返工率 |
| P20 | 构建阶段不只要生成代码，还要把执行圈住、拦住、看清 | 圈住执行边界，拦住违规动作，看清事实轨迹 |
| P21 | 先审 `plan.md`，再允许修改代码 | files、order、risks、proof |
| P22 | 团队规则要写进 agent 每次都能读到的文件 | `AGENTS.md` 保存共同约定，`skills/` 按条件加载政策 |
| P23 | 必须遵守的规则，要由 hooks 自动执行 | 保护路径、格式与 lint、凭据检查 |
| P24 | 并行会话越多，隔离和责任归属越重要 | 每条工作线都有独立环境、日志和启动者 |
| P25 | 平台维护共同基线，工程师对具体改动负责 | 工件：plan+diff+tests｜门禁：沙箱+hooks｜反馈：返工与计划吻合度 |
| P26 | 测试既要验证产品改动，也要验证 harness 配置 | Guides 在执行前给方向，Sensors 在执行后返回事实 |
| P27 | agent 不能只说“完成了”，必须留下验证证据 | 写代码 → 失败测试 → 修改 → 通过证据 |
| P28 | 规则、skills 和 hooks 也要做回归测试 | 用真实任务组成 eval suite，配置一变就运行 |
| P29 | QA 要从逐单执行，转向维护验证系统 | test+eval evidence｜合并阈值｜QA+配置责任人｜首次通过率与失败趋势 |
| P30 | agent 可以提出动作，生产执行必须另行授权 | 授权发生在执行那一刻，而不是生成方案时 |
| P31 | 写代码与批准发布，必须由不同角色承担 | 机器复用检查，人的判断集中在意图、风险和例外 |
| P32 | 生产边界必须封在执行管道里 | allow / ask / block；权限、沙箱和凭据由托管配置守住 |
| P33 | agent 的权限止步于生产门禁 | 开发自主度较高，预发布收紧，生产必须由发布责任人授权 |
| P34 | 生产门禁必须独立于代码生成 | PR+发布证据｜生产授权｜代码+发布责任人｜等待与变更失败率 |
| P35 | 生产事实要沿同一条受控路径回流 | 自动触发诊断，不等于自动获得处置权 |
| P36 | 只有指标越界，才触发 agent 进入诊断 | 1σ 记录｜2σ 只读诊断｜3σ 提议 PR 或 runbook |
| P37 | 定时扫描发现的问题，也要走同一套门禁 | finding → PR；重大问题先形成新的 intent |
| P38 | 自动诊断可以先开始，处置授权仍由服务责任人掌握 | 工件：事件+诊断｜门禁：分诊+授权｜反馈：恢复时间与复发率 |
| P39 | 工件链补齐五项控制，才能真正支持审计 | 身份、版本、证据、审批、不可绕过的门禁 |
| P40 | 机器负责可重复判断，人负责结合语境作决定 | 确定性检查托底，推断性审查补充语境，两类决定都要留痕 |
| P41 | DSH 展示三项控制原则怎样进入运行时 | 知识外置、正确路径、可执行反馈 |
| P42 | 共享控制面要同时说清：现在由什么组成，刚才做过什么 | 插件图描述能力，事件流记录事实，loop 在两者之间运行 |
| P43 | 一个事实只认一个权威来源 | 当前事实写进权威文件，决策理由写进 ADR，未选方案也要留下记录 |
| P44 | 正确路径应该最省力，不正确的路径应该走不通 | patch → extension → seam → loop；每层都有入口、合同和检查范围 |
| P45 | 门禁只有经过负例验证，才值得信任 | 不只测试允许什么，也要反复证明无效动作确实会被拒绝 |
| P46 | 共享控制面统一能力合同，不统一所有后端 | Definition + Provider + Consumer；换后端，Consumer 不跟着改 |
| P47 | 输入、工具结果和审批，都必须能从日志还原 | 只追加日志；asked / decided 成对；无人作答时默认关闭 |
| P48 | 采用顺序只有一条：先让工件可读，再让门禁可信，最后运行闭环 | 准入、替换、放行、事实重建，各有明确机制 |
| P49 | 代码不再是瓶颈，流程才是 | 转型不是追求更多代码，而是让整条 SDLC 能可靠运行 |
| P50 | 从最慢的一次交接开始 | 为一条真实价值流补齐一个工件、一道门禁、一位责任人和一个反馈指标 |

朗读检查：标题均能作为现场完整判断直接说出口；英文只保留产品名、文件名和精确机制名；六阶段、四问、工件、门禁、责任人与反馈的用词全篇一致。
