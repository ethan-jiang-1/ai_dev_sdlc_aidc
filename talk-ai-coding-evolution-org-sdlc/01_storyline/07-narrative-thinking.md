## 二、被什么启发（关键触点）

1. **「Code is no longer the bottleneck」**（Anthropic）——软件价值流钩子：当构建被显著压缩、交付却没有同步加速，慢点已经转到流程与治理。这句成为开场诊断 + 收尾 slogan 的来源；具体是否成立由听众用自身数据验证。
2. **「Agents follow enforced gates far more reliably than prose conventions」**（DSH FAQ 07）——确定性优先的最硬表达，由此确定“机器执行可重复判断的规则，人负责结合语境作决定”。
3. **DSH 的三条腿**（知识外置 / 正确路径 / 可执行反馈）——这是「DSH 怎么帮流程」的钥匙，也成为整场的**统一命题**（见下）。
4. **「工件链是审计的骨架」**（playbook 的 committed artifact chain）——`intent→spec→plan→diff+tests→PR+review→incident` 提供贯穿主线；身份、版本、证据、审批和不可绕过的 gate 让它承担审计。
5. **五层 = 深度，六阶段 = 宽度**——两套素材本来正交，但反复试下来，**不能让任何一轴吞掉另一轴**（见演化史）。

## 三、叙事思路的演化（v0.1 → v0.5，为什么最后是「主轴 + 引子」）

| 版 | 思路 | 问题（用户反馈） |
|---|---|---|
| v0.1 | harness 单焦点：「组织唯一该集中建设的是 harness」+ 23 页 | 被 playbook 重定调：对象扩为软件交付链（这是历史口径，v0.7 已收紧为从产品意图到生产运维） |
| v0.2 | 全 SDLC：六阶段做主轴，五层挤成「深轴」 | **harness 出现太晚**；**Loop/Graph/DSH 关系不大**——五层被边缘化 |
| v0.3 | 五层各成一幕 + 三层（任务/平台/治理）概括 | **Prompt/Context 被吞进「任务层」**——五层变三层，前两层不见了 |
| v0.4 | 五层各成一幕（谁都不并） | **强扭**——SDLC 这个好轴被放弃了，五层硬凑成章 |
| **v0.5** | **SDLC 六阶段是主轴，五层 + DSH 各在自然接点作「引子」插入** | 定调，不再反复 |
| **v0.6** | **在固定 50 页内收紧因果：起始诊断 → 可执行 SDLC → 四问贯穿六阶段 → 共享控制面** | 不改主轴，解决「三套素材并列」和过强口径 |
| **v0.7** | **目录更名为 `talk-ai-coding-evolution-org-sdlc/`，对象收紧为软件 SDLC 跨职能组织** | 「组织」有多种；用软件价值流边界防止结论泛化，为其他组织类型保留平行 talk 空间 |
| **v0.8** | **50 页不再改轴，统一白底，先过中文编辑和四张视觉样片** | 内容持续增加时，必须用稳定容器、原生中文和统一视觉系统防止故事线与页面职责漂移 |

**v0.5 为什么对**：SDLC 六阶段是软件价值流最自然的轴（宽度）；五层提供深度镜头；DSH 提供参考实现。三者各司其职，谁也不吞谁。

**v0.6 收紧了什么**：

1. 「代码不再是瓶颈」从普适事实改成起始诊断，由听众用自己数据验证。
2. 中心命题收到“可执行 SDLC”：工件可交接、门禁能执行、责任有人担、结果能回流。
3. 六阶段不再以 play 清单并列，每个阶段都回答四问：留下什么工件、哪道门禁必须执行、谁作最后决定、结果怎样回到下一轮。
4. 五层不再声称是某一阶段的「本质」，只负责解释外置与控制深度。
5. DSH 从答案改为参考实现；第三幕的任务是解释共享控制面如何工程化。

**v0.7 定调了什么**：

1. 「组织」不再是泛化对象；本 talk 只讨论软件 SDLC 上的产品、架构、平台、开发、QA、安全、发布与 SRE / 运维。
2. 范围从「产品意图」到「生产运维」，不使用易与一般企业实施混淆的「从产品到实施」口径。
3. 不外推到销售、市场、客服、财务、人力或通用组织设计；若未来要讲，应当新建平行目录与独立故事线。

**v0.8 定调了什么**：

1. 50 页是已锁定的生产容器，不再用新增页数消化新增内容；新增材料必须回到既定页面职责中取舍。
2. 50 页统一使用纸白或极浅冷灰底，不用黑白交替制造节奏；节奏来自标题尺度、局部石墨结构、线宽、疏密和留白。
3. 所有上屏中文从意思出发重写，标题必须能直接讲出口；阶段统一写规划、设计、构建、测试、发布、运维，四问统一写工件、门禁、责任人、反馈闭环。
4. GPT Image 2 按页判断，不只是封面插图工具。它可以承担图文一体的视觉主体、场景、材质、空间关系和整体构图，但关键结论与精确关系必须保持可控、可编辑、可核对。
5. 先做 P1、P8、P20、P42 四张样片，分别验证世界观、容量失配、harness 母图和控制面精密度；用户确认前不铺完整 50 页。

## 四、关键决策与理由

1. **对象 = 软件 SDLC 上的跨职能研发与交付组织**（CTO/产品/架构/平台/开发/QA/安全/发布/SRE），不是 OPC、不是一般企业组织论——每页落「这条软件价值流该建什么/谁负责/怎么治理/怎么度量」。
2. **A 档单场加长**（75–90 min，**50 页已定**）——总页数作为稳定边界，内容 REVIEW 只在边界内调整页面职责。
3. **独立成篇**——不依赖、不承接 `deck_ai_sdlc_keynote`（听众不同：那边是战略隐喻，这边是操作级转型）。
4. **题目**：AI-Native 软件研发组织：从产品意图到生产运维的 SDLC 转型之道；**slogan**：代码不再是瓶颈，流程才是。
5. **harness 开场先立住（P5）**，Build/Test/Deploy 再展开——它是临界点，不能晚出。
6. **DSH 三条腿保留在第三幕**（P41–P47）——它是「知识外置 / 正确路径 / 可执行反馈」的参考实现，不是唯一选型；所有机制必须回指第二幕的组织问题。
7. **工具不可知命名**：`CLAUDE.md` → `AGENTS.md`、`.claude/skills` → skills 目录、`.claude/agents` → subagents——随大流，不绑定 Claude Code。

## 五、统一命题（一句话焊点）

> 当编码不再是主要瓶颈，组织要把整条 SDLC 重建成可执行的交付系统：工件可交接、门禁能执行、责任有人担、结果能回流；
> 五层说明控制深度，DSH 作为共享 harness 控制面的参考实现。

这一句把“六阶段说明改造发生在哪里、五层说明控制做到多深、DSH 说明怎样进入运行时”连成一条线。三项原则正好与之对应：知识外置形成工件链，正确路径明确责任归属，可执行反馈把规则变成门禁。

## 六、为什么采用“Image 2 视觉主体 + PowerPoint 文字层”

这不是“图片页”和“文字页”的二选一。GPT Image 2 擅长把材质、空间、视觉隐喻、局部文字和构图揉成一个整体，适合建立复杂图文表达的视觉主体；PowerPoint 擅长稳定控制字体、字号、位置、颜色、术语和跨页节奏。两者各自承担最可靠的部分：

1. 每页先判断要讲清的是场景、关系、过程、对比还是证据，再选择不用 Image 2、用作视觉底图，或用作图文一体的视觉主体。
2. `title`、`subtitle`、`kicker`、`callout` 和关键结论由 PowerPoint 原生渲染；生成资产必须提前留出文字安全区。
3. Image 2 可以把局部说明、标签、界面字样与场景合成为丰富的图文主体；这些主体内嵌文字可以承担局部解释，但必须逐字核对。主标题、副标题、眉题、强调句和固定术语仍由 PowerPoint 统一渲染。
4. 工件顺序、门禁位置、责任归属、因果方向、数字、引用、日志、拓扑和关键论证保持为 PowerPoint 或 Graphviz 可编辑结构；Image 2 主要强化原生图元难以表达的感知关系。
5. 一页只有一个主构图。混合生产的目标是让图像与文字共同完成一个判断，而不是在图旁边再堆一组说明卡片。

v0.8 的 P1 验证了 Image 2 与 PowerPoint 可以混合生产，也暴露了两点：封面并没有足够的表达收益来支撑大幅生成图，生成资产自带的近似白底也会与固定画布产生色差。v0.9 因此把 P1 改为原生主体，把 Image 2 的主要验证转到更需要丰富图文表达的 P8，并用 P20 继续验证混合主体。

## 七、服务商实验为什么这样选

从工作区 `.env` 中发现多个 GPT Image 2 入口后，用同一条低成本提示、同一模型名、尺寸和质量档位先测连通性，再比较约束遵循、留白、轮廓、材质和返工风险。结果是：Packy 在正确尺寸、克制构图和标题安全区上最好，选作主入口；MICU 可用但青绿回路偏强、留白较弱，作为备用；Duck 尺寸遵循不稳定；Duck Fast 没有可用通道；APIMART 当前响应不能由现有脚本保存成 PNG。实验过程、提示词和样图都在 `_asset/experiments/imagegen-v0.8/`，密钥不落盘。
