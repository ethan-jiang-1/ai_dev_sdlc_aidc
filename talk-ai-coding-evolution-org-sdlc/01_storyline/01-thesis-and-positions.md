# 核心论点与立场（v0.6 内容 REVIEW）

> 详细论证见 [`00-storyline-map.md`](./00-storyline-map.md)。对象 = 软件研发与交付组织，独立成篇。

1. **起始诊断：瓶颈会转移**。当 Build 被 agent 明显压缩、端到端 lead time 却没同步下降，慢点会移向 plan / review / test / deploy，旧控制的排队与治理成本随之暴露。这是 Anthropic 的观点与本 talk 的诊断入口，需用组织自身数据验证。
2. **中心命题：转型对象是交付系统**。AI-native SDLC 不是给六阶段各塞一个 AI 工具，而是把整条链重建成「工件可交接、gate 可执行、owner 可问责、feedback 可回流」的运行系统。
3. **工件链是审计的骨架，不是自动等于合规**。`intent → spec → plan → diff+tests → PR+review → incident` 只有同时记下身份、版本、证据、审批和不可绕过的 gate，才能从交接链变成审计链。
4. **人守判断 gate，机器守机械 gate**。测试 / lint / 类型 / schema / policy check 优先做成确定性门禁；人的注意力放在意图、风险、例外与生产授权。提议权可以下放给 agent，执行权在执行时独立授权。
5. **组织原则：共享控制面，分布领域知识**。Prompt / Context 由懂业务的一线 owner 负责；沙箱、权限、工具准入、门禁、观测与审计由平台集中建设；Loop / Graph 的授权与编排规则由治理定义。
6. **采用顺序：先工件，再 gate，最后关 loop**。没有可交接的工件，loop 无事实可读；没有可执行 gate，loop 只会更快放大错误。
7. **三套素材各司其职**：六阶段是转型范围；五层是观察「外置与控制深度」的镜头，不把某阶段简化成某一层的「本质」；DSH 是把知识外置、正确路径和可执行反馈做成 runtime 的参考实现，不是唯一选型。
8. **带走原则**：代码不再是瓶颈，流程才是；转型从自己链上最慢的交接开始。

## 一句话主线（源自 00-storyline-map）

当 Build 不再是瓶颈，组织要重建的是整条 SDLC：让每阶段留下可交接的工件，每次转换经过可执行的 gate，每个判断有 owner，每个结果能回流成下一次 intent。
