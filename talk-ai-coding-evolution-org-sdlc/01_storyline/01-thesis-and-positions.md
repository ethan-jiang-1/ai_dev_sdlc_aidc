# 核心论点与立场（v0.7 · 软件 SDLC 内容 REVIEW）

> 详细论证见 [`00-storyline-map.md`](./00-storyline-map.md)。对象 = 软件研发与交付组织，独立成篇。

1. **起始诊断：瓶颈会迁移**。当 Build 被 agent 明显压缩、端到端 lead time 却没同步下降，慢点会移向 plan / review / test / deploy，旧控制的排队与治理成本随之暴露。这是 Anthropic 的观点与本 talk 的诊断入口，需用听众自己的价值流数据验证。
2. **中心命题：转型对象是软件交付系统**。AI-native SDLC 不是给六阶段各塞一个 AI 工具，而是把整条链重建成「工件可交接、gate 可执行、owner 可问责、feedback 可回流」的运行系统。
3. **交接必须变成可执行合同**。`intent → spec → plan → diff+tests → PR+review → incident` 提供交接与审计的骨架；身份、版本、证据、审批和不可绕过的 gate，才让这条链具备可追溯与可问责能力。
4. **控制容量必须跟上产出容量**。测试 / lint / 类型 / schema / policy check 优先做成确定性 gate；人的注意力保留给意图、风险、例外与生产授权。agent 可以提出动作，执行权在动作真正发生时独立授权。
5. **运行模型是共享控制面、分布领域知识**。平台提供沙箱、权限、工具准入、门禁、观测与审计的共同基线；产品、架构、服务与政策 owner 负责 intent、context、取舍与例外。采用顺序固定为先工件、再 gate、最后关 loop。

六阶段、五层与 DSH 不是三套竞争框架：六阶段界定软件 SDLC 的改造范围；五层是观察外置与控制深度的能力镜头；DSH 是把知识外置、正确路径和可执行反馈做成 runtime 的参考实现，不是唯一选型。

带走原则：**代码不再是瓶颈，流程才是；转型从自己链上最慢的一次交接开始。**

## 一句话主线（源自 00-storyline-map）

当 Build 不再是瓶颈，组织要重建的是整条 SDLC：让每阶段留下可交接的工件，每次转换经过可执行的 gate，每个判断有 owner，每个结果能回流成下一次 intent。
