# 故事线总图（v0.7 · 软件 SDLC 定调 · 固定 50 页）

> **对象**：软件 SDLC 上的跨职能研发与交付组织——从产品意图、需求与设计，到构建、测试、发布与生产运维。
> **题目已定**：AI-Native 软件研发组织：从产品意图到生产运维的 SDLC 转型之道。**slogan**：代码不再是瓶颈，流程才是。
> **范围红线**：只讨论软件价值流和 SDLC 控制系统，不外推到销售、市场、客服、财务、人力或一般企业组织设计。
> **篇幅档位 A**：单场加长 Keynote（75–90 min，**50 页已定**）。**独立成篇**（不承接 `deck_ai_sdlc_keynote`）。
> **已锁定结构**：**SDLC 六阶段是主轴**；五层（Prompt→Context→Harness→Loop→Graph）作深度镜头，
> DSH 作参考实现，均在自然接点嵌入，不另起一条主线。本轮只在 50 页内收紧命题、页面职责与转场。

## 沟通任务

> 到结束时，CTO，以及平台、产品、QA、安全、发布和运维负责人，应该能够共同选出一条价值流试点，
> 重新说清它留下什么工件、经过哪道门禁、由谁作决定、结果怎样回到下一轮；因为只加速编码，会把瓶颈和治理成本推向代码两侧，并不会自动改善端到端交付。

## 一句话主线

当编码不再是主要瓶颈，组织要重建的是整条 SDLC：**每个阶段留下可交接的工件，每次转换经过真正执行的门禁，
每项判断都有人负责，每个结果都能回到下一轮意图**。六阶段说明改造范围，五层说明控制深度，
DSH 说明知识外置、路径明确和反馈可执行怎样进入共享 runtime。

## 5–8 分钟口述主线（内容锁验收稿）

这场 talk 从一个需要听众自己验证的现象开始：agent 已经显著缩短了编码时间，端到端交付是否也同步变快？如果没有，就不要再只看代码生成速度，而要把一条真实的软件价值流拆开来看：需求等了多久，第一次审查等了多久，测试证据补了几轮，生产审批排了多久，故障信息又花了多久才回到下一次规划。Anthropic 把这个变化概括为「Code is no longer the bottleneck」。这里不把它当成所有组织都成立的事实，而把它当成一个诊断入口：编码一旦不再是主要约束，瓶颈就会向前后环节迁移。

问题在于，传统 SDLC 的控制方式是围绕「代码稀缺、步骤主要由人执行」建立的，默认处理的是人力规模的变更与人速交接，所以会议、文档提醒、逐行检查和阶段闸门还能维持。当 agent 把产出容量突然放大，控制容量却没有一起扩大，系统只会出现两种结果：一种是更多工作排队，交付并没有更快；另一种是为了追赶速度而减少检查，风险和返工转移到下游。于是 AI-native 转型的对象不能只是编码工具，而必须是整套软件交付系统。

这套系统可以用四个问题重新设计：这一阶段留下什么可交接的工件？哪一道规则必须成为真正执行的门禁？谁对不能机械判断的价值、风险和例外作最后决定？什么反馈能够证明这次改造确实改善了交付？工件让接手的人不必重新猜测上游意图；门禁把可以重复判断的规则从文字提醒变成机器关卡；责任人保留人的判断与问责；反馈则让结果不只停在报表里，而能回到下一轮意图。四个问题合起来，才构成一条可执行、可追溯、能够持续学习的软件价值流。

沿六阶段看，改造不是给每个环节各塞一个 AI 助手。规划要把模糊需求收成带取舍和验收边界的 intent；设计要把约束、政策和冲突收成当时有效的 spec；构建要先有 plan，并在受控环境中执行；测试不只验证产品改动，也验证 harness 和门禁本身是否仍然有效；发布要把 agent 提出动作的权力与生产执行权分开，在动作发生时重新授权；运维要让事件、扫描和生产事实沿同一条受控路径回流，重新形成 intent，再经过相同的门禁。这样，六个阶段不再是六段松散流程，而是由工件连接、由反馈闭环的一套运行系统。

五层模型在这里不另起一条故事线。Prompt、Context、Harness、Loop、Graph 只是五种观察能力与控制深度的镜头：意图有没有说清楚，事实有没有给对，执行有没有被圈住、拦住、看清，结果能不能安全回流，多个执行单元能不能在明确合同下协作。它们不等于五个团队，也不与六阶段一一对应。真正的组织原则是：控制面共享，领域知识分布。平台提供沙箱、权限、工具准入、门禁、观测和审计的共同基线；产品、架构、服务与政策责任人继续掌握 intent、context、取舍和例外；治理层定义不可绕过的授权与审计规则。

DSH 在最后出现，不是作为唯一答案，而是作为这套控制面可以被工程化的参考实现。它用知识外置减少部落知识，用明确路径把变更送到正确的扩展点，用可执行反馈证明无效动作确实会被拒绝，再用 capability seam 和 append-only log 支撑替换、审批与事实重建。它要证明的不是某个产品更强，而是制度能够进入 runtime：机器负责可重复判断的规则，人负责结合语境作决定，两类行为都留下可追溯证据。

因此采用顺序也很明确：先让一次交接留下可读工件和明确责任人，再把必须成立的规则做成门禁；等事实可读、门禁可信之后，最后才让闭环自动运行。结尾不要求听众一次重做整个 SDLC，只要求从一条软件价值流里找出最慢的交接，为它补齐一个工件、一道门禁、一位责任人和一个反馈指标。这样，「代码不再是瓶颈，流程才是」就不只是一句口号，而成为能够用真实变更和真实数据验证的试点。

## 每一幕的要点

### 开场（钩子 + 五层预告 + harness 引子先立住）
- 问题：**如果**组织的编码环节已经显著加速，端到端交付为什么没有同步变快？让听众先用自己的交付周期和排队时间对照，不虚构“翻倍”数据。
- 钩子：**Code is no longer the bottleneck**（Anthropic，标注来源）。
- **P4 五层预告**：五层是包含而不替换的能力叠层——模型变强一步，工程重心往外移一步，每一步把前一步包进来；今天承重的是 harness，loop 和 graph 是把它用得更稳的进阶用法。五层同时仍是后面观察「外置与控制深度」的镜头，不是第二条故事线。
- **P5 harness 引子（先立住）**：模型决定能做什么，harness 决定能否可靠地做成；组织集中建设共享控制面，同时让一线责任人继续掌握领域 intent 与 context。

### 第一幕：为什么整条 SDLC 要转型
- 编码加速后会出现三个后果：瓶颈向前后转移、旧控制失效、治理成本上升。
- 传统 SDLC 的控制假设：每一步都是人做的；逐行 review、阶段闸门跟不上 agent 产出。
- 转型的本质：从“人启动、人交接、人逐项检查”，转向“agent 执行、工件交接、机器执行确定性门禁、人作语境判断”。
- 贯穿全场的工件链是 `intent→spec→plan→diff+tests→PR+review→incident`；它提供审计骨架，身份、版本、证据、审批和不可绕过的门禁让这条链具备追溯与问责能力。
- 用一张总表呈现六个阶段从传统控制到 AI-native 控制的变化。

### 第二幕：六阶段转型（同一组问题，逐段回答）

每个阶段都明确回答四问：**留下什么工件？哪道门禁必须执行？谁作最后决定？什么反馈证明改造有效？**

- **规划（Prompt 镜头）**：把模糊需求变成可交接的 `intent.md`，产品责任人对价值和取舍负责。
- **设计（Context 镜头）**：把政策、标准与冲突变成带版本的 `spec.md` 和待处理事项清单，政策责任人处理例外。
- **构建（Harness 镜头）**：把执行圈住、拦住、看清；`plan.md`、知识文件、hooks 和隔离环境共同缩小影响范围。
- **测试（Sensors / Loop 镜头）**：同时验证产品改动和 harness 配置；QA 从逐单执行测试，转为维护验证系统。
- **发布（Harness 镜头）**：用职责分离、执行时授权和环境分级，确保 agent 的权限止步于生产门禁。
- **运维（Loop / Graph 镜头）**：只有确定性指标越界时才调用 agent，结果写回 `intent.md` 并经过同一套门禁；Graph 只作为新兴编排镜头，不宣称已经成熟。

### 第三幕：共享控制面 + DSH 参考实现
- 先说清工件链怎样具备审计能力：身份、版本、证据、审批、不可绕过的门禁和可重建事实缺一不可。
- 共享控制面不等于统一所有业务：平台统一权限、工具准入、门禁、观测和审计，领域责任人继续掌握 intent、context 和例外。
- **DSH 参考实现的三条腿**：知识外置、正确路径、可执行反馈。它证明这些不只能写成制度，也能做成 runtime 合同。
- 用插件图 / 事件流 / loop、capability seam、enforced gate、append-only log 分别回答「现在由什么组成 / 刚才做过什么 / 如何替换 / 如何放行 / 如何重建事实」。
- 落地顺序只留一条：**先让工件可读，再让门禁可信，最后运行闭环**。插件数、star 和可替换率不进入核心故事，避免把组织决策带向生态热度和实现细节。

### 收尾
- 带走一句：**代码不再是瓶颈，流程才是。**
- 回到开场：先用数据找到自己链上最慢的一次交接，选一条价值流，补齐一个工件、一道门禁、一位责任人和一个反馈指标。

## 口径红线

- 前三层成熟，Loop / Graph 新兴（沿用 `-opc`；本 talk 只用它们检查反馈与编排的控制深度，不讲成既定生产范式）。
- 五层的「层」指包含（subsume）而非并列或换代：context 是 prompt 的自然演进，harness 是 context 的具体形式，loop 每次迭代实例化一个 harness，graph 的每个节点各跑各的 harness；不把五层与 SDLC 六阶段画成并置或映射，也不讲成五门并列学科或五代替换。
- 「代码不再是瓶颈」是 Anthropic 论点，引用标注来源；playbook 是 Claude 视角，机制讲透、产品名不唯一。
- 「代码不再是瓶颈」在叙事中作诊断假设；不虚构「代码产出翻倍 / 交付不变」数据，让听众用自身数据验证。
- 不把工件链直接说成审计链；严格口径是“工件链提供审计骨架，补齐身份、版本、证据、审批和不可绕过的门禁之后，才具备追溯与问责能力”。
- DSH 原生机制不是 MCP；说 `ctx.llm`、`ctx.tools`、capability seam、plugin。
- DSH 作参考实现，不讲成唯一产品选型或组织转型的必要前置。
- DSH 命名随大流：`CLAUDE.md` 概念 → `AGENTS.md`；`.claude/skills` → skills 目录；`.claude/agents` → subagents。机制讲透，不绑定 Claude Code。
