# 五层叠加 · 软件 SDLC 能力读法（v0.7 · 深度镜头的理论底）

> 本文件解释 Prompt / Context / Harness / Loop / Graph 如何作为五个**能力与控制深度镜头**，检查软件 SDLC 各阶段的外置程度、运行边界与反馈能力。
> 它们不与 Plan / Design / Build / Test / Deploy / Maintain 一一对应，也不等于五个岗位、五支团队或五个组织层级。

> 源：`../_reference/rawdata_ai-coding-evolution-final/final_v4.md`。与 `-opc` 的个人深度标尺相比，本 talk 只问：
> 当这些能力进入跨职能软件价值流时，哪部分由领域 owner 掌握，哪部分应成为平台共同基线，哪部分需要治理规则。

## 先把「层」说死：包含，不是并列，也不是换代

- **一脉相承**：五层是同一份工程注意力随模型能力上移留下的五个落点——说什么、看到什么、在什么环境里跑、该不该反复跑、怎么组织很多个一起跑。
- **包含而非替换**：每层把前一层包进自己——context 是 prompt 的自然演进，harness 是 context 的具体形式，loop 每次迭代实例化一个 harness，graph 的每个节点各跑各的 harness。旧层没有消失，今天全部同时在场。
- **当下承重是 harness**：它是今天团队真正靠它生产的可靠性承载体；loop 和 graph 是把 harness 在更多场景里用得轻松、可靠的进阶用法，仍是新兴层，不与 harness 并列成「下一件大事」。
- P4 的上屏与视觉以此为准：画面表达包含关系与增长来历，不把五层与 SDLC 六阶段并置；「镜头 / 深度标尺」的读法从 P12 开始回收。

## 发动机没变，但问的问题变了

五层背后只有**一个**驱动机制：

> 模型越强，单次交互的边际工程收益越低，工程杠杆点就往上移。

`-opc` 把它读成「一个人的成长史 / 深度标尺」；本 talk 把它读成「软件价值流的能力深度检查表」。
四次换挡仍是同一种句式：

```
Prompt → Context：模型够强 → 不用把事实塞进 prompt
Context → Harness：环境受控 → 不用在 context 里写规则
Harness → Loop：运行受控 → 不用人决定"再来一次"
Loop → Graph：单 agent 够强 → 不用手动拆任务给谁
```

每一步「能力到位后，某个手工动作被上移或自动化」，都会改变 SDLC 的控制点：谁提供事实、谁建立运行边界、谁定义反馈规则、谁承担最后判断。

## 五个镜头分别检查什么

| 镜头 | 检查的问题 | 在软件 SDLC 中的主要落点 |
|---|---|---|---|
| Prompt | 意图是否足够清楚，能否形成下一角色可读的输入 | Plan 的意图表达、验收边界与取舍 |
| Context | 当时生效的事实、政策与约束是否被正确策展 | Design / Build 前的 spec、标准、技能与版本 |
| Harness | agent 的执行是否被圈住、拦住、看清 | Build / Test / Deploy 的沙箱、权限、工具、gate 与观测 |
| Loop | 结果是否能自动回流，并在错误扩大前被 gate 拦住 | Test / Maintain 的验证、评估、诊断与再进入 |
| Graph | 多个执行单元是否按明确合同编排并保留责任边界 | 跨任务或跨阶段编排；当前只作新兴镜头，不当成成熟默认范式 |

这五个镜头改变的是**控制深度与责任接口**，不是把人替换成五个新岗位。领域 owner 仍对意图与例外负责，平台提供共同运行边界，治理定义授权、审计与不可绕过的规则。

## 它是能力叠加，不是时间线

1. **一个因，五个观察面**：模型越强，工程杠杆点越往运行环境、反馈系统与编排合同上移。
2. **问题逐层上移**：说清楚 → 给对事实 → 在边界内执行 → 把结果送回 → 协调多个执行单元。
3. **叠加而非替代**：五层会同时存在；它们不对应五个独立团队，也不是年度升级路线。
4. **成熟度不相同**：Prompt / Context / Harness 已有较成熟的工程实践；Loop / Graph 需要更谨慎地验证授权、失败半径与审计能力。
5. **四个反转 = 四个记忆点**：
   - Loop ≠ 24/7 无人值守 → 可能错得更贵（blast radius 更大）
   - Graph ≠ 又一个 agent 框架 → 是编排范式（orchestration）
   - 五层 ≠ 年度替换 → 同一时间同时需要
   - 上升 ≠ 变简单 → 每一层都有自己的失败面

## 它怎样服务六阶段主轴

- **领域知识分布**：Prompt / Context 由最接近产品、架构、服务与政策的人维护，形成带 owner 和版本的工件。
- **运行控制共享**：Harness 的沙箱、权限、工具准入、门禁、观测与 provenance 形成平台共同基线，同时允许领域配置。
- **自动化受治理**：Loop / Graph 只有在事实可读、gate 可信、授权明确、日志可重建时才逐步放开。

因此五层只回答「这一步控制得有多深」，六阶段继续回答「软件价值流在哪一段发生改变」。两者的焊点是同一句话：
**把怎么正确参与外置成系统，同时保留领域判断的明确 owner。**
