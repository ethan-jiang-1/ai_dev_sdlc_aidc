# Harness 里头干啥 · 软件 SDLC 读法（抓要害的讲法 · v0.7）

> **v0.7 定位**：本页是 harness「引子」的核心——圈住 / 拦住 / 看清。在整场 talk 里，它是 Build / Test / Deploy 三个阶段的引子，
> 第三幕再由 DSH 把它做成可组合 runtime（managed settings / hooks / sandbox / evals / observability）。机制本身不变。

> 这是第二幕的核心讲法。目的：让软件 SDLC 决策者用一句话记住 harness 到底在干什么，以及**哪些能力应进入共享控制面**。
> 源：Böckeler 定义（`../_reference/rawdata_ai-coding-evolution-final/final_v4/03-2026-harness-era.md`）。
> 机制本身与 `-opc` 相同，落点换成跨职能软件价值流。

## 一句话

**模型给能力，harness 给可靠性。** Harness = 模型之外的运行边界，它干的事是
**把一个"很强的模型"变成受控、可验证、可追溯的交付。**对组织，需要集中建设的是共享控制面：
沙箱、权限、工具准入、门禁、观测与审计；领域意图、上下文与例外仍由对应 owner 承担。

## 两套控制（Böckeler 的框架）

- **Guides（引导 / 前馈）**：在 agent 行动**前**约束它——"按这个样式写"、"必须过这个 lint"、"只能用这些工具"。
- **Sensors（感知 / 反馈）**：在 agent 行动**后**把结果喂回——"测试挂了"、"用户拒绝了这个 diff"、"exit code 非零"。
- 每套再分两档：
  - **computational（确定性）**：测试 / lint / 类型 / schema——可复现、可审计。
  - **inferential（概率性）**：AI review / LLM-as-judge——可留痕与复核，但不等同于可复现的确定性证明。
- **原则：确定性可表达的规则，不降级为纯概率判断。** 必须始终成立的控制做成可复现、可留痕的门禁；需要上下文判断的部分可用 AI 辅助，最终责任不外包。

## 抓要害：三个动词 → 软件交付平台的三类共同基线

harness 里头干的事，归成三个动词；在跨团队软件交付中，它们各自对应一类平台共同基线：

1. **圈住（bound）** —— 沙箱 + 权限：让它只能碰该碰的文件、连该连的网、做被授权的操作。
   文件系统 + 网络双重隔离（bubblewrap / seatbelt）。→ **共享沙箱与权限基线**（谁、碰什么、问谁）。
2. **拦住（gate）** —— 工具协议 + 验证门禁：把"对错"变成机器可判的关卡，在错误离源头最近处就地拦下。
   授权要点：**authorize at execution, not at generation**。→ **共享工具协议与门禁基线**（准入 + 放行）。
3. **看清（see）** —— 可观测性 + provenance + CI：trace / metrics / logs 记下每一步，
   provenance 记下「产物谁造的、从哪来」，接进 CI 让每次交付可审计。→ **共享观测与审计基线**（还原事实 + 合规）。

## 六个构件（落到「装了什么」）→ 软件交付平台的六类基线能力

| 构件 | 干什么 | 归到 | 软件交付读法 |
|---|---|---|---|
| 沙箱 | 文件 + 网络双重隔离 | 圈住 | 沙箱基线 |
| 权限模型 | 什么能做、什么先问；执行时授权 | 圈住 | 权限 / 授权基线 |
| 工具协议 | 模型能调什么工具、怎么执行、结果回哪 | 拦住 | 工具准入基线 |
| 验证门禁 | 测试 / lint / 类型 / schema，尽量确定性 | 拦住 | 门禁基线 |
| 可观测性 | trace / metrics / logs 还原 agent 决策 | 看清 | 观测基线 |
| provenance + CI | 产物可追溯、交付可审计 | 看清 | 审计 / 合规基线 |

## 为什么这些基线适合进入共享控制面（承接第二幕）

- loop / graph 都站在它上面：loop 每次迭代实例化一个 harness；graph 每个 agent 节点跑在自己的 harness 里。
  如果 harness 各自为政，loop 会各自放大各自的错误，graph 会把不可靠的节点组织得更复杂。
- 三层本质是同一件事：**用反馈 + 确定性约束模型，换可靠结果**——harness 给单次反馈（Sensors），loop 把它连成循环，
  graph 把它编排起来。在软件 SDLC 中，这三层的**责任归属不同**：平台提供 harness 的共同基线，领域团队配置本地上下文与工作流，治理定义 loop / graph 的授权与审计规则。
- 授权与供应链风险说明，护栏不能只在模型生成请求时存在，必须在工具执行时独立授权。对软件交付系统，这里出问题的代价不是「一个人踩坑」，
  而是**供应链 / 授权 / 合规的组织级事故**。具体案例与日期必须回到证据卡片，不靠概括性数量词。

## 与 `-opc` 的分野（一句话）

`-opc`：harness 是「个人要握住的 final say」；本 talk：harness 是「软件交付平台提供共同控制基线，领域决策仍归对应 owner，治理定义不可绕过的边界」。
机制仍是圈住 / 拦住 / 看清，但责任由领域 owner、平台与治理共同承担，不被压成一个泛化的“组织主体”。
