# 听众、时长与核心目的（v0.7 · 软件 SDLC 内容 REVIEW）

## 听众

- **软件 SDLC 上的跨职能决策者**：CTO / 技术 VP、产品、架构、平台工程、开发、QA、安全、发布、SRE / 运维负责人——从产品意图到生产运维每个阶段的 owner。
- **独立成篇**：不依赖、不承接 `04_output/deck_ai_sdlc_keynote`。那边听众是「软件 + 业务」混合的战略听众（讲为什么世界变了），这边是研发组织的操作级听众（讲六阶段怎么一步步转）。
- 不假设听众都懂 prompt / harness 细节，但要讲得专业、抓要害、落到「组织怎么转型」，不滑向个人技能课。

## 时长与形式

- **单场加长 Keynote**：75–90 min，**50 页已定**。
- 无 demo（内容已满）。

## 核心目的

1. 建立起始诊断：**当 Build 加速、端到端交付却没同步变快时，瓶颈与风险已经移到代码两侧**。
2. 讲清中心命题：AI-native SDLC 不是在六阶段各加一个 AI 工具，而是把交付链重建成「**工件可交接、gate 可执行、owner 可问责、feedback 可回流**」的系统。
3. 沿六阶段说明这四件事如何落地，并对每阶段回答「留下什么工件 / 哪个 gate / 谁作判断 / 如何度量」。
4. 用 DSH 作为**参考实现**，说明如何把知识外置、正确路径、可执行反馈做成组织共享的 harness 控制面；不把某个产品讲成唯一答案。

## 沟通任务

> 到结束时，CTO、平台、产品、QA、安全、发布与运维 owner 应该能够共同选出一条价值流试点，
> 用「工件 / gate / owner / feedback」重画它，因为只加速编码会把瓶颈与治理成本推向代码两侧，不会自动改善端到端交付。

## 一句话 pitch

- 主题：**AI-Native 软件研发组织：从产品意图到生产运维的 SDLC 转型之道**
- 已定 slogan：**代码不再是瓶颈，流程才是。**
- 口径边界：slogan 是对 Anthropic 观点的记忆化表达，不是对每个组织的先验事实；现场使用「当……时」的诊断句式，并要求听众用自己的 lead time / queue time / change failure 数据验证。

## 讲述基调

- 抓要害 + 讲治理 + 引发研发决策者共鸣（不是炫技，不是论文复述，不是个人技能课）。
