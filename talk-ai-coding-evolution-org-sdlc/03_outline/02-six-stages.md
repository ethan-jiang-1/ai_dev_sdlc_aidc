# 第二幕逐页内容（P13–P38 · 六阶段转型 · v0.7）

> 主轴是 SDLC 六阶段。每个阶段都回答同样四个问题：**留下什么工件 / 哪道门禁必须执行 / 谁作最后决定 / 结果怎样回到下一轮**；五层只用来观察控制深度。
> play 是证据与实现选项，不是叙事目录。细则见 `../02_evidence/00-absorption-plan.md`。

### P13 工件把六个阶段接成一条闭环
- **页面结论**：六阶段描述交付顺序，并不规定改造顺序；每个阶段留下工件，下一阶段才接得住。
- **上屏**：六阶段闭环 + 工件之间的依赖关系。
- **讲点**：playbook 里的阶段顺序和采用顺序不是一回事。组织可以从依赖最少的做法开始，逐步让反馈闭环运行起来；但在交付链上，每个阶段仍要以可读工件结束，并触发下一阶段。
- **视觉**：闭环图 + 工件依赖箭头。

## Plan（P14–P16 · Prompt 深度镜头）

### P14 提示词镜头：规划先解决“原始意图怎样不丢失”
- **页面结论**：规划阶段首先要解决的，不是谁来写 PRD，而是怎样让原始意图经过多人交接后仍然准确。
- **上屏**：「先让原始意图可交接。」
- **讲点**：提示词镜头帮助我们检查意图是否表达清楚，但规划不等于提示词工程。真正的组织变化是：提出需求的人用自己的话说明问题，AI 帮助补齐边界，产品责任人作最终取舍。
- **视觉**：意图→工件 的转化。

### P15 规划：用 `intent.md` 留住需求提出者的原意
- **页面结论**：提出需求的人先用自己的话说明问题，再与 AI 一起补齐边界，形成 `intent.md`。
- **上屏**：`intent.md` 五段（问题 / 预期结果 / 影响对象 / 约束 / 待确认问题）。
- **讲点**：产品责任人不再替需求提出者层层转写，而是审查 AI 辅助形成的初步规格。最终批准权属于产品责任人，不属于工程师。
- **视觉**：intent.md 样例 + 传统 backlog 对比。

### P16 规划收口：意图要能被批准，也要能被度量
- **页面结论**：规划留下 `intent.md`，由验收门禁决定接受或退回，产品责任人作最终决定，并用提交耗时和后续通过率检验质量。
- **上屏**：审批写入版本库；度量关注「从首次对话到提交」的耗时，以及意图进入设计后的通过率。
- **讲点**：组织需要为 intent 建立受版本控制的固定位置，并明确谁可以写入。前置指标看从首次对话到正式提交用了多久，后置指标看这些意图有多少顺利进入后续阶段。
- **视觉**：审批门 + 双指标。

## Design（P17–P19 · Context 深度镜头）

### P17 上下文镜头：动手构建之前，先让约束和冲突可见
- **页面结论**：设计阶段的关键不是给模型塞入更多材料，而是让政策、标准、冲突和待确认问题在构建前可见、可追溯。
- **上屏**：「动手构建之前，先让政策、标准和冲突浮出水面。」
- **讲点**：上下文镜头要回答的是「模型当时依据什么作出判断」。组织需要把品牌、安全、合规和用户体验等要求写成带版本的约束，并为冲突项指定处理路径。
- **视觉**：context 策展示意。

### P18 设计：形成 `spec.md` 时就施加政策约束
- **页面结论**：需求与设计在同一次工作中收敛，政策不等到审查阶段才补上。
- **上屏**：`intent.md + skills → spec.md`；skills 提供品牌、安全、合规和用户体验约束。
- **讲点**：产品责任人主导这次会话，组织政策通过 skills 约束产出。产品责任人负责审查规格，而不是亲自代写规格。
- **视觉**：intent→spec 转化 + skills 约束环。

### P19 设计收口：规格必须带着约束、风险和责任归属进入构建
- **页面结论**：设计留下 `spec.md` 和待处理事项清单；风险门禁负责拦住未解决的冲突，产品与政策责任人分别作决定，并用后续返工衡量规格质量。
- **上屏**：规格、原始提示和当时生效的 skill 版本一并入库；标出的风险和冲突优先解决。
- **讲点**：产品责任人签署规格，矛盾或高风险事项交给相应政策责任人。工程团队拿到规格时，关键冲突应该已经被解决或明确接受。
- **视觉**：政策施加点前移示意。

## Build（P20–P25 · Harness 深度镜头）

### P20 Harness 镜头：构建阶段要把执行圈住、拦住、看清
- **页面结论**：构建不只是生成代码；还要限制执行边界，在错误发生的近处拦截，并为产物留下来源记录。
- **上屏**：圈住 = 沙箱与权限；拦住 = hooks 与门禁；看清 = 观测与来源记录。
- **讲点**：五层模型把 harness 看作可靠性边界，构建阶段最集中地体现这层能力，测试和发布也会复用同一基线。平台提供共享沙箱、权限、门禁和观测，领域团队保留本地配置与业务判断。
- **视觉**：harness 三层归位。

### P21 构建：先审 `plan.md`，再允许修改代码
- **页面结论**：计划必须先于代码出现，而且能够被审查、复核和追责。
- **上屏**：`plan.md`（files / order / risks / proof）。
- **讲点**：工程师让 agent 在 plan mode 中只读代码库并产出实现计划，计划被接受前不得修改文件。计划写入 `plan.md`，审查 PR 时再用实际改动与计划逐项核对；高风险事项交给技术负责人或架构师。
- **视觉**：plan.md 样例 + plan-mode 门。

### P22 构建：把团队规则写成 agent 每次都能读到的文件
- **页面结论**：组织知识要从人脑和零散 wiki 中移出来，进入版本受控、按需加载的规则文件。
- **上屏**：`AGENTS.md` 四段 + `skills/`（版本受控目录）。
- **讲点**：`AGENTS.md` 承载团队约定，skill 把政策变成按条件触发的约束。同一个错误重复出现，就把预防方法写进规则；skill 的变更由相应政策责任人审查。
- **视觉**：AGENTS.md 样例 + skill 触发。

### P23 构建：用 hooks 让硬规则自动生效
- **页面结论**：必须遵守的规则不能只靠记忆，而要变成每次都会执行的护栏。
- **上屏**：阻止修改保护路径 / 自动运行 formatter 与 lint / 拦截 credentials。
- **讲点**：hook 是 skill 背后的确定性执行层。它应该快而窄；较重的检查放到 commit 或 PR，必须由人批准的门禁放到发布阶段。这一页对应“圈住”和“拦住”。
- **视觉**：hook 拦截示意。

### P24 构建：并行会话越多，隔离和责任归属越重要
- **页面结论**：工程师可以同时编排多个会话和子 agent，但每条工作线都要隔离环境、记录日志并明确归属。
- **上屏**：worktree 隔离 + `subagents/` 定义。
- **讲点**：这是 Graph 层的雏形，只在这里点到为止，运维阶段和第三幕再回收。控制来自仓库配置中的 hooks 与 permissions，每条日志都归属于启动该会话的工程师。
- **视觉**：并行 worktree + 子 agent 图。

### P25 构建收口：共同基线与具体改动要由不同角色负责
- **页面结论**：构建留下计划、代码改动和测试证据；沙箱、权限与 hooks 负责守门，平台维护共同基线，工程师对具体改动负责，并用返工和计划吻合度检验执行质量。
- **上屏**：四件套归位。
- **讲点**：构建是 harness 最集中的落点，也是各团队最容易重复建设的地方。因此平台提供共同基线，工程师和领域责任人对具体改动负责。
- **视觉**：四件套 + 平台共同基线。

## Test（P26–P29 · Sensors / Loop 深度镜头）

### P26 Sensors / Loop 镜头：测试要同时验证改动和控制配置
- **页面结论**：一类证据回答“产品改动是否正确”，另一类证据回答“驱动 agent 的配置是否仍然可靠”。
- **上屏**：「没有验证证据，就不能算完成。」
- **讲点**：harness 有两类控制：Guides 在执行前给出方向，Sensors 在执行后返回事实。测试是 Sensors 最集中的落点，而“根据反馈修改，再次验证”正是闭环的起点。
- **视觉**：Guides/Sensors 两套控制。

### P27 测试：让 agent 在会话内完成验证并留下证据
- **页面结论**：agent 不能只声称任务已经完成，必须用工具链输出证明结果。
- **上屏**：统一测试入口；量化通过标准；「修代码，不改测试来迁就结果」。
- **讲点**：组织要把“验证完成”写进完成定义。修复缺陷时先写一个会失败的测试，并用 hook 防止 agent 擅自修改测试文件；工具链输出进入会话记录和 PR 检查，成为可追溯证据。
- **视觉**：反馈闭环（写→测→改）。

### P28 测试：用 evals 给 harness 配置做回归测试
- **页面结论**：规则、skills 和 hooks 发生变化时，也要证明原有任务仍能可靠完成。
- **上屏**：选取 20–50 个真实任务形成 eval；配置一变就运行；每次生产事故都补一个回归样本。
- **讲点**：组织应当像对待代码一样对待配置：`AGENTS.md`、skills 或 hooks 只要变化，就要运行回归测试，并把通过率阈值设为合并门禁。
- **视觉**：eval suite + CI 门。

### P29 测试收口：QA 从逐单执行转向维护验证系统
- **页面结论**：测试留下产品测试与 eval 证据，以通过阈值守门；QA 和配置责任人分别维护验证体系与控制配置，并持续观察首次通过率、漏检和变更失败趋势。
- **上屏**：前置指标看首次 CI 通过率；后置指标看审查耗时和变更失败率。
- **讲点**：QA 的职责从“逐单执行测试”转向“维护 eval 套件、审查配置变更”。能稳定交给门禁判断的事项，不再依赖模型自觉。
- **视觉**：QA 角色转变。

## Deploy（P30–P34 · Harness 深度镜头）

### P30 Harness 镜头：agent 可以提出动作，生产执行必须另行授权
- **页面结论**：agent 可以准备发布、解释风险、提出动作，但真正触碰生产环境时，必须根据当下语境重新授权。
- **上屏**：「授权发生在执行那一刻，而不是生成方案时。」
- **讲点**：护栏不能建立在“模型会主动发出合法调用”这个假设上，授权必须独立发生在工具执行时。若引用具体安全事件，必须使用对应证据卡片，不用含糊的年份或 CVE 泛称。
- **视觉**：提议/执行分离。

### P31 发布：写代码与批准发布必须分开
- **页面结论**：所有 PR 经过同一套审查步骤，机器检查可以复用，人的判断集中在意图、风险和例外。
- **上屏**：`REVIEW.md`（审查步骤 / 严重级别 / 通过阈值）；PR 历史保留决定过程。
- **讲点**：写代码的 agent 不能批准自己的改动，最终批准通过 branch protection 由人完成；反复出现的问题再回写 `AGENTS.md`。
- **视觉**：PR 多层 review + 人守 gate。

### P32 发布：用 hooks 和托管配置封住生产边界
- **页面结论**：审批不能只写在流程文档里，而要成为执行管道中的门禁；平台托管的配置负责保证边界不能被个人放宽。
- **上屏**：PreToolUse hook（允许 / 询问 / 阻止）+ 托管配置（权限 / 沙箱 / 凭据 / 市场 / 最低版本）。
- **讲点**：门禁必须对每个人、每次执行都生效，并留下带时间戳的记录。托管配置用于阻止放宽权限、旁加载或使用过低版本；配置里的每一行，背后都是一项治理决定。
- **视觉**：gate 放行/拒绝 + 托管配置清单。

### P33 发布：agent 的权限止步于生产门禁
- **页面结论**：agent 可以完成判断、准备变更并发起发布请求，但不能越过生产门禁自行执行。
- **上屏**：先从只读判断开始；写操作走 PR；部署能力通过 MCP 暴露；自主权按环境逐级收紧；回滚路径反复演练。
- **讲点**：开发环境允许较高自主度，预发布环境居中，生产环境必须由发布负责人授权，并由 hook 强制执行。回滚是最需要反复演练的路径；每次执行使用 agent 自己的身份，日志必须能够区分。
- **视觉**：环境分层 + 生产 gate。

### P34 发布收口：生产门禁必须独立于代码生成
- **页面结论**：发布留下 PR 和发布证据，由分支保护与生产授权共同守门；代码责任人和发布责任人分开签字，并用门禁等待时间与变更失败率持续改进。
- **上屏**：提出动作 → 独立门禁 → 放行或拒绝 → 写入记录。
- **讲点**：生产门禁不能依赖流程自觉，必须由 hook 强制执行。这就是“在执行时授权”的组织落点。
- **视觉**：门禁强制示意。

## Maintain（P35–P38 · Loop / Graph 深度镜头）

### P35 Loop / Graph 镜头：生产事实要沿同一条受控路径回流
- **页面结论**：运维自动化不是给 agent 开一条直达生产的通道，而是在指标越界时触发诊断，再让结果回到同一条工件链和门禁体系。
- **上屏**：「闭环可以持续运行，人的判断始终位于闭环之上。」
- **讲点**：Loop 层检查反馈能否回到下一轮，Graph 层只用来观察多个执行节点之间的交接和门禁。这里不把多 agent 编排说成已经成熟的生产范式。
- **视觉**：loop 闭合 + 多 agent。

### P36 运维：只有指标越界，才触发 agent 进入诊断
- **页面结论**：确定性检测负责发现异常，agent 负责形成诊断；诊断写回 `intent.md` 后，重新进入完整交付链。
- **上屏**：确定性检测（均值 / 标准差 + Western Electric）+ `bands.yaml`（1σ 记录 / 2σ 只读诊断 / 3σ 提议 PR 或 runbook）。
- **讲点**：检测过程不依赖模型，只有越界才调用 agent。触发无需人工启动，但后续动作仍受分级门禁约束；服务责任人或当班人员负责分诊与授权。
- **视觉**：control-band → intent.md → 环。

### P37 运维：定时扫描发现的问题，也要走同一套门禁
- **页面结论**：安全扫描不再是一次性活动；发现项按固定节奏产生，并沿既有 PR 和意图工件路径处理。
- **上屏**：首次扫描建立基线；每周运行；给出置信度；忽略必须说明理由；修复后补充 eval。
- **讲点**：安全负责人集中管理仓库范围、席位和成本。一般发现项走 PR 门禁，重大修复先写 `intent.md`；确定性检查保留在 CI 中，模型驱动扫描用于补充需要结合上下文判断的问题。
- **视觉**：定时扫描 + 走 gate。

### P38 运维收口：自动诊断可以先开始，处置授权仍由服务责任人掌握
- **页面结论**：运维留下事件、诊断和意图工件；分诊与 PR/runbook 授权负责守门，服务责任人作最终决定，并用恢复时间和同类问题复发率检验闭环。
- **上屏**：「晚上十点发生的事件，可以先诊断，不必先等人上线。」
- **讲点**：事件触发 agent 诊断，并验证指标是否回到基线；事后总结写入 lessons。人在 channel 中可以引导和授权，小修走 PR，大修先写 `intent.md`。channel 可以成为证据的一部分，但单凭聊天记录不能声称审计已经完成。
- **视觉**：channel 证据并入工件链。
