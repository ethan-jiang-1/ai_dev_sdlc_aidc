# 开场 + 第一幕逐页内容（P1–P12 · v0.7）

> 软件 SDLC 视角：每页都要说清「价值流哪里失配、应该建立什么控制、谁来负责、怎样验证」。口径红线见 `../02_evidence/00-absorption-plan.md` §三。

## 开场（P1–P5）

### P1 封面
- **页面结论**：AI-Native 软件研发组织：从产品意图到生产运维的 SDLC 转型之道。
- **上屏**：题目 + 副题「让产品意图顺畅抵达生产现场，重建整条软件交付链」+ 讲者。
- **讲点**：对象是**软件 SDLC 上的跨职能研发与交付组织**（CTO/产品/架构/平台/开发/QA/安全/发布/SRE），不是程序员个人，也不是泛化的「AI 组织」。
- **视觉**：封面；六阶段 loop 作暗线。

### P2 钩子：编码变快了，为什么交付没有同步加速
- **页面结论**：编码速度和交付速度不是一回事；两者出现落差时，先去找价值流里仍在等待的环节。
- **上屏**：「编码环节已经变快，为什么交付周期没有同步缩短？」
- **讲点**：这是一个诊断问题，不预设所有组织都已经出现「代码翻倍、交付不变」。请听众对照自己的编码耗时、排队时间、首次审查等待和发布周期。
- **视觉**：后续表现阶段再定。

### P3 Anthropic 的判断：瓶颈正在向编码前后转移
- **页面结论**：编码耗时一旦显著缩短，规划、审查、测试和发布这些仍按人的速度运行的环节，就会决定端到端交付。
- **上屏**：「Code is no longer the bottleneck.」
- **讲点**：明确标注这是 Anthropic 的论点，不是普适事实。它对软件交付决策者的意义是：不能只衡量代码产出，要把转型对象扩到从产品意图到生产运维的整条 SDLC。
- **视觉**：线性 SDLC——build 塌缩，两边原长。

### P4 五层预告：它们不是另一条流程，而是五种观察深度
- **页面结论**：Prompt 到 Graph 用来检查知识外置和执行控制做到了多深，不代表另一条演进时间线。
- **上屏**：Prompt → Context → Harness → Loop → Graph（每层一句话）。
- **讲点**：不展开，只给后面的观察语言：意图怎么表达，上下文怎么策展，运行怎么受控，反馈怎么回流，多节点怎么编排。不宣称某个 SDLC 阶段的「本质」等于某一层。
- **视觉**：五层图（预告态，浅标注）。

### P5 harness 先立住：能力来自模型，可靠执行来自控制系统
- **页面结论**：模型决定能做什么，harness 决定能否可靠地做成；平台统一权限、门禁、观测和审计基线，领域判断仍由相应责任人承担。
- **上屏**：「模型决定能做什么，harness 决定能否可靠地做成。」
- **讲点**：先点出这个分界，后面再到构建、测试和发布阶段展开。平台提供共同控制基线，但产品意图、领域背景和业务例外仍由相应责任人掌握；共享的是控制，不是把所有业务知识收归平台。
- **视觉**：Agent = Model + Harness（Böckeler）。

## 第一幕：为什么整条 SDLC 要转型（P6–P12）

### P6 编码不再是主要约束之后，压力会转移到三个地方
- **页面结论**：等待向前后环节转移，原有控制开始失效，治理例外随之增多。
- **上屏**：一张因果图，依次呈现「等待转移、控制失配、例外增加」。
- **讲点**：① 慢点移到规划、审查和发布；② 按人工产出配置的审查能力跟不上 agent；③ 新问题仍要挤进低频审批流程。三者叠加后，交付周期和风险都会上升。
- **视觉**：单一因果图，不拆成三张卡片。

### P7 传统控制方式有一个共同前提：主要工作由人执行
- **页面结论**：当代码稀缺、步骤主要由人完成时，文档、工单、签字和人工审查还能支撑交接与问责。
- **上屏**：线性六阶段 + 交接物（PRD/工单/签字）。
- **讲点**：传统控制之所以流程较重，是因为它默认「人执行、人交接」。AI 改变的正是这个前提。
- **视觉**：线性流程 + 交接节点。

### P8 产出速度超过控制能力，结果只有排队或审查不足
- **页面结论**：当 agent 的产出超过审查、安全和发布团队的处理能力，工作要么堵在门前，要么绕过检查进入生产。
- **上屏**：「产出变宽了，控制通道却没有变宽。」
- **讲点**：playbook 用安全团队举例：人员配置仍按人的产出估算，agent 却把代码产出显著放大。结果不是审查队列不断增长，就是代码在证据不足时被发布；对受监管的软件交付来说，两者都不可接受。
- **视觉**：漏斗（产出洪流 vs review 吸管）。

### P9 机器负责重复判断，人负责意图、风险、例外和授权
- **页面结论**：能稳定复现的检查交给工具链，人的注意力留给必须结合语境作出的决定。
- **上屏**：「人启动、人交接、人逐项检查」转为「agent 执行、工件交接、机器门禁、人作判断」。
- **讲点**：这是整场转型的轴心。参与规则被外置成四件事：工件记录事实，门禁执行机械判定，责任人承担价值判断，反馈把结果带回下一轮。
- **视觉**：in-the-loop → on-the-loop。

### P10 工件链只是审计骨架，还不是完整的审计能力
- **页面结论**：每个阶段留下工件，审计才有主线可循；要真正追溯和问责，还要补齐身份、版本、证据、审批与不可绕过的门禁。
- **上屏**：`intent → spec → plan → diff+tests → PR+review → incident`。
- **讲点**：这一页故意留下一个问题：怎样避免工件链沦为一串文件？第二幕会逐段补齐工件、门禁、责任人和证据，P39 再给出完整答案。
- **视觉**：工件链首尾相接。

### P11 六个阶段都要换一种控制方式
- **页面结论**：AI-native 转型不是给每个阶段各加一个助手，而是重做交接、门禁和责任边界。
- **上屏**：六阶段对照表（规划/设计/构建/测试/发布/运维，两列）。
- **讲点**：这里只逐行点到为止，第二幕再展开。共同变化是：从「人执行、人工守关」转为「agent 执行、工件交接、确定性门禁、人作判断」。
- **视觉**：对照表（进货单 §一）。

### P12 后面每个阶段，都要回答同样四个问题
- **页面结论**：每个阶段都必须说清留下什么工件、哪道门禁必须执行、谁作最后决定、结果怎样回到下一轮；五层只用来观察控制做到了多深。
- **上屏**：六阶段 × 四问；旁边轻量标注 Prompt / Context / Harness / Loop / Graph 镜头。
- **讲点**：这也是听众后面的记录表：每讲完一个阶段，就能填上一行。六行全部填完，才算真正重做了整条 SDLC。
- **视觉**：六阶段 + 五层对齐图。
