# 开场 + 第一幕逐页内容（P1–P12 · v0.6 内容 REVIEW）

> 组织视角：每页回答「组织该建什么 / 谁负责 / 怎么治理」。口径红线见 `../02_evidence/00-absorption-plan.md` §三。

## 开场（P1–P5）

### P1 封面
- **页面结论**：AI-Native 软件研发组织：从产品意图到生产运维的 SDLC 转型之道。
- **上屏**：题目 + 副题「从产品意图到生产运维，重建软件 SDLC」+ 讲者。
- **讲点**：对象是**软件 SDLC 上的跨职能研发与交付组织**（CTO/产品/架构/平台/开发/QA/安全/发布/SRE），不是程序员个人，也不是泛化的「AI 组织」。
- **视觉**：封面；六阶段 loop 作暗线。

### P2 钩子：当 Build 变快，端到端交付为什么没同步变快
- **页面结论**：编码速度和交付速度不是同一个指标；差距出现时，先找价值流里还在排队的地方。
- **上屏**：「Build 快了，lead time 为什么没同步下降？」
- **讲点**：这是诊断问题，不预设每个组织都已经「代码翻倍、交付不变」。请听众对照自己的 coding time、queue time、review time 和 deployment lead time。
- **视觉**：后续表现阶段再定。

### P3 Anthropic 的诊断：瓶颈从 Build 移向代码两侧
- **页面结论**：当 Build 被显著压缩，plan / review / test / deploy 这些人速环节决定端到端交付。
- **上屏**：「Code is no longer the bottleneck.」
- **讲点**：明确标注这是 Anthropic 的论点，不是普适事实。它对组织的意义是：不能只衡量代码产出，要把转型对象扩到从产品到运维的整条 SDLC。
- **视觉**：线性 SDLC——build 塌缩，两边原长。

### P4 五层预告：同一条 SDLC 可以有不同控制深度
- **页面结论**：Prompt 到 Graph 是观察外置与控制深度的五个镜头，不是另一条时间线。
- **上屏**：Prompt → Context → Harness → Loop → Graph（每层一句话）。
- **讲点**：不展开，只给后面的观察语言：意图怎么表达，上下文怎么策展，运行怎么受控，反馈怎么回流，多节点怎么编排。不宣称某个 SDLC 阶段的「本质」等于某一层。
- **视觉**：五层图（预告态，浅标注）。

### P5 harness 先立住：组织需要共享控制面
- **页面结论**：模型给能力，harness 给可靠性；共享的权限、门禁、观测和审计不能由每个团队重造。
- **上屏**：「模型给能力，harness 给可靠性。」
- **讲点**：先点破临界点，后面 Build/Test/Deploy 再展开。组织集中建共享控制面，但 intent/context/业务例外仍由领域 owner 负责；这是「控制集中、知识分布」，不是所有业务统一。
- **视觉**：Agent = Model + Harness（Böckeler）。

## 第一幕：为什么整条 SDLC 要转型（P6–P12）

### P6 代码不再是瓶颈 → 三个后果
- **页面结论**：瓶颈左移右移 / 旧控制失效 / 治理成本上升。
- **上屏**：三张卡片。
- **讲点**：① 慢的移到 plan/review/deploy；② 逐行 review 是「人写代码」时代设计的，agent 一次吐几千行就崩；③ 例外仍走周会/月会委员会。**三个都是组织级问题**。
- **视觉**：三卡片。

### P7 传统 SDLC 的控制假设
- **页面结论**：传统 SDLC 围绕「代码稀缺 + 人执行」设计，所以用文档、工单、签字和人工 review 换问责。
- **上屏**：线性六阶段 + 交接物（PRD/工单/签字）。
- **讲点**：传统控制为了问责而流程重——但它的前提是「人执行、人交接」。这个前提被 AI 挖了。
- **视觉**：线性流程 + 交接节点。

### P8 产出与控制容量失配
- **页面结论**：当 agent 产出超过 review / security / release 的人工容量，只有两个坏答案：排队，或欠审。
- **上屏**：「安全团队按人的产出配备——排队，或欠审。」
- **讲点**：playbook 的安全例子：代码产出成倍、安全团队规模没变 → 要么排队、要么欠审。受监管组织两个都不能接受。
- **视觉**：漏斗（产出洪流 vs review 吸管）。

### P9 新控制模型：工件交接，机器守确定性 gate，人守判断 gate
- **页面结论**：机械检查下沉到工具链，人的注意力留给意图、风险、例外与授权。
- **上屏**：「人启动 / 人交接 / 人机械检查」→「agent 执行 / 工件交接 / 机器 gate / 人判断」。
- **讲点**：这是整场转型的轴心。「怎么正确参与」被外置成四件事：工件记事实，gate 做机械判定，owner 承担价值判断，feedback 把结果带回链上。
- **视觉**：in-the-loop → on-the-loop。

### P10 工件链是审计的骨架
- **页面结论**：每阶段留下工件，可以给审计一条主线；要真正成为审计链，还需身份、证据、审批与不可绕过的 gate。
- **上屏**：`intent → spec → plan → diff → PR → incident`。
- **讲点**：这一页故意留一个未解条件：工件链怎样才不只是「文件串」？第二幕逐段收集工件、gate、owner 和证据，P39 再给出完整答案。
- **视觉**：工件链首尾相接。

### P11 六阶段 shifts 总表
- **页面结论**：传统 vs AI-native，一屏看清六阶段转变。
- **上屏**：六阶段对照表（Plan/Design/Build/Test/Deploy/Maintain，两列）。
- **讲点**：逐行点到为止（细节第二幕展开）。重点：每一阶段从「人执行 + 人工闸」变成「agent 执行 + 工件交接 + 确定性闸」。
- **视觉**：对照表（进货单 §一）。

### P12 全场导航：六阶段都回答同一组四问
- **页面结论**：每一阶段都必须说清工件、gate、owner 和 feedback；五层只用来观察这一阶段的控制深度。
- **上屏**：六阶段 × 四问；旁边轻量标注 Prompt / Context / Harness / Loop / Graph 镜头。
- **讲点**：这是听众后面的记录表：每讲完一阶段，都能填上一行。六行全部填完，才能说整条 SDLC 被重新设计过。
- **视觉**：六阶段 + 五层对齐图。
