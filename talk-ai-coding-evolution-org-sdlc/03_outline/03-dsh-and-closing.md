# 第三幕 + 收尾逐页内容（P39–P50 · v0.7）

> 软件 SDLC 视角：先回答「工件链在什么条件下才具备审计能力」，再解释共享控制面如何工程化。
> DSH 作「知识外置 / 正确路径 / 可执行反馈」的**参考实现**，不是唯一产品选型。DSH 素材见 `../02_evidence/00-absorption-plan.md` §四。

## 第三幕：共享控制面 + DSH 参考实现（P39–P48）

### P39 工件链补齐五项控制，才能真正支持审计
- **页面结论**：`intent → spec → plan → diff+tests → PR+review → incident` 提供审计骨架；身份、版本、证据、审批和不可绕过的门禁，才让这条链能够追溯和问责。
- **上屏**：工件链 + 五个控制条件。
- **讲点**：这一页回答 P10 留下的问题。把文件放进版本库，不等于自动获得合规能力；只有能够还原“谁在什么版本下、依据什么证据、作出什么决定、由哪道门禁放行”，整条链才真正具备问责能力。
- **视觉**：工件链 + 审计标注。

### P40 机器负责可重复判断的规则，人负责结合语境作决定
- **页面结论**：能够机械表达的规则做成可复现门禁；必须理解语境的判断可以由 AI 辅助，但最终由人负责，两类决定都要留痕。
- **上屏**：确定性检查（测试 / lint / 类型 / schema）托底；推断性审查（AI review）补充语境判断。
- **讲点**：Böckeler 把控制分为 Guides 和 Sensors，两类控制都可能有确定性或概率性实现。概率性审查可以记录、复核，却不能冒充确定性证明；必须始终成立的规则，需要确定性机制托底。
- **视觉**：computational vs inferential 阶梯。

### P41 DSH 说明三项控制原则怎样进入运行时
- **页面结论**：DSH 的价值不在于提供“更聪明的 agent”，而在于证明知识外置、路径明确和反馈可执行，可以从制度要求变成 runtime 合同。
- **上屏**：三条腿——**知识外置 / 正确路径 / 可执行反馈**。
- **讲点**：这里必须回到前 38 页：知识外置对应 intent、spec、plan 和 `AGENTS.md`；正确路径对应责任人与门禁；可执行反馈对应 hooks、tests、evals 和审查证据。一个 DSH 机制如果回答不了前面的组织问题，就不进入这场演讲。

### P42 共享控制面必须同时回答两个问题
- **页面结论**：插件图回答“系统现在由什么组成”，事件流回答“刚才实际做了什么”；loop 从前者取得能力，把执行事实写入后者。
- **上屏**：插件图（live plugin graph）+ 事件流（session event log）+ loop。
- **讲点**：参与一个 harness 需要两类知识：一类由系统明确写出，包括写在哪里、怎样修改、如何验证；另一类只能靠参与者自己知道，包括行话和部落知识。DSH 的工程重点，是让前一类尽可能多、后一类尽可能少：**参与规则应该住在运行时里，而不是只住在人脑里**。
- **视觉**：插件图 + 事件流 + loop 三件套。

### P43 知识外置：一个事实只认一个权威来源
- **页面结论**：规则是什么、结构在哪里、应该改哪一处、为什么这样决定，都要写进可搜索、可检查的文件，而不是依赖资深成员脑中的部落知识。
- **上屏**：「一个事实，一个权威来源」「当前状态与决策理由分开记录」「也要写清为什么没有选择另一条路」。
- **讲点**：这是避免系统变糊涂的地基。agent 遇到问题时应查权威文件，而不是在过时故事中猜测。第二幕里的 `intent.md`、`spec.md`、`AGENTS.md` 和 skills 都在把“要什么、为什么、怎样做”写成文件；ADR 记录决策理由，rejected notes 记录为什么没有选择某个方案。
- **视觉**：知识外置 → 单一事实源。

### P44 正确路径应该最省力，不正确的路径应该走不通
- **页面结论**：变更按 patch、扩展点、seam、loop 分层进入；每一层都有明确入口、能力合同和检查范围。
- **上屏**：先问四件事：事实归谁、在哪里拦截、增加什么能力、是否需要改动 loop；再选择参与层级。
- **讲点**：这里首先解决“应该改哪里”。谁能改配置、谁能增加能力、谁能替换后端、谁能改动 loop，都需要各自的入口和门禁。第二幕里的产品审批、hooks、PR 审查和托管配置，都是把正确路径做成机制；P48 会把这些机制收成四项治理决定。
- **视觉**：参与阶梯（四层 + 门）。

### P45 门禁只有经过负例验证，才值得信任
- **页面结论**：能机械判断的规则必须进入执行管道，门禁本身也要接受测试，持续证明无效动作确实会被拒绝。
- **上屏**：类型 / load / 测试 / snapshot / invariant / CI；「强制门禁比文字约定更可靠。」
- **讲点**：这也是 DSH 最值得借鉴的一点。文档负责告诉参与者去哪里看，系统负责证明动作是否正确。DSH 的工具执行管道是 `tools/pre-execute → execute → post-execute`；`pre-execute` 统一处理允许、拒绝和询问，timeout 作用在 execute 上。门禁集中守在执行管道，而不是散落在每个工具内部。第二幕中的 evals 和 hooks 也采用同一原则；DSH 更进一步，连门禁本身都持续接受负例测试。
- **视觉**：门禁清单 + 「门禁被测试」示意。

### P46 共享控制面统一能力合同，不统一所有后端
- **页面结论**：一条 seam 只有同时具备 Definition、Provider 和 Consumer，才构成可替换的完整能力；更换后端时，Consumer 不应跟着改。
- **上屏**：Definition（声明能力）+ Provider（提供实现）+ Consumer（使用能力）。
- **讲点**：这让不同环节能够在共同控制面上保留自己的实现。更换沙箱、模型或持久化后端时，Consumer 不必修改。DSH 进一步把 loop、会话服务、模型适配器和工具注册表都做成插件；新增行为挂到扩展点，不直接改 loop 核心。平台统一的是“如何替换、如何扩展”的合同，领域团队仍可按需要选择后端。
- **视觉**：三角色图 + 换后端示意。

### P47 输入、工具结果和审批必须能够从日志还原
- **页面结论**：模型能看到的内容必须已经记录；审批请求与决定成对出现，无人能够作答时默认关闭。这是扩大自主度的前提。
- **上屏**：只追加的会话日志；`asked/decided` 成对；无人作答时关闭；会话格式带版本。
- **讲点**：这里提供的是“事实能够被谁重建”的运行时保证。三条不变式是：① 模型看到的每项输入都能从日志恢复，这由 loop 构建时检查，而不是靠文档承诺；② 审批由成对审计事件组成，没有 answerer 时默认失败；③ 会话格式遵守版本纪律，冷启动后仍可恢复。同一份日志也记录 runtime 自己的行为。
- **视觉**：append-only log + 成对审批。

### P48 采用顺序只有一条：先让工件可读，再让门禁可信，最后运行闭环
- **页面结论**：能力准入、后端替换、动作放行和事实重建各自需要明确机制，但采用时应先解决交接，再解决强制执行，最后扩大自动化。
- **上屏**：准入 = registry + knowledge map；替换 = adapter + seam；放行 = enforced gate + invariant；重建事实 = session log。
- **讲点**：这一页把 P44–P47 收成四项可操作决定。组织不应从自动化整个 loop 开始，而应先让一次交接拥有可读工件和明确责任人，再把必须成立的规则做成门禁；只有事实可读、门禁可信之后，才让闭环自动运行。生态规模、star 数和可替换率留在证据库，不承担这一页的组织结论。
- **视觉**：四决定 → 四机制对齐图 + 落地三步。

## 收尾（P49–P50）

### P49 带走一句
- **页面结论**：代码不再是瓶颈，流程才是。
- **上屏**：「代码不再是瓶颈，流程才是。」
- **讲点**：回到开场：当编码加速而交付周期没有缩短，问题就在编码前后的交接、门禁和反馈。转型不是追求更多代码，而是让整条 SDLC 能够交接、能够执行、责任清楚、结果回流。
- **视觉**：slogan 大字 + 六阶段 loop 暗线。

### P50 从最慢的一次交接开始
- **页面结论**：选一条真实价值流，找到最慢的一次交接，为它补齐一个工件、一道门禁、一位责任人和一个反馈指标。
- **上屏**：四个空格：工件 / 门禁 / 责任人 / 反馈；问题「你们这条链上，哪一次交接最慢？」
- **讲点**：这是会后行动，不是泛泛致谢。试点的完成标准是：一次真实变更能够沿新路径走完，并且能用交付周期、排队、返工或失败中的至少一个指标，对比改造前后。
