# 第三幕 + 收尾逐页内容（P39–P50 · v0.6 内容 REVIEW）

> 组织视角：先回答「工件链在什么条件下才是审计链」，再解释共享控制面如何工程化。
> DSH 作「知识外置 / 正确路径 / 可执行反馈」的**参考实现**，不是唯一产品选型。DSH 素材见 `../02_evidence/00-absorption-plan.md` §四。

## 第三幕：DSH + 治理收束（P39–P48）

### P39 工件链加上控制，才成为审计链
- **页面结论**：`intent → spec → plan → diff+tests → PR+review → incident` 提供审计骨架；身份、版本、证据、审批与不可绕过的 gate 让它成为审计链。
- **上屏**：工件链 + 五个控制条件。
- **讲点**：回答 P10 留下的问题。版本库不会自动产生合规；只有能重建「谁在什么版本下，根据什么证据，作了什么决定，哪个 gate 放行」，链才有问责力。
- **视觉**：工件链 + 审计标注。

### P40 机器守确定性 gate，人守判断 gate
- **页面结论**：可机械表达的规则做成可复现门禁；需要上下文的判断由 AI 辅助、人负责，两者都要留痕。
- **上屏**：computational（测试/lint/类型/schema）> inferential（AI review）。
- **讲点**：Böckeler 两套控制（Guides/Sensors），每套都可有确定性/概率性实现。概率性 review 可以留痕和复核，但不能冒充确定性证明。必须始终成立的规则，要有确定性底座。
- **视觉**：computational vs inferential 阶梯。

### P41 DSH 参考实现：把三条组织原则做成 runtime
- **页面结论**：DSH 的价值不在「更聪明的 agent」，而在证明知识外置、正确路径、可执行反馈可以从制度变成 runtime 合同。
- **上屏**：三条腿——**知识外置 / 正确路径 / 可执行反馈**。
- **讲点**：必须回指前 38 页：知识外置对应 intent/spec/plan/AGENTS.md；正确路径对应 owner 和 gates；可执行反馈对应 hooks/tests/evals/review evidence。若一个 DSH 机制无法回答前面的组织问题，就不进这场 talk。

### P42 共享控制面同时管「现在是什么」和「刚才发生了什么」
- **页面结论**：插件图回答当前能力与配置，事件流回答实际执行与决策，loop 在两者之间取能力、写事实。
- **上屏**：插件图（live plugin graph）+ 事件流（session event log）+ loop。
- **讲点**：参与一个 harness 需要两类知识——系统外置的（写在哪、怎么写、怎么验证）和读者自带的（行话、部落知识）。DSH 的工程重心是让前者尽可能多、后者尽可能少：**参与规则住在运行时里，不在人脑里**。
- **视觉**：插件图 + 事件流 + loop 三件套。

### P43 知识外置：工件可以交接，因为事实与决策有 owner
- **页面结论**：规则、结构、改哪里、为什么，写进可搜索可检查的文件——不靠资深成员脑子里的部落知识。
- **上屏**：「一个事实一个 owner」「当前状态与决策理由分开」「负知识外置（为什么不做 X）」。
- **讲点**：这是「不糊涂」的地基——agent 遇到问题去权威文件查，而不是在过时故事里猜。**回指第二幕**：Plan 的 intent.md（P15）、Design 的 spec.md（P18）、Build 的 AGENTS.md+skills（P22），都是「把要什么/为什么/怎么做外置成文件」——加上 ADR 记决策理由、rejected notes 记「为什么不做 X」。
- **视觉**：知识外置 → 单一事实源。

### P44 正确路径：gate 有用，因为变更先被路由到对的层级
- **页面结论**：正确做法是阻力最小的路径；参与分层（patch → 扩展点 → seam → loop），每层有门、合同与检查半径。
- **上屏**：扩展点路由四问（事实 / 拦截 / 能力 / loop）+ 参与阶梯。
- **讲点**：这是「不乱发挥」的前半段——**改哪里先问归属**。组织读法：谁能改配置、谁能加能力、谁能换后端、谁能改 loop，各有一道门。**回指第二幕**：Plan/Design 的产品 owner 审批（P16/P19）、Build 的 hooks（P23）、Deploy 的 PR review + managed settings（P31/P32）——都是「把门做成机制」。直接引出 P48 的四项治理决定。
- **视觉**：参与阶梯（四层 + 门）。

### P45 可执行反馈：gate 可信，因为负例会持续证明它真会拒绝
- **页面结论**：能机械判断的规则全部落到执行，而且门禁自己被测试——证明无效案例会被拒绝。
- **上屏**：类型 / load / 测试 / snapshot / invariant / CI；「Agents follow enforced gates far more reliably than prose conventions.」
- **讲点**：这是「不乱发挥」的后半段，也是 DSH 最值得抄的一句话。org 读法 = 确定性优先的最硬实现：文档负责「告诉你往哪看」，系统负责「证明你做对了」。**机制落地**：DSH 的工具执行管道 `tools/pre-execute → execute → post-execute`，`pre-execute` 就是 allow/deny/ask 的门禁，timeout 挂在 execute 上——门禁不是散在每个 tool 里，是统一守在管道上。**回指第二幕**：Test 的 evals（P28）、Deploy 的 hooks as gates（P32）都是「把对错做成机器可判的门」——DSH 更进一步，连门禁本身都被测试（证明无效案例会被拒绝）。
- **视觉**：门禁清单 + 「门禁被测试」示意。

### P46 定制/替换：共享控制面要统一合同，不统一每个后端
- **页面结论**：一条 seam 是「可替换的完整能力」——Definition / Provider / Consumer 三角色齐了才算；「换一个后端，Consumer 不用改」。
- **上屏**：Definition（声明）+ Provider（实现）+ Consumer（使用）。
- **讲点**：这就是「给不同环节定制」的机制——组织换沙箱、换模型、换持久化，业务 Consumer 一行不改。**再加一层**：DSH 的整机是「一切皆插件」——loop、会话服务、模型适配器、工具注册表本身都是插件，**新行为挂到扩展点上，而不是去改 loop 源码**。org 读法：**平台团队把「能替换、能扩展」做成一等公民，业务团队才能按环节定制、加能力不改核心。**
- **视觉**：三角色图 + 换后端示意。

### P47 重建事实：模型可见的输入、工具结果与审批必须可从日志还原
- **页面结论**：模型可见 ⟺ 已记录；审批成对、无人可答就失败关闭——这是「敢放手」的底座。
- **上屏**：append-only session log；`asked/decided` 成对；fail-closed；会话格式版本纪律。
- **讲点**：组织读法 = 「谁能重建事实」的运行时保证。三条不变式：① 模型看到的每一件事都能从日志重建（loop 构建期检查，不是文档承诺）；② 审批是成对的审计事件，没有 answerer 时 fail-closed；③ 会话格式有版本纪律、冷读可恢复。**审计对称**：同一张日志也记录 DSH 官方自己的行为。
- **视觉**：append-only log + 成对审批。

### P48 四项治理决定 + 采用顺序
- **页面结论**：准入/替换/放行/重建事实各需明确机制；组织采用顺序是先工件、再 gate、最后关 loop。
- **上屏**：准入=registry+knowledge map；替换=adapter+seam；放行=enforced gate+invariant；重建事实=session log。
- **讲点**：把 P44–P47 收成四个可操作的决定。采用不从自动化整个 loop 开始：先让一次交接有可读工件和 owner，再把必须成立的规则做成 gate，当事实可读、门禁可信后再关 loop。生态数量、star 和可替换率留在证据库，不承担这一页的组织结论。
- **视觉**：四决定 → 四机制对齐图 + 落地三步。

## 收尾（P49–P50）

### P49 带走一句
- **页面结论**：代码不再是瓶颈，流程才是。
- **上屏**：「代码不再是瓶颈，流程才是。」
- **讲点**：回到开场：当 Build 加速而 lead time 不变，问题就在代码两侧的交接、门禁和反馈。转型不是追求更多代码，而是让整条 SDLC 可交接、可执行、可问责、可回流。
- **视觉**：slogan 大字 + 六阶段 loop 暗线。

### P50 从最慢的一次交接开始
- **页面结论**：选一条价值流，找到最慢的一次交接，为它补齐一个工件、一道 gate、一个 owner 和一个 feedback 指标。
- **上屏**：四个空格：Artifact / Gate / Owner / Feedback；问题「你们的链上，哪一次交接最慢？」
- **讲点**：这是会后行动，不是泛泛致谢。试点完成标准：一次真实变更能沿新路径走完，且能用 lead/queue/rework/failure 中的至少一个指标对比改造前后。
