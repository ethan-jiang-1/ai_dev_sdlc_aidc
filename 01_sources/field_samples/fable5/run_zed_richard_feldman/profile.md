# Richard Feldman / Zed

- 身份：`zed-industries/zed` 公开仓库维护者之一；本次 Fable 5 集成 PR 的主要推进者是 `rtfeldman`
- 角色定位：面向终端产品的工程/产品集成样本，不是单纯模型使用者，而是把 Fable 5 接进真实桌面产品并处理隐私与回退逻辑的人
- 为什么值得单列：这条线不是在夸 Fable 5 的能力，而是在回答一个更硬的问题: 当一个产品要正式支持 Fable 5 时，数据保留、同意门槛、拒绝后的体验和默认回退怎么设计
- 核心贡献：把 `Zero Data Retention` 约束显式写进产品设置和错误处理流程里，并在 Fable 拒绝请求时透明回退到 `Claude Opus 4.8`
- 最重要的判断：Fable 5 的能力再强，只要数据保留策略不满足产品要求，它就不能被当成“无条件默认模型”直接打开

## 这条样本到底说明了什么

- `Zed` 这条线最值钱的不是“支持了 Fable 5”，而是它把 Fable 5 接入产品时真正卡人的地方全部公开了。
- PR `#58945` 里明确写出：Fable 5 不能在 `Zero Data Retention` 条件下提供，因为 Anthropic 会保留 30 天推理日志，所以必须增加显式的数据保留同意开关。
- 它还不是停在设置层，而是继续深入到运行时：如果缺少同意，就抛出不可重试的 typed error；如果 Fable 拒绝请求，则透明切回 `Opus 4.8`，用户不用重打消息。
- 这意味着 `Zed` 把 Fable 5 视为一个要同时经过隐私、产品体验、错误恢复三层约束的系统组件，而不只是一个“更强模型选项”。

## 最值得记住的判断

- 这条样本补上了资料库里很重要的一类外部证据：当 Fable 5 进入真实产品而不是个人终端时，能力不是唯一决策因素，合规和交互恢复路径同样决定它能不能上线。
- 它和 `plugin-codeforge` 形成很好的对照：
- 前者强调 agent 岗位分配和 runtime governance
- 这条线强调产品级隐私同意、数据保留约束和 user-facing fallback
