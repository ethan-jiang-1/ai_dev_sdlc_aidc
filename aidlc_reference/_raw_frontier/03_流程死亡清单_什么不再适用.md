# 流程死亡清单：他们宣布了什么不再适用

> 来源：`ai_sdlc_frontier/` 七位人物 + 三份深度研究
> 研究日期：2026-07-07
> 核心问题：这些站在最前沿的人，明确宣布了哪些流程、做法、假设已经"死了"？

---

## 零、死亡的标准

这里收录的不是"有人觉得不太好"的流程，而是被**明确宣布不再适用**、**已经停止使用**、或**被证明有系统性危害**的做法。

每条标注：
- **宣布者**
- **死亡程度**：☠️ 已死（宣布者自己已停止）/ ⚠️ 垂死（宣布者认为应该停止但仍在过渡）/ 🔮 预言死亡（宣布者预测将死）
- **替代方案**

---

## 一、规划类

### ☠️ 六个月产品路线图

**宣布者**：Fiona Fung (Anthropic)

> "When I first joined the Claude Code team, we wrote a pretty good six month roadmap, and then because of Claude Code, so many things changed that it was out of date by month three."

**为什么死**：AI 本身在加速变化。你规划的"六个月后要做什么"基于的是"六个月后世界会怎样"的假设——这个假设在 AI 时代撑不过三个月。

**替代方案**：JIT（即时规划）——原型 → 拉内测用户 → 根据反馈迭代

---

### ☠️ 设计文档争论

**宣布者**：Fiona Fung

> "Build is cheap. Argument is expensive."

**为什么死**：当原型成本降到接近于零时，与其在文档里争论方案优劣，不如直接出几个原型看效果。

**替代方案**：先原型，再讨论。Fable 5 的"出 4 种设计方向"模式——低成本差异化的原型比抽象争论更能暴露真实偏好。

---

### ☠️ "先想清楚再动手"

**宣布者**：Thariq Shihipar + Erik Schluntz

> "仅仅提前规划并不总是足够的。你可能会在实现深处发现未知项。"

**为什么死**：不是不需要想——而是"想清楚"这件事本身也需要 AI 参与。人无论怎么提前想，总有些未知项只有在实现深处才会暴露。

**替代方案**：blindspot pass 前置扫描 + 实现笔记（记录偏离）+ 接受"想清楚"是一个贯穿全过程的迭代行为，不是前置一步到位的。

---

### ☠️ Sprint 排期/预估

**宣布者**：Fiona Fung（隐含）+ Ryan Lopopolo（数据支撑）

Fiona 放弃了传统的 sprint planning。Ryan 的数据：每人每天 3.5 个 PR，传统排期完全跟不上这个节奏。

**为什么死**：当吞吐量是传统开发的 10 倍时，"这周能做几个 story point" 这种估算失去了意义。瓶颈不再是"能做多少"，而是"什么值得做"。

**替代方案**：JIT planning + 按价值排序而非按工作量排期。

---

## 二、Review 类

### ☠️ 人类全覆盖 Code Review

**宣布者**：Fiona Fung, Ryan Lopopolo

Fiona：Claude 负责风格、lint、bug、测试，人只审法律、安全、品味。

Ryan：**"人类审查 PR 已不再是必需流程。"** 几乎全部审查已调为 agent 之间完成。

**为什么死**：人的注意力是硬约束，AI 的产出量远超人的审查能力。逐行 review 终将成为瓶颈（Erik Schluntz）。

**替代方案**：
- Trust but Verify（Fiona）
- Agent 自我审查循环（Ryan）
- 人类验证产品行为而不是代码行（Erik）

---

### ☠️ "找到代码作者问"

**宣布者**：Fiona Fung

> "Now, since all our PRs are assisted by Claude, 'Who made this change?' is no longer sufficient."

**为什么死**：代码是 AI 写的，"谁写的"失去了原来的信息量。真正需要的是"为什么这样写"、"有没有人审过"、"有没有已知问题"——这些问题的答案不在作者那里。

**替代方案**：先问 Claude。每次追问"这个能自动化吗？"

---

### ⚠️ 基于 diff 的代码理解

**宣布者**：Thariq Shihipar

> "只看代码 diff 往往只能让我对发生了什么有一个浅层理解，因为很多行为都取决于既有代码路径。"

**为什么死**：AI 的一次变更可能跨越很多既有代码路径。diff 只显示了变化，没显示变化与既有系统的交互。

**替代方案**：让 Claude 出 HTML 报告（上下文 + 直觉解释 + 具体变更 + 测验），人通过测验证明自己理解了，才合并。

---

## 三、角色类

### ☠️ 工程师 = 写代码的人

**宣布者**：Ryan Lopopolo（最极端）, Fiona Fung, Jesse Vincent

Ryan 的团队原则：**不手写代码。** Fiona 的团队里 PM 写代码，工程师做设计。

Jesse Vincent（从 fable5_field_signals 交叉引用）：

> "Those who love hand-tuning algorithms will find that this is now a hobby, rather than work humans should be doing."

**为什么死**：当 AI 能写代码时，"写代码"不再是区分工程师和非工程师的边界。区分边界变成了：谁能定义问题、设计验证、做出判断。

**替代方案**：
- 工程师的新角色：设计环境、澄清意图、构建反馈回路（Ryan）
- 只重点招两种人：有产品感的 creative builder + 深度系统专家（Fiona）
- 写作能力比算法能力更重要（Jesse Vincent）

---

### ☠️ PM 只规划不写代码

**宣布者**：Fiona Fung

> "Our PMs code a lot now, which is fun to see. With Claude, you have nontraditional coders now being able to do more engineering."

**为什么死**：写代码的门槛降到接近于零 → "会不会写代码"不再是一个有效的角色划分标准。PM 可以直接用 Claude 把想法变成原型。

**替代方案**：角色模糊。PM 做原型，工程师做设计，设计师参与产品决策。

---

### ☠️ 雇人看裸编码吞吐量

**宣布者**：Fiona Fung

> "What I index on less, on the other hand, is raw throughput; the models handle that."

**为什么死**：模型已经覆盖了吞吐量。人的价值在吞吐量之外——判断力、品味、系统思维。

**替代方案**：雇人看判断力，看"你知不知道边界该画在哪"（Erik Schluntz）。

---

## 四、上下文类

### ☠️ 一个超大的 AGENTS.md / CLAUDE.md

**宣布者**：Ryan Lopopolo（实验验证）, Jediah Katz（独立验证）

Ryan 的实验结论：超大 AGENTS.md 是**失败方案**——
- 挤占上下文 → 漏掉关键约束
- "一切重要 = 一切都不重要"
- 迅速腐化成陈旧规则坟场
- 无法机械检查新鲜度

ETH Zurich (Galster et al., 2026) 独立验证：LLM 生成的 AGENTS.md 实际上**降低了 3% 的任务成功率**，增加了 20% 推理成本。

**为什么死**：上下文是稀缺资源。信息过载比信息不足更危险。

**替代方案**：
- AGENTS.md ~100 行作为目录页（Ryan）
- 动态上下文发现——agent 按需拉取（Jediah）
- 只写在代码中不可推断的细节（ETH Zurich 研究结论）

---

### ⚠️ 静态上下文全量注入

**宣布者**：Jediah Katz

> "As models have become better as agents, we've found success by providing fewer details up front."

**为什么死**：模型已经从"我给你什么你看什么"进化到"我知道我还需要什么，我自己去找"。全量注入不仅浪费 token（A/B 测试 -46.9%），还会引入矛盾信息导致幻觉。

**替代方案**：动态上下文发现——文件化 + 惰性加载。能动态的绝不静态。

---

### ⚠️ 截断长工具输出

**宣布者**：Jediah Katz

**为什么死**：截断可能丢失关键信息（一个被截断的错误信息可能就是 debug 的关键线索）。

**替代方案**：完整输出写入文件，agent 用 tail 检查末尾、grep 搜索相关部分、按需 read 更多。

---

## 五、合并与质量类

### ⚠️ 多个阻塞式合并门

**宣布者**：Ryan Lopopolo

> "在一个智能体吞吐量远高于人类注意力上限的系统里，修错的成本很低，等待的成本却很高。"

**为什么死**：传统门控假设"拦住一个问题比放过去再修更划算"。这个假设在低修复成本、高吞吐量环境下不再成立。

**替代方案**：极少数阻塞门。Flaky 测试不阻塞，后续重跑处理。结构约束 + linter 捕捉系统性问题。

---

### ⚠️ "Flaky 测试必须修了才能合"

**宣布者**：Ryan Lopopolo

> "测试的偶发失败通常通过后续重跑解决，而不是无限期阻碍进度。"

**为什么死**：不是 flaky 测试不重要——而是在高吞吐量环境中，阻塞的代价 > 偶发 flaky 带来的风险。

**替代方案**：后续重跑处理。但如果 flaky 率超过阈值，触发自动化修复。

---

### 🔮 人类逐行 Code Review 作为质量保障

**宣布者**：Erik Schluntz

> "当模型 7 个月翻一倍能力时，人类逐行 code review 会成为瓶颈。你必须找到不读代码也能验证的抽象层。"

**为什么将死**：不是现在完全不用——Erik 仍然要求核心逻辑逐行审查。但随着模型能力继续翻倍，人的审查速度跟不上。必须找到替代的验证方式。

**替代方案**（正在建立中）：
- 长跑压力测试 + I/O 标准（Erik）
- 可验证的检查点——不看代码看产品行为（Erik）
- Agent 自我审查循环（Ryan）
- 结构约束 + linter 自动化（Ryan）

---

## 六、知识管理类

### ☠️ 知识在 Slack/Google Docs/人脑里

**宣布者**：Ryan Lopopolo

> "凡是不在代码仓库里、不能被运行时上下文访问的知识，对 Codex 来说都等同于不存在。"

**为什么死**：agent 只能看到仓库里可版本化的内容。Slack 讨论、Google Docs 设计文档、人脑里的上下文——对 agent 不可见。

**替代方案**：
- 一切推入仓库，版本化、可搜索
- 讨论结论转为 docs/ 下的结构化文档
- 架构决策记录（ADR）成为一等工件

---

### ☠️ 写文档是"最好有"的事后工作

**宣布者**：Ryan Lopopolo

Ryan 的团队把文档当做**代码本身**来治理：专用 linter + CI 检查新鲜度 + doc-gardening agent 定期扫描过时文档并自动发起修复 PR。

**为什么死**：在 agent-first 世界，文档是 agent 的操作系统。腐化的文档 = agent 做出错误决策。

**替代方案**：文档进入 CI pipeline。新鲜度、交叉链接、结构合理性全部自动化检查。过时文档自动修复。

---

## 七、清理与维护类

### ☠️ 人工定期清理技术债

**宣布者**：Ryan Lopopolo

> "我们团队每周五都拿出将近一整天，也就是一周约 20% 的时间，专门清理所谓的 'AI 残留物'。显然，这种做法根本不可扩展。"

**为什么死**：AI 产出速度远超人工清理速度。20% 时间清理不够用。

**替代方案**：持续 GC——后台 agent 定期扫描偏差 → 自动发起小重构 PR → 一分钟内审查合并。

---

### ⚠️ "技术债先记下来，以后还"

**宣布者**：Ryan Lopopolo + Rody Davis

> "技术债务就像高息贷款：持续、小额地偿还，总比任其累积，最后再痛苦地一次性清账要划算得多。"（Ryan）

> "像盆景艺术家一样持续修剪代码库。"（Rody Davis）

**为什么死**：agent 会复制仓库里已有的模式——包括不好的模式。不持续清理的话，坏模式会通过 agent 的输出扩散到整个仓库。

**替代方案**：持续小修剪，不清大账。

---

## 八、模型使用类

### ☠️ 所有任务用同一个模型

**宣布者**：Willie Williams + mclayer/plugin-codeforge（从 fable5_field_signals 交叉引用）+ Jediah Katz（模型版本级定制）

**为什么死**：
1. 最强模型 ≠ 最好用的协作者（Willie Williams）
2. 不同阶段需要不同的能力/成本/速度组合
3. Cursor 甚至按模型版本定制工具格式

**替代方案**：外科手术式采用（mclayer）——Fable 只用于重任务，编排层保持 Opus，小修小改用轻模型。

---

### ⚠️ 所有 MCP 工具全量加载

**宣布者**：Jediah Katz

A/B 测试：动态加载 → token **-46.9%**。

**为什么死**：大量工具描述占据上下文，但大多数对话中只用少数几个。全量加载 = 为不用的东西持续交 token 税。

**替代方案**：工具名在静态上下文，完整描述按需加载。agent 用 grep 查找需要的工具。
