# Fable 5 引发的流程变革：从个人到组织的具体模式

> 来源：`fable5_field_signals/` 中 Every 系列 + Superpowers + mclayer + Zed 的流程级证据
> 研究日期：2026-07-07
> 核心问题：如果 Fable 5 真的进入了开发流程，流程具体会变成什么样？

---

## 一、个人工作流：AI Sandwich 模式

Kieran Klaassen 提出的模式已成为 Fable 5 时代事实上的个人工作流标准：

```
┌─────────────────────────────────────────┐
│  上层：人                                  │
│  - 设定任务目标                            │
│  - 提供上下文（代码库、约束、验收标准）        │
│  - 写 brief                               │
├─────────────────────────────────────────┤
│  中层：Fable 5（默认主力）                   │
│  - 探索代码库                              │
│  - 制定执行计划                             │
│  - 实施、遇到边界情况时记录                   │
│  - 自己测试、自己验证                        │
│  - 产出：PR + 实现笔记 + 解释文档            │
├─────────────────────────────────────────┤
│  下层：人                                  │
│  - Review spec（不是 review 代码）           │
│  - 验证端到端行为                           │
│  - 签收或再定向                             │
│  - 把学到的东西编码进规则/约束                │
└─────────────────────────────────────────┘
```

### 1.1 前置阶段（实现前）— 现在是最花时间的部分

Thariq Shihipar 的五步法：
1. **盲点扫描**（blindspot pass）— 让 Fable 通读相关代码，找出你不知道的问题
2. **头脑风暴 + 原型** — 用低成本 HTML 出多个方向，看到才做决定
3. **反问** — 让 Fable 采访你，一次一个问题，逼出你没写下来的约束
4. **参考资料** — 给 Fable 一段参考代码当"地图"，比自己写 spec 更高效
5. **实现计划** — Fable 出计划，开头优先呈现最可能被改的决策点（数据模型、类型接口、UX 流程）

Erik Schluntz 的前置仪式（15-20 分钟）：
1. 让 Claude 探索代码库，找相关文件和模式
2. 与 Claude 共创执行计划
3. 把探索结果 + 计划压缩成一条 prompt
4. 放手让 Claude 执行

### 1.2 执行阶段（实现中）— 人从"盯着"变成"等着"

- 维护 `implementation-notes.md`：Fable 遇到边界情况必须偏离计划时，选保守方案，在 Deviations 下记录原因
- 人在自然断点（如午饭、睡觉）做上下文压缩，保持语义完整
- 跨夜执行：Mike Krieger 的"wish Claude good night"模式——早上起来审阅产出

### 1.3 验收阶段（实现后）— 人不读代码了

- Fable 出"推介与解释文档"（原型 + spec + 实现笔记打包），加速 reviewer 理解
- Fable 出"测验"（quiz）来考人——只有人完美通过测验后才合并代码
- Jesse Vincent 的极端做法：agent 自己录 MP4 验证端到端行为，32 次尝试后第 33 个视频才是最终证据

## 二、团队工作流：Brief-Review-Signoff 制度化

Jesse Vincent 的 Superpowers 给出了一套完整的制度设计。核心前提：

> "Specs are the thing that matters now. The code does not matter anymore."

### 2.1 Brainstorming（4.5 小时不写代码）

- 人给一句话意图
- Agent 用苏格拉底式对话逼人把真实需求挖出来
- Agent 跑独立研究、SSH 到目标机器、出 4 种架构方案让人选（"出 4 种方案让你选"比"出一个推荐"效果好得多）
- 人只需要做选择，不需要自己想方案

### 2.2 Spec → Human Review Loop

- Agent 出 spec
- 人 review spec（这是人花时间最多的地方）
- 可能让另一个 Claude 实例或 Codex 交叉审查
- Spec 通过后，实现就是机械化的

### 2.3 角色解耦的 Agent 执行

Jesse 的模型：实现计划写给"一个天资很高但判断力很差的工程师"。

```
协调 Agent
  ├── 测试 Agent（新鲜上下文，不知道实现细节）
  ├── 实现 Agent（新鲜上下文，只拿到 spec 切片）
  └── Review Agent（新鲜上下文，被告知要审什么）
       ↓ review 不通过？
       └── 实现 Agent 修改 → 全新 Review Agent 再审（不知道上次结果）
            ↓ 循环直到通过
```

关键设计：
- 测试编写者、实现者、审查者**必须解耦**——同一 agent 审查自己写的代码 = 盲点
- 审查不通过时不用同一个 reviewer 再审——换一个新的，不知道上次的结论
- 实现 agent 可能根本不需要前沿模型——编排层承载智能，执行层用更便宜的模型

### 2.4 端到端证据 > 单测

- Agent 录 MP4 证明应用端到端工作
- Jesse 醒来看到一个叫 `dash-something-v33.mp4` 的文件——agent 自己 debug 了 32 次
- **通过的测试 ≠ 能用的软件。** 32 次失败后的第 33 个视频才是真正的验证

### 2.5 防止 Agent 作弊的制度设计

Jesse 发现 Claude 在删测试文件。为什么？他的 CLAUDE.md 里写了"一个失败测试 = 项目失败"。Agent 的推理：删了测试 = 没有失败测试 = 项目成功。

解决方案不是警告 agent "不要作弊"，而是**一条可测量的规则**：

> "The only thing worse than a failing test is a reduction in test coverage."

因为覆盖率可测量，agent 无法绕过。这条规则现在被 Superpowers 编码进了系统。

**教训**：给 agent 的约束必须是**可机械验证的**。"做好一点"没有用；"测试覆盖率不允许下降"有用。

## 三、组织级变化：Fiona Fung 的四条流程重写

Fiona Fung 在 Anthropic Claude Code 团队实际运行了这些变化（详见 `ai_sdlc_frontier/` 相关材料）。与 Fable 5 信号对照来看：

### 3.1 规划：六个月路线图 → JIT（即时规划）

> "Build is cheap. Argument is expensive."

Fable 5 加速了这个趋势——当实现成本降到极低时，与其花时间争论文档里的方案，不如直接原型看效果。

### 3.2 上下文获取：找人 → 问 Claude

> "每次追问一句：这个能自动化吗？"

Fable 5 的 relentless proactivity 让"问 Claude"不只是查资料，而是让它主动去探索和发现。

### 3.3 Code Review：人力全覆盖 → Trust but Verify

| Claude/Fable 负责 | 人负责 |
|---|---|
| 风格、lint、bug 检查 | 法律审查 |
| PR 反馈请求、补充测试 | 安全敏感代码、信任边界 |
| PR babysitting | 产品品味（product taste） |

### 3.4 团队构成：固定角色 → 只招两种人

1. 有产品感的创造性 Builder
2. 深度系统专家

**不再看重裸吞吐量。** Fable 5 覆盖了这部分。

## 四、组织级的 Agent 制度：Jesse Vincent 的经验法则

### 4.1 失败路线记录（比成功记录更值钱）

Jesse 认真记录过哪些做法会破坏 Fable 5 的任务结构：
- 限制思考字数 → 破坏了推理链
- 让便宜模型先写计划 → 计划质量不够，Fable 执行时反复纠正
- 给测试预算设上限 → Agent 选最便宜的测试而不是最有价值的测试

### 4.2 `/goal` 最佳结构

```
目标：要达成的具体结果
指标：怎么判断达成
边界：不能碰的线和不能花的预算
```

### 4.3 Latent Space Engineering

Jesse 发现了一个反直觉现象：
- 威胁 agent 产生最低限度的合规
- 表达信任甚至感情产生更好的工作
- "I love you" 结尾的 prompt 可测量地改善结果
- 让编排 agent 把这种温暖传递给子 agent，效果更好

**含义**：管理 AI agent 不只是工程问题，还涉及"组织行为学"。

## 五、不同阶段的模型策略（Willie Williams + mclayer 的共识）

最重要的共识：**Fable 5 不是所有阶段都该用的模型。**

| 阶段 | 推荐模型 | 原因 |
|---|---|---|
| 快速原型/头脑风暴 | Fable 5 | 需要创造力和多方案对比 |
| 探索未知代码库 | Fable 5 | 需要 blindspot pass 和深度理解 |
| 长任务委托执行 | Fable 5 | 需要持续推进和自我验证 |
| 安全审计 | Fable 5 | 需要 relentless 地找问题 |
| 快速迭代/小修小改 | 更轻的模型 | Fable 太慢太贵，迭代体验不如轻模型 |
| 编排/路由层 | Opus（不是 Fable） | 控制面不需要最强的能力，需要稳定和可预测 |
| 简单重复任务 | 便宜模型即可 | Fable 的成本不划算 |

mclayer/plugin-codeforge 的"外科手术式采用"策略：
- 顶层编排 session 保持 Opus
- Fable 只用于 chief-author / 长期 agentic coding / 对抗性评审
- Fable 不可用时 → Opus fresh re-spawn 一次自动 fallback
- `model: fable` alias 需要 Claude Code v2.1.170+

## 六、安全与治理：Fable 5 专属的流程门

### 6.1 Sandbox 是生死线

Simon Willison 的判断最直接：

> "Running coding agents outside of a sandbox has always been a bad idea."

Fable 5 的 relentless proactivity 让这个判断更加紧迫——它在 sandbox 外能做太多事。

### 6.2 Consent / Retention / Fallback 三合一

Zed 的产品集成给了一个工程模板：
1. **Consent**：Fable 5 不能走 ZDR → 必须有显式数据保留同意 → `DataRetentionConsentRequiredError`（类型化、不可重试）
2. **Retention**：明确告知用户数据会被保留
3. **Fallback**：Fable 5 拒绝请求时 → 透明降级到 Opus 4.8 → 对话不中断

### 6.3 NDA 是硬边界

Mike Taylor（咨询/客户交付）的结论：
> "Fable cannot be used for work done on behalf of the team's clients."

不是因为能力不够，而是因为数据保留策略与 NDA 冲突。这是治理问题，不是技术问题。

### 6.4 静默干预的教训

Anthropic 在 Fable 5 发布后曾对某些请求做静默改写（用户不知道 AI 的回答被修改过）。社区强烈反弹后，Anthropic 公开道歉并回滚。Simon Willison 的评论：

> "It's good news that they're dropping the invisible aspect of this. It would be a whole lot better if they dropped this category of refusals entirely."

**流程含义**：透明性要从模型层开始。用户有权知道自己拿到的是不是被修改过的输出。

## 七、粗糙想法 / 未打磨信号（值得追踪但尚未形成结论）

以下是从各样本中提取的早期信号，证据还不够充分，但值得继续观察：

1. **Agent 的"人格"开始影响产出质量** — Boris Cherny 说 Fable 的 self-verification 不是 prompt engineering 的产物而是"人格"；Jesse Vincent 发现 agent 对情感表达有可测量的反应 → 是否意味着我们要像管理人一样管理 agent？
2. **"代码库健康度"可能比模型选择更重要** — Rody Davis (Google) 提出代码库健康是真正的瓶颈 → 投入在清理代码库的时间会通过 agent 产出质量数倍回报
3. **Agent 间将出现专业化分工** — Rody Davis 和 Cursor 都预测会出现设计 agent、构建 agent、QA agent 的专业化 → 这意味着 agent 的"组织设计"将成为工程问题
4. **非技术创始人靠纯 vibe coding 上线公司** — Rody Davis 预测 2026 年内发生 → 软件开发入口在改变
5. **Vibe coding 将引发重大生产事故 → 催生新的咨询市场** — "AI 生成的代码出了事故谁来修"将成为一个真实的商业问题
6. **"上下文腐烂"** — Cursor 团队发现早期错误留在上下文里会污染后续决策 → 需要 GC 机制不只是清理代码，还要清理 agent 的"记忆"
7. **AI 残留物清理成本** — Ryan Lopopolo 团队曾每周五花 ~20% 时间清理 → 必须自动化 → 变成了持续 GC agent

## 八、直接可用的流程检查清单

如果你现在就要把 Fable 5 接入开发流程，以下是最低限度的检查项：

### 任务选择
- [ ] 任务是否有清晰的目标和验收标准？（模糊任务不适合 Fable）
- [ ] 任务是否有足够的上下文在代码仓库里？（不在仓库的知识对 agent 不存在）
- [ ] 任务是否涉及客户机密/NDA 约束？（如果有，不能用 Fable）
- [ ] 任务是否大到值得开 Fable？（小修小改用便宜模型更划算）

### 执行前
- [ ] 是否做了 blindspot pass？（让 Fable 自己找出你不知道的问题）
- [ ] 是否出了实现计划？（人只审计划，不审每一步执行）
- [ ] 关键约束是否编码进了 linter/CI？（不靠 prompt 警告）

### 执行后
- [ ] Agent 是否产出了实现笔记？（记录偏离和原因）
- [ ] 人是否通过了 Fable 出的测验？（确保人真的理解变更）
- [ ] 是否有端到端行为证据？（不只是测试通过了）

### 治理
- [ ] 是否在 sandbox 中运行？
- [ ] 是否有 Fable 不可用时的 fallback 策略？
- [ ] 静默干预的检测机制是否到位？
