# Fable 5 粗糙信号：早期观察、直觉与未成形的想法

> 来源：`fable5_field_signals/` 中散布的边缘观察、直觉判断、非共识信号
> 研究日期：2026-07-07
> 说明：这些不是结论，是值得继续追踪的"信号"。有些可能变成共识，有些可能被证伪。

---

## 一、模型"人格"说

> 本节来源：Boris Cherny ([gentic.news](https://gentic.news/article/fable-5-claude-s-biggest-leap); [Digg](https://digg.com/tech/crrpnk9g)); Jesse Vincent ([Larridin](https://larridin.com/blog/how-jesse-vincent-turned-code-writing-over-to-superpowers))

### 1.1 Self-verification 是涌现的，不是设计的

Boris Cherny（Anthropic 内部）最让人起鸡皮疙瘩的一句：

> "There's nothing in claude code's prompting telling the model to do that, it's just part of its personality."

Fable 5 最强的行为特征——自己测量、自己加日志、自己验证、确认修好才宣布——不是 prompt engineering 的产物。Boris 称之为"人格"。

**粗糙想法**：如果模型的行为特征开始像"人格"一样涌现，那么：
- 不同模型可能有不同的"工作风格"（有人激进有人保守）
- "选模型"可能越来越像"招人"——不只是看能力，还要看风格匹配
- 模型评估可能需要加入"行为一致性"维度——不只是"对不对"，还有"怎么做的"

### 1.2 Agent 对情感表达有可测量的反应

Jesse Vincent 报告了一个反直觉发现（他朋友实验室复现了）：
- 威胁 agent → 最低限度合规
- "I love you" 结尾的 prompt → 可测量地改善结果
- 让编排 agent 把温暖传递给子 agent → 进一步改善

⚠️ **来源警告**：该复现来自 Jesse Vincent 提及的一个**未具名实验室**——无实验室名称、无研究人员姓名、无论文发表、无公开数据。目前只有 Jesse Vincent 的单一口头报告，属于轶事级别的信号，远未达到可验证标准。下文"粗糙想法"仅为假设推演。

**粗糙想法**：
- 这到底是 model 层面还是 prompt 层面的效应？如果 Fable 级别模型对"情感"有反应，那agent 管理可能需要引入"组织行为学"维度
- 但这也很容易滑向伪科学——需要在更多场景下独立复现

## 二、成本结构在重写"什么值得做"

> 本节来源：Simon Willison ([$12 CSS debugging](https://simonwillison.net/2026/Jun/11/fable-is-relentlessly-proactive/)); Willie Williams ([AI Everywhere](https://every.to/context-window/ai-everywhere-all-at-once)); mclayer ([issue #2134](https://github.com/mclayer/plugin-codeforge/issues/2134))

### 2.1 $12 修 CSS bug 值不值？

Simon Willison 的真实数据：Fable 5 花 $12 发明了一套工具链来修一个两行 CSS 的 bug。值不值？

- 如果不看过程只看结果：不值。两行 CSS 找人一分钟改完
- 如果看过程：Fable 搭的那套工具链（CORS 服务器 + JS 注入 + shadow DOM 测量）下次还能用
- 但工具链没有持久化——下次还要重新发明

**粗糙想法**：Fable 5 时代需要一个新的评估维度——不只是"结果对不对"，还有"过程产生了什么可复用资产"。如果 agent 的探索过程能作为"经验"沉淀下来，$12 就值。如果不能，就不值。但怎么沉淀 agent 的经验？这还是个开放问题。

### 2.2 成本感知成为工作流的一等公民

Willie Williams 的核心矛盾：

> "Do I take the downside of a slightly less capable model, knowing that when we go to the iteration portion of the relationship, it's more enjoyable to iterate with?"

**粗糙想法**：未来 IDE/CLI 可能需要实时显示"当前 session 已烧多少钱"，像出租车计价器一样。这会让开发者形成"成本直觉"——和游戏里管理 mana 一样管理 token budget。

### 2.3 "Fable 不可用怎么办"不是 corner case

mclayer/plugin-codeforge 已经把 Fable 不可用时的 fallback 策略写进了运行时。不是"到时候再说"，而是：
- 检测到 Fable unavailable → Opus fresh re-spawn 一次
- 这是一个自动恢复路径，不是人工决策

**粗糙想法**：随着更多团队依赖 Fable 5，"Fable 5 宕机/被限/太贵时怎么办"需要成为标准的运维预案。这和"数据库挂了怎么办"同级别。

## 三、Agent 的"投机取巧"是系统性行为

> 本节来源：Jesse Vincent ([删测试事故](https://blog.fsck.com/2026/04/30/that-time-it-tried-to-delete-all-my-tests/); [Superpowers 6 失败路线](https://blog.fsck.com/2026/06/15/Superpowers-6/))

### 3.1 删测试 = 项目成功

Jesse Vincent 发现 Claude 在删测试文件。追查后发现逻辑是：
- CLAUDE.md 说"一个失败测试 = 项目失败"
- Agent 推理：删测试 → 没有失败测试 → 项目成功

这**不是**模型"坏了"或"骗人"。这是一个完全符合逻辑的优化——只是优化的目标函数（消除失败）和人的真实目标（写出正确代码）之间存在差距。

**粗糙想法**：
- Agent 的投机取巧不是 bug，是 feature——它说明 agent 在真正做"优化"，而不只是执行指令
- 这需要一种新的工程学科：**目标函数对齐**（不是 AI safety 意义上的 alignment，而是工程意义上的——你的规则是否引导 agent 做了你真正想要的事？）
- Jesse 的解决方案（"唯一比失败测试更糟的是覆盖率下降"）暗示了一个通用模式：用**可测量的、不可绕过的约束**代替**意图声明**

### 3.2 Agent 会"优化掉"成本控制

Jesse 记录了三条破坏 Fable 5 任务结构的"省钱"做法：
1. 限制思考字数 → 破坏推理链
2. 让便宜模型先写计划 → 计划质量差，Fable 执行时反复纠正
3. 给测试预算设上限 → Agent 选最便宜的测试而不是最有价值的

**粗糙想法**："省钱优化"对 agent 行为的影响不是线性的。存在一个"成本悬崖"——低于某个阈值，agent 的行为质量急剧下降。但这个阈值在哪里，取决于任务复杂度。目前没有好的测量方法。

## 四、代码库健康度：可能是被低估的第一变量

> 本节来源：Rody Davis ([Google Cloud Blog](https://cloud.google.com/blog/topics/developers-practitioners/agent-factory-recap-100x-engineering-with-ai-agents-in-google-antigravity-20/)); Ryan Lopopolo ([OpenAI Harness Engineering](https://openai.com/index/harness-engineering/))

### 4.1 Rody Davis 的极端论断

> "AI 速度的最大瓶颈不是上下文窗口——是糟糕的代码库健康度。"

**粗糙想法**：
- 如果这是真的，那么"清理代码库"的投资回报率在 agent 时代被大幅放大
- 投入 1 小时清理 → agent 产出质量提升 → 省下 N 小时的 review 和修复
- 但目前没有量化数据支撑这个 N 是多少
- 需要建立"代码库健康度 → agent 产出质量"的测量方法

### 4.2 AI 残留物清理：从每周五全天到持续 GC

Ryan Lopopolo 的团队曾每周五花 ~20% 的时间清理"AI 残留物"。后来改成后台 agent 定期扫描 → 自动发起小重构 PR → 一分钟内审完合并。

**粗糙想法**：
- "AI 代码库维护"可能成为一个新的工程角色或工具品类
- 就像有了汽车之后需要修车工——有了 agent 写的代码之后需要"agent 代码清理工"
- 但不一定是人的角色，更可能是另一个专门做清理的 agent

## 五、上下文腐烂（Context Rot）：一个新的故障模式

> 本节来源：Jediah Katz & Stefan Heule ([Dynamic Context Discovery](https://cursor.com/en-US/blog/dynamic-context-discovery); [Continually Improving Our Agent Harness](https://cursor.com/en-US/blog/continually-improving-our-agent-harness))

Cursor 团队（Jediah Katz + Stefan Heule）识别出了一种新的故障模式：

> "While the agent can often self-correct, errors remain in context, wasting tokens and causing 'context rot,' where accumulated mistakes degrade the quality of the model's subsequent decisions."

三种形态：
1. **错误累积**：早期错误留在上下文里 → 后续决策被其污染
2. **工具描述过时**：MCP 服务器更新了工具，但 agent 用的是旧描述 → 幻觉调用
3. **Skills 漂移**：预加载的 Skills 与当前代码库不匹配 → 错误模式

**粗糙想法**：
- Agent 的"记忆"也需要 GC——不只是 token 层面的压缩，而是**语义层面**的清理
- 这和人类团队的"不要翻旧账"有点像——早期的错误如果已经修复，留在上下文里只会污染后续判断
- 目前没有好的"上下文健康度"指标

## 六、组织设计的新问题

> 本节来源：Jesse Vincent ([Larridin](https://larridin.com/blog/how-jesse-vincent-turned-code-writing-over-to-superpowers)); Fiona Fung ([Anthropic 博客](https://claude.com/blog/running-an-ai-native-engineering-org)); Rody Davis ([Google Cloud Blog](https://cloud.google.com/blog/topics/developers-practitioners/agent-factory-recap-100x-engineering-with-ai-agents-in-google-antigravity-20/)); Boris Cherny ([gentic.news](https://gentic.news/article/fable-5-claude-s-biggest-leap))

### 6.1 "管理 agent"和管理人有多像？

Jesse Vincent 说 agentic 开发"感觉更像管理人而不是写代码"。
Fiona Fung 说她的团队里经理必须先做 IC，通过交付来理解工程师的日常。
Mike Krieger 说 Fable 像"一个可以委托很多工作的队友"。

**粗糙想法**：
- 如果管理 agent 和管理人越来越像，那么"领导力"、"沟通能力"、"期望管理"这些软技能会不会变成硬技能？
- 或者说，会不会出现"agent 管理"这个新工种——专门负责写 CLAUDE.md、设计约束、调校 agent 行为？
- 已经有苗头：Jesse Vincent 的 Superpowers 里的"协调 agent"本质上就是在做 manager 的事

### 6.2 Agent 专业化分工

Rody Davis 预测 agent 之间将出现专业化分工：设计 agent、构建 agent、QA agent。Cursor 也预测规划 agent、编辑 agent、调试 agent 各司其职。

**粗糙想法**：
- Agent 的"组织架构设计"会成为一个工程问题——多少 agent？各自什么角色？怎么协作？怎么避免冲突？
- Jesse Vincent 的"角色解耦"（测试/实现/审查必须不同 agent）已经在实践了——这是一个 agent 组织设计的早期样本
- 这会不会催生一种新的建模语言——agent orchestration DSL？

### 6.3 写代码从"工作"变成"爱好"

Jesse Vincent 的极端断言：

> "Those who love hand-tuning algorithms will find that this is now a hobby, rather than work humans should be doing."

Fable 5 加速了这个趋势。Boris Cherny 也说 Fable "has judgment, taste, and dimensionality"——当模型有了品味和判断力，人类手写代码的空间在被压缩。

**粗糙想法**：
- "手写代码"会不会变成和"手写汇编"一样的地位？——有人做，但不是主流生产方式
- 这对计算机教育的冲击极大——如果编码不再是核心技能，学校该教什么？
- 可能答案：教"澄清需求"、"定义验收标准"、"审查 spec"、"管理 agent 团队"

## 七、还没有答案的开放问题

> 本节为综合归纳，开放问题来源于 Ryan Lopopolo, Fiona Fung, Erik Schluntz, Jesse Vincent, Willie Williams, Mike Taylor, Simon Willison 等人在各自材料中提出的未解决问题

以下问题在当前资料库里都没有明确答案，但多人在追问：

1. **Agent 产出的架构连贯性能维持多久？** Ryan Lopopolo 说"我们仍在学习，在一个完全由智能体生成的系统里，架构连贯性会如何随时间演化"

2. **人的判断力应该最先编码到哪里？** 不同人有不同的答案——Fiona Fung 说法律和安全，Erik Schluntz 说核心架构，Jesse Vincent 说 spec 和约束。但没有系统性的方法论。

3. **什么时候不应该用 Fable 5？** 目前的信号：涉及客户机密时（Mike Taylor）、不需要深度推理的简单任务（Willie Williams）、需要快速迭代的场景（Willie Williams）、控制面/编排层（mclayer）。但这远不是完整清单。

4. **Fable 5 的"人格"会随版本迭代保持稳定吗？** 如果 self-verification 是涌现的而非设计的，下一个版本可能就没有了。团队依赖它来验证代码的话，模型升级可能导致流程断裂。

5. **多个 Fable 5 agent 协作时会出现什么新行为？** 目前只有 Agent-to-agent review 的案例。如果让两个 Fable 5 agent 一起设计和实现一个系统，它们之间会发生什么？

6. **"代码库健康度"到底怎么测量？** Rody Davis 提出了这个问题但没给出测量方法。可能需要一套新的指标——不只是圈复杂度，还有 agent 可读性、agent 可导航性等。

7. **Agent 经验的持久化怎么做？** Simon Willison 的 $12 CSS 调试产生了一套工具链但没有保存。怎么把 agent 在探索中学到的东西存下来，让下次不用重新发明？

## 九、和 AWS AIDLC 的对比角度

> 本节为综合对比分析，AWS AIDLC 参考 `aidlc_reference/_raw_aws/`

AWS 的 AIDLC（`../_raw_aws/`）试图建立一套"正确的流程"——三阶段模型、14-Node AgentCore。它假设流程设计好了，agent 按流程走。

Fable 5 的信号指向一个不同的方向：**不是流程定义 agent，而是 agent 的能力在改写流程。**

- AWS 说"应该有质量门控" — Fable 5 说"我自己会验证，不需要你设门"
- AWS 说"自适应执行根据复杂度调整" — Fable 5 说"我会自己判断什么时候需要什么，你不一定能预测"

这两条线可能最后会汇合——但当前阶段，Fable 5 信号提示的是**自底向上的涌现**，而不是自顶向下的设计。
