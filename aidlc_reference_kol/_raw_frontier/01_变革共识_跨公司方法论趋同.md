## 一、变革的七个共识

> 本节为跨 7 人综合归纳。来源：Erik Schluntz ([YouTube](https://www.youtube.com/watch?v=78EYLieMpvc)); Fiona Fung ([Anthropic](https://claude.com/blog/running-an-ai-native-engineering-org)); Thariq Shihipar ([X](https://x.com/trq212/status/2073100352921215386)); Ryan Lopopolo ([OpenAI](https://openai.com/index/harness-engineering/)); Michael Bolin ([OpenAI](https://openai.com/index/unwinding-codex-agent-loop/)); Jediah Katz ([Cursor](https://cursor.com/en-US/blog/dynamic-context-discovery)); Rody Davis ([Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/agent-factory-recap-100x-engineering-with-ai-agents-in-google-antigravity-20/))

2026 年上半年，Anthropic、OpenAI、Cursor、Google 四家公司的工程团队几乎同时发声。虽然用词不同，但指向同一个方向：**软件工程的底层假设正在被改写**。

### 共识 1：瓶颈转移 — 从"写代码"到"验证"

| 旧瓶颈 | 新瓶颈 | 来源 |
|---|---|---|
| 写代码太慢 | **Verification** — 代码对不对？ | Fiona Fung (Anthropic) |
| 人手不够 | **Code Review** — 人类跟不上 AI 产出量 | Fiona Fung |
| 排期紧张 | **安全与信任边界** — 什么可以交给 AI？ | Fiona Fung |
| 模型能力不够 | **澄清未知项的能力** — 人是否想清楚了？ | Thariq Shihipar (Anthropic) |
| context window 太小 | **代码库健康度** — 混乱的代码让 agent 也乱写 | Rody Davis (Google) |

> 核心含义：工程团队的精力投向必须变——从"怎么写"转向"怎么验证对不对"。

### 共识 2：角色转变 — 从"写代码的人"到"设计环境的人"

这是最深层的变化。三家公司的表述惊人一致：

| 旧角色 | 新角色 | 来源 |
|---|---|---|
| 写代码 | **设计环境** — 工具、抽象、内部结构 | Ryan Lopopolo (OpenAI) |
| Debug | **澄清意图** — 把高层目标拆成小构件 | Ryan Lopopolo |
| Code Review | **构建反馈回路** — 让 agent 自行发现和修正错误 | Ryan Lopopolo |
| 程序员 | **PM** — 花 15-20 分钟帮 Claude 探索代码库、共写执行计划 | Erik Schluntz (Anthropic) |
| 固定角色（PM/工程师/设计师） | **角色模糊** — PM 写代码，工程师做设计 | Fiona Fung |
| 追求裸吞吐量 | **追求判断力** — 吞吐量模型覆盖了，人负责画边界 | Fiona Fung + Erik Schluntz |

> 核心含义：**"人类负责掌舵，智能体负责执行。"** (Ryan Lopopolo) 人的价值从"生产代码"转向"生产决策"。

### 共识 3：流程过时 — "服务于过去的流程，该杀了"

| 旧流程 | 新流程 | 来源 |
|---|---|---|
| 六个月路线图 | **JIT（即时规划）** — 原型 → 内测 → 迭代 | Fiona Fung |
| 设计文档争论 | **直接原型看效果** — "Build is cheap. Argument is expensive." | Fiona Fung |
| 找人问代码 | **先问 Claude**，再问"这个能自动化吗？" | Fiona Fung |
| 人类全覆盖 Review | **Trust but Verify** — Claude 管风格/bug/测试，人管法律/安全/品味 | Fiona Fung |
| 阻塞式合并门 | **极少阻塞门** — 修复成本低时，快速重试 > 无限期等待 | Ryan Lopopolo |

> 核心含义：流程不是为了存在而存在——当它服务的前提（工程带宽昂贵）不再成立时，流程本身也必须变。Fiona 的激进态度："任何人可以质疑任何流程，不合适就毙。"

### 共识 4：上下文范式转移 — 从"全部注入"到"按需发现"

| 旧范式（静态上下文） | 新范式（动态上下文） | 来源 |
|---|---|---|
| 启动时一次性注入所有信息 | Agent 运行时按需拉取 | Jediah Katz (Cursor) |
| 超大 AGENTS.md 百科全书 | ~100 行目录页，真实知识存 docs/ | Ryan Lopopolo |
| 全部 MCP 工具描述注入 | 仅名称注入，schema 按需加载（token -46.9%） | Jediah Katz |
| 预置所有 Skills 指令 | Skills 名称在静态，完整指令动态加载 | Jediah Katz + Anthropic |
| 截断长输出 | 写入文件，agent 用 tail/grep 按需读取 | Jediah Katz |

> 核心含义：**"少即是多"在 2026 年成立。** 模型已经能从"我给你什么你看什么"进化到"我知道我还需要什么，我自己去找"。

### 共识 5："地图 ≠ 疆域" — 信息差的制度化应对

Thariq Shihipar 提出的核心隐喻被多篇文章交叉引用：

| 地图（你给 Claude 的） | 疆域（真正发生工作的地方） |
|---|---|
| 提示词、Skill、上下文 | 代码库、现实世界约束 |

**地图与疆域的差距 = 未知项（Unknowns）。** Claude 遇到未知项时只能猜测你的意图。

> **Fable 5 是第一个让"澄清未知项的能力"成为工作质量瓶颈的模型。** (Thariq)

应对方法不再靠"更好的提示词工程"——而是靠一套制度化的流程：盲点扫描 → 头脑风暴 → 反问 → 参考资料 → 实现计划 → 实现笔记 → 测验。

> 核心含义：**"减少并提前规划未知项，就是智能体式编程的核心能力。"** 这与传统编程的核心能力（算法、系统设计）已经是完全不同的技能树。

### 共识 6：约束不是束缚，是杠杆

| 旧观念 | 新观念 | 来源 |
|---|---|---|
| 规则越多越束缚人 | 规则编码后立即、统一作用到所有地方 → **倍增器** | Ryan Lopopolo |
| 让 agent 自由发挥 | **边界严格 + 内部自由** — 在边界处强约束，边界内给自由度 | Ryan Lopopolo |
| 人类逐行 review 保证质量 | **linter + 结构测试 + 自动化规则** — 规则本身由 agent 生成 | Ryan Lopopolo |
| Leaf node 可以烂一点 | 核心架构人类深度保护，叶子节点接受技术债——边界动态移动 | Erik Schluntz |
| 架构约束在百人团队才需要 | **对编码 agent 是早期前提** — 没有约束速度马上降 | Ryan Lopopolo |

> 核心含义：**"在传统人工团队里显得迂腐的约束，有了智能体反而成了倍增器。"** 规则一旦写成代码，就能瞬间应用到所有 agent 产出。人的品味通过规则放大，而不是通过逐行 review。

### 共识 7：知识管理重构 — "不在仓库里的，对 agent 不存在"

| 旧做法 | 新做法 | 来源 |
|---|---|---|
| 知识在 Slack/Google Docs/人脑里 | **一切推入仓库** — 版本化、可搜索、agent 可见 | Ryan Lopopolo |
| 文档是给人看的 | **文档是给 agent 看的** — "给地图，不给一千页手册" | Ryan Lopopolo |
| 文档写了就忘 | **自动化治理** — linter + CI + doc-gardening agent 持续维护 | Ryan Lopopolo |
| 技术债靠人工周五清理 | **持续 GC** — 后台 agent 定期扫描、自动发起小重构 PR | Ryan Lopopolo |

## 三、变革的烈度：这些共识有多"猛"？

> 本节为作者综合分析，烈度分级基于各人物对其主张的实施程度（已停止旧做法 vs 预测将停止）

### 温和的变革
- 上下文管理从静态到动态 → 增量改进，可渐进采用
- Skills 作为上下文作弊条 → 不改变现有流程，只是提效

### 中等的变革
- JIT 规划替代六个月路线图 → 改变了团队节奏和沟通方式
- Trust but Verify review → 改变了人的日常工作内容

### 激进的变革
- **不手写代码**（Ryan Lopopolo 的团队原则）→ 直接禁止了工程师最基本的日常行为
- **Agent 自我审查**（人类不再审查 PR）→ 去掉了软件工程最后一道人工防线
- **"杀掉不再服务的流程"**（Fiona Fung 的铁律）→ 任何流程都可能被任何人随时毙掉
- **"Be unreasonable"**（Thariq Shihipar）→ 不要预设取舍，逼现实证明它真的会逼你取舍
- **合并哲学反转**（Ryan Lopopolo）→ flaky 测试不阻塞，快速重试 > 无限期等待 → 传统 QA 理念的彻底颠覆

## 四、与 AWS AIDLC 的对比

> 本节为作者对比分析，AWS AIDLC 参考 `aidlc_reference/_raw_aws/`

AWS 的 AI-DLC（`../_raw_aws/`）是从**方法论框架**的角度定义变革：三阶段模型、14-Node AgentCore、自适应执行。它试图建立一个"正确"的流程。

而 Frontier 材料揭示的变革是从**人的体验**出发的：
- AWS 说"应该有这些阶段" — 顶层设计
- Frontier 说"我们试过了，这些旧流程死了，这些新做法管用" — 实践验证

两者互补。AWS 提供框架，Frontier 提供"为什么要变"和"变了之后实际怎么样"的证据。
