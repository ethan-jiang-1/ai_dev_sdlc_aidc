最近，“Loop Engineering”（循环工程）这个词在技术圈突然热了起来。

吴恩达（Andrew Ng）在 X 中提到，这个概念之所以走红，和 Claude Code 创作者 Boris Cherny、OpenClaw 创作者 Peter Steinberger 在社交媒体上的讨论有关。但在吴恩达看来，它不只是一个新 buzzword，而是 AI Agent 能够长时间迭代、持续构建软件的关键方法。

更重要的是，他把自己做 0 到 1 产品时依赖的三个核心循环讲得非常清楚：**Agentic coding loop、Developer feedback loop、External feedback loop**。

这篇文章就基于吴恩达原文，做一次核心内容转述，并结合中文开发者、产品团队的语境聊聊它的启发。

## 第一个循环：Agentic Coding Loop，让 AI 自己写、测、改

吴恩达说，第一个循环是 **Agentic coding loop**。

简单说，就是给 AI Agent 一个产品规格说明，必要时再给它一组 evals，也就是用于衡量表现的数据集。然后让 AI Agent：

-   写代码；
    
-   测试自己的工作；
    
-   根据测试结果继续迭代；
    
-   直到代码没有明显 bug，并且满足规格要求。
    

这个“闭环”的思路在去年底开始快速发展。吴恩达认为，它已经成为让 coding agent 能够在没有人类频繁干预的情况下，长时间高效工作的游戏规则改变者。

他举了一个很生活化的例子：周末，他在给女儿做一个练习打字的应用。过程中，coding agent 可以轻松工作一个小时左右，还会自己用浏览器多次检查构建出来的结果，然后再回来向他汇报，中间不需要他介入。

这和过去很多人对 AI 编程工具的印象不一样。过去我们更像是在“让 AI 写一段代码”，然后人来检查、复制、调试。现在的变化是，AI 不只是生成代码，而是进入一个持续执行的工程循环：构建、验证、修复、再构建。

我的理解是，这正是 AI 编程从“代码补全工具”走向“工程协作者”的分水岭。

## 这个循环跑得很快：几分钟就能产生一个新版本

吴恩达强调，工程循环的执行速度非常快。每隔几分钟，coding agent 就可能构建并测试一个新版本的软件。

他也提到，自己经常听到开发者在探索新的方法，去设计更有效的工程循环。换句话说，这仍然是一个非常活跃的发明领域。

这点对中文开发者尤其有启发：未来竞争力不只是“会不会用 AI 写代码”，而是你能不能设计一个高质量的循环，让 AI 在里面稳定地产生有效进展。

比如：

-   规格说明是否足够清楚；
    
-   测试是否能覆盖关键路径；
    
-   evals 是否能衡量真正重要的结果；
    
-   Agent 遇到问题时是否有明确的修复方向。
    

AI 变强之后，工程师的价值没有消失，而是更多转移到了“设计循环”和“定义标准”上。

## 第二个循环：Developer Feedback Loop，人类从 QA 升级为产品判断者

第二个循环是 **Developer feedback loop**，也就是开发者反馈循环。

在这个循环里，开发者查看当前产品，然后引导 coding agent 继续改进。

吴恩达说，去年很多开发者，包括他自己，都还在给 coding agent 扮演 QA 的角色：手动找 bug，然后让 AI 修。但随着 coding agent 越来越能测试自己的代码，人类在这部分花的时间已经明显减少。

这释放了开发者，让他们可以做更高层次的产品决策，比如：

-   应该提供哪些关键功能；
    
-   UI 哪些地方需要改进；
    
-   用户流程是否合理；
    
-   产品体验是否符合预期。
    

这个循环的节奏比工程循环慢一些，通常是几十分钟到几小时。开发者可能隔一段时间看一次产品，然后给出反馈。

吴恩达在打字应用的例子里，也不断调整自己的想法：视觉设计要怎么做，女儿学习过程中可以解锁哪些猫咪服装——因为她喜欢猫，以及成年人如何登录并引导孩子学习的用户流程。

这里很有意思。AI 可以快速实现，但“想要什么”仍然经常是在看到实现之后才变清楚的。

很多产品不是一开始就有完美规格，而是在不断看到版本、不断修改判断中成形的。

## 人类的关键价值，不只是“品味”，而是“上下文优势”

吴恩达在这里提出了一个很重要的观点。

很多人会把人类在产品中的贡献称为 “taste”，也就是品味。但他更愿意把它理解为：**人类相对于当前 AI 系统拥有上下文优势**。

因为在绝大多数他参与的产品中，人类对用户、场景、产品运行环境知道得更多。AI 也许能总结材料、分析数据、提出建议，但它并不天然拥有完整上下文。

这也解释了为什么这一环不能完全自动化：只要人类知道一些 AI 不知道的信息，就需要 human-in-the-loop，把这些知识注入系统。

这句话很值得产品经理、工程师和创业者反复咀嚼。

所谓“人机协作”，不是人类站在旁边按按钮，而是人类把自己掌握的用户理解、业务限制、审美偏好、场景细节持续注入系统。AI 越能执行，人类越要负责方向。

## 第三个循环：External Feedback Loop，把真实用户带进来

第三个循环是 **External feedback loop**，外部反馈循环。

它包括很多方式，比如：

-   找几个朋友体验并反馈；
    
-   发布给 alpha 测试用户；
    
-   上线到生产环境做 A/B 测试。
    

这些方法通常比较慢，很少少于几个小时，有时要几天甚至几周。

但这类反馈非常关键，因为它会反过来影响开发者的产品愿景；产品愿景再影响详细规格；详细规格再驱动 coding agent 去执行。

也就是说，三个循环并不是孤立的。

外部反馈帮助你修正方向，开发者反馈把方向变成更清晰的规格，工程循环则让 AI 快速把规格实现出来。

如果只追求第一个循环，可能会很快做出一堆没人要的功能；如果只等外部反馈，又会丧失 AI 加速带来的迭代优势。真正的能力，是让三个循环以合适的节奏协同起来。

## AI 让工程师开始承担一部分产品经理角色

吴恩达最后提到，随着 coding agent 加速软件开发，越来越多工程师开始扮演一部分产品管理角色。

对很多正在成长为这个角色的工程师来说，最难的部分不是让 AI 写代码，而是塑造产品愿景，并在“继续构建”和“获取用户反馈”之间找到平衡。

他强调：两件事都很重要。

这也是我认为这篇文章最有价值的地方。AI 编程工具的普及，不只是让工程师效率提升，而是在重塑团队分工。

当实现成本下降，真正稀缺的东西会变成：

-   对用户的理解；
    
-   对问题的判断；
    
-   对产品方向的取舍；
    
-   把模糊愿景转成可执行规格的能力；
    
-   设计有效反馈循环的能力。
    

## 给团队的启发：别只学工具，要学会设计循环

如果把吴恩达这篇文章压缩成一句话，我会概括为：

> AI 时代的软件开发，不是一次性把需求丢给模型，而是设计一组能持续变好的循环。

对个人开发者来说，可以先从一个小项目开始，刻意练习三件事：

-   写清楚规格，让 AI 能独立构建和测试；
    
-   定期查看版本，把反馈从“修 bug”提升到“改体验、改方向”；
    
-   尽早让真实用户或朋友试用，不要只在本地和 AI 自嗨。
    

对团队来说，也许更应该问：我们的 AI Agent 有没有测试闭环？开发者反馈有没有沉淀成规格？真实用户反馈有没有及时进入下一轮产品判断？

Loop Engineering 之所以重要，不是因为它是新名词，而是因为它提醒我们：当 AI 越来越会执行，真正决定结果的，是人类如何组织迭代。
