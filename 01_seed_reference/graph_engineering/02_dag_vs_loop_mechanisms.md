# 02. 核心机制拆解：DAG 状态机、两层自愈与架构设计

---

## 1. 为什么必须抛弃“多 Agent 自由聊天（Chat-based）”？

在 Multi-Agent 发展初期（如 AutoGen、ChatDev 早期原型），常见做法是为不同角色（PM、Coder、Reviewer）设定系统提示词，让它们在同一个聊天群内自由发言，通过对话推进开发。

在真实的工业 AI Coding 场景中，这种模式被证明是**无法商用的反模式**：
- **Token 爆炸与算力耗尽**：每次角色发言都必须携带群聊的完整全量历史，导致 Token 消耗随轮次呈二次方甚至指数级飙升；
- **客套与注意力漂移**：大模型角色之间充斥着大量礼貌性客套（“好的，我同意你的观点”、“非常棒的建议”），严重稀释关键业务上下文；
- **无收敛性与死循环**：一旦 Reviewer 与 Coder 陷入细节分歧，极易形成无限循环反驳，缺乏强制中断与终局裁决机制；
- **缺乏确定性产物验证**：自由对话中产生的是松散文本，而非标准化的 AST、Diff 文件或测试日志。

### 替代方案：DAG 状态机（DAG State Machine）
- 不靠角色对话推进，而是依靠**明确的 DAG 状态机**推进；
- 节点之间只交接**强类型工件（Artifacts）**（如需求规范 JSON、代码补丁 Patch、单元测试报告）；
- 只有当前驱节点的产物通过前置检查时，后续节点才被调度触发。

## 2. 两层自愈体系（Two-tier Self-Healing）

这是 **Loop Engineering 与 Graph Engineering 最核心的工程结合点**：

```text
                     [任务启动: Planner 生成 DAG]
                                 │
                                 ▼
                     ┌───────────────────────┐
                     │ 静态合法性校验 (Lint)  │ ◄───────┐
                     └───────────┬───────────┘         │
                                 │ Pass                │
                                 ▼                     │ L2 拓扑自愈:
                       [执行 Worker 节点]               │ 编排者修改 DAG 图
                                 │                     │
                ┌────────────────┴────────────────┐    │
                ▼                                 ▼    │
     ┌──────────────────────┐         ┌────────────────┴──────┐
     │   本地有限退避重试    │ ◄──┐    │ Worker 无法修复 (FAIL) │
     │  (L1 局部自愈: Loop) │    │    └───────────────────────┘
     └──────────┬───────────┘    │
                │ Retry <= N     │
                └─── 失败 ───────┘
                │
                ▼ Pass
       [更新状态机，流转下一节点]
```

### L1 层：Worker 节点内局部自愈（Loop Engineering）
- 目标：处理语法错误、临时网络抖动、单文件 import 缺失等局部问题；
- 机制：
  - **有限重试上限（Hard Cap）**：限制最多重试 3~5 次；
  - **退避机制（Backoff）**：在重试中逐步增加约束或精简上下文；
  - **机器判据闸门（Machine Gates）**：运行 `pytest`、`tsc` 或 `linter`，根据真实终端输出决定是否重试。

### L2 层：编排者全局拓扑自愈（Graph Engineering）
- 目标：处理架构设计冲突、依赖死锁、底层设计假设被推翻等根本性错误；
- 机制：
  - 当 Worker 耗尽局部重试预算后，向上抛出带有错误上下文的异常；
  - 编排者（Planner/Orchestrator）介入，识别出原有任务分解的缺陷；
  - **动态修改 DAG 图拓扑（Dynamic DAG Re-planning）**：插入排错节点、拆解高风险任务、或回退到先前的 Checkpoint 并重新规划分支。

## 3. 核心架构抉择：Session 内 Tool vs Session 外 外部系统

在系统实现上，目前存在两种截然不同的架构路线：

| 维度 | 路线 A：Session 内 Tool 驱动 | 路线 B：Session 外 外部状态机驱动 |
|---|---|---|
| **基本形态** | 一个主智能体在自身 Session 内调用 `generate_dag`、`dispatch_task` 等 Tool | 独立的外部编排引擎（Python/Go），智能体只是其调用的无状态无记忆算子 |
| **上下文管理** | 单一主 Session 上下文，主 Agent 拥有全局全局视野 | 严格隔离，每个 Worker 仅在执行自己节点时拥有最小独立上下文 |
| **稳定性与确定性** | 较低。主 Agent 会随子任务增加出现 Context Rot，可能忘记初始计划 | 极高。状态机由确定性代码硬约束，不受模型注意力衰减影响 |
| **灵活性与自适应** | 极高。模型可随时随地根据感知调用工具调整计划 | 较低。必须在预定义的状态转移图与重规划接口内受限流转 |
| **典型代表** | Claude Code / Agentic CLI 的内置多步规划工具 | Temporal、LangGraph、Raven A2A、工业级 CI/CD Agent 平台 |
| **结论趋势** | 适合快速实验、单人单机探索 | **中大型工程项目必走向路线 B（Session 外状态机硬治理）** |

## 4. 业务语义：DAG 即组织结构与岗位交接

- 软件工程本质上是人的协作网络，而 DAG 是组织架构在机器侧的同构投影：
  - **Node（节点）= 专职岗位（Role Responsibility）**：架构师、前端开发、后端开发、安全合规审计员、QA；
  - **Edge（边）= 交付物标准与审批流（Handoff Contract & PR Review）**：接口定义 Swagger、功能测试报告、合规签批单；
  - **Cycle（回路）= 返工与打回机制（Code Review Rejection）**。
- Graph Engineering 的终极目标不是让模型学会写图，而是**将成熟的软件工程治理（敏捷看板、CI/CD、代码审查、门禁）编译为可运行的 AI 状态机**。
