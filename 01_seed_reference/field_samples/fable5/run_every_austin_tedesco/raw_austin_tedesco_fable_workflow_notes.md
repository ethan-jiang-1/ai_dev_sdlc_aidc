## 这份材料补的是什么

Austin 目录原来已经有一篇 Every 长文归档，但那篇其实是团队混合文章。

这份 raw 是把 Austin 自己在两篇 Every 文里的 Fable 5 方法抽成专属笔记，便于之后单独看这个人到底怎么用 Fable。

## Austin 的核心判断

> “Fable 5 demands a very different way of approaching knowledge work.”

这句话说明在 Austin 看来，Fable 5 改变的不是某个 prompt 技巧，而是知识工作的组织方式。

## 什么任务值得开 Fable

Austin 把 Fable 留给：

- 大任务
- 复杂任务
- 可委托任务
- 值得为高 token 成本买单的任务

Every 文里给出的具体表述包括：

- `rocket launcher` projects
- 能跑 `four-plus hours`
- 可以隔夜推进的增长实验
- 从零搭建 go-to-market strategy

## 什么任务不值得开 Fable

Austin 没有把 Fable 当默认模型。

他依然保留：

- `Codex` 处理会后 action items
- `Codex + Spiral MCP` 处理社交文案、内部策略文档和多数当天任务

这说明他的工作流不是“Fable 替代一切”，而是：

- Fable 接长任务
- 其他 agent 接快任务

## 他怎么给 Fable 喂任务

Every 的总结里有一条很关键：

> Tasks that are good candidates for Fable 5 have four qualities: You’re able to give the model organized and deep context, a well-defined goal, and a clear definition of what good or done looks like, and the importance of the task justifies the cost.

这几乎可以看作 Austin 的 Fable 使用检查单：

- organized and deep context
- well-defined goal
- clear definition of done
- task value high enough to justify cost

## 工作流框架

Austin 常用：

- `compound engineering`
- `LFG flow`

具体步骤是：

- brainstorm
- plan
- work
- review
- repeat

这让 Austin 这条线特别值钱，因为它已经接到了一个可迁移的工作流壳子，而不是停在感受层。
